# 2. Critical correction to v8.1.2

There is one particularly important problem that must be fixed before using the previous plugin.

The current QuickDate implementation uses the `followers` table for both:

```text
ordinary follow
        AND
friend request / friendship
```

The actual QuickDate code confirms this. `Wo_RegisterFollow()` inserts:

```text
following_id
follower_id
active
created_at
```

into `followers`; `active=0` represents a pending request and `active=1` represents an active relationship. 

QuickDate's `add_friend()` ultimately calls `Wo_RegisterFollow()`, while its accept/reject routines operate on the same `followers` row. 

Therefore, this is **not safe**:

```php
if ($friendship_is_connected) {
    $active = 1;
} elseif ($friendship_is_pending) {
    $active = 0;
} else {
    $active = $ordinary_follow;
}
```

because an ordinary follow can already occupy the same directional row.

### Example

A already follows B:

```text
followers
following_id = B
follower_id  = A
active       = 1
```

A subsequently sends B a QuickDate/BuddyBoss friend request.

Changing the existing row to:

```text
active = 0
```

would turn the ordinary follow into a friend request.

Likewise, deleting the row when a friend request is withdrawn could accidentally delete a legitimate ordinary follow.

**Therefore v8.1.3 must preserve the pre-existing ordinary follow state separately from the QuickDate friend-request projection.**

This is the most important additional correction to the previous GitHub implementation.

# 6. Blocking becomes the dominant operation

Blocking should be treated differently from ordinary relationship removal.

When A blocks B:

```text
1. BuddyBoss creates block
2. BuddyBoss connection A↔B is removed
3. BuddyBoss A→B follow is removed
4. BuddyBoss B→A follow is removed
5. Streams A→B follow removed
6. Streams B→A follow removed
7. Streams A→B block created
8. Socials A→B follow removed
9. Socials B→A follow removed
10. Socials friend projection removed
11. Socials A→B block created
```

The previous GitHub response correctly identified blocking as a dominant/destructive relationship state. ([GitHub][3])

### Unblocking

Unblocking does **only this**:

```text
BuddyBoss block removed
Streams block removed
Socials block removed
```

It does **not** restore:

* friendship
* previous follow
* previous friend request

This prevents stale relationships from silently reappearing.

# 9. Idempotency

Every external request should carry:

```text
event_uuid
timestamp
origin
operation
actor
target
signature
```

For example:

```json
{
  "event_uuid": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "origin": "streams",
  "operation": "follow",
  "actor": 123,
  "target": 456,
  "timestamp": 1790123456
}
```

The signature should be:

```text
HMAC-SHA256(
    timestamp + "." + raw_json_body,
    BUZZ_SSO_SECRET
)
```

The WordPress endpoint verifies:

1. secret exists;
2. timestamp is within the permitted window;
3. event UUID is valid;
4. event UUID has not already been processed;
5. actor and target are valid mapped users;
6. operation is permitted;
7. pair lock is acquired.

This is safer than placing WordPress usernames/passwords inside the external platforms.

# 16. Required Streams `Wo_IsFollowRequested()` change

There is a subtle problem with the requested modification.

The current function merely detects an `active=0` row. 

The requested behavior is to automatically accept it.

However, simply putting:

```php
Wo_AcceptFollowRequest(...)
```

inside:

```php
Wo_IsFollowRequested()
```

would create recursion:

```text
Wo_IsFollowRequested()
    ↓
Wo_AcceptFollowRequest()
    ↓
Wo_IsFollowRequested()
    ↓
Wo_AcceptFollowRequest()
    ↓
...
```

The GitHub response correctly identified this danger. ([GitHub][3])

### Correct implementation

Do **not** call `Wo_AcceptFollowRequest()` from `Wo_IsFollowRequested()`.

Instead, change `Wo_IsFollowRequested()` so that it directly promotes the pending row:

```php
function Wo_IsFollowRequested($following_id = 0, $follower_id = 0)
{
    global $conn;

    if (!isset($following_id) || empty($following_id) || !is_numeric($following_id) || $following_id < 1) {
        return false;
    }

    if (!isset($follower_id) || empty($follower_id) || !is_numeric($follower_id) || $follower_id < 1) {
        return false;
    }

    $following_id = Secure($following_id);
    $follower_id  = Secure($follower_id);

    $query = "
        SELECT `id`
        FROM `followers`
        WHERE `follower_id` = {$following_id}
          AND `following_id` = {$follower_id}
          AND `active` = '0'
        LIMIT 1
    ";

    $sql_query = mysqli_query($conn, $query);

    if (!$sql_query) {
        return false;
    }

    if (mysqli_num_rows($sql_query) === 0) {
        return false;
    }

    /*
     * Streams has Friends disabled.
     *
     * Therefore a pending follow request is automatically converted
     * into an active follow. Do this directly rather than calling
     * Wo_AcceptFollowRequest(), which itself calls this function.
     */
    $update = mysqli_query(
        $conn,
        "
        UPDATE `followers`
        SET `active` = '1'
        WHERE `follower_id` = {$following_id}
          AND `following_id` = {$follower_id}
          AND `active` = '0'
        LIMIT 1
        "
    );

    if (!$update) {
        return false;
    }

    return true;
}
```

But there is an additional required change.

`Wo_AcceptFollowRequest()` currently expects `Wo_IsFollowRequested()` to leave the request pending and then performs its own `UPDATE`. 

Therefore, after implementing automatic acceptance, **`Wo_AcceptFollowRequest()` must no longer be used as the normal acceptance path for Streams**.

Its callers should either be removed from the active Streams UI or converted into a simple idempotent:

```text
if already active → success
```

operation.

This is preferable because Streams should no longer have a meaningful pending-follow state under the new architecture.

# 30. `created_at` correction

The actual Streams database uses:

```text
created_at = UNIX timestamp
```

as demonstrated by the current `Wo_RegisterFollow()` implementation. 

Therefore the synchronization code must **inspect the actual column type before deciding whether to insert**:

```text
time()
```

or:

```text
Y-m-d H:i:s
```

The generic v8.1.2 logic that tries `created_at` versus `time` based only on column name is directionally useful, but the value type should also be verified.

This was another valid point in the GitHub review. ([GitHub][3])

## 33. Bottom line

The **concept** of the previous implementation was sound, but I would not install v8.1.2 as-is.

The important corrections are:

1. **BuddyBoss remains the source of truth.**
2. **Streams Friends stays disabled.**
3. **Streams follow ≠ friendship.**
4. **QuickDate friend ≠ follow.**
5. **QuickDate's shared `followers` table must not be blindly rewritten when friend state changes.**
6. **An existing QuickDate follow must survive a pending friend request and an unfriend operation.**
7. **Blocking removes relationship state and dominates other relationships.**
8. **Unblocking never restores old relationships.**
9. **`Wo_IsFollowRequested()` must not recursively call `Wo_AcceptFollowRequest()`.**
10. **Streams pending follows should be automatically promoted to active follows because the Streams Friends system is disabled.**
11. **External actions must enter BuddyBoss through one authenticated connection-management control plane.**
12. **BuddyBoss-originating events must synchronize through hooks, not HTTP calls back into WordPress.**
13. **Pair locking and idempotent event IDs are retained.**
14. **Operational logging stays in `/data/logs`.**
15. **A small recovery queue is justified; a second permanent relationship authority is not.**
16. **The existing BuddyBoss connection restrictions must not be bypassed by the integration endpoint.**
17. **The old v8.1.x MU-plugin copies must not remain active.**

The actual repository code supports the critical lifecycle assumptions above, particularly the BuddyBoss hooks and the QuickDate/WoWonder `followers` semantics. ([GitHub][1])

**I would therefore designate this architecture as `BZJ Connections Sync v8.2.0`, rather than applying another incremental v8.1.2 patch.**

One caution before treating any generated PHP as production-ready: the repository-visible QuickDate schema is sufficiently clear about its `followers` behavior, but the exact deployed database schema should still be inspected on the live database before a final migration that depends on additional QuickDate tables/columns. The current source establishes the `followers` behavior; it does not justify inventing a separate QuickDate friendship table.
