## EXECUTIVE SUMMARY

The synchronization integration establishes **BuddyBoss as the canonical authority** for all user relationship states (connections, follows, blocks) across the Buzzjuice ecosystem. Actions may originate on any platform, but all canonical state resides in WordPress/BuddyBoss, with Streams (WoWonder) and Socials (QuickDate) maintained as synchronized projections.

**Core Principle:**
> An action may originate anywhere, but the relationship ledger belongs exclusively to BuddyBoss.

## REVISED INTEGRATION PROPOSAL v7.1

### Architectural Corrections Incorporated

#### **1. Streams (WoWonder) Constraint**
- **Friends system is DISABLED** → only Follow and Block systems are active
- BuddyBoss connections do NOT create Streams follows or friends
- BuddyBoss connections sync ONLY to Socials (QuickDate) as friend relationships
- Streams relationships use: `following_id` (recipient), `follower_id` (initiator), `active` (1=confirmed, 0=pending)
- Streams blocks use: `blocker` and `blocked` columns in `Wo_Blocks` or `Wo_BlockedUsers` table

#### **2. Socials (QuickDate) Correction**
- "Add Friend" functionality uses the followers infrastructure (same table as Follow)
- Friend request: `followers` row with `active = 0` (pending)
- Accepted friend: `followers` row with `active = 1` (confirmed)
- Blocks table: `blocks` with `user_id` (blocker) and `block_userid` (blocked)
- The sync layer must distinguish **intent**: connection requests ≠ follow requests

#### **3. Canonical Relationship Dimensions**
Each user pair (A ↔ B) maintains three independent relationship dimensions:

| Dimension | States | BuddyBoss Table | Streams Table | Socials Table |
|-----------|--------|-----------------|---------------|---------------|
| **Connection** | none → requested → connected | `wp_bp_friends_friendships` | *N/A* (disabled) | `followers` (active 0→1) |
| **Follow** | not_following → following | `wp_bp_activity` | `following` or `followers` | `followers` |
| **Block** | not_blocked → blocked | `wp_bp_user_blocklists` | `Wo_Blocks` | `blocks` |

## REVISED SYNC FLOWS v7.1

### SECTION A: BuddyBoss → Streams & Socials (Source of Truth Propagation)

| # | Trigger Event | BuddyBoss Hook | BuddyBoss State | Streams Action | Socials Action |
|---|---|---|---|---|---|
| **A1** | User A sends connection request to User B | `friends_friendship_requested` | Request recorded (`is_confirmed = 0`) | *None* | Insert pending friend: `followers(following_id=B, follower_id=A, active=0)` |
| **A2** | User A/B withdraws/rejects request | `friends_friendship_withdrawn` or `friends_friendship_rejected` | Request deleted | *None* | Delete pending row from followers |
| **A3** | User B accepts connection request | `friends_friendship_accepted` | Connection confirmed (`is_confirmed = 1`) | *None* | Update followers: `active = 1` |
| **A4** | User A/B removes connection | `friends_friendship_deleted` | Connection deleted | *None* | Delete confirmed friend row from followers |
| **A5** | User A blocks User B | `bp_moderation_block_created` | Block created + **Auto-unfriend** (if connected) + **Remove follows (both directions)** | Block via `Wo_RegisterBlock(A, B)` + Delete follows via `Wo_DeleteFollow()` | Block: insert `blocks(user_id=A, block_userid=B)` + Delete friend/follow rows |
| **A6** | User A unblocks User B | `bp_moderation_block_removed` | Block deleted | Unblock via `Wo_RemoveBlock(A, B)` | Unblock: delete from blocks table |
| **A7** | User A follows User B | `bp_follow_start_following` | Follow recorded in activity stream | Follow via `Wo_RegisterFollow(B, A)` | Follow: insert/update `followers(following_id=B, follower_id=A, active=1)` |
| **A8** | User A unfollows User B | `bp_follow_stop_following` | Follow deleted from activity stream | Unfollow via `Wo_DeleteFollow(A, B)` | Unfollow: delete from followers |

### SECTION B: Streams → BuddyBoss & Socials (External Action Sync)

| # | Trigger Event | Streams Function | Method | BuddyBoss Action | Socials Action |
|---|---|---|---|---|---|
| **B1** | User A follows User B | `Wo_RegisterFollow()` | REST API → bzj-connections-sync.php | Query canonical ledger; if not following, call `bp_follow_start_following()` | Sync to Socials followers if not present |
| **B2** | User A unfollows User B | `Wo_DeleteFollow()` | REST API → bzj-connections-sync.php | Query canonical ledger; if following, call `bp_follow_stop_following()` | Sync deletion to Socials followers |
| **B3** | User A blocks User B | `Wo_RegisterBlock()` | REST API → bzj-connections-sync.php | Query canonical ledger; if not blocked, call `bp_moderation_block_created()`; **Auto-unfriend if connected** | Sync block to Socials blocks table; remove friend/follow rows |
| **B4** | User A unblocks User B | `Wo_RemoveBlock()` | REST API → bzj-connections-sync.php | Query canonical ledger; if blocked, call `bp_moderation_block_removed()` | Sync unblock to Socials blocks table |

### SECTION C: Socials → BuddyBoss & Streams (External Action Sync)

| # | Trigger Event | Socials Function | Method | BuddyBoss Action | Streams Action |
|---|---|---|---|---|---|
| **C1** | User A sends add-friend request to User B | `add_friend()` in profile.php | REST API → bzj-connections-sync.php | Query canonical ledger; if not connection-requested, call `friends_add_friend()` | *None* (friends disabled) |
| **C2** | User A/B declines add-friend request | `disapprove_friend_request()` | REST API → bzj-connections-sync.php | Query canonical ledger; if connection-requested, delete via friendship removal | *None* |
| **C3** | User B accepts add-friend request | `approve_friend_request()` | REST API → bzj-connections-sync.php | Query canonical ledger; if connection-requested, call `friends_accept_friendship()` | *None* |
| **C4** | User A/B unfriends | `add_friend()` (unfriend branch) | REST API → bzj-connections-sync.php | Query canonical ledger; if connected, call `friends_remove_friend()` | *None* |
| **C5** | User A blocks User B | `block()` in useractions.php | REST API → bzj-connections-sync.php | Query canonical ledger; if not blocked, call `bp_moderation_block_created()`; **Auto-unfriend if connected** | Block in Streams via `Wo_RegisterBlock()` |
| **C6** | User A unblocks User B | `unblock()` in useractions.php | REST API → bzj-connections-sync.php | Query canonical ledger; if blocked, call `bp_moderation_block_removed()` | Unblock from Streams via `Wo_RemoveBlock()` |
| **C7** | User A follows User B | Socials follow mechanism | REST API → bzj-connections-sync.php | Query canonical ledger; if not following, call `bp_follow_start_following()` | Sync to Streams via `Wo_RegisterFollow()` |
| **C8** | User A stops following User B | Socials unfollow mechanism | REST API → bzj-connections-sync.php | Query canonical ledger; if following, call `bp_follow_stop_following()` | Sync deletion from Streams via `Wo_DeleteFollow()` |

### Phase 2: REST API Endpoint Design

#### **2.1 Endpoint Structure**

**Base URL:** `/wp-json/bzj/v6/connection-management`

**Authentication:** 
- Uses WordPress nonce + secret validation
- Streams/Socials include `X-BZJ-Signature` header (HMAC-SHA256 of request body + secret)
- Secret stored in `.env` as `BUZZ_SYNC_SECRET`

**Endpoint Specifications:**

##### **POST /wp-json/bzj/v6/connection-management/follow**
```json
{
  "action": "start_following",
  "user_id_a": 123,
  "user_id_b": 456,
  "origin_platform": "streams",
  "timestamp": 1726492800
}
```
- Validates both users exist in WordPress
- Checks canonical ledger to avoid duplicate follows
- Calls `bp_follow_start_following()` if not already following
- Syncs to other platform as needed
- Returns: `{ "status": 200, "message": "Follow created", "ledger_state": {...} }`

##### **POST /wp-json/bzj/v6/connection-management/unfollow**
```json
{
  "action": "stop_following",
  "user_id_a": 123,
  "user_id_b": 456,
  "origin_platform": "socials",
  "timestamp": 1726492800
}
```
- Validates follow exists in canonical ledger
- Calls `bp_follow_stop_following()` if currently following
- Syncs deletion to other platform
- Returns: `{ "status": 200, "message": "Follow removed", "ledger_state": {...} }`

##### **POST /wp-json/bzj/v6/connection-management/block**
```json
{
  "action": "create_block",
  "user_id_a": 123,
  "user_id_b": 456,
  "origin_platform": "socials",
  "timestamp": 1726492800
}
```
- Validates block doesn't already exist
- Calls `bp_moderation_block_created()` in WordPress
- **Auto-unfriend** if A and B are connected
- **Remove all follows** between A and B (both directions)
- Syncs block to other platform
- Returns: `{ "status": 200, "message": "Block created", "unfriended": true, "follows_removed": 2, "ledger_state": {...} }`

##### **POST /wp-json/bzj/v6/connection-management/unblock**
```json
{
  "action": "remove_block",
  "user_id_a": 123,
  "user_id_b": 456,
  "origin_platform": "streams",
  "timestamp": 1726492800
}
```
- Validates block exists in canonical ledger
- Calls `bp_moderation_block_removed()` in WordPress
- Syncs unblock to other platform
- Returns: `{ "status": 200, "message": "Block removed", "ledger_state": {...} }`

##### **POST /wp-json/bzj/v6/connection-management/add-friend-request**
```json
{
  "action": "create_friend_request",
  "user_id_a": 123,
  "user_id_b": 456,
  "origin_platform": "socials",
  "timestamp": 1726492800
}
```
- Validates request doesn't already exist in canonical ledger
- Calls `friends_add_friend()` in WordPress
- Returns: `{ "status": 200, "message": "Friend request created", "ledger_state": {...} }`

##### **POST /wp-json/bzj/v6/connection-management/accept-friend**
```json
{
  "action": "accept_friend_request",
  "friendship_id": 789,
  "user_id_acceptor": 456,
  "origin_platform": "socials",
  "timestamp": 1726492800
}
```
- Validates friendship exists and is pending
- Calls `friends_accept_friendship()` in WordPress
- Syncs confirmed connection to Socials followers table
- Returns: `{ "status": 200, "message": "Friend request accepted", "ledger_state": {...} }`

##### **POST /wp-json/bzj/v6/connection-management/reject-friend**
```json
{
  "action": "reject_friend_request",
  "friendship_id": 789,
  "user_id_rejector": 456,
  "origin_platform": "socials",
  "timestamp": 1726492800
}
```
- Validates friendship exists and is pending
- Calls friendship rejection/deletion in WordPress
- Removes pending row from Socials followers
- Returns: `{ "status": 200, "message": "Friend request rejected", "ledger_state": {...} }`

##### **POST /wp-json/bzj/v6/connection-management/remove-friend**
```json
{
  "action": "remove_friend",
  "user_id_a": 123,
  "user_id_b": 456,
  "origin_platform": "socials",
  "timestamp": 1726492800
}
```
- Validates friendship exists and is confirmed
- Calls `friends_remove_friend()` in WordPress
- Removes confirmed row from Socials followers
- Returns: `{ "status": 200, "message": "Friend removed", "ledger_state": {...} }`

### Phase 4: BuddyBoss Event Hook Integration

#### **4.1 Hook: `friends_friendship_requested`**

**Triggers:** When user A sends connection request to user B

**Arguments:** `$friendship_id`, `$initiator_user_id`, `$friend_user_id`

**BZJ Handler Actions:**
1. Query canonical state (should be "not_friends")
2. Sync to Socials: Insert pending friend row in `followers` table with `active = 0`
3. Log operation
4. No Streams action (friends disabled)

#### **4.2 Hook: `friends_friendship_accepted`**

**Triggers:** When user B accepts connection request from user A

**Arguments:** `$friendship_id`, `$initiator_user_id`, `$friend_user_id`

**BZJ Handler Actions:**
1. Query canonical state (should be "pending")
2. Sync to Socials: Update followers row to `active = 1`
3. Log operation
4. No Streams action

#### **4.3 Hook: `friends_friendship_rejected` / `friends_friendship_withdrawn`**

**Triggers:** When connection request is rejected or withdrawn

**Arguments:** `$friendship_id`, `$initiator_user_id`, `$friend_user_id`

**BZJ Handler Actions:**
1. Query canonical state
2. Sync to Socials: Delete pending friend row from followers
3. Log operation
4. No Streams action

#### **4.4 Hook: `friends_friendship_deleted`**

**Triggers:** When confirmed connection is removed by either user

**Arguments:** `$friendship_id`, `$initiator_user_id`, `$friend_user_id`

**BZJ Handler Actions:**
1. Query canonical state (should be "connected")
2. Sync to Socials: Delete confirmed friend row from followers
3. Log operation
4. No Streams action

#### **4.5 Hook: `bp_moderation_block_created`**

**Triggers:** When user A blocks user B

**Arguments:** `$moderation_id`, `$user_id` (blocker), `$item_id` (blocked)

**BZJ Handler Actions:**
1. Query canonical connection state between A and B
2. **If connected:** Call `friends_remove_friend()` to auto-unfriend (prevents orphaned relationships)
3. **Remove all follows:** Query and delete follows in both directions (A→B and B→A)
4. Sync to Streams: Call `Wo_RegisterBlock($user_id_a, $user_id_b)` via direct DB write
5. Sync to Socials: Insert block row + delete any friend/follow rows
6. Log operation with unfriend and follow removal counts

#### **4.6 Hook: `bp_moderation_block_removed`**

**Triggers:** When user A unblocks user B

**Arguments:** `$moderation_id`, `$user_id` (blocker), `$item_id` (blocked)

**BZJ Handler Actions:**
1. Query canonical block state
2. Sync to Streams: Call `Wo_RemoveBlock()` via direct DB write
3. Sync to Socials: Delete block row from blocks table
4. Log operation

#### **4.7 Hook: `bp_follow_start_following`**

**Triggers:** When user A follows user B

**Arguments:** `$follow_id`, `$follower_id`, `$following_id`

**BZJ Handler Actions:**
1. Query canonical ledger (should be "not_following")
2. Sync to Streams: Call `Wo_RegisterFollow($following_id, $follower_id)` via direct DB write
3. Sync to Socials: Insert/update followers row with `active = 1`
4. Log operation

#### **4.8 Hook: `bp_follow_stop_following`**

**Triggers:** When user A unfollows user B

**Arguments:** `$follow_id`, `$follower_id`, `$following_id`

**BZJ Handler Actions:**
1. Query canonical ledger (should be "following")
2. Sync to Streams: Call `Wo_DeleteFollow()` via direct DB write
3. Sync to Socials: Delete follow row from followers
4. Log operation

## CRITICAL IMPLEMENTATION NOTES

1. **BuddyBoss is authoritative.** All other platforms are projections. Never update BuddyBoss state from external platforms—always route through the REST API to trigger the BuddyBoss hook, which then cascades to others.

2. **Block is destructive.** Blocking automatically removes the connection and all follows between users. This is intentional and prevents orphaned relationships.

3. **No API calls.** Streams and Socials sync via direct database writes only. No WoWonder or QuickDate APIs are called. This prevents external API dependencies and rate limiting.

4. **Idempotency.** All operations check canonical state first. Duplicate requests for the same action (e.g., two follow requests in rapid succession) are safely de-duplicated.

5. **Audit everything.** Every sync operation is logged with full context. This enables forensic analysis and recovery.

6. **Validate foreign keys.** Before any cross-platform write, verify the target user exists in both the source and target platforms.

7. **Maintain BuddyBoss capabilities.** BuddyBoss block filtering (by role, profile type, gender) is preserved and executed before any sync operation.

This refined v7.1 implementation establishes a robust, maintainable synchronization layer that treats BuddyBoss as the canonical authority while keeping Streams and Socials consistent through atomic, logged, and recoverable operations.
