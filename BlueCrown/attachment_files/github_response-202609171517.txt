The previous v8.2 implementation should **not** be deployed unchanged. It contains several architectural and implementation defects, especially around QuickDate follow semantics, event retries, blocking, identity authentication, and BuddyBoss hook handling.

The corrected target should be **v8.3.0**, with BuddyBoss as the only canonical relationship authority.

# Buzzjuice Network Relationship Synchronization Specification

## 1. Final authority model

BuddyBoss/WordPress is authoritative for:

- Connection requests
- Accepted connections
- BuddyBoss follows
- BuddyBoss blocks
- BuddyBoss unblocks
- Destructive relationship cleanup caused by blocking

WoWonder Streams and QuickDate Socials are:

- User-facing action interfaces
- Local database projections
- Synchronization clients

External platforms must never directly modify:

- BuddyBoss friendship tables
- BuddyBoss follow tables
- BuddyBoss moderation tables

External actions must use:

```text
Local external action
    ↓
Signed connection-management request
    ↓
BuddyBoss native function
    ↓
BuddyBoss lifecycle hook
    ↓
Canonical projection to Streams and/or Socials
```

The endpoint should be:

```text
POST /wp-json/bzj/v6/connection-management
```

The endpoint is not a general-purpose relationship API. It is a controlled synchronization command endpoint.

---

# 2. Relationship types

These relationships must remain separate.

## 2.1 BuddyBoss connection

A connection has three states:

```text
none
requested
connected
```

A request is directional:

```text
A requests B
```

An accepted connection is reciprocal:

```text
A connected to B
B connected to A
```

## 2.2 Ordinary follow

A follow is directional and independent:

```text
A follows B
```

It must not automatically create a connection request.

## 2.3 Block

A block is directional:

```text
A blocks B
```

It does not mean that B blocks A.

However, blocking is destructive to the relationship pair. When A blocks B, existing connections and follows involving the pair are removed.

## 2.4 QuickDate `followers` table

QuickDate uses one overloaded table for:

- Ordinary follows
- Pending friend requests
- Accepted friendship projections

Therefore, the existence of a row or reciprocal rows must not be used by itself to infer its meaning.

The synchronization layer must receive an explicit semantic operation:

```text
connection_request
connection_accept
connection_reject
connection_withdraw
connection_remove
follow
unfollow
block
unblock
```

A generic `Wo_DeleteFollow()` call must never attempt to infer whether the user intended to unfollow, reject, withdraw, or unfriend.

# 3. Correct synchronization matrix

## 3.1 BuddyBoss connection request

When A requests B on BuddyBoss:

| Platform | Result |
|---|---|
| BuddyBoss | Normal pending connection |
| QuickDate | `following_id = B`, `follower_id = A`, `active = 0` |
| Streams | No follow or friendship row |

The QuickDate row must be marked or otherwise identifiable as a synchronization-owned pending connection. Because the existing table does not contain relationship type metadata, the WordPress synchronization ledger must remain the semantic authority.

## 3.2 BuddyBoss request withdrawal or rejection

When the pending request is withdrawn or rejected:

| Platform | Result |
|---|---|
| BuddyBoss | Pending request removed |
| QuickDate | Delete only the corresponding `active = 0` pending row |
| Streams | No change |

An independent ordinary QuickDate follow must not be deleted accidentally.

## 3.3 BuddyBoss connection acceptance

When B accepts A's BuddyBoss request:

| Platform | Result |
|---|---|
| BuddyBoss | Connection becomes canonical |
| QuickDate | Reciprocal `active = 1` rows |
| Streams | No friendship projection |

Streams has its Friends System disabled, so an accepted BuddyBoss connection must not create a WoWonder friend relationship.

## 3.4 BuddyBoss connection removal

When an accepted BuddyBoss connection is removed:

| Platform | Result |
|---|---|
| BuddyBoss | Connection removed |
| QuickDate | Remove only connection-owned friend projection rows |
| Streams | Preserve independent follows |

If QuickDate has an independent ordinary follow in the same direction, that follow must survive the removal of the connection.

## 3.5 BuddyBoss follow

When A follows B on BuddyBoss:

| Platform | Result |
|---|---|
| BuddyBoss | A follows B |
| Streams | A follows B with `active = 1` |
| QuickDate | No synchronization |

This is an explicit correction to the previous v8.2 proposal. BuddyBoss follows must not populate QuickDate Socials.

## 3.6 BuddyBoss unfollow

When A unfollows B on BuddyBoss:

| Platform | Result |
|---|---|
| BuddyBoss | A → B follow removed |
| Streams | A → B follow removed |
| QuickDate | No change |

## 3.7 BuddyBoss block

When A blocks B:

1. Create or retain the BuddyBoss block.
2. Remove any BuddyBoss connection between A and B.
3. Remove pending connection requests between A and B.
4. Remove BuddyBoss follow A → B.
5. Remove BuddyBoss follow B → A.
6. Remove Streams follow A → B.
7. Remove Streams follow B → A.
8. Create Streams block A → B.
9. Remove QuickDate relationship rows belonging to the pair.
10. Create QuickDate block A → B.

The block remains directional. B is not automatically blocked from A.

## 3.8 BuddyBoss unblock

When A unblocks B:

| Platform | Result |
|---|---|
| BuddyBoss | A → B block removed |
| Streams | A → B block removed |
| QuickDate | A → B block removed |

Previous relationships must not be restored automatically.

# 4. Streams-originated actions

WoWonder Friends System remains disabled.

All integration-created follow rows must therefore be:

```text
active = 1
```

The values of `confirm_followers` and `connectivitySystem` must not cause a Buzzjuice integration follow to remain pending.

## 4.1 Streams follow

When A follows B on Streams:

1. Insert or retain the Streams row.
2. Force the row to `active = 1`.
3. Verify the row.
4. Submit:

```text
origin     = streams
operation  = follow
actor_id   = A's wo_user_id
target_id  = B's wo_user_id
```

5. WordPress maps the WoWonder IDs to WordPress IDs.
6. WordPress calls BuddyBoss's native follow function.
7. BuddyBoss's follow hook updates the canonical ledger.
8. BuddyBoss projects the canonical follow to Streams if required.
9. QuickDate remains unchanged.

The local Streams action should not fail merely because WordPress is temporarily unavailable. The signed command must enter a retry queue.

## 4.2 Streams unfollow

When A unfollows B on Streams:

1. Delete the local Streams row.
2. Verify deletion.
3. Submit:

```text
origin     = streams
operation  = unfollow
```

4. WordPress invokes the native BuddyBoss follow removal function.
5. BuddyBoss confirms the canonical state.
6. QuickDate remains unchanged.

## 4.3 Streams block

When A blocks B on Streams:

1. Insert the Streams block.
2. Verify the block.
3. Submit `block`.
4. WordPress creates the BuddyBoss block using BuddyBoss-native moderation behavior.
5. BuddyBoss performs the destructive cascade.
6. QuickDate receives the block projection.

Streams must never insert a BuddyBoss moderation record directly.

## 4.4 Streams unblock

When A unblocks B:

1. Delete the local Streams block.
2. Verify deletion.
3. Submit `unblock`.
4. WordPress removes the BuddyBoss block.
5. BuddyBoss projects the unblock to QuickDate.
6. No previous connection or follow is restored.

# 5. Socials-originated actions

QuickDate must distinguish between **Add Friend** and **Follow** at the action-handler level.

## 5.1 QuickDate Add Friend

QuickDate Add Friend is a connection request, not an ordinary follow.

When A selects Add Friend for B:

1. QuickDate creates its local pending row.
2. Verify that the row is pending.
3. Submit:

```text
origin     = socials
operation  = connection_request
actor_id   = A's qd_user_id
target_id  = B's qd_user_id
```

4. WordPress maps QuickDate IDs to WordPress IDs.
5. WordPress invokes `friends_add_friend()`.
6. BuddyBoss applies all native restrictions, including:
   - Role restrictions
   - Profile-type restrictions
   - Gender restrictions
   - Privacy restrictions
   - Existing block restrictions
7. If BuddyBoss rejects the request, the QuickDate pending row must be removed and the rejection logged.
8. If BuddyBoss accepts the request, the normal BuddyBoss lifecycle hook updates the canonical state.

QuickDate must not call the ordinary-follow synchronization operation for Add Friend.

## 5.2 QuickDate Add Friend rejection

When B rejects A's pending request:

1. Delete the QuickDate pending row.
2. Verify deletion.
3. Submit:

```text
operation = connection_reject
actor_id  = A
target_id = B
```

4. WordPress calls BuddyBoss's native rejection function.
5. If the BuddyBoss request is already gone, treat the command as idempotently reconciled.

## 5.3 QuickDate Add Friend withdrawal

When A cancels a pending request:

1. Delete the QuickDate pending row.
2. Verify deletion.
3. Submit:

```text
operation = connection_withdraw
actor_id  = A
target_id = B
```

4. WordPress invokes the native BuddyBoss withdrawal function.

## 5.4 QuickDate Add Friend acceptance

When B accepts A's request:

1. Update the local QuickDate row to `active = 1`.
2. Ensure the reciprocal QuickDate projection exists.
3. Verify the local state.
4. Submit:

```text
operation = connection_accept
actor_id  = A
target_id = B
```

5. WordPress locates the BuddyBoss pending friendship.
6. WordPress calls `friends_accept_friendship()`.
7. WordPress verifies:

```php
friends_check_friendship_status($a, $b) === 'is_friend'
```

## 5.5 QuickDate unfriend

When either user removes an accepted QuickDate friendship:

1. Remove only the QuickDate connection projection.
2. Preserve any independent ordinary follow rows.
3. Submit:

```text
operation = connection_remove
```

4. WordPress calls `friends_remove_friend()`.
5. BuddyBoss removes the canonical connection.
6. Independent BuddyBoss and Streams follows survive.

QuickDate unfriend must never call:

```php
bp_stop_following()
```

## 5.6 QuickDate ordinary follow

QuickDate ordinary Follow must remain independent from Add Friend.

The recommended mapping is:

```text
QuickDate Follow
    ↓
BuddyBoss Follow
    ↓
Streams Follow
```

It must not create a BuddyBoss connection request.

When A follows B:

1. QuickDate creates the local directional follow.
2. Verify the row.
3. Submit `follow`.
4. WordPress calls the native BuddyBoss follow function.
5. BuddyBoss's follow hook projects the follow to Streams.
6. No connection request is created.

If the QuickDate interface uses the same handler for both “Follow” and “Add Friend”, the handler must be split or must receive an explicit action type. It must not infer intent from the database row.

## 5.7 QuickDate ordinary unfollow

When A stops following B:

1. Delete the local directional QuickDate follow.
2. Verify deletion.
3. Submit `unfollow`.
4. WordPress calls the native BuddyBoss follow removal function.
5. BuddyBoss projects the unfollow to Streams.
6. No connection is removed.

# 6. Required WordPress control-plane design

The MU plugin should contain the synchronization control plane:

```text
/wp-content/mu-plugins/bzj-connections-sync.php
```

It should provide:

- REST command endpoint
- HMAC request authentication
- Per-platform credentials
- UUID idempotency
- Relationship-pair locking
- Relationship ledger
- Durable event queue
- Retry worker
- External database projections
- Read-back verification
- Operational logging
- Diagnostics endpoint restricted to administrators

## 6.1 Do not use the WordPress API username/password

The supplied WordPress API credentials must not be used as the synchronization credential.

Use:

```text
BUZZ_SSO_SECRET
```

or, preferably, separate secrets:

```text
BZJ_STREAMS_SYNC_SECRET
BZJ_SOCIALS_SYNC_SECRET
```

The request signature should be:

```text
HMAC-SHA256(timestamp + "." + raw_json_body, platform_secret)
```

Required headers:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

Reject requests when:

- Timestamp is missing
- Timestamp is not numeric
- Timestamp is outside the allowed window
- Signature is missing
- Secret is unavailable
- Signature is invalid
- JSON is invalid
- Origin is not permitted
- Operation is not permitted for that origin
- User mappings are missing
- Actor and target are the same user

The current `db_helpers.php` fallback secret is unsafe for synchronization. The control plane must fail closed when the configured secret is missing rather than deriving a predictable fallback from `ABSPATH`.

## 6.2 Actor authentication

A shared HMAC secret alone proves that the request originated from a trusted server. It does not prove that the user actually initiated the action.

Each external adapter must therefore:

1. Validate the logged-in local user.
2. Confirm that the local action actor matches the authenticated local session.
3. Include the actor's platform ID in the signed payload.
4. Never accept a client-supplied actor ID without comparing it to the server-side session.

The WordPress endpoint should also validate that the mapped actor is the user associated with the local action context supplied by the trusted platform adapter.

## 6.3 Event table

The event table is required for durable idempotency and retry handling. A log file alone is insufficient.

Recommended table:

```text
wp_bzj_relationship_events
```

Required fields:

```text
event_uuid
origin
operation
actor_wp_id
target_wp_id
pair_a
pair_b
payload
status
attempts
next_attempt_at
last_error
processed_at
created_at
updated_at
```

Allowed states:

```text
pending
processing
processed
failed
```

Correct UUID behavior:

| Existing state | New request behavior |
|---|---|
| No event | Insert and process |
| `processed` | Return `already_processed` |
| `pending` | Resume or process |
| `failed` | Retry if attempts remain |
| `processing` | Return busy or recover after timeout |

The previous v8.2 logic was incorrect because it treated any existing UUID as already processed.

## 6.4 Retry worker

The recovery worker must actually process events. Merely logging that an event needs reconciliation is insufficient.

The worker must:

1. Select pending events whose retry time has arrived.
2. Acquire the relationship-pair lock.
3. Mark the event as `processing`.
4. Re-execute the canonical operation or reconciliation.
5. Verify the resulting external state.
6. Mark the event `processed` on success.
7. Increment attempts and calculate a backoff on failure.
8. Mark the event `failed` after the configured maximum attempts.
9. Log the final failure.

Suggested retry schedule:

```text
60 seconds
2 minutes
4 minutes
8 minutes
16 minutes
32 minutes
60 minutes
```

## 6.5 Relationship-pair locking

Every operation involving A and B must use the same lock regardless of direction:

```text
bzj_pair_<lower_wp_id>_<higher_wp_id>
```

This prevents concurrent operations such as:

```text
follow
unfollow
connection_accept
connection_remove
block
unblock
```

from producing an invalid final state.

## 6.6 Relationship ledger

The ledger is not a replacement for BuddyBoss. It is an interpretation and reconciliation record.

Recommended table:

```text
wp_bzj_relationships
```

Recommended fields:

```text
user_a
user_b
connection_state
requested_by
follow_a_to_b
follow_b_to_a
block_a_to_b
block_b_to_a
socials_follow_a_to_b
socials_follow_b_to_a
version
last_event_uuid
created_at
updated_at
```

The `socials_follow_*` fields are important because QuickDate's `followers` table cannot distinguish an ordinary follow from an accepted-friend projection merely by inspecting `active`.

The final semantic authority remains BuddyBoss. The ledger records what the synchronization layer believes should exist externally.

# 7. BuddyBoss hooks

The MU plugin should use actual post-operation lifecycle hooks and verify their arguments against the BuddyBoss version installed in production.

Connection hooks to support:

```text
friends_friendship_requested
friends_friendship_accepted
friends_friendship_rejected
friends_friendship_withdrawn
friends_friendship_deleted
friends_friendship_post_delete
```

The misspelled defensive hook sometimes found in older implementations:

```text
friends_friendship_whithdrawn
```

should not be relied upon as the primary hook.

Follow hooks to support only after verifying the installed BuddyBoss implementation:

```text
bp_start_following
bp_stop_following
```

The follow direction is:

```php
$follow->follower_id → $follow->leader_id
```

The functions must not accidentally reverse this direction.

For moderation, request handlers such as:

```text
bp_moderation_block_member
bp_moderation_unblock_user
```

must not be treated as reliable post-operation synchronization hooks.

The synchronization layer should observe the actual moderation save/delete lifecycle and verify that the moderation item is a member block, not a report or unrelated moderation object.

Before deployment, confirm:

```php
$item_type === BP_Moderation_Members::$moderation_type
```

and verify the actual object properties used by the installed BuddyBoss version.

# 8. Correct Streams patch

Do not regenerate the entire `functions_one.php`.

Apply only surgical changes.

## 8.1 Automatic follow acceptance

The requested `Wo_IsFollowRequested()` behavior should apply to WoWonder Streams only. It must not be copied into QuickDate in a way that silently converts QuickDate friend requests into accepted friends.

The effective Streams behavior should be:

```text
pending Streams follow detected
    ↓
UPDATE active = 1
    ↓
return accepted/immediate follow state
```

The update must:

- Validate both IDs
- Reject self-follow
- Check the SQL result
- Log `mysqli_error($sqlConnect)` on failure
- Verify the resulting row
- Avoid recursively invoking the synchronization adapter

## 8.2 `Wo_RegisterFollow()`

For Buzzjuice integration-created follows:

```php
$active = 1;
```

Do not allow:

```php
confirm_followers
connectivitySystem
```

to produce an integration-created pending follow.

After a successful insert or update:

1. Invalidate the relevant cache.
2. Verify the row exists with `active = 1`.
3. Call the Streams synchronization adapter exactly once.
4. If the adapter fails, retain a retryable event.

Do not call the adapter when the database operation failed.

## 8.3 `Wo_DeleteFollow()`

After a successful delete:

1. Verify the directional row no longer exists.
2. Call the adapter with:

```text
operation = unfollow
actor     = follower_id
target    = following_id
```

Do not call the adapter when no local deletion occurred unless the operation is intentionally idempotent and explicitly logged as already reconciled.

## 8.4 `Wo_RegisterBlock()`

The existing implementation should also:

- Reject self-blocks
- Avoid duplicate inserts
- Verify the block row
- Log SQL failures
- Submit the signed `block` command only after successful local state verification

## 8.5 `Wo_RemoveBlock()`

After deletion:

- Verify the directional block is absent
- Submit `unblock`
- Do not restore previous follow or connection state

# 9. Correct Socials patch

Do not use a generic `Wo_DeleteFollow()` call as the integration decision point.

The following handlers must submit explicit operations:

| QuickDate handler | Synchronization operation |
|---|---|
| `add_friend()` new request | `connection_request` |
| Cancel pending request | `connection_withdraw` |
| `disapprove_friend_request()` | `connection_reject` |
| `approve_friend_request()` | `connection_accept` |
| Unfriend | `connection_remove` |
| Ordinary Follow | `follow` |
| Ordinary Unfollow | `unfollow` |
| `block()` | `block` |
| `unblock()` | `unblock` |

Each handler must:

1. Validate the active QuickDate user.
2. Validate that the target belongs to the same authenticated action.
3. Perform the local database operation.
4. Verify the resulting database state.
5. Submit the signed command.
6. Return a local success response even if WordPress is temporarily unavailable, provided the event was queued successfully.
7. Return a synchronization warning only when the local action succeeded but event queuing failed.

The current QuickDate code also uses:

```php
Wo_IsFollowRequested()
```

and:

```php
Wo_DeleteFollow()
```

for multiple meanings. Those calls must be separated by context before synchronization code is added.

# 10. External database projection rules

The control plane may write directly to the Streams and Socials databases because they are external projections and the databases are available through `db_helpers.php`.

Every external write must:

1. Confirm the database connection.
2. Confirm the table exists.
3. Confirm required columns exist.
4. Use prepared statements for values.
5. Execute the write.
6. Check the execution result.
7. Verify the final row state with a `SELECT`.
8. Log database name, table name, operation, IDs, affected rows, and SQL error if applicable.

The log must explicitly identify:

```text
database connection successful
database name
table name
operation
actor external ID
target external ID
affected rows
verification result
```

Do not log passwords, API credentials, HMAC secrets, or complete authentication tokens.

The table names should be discovered from the installed schema or configured explicitly. Do not assume that the table is always named exactly:

```text
Wo_Followers
followers
Wo_Blocks
blocks
```

The actual production table names and columns must be confirmed before enabling writes.

# 11. Logging

Operational logs should be stored under:

```text
/data/logs/
```

Recommended files:

```text
/data/logs/bzj-connections-sync.log
/data/logs/bzj-streams-sync.log
/data/logs/bzj-socials-sync.log
```

The log directory must:

- Be created if missing
- Be writable by the application user
- Be protected from direct web access
- Use append-only JSON Lines or equivalent structured records
- Avoid logging secrets and passwords

Use the WordPress error log as a secondary fallback, not as the primary synchronization log.

`wwqd_bridge.php` currently writes several logs under `/shared`. That profile/identity logging should remain separate from relationship synchronization logging.

`shared/wwqd_bridge.php` should remain focused on:

- User identity mapping
- Profile synchronization
- Existing backward-compatible bridge helpers
- `wo_user_id` and `qd_user_id` mapping support

Do not place the relationship control plane inside `wwqd_bridge.php`.

The relationship orchestration belongs exclusively in:

```text
/wp-content/mu-plugins/bzj-connections-sync.php
```

This avoids creating two competing synchronization controllers.

# 13. Corrections to the previous v8.2 proposal

The following v8.2 recommendations must be changed:

| Previous behavior | Corrected behavior |
|---|---|
| BuddyBoss follow projected to Socials | No Socials projection |
| QuickDate ordinary follow interpreted like friendship | Keep ordinary follow separate |
| Generic row deletion determines action | Use explicit semantic operations |
| Any existing event UUID means processed | Only `processed` means processed |
| Recovery worker only logs failures | Recovery worker must retry |
| Shared fallback SSO secret | Fail closed if secret is unavailable |
| Shared secret alone authenticates actor | Validate local authenticated actor |
| Block only creates external blocks | Block also removes connections and both follow directions |
| Unblock restores previous relationships | Unblock never restores relationships |
| Direct or inferred BuddyBoss database edits | Use BuddyBoss native functions |
| Generic moderation request hooks | Use verified post-operation moderation lifecycle |
| Assumed table names | Verify installed table names and columns |
| Full regeneration of long files | Apply surgical patches only |

# 15. Required test matrix

## Connections

- BuddyBoss request creates QuickDate pending request.
- BuddyBoss withdrawal removes only the QuickDate pending row.
- BuddyBoss rejection removes only the QuickDate pending row.
- BuddyBoss acceptance creates reciprocal QuickDate active rows.
- BuddyBoss connection removal removes only connection-owned QuickDate rows.
- QuickDate Add Friend creates a BuddyBoss request.
- QuickDate approval accepts the BuddyBoss request.
- QuickDate rejection rejects the BuddyBoss request.
- QuickDate withdrawal withdraws the BuddyBoss request.
- QuickDate unfriend removes the BuddyBoss connection.
- Independent follows survive connection removal.

## Follows

- BuddyBoss follow creates an active Streams follow.
- BuddyBoss unfollow removes the corresponding Streams follow.
- BuddyBoss follow does not modify Socials.
- Streams follow creates a BuddyBoss follow.
- Streams unfollow removes the BuddyBoss follow.
- QuickDate ordinary follow creates a BuddyBoss follow.
- QuickDate ordinary unfollow removes the BuddyBoss follow.
- Ordinary follow never creates a BuddyBoss connection request.
- Integration-created Streams follow is always active.

## Blocking

- BuddyBoss block removes any connection.
- BuddyBoss block removes pending connection requests.
- BuddyBoss block removes both BuddyBoss follow directions.
- BuddyBoss block removes both Streams follow directions.
- BuddyBoss block creates the directional Streams block.
- BuddyBoss block creates the directional Socials block.
- Streams block creates the BuddyBoss block.
- Socials block creates the BuddyBoss block.
- Unblock removes only the block.
- Unblock does not restore follows or connections.
- A directional block does not block the reverse direction.

## Reliability

- Repeated event UUID returns `already_processed` only after successful processing.
- Pending event retries successfully.
- Failed event records an error.
- Retry attempts use backoff.
- Pair locks prevent concurrent opposing operations.
- Local success is preserved when the remote platform is temporarily unavailable.
- Every external write has a successful read-back verification.
- Missing mapping creates a logged synchronization failure.
- Missing database or table creates a logged synchronization failure.
- No credentials or secrets appear in logs.

---

## Final recommendation

Use the v8.3 architecture above, but do not deploy the previous v8.2 PHP artifacts without refactoring. In particular:

1. Remove BuddyBoss-follow-to-Socials projection.
2. Separate QuickDate Add Friend from ordinary Follow.
3. Replace generic QuickDate deletion inference with explicit operations.
4. Correct event idempotency and implement actual retries.
5. Add destructive block cascades.
6. Fail closed when synchronization secrets are missing.
7. Authenticate and validate the actor at every external adapter.
8. Verify real BuddyBoss hook signatures and moderation lifecycle behavior against the installed version.
9. Verify database names and table schemas before enabling direct projections.
10. Keep `wwqd_bridge.php` as an identity/profile bridge, not the relationship control plane.
