## Conclusion

Your diagnosis is **substantially correct**, but there are actually **three interacting problems**, not one:

1. `Wo_GetMedia()` itself is not regenerating the PHP session. It is a URL-builder and should remain completely side-effect-free.
2. The current `init.php` has **destructive session recovery**: if `session_start()` encounters a problem, it destroys the existing session and expires the cookie. That can remove `$_SESSION['main_hash_id']`. GitHub identified this same failure chain. 
3. More importantly, the current `Wo_RegisterFollow()` JavaScript **does not explicitly send `hash_id`**. Yet `requests.php` obtains `$hash_id` exclusively from the request's `POST`/`GET` values, and `follow_user.php` immediately requires `Wo_CheckMainSession($hash_id)`. ([GitHub][1])

That third point is a particularly important finding from reviewing the **actual current repository code**. The current browser code changes the button to `Requested` **before** the AJAX response arrives, while the server can silently return an empty response when `Wo_CheckMainSession()` fails. 

### The avatar code is also genuinely problematic

The current profile markup does this:

```php
src="<?php echo Wo_GetMedia($wo['user_profile']['avatar_full'])?>"
data-image="<?php echo $wo['user_profile']['avatar_full']; ?>"
```

So `src` receives a normalized URL, while `data-image` receives the raw database path. `CropImage()` later reads `data-image` and submits that value to the server. 

I therefore agree with GitHub's recommendation to normalize **both** attributes through `Wo_GetMedia()`.

The fact that the profile's `BUZZSTREAMSESSID` changes while the main page retains the same session is especially significant. For a normal same-host navigation, you want:

```text
Main page:

main_hash X

Profile:
Session A
main_hash X

Profile refresh:
Session A
main_hash X
```

not:

```text
Main page:
Session A
main_hash X

Profile:
Session B
main_hash Y

Profile refresh:
Session C
main_hash Z
```

GitHub correctly points out that if that continues after the `init.php` correction, the remaining problem is **cookie scope, SSO/session handling, another endpoint destroying/regenerating the session, or another application overwriting the cookie**—not `Wo_GetMedia()` itself.
