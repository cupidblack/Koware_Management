# ww-sso-bridge.php integration

Add this immediately after the existing require_once block near the top:

require_once __DIR__ . '/bzj-wo-account-diagnostics.php';


Then, after the bridge has established or recovered `$wo_user_id`, add this
diagnostic call in each successful mapping path where you want the account
checked. The safest minimal placement is immediately after the mapping/
registration section and before the final session hydration:

if (
    !empty($wo_user_id) &&
    function_exists('bzj_wo_account_diagnostic_log')
) {
    bzj_wo_account_diagnostic_log(
        (int) $wo_user_id,
        (int) ($wp_user_id ?? ($access_payload['wp_user_id'] ?? 0)),
        'sso_mapping'
    );
}


For the new-registration path, immediately after the database verification
has found `$created_user_id`, also call:

if (
    !empty($created_user_id) &&
    function_exists('bzj_wo_account_diagnostic_log')
) {
    bzj_wo_account_diagnostic_log(
        (int) $created_user_id,
        (int) $wp_user_id,
        'auto_registration'
    );
}


The existing bridge already performs a post-registration database lookup of
the created row, so this diagnostic layer is intentionally non-mutating.

Important finding from the current bridge:
- The current registration request already sends `active => 1`.
- The bridge already queries Wo_Users after registration and accepts an
  existing row if Wo_RegisterUser() returned no payload.
- Therefore SSO auto-registration is worth auditing, but it is not the
  primary explanation for active=0 follow rows.
- Do not alter the SSO identity/reconciliation logic merely to solve the
  follow-state bug.
