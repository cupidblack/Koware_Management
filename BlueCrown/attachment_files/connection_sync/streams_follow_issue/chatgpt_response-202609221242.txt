```php
                (int) $wo['user']['user_id'],

            'hash_id' =>
                Wo_SessionValueDiagnostics(
                    $fast_hash_id
                ),

            'main_hash_id' =>
                Wo_SessionValueDiagnostics(
                    $fast_main_hash_id
                ),

            'ready' =>
                $fast_path_ready
        )
    );

    if (!$fast_path_ready) {

        http_response_code(500);

        exit(
            'Unable to initialize the Streams request session.'
        );
    }

    header('Location: ' . $last_url);
    exit;
}
```

# Phase 8 — Do not confuse `hash` with `main_session`

This is particularly important when debugging `requests.php`.

The request handler currently extracts:

```php
$hash_id = '';
```

from:

```php
$_POST['hash_id']
$_GET['hash_id']
$_GET['hash']
$_POST['hash']
```

as demonstrated in the current repository. ([GitHub][4])

Therefore we should explicitly distinguish:

```text
hash
   ↓
hash_id
   ↓
Wo_CheckSession()
```

from:

```text
main_session
   ↓
main_hash_id
   ↓
Wo_CheckMainSession()
```

A request can therefore have:

```text
hash_id             = valid
main_session        = valid
PHP session         = active
```

while the server-side:

```text
$_SESSION['main_hash_id']
```

is missing.

That is exactly what your log showed.

# One important security correction

I would **not** log the actual values of:

```php
$_SESSION['hash_id']
$_SESSION['main_hash_id']
```

even though you requested "hash values created and detected."

These values function as request credentials.

The GitHub response correctly changed the diagnostic design to record:

* presence
* length
* SHA-256 fingerprint
* format
* matching status

rather than the bearer value itself. ([GitHub][3])

For example:

```text
length: 20
sha256: 625413...
format: hexadecimal
```

is enough to prove:

```text
browser supplied value
        ==
server stored value
```

without putting the credential into your log files.

## Bottom line

The key discovery is that your original assumption needs one refinement:

> The problem isn't that the browser cannot "see" `$_SESSION['main_hash_id']`. PHP sessions are server-side. The browser only carries the session cookie.

Your log shows the browser **was carrying a PHP session cookie**, but the server-side session associated with it did not contain `main_hash_id`. ([GitHub][1])

And because the current Streams session is named:

```text
PHPSESSID
```

while Streams and QuickDate coexist under the same domain, **session-cookie collision/interference is now one of the primary things we should eliminate**. The GitHub analysis independently reached the same architectural conclusion. ([GitHub][3])

So the correct end state is:

```text
WordPress
    │
    ├── WP authentication cookies
    │
    ├── Streams
    │      └── BUZZSTREAMSESSID
    │             ├── hash_id
    │             ├── main_hash_id
    │             ├── wo_user_id
    │             └── SSO state
    │
    └── Socials
           └── BUZZSOCIALSESSID
                  └── QuickDate session
```

with `Wo_CheckSession()` and `Wo_CheckMainSession()` restored as genuine validation functions rather than permanently returning `true`.

The next practical step is **not to modify Follow further**. It is to implement Deployment A and B, then use the resulting `streams-session-YYYY-MM-DD.log` and `session-YYYY-MM-DD.log` to prove whether the Streams session survives the `/social` transition. That will give us a deterministic answer rather than continuing to debug the symptom.
