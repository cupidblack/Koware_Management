## Conclusion

Yes. After comparing the current Buzzjuice Streams code with the GitHub review, there is a clearer picture of the problem.

The issue is **not one single corrupt-user problem**. There are several interacting problems in the current implementation:

1. The current JavaScript still decides the button state **before the server responds**. In particular, `confirm_followers` can cause the browser to render **Requested** even though your PHP function is supposed to force `active = 1`. 
2. The current `Wo_RegisterFollow()` does force `active = 1`, but it does **not reliably promote an existing `active=0` row** or clean up duplicate relationship rows. 
3. `Wo_IsFollowing()` currently uses `COUNT(...) == 1`. That is fragile: if an account has two active duplicate rows, it incorrectly reports that the user is **not** following. 
4. `Wo_DeleteFollow()` depends on those state functions, making legacy/inconsistent rows capable of preventing a clean unfollow. 
5. `follow_user.php` currently returns only a generic success response and does not read the database back and return the **verified final state**. 
6. The current button templates explicitly pass `confirm_followers` into JavaScript, which is one of the mechanisms allowing the Requested branch to remain in play. 
7. The SSO bridge already registers new WoWonder accounts with `active => 1` and subsequently verifies the newly created database row. Therefore I would **diagnose SSO accounts, but not make SSO the primary fix for this particular follow bug**. ([GitHub][1])

### The most important architectural change

The new flow is now:

**Follow button → server → database → verify database → return `following` → browser renders Following**

and:

**Following button → server → delete database row → verify deletion → return `follow` → browser renders Follow**

The browser no longer gets to decide whether the state is `Requested`, `Following`, or `Follow`.

# Your two existing follow rows are significant

You currently have:

```text
97, 66, 38407, 0, 1, 0, 0
98, 66, 1,     0, 1, 0, 0
```

Interpreting the WoWonder structure:

```text
following_id = 66
follower_id  = 38407
active       = 0
```

means user `38407` has a **pending/non-active relationship toward user 66**.

Likewise:

```text
following_id = 66
follower_id  = 1
active       = 0
```

is another pending relationship toward user 66.

That is consistent with the exact symptom you're seeing: old/pending database state exists even though the new desired behaviour is immediate following.

The new `Wo_RegisterFollow()` specifically handles this situation:

```text
existing active=0 row
        ↓
promote same row
        ↓
active=1
        ↓
verify
        ↓
Following
```

rather than inserting another row.

It also handles the opposite problem:

```text
duplicate rows
        ↓
retain newest relationship
        ↓
remove older duplicates
        ↓
verify active=1
```

That is important because the current `Wo_IsFollowing()` implementation can incorrectly fail when duplicates exist.

## One particularly useful diagnostic outcome

If the new code produces:

```text
database = active=1
endpoint = state=following
browser = Follow
```

then the remaining problem is **front-end/template/cache-related**.

If it produces:

```text
database = no row
endpoint = 500
```

then the problem is **PHP/database-related**.

If it produces:

```text
database = active=0
```

after the new `Wo_RegisterFollow()` has been deployed, then something else in the WoWonder request path is writing `active=0`. At that point the extensive `data.logs/follow/` logging should make that much easier to isolate.
