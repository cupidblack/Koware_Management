# 5. More important: fix `bz_safe_session_start()`

This is the code I would change immediately.

The current version destroys the user's authenticated session whenever `session_start()` throws. That is much too aggressive for a production SSO system. ([GitHub][1])

Replace it with:

```php
function bz_safe_session_start()
{
    /*
     * Buzzjuice / Blue Crown R&D
     *
     * Session startup must be conservative.
     *
     * NEVER automatically destroy an existing authenticated session
     * merely because session_start() encounters an exception.
     *
     * Destructive session recovery belongs in an explicit authentication
     * recovery/logout flow, not in the global bootstrap.
     */

    if (session_status() === PHP_SESSION_ACTIVE) {
        return true;
    }

    try {
        $started = @session_start();

        if ($started && session_status() === PHP_SESSION_ACTIVE) {
            return true;
        }
    } catch (Throwable $e) {
        /*
         * Do not destroy the session here.
         *
         * The request should continue with the session state that PHP
         * was able to establish, or fail normally if no session exists.
         */
    }

    /*
     * Last non-destructive attempt.
     *
     * We deliberately do NOT:
     *
     *   session_destroy()
     *   session_regenerate_id()
     *   setcookie(... expired ...)
     *   $_SESSION = []
     *
     * Those operations can invalidate the SSO/session relationship.
     */
    if (session_status() !== PHP_SESSION_ACTIVE) {
        @session_start();
    }

    return session_status() === PHP_SESSION_ACTIVE;
}
```

Then:

```php
bz_safe_session_start();
```

can remain exactly where it currently is.

This is a much safer design for the Buzzjuice architecture.

# 7. `Wo_CreateSession()` and `Wo_CreateMainSession()` are not actually regenerating the values

The existing functions are:

```php
function Wo_CreateSession() {
    $hash = sha1(rand(1111, 9999));

    if (!empty($_SESSION["hash_id"])) {
        $_SESSION["hash_id"] = $_SESSION["hash_id"];
        return $_SESSION["hash_id"];
    }

    $_SESSION["hash_id"] = $hash;
    return $hash;
}
```

and:

```php
function Wo_CreateMainSession() {
    $hash = substr(sha1(rand(1111, 9999)), 0, 20);

    if (!empty($_SESSION["main_hash_id"])) {
        $_SESSION["main_hash_id"] = $_SESSION["main_hash_id"];
        return $_SESSION["main_hash_id"];
    }

    $_SESSION["main_hash_id"] = $hash;
    return $hash;
}
```

They preserve existing values. The assignments:

```php
$_SESSION["hash_id"] = $_SESSION["hash_id"];
```

and:

```php
$_SESSION["main_hash_id"] = $_SESSION["main_hash_id"];
```

are redundant but harmless. 

The important part is:

```php
if (!empty($_SESSION["main_hash_id"]))
```

If the PHP session itself changes, then the new session has no:

```php
$_SESSION["main_hash_id"]
```

so the next rendering generates a new value.

That exactly matches what you're observing:

```text
Profile load
    session = A
    main_hash_id = X

Profile refresh
    session = B
    main_hash_id = Y
```

The hash changing is therefore probably **a symptom of the session changing**, not the cause.

```php
    $root = dirname(__DIR__, 2);
    $log_dir = $root . '/data/logs';

    if (!is_dir($log_dir)) {
        @mkdir($log_dir, 0755, true);
    }

    $data = array(
        'time' => gmdate('Y-m-d H:i:s'),
        'event' => $event,
        'request_method' => $_SERVER['REQUEST_METHOD'] ?? '',
        'request_uri' => $_SERVER['REQUEST_URI'] ?? '',
        'script' => $_SERVER['SCRIPT_NAME'] ?? '',
        'session_name' => function_exists('session_name')
            ? session_name()
            : '',
        'session_status' => function_exists('session_status')
            ? session_status()
            : null,
        'session_id' => function_exists('session_id')
            ? session_id()
            : '',
        'hash_id' => $_SESSION['hash_id'] ?? null,
        'main_hash_id' => $_SESSION['main_hash_id'] ?? null,
    );

    $data = array_merge($data, $extra);

    @file_put_contents(
        $log_dir . '/buzzjuice-streams.log',
        json_encode(
            $data,
            JSON_UNESCAPED_SLASHES
        ) . PHP_EOL,
        FILE_APPEND | LOCK_EX
    );
}
```

Then:

```php
bzj_streams_session_debug('before_session_start');

bz_safe_session_start();

bzj_streams_session_debug('after_session_start');
```

That will tell us immediately whether the session is changing **before `Wo_GetMedia()` is even reached**.

# 17. One more architectural issue I spotted

Your `ww-sso-bridge.php` currently has a very aggressive branch:

```php
if (!$wordpress_logged_in) {
    if (session_status() === PHP_SESSION_ACTIVE) {
        $_SESSION = [];
        session_unset();
        @session_destroy();
    }

    ...
}
```

and then the bridge redirects to WordPress login. 

That's reasonable **inside the SSO bridge itself**, but it reinforces why we should not let ordinary media requests accidentally enter the SSO bridge.

The long-term architecture should therefore be:

```text
                   ┌───────────────────────┐
                   │ WordPress / BuddyBoss │
                   │   Source of Truth     │
                   └───────────┬───────────┘
                               │
                         SSO / JWT
                               │
                               ▼
                   ┌───────────────────────┐
                   │   WoWonder Session   │
                   │   Canonical Runtime  │
                   └───────────┬───────────┘
                               │
               ┌───────────────┼───────────────┐
               │               │               │
               ▼               ▼               ▼
           HTML page        AJAX/API        Static media
               │               │               │
          session-aware    session-aware       NO PHP
                                             authentication
```

**Static media should never need the SSO/session bootstrap.**

That is the scalable solution.
