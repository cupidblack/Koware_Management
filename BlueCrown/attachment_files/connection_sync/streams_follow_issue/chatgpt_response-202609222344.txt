```php
            return false;
        }

        try {

            $started = session_start();

        } catch (Throwable $e) {

            Wo_SessionDiagnosticLog(
                'php_session_start_exception',
                array(
                    'exception_class' =>
                        get_class($e),
                    'exception_message' =>
                        $e->getMessage()
                )
            );

            return false;
        }

        $active =
            $started &&
            session_status() === PHP_SESSION_ACTIVE;

        Wo_SessionDiagnosticLog(
            $active
                ? 'php_session_started'
                : 'php_session_start_failed',
            array(
                'start_return_value' =>
                    $started,
                'last_error' =>
                    error_get_last()
            )
        );

        return $active;
    }
}
```

# 15. One subtle but important correction

The old code:

```php
if (!empty($_SESSION["hash_id"])) {
    $_SESSION["hash_id"] = $_SESSION["hash_id"];
    return $_SESSION["hash_id"];
}
```

doesn't actually preserve anything that wasn't already there.

It is equivalent, for practical purposes, to:

```php
return $_SESSION["hash_id"];
```

The assignment:

```php
$_SESSION["hash_id"] = $_SESSION["hash_id"];
```

does not protect the session from destruction, regeneration, replacement, or loading another session.

The same applies to:

```php
$_SESSION["main_hash_id"] =
    $_SESSION["main_hash_id"];
```

The new implementation removes that misleading operation.

# 16. Another improvement: stronger token generation

The original:

```php
sha1(rand(1111, 9999))
```

has a tiny entropy source because `rand()` only receives a four-digit range.

The new implementation uses:

```php
bin2hex(random_bytes(20))
```

for `hash_id` and:

```php
bin2hex(random_bytes(10))
```

for `main_hash_id`.

That preserves the original token lengths while using a proper cryptographic random source. This was also correctly identified in the GitHub analysis.

## Bigger picture

The architecture we are moving toward is:

```text
                         BUZZJUICE
                       WordPress SSO
                            │
              ┌─────────────┴─────────────┐
              │                           │
         /streams                     /social
              │                           │
     BUZZSTREAMSESSID              BUZZSOCIALSESSID
              │                           │
       WoWonder session             QuickDate session
              │
       ┌──────┴──────┐
       │             │
   hash_id     main_hash_id
       │             │
       └──────┬──────┘
              │
        request validation
              │
       WoWonder operations
```

This is much safer than trying to make the three applications share one PHP session. The SSO identity should remain centralized through WordPress/JWT, while each downstream application owns its own runtime session.

The existing WoWonder SSO bridge is already designed around stateless JWT authority rather than trusting PHP sessions for SSO identity, so isolating the runtime sessions is consistent with that architecture.
