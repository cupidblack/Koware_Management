The root cause is **not that `$_SESSION['hash_id']` or `$_SESSION['main_hash_id']` should appear in browser DevTools**. Those values are server-side. The browser only receives:

1. The PHP session cookie, currently `PHPSESSID`.
2. The rendered `.main_session` value in the HTML.
3. That rendered value must be submitted with protected AJAX requests.

Your log shows that the PHP session is active, but `main_hash_id` is repeatedly missing or does not match the token submitted by the browser. The most important evidence is:

- `PHPSESSID` is present and PHP reports an active session.
- `hash_id` sometimes survives.
- `main_hash_id` is recreated or missing.
- Requests repeatedly submit an older `main_hash_id`.
- `follow_user` is rejected before the follow operation completes.
- The frontend changes the button optimistically to `Requested`, but the database operation either never executes or the response is not interpreted correctly.

The repository code confirms an additional problem: `streams/xhr/follow_user.php` requires:

```php
Wo_CheckMainSession($hash_id)
```

but the shown JavaScript request sends only:

```javascript
$.get(Wo_Ajax_Requests_File(), {
    f: 'follow_user',
    following_id: id
}, ...)
```

Therefore, the follow request can arrive with an empty `$hash_id`.

Do not leave `Wo_CheckMainSession()` as:

```php
return true;
```

That bypasses the same security boundary used by follow, chat, payments, reactions, profile changes, and other protected actions.

# 1. Important correction about the log

The supplied diagnostic log strongly indicates **session continuity and token transport problems**, not an inability to generate hashes.

For example, the log shows sequences equivalent to:

```text
create_main_session_created
main_session_rendered_into_html
request_router_hash_selected
check_main_session_failed
```

It also shows a request submitting a token whose fingerprint differs from the current server-side token.

This pattern is consistent with one or more of the following:

1. The main token is not sent with the follow request.
2. The HTML page is cached and contains an old token.
3. QuickDate and Streams share the same `PHPSESSID`.
4. One application destroys or replaces the shared PHP session.
5. The SSO bridge redirects before initializing both tokens.
6. Different Streams entry points use different session settings.
7. A page loaded through AJAX contains a different `.main_session` value.
8. Concurrent AJAX requests are creating or replacing session values.
9. PHP session storage is not shared consistently between PHP-FPM workers.
10. The follow request is being sent to a different hostname or cookie scope.

The log results may be incomplete because the available repository output is limited to the retrieved portion of the log. Continue diagnosis with a fresh log after applying the instrumentation below.

# 3. Separate the Streams PHP session from QuickDate

This is the most important architectural change.

Streams and QuickDate currently risk sharing the default cookie:

```text
PHPSESSID
```

Both applications run under the same parent domain, and both call `session_start()`. This can make one application read, overwrite, clear, or reinterpret the other application's session data.

Use separate cookie names:

```text
Streams  → BUZZSTREAMSESSID
QuickDate → BUZZSOCIALSESSID
```

The browser will still not show `hash_id` or `main_hash_id`. It will show only the session cookie.

The existing functions use weak random generation:

```php name=streams/assets/includes/functions_two.php url=https://github.com/cupidblack/buzzjuice.net/blob/main/streams/assets/includes/functions_two.php
if (!function_exists('Wo_SessionValueDiagnostics')) {
    function Wo_SessionValueDiagnostics($value)
    {
        if (!is_scalar($value)) {
            $value = '';
        }

        $value = (string) $value;

        return array(
            'present' => $value !== '',
            'length' => strlen($value),
            'sha256' => $value !== ''
                ? hash('sha256', $value)
                : '',
            'format' => $value === ''
                ? 'empty'
                : (
                    preg_match('/^[a-f0-9]+$/i', $value)
                        ? 'hexadecimal'
                        : 'invalid'
                )
        );
    }
}

if (!function_exists('Wo_CreateSession')) {
    function Wo_CreateSession()
    {
        if (!Wo_EnsurePhpSession()) {
            Wo_SessionDiagnosticLog(
                'create_session_failed',
                array(
                    'session_key' => 'hash_id',
                    'reason' => 'php_session_not_active'
                )
            );

            return '';
        }

        $existing = isset($_SESSION['hash_id'])
            ? (string) $_SESSION['hash_id']
            : '';

        if (preg_match('/^[a-f0-9]{40}$/i', $existing)) {
            Wo_SessionDiagnosticLog(
                'create_session_reused',
                array(
                    'session_key' => 'hash_id',
                    'value' => Wo_SessionValueDiagnostics($existing)
                )
            );

            return $existing;
        }

        try {
            $hash = bin2hex(random_bytes(20));
        } catch (Throwable $exception) {
            Wo_SessionDiagnosticLog(
                'create_session_random_bytes_failed',
                array(
                    'session_key' => 'hash_id',
                    'exception_class' => get_class($exception),
                    'exception_message' => $exception->getMessage()
                )
            );

            return '';
        }

        $_SESSION['hash_id'] = $hash;

        Wo_SessionDiagnosticLog(
            'create_session_created',
            array(
                'session_key' => 'hash_id',
                'old_value' => Wo_SessionValueDiagnostics($existing),
                'new_value' => Wo_SessionValueDiagnostics($hash)
            )
        );

        return $hash;
    }
}

if (!function_exists('Wo_CheckSession')) {
    function Wo_CheckSession($hash = '')
    {
        $provided = is_scalar($hash)
            ? (string) $hash
            : '';

        if (!Wo_EnsurePhpSession()) {
            Wo_SessionDiagnosticLog(
                'check_session_failed',
                array(
                    'session_key' => 'hash_id',
                    'reason' => 'php_session_not_active',
                    'provided' => Wo_SessionValueDiagnostics($provided)
                )
            );

            return false;
        }

        $stored = isset($_SESSION['hash_id'])
            ? (string) $_SESSION['hash_id']
            : '';

        $provided_valid = (bool) preg_match(
            '/^[a-f0-9]{40}$/i',
            $provided
        );

        $stored_valid = (bool) preg_match(
            '/^[a-f0-9]{40}$/i',
            $stored
        );

        $matched = (
            $provided_valid &&
            $stored_valid &&
            hash_equals($stored, $provided)
        );

        Wo_SessionDiagnosticLog(
            $matched
                ? 'check_session_passed'
                : 'check_session_failed',
            array(
                'session_key' => 'hash_id',
                'provided' => Wo_SessionValueDiagnostics($provided),
                'stored' => Wo_SessionValueDiagnostics($stored),
                'provided_valid' => $provided_valid,
                'stored_valid' => $stored_valid,
                'matched' => $matched
            )
        );

        return $matched;
    }
}
```

# 9. Add client-side diagnostic logging

Add this once to `content.phtml` or another globally loaded Streams JavaScript file:

```javascript
function Wo_SessionDiagnosticLogClient(event, context) {
  context = context || {};

  var mainSession = $('.main_session').first().val() || '';

  var payload = {
    event: event,
    context: {
      page: window.location.href,
      session_cookie_names: document.cookie
        .split(';')
        .map(function(item) {
          return item.trim().split('=')[0];
        })
        .filter(function(name) {
          return name.length > 0;
        }),
      main_session_present: mainSession.length > 0,
      main_session_length: mainSession.length,
      main_session_sha256: '',
      extra: context
    }
  };

  /*
   * Do not send the raw token to the server.
   * Use Web Crypto when available to calculate a fingerprint.
   */
  if (
    window.crypto &&
    window.crypto.subtle &&
    window.TextEncoder
  ) {
    window.crypto.subtle.digest(
      'SHA-256',
      new TextEncoder().encode(mainSession)
    ).then(function(buffer) {
      var bytes = new Uint8Array(buffer);
      var hex = '';

      bytes.forEach(function(byte) {
        hex += byte.toString(16).padStart(2, '0');
      });

      payload.context.main_session_sha256 = hex;

      if (navigator.sendBeacon) {
        navigator.sendBeacon(
          Wo_Ajax_Requests_File() +
          '?f=session_status_client_log',
          JSON.stringify(payload)
        );
      }
    }).catch(function() {});
  }
}
```

Do not depend on this client-side logger for security. It is diagnostic only.

```php name=streams/xhr/follow_user.php url=https://github.com/cupidblack/buzzjuice.net/blob/main/streams/xhr/follow_user.php
<?php

if ($f == 'follow_user' && $wo['loggedin'] === true) {
    $data = array(
        'status' => 400,
        'can_send' => 0,
        'html' => ''
    );

        ? (int) $_GET['following_id']

    } else {
        $user_followers = Wo_CountFollowing(
            $wo['user']['id'],
            true
        );

        $friends_limit =
            $wo['config']['connectivitySystemLimit'];

        $already_following =
            Wo_IsFollowing(

            Wo_IsFollowRequested(
                $following_id,
                $wo['user']['user_id']
            ) === true;

        if ($already_following || $already_requested) {
```

# 12. Do not use the admin-panel session functions for Streams

`social/admin-panel/function.php` defines functions with the same names:


Those are QuickDate/admin functions and must not be copied into Streams.

In particular, this QuickDate implementation:

```php
function Wo_CreateMainSession(){
```

Keep the two applications separate. If both applications expose global functions with identical names in the same PHP request, that is also a function-collision risk and should be eliminated.

# 15. Why some accounts appear to work

The different behavior between user 66 and other accounts is probably incidental rather than evidence that user 66 has a special valid session.

Possible explanations include:

1. User 66 was followed from a page rendered with the current token.
2. Another account used a cached page with a stale token.
3. The request for user 66 was sent through a different JavaScript path.
4. User 66 has follower confirmation disabled.
5. Another target has follower confirmation enabled.
6. A previous request already created a follow row.
7. The follow response is being overwritten by a second AJAX request.
8. The target account has a different privacy or block configuration.

Once session fingerprints are logged for both cases, compare:

```text
request_hash
stored_main_hash_id
following_id
connectivitySystem
confirm_followers
Wo_RegisterFollow() result
Wo_IsFollowing()
Wo_IsFollowRequested()
```

Do not infer that user 66 proves the browser session is healthy unless the server-side fingerprints match during that exact request.

```php
if (!headers_sent()) {
```

If the profile HTML is cached, it may contain a valid-looking but stale `.main_session` value. That exactly produces the repeated old fingerprint seen in your log.

# 18. Final implementation order

Apply the work in this order:

1. Back up the files.
2. Create and permission `data/logs`.
3. Separate the Streams cookie as `BUZZSTREAMSESSID`.
4. Give QuickDate a different cookie name.
5. Replace the four Streams session functions.
6. Initialize both tokens during SSO.
7. Repair the SSO fast path.
8. Render one canonical `.main_session`.
9. Send `hash_id` explicitly with Follow.
10. Add diagnostics to `requests.php`.
11. Improve `follow_user.php` error handling.
12. Disable caching for logged-in Streams pages.
13. Clear old `PHPSESSID` cookies.
14. Test with user 66 and another target account.
15. Remove or reduce verbose logging after the issue is resolved.

The final production behavior should be:

```text
Browser
  ├── BUZZSTREAMSESSID
  └── rendered main_session token

Streams PHP session
  ├── hash_id
  └── main_hash_id

Follow request
  ├── BUZZSTREAMSESSID cookie
  └── hash_id=<current main_hash_id>

Server
  └── Wo_CheckMainSession() validates the submitted token
```

The permanent fix is therefore **session isolation plus explicit token transport**, not permanently returning `true` from `Wo_CheckMainSession()`.
