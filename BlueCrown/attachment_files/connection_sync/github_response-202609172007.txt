# Updated Buzzjuice Network Integration Proposal and Implementation Plan

## Executive decision

The previous v8.3.0 implementation is a useful baseline, but it should **not be deployed unchanged**. The architecture is directionally correct, but several issues must be corrected before production:

1. External platforms must never write BuddyBoss tables directly.
2. External IDs must not be sent to WordPress as if they were WordPress user IDs.
3. QuickDate **Add Friend** and QuickDate **Follow** must remain separate relationship types.
4. Synchronization must be idempotent and retryable.
5. BuddyBoss lifecycle hooks must be used as the authoritative projection trigger.
6. `Wo_IsFollowRequested()` must not be used as a side-effect-free read function if it modifies the database.
7. Blocking must remove existing connections and follows, but unblocking must not restore them automatically.
8. Every database write must be read-back verified and logged.

The recommended implementation is therefore a **v8.4 control-plane design** based on the v8.3 architecture, with corrected identity mapping, hook handling, operation semantics, retry behavior, and external-client routing.

---

# 1. Canonical relationship model

BuddyBoss remains the source of truth for the three relationship types.

## 1.1 BuddyBoss connections

A BuddyBoss connection has these states:

- `none`
- `pending`
- `connected`

The BuddyBoss friendship table is authoritative.

QuickDate mirrors the state as follows:

| BuddyBoss state | QuickDate projection |
|---|---|
| Pending connection | One pending `followers` row with `active = 0` |
| Connected | Reciprocal `followers` rows with `active = 1` |
| Rejected or withdrawn | Pending projection removed |
| Removed | Connection-owned friendship projection removed |

Streams receives no BuddyBoss connection or friendship projection because the WoWonder Friends System is disabled.

## 1.2 Ordinary follows

An ordinary follow is directional:

```text
A follows B
```

It is independent from a BuddyBoss connection.

The following mappings apply:

- BuddyBoss Follow → Streams Follow
- Streams Follow → BuddyBoss Follow
- QuickDate Follow → BuddyBoss Follow → Streams Follow
- Unfollow in any platform removes the same directional follow from the other applicable platforms
- Ordinary follows must not create QuickDate Add Friend requests
- Ordinary follows must not create BuddyBoss connection requests

## 1.3 Blocks

Blocks are directional:

```text
A blocks B
```

A block must:

1. Be stored in BuddyBoss.
2. Remove any BuddyBoss connection or pending request between the pair.
3. Remove both directional BuddyBoss follows.
4. Create the directional block in Streams.
5. Create the directional block in QuickDate.
6. Remove corresponding external relationship projections.
7. Prevent future connection and follow creation while the block exists.

Unblocking removes only the directional blocks. It does not recreate former connections or follows.

# 3. Important corrections to v8.3.0

## 3.1 External IDs must be mapped to WordPress IDs

The v8.3 client currently sends values such as:

```text
actor_id
target_id
```

The control plane then treats them as WordPress user IDs. That is unsafe because WoWonder and QuickDate IDs are not necessarily identical to WordPress IDs.

The corrected request must identify both the platform and the platform-native IDs:

```text
origin: streams
actor_external_id: 123
target_external_id: 456
```

or:

```text
origin: socials
actor_external_id: 123
target_external_id: 456
```

The WordPress control plane must resolve them as follows:

- Streams external ID → `wp_usermeta.meta_key = wo_user_id`
- Socials external ID → `wp_usermeta.meta_key = qd_user_id`

The command must be rejected if either mapping is missing or ambiguous.

The control plane should internally normalize the request to:

```text
actor_wp_id
target_wp_id
```

Only normalized WordPress IDs may be passed to:

- `friends_add_friend()`
- `friends_accept_friendship()`
- `friends_reject_friendship()`
- `friends_withdraw_friendship()`
- `friends_remove_friend()`
- `bp_start_following()`
- `bp_stop_following()`
- BuddyBoss moderation functions

Do not infer identity by email during relationship synchronization. Email matching can silently associate the wrong account after an email change.

## 3.2 External commands must be intent commands

A Streams or Socials request should not directly modify BuddyBoss database tables.

The correct sequence is:

```text
External user action
    ↓
Local external database mutation
    ↓
Read-back verification
    ↓
Signed command to WordPress
    ↓
WordPress validates external identity mapping
    ↓
WordPress calls native BuddyBoss function
    ↓
BuddyBoss hook fires
    ↓
Control plane projects canonical state
```

The external platform may directly update its own local database, because its native action already requires that. It must not directly update WordPress friendship, follow, or moderation tables.

## 3.3 BuddyBoss hooks must be deduplicated

`friends_friendship_deleted` fires before the friendship is deleted, while `friends_friendship_post_delete` fires afterward. Registering both as independent removal events can create duplicate projections.

Use one canonical connection-removal handler, preferably attached to:

- `friends_friendship_deleted` for the relationship identity
- or `friends_friendship_post_delete` if the implementation explicitly re-reads the prior relationship context

Do not process both hooks as separate operations unless the event ledger has a stable deduplication key such as:

```text
connection removal + friendship ID
```

The same applies to request withdrawal and rejection. The friendship object must be used to retrieve the original initiator and recipient because the current logged-in user is not always the request initiator.

## 3.4 Do not rely on a generic QuickDate `Wo_DeleteFollow()`

QuickDate uses an overloaded `followers` table. A row with:

```text
active = 1
```

may represent:

- an ordinary follow, or
- an accepted friendship projection.

Therefore, `Wo_DeleteFollow()` cannot determine the semantic operation by itself.

The QuickDate handlers must issue explicit commands:

- `connection_request`
- `connection_accept`
- `connection_reject`
- `connection_withdraw`
- `connection_remove`
- `follow`
- `unfollow`

The control plane must maintain separate projection metadata so an ordinary QuickDate follow is not accidentally deleted when a BuddyBoss connection is removed.

# 4. Recommended data model

The existing ledger and event tables are appropriate, but the ledger must distinguish canonical state from external projections.

## 4.1 Relationship ledger

Recommended fields:

```text
user_a
user_b
connection_state
connection_requested_by
follow_a_to_b
follow_b_to_a
block_a_to_b
block_b_to_a
socials_connection_projection
socials_follow_a_to_b
socials_follow_b_to_a
streams_follow_a_to_b
streams_follow_b_to_a
version
last_event_uuid
created_at
updated_at
```

`user_a` must always be the lower WordPress user ID and `user_b` the higher ID.

Directional fields must always be interpreted relative to the canonical ordered pair.

## 4.2 Event ledger

The event table should contain:

```text
event_uuid
origin
operation
actor_wp_id
target_wp_id
actor_external_id
target_external_id
pair_a
pair_b
payload
status
attempts
next_attempt_at
last_error
created_at
processed_at
```

Recommended statuses:

```text
pending
processing
processed
failed
ignored
```

A unique index on `event_uuid` is required.

The event UUID must be generated by the originating platform and retained during retries. A retry must never create a new UUID for the same logical event.

# 5. BuddyBoss event handling

## 5.1 Connection request

Attach to:

```text
friends_friendship_requested
```

Use the hook arguments:

```text
friendship_id
initiator_user_id
friend_user_id
friendship_object
```

The handler should:

1. Confirm that the friendship is still pending.
2. Record `connection_state = pending`.
3. Record the actual initiator.
4. Create or update the QuickDate pending projection.
5. Verify the QuickDate row exists with `active = 0`.
6. Log the database and table used.

No Streams write is performed.

## 5.2 Connection acceptance

Attach to:

```text
friends_friendship_accepted
```

The handler should:

1. Read the initiator and recipient from the friendship object or hook arguments.
2. Set `connection_state = connected`.
3. Remove any stale QuickDate pending row.
4. Create reciprocal QuickDate accepted rows with `active = 1`.
5. Verify both rows.
6. Log both writes.

No Streams friendship row is created.

## 5.3 Rejection and withdrawal

Attach to:

```text
friends_friendship_rejected
friends_friendship_withdrawn
```

The handler should:

1. Obtain the friendship object.
2. Extract the original initiator and recipient.
3. Delete only the QuickDate pending projection.
4. Verify no pending projection remains.
5. Update the ledger to `connection_state = none`.
6. Log the result.

The rejected or withdrawn request must not delete independent ordinary follows.

## 5.4 Connection removal

Use one deduplicated handler for the BuddyBoss removal lifecycle.

The handler should:

1. Identify both WordPress users.
2. Remove the QuickDate connection-owned projection.
3. Preserve QuickDate ordinary follows recorded independently in the ledger.
4. Preserve Streams ordinary follows.
5. Verify the accepted friendship projection is gone.
6. Update the ledger.
7. Log the result.

The earlier failure where only one direction removed correctly is most likely caused by relying on a post-delete hook or by using the current user instead of the friendship object’s original participants.

# 6. BuddyBoss blocking

The original block assumptions are too general. The implementation must use the actual BuddyBoss moderation lifecycle hooks available in the installed version.

Before deployment, inspect the member moderation class and locate the method that creates and deletes the member-block record. Attach to the action emitted after the successful database mutation.

The handler must receive or derive:

```text
blocker_wp_id
blocked_wp_id
```

It must not assume that:

```text
$user_id
$item_id
```

always have the same meaning without verifying the moderation class.

## 6.1 Block operation

When A blocks B:

1. Let BuddyBoss complete its native block operation.
2. Remove any BuddyBoss pending connection or accepted connection.
3. Remove both BuddyBoss directional follows.
4. Set `block_a_to_b = 1`.
5. Delete QuickDate connection and ordinary follow projections for the pair.
6. Insert the directional QuickDate block.
7. Insert the directional Streams block.
8. Verify both external block rows.
9. Verify both external relationship directions were removed.
10. Log every affected table.

The connection removal must be performed through `friends_remove_friend()` where possible, so BuddyBoss totals, notifications, and native hooks remain consistent.

## 6.2 Unblock operation

When A unblocks B:

1. Let BuddyBoss complete its native unblock operation.
2. Delete only A → B in Streams.
3. Delete only A → B in Socials.
4. Verify both deletions.
5. Do not recreate a connection or follow.
6. Log the result.

# 7. Follow synchronization

## 7.1 BuddyBoss follow to Streams

Attach to the actual follow lifecycle hooks used by the installed BuddyBoss version:

```text
bp_start_following
bp_stop_following
```

The follow object should be used to determine:

```text
follower_id
leader_id
```

For BuddyBoss follow A → B:

1. Set the ledger field `follow_a_to_b = 1`.
2. Insert or update the Streams followers row:
   - `follower_id = A's wo_user_id`
   - `following_id = B's wo_user_id`
   - `active = 1`
3. Verify the row.
4. Do not update QuickDate.

For an unfollow:

1. Delete only A → B in Streams.
2. Verify the row is absent.
3. Leave QuickDate unchanged.
4. Do not delete an independent QuickDate ordinary follow unless the product decision explicitly requires it.

The original proposal requested removal from Socials for BuddyBoss unfollow, but the corrected semantic model should not do this automatically. An ordinary follow is independent on each platform unless it was explicitly created by the synchronized follow action.

## 7.2 Streams follow to BuddyBoss

After a successful local Streams insertion:

1. Send a signed `follow` command with Streams external IDs.
2. WordPress maps both IDs to WordPress IDs.
3. WordPress checks the BuddyBoss block state.
4. WordPress calls `bp_start_following()`.
5. The BuddyBoss follow hook updates the canonical ledger.
6. The Streams projection is verified as already present.

If the WordPress request fails, the local Streams follow remains intact and the external client must retry.

## 7.3 Streams unfollow to BuddyBoss

After the local Streams deletion succeeds:

1. Send a signed `unfollow` command.
2. WordPress calls `bp_stop_following()`.
3. The BuddyBoss hook updates the ledger.
4. QuickDate is not modified.

# 8. WoWonder `Wo_IsFollowRequested()` correction

The requested automatic acceptance behavior should be implemented carefully.

The current function is a predicate, but the proposed modification performs an `UPDATE` inside the predicate and then returns `false`. That is problematic because:

- A function named `Wo_IsFollowRequested()` is expected to answer a question.
- Returning `false` after successfully accepting a request is misleading.
- Callers may perform a second insert or take the wrong branch.
- QuickDate and Streams semantics can become coupled accidentally if shared functions are reused.

The preferred implementation is:

1. Force integration-created Streams follows to `active = 1` in `Wo_RegisterFollow()`.
2. Keep `Wo_IsFollowRequested()` read-only.
3. Add a separate helper such as `Wo_AcceptPendingFollowImmediately()`.
4. Call that helper only from the Streams follow action or synchronization path.

If the automatic acceptance requirement must be implemented inside `Wo_IsFollowRequested()`, then the function must:

- update the matching pending row,
- verify the row is now active,
- clear relevant caches,
- return `true` only if the operation successfully completed.

However, this is less desirable than keeping query and mutation functions separate.

## 8.1 Required `Wo_RegisterFollow()` behavior

For integration and normal Streams follows:

```text
active = 1
```

The following settings must not convert the integration follow into a pending request:

- `follow_privacy`
- `confirm_followers`
- `connectivitySystem`

Because the Friends System is disabled, there should be no Streams follow approval flow.

## 8.2 Required local verification

After inserting a Streams follow:

1. Check the insert query result.
2. Query the exact row.
3. Confirm `active = 1`.
4. Log:
   - database name,
   - table name,
   - follower ID,
   - following ID,
   - operation,
   - verification result.
5. Only then submit the WordPress synchronization command.

# 9. QuickDate synchronization

## 9.1 QuickDate Add Friend

The current QuickDate `add_friend()` ultimately uses the overloaded `followers` mechanism. The handler must explicitly treat this action as a BuddyBoss connection request.

After the local pending row is successfully inserted and verified:

```text
origin = socials
operation = connection_request
```

The command must contain QuickDate external IDs, not WordPress IDs.

WordPress then calls:

```text
friends_add_friend( $actor_wp_id, $target_wp_id, false )
```

BuddyBoss’s connection restrictions remain active because the native BuddyBoss function performs the authorization and relationship checks.

## 9.2 QuickDate Add Friend approval

After the QuickDate pending row is converted to an accepted friendship and reciprocal local data is confirmed:

```text
origin = socials
operation = connection_accept
```

WordPress resolves the IDs and calls:

```text
friends_accept_friendship( $friendship_id )
```

Do not call a generic follow function for this operation.

## 9.3 QuickDate rejection or withdrawal

After the local QuickDate pending row has been deleted:

- Use `connection_reject` when the recipient declines.
- Use `connection_withdraw` when the requester cancels.

The command must use the actual requester as the actor for withdrawal. Do not use the currently logged-in recipient by mistake.

## 9.4 QuickDate unfriend

After the accepted QuickDate connection projection is removed:

```text
origin = socials
operation = connection_remove
```

WordPress calls the native BuddyBoss removal function.

The implementation must not delete independent ordinary follows.

## 9.5 QuickDate ordinary Follow

QuickDate ordinary Follow must be implemented as a distinct code path. It must not call `add_friend()`.

After the local ordinary follow succeeds:

```text
origin = socials
operation = follow
```

WordPress calls:

```text
bp_start_following()
```

The BuddyBoss hook then projects the follow into Streams.

For ordinary unfollow:

```text
origin = socials
operation = unfollow
```

WordPress calls:

```text
bp_stop_following()
```

This has no effect on BuddyBoss connections.

# 10. Client and path corrections

The previous guide contains fragile path calculations such as:

```text
dirname(__DIR__, 3)
dirname(__DIR__, 5)
```

These are unsafe because the correct parent depth differs between:

- `streams/assets/includes/functions_one.php`
- `streams/themes/sunshine/layout/extra_js/content.phtml`
- `social/requests/ajax/profile.php`
- `social/requests/ajax/useractions.php`

Use one of these approaches instead:

1. Define the Buzzjuice root explicitly in the client.
2. Resolve the root from `$_SERVER['DOCUMENT_ROOT']`.
3. Use an environment variable such as `BUZZJUICE_ROOT`.
4. Use a controlled list of candidate paths and verify the file exists.

The client should refuse to continue if it cannot load the shared client file. It should log:

```text
client file not found
platform
operation
source file
resolved candidate paths
```

Do not silently skip synchronization when the client file is missing.

# 11. Authentication

The existing HMAC approach is preferable to using the WordPress username and password configuration.

Use platform-specific secrets:

```text
BZJ_STREAMS_SYNC_SECRET
BZJ_SOCIALS_SYNC_SECRET
```

Use `BUZZ_SSO_SECRET` only as a documented fallback.

The signature input must be:

```text
timestamp + "." + raw_json_body
```

The request must include:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

The control plane must validate:

1. The timestamp is numeric.
2. The timestamp is within the permitted clock-skew window.
3. The HMAC matches the expected platform secret.
4. The origin is one of:
   - `streams`
   - `socials`
5. The operation is permitted for that origin.
6. The event UUID has not already been processed.

The REST route should remain:

```text
/wp-json/bzj/v6/connection-management
```

Do not use a generic `/relationship` route.

## 12.4 Startup connection verification

The control plane should write a startup diagnostic entry confirming:

```text
WordPress database connected
QuickDate database connected
WoWonder database connected
WordPress usermeta table available
QuickDate followers table available
QuickDate blocks table available
WoWonder followers table available
WoWonder blocks table available
```

The log should include the database and table names.

A connection is not considered successful merely because `mysqli` returned an object. The implementation must run a harmless verification query such as:

```text
SELECT 1
```

and verify the required tables with `SHOW COLUMNS` or an equivalent metadata query.

# 13. Database safety requirements

All external database writes must:

1. Use prepared statements where possible.
2. Validate table names against a discovered schema.
3. Never interpolate user-controlled table names.
4. Use integer casts for user IDs.
5. Verify affected rows.
6. Perform a read-back query.
7. Treat an already-existing desired row as an idempotent success.
8. Treat an already-absent deletion target as an idempotent success.
9. Log the MySQL error when the operation fails.

For QuickDate, do not assume a single fixed table prefix. The actual table name must be discovered or configured. The existing helpers indicate that QuickDate uses `users` and likely unprefixed relationship tables, while WoWonder commonly uses names such as `Wo_Followers` and `Wo_Blocks`. The implementation must verify the installed schema rather than relying only on candidate names.

---

# 14. Retry and recovery design

A failed external projection must not cause a successful local action to be rolled back.

The correct behavior is:

```text
Local mutation succeeds
    ↓
WordPress command fails
    ↓
Write pending synchronization event locally
    ↓
Retry with the same event UUID
```

The retry strategy should use exponential backoff, for example:

```text
60 seconds
2 minutes
4 minutes
8 minutes
16 minutes
32 minutes
60 minutes
failed
```

The retry process must actually re-execute the event. It must not merely log that reconciliation is required.

Each retry must:

1. Revalidate identity mappings.
2. Revalidate the requested operation.
3. Recheck the current BuddyBoss state.
4. Apply the operation only if it is still necessary.
5. Mark the event processed when the desired state is confirmed.
6. Mark the event failed after the maximum number of attempts.
7. Preserve the last error.

---

# 15. Reentrancy and loop prevention

The control plane needs an internal synchronization context.

When WordPress calls a native function because of an external command, that function may fire the ordinary BuddyBoss hook. The hook must not create a second command back to the originating platform.

Use an internal context containing:

```text
event_uuid
origin
operation
actor_wp_id
target_wp_id
```

Before processing a hook, the control plane should determine whether the hook was caused by an internal operation.

Do not rely only on a global boolean because nested operations and concurrent requests can overlap.

Pair-level locking should be retained, but the lock name must be deterministic:

```text
bzj_pair_<lower_wp_id>_<higher_wp_id>
```

All operations involving the same pair must acquire this lock before reading and modifying the ledger.

# 17. Required BuddyBoss restriction behavior

BuddyBoss must remain responsible for deciding whether a connection request is allowed.

The control plane must not bypass:

- role restrictions,
- profile-type restrictions,
- gender restrictions,
- moderation restrictions,
- blocked-user restrictions,
- BuddyBoss connection settings,
- BuddyBoss permission checks.

External Add Friend actions must call the native BuddyBoss function. They must not insert directly into the BuddyBoss friendship table.

If BuddyBoss rejects the request, the external platform must leave its local operation pending for reconciliation or remove the local projection according to the configured failure policy. It must not force the request into BuddyBoss.

---

# 18. Blocking policy

The recommended policy is explicitly destructive:

```text
Block
 ├─ remove BuddyBoss connection
 ├─ remove BuddyBoss pending request
 ├─ remove BuddyBoss follow A → B
 ├─ remove BuddyBoss follow B → A
 ├─ remove Streams follows
 ├─ remove Socials relationship projections
 ├─ create Streams block A → B
 └─ create Socials block A → B
```

Unblock is not restorative:

```text
Unblock
 ├─ remove Streams block A → B
 ├─ remove Socials block A → B
 └─ do not recreate any previous relationship
```

This should be documented clearly because users may expect an old connection or follow to return after unblocking.

# Final recommendation

Use the v8.3 architecture only as a starting point. The production implementation should be designated **v8.4**, with these mandatory changes:

- resolve external IDs through `wo_user_id` and `qd_user_id`,
- separate Add Friend from Follow,
- process BuddyBoss hooks as the canonical event source,
- use native BuddyBoss functions for external-origin operations,
- deduplicate friendship lifecycle hooks,
- verify every database write,
- retain durable retry events,
- use platform-specific HMAC secrets,
- correct fragile filesystem paths,
- preserve BuddyBoss request restrictions,
- make blocks destructive and unblocks non-restorative,
- keep all operational logs under `/data/logs`.

The most serious issue in the prior implementation is the assumption that WoWonder or QuickDate user IDs can be passed directly into BuddyBoss functions. That must be corrected before any synchronization testing is considered valid.

Generate the fully developed and functional codes for deployment. Include step by step instructions for implementation wherever appropriate.

- keep Add Friend and Follow distinct

```php name=wp-content/mu-plugins/bzj-connections-sync.php
    public function rest_connection_management(WP_REST_Request $request) {
        $raw_body = file_get_contents('php://input');

        if (empty($raw_body)) {
            return new WP_REST_Response(['error' => 'empty_body'], 400);
        }

        $headers = $request->get_headers();
        $timestamp = isset($headers['x_bzj_timestamp'][0]) ? $headers['x_bzj_timestamp'][0] : '';
        $signature = isset($headers['x_bzj_signature'][0]) ? $headers['x_bzj_signature'][0] : '';

        $data = json_decode($raw_body, true);
        if (!is_array($data)) {
            return new WP_REST_Response(['error' => 'invalid_json'], 400);
        }

        $origin = isset($data['origin']) ? sanitize_text_field($data['origin']) : '';
        $operation = isset($data['operation']) ? sanitize_text_field($data['operation']) : '';
        $event_uuid = isset($data['event_uuid']) ? sanitize_text_field($data['event_uuid']) : '';

        if (!in_array($origin, ['streams', 'socials'], true)) {
            return new WP_REST_Response(['error' => 'unsupported_origin'], 400);
        }

        if (empty($event_uuid)) {
            $event_uuid = wp_generate_uuid4();
            $data['event_uuid'] = $event_uuid;
        }

        if (!$this->verify_origin_signature($raw_body, $timestamp, $signature, $origin)) {
            $this->log('refused_request', [
                'origin' => $origin,
                'operation' => $operation,
                'event_uuid' => $event_uuid,
                'reason' => 'signature_mismatch',
            ]);
            return new WP_REST_Response(['error' => 'invalid_signature'], 401);
        }

        if ($this->event_exists($event_uuid)) {
            return new WP_REST_Response(['status' => 'already_processed'], 200);
        }

        $actor_external_id = isset($data['actor_external_id']) ? intval($data['actor_external_id']) : 0;
        $target_external_id = isset($data['target_external_id']) ? intval($data['target_external_id']) : 0;

        if ($actor_external_id <= 0 || $target_external_id <= 0) {
            return new WP_REST_Response(['error' => 'invalid_user_ids'], 400);
        }

        $actor_wp_id = $this->resolve_external_to_wp_user($origin, $actor_external_id);
        $target_wp_id = $this->resolve_external_to_wp_user($origin, $target_external_id);

        if (!$actor_wp_id || !$target_wp_id) {
            return new WP_REST_Response(['error' => 'unknown_external_user_mapping'], 400);
        }

        $this->record_event($event_uuid, $origin, $operation, $actor_wp_id, $target_wp_id, $actor_external_id, $target_external_id, $data);

        try {
            $this->apply_remote_operation($origin, $operation, $actor_wp_id, $target_wp_id, $data);
            $this->mark_event_processed($event_uuid);
            return new WP_REST_Response(['status' => 'ok', 'event_uuid' => $event_uuid], 200);
        } catch (Exception $e) {
            $this->mark_event_failed($event_uuid, $e->getMessage());
            $this->log('remote_operation_failed', [
                'origin' => $origin,
                'operation' => $operation,
                'event_uuid' => $event_uuid,
                'actor_wp_id' => $actor_wp_id,
                'target_wp_id' => $target_wp_id,
                'message' => $e->getMessage(),
            ]);
            return new WP_REST_Response(['error' => $e->getMessage()], 500);
        }
    }

    private function verify_origin_signature($raw_body, $timestamp, $signature, $origin) {
        if (!is_numeric($timestamp)) {
            return false;
        }

        $diff = abs(time() - intval($timestamp));
        if ($diff > 300) {
            return false;
        }

        $secret = $this->get_secret_for_origin($origin);
        if (empty($secret)) {
            return false;
        }

        $expected = hash_hmac('sha256', $timestamp . '.' . $raw_body, $secret);
        return hash_equals($expected, $signature);
    }

    private function get_secret_for_origin($origin) {
        switch ($origin) {
            case 'streams':
                return defined('BZJ_STREAMS_SYNC_SECRET') ? BZJ_STREAMS_SYNC_SECRET : '';
            case 'socials':
                return defined('BZJ_SOCIALS_SYNC_SECRET') ? BZJ_SOCIALS_SYNC_SECRET : '';
            default:
                return '';
        }
    }

    private function resolve_external_to_wp_user($origin, $external_id) {
        $meta_key = $this->external_meta_key_for_origin($origin);

        if (empty($meta_key)) {
            return 0;
        }

        global $wpdb;

        $sql = $wpdb->prepare(
            "SELECT user_id FROM {$wpdb->usermeta} WHERE meta_key = %s AND meta_value = %s LIMIT 1",
            $meta_key,
            (string) $external_id
        );

        $user_id = $wpdb->get_var($sql);

        if ($user_id === null) {
            return 0;
        }

        return intval($user_id);
    }

    private function external_meta_key_for_origin($origin) {
        switch ($origin) {
            case 'streams':
                return 'wo_user_id';
            case 'socials':
                return 'qd_user_id';
            default:
                return '';
        }
    }

    private function sync_quickdate_request($user_a, $user_b, $state) {
        $db = $this->get_quickdate_db();
        if (!$db) {
            return;
        }

        $table = $this->resolve_quickdate_table($db, ['followers', 'quickdate_followers', 'wd_followers', 'qd_followers', 'friends']);
        if (!$table) {
            return;
        }

        $a = intval($user_a);
        $b = intval($user_b);

        if ($state === 'accepted') {
            $this->upsert_quickdate_connection($db, $table, $a, $b, 1);
            $this->upsert_quickdate_connection($db, $table, $b, $a, 1);
            return;
        }

        $this->upsert_quickdate_connection($db, $table, $a, $b, 0);
    }

    private function clear_quickdate_projection($user_a, $user_b) {
        $db = $this->get_quickdate_db();
        if (!$db) {
            return;
        }

        $table = $this->resolve_quickdate_table($db, ['followers', 'quickdate_followers', 'wd_followers', 'qd_followers', 'friends']);
        if (!$table) {
            return;
        }

        $a = intval($user_a);
        $b = intval($user_b);

        $db->delete($table, ['user_id' => $a, 'friend_id' => $b], ['%d', '%d']);
        $db->delete($table, ['user_id' => $b, 'friend_id' => $a], ['%d', '%d']);
    }

    private function sync_streams_follow($user_a, $user_b, $is_following) {
        $db = $this->get_streams_db();
        if (!$db) {
            return;
        }

        $table = $this->resolve_streams_table($db, ['followers', 'streams_followers', 'wl_followers', 'wo_followers']);
        if (!$table) {
            return;
        }

        $a = intval($user_a);
        $b = intval($user_b);

        if ($is_following) {
            $exists = $db->get_var($db->prepare(
                "SELECT id FROM {$table} WHERE follower_id = %d AND following_id = %d LIMIT 1",
                $a,
                $b
            ));

            if ($exists === null) {
                $db->insert($table, [
                    'follower_id' => $a,
                    'following_id' => $b,
                    'active' => 1,
                    'created_at' => current_time('mysql'),
                    'updated_at' => current_time('mysql'),
                ], ['%d', '%d', '%d', '%s', '%s']);
            } else {
                $db->update($table, ['active' => 1, 'updated_at' => current_time('mysql')], ['id' => $exists], ['%d', '%s'], ['%d']);
            }
            return;
        }

        $db->delete($table, ['follower_id' => $a, 'following_id' => $b], ['%d', '%d']);
    }

    private function upsert_quickdate_connection($db, $table, $user_a, $user_b, $active) {
        if (empty($table) || !$db) {
            return;
        }

        $existing = $db->get_var($db->prepare(
            "SELECT id FROM {$table} WHERE user_id = %d AND friend_id = %d LIMIT 1",
            $user_a,
            $user_b
        ));

        if ($existing === null) {
            $db->insert($table, [
                'user_id' => $user_a,
                'friend_id' => $user_b,
                'active' => $active,
                'created_at' => current_time('mysql'),
                'updated_at' => current_time('mysql'),
            ], ['%d', '%d', '%d', '%s', '%s']);
            return;
        }

        $db->update($table, [
            'active' => $active,
            'updated_at' => current_time('mysql'),
        ], ['id' => $existing], ['%d', '%s'], ['%d']);
    }

    private function event_exists($event_uuid) {
        global $wpdb;
        $table = $wpdb->prefix . 'bzj_sync_events';
        $count = $wpdb->get_var($wpdb->prepare(
            "SELECT COUNT(*) FROM {$table} WHERE event_uuid = %s",
            $event_uuid
        ));
        return intval($count) > 0;
    }

                'target_wp_id' => $target_wp_id,

                'target_external_id' => $target_external_id,
                'payload' => $payload_json,
                'status' => 'processing',
                'attempts' => 1,
            ],
            ['%s', '%s', '%s', '%d', '%d', '%d', '%d', '%s', '%s', '%d']
        );
    }

    private function mark_event_processed($event_uuid) {
        global $wpdb;
        $table = $wpdb->prefix . 'bzj_sync_events';
        $wpdb->update(
            $table,
            ['status' => 'processed', 'processed_at' => current_time('mysql')],
            ['event_uuid' => $event_uuid],
            ['%s', '%s'],
            ['%s']
        );
    }

    private function mark_event_failed($event_uuid, $message) {
```

2) Shared client library for external integrations

File:
```php name=shared/bzj-sync-client.php
<?php
/**
 * BZJ Sync Client
 * Use from Streams or Socials custom handlers after local DB mutation succeeds.
 */

final class BZJ_Sync_Client {
    private $base_url;
    private $secret;
    private $origin;
    private $timeout = 15;

    public function __construct($origin, $base_url, $secret) {
        $this->origin = $origin;
        $this->base_url = rtrim($base_url, '/');
        $this->secret = $secret;
    }

    public function send($operation, $actor_external_id, $target_external_id, array $extra = []) {
        $payload = [
            'origin' => $this->origin,
            'operation' => $operation,
            'actor_external_id' => intval($actor_external_id),
            'target_external_id' => intval($target_external_id),
            'event_uuid' => wp_generate_uuid4(),
        ];

        $payload = array_merge($payload, $extra);

        $raw = wp_json_encode($payload);
        if ($raw === false) {
            throw new Exception('payload_json_encode_failed');
        }

        $ts = time();
        $signature = hash_hmac('sha256', $ts . '.' . $raw, $this->secret);

        $response = wp_remote_post($this->base_url . '/wp-json/bzj/v6/connection-management', [
            'method' => 'POST',
            'timeout' => $this->timeout,
            'headers' => [
                'Content-Type' => 'application/json',
                'X-BZJ-Timestamp' => (string) $ts,
                'X-BZJ-Signature' => $signature,
            ],
            'body' => $raw,
        ]);

        if (is_wp_error($response)) {
            throw new Exception($response->get_error_message());
        }

        $code = wp_remote_retrieve_response_code($response);
        $body = wp_remote_retrieve_body($response);

        if ($code >= 400) {
            throw new Exception('sync_http_error: ' . $code . ' ' . $body);
        }

        $decoded = json_decode($body, true);
        if (!is_array($decoded)) {
            throw new Exception('sync_invalid_http_response');
        }

        return $decoded;
    }
}
```

Critical implementation notes

- Never call Woo/WP or QuickDate DB functions directly from external platforms.
- Never send external IDs and pretend they are WordPress IDs.
- Distinguish connection actions from follow actions.
- Verify every mutation with a direct read-back query.
- Keep event UUIDs stable across retries.
- Use HMAC signatures.
- Keep logs in `/wp-content/logs` or the path defined in `BZJ_LOG_PATH`.
- Do not rely on `Wo_IsFollowRequested()` as an impure “test-and-accept” function.

The code above is intentionally generic and safe. You must still verify:

- whether your environment requires `bp_block_user` or a different moderation hook.
