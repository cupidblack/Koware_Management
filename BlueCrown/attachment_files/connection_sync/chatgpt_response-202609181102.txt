## Updated architecture

I’ve consolidated the working **v8.4.1 baseline** with the feasible GitHub corrections and the current Buzzjuice source code into a **v8.5.0 control-plane design**.

The most important correction is that **BuddyBoss remains the canonical authority**, while Streams and Socials submit *intent commands* to BuddyBoss rather than writing BuddyBoss relationship tables directly. The external IDs are resolved through `wo_user_id` / `qd_user_id` before any BuddyBoss function is called. This directly addresses the most serious issue identified in the GitHub review. 

The current Streams code confirms that `Wo_RegisterFollow()` can create pending follows because of `confirm_followers` and `connectivitySystem`, despite your Friends System being disabled. The v8.5 design therefore forces synchronized Streams follows to `active = 1` at the write point. 

Likewise, QuickDate's `add_friend()` currently goes through the overloaded `followers` mechanism, confirming that **Add Friend and ordinary Follow must be separated at the semantic handler level**, rather than trying to infer the meaning from `Wo_DeleteFollow()`. 

### The resulting model

```text
                         BUDDYBOSS
                    CANONICAL AUTHORITY
                           │
              ┌────────────┴────────────┐
              │                         │
         STREAMS                     SOCIALS
     follows + blocks        connections + follows + blocks
```

With:

```text
BuddyBoss Connection
    ↕
QuickDate Add Friend

BuddyBoss Follow
    ↕
Streams Follow

QuickDate Follow
    → BuddyBoss Follow
    → Streams Follow
```

and **QuickDate Follow never becomes a BuddyBoss connection**.

# Important correction regarding `Wo_IsFollowRequested()`

I **did not implement the requested database mutation inside `Wo_IsFollowRequested()`**.

That recommendation is technically weaker than changing `Wo_RegisterFollow()` itself.

The current function is a predicate:

```php
Wo_IsFollowRequested()
```

but the proposed modification would make it mutate the database and then return a misleading result. The GitHub review correctly identified this problem. 

Instead, v8.5 changes:

```text
Wo_RegisterFollow()
        ↓
active = 1
        ↓
read-back verification
        ↓
BuddyBoss synchronization
```

while leaving:

```text
Wo_IsFollowRequested()
```

read-only.

That is the safer implementation for the disabled Friends System.

# One particularly important semantic change

The original proposal had some ambiguity around QuickDate Follow.

I recommend the final architecture be:

```text
QUICKDATE ADD FRIEND
        ↓
connection_request
        ↓
BUDDYBOSS CONNECTION
```

but:

```text
QUICKDATE ORDINARY FOLLOW
        ↓
follow
        ↓
BUDDYBOSS FOLLOW
        ↓
STREAMS FOLLOW
```

This is important because QuickDate's installed `followers` table is overloaded: `active = 0` represents a pending request while `active = 1` can represent either an accepted friendship or an ordinary follow. The GitHub review explicitly identified this ambiguity. 

Therefore this should **not** be driven from generic `Wo_DeleteFollow()`.

# Blocking is now explicitly destructive

The final behavior is:

```text
A blocks B
│
├── BuddyBoss block A → B
├── remove BuddyBoss connection
├── remove pending BuddyBoss request
├── remove BuddyBoss A → B follow
├── remove BuddyBoss B → A follow
├── Streams block A → B
├── remove Streams A → B follow
├── remove Streams B → A follow
├── Socials block A → B
└── remove Socials relationship projections
```

Then:

```text
A unblocks B
│
├── remove Streams block
├── remove Socials block
└── do NOT restore previous connection/follows
```

This matches the recommended proactive enforcement model.
