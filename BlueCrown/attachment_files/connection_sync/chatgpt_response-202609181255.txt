## Updated architecture

I reviewed the working v8.4.1 behavior, the v8.x control-plane architecture, and the current Buzzjuice source files. The most important correction is to make the synchronization model **explicitly asymmetric**:

> **BuddyBoss/WordPress owns the canonical relationship state. Streams and Socials are projections of that state.**

The current BuddyBoss source confirms the exact lifecycle hooks and argument structures: requests/acceptance fire through `friends_friendship_requested` and `friends_friendship_accepted`; rejection and withdrawal have dedicated hooks; and `friends_friendship_deleted` fires immediately before a friendship is deleted, followed by `friends_friendship_post_delete`. 

The current Streams source also confirms that WoWonder's follower table uses `following_id`, `follower_id`, and `active`, and that its normal implementation can create `active=0` pending rows. 

QuickDate's current implementation confirms that `add_friend()` is built on the same follower table, while approval changes the pending row to `active=1`. 

### The major v8.6 corrections

1. **BuddyBoss connection → QuickDate friend request**
2. **BuddyBoss connection cancellation/rejection → QuickDate request cancellation**
3. **BuddyBoss connection acceptance/removal → QuickDate friend acceptance/removal**
4. **BuddyBoss follow → Streams only**
5. **BuddyBoss follow → NEVER QuickDate**
6. **Streams follow → BuddyBoss follow only**
7. **Streams unfollow → BuddyBoss unfollow only**
8. **QuickDate add-friend → BuddyBoss connection request**
9. **QuickDate follow → treated exactly like a connection request, not a follow**
10. **QuickDate accepted friend → BuddyBoss connection**
11. **QuickDate unfriend → BuddyBoss connection removal**
12. **All three platforms' blocks remain synchronized**
13. **Blocking removes existing BuddyBoss friendship and both-direction follows**
14. **Unblocking never recreates a previous relationship**
15. **Streams pending follows are normalized to immediate follows**
16. **No WoWonder or QuickDate relationship API is used**
17. **Pair locks + UUID events + recovery queue remain**
18. **Database/table connection success is logged**
19. **The existing `shared/db_helpers.php` remains the database authority**
20. **The working v8.4.1 control-plane architecture is retained rather than unnecessarily rebuilt**

This also fixes an architectural problem in the earlier v8.x implementation: its BuddyBoss-follow projection could write into QuickDate's `followers` table. That is incompatible with your clarified requirement that **QuickDate follows are actually connection/friend-request semantics, while BuddyBoss follows are independent and should only reach Streams**.

# Why the Streams change is important

Your current Streams `Wo_RegisterFollow()` explicitly changes `$active` to `0` when `confirm_followers` or the WoWonder connectivity system requires confirmation. 

That conflicts with:

> Streams has no friend system and every follow must take immediate effect.

The supplied surgical patch therefore makes:

```php
$active = 1;
```

authoritative for Buzzjuice Streams.

I also changed `Wo_IsFollowRequested()` so that **legacy `active=0` rows are automatically normalized to `active=1`** rather than being treated as a genuine pending Buzzjuice relationship.

This is deliberately done only in **Streams**.

It should **not** be applied to QuickDate because QuickDate's `active=0` row is meaningful: it represents its friend-request state. QuickDate's current `approve_friend_request()` explicitly looks for that pending state and then changes it to active.

# Blocking model

The block implementation is now deliberately stronger than simply inserting a block row.

When:

```text
A blocks B
```

the control plane:

```text
BuddyBoss block
       ↓
remove BB friendship
       ↓
remove BB A→B follow
       ↓
remove BB B→A follow
       ↓
Streams A→B block
       ↓
Socials A→B block
       ↓
remove external relationship rows
```

This is consistent with the current BuddyBoss moderation implementation, whose `BP_Moderation::save()` and `delete()` expose the `bp_moderation_after_save` and `bb_moderation_after_delete` lifecycle hooks. 

Most importantly:

```text
UNBLOCK
   ↓
remove block only
   ↓
DO NOT restore friendship
   ↓
DO NOT restore follows
```

That prevents stale relationships from being resurrected.

# Database architecture

The existing two control-plane tables remain:

```text
wp_bzj_relationships
wp_bzj_relationship_events
```

The first is the current canonical pair state:

```text
connection_state
requested_by

follow_a_to_b
follow_b_to_a

block_a_to_b
block_b_to_a
```

The second is the durable event/outbox layer.

This is important because a successful BuddyBoss action should not become permanently inconsistent merely because, for example:

```text
BuddyBoss update succeeded
        ↓
QuickDate DB temporarily unavailable
```

The external projection is then retained as a pending event and retried.

# REST security

The external platforms do **not** receive a WordPress authentication session.

Instead:

```text
Streams/Socials
      ↓
HMAC-SHA256
      ↓
/wp-json/bzj/v6/connection-management
      ↓
WordPress
      ↓
BuddyBoss mutation
      ↓
BuddyBoss hooks
      ↓
canonical projection
```

The request contains:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

and the signature is calculated over:

```text
timestamp + "." + raw JSON body
```

using:

```text
BUZZ_SSO_SECRET
```

with a five-minute replay window.

This is preferable to putting the WordPress API username/password into Streams/Socials relationship requests.

# One particularly important safeguard

The v8.6 control plane **does not use the WordPress REST API to manipulate BuddyBoss when it is already running inside WordPress**.

It directly calls the existing BuddyBoss functions:

```php
friends_add_friend()
friends_accept_friendship()
friends_reject_friendship()
friends_withdraw_friendship()
friends_remove_friend()

bp_start_following()
bp_stop_following()
```

That preserves BuddyBoss's existing business rules, including your existing restrictions on who can send connection requests.

For example, `friends_add_friend()` itself creates the friendship object and fires the appropriate BuddyBoss lifecycle hook. 

That means your existing role/profile/gender/other connection restrictions remain part of the canonical decision process rather than being bypassed by the synchronization layer.
