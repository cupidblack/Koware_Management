# 2. Revised relationship model

There are actually **four distinct relationship concepts** and they must not be conflated.

| Relationship        | BuddyBoss     | Streams           | Socials                         |
| ------------------- | ------------- | ----------------- | ------------------------------- |
| Connection / Friend | authoritative | none              | accepted Add Friend projection  |
| Pending Connection  | authoritative | none              | pending Add Friend projection   |
| Ordinary Follow A→B | authoritative | follow projection | ordinary follow projection only |
| Block A→B           | authoritative | block projection  | block projection                |

This distinction is especially important in QuickDate because its `followers` table is overloaded: `active=0` can represent a pending Add Friend request, while `active=1` can represent either an ordinary follow or an accepted friendship. Therefore `Wo_DeleteFollow()` cannot safely determine what semantic event occurred. Synchronization must happen in the semantic handler itself. ([GitHub][2])

### Consequently, one important item in the original proposal changes

The original proposal said:

> QuickDate ordinary Follow → same logic as Add Friend → BuddyBoss connection.

That should **not** be implemented.

The corrected model is:

```text
QuickDate ordinary Follow
        ↓
BuddyBoss Follow
        ↓
Streams Follow

NOT:

QuickDate ordinary Follow
        ↓
BuddyBoss Connection
```

This prevents ordinary follows from consuming the BuddyBoss connection-request workflow. ([GitHub][2])

# 3. Revised Integration Proposal

## A. BuddyBoss → Socials

### A1. Connection request

When A sends a BuddyBoss connection request to B:

```text
BuddyBoss:
A → B pending connection

        ↓

QuickDate:
A → B pending Add Friend
```

No Streams operation occurs.

This existing v8.4.1 functionality is retained. ([GitHub][1])

### A2. Connection withdrawal/cancellation

This is the currently known defect.

Both BuddyBoss lifecycle paths must be covered:

```text
friends_friendship_deleted
friends_friendship_post_delete
```

with the **pre-delete path preferred** and the post-delete path retained as compatibility fallback.

The friendship participants must be obtained from the friendship object/record, not assumed from the current logged-in user.

The QuickDate projection must delete **only**:

```sql
WHERE following_id = recipient_id
AND follower_id = requester_id
AND active = 0
```

It must not delete an accepted friendship or ordinary follow.

The two lifecycle hooks must be deduplicated using the friendship ID and normalized participant pair. This is the principal correction identified by GitHub. ([GitHub][1])

## B. BuddyBoss connection acceptance

When B accepts A:

```text
BuddyBoss
A ↔ B connected

        ↓

QuickDate
A ↔ B accepted friendship
```

No Streams operation.

The existing v8.4.1 acceptance projection is retained. ([GitHub][1])

## C. BuddyBoss connection removal

When either participant removes the BuddyBoss connection:

```text
BuddyBoss
A ↔ B removed

        ↓

QuickDate
A ↔ B accepted friendship projection removed
```

Any independent ordinary follows must remain untouched.

This distinction is important because an accepted friendship and ordinary follow can coexist.

# 4. BuddyBoss follows

BuddyBoss remains authoritative.

### Follow

```text
BuddyBoss A → B follow
        ↓
Streams A → B follow
```

No Socials projection.

This existing v8.4.1 behavior is retained. ([GitHub][3])

### Unfollow

```text
BuddyBoss A → B unfollow
        ↓
Streams A → B unfollow
```

No Socials ordinary-follow operation is required from the BuddyBoss event.

The existing Socials relationship should not be indiscriminately deleted merely because BuddyBoss follow changed.

# 5. BuddyBoss blocking

Blocking should be treated as **destructive moderation**, not simply as another relationship flag.

Recommended behavior:

```text
A blocks B on BuddyBoss
        │
        ├── remove BuddyBoss A ↔ B connection
        ├── remove pending BuddyBoss connection request
        ├── remove BuddyBoss A → B follow
        ├── remove BuddyBoss B → A follow
        │
        ├── Streams A → B block
        ├── remove Streams A → B follow
        ├── remove Streams B → A follow
        │
        └── Socials A → B block
            remove relevant relationship projections
```

This matches the destructive-block policy documented in the surgical patch analysis. ([GitHub][2])

### Unblock

Unblocking is **non-restorative**:

```text
A unblocks B
       │
       ├── remove Streams block
       └── remove Socials block
```

Old friendships/follows are **not automatically recreated**.

That avoids unexpectedly restoring relationships after a moderation action. ([GitHub][2])

BuddyBoss's own connection-request restrictions must remain intact. The synchronization layer must not replace or bypass those native eligibility rules.

### Follow

The critical change is:

```text
Wo_RegisterFollow()
        ↓
active = 1
        ↓
read-back verification
        ↓
signed WordPress command
        ↓
BuddyBoss native follow
        ↓
```

`Wo_IsFollowRequested()` should **remain a read-only predicate**.

The proposed mutation inside `Wo_IsFollowRequested()` should therefore **not be implemented**. GitHub specifically identified this as a design error. Instead, `Wo_RegisterFollow()` must force immediate active follow behavior. ([GitHub][1])

The relevant value should be:

```php
$active = 1;
```

and the request/approval branch should not remain capable of creating a pending follow.

# 15. Common signed REST contract

The current v8.5.0 implementation uses `event_uuid`; the GitHub review recommends standardizing the contract around `event_id`. The important thing is consistency.

I recommend standardizing the production contract as:

```json
{
  "origin": "streams",
  "operation": "follow",
  "event_id": "UUID",
  "actor_external_id": 123,
  "target_external_id": 456
}
```

or:

```json
{
  "origin": "socials",
  "operation": "connection_request",
  "event_id": "UUID",
  "actor_external_id": 123,
  "target_external_id": 456
}
```

The accepted origins are only:

```text
streams
socials
```

and the allowed operations are:

```text
connection_request
connection_accept
connection_reject
connection_withdraw
connection_remove
follow
unfollow
block
unblock
```

The external IDs are resolved through:

```text
streams external ID → wp_usermeta.wo_user_id
socials external ID → wp_usermeta.qd_user_id
```

They are never passed directly to BuddyBoss functions. ([GitHub][1])

# 16. REST authentication correction

The control-plane endpoint should be:

```text
/wp-json/bzj/v6/connection-management
```

with:

```text
X-BZJ-Timestamp
X-BZJ-Signature
X-BZJ-Platform
```

The current v8.5.0 client sends timestamp/signature but does **not** send `X-BZJ-Platform`, while the endpoint documentation expects it. The latest GitHub review specifically identifies this discrepancy. ([GitHub][4])

The WordPress endpoint must enforce:

```php
$payload['origin'] === $request->get_header('X-BZJ-Platform')
```

and only accept:

```text
streams
socials
```

for the header.

The signature should continue to be:

```text
HMAC-SHA256(
    timestamp + "." + raw_json,
    platform_secret
)
```

with separate:

```text
BZJ_STREAMS_SYNC_SECRET
BZJ_SOCIALS_SYNC_SECRET
```

falling back to the existing `BUZZ_SSO_SECRET` only where already supported.

# 17. Idempotency

Every logical event receives one UUID.

That UUID must survive every retry.

Example:

```text
QuickDate follow
event_id = 4c...9a

first request → timeout
retry          → same event_id
retry          → same event_id
```

Never generate a new event UUID for each retry.

The existing event ledger should continue to use:

```text
pending
processing
processed
failed
```

and the filesystem outbox should retain the same UUID. The README already defines this model. ([GitHub][5])

# 19. Database verification

Every external mutation should now follow:

```text
WRITE
 ↓
READ BACK
 ↓
CONFIRMED?
 ├── YES → send next synchronization command
 └── NO  → log failure / retry
```

For example, Streams follow:

```sql
INSERT INTO followers
(
    following_id,
    follower_id,
    active
)
VALUES
(
    target,
    actor,
    1
);
```

Then:

```sql
SELECT id
FROM followers
WHERE following_id = target
  AND follower_id = actor
  AND active = 1
LIMIT 1;
```

Only after that succeeds should the WordPress command be sent.

The same pattern applies to deletes and blocks.

# 27. One additional architectural correction

I would **not** make `wwqd_bridge.php` the primary relationship-control engine.

It should remain a shared identity/database utility layer.

The responsibilities should be separated:

```text
db_helpers.php
    ↓
database connections

wwqd_bridge.php
    ↓
identity / cross-platform ID helpers

bzj-connections-sync.php
    ↓
canonical relationship control plane

bzj-connection-client.php
    ↓
external signed command transport

bzj-sync-outbox-cron.php
    ↓
retry transport
```

This keeps the relationship state machine in one place instead of creating a second hidden relationship engine in the bridge.
