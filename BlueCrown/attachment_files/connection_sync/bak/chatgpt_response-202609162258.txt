## Updated Architecture — v8.1

I reviewed the original proposal, the previous implementation, the two GitHub reviews, the existing `bzj-connections-sync.php`, BuddyBoss friendship functions, QuickDate friendship/follow logic, WoWonder follow/block functions, and the shared database layer.

The GitHub recommendations are directionally correct, but I would **not** adopt them literally in a few places. In particular:

* BuddyBoss remains the **actual source of truth**; the synchronization ledger is a state/recovery projection, not a second authority.
* WoWonder Friends remain completely excluded because the Streams Friends System is disabled.
* QuickDate `followers` must be treated as a **shared friend/follow projection**, rather than assuming every row represents only a follow.
* External actions must mutate BuddyBoss first and then allow BuddyBoss's native lifecycle to drive synchronization.
* BuddyBoss's native `friends_add_friend()`, `friends_accept_friendship()`, `friends_reject_friendship()`, `friends_withdraw_friendship()`, `friends_remove_friend()`, `bp_start_following()` and `bp_stop_following()` remain the canonical mutation functions. The supplied BuddyBoss source confirms the friendship hooks and that `friends_friendship_deleted` fires before the friendship is actually deleted. 
* The BuddyBoss follow hooks must consume the `BP_Activity_Follow` object and extract `follower_id`/`leader_id`; the earlier scalar-ID assumption was incorrect. 
* QuickDate's `add_friend()` actually calls `Wo_RegisterFollow($to, active_user)`, meaning `followers.following_id` is the **recipient** and `follower_id` is the **requester**. This corrects an important directional error in the previous implementation. 
* WoWonder's normal follow representation is likewise `following_id = followed user`, `follower_id = actor`. 
* Blocking is now explicitly destructive: connection + both follows are removed, external blocks are created, and **unblocking never restores the previous relationships**.
* The proposed `bp_moderation_block_created()` approach should not be inserted blindly. The supplied BuddyBoss member-moderation class establishes the `user` moderation type, while the earlier simplistic function-based recommendation is not established by the supplied source. 
* Direct external database access uses the existing `db_helpers.php` connection layer, which already exposes `get_wowonder_db()` and `get_qd_db_conn()`. ([GitHub][1])
* No WoWonder or QuickDate API is used.

## Relationship rules

### Connections

| Origin           | BuddyBoss             | Streams | Socials                                                            |
| ---------------- | --------------------- | ------- | ------------------------------------------------------------------ |
| BB request       | Pending               | None    | Pending friend                                                     |
| BB accept        | Connected             | None    | Active friend                                                      |
| BB reject        | Removed               | None    | Pending friend removed                                             |
| BB withdraw      | Removed               | None    | Pending friend removed                                             |
| BB unfriend      | Removed               | None    | Friend removed unless an independent follow still requires the row |
| Socials request  | Creates BB request    | None    | Pending                                                            |
| Socials accept   | Creates BB connection | None    | Active friend                                                      |
| Socials unfriend | Removes BB connection | None    | Friend removed                                                     |

This preserves the distinction you specifically wanted: **QuickDate Add Friend maps to BuddyBoss Connection, not to a WoWonder/BB follow.**

### Follows

```text
BuddyBoss follow
      ↓
Streams follow
      +
Socials follow

Streams follow
      ↓
BuddyBoss follow
      ↓
Socials follow

Socials follow
      ↓
BuddyBoss follow
      ↓
Streams follow
```

The external action first invokes the BuddyBoss native operation, so the BuddyBoss hook becomes the synchronization trigger.

### Blocks

```text
A blocks B
   │
   ├── BuddyBoss block
   ├── remove BB connection
   ├── remove A → B BB follow
   ├── remove B → A BB follow
   │
   ├── Streams block A → B
   ├── remove Streams follows both directions
   │
   ├── Socials block A → B
   └── remove Socials friend/follow projections
```

Then:

```text
A unblocks B
      ↓
remove block only
      ↓
NO relationship restoration
```

That is the correct long-term model.

# Important QuickDate correction

This was one of the most important fixes.

The previous implementation had the friend projection direction backwards in places.

QuickDate's actual code does:

```php
Wo_RegisterFollow($to, (int) self::ActiveUser()->id)
```

and `Wo_RegisterFollow()` inserts:

```text
following_id = recipient
follower_id  = requester
```

So:

```text
A sends friend request to B

QuickDate:
following_id = B
follower_id  = A
active = 0
```

When accepted:

```text
following_id = B
follower_id  = A
active = 1
```

The new implementation follows that model. 

This is particularly important because QuickDate uses the same `followers` table for both its friendship and follow mechanisms.

# Security

The external endpoint is:

```text
POST /wp-json/bzj/v6/connection-management
```

Authentication:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

Signature:

```text
HMAC-SHA256(
    timestamp + "." + raw JSON body,
    BUZZ_SSO_SECRET
)
```

The endpoint rejects:

* missing authentication
* invalid signatures
* stale timestamps
* malformed JSON
* invalid origin
* invalid operation
* invalid UUID
* invalid users
* unmapped external IDs
* same actor/target

The five-minute replay window and UUID idempotency are retained from the GitHub recommendation.

# Critical implementation improvement

One subtle but important correction from the earlier implementation is how external operations interact with BuddyBoss hooks.

It is **wrong** to do:

```text
External action
   ↓
set "internal context"
   ↓
friends_add_friend()
   ↓
BuddyBoss hook suppressed
```

because then the canonical BuddyBoss hook never performs the normal projection.

The updated architecture instead does:

```text
Streams/Socials
      ↓
signed REST
      ↓
BuddyBoss native mutation
      ↓
BuddyBoss native hook
      ↓
canonical ledger
      ↓
Streams + Socials projection
```

Internal cascading operations—particularly block → unfriend/unfollow—use the context guard to prevent loops.

That gives us a clean distinction between:

**external-originated canonical mutation**

and

**internal synchronization mutation**.

# Recovery / self-healing

If this occurs:

```text
BuddyBoss     ✓
Streams       ✓
Socials       ✗
```

we do **not** roll back BuddyBoss.

Instead:

```text
BuddyBoss remains authoritative
          ↓
failed projection recorded
          ↓
recovery queue
          ↓
retry
          ↓
Socials repaired
```

This follows the GitHub/previous analysis recommendation and avoids pretending that three independent databases can participate in one atomic transaction. 

Reconciliation periodically performs:

```text
Read BuddyBoss
      ↓
refresh synchronization state
      ↓
compare/projection
      ↓
repair Streams
      ↓
repair Socials
```

Thus:

> **If the platforms disagree, BuddyBoss wins.**
