## Recommendation

Do **not** deploy `bzj-connections-sync-v8.1.1.php` unchanged. Its overall architecture is sound, but several implementation defects can cause exactly the failures already observed:

- external BuddyBoss accept/reject/withdraw operations may run without the correct WordPress current user;
- QuickDate’s shared `followers` table can incorrectly convert a pending friend request into an accepted friend when an ordinary follow is created;
- external `created_at` values may be written with the wrong data type;
- database write failures are not consistently surfaced;
- the BuddyBoss moderation hooks must be treated as version-dependent;
- `Wo_IsFollowRequested()` must not recursively call `Wo_AcceptFollowRequest()`;
- the existing `wwqd_bridge.php` contains recursive fallback wrappers that must not be used as the synchronization control plane.

The corrected design below keeps:

1. **BuddyBoss as the only relationship authority**.
2. **Streams Friends disabled**.
3. **Streams and Socials as projections**.
4. **Direct database writes only for external projections**.
5. **Signed REST commands only to mutate BuddyBoss**.
6. **QuickDate connection and follow state treated as one shared directional row**.
7. **File logging in `/data/logs`**.
8. **Durable recovery events in WordPress only for retry/idempotency, not general-purpose logging**.

# 1. Final relationship model

## 1.1 Connections

| Action | BuddyBoss | Streams | Socials |
|---|---|---|---|
| A requests B | Pending connection | No change | `followers(B,A,active=0)` |
| B accepts A | Connected | No change | Friend projection becomes `active=1` |
| A withdraws | Removed | No change | Pending friend row removed unless required by follow |
| B rejects | Removed | No change | Pending friend row removed unless required by follow |
| A or B unfriends | Removed | No change | Friend projection removed unless required by follow |

A QuickDate add-friend action **must never create a BuddyBoss follow**.

## 1.2 Follows

| Action | BuddyBoss | Streams | Socials |
|---|---|---|---|
| A follows B | Follow A→B | Follow A→B | Follow A→B |
| A unfollows B | Removed | Removed | Removed unless a QuickDate friend projection still requires the row |

## 1.3 Blocks

Blocking is dominant and destructive:

1. Create the BuddyBoss block.
2. Remove the BuddyBoss connection.
3. Remove BuddyBoss follows in both directions.
4. Create the external block in Streams and Socials.
5. Remove external follows in both directions.
6. Remove the QuickDate friend projection.
7. Unblocking removes only the block.
8. Unblocking does not restore previous connections or follows.

# 3. Correct external BuddyBoss mutations

The BuddyBoss source shows that:

- `friends_accept_friendship()` accepts by friendship ID;
- `friends_reject_friendship()` requires the logged-in user to be the recipient;
- `friends_withdraw_friendship()` requires the logged-in user to be the initiator;
- the friendship lifecycle hooks are fired by BuddyBoss itself.

Therefore, external requests must temporarily establish the correct WordPress current user.

Add this method to the `BZJ_Connections_Sync` class:

```php name=bzj-connections-sync.php url=https://github.com/cupidblack/Koware_Management/blob/dd0d58d47db8ca4d177bf6243905999420206260/BlueCrown/attachment_files/bzj-connections-sync-v8.1.1.php
private function run_as_wp_user($user_id, $callback) {
    $user_id = absint($user_id);

    if ($user_id < 1 || !is_callable($callback)) {
        return new WP_Error(
            'bzj_invalid_wp_user_context',
            'A valid WordPress user is required.'
        );
    }

    $previous_user_id = get_current_user_id();
    $previous_user = wp_get_current_user();

    wp_set_current_user($user_id);

    try {
        return call_user_func($callback);
    } catch (Throwable $e) {
        $this->log('WordPress user-context operation failed', array(
            'user_id' => $user_id,
            'error' => $e->getMessage(),
        ));

        return new WP_Error(
            'bzj_wp_user_context_exception',
            $e->getMessage()
        );
    } finally {
        if ($previous_user instanceof WP_User && !empty($previous_user->ID)) {
            wp_set_current_user((int) $previous_user->ID);
        } else {
            wp_set_current_user((int) $previous_user_id);
        }
    }
}
```

# 5. Correct QuickDate relationship projection

This is the most important external projection correction.

QuickDate uses the same `followers` table for:

- pending friend requests;
- accepted friends;
- ordinary follows.

Therefore the row’s desired state must be calculated from the **BuddyBoss state**, not from the event type alone.

The following rules must be used:

```text
connection = connected
    => QuickDate friend row active=1

connection = requested
    => QuickDate pending friend row active=0

connection = none and follow A→B exists
    => QuickDate follow row active=1

connection = none and follow A→B does not exist
    => Remove only A→B if no other relationship requires it
```

Do not let a BuddyBoss ordinary follow blindly update a pending QuickDate friend request to `active=1`.

Add this method:

```php name=bzj-connections-sync.php url=https://github.com/cupidblack/Koware_Management/blob/dd0d58d47db8ca4d177bf6243905999420206260/BlueCrown/attachment_files/bzj-connections-sync-v8.1.1.php
private function qd_desired_direction_state($actor_wp, $target_wp) {
    $ledger = $this->get_ledger($actor_wp, $target_wp);

    $connection_state = isset($ledger['connection_state'])
        ? (string) $ledger['connection_state']
        : 'none';

    if ('connected' === $connection_state) {
        return 1;
    }

    if ('requested' === $connection_state) {
        /*
         * QuickDate has no independent column for a simultaneous ordinary
         * follow plus pending friend request. Preserve the friend-request
         * state until the request is accepted or removed.
         */
        return 0;
    }

    $pair = $this->pair($actor_wp, $target_wp);
    $actor_wp = absint($actor_wp);

    if ($actor_wp === (int) $pair[0]) {
        return !empty($ledger['follow_a_to_b']) ? 1 : 0;
    }

    return !empty($ledger['follow_b_to_a']) ? 1 : 0;
}
```

        function_exists('friends_check_friendship_status') &&
        function_exists('friends_remove_friend') &&
        'is_friend' === friends_check_friendship_status($actor, $target)

            friends_remove_friend($actor, $target);
        } finally {
            $this->pop_context();
        }

        return;
    }

        array($actor, $target),
        array($target, $actor),
    ) as $direction) {
        $follower = absint($direction[0]);
        $leader = absint($direction[1]);

        if (
            function_exists('bp_is_following') &&
            bp_is_following(array(
                'leader_id' => $leader,
                'follower_id' => $follower,
            ))
        ) {

                'origin' => 'internal_block_cascade',
                'operation' => self::OP_UNFOLLOW,
                'actor' => $follower,
                'target' => $leader,
            ));

            try {
                bp_stop_following(array(
                    'leader_id' => $leader,
                    'follower_id' => $follower,
                ));
            } finally {
                $this->pop_context();
            }

# 8. REST endpoint rules

The endpoint remains:

```text
POST /wp-json/bzj/v6/connection-management
```

The signed body must use external IDs:

```json
{
  "origin": "streams",
  "event_id": "uuid-v4",
  "operation": "follow",
  "actor_id": 123,
  "target_id": 456,
  "authenticated_id": 123
}
```

The signature must be generated over the exact raw JSON body:

```text
HMAC-SHA256(timestamp + "." + raw_json_body, BUZZ_SSO_SECRET)
```

Headers:

```text
X-BZJ-Timestamp: 1726516800
X-BZJ-Signature: <hexadecimal-hmac>
```

The endpoint must reject:

- missing signature;
- missing timestamp;
- stale timestamp;
- malformed JSON;
- invalid UUID;
- unknown origin;
- unknown operation;
- same actor and target;
- missing external-to-WordPress mappings;
- blocked follow or connection attempts;
- failed native BuddyBoss operations.

External applications must not send WordPress IDs as `actor_id` or `target_id`.

# 9. Streams integration

Because Streams has no `wp-load.php`, it must not call WordPress functions directly.

The Streams action boundary should:

2. If successful, send a signed request to WordPress.

## 9.1 Shared Streams command helper

Add this to a Streams-loaded shared file, preferably near the end of `functions_one.php` or in a separately included helper:

```php name=streams-bzj-sync.php
<?php

if (!function_exists('bzj_streams_sync_command')) {
    function bzj_streams_sync_command($operation, $actor_id, $target_id, $event_id = '') {
        $operation = preg_replace('/[^a-z_]/', '', strtolower((string) $operation));
        $actor_id = (int) $actor_id;
        $target_id = (int) $target_id;

        if (
            !$operation ||
            $actor_id < 1 ||
            $target_id < 1 ||
            $actor_id === $target_id
        ) {
            return array(
                'success' => false,
                'error' => 'Invalid synchronization command.',
            );
        }

        $secret = getenv('BUZZ_SSO_SECRET');

        if (!$secret && defined('BUZZ_SSO_SECRET')) {
            $secret = BUZZ_SSO_SECRET;
        }

        if (!$secret) {
            error_log('[BZJ Streams Sync] BUZZ_SSO_SECRET is missing.');
            return array(
                'success' => false,
                'error' => 'Synchronization secret is unavailable.',
            );
        }

        $event_id = $event_id ?: sprintf(
            '%04x%04x-%04x-%04x-%04x-%04x%04x%04x%04x',
            mt_rand(0, 0xffff),
            mt_rand(0, 0xffff),
            mt_rand(0, 0xffff),
            mt_rand(0, 0x0fff) | 0x4000,
            mt_rand(0, 0x3fff) | 0x8000,
            mt_rand(0, 0xffff),
            mt_rand(0, 0xffff),
            mt_rand(0, 0xffff),
            mt_rand(0, 0xffff)
        );

        $payload = array(
            'origin' => 'streams',
            'event_id' => $event_id,
            'operation' => $operation,
            'actor_id' => $actor_id,
            'target_id' => $target_id,
            'authenticated_id' => $actor_id,
        );

        $raw_body = json_encode(
            $payload,
            JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE
        );

        $timestamp = time();

        $signature = hash_hmac(
            'sha256',
            $timestamp . '.' . $raw_body,
            $secret
        );

        $ch = curl_init(
            'https://buzzjuice.net/wp-json/bzj/v6/connection-management'
        );

        curl_setopt_array($ch, array(
            CURLOPT_POST => true,
            CURLOPT_POSTFIELDS => $raw_body,
            CURLOPT_RETURNTRANSFER => true,
            CURLOPT_CONNECTTIMEOUT => 5,
            CURLOPT_TIMEOUT => 15,
            CURLOPT_HTTPHEADER => array(
                'Content-Type: application/json',
                'Content-Length: ' . strlen($raw_body),
                'X-BZJ-Timestamp: ' . $timestamp,
                'X-BZJ-Signature: ' . $signature,
            ),
        ));

        $response_body = curl_exec($ch);
        $curl_error = curl_error($ch);
        $http_code = (int) curl_getinfo($ch, CURLINFO_HTTP_CODE);

        curl_close($ch);

        if ($response_body === false || $curl_error) {
            error_log('[BZJ Streams Sync] HTTP failure: ' . $curl_error);

            return array(
                'success' => false,
                'error' => 'WordPress synchronization request failed.',
                'event_id' => $event_id,
            );
        }

        $response = json_decode($response_body, true);

        if ($http_code < 200 || $http_code >= 300 || !is_array($response)) {
            error_log('[BZJ Streams Sync] Invalid response: ' . $response_body);

            return array(
                'success' => false,
                'error' => 'WordPress synchronization returned an invalid response.',
                'event_id' => $event_id,
                'http_code' => $http_code,
            );
        }

        return $response;
    }
}
```

# 13. Recovery and reconciliation

The recovery queue should not roll back BuddyBoss.

When a projection fails:

```text
BuddyBoss succeeds
Streams or Socials fails
        ↓
Record pending event
        ↓
Retry projection
        ↓
BuddyBoss remains unchanged
```

Recovery must always:

1. read the current BuddyBoss state;
2. refresh the synchronization ledger from BuddyBoss;
3. project the current canonical state;
4. mark the event processed only after projections succeed.

Do not use the ledger to downgrade BuddyBoss.

# 17. Final expected event paths

## BuddyBoss request

```text
BuddyBoss friends_add_friend()
    ↓
friends_friendship_requested
    ↓
ledger = requested
    ↓
QuickDate followers(B,A,active=0)
```

## Socials add-friend

```text
QuickDate add_friend()
    ↓
signed connection_request
    ↓
friends_add_friend(A,B)
    ↓
friends_friendship_requested
    ↓
QuickDate pending projection
```

## Streams follow

```text
Wo_RegisterFollow()
    ↓
local Streams follow
    ↓
signed follow command
    ↓
bp_start_following()
    ↓
bp_start_following hook
    ↓
Streams + Socials ordinary follow projections
```

## Block

```text
Any platform block
    ↓
signed block command, if external
    ↓
BuddyBoss block
    ↓
remove BB connection
    ↓
remove BB follows in both directions
    ↓
project Streams block
    ↓
project Socials block
    ↓
remove external follows/friend projections
```

## Unblock

```text
Any platform unblock
    ↓
BuddyBoss unblock
    ↓
remove Streams block
    ↓
remove Socials block
    ↓
do not restore prior relationships
```

This is the appropriate final architecture for Buzzjuice because it preserves BuddyBoss restrictions and moderation behavior, avoids the disabled WoWonder Friends system, prevents QuickDate friend/follow corruption, avoids direct platform-to-platform authority loops, and provides durable recovery when either external database is temporarily unavailable.
