# 1. What changed architecturally

The fundamental architecture is now:

```text
                         ┌─────────────────────────────┐
                         │      WORDPRESS / BB         │
                         │   CANONICAL CONTROL PLANE   │
                         │                             │
                         │ Connections                 │
                         │ Follows                     │
                         │ Blocks                      │
                         │ Relationship Ledger         │
                         │ Event Ledger                │
                         └──────────────┬──────────────┘
                                        │
                         signed intent │ native BB functions
                                        │
              ┌─────────────────────────┴────────────────────────┐
              │                                                  │
       ┌──────▼──────┐                                    ┌──────▼──────┐
       │   STREAMS   │                                    │   SOCIALS   │
       │  WoWonder   │                                    │  QuickDate  │
       │             │                                    │             │
       │ local DB    │                                    │ local DB    │
       │ mutation    │                                    │ mutation    │
       │ verification│                                    │ verification│
       └─────────────┘                                    └─────────────┘
```

This is materially different from allowing each application to manipulate the other applications' databases.

The latest GitHub review correctly concluded that external platforms should issue **intent commands**, while BuddyBoss remains responsible for executing native WordPress relationship operations. ([GitHub][1])

# 2. Canonical relationship model

### BuddyBoss connections

```text
none
pending
connected
```

BuddyBoss remains authoritative.

QuickDate mirrors these states:

| BuddyBoss | QuickDate                           |
| --------- | ----------------------------------- |
| pending   | requester → recipient `active=0`    |
| connected | reciprocal `active=1`               |
| rejected  | pending row removed                 |
| withdrawn | pending row removed                 |
| removed   | connection-owned projection removed |

No Streams friendship is created because the WoWonder Friends System is disabled. This is consistent with the latest architecture recommendation. ([GitHub][1])

### Ordinary follows

The directional model is:

```text
A → B
```

and remains independent from friendship.

The resulting synchronization is:

```text
BuddyBoss Follow
       ↓
Streams Follow

Streams Follow
       ↓
BuddyBoss Follow

Socials Follow
       ↓
BuddyBoss Follow
       ↓
Streams Follow
```

Ordinary follows **do not generate Add Friend requests**. ([GitHub][1])

# 3. QuickDate Add Friend and Follow are now explicitly separated

This is one of the most important corrections.

The QuickDate `followers` table is overloaded. An `active=1` row can represent either an ordinary follow or an accepted friendship. The latest review specifically warned against using the generic `Wo_DeleteFollow()` function as the semantic synchronization mechanism. ([GitHub][1])

Therefore v8.4.0 uses separate commands:

```text
connection_request
connection_accept
connection_reject
connection_withdraw
connection_remove

follow
unfollow

block
unblock
```

That distinction is built into the new control plane.

# 4. External IDs are no longer treated as WordPress IDs

This fixes a significant v8.3.0 architectural weakness.

Streams sends:

```json
{
  "origin": "streams",
  "actor_external_id": 123,
  "target_external_id": 456
}
```

Socials sends:

```json
{
  "origin": "socials",
  "actor_external_id": 123,
  "target_external_id": 456
}
```

WordPress resolves them through:

```text
Streams ID → wp_usermeta.wo_user_id
Socials ID → wp_usermeta.qd_user_id
```

Only after successful, unambiguous mapping does WordPress obtain:

```text
actor_wp_id
target_wp_id
```

and pass those to:

```text
friends_add_friend()
friends_accept_friendship()
friends_reject_friendship()
friends_withdraw_friendship()
friends_remove_friend()

bp_start_following()
bp_stop_following()

BuddyBoss moderation functions
```

This is explicitly one of the corrections recommended in the latest GitHub analysis. ([GitHub][1])

# 5. BuddyBoss lifecycle handling

The v8.4 control plane uses the native BuddyBoss lifecycle:

```text
friends_friendship_requested
friends_friendship_accepted
friends_friendship_rejected
friends_friendship_withdrawn
friends_friendship_deleted
```

Importantly, I have **not** treated both `friends_friendship_deleted` and `friends_friendship_post_delete` as separate connection-removal events.

The BuddyBoss source confirms that `friends_friendship_deleted` fires immediately before deletion and `friends_friendship_post_delete` after deletion. 

This was a likely contributor to the earlier one-sided removal problem.

The handler uses the actual friendship participants rather than assuming the current logged-in user is the initiator.

That directly addresses the previous:

> “works when B removes A, but not when A removes B”

failure.

# 6. BuddyBoss restrictions remain authoritative

This is preserved.

When Socials or Streams asks WordPress to create a connection:

```php
friends_add_friend( $actor_wp_id, $target_wp_id, false );
```

is used.

Therefore the existing BuddyBoss rules that determine whether a connection request is permitted remain in the execution path rather than being bypassed.

The BuddyBoss source confirms that `friends_add_friend()` accepts the initiator, recipient and `force_accept`, with `false` creating the normal pending request.

# 7. Blocking has been strengthened

The new model treats:

```text
BLOCK
```

as dominant.

If A blocks B:

### BuddyBoss

* block A → B
* remove existing connection
* remove pending connection
* remove A → B follow
* remove B → A follow

### Streams

* create A → B block
* remove affected follow

### Socials

* create A → B block
* remove relationship/follow projections

And:

```text
UNBLOCK
```

only removes the blocks.

It does **not** automatically restore friendship or follows.

This follows the latest recommended semantics. ([GitHub][1])

# 8. `Wo_IsFollowRequested()` correction

I deliberately **did not** implement the proposed database mutation inside:

```php
Wo_IsFollowRequested()
```

That would make a predicate mutate the database.

The latest GitHub review correctly identified this as dangerous because callers expect the function to answer:

```text
Is there a pending request?
```

rather than:

```text
Accept the request.
```

The v8.4 implementation therefore keeps it read-only and introduces:

```php
Wo_AcceptPendingFollowImmediately()
```

instead. ([GitHub][1])

More importantly, normal Buzzjuice Streams follows are forced to:

```text
active = 1
```

because the Friends System is disabled.

So the primary fix is actually at `Wo_RegisterFollow()`, not by corrupting the semantics of `Wo_IsFollowRequested()`.

# 12. Synchronization loop prevention

The new control plane uses an internal synchronization context rather than relying solely on a global boolean.

For example:

```text
Socials
  ↓
connection_request
  ↓
WordPress
  ↓
friends_add_friend()
  ↓
BuddyBoss hook
```

The hook is aware that the native operation was internally initiated and therefore does not generate another external command.

This prevents:

```text
Socials → WP → Socials → WP → Socials...
```

The pair lock is deterministic:

```text
bzj_pair_<lower_wp_id>_<higher_wp_id>
```

which is also the pattern recommended in the latest review. ([GitHub][1])

# 15. Important improvement over the old v8.3.0 Socials logic

The v8.3 implementation could not reliably distinguish:

```text
ordinary QuickDate follow
```

from:

```text

```

because both ultimately use the same `followers` table.

v8.4 adds explicit projection fields to the relationship ledger:


This gives the control plane semantic ownership information that the QuickDate table itself does not contain.

That is the key architectural mechanism for avoiding the earlier “unfriend accidentally deletes follow” problem.

# 5. Resulting synchronization architecture

The final flow is:

```text
                         ┌─────────────────────┐
                         │ WordPress/BuddyBoss  │
                         │  CANONICAL STATE    │
                         └──────────┬──────────┘
                                    │
                    ┌───────────────┼───────────────┐
                    │               │               │
                    ▼               ▼               ▼
              BB connection     BB follow       BB block
                    │               │               │
                    └───────────────┼───────────────┘
                                    ▼
                         Canonical relationship
                               ledger/event
                                    │
                         ┌──────────┴──────────┐
                         ▼                     ▼
                  WoWonder Streams       QuickDate Socials
                  directional follow     friend/follow/block
```

For external-origin actions:

```text
Streams/Socials
      │
      │ signed command
      ▼
WordPress REST
      │
      ▼
native BuddyBoss operation
      │
      ▼
BuddyBoss lifecycle hook
      │
      ▼
canonical ledger
      │
      ├──────────────► Streams
      │
      └──────────────► Socials
```

This is important because the external platforms **do not become competing sources of truth**.

# 6. Connection semantics

### BuddyBoss request

```text
BB:
A → B pending

Socials:
A → B active=0

Streams:
nothing
```

### BuddyBoss accept

```text
BB:
A ↔ B connected

Socials:
A → B active=1
B → A active=1

Streams:
nothing
```

The reciprocal QuickDate projection is retained from the proven v8.1 behavior. 

### BuddyBoss reject/withdraw

```text
BB:
request removed

Socials:
pending projection removed
```

### BuddyBoss unfriend

```text
BB:
connection removed

Socials:
connection projection removed

ordinary independent follows:
preserved
```

This distinction is particularly important because QuickDate's `followers` table serves multiple relationship meanings.

# 7. Block semantics

Blocking remains **destructive**.

If A blocks B:

### BuddyBoss

```text
A ↔ B connection removed
A → B follow removed
B → A follow removed
A → B block created
```

### Streams

```text
A → B block
A → B follow removed
B → A follow removed
```

### Socials

```text
A → B block
relationship projections removed
```

The original working implementation already followed this destructive model. 

Unblocking does **not** recreate anything.

```text
unblock
   ↓
block removed only
```

That is intentional.

# 8. Durable retry

Install:

```text
/shared/bzj-sync-outbox-cron.php
```

Then configure a five-minute cron:

```cron
*/5 * * * * /usr/bin/php /FULL/PATH/shared/bzj-sync-outbox-cron.php >/dev/null 2>&1
```

The client keeps the **same event UUID** when retrying.

That is important for idempotency.

The WordPress control plane also maintains:

```text
wp_bzj_relationships
wp_bzj_relationship_events
```

and recovery/reconciliation jobs.

The original v8.1 architecture already had durable event/recovery infrastructure; v8.4.1 keeps that concept instead of replacing it with transient HTTP calls.
