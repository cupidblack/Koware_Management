I would **not deploy the supplied v8.5.0 file unchanged**. The correct production baseline is the working v8.4.1 control plane, with a small number of targeted corrections. A wholesale rewrite risks reintroducing the regressions already observed in the v8.4.0 rewrite.

The most important corrections are:

1. Preserve the proven v8.4.1 BuddyBoss hooks and QuickDate projection functions.
2. Fix BuddyBoss request cancellation by handling both pre-delete and post-delete lifecycle paths with deduplication.
3. Use one consistent REST payload contract.
4. Require and validate `X-BZJ-Platform`.
5. Keep `Wo_IsFollowRequested()` read-only.
6. Force WoWonder follows to `active = 1` in `Wo_RegisterFollow()`.
7. Do not use the generic QuickDate `Wo_DeleteFollow()` as a synchronization trigger.
8. Do not directly create BuddyBoss moderation records from unauthenticated external commands unless the installed BuddyBoss moderation authorization path is explicitly verified.
9. Preserve independent QuickDate ordinary follows when a BuddyBoss connection is removed.
10. Add required-column diagnostics and five-minute recovery scheduling.

BuddyBoss connections ─────────► QuickDate Add Friend

## Critical correction: QuickDate Add Friend versus ordinary Follow

QuickDate uses the `followers` table for multiple meanings:

```text
active = 0  pending Add Friend
active = 1  ordinary follow or accepted friendship
```

Therefore these operations must remain separate:

```text
connection_request
connection_accept
connection_reject
connection_withdraw
connection_remove

follow
unfollow

block
unblock
```

Do not infer the operation from `Wo_DeleteFollow()`. The synchronization call must be made from the semantic handler:

```text
add_friend()
approve_friend_request()
disapprove_friend_request()
withdraw/cancel handler
unfriend handler
ordinary follow handler
ordinary unfollow handler
block handler
unblock handler
```

This is necessary to prevent an ordinary QuickDate follow from being mistaken for an accepted friendship.

## Required REST contract

All external commands should use exactly this structure:

```json
{
  "origin": "streams",
  "operation": "follow",
  "event_id": "UUID",
  "actor_external_id": 123,
  "target_external_id": 456
}
```

or:

```json
{
  "origin": "socials",
  "operation": "connection_request",
  "event_id": "UUID",
  "actor_external_id": 123,
  "target_external_id": 456
}
```

The endpoint should accept:

```text
X-BZJ-Timestamp
X-BZJ-Signature
X-BZJ-Platform
```

The following must all be true:

```php
$payload['origin'] === $request->get_header('X-BZJ-Platform')
```

The endpoint must reject:

```text
actor_id
target_id
```

unless backward compatibility is intentionally retained. The preferred fields are:

```text
actor_external_id
target_external_id
```

The external IDs must be mapped through:

```text
streams → wp_usermeta.wo_user_id
socials → wp_usermeta.qd_user_id
```

They must never be passed directly into BuddyBoss functions.

## BuddyBoss connection cancellation fix

The reported defect is most likely caused by relying on a friendship object after the friendship has already been deleted, or by assuming the current logged-in user is the requester.

The implementation should:

1. Read `initiator_user_id` and `friend_user_id` from the hook-supplied friendship object where available.
2. If the object is unavailable, retrieve the friendship record before deletion.
3. Use `friends_friendship_deleted` as the primary pre-delete handler.
4. Use `friends_friendship_post_delete` only as a compatibility fallback.
5. Deduplicate using a short-lived key containing:

```text
friendship ID
lower participant ID
higher participant ID
```

The cancellation projection must remove only the pending QuickDate row:

```sql
DELETE FROM followers
WHERE following_id = :recipient_id
  AND follower_id = :requester_id
  AND active = 0
```

It must not remove an independent ordinary follow.

## BuddyBoss block policy

Blocking remains destructive:

```text
A blocks B
├── BuddyBoss block A → B
├── remove existing BuddyBoss connection
├── remove pending BuddyBoss request
├── remove BuddyBoss A → B follow
├── remove BuddyBoss B → A follow
├── create Streams A → B block
├── remove Streams follows in both directions
├── create Socials A → B block
└── remove Socials relationship projections
```

Unblocking is non-restorative:

```text
A unblocks B
├── remove BuddyBoss block
├── remove Streams block
├── remove Socials block
└── do not restore former relationships
```

The existing BuddyBoss restrictions for connection requests must remain active. External requests must call native BuddyBoss functions such as:

```php
friends_add_friend()
friends_accept_friendship()
friends_reject_friendship()
friends_withdraw_friendship()
friends_remove_friend()
bp_start_following()
bp_stop_following()
```

However, direct construction of `BP_Moderation` from an external REST command should not be considered production-safe until the installed BuddyBoss moderation authorization path has been verified. The preferred implementation is:

```text
external command
    ↓
authenticated WordPress callback
    ↓
validated actor and target
    ↓
installed BuddyBoss moderation function or verified moderation path
    ↓
BuddyBoss moderation hook
```

Do not bypass role, profile-type, gender, or other BuddyBoss moderation restrictions.

## WoWonder changes

Do **not** modify `Wo_IsFollowRequested()` to update the database. It is a predicate and must remain read-only.

The required behavior belongs in `Wo_RegisterFollow()`:

```php
$active = 1;
```

The follow flow should be:

```text
Wo_RegisterFollow()
    ↓
insert or activate followers row
    ↓
verify active=1
    ↓
send signed follow intent to WordPress
```

The relevant local database row is:

```text
following_id = target WoWonder ID
follower_id  = actor WoWonder ID
active       = 1
```

For unfollow:

```text
delete local directional row
verify row is absent
send signed unfollow intent to WordPress
```

For block and unblock:

```text
local block mutation
verify local result
send block/unblock intent to WordPress
```

The WoWonder API endpoints must not be used.

## QuickDate changes

### Add Friend

After the local pending row is successfully written and verified:

```text
origin   = socials
operation = connection_request
actor    = QuickDate requester ID
target   = QuickDate recipient ID
```

### Approve Add Friend

After the local request is converted to an accepted friendship and reciprocal rows are verified:

```text
origin    = socials
operation = connection_accept
actor     = QuickDate recipient/acceptor ID
target    = original requester ID
```

### Reject

After deleting the pending row:

```text
origin    = socials
operation = connection_reject
actor     = recipient who rejected
target    = original requester
```

### Withdraw

After deleting the pending row:

```text
origin    = socials
operation = connection_withdraw
actor     = original requester
target    = recipient
```

### Unfriend

After removing the accepted QuickDate friendship projection:

```text
origin    = socials
operation = connection_remove
actor     = user performing the unfriend
target    = other participant
```

Do not send `unfollow` for an unfriend operation.

### Ordinary Follow

After a normal QuickDate follow is inserted or activated:

```text
origin    = socials
operation = follow
actor     = QuickDate follower
target    = QuickDate followed user
```

After a normal QuickDate unfollow:

```text
origin    = socials
operation = unfollow
actor     = QuickDate follower
target    = QuickDate followed user
```

Ordinary QuickDate follows must never create BuddyBoss connection requests.

## Recovery and idempotency

The event UUID must be generated once by the originating platform and retained for every retry.

The WordPress event record should support:

```text
pending
processing
processed
failed
```

Failed external commands must be retried with exponential backoff. Recovery should run every five minutes rather than hourly.

A successful local external action must not be rolled back merely because WordPress is temporarily unavailable:

```text
local mutation succeeds
    ↓
WordPress request fails
    ↓
outbox event is stored
    ↓
same UUID is retried
```

The retry must re-check the desired state rather than blindly repeating a destructive operation.
