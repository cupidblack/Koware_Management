# 1. Final architecture

The important conceptual change is that we should **not synchronize three chat systems**.

We should eliminate the concept of three independent chats.

```text
                         BUZZJUICE NETWORK
                                │
                                ▼
                 ┌─────────────────────────────┐
                 │      WORDPRESS              │
                 │                             │
                 │   BP Better Messages        │
                 │   ───────────────────       │
                 │   Canonical conversations   │
                 │   Canonical messages        │
                 │   Participants              │
                 │   Read/unread state         │
                 │   Notifications             │
                 │   Messaging policy          │
                 │   Chat requests             │
                 │   Entitlements              │
                 │   Identity resolution       │
                 └──────────────┬──────────────┘
                                │
                       Private signed gateway
                                │
             ┌──────────────────┴──────────────────┐
             │                                     │
             ▼                                     ▼
     ┌─────────────────┐                   ┌─────────────────┐
     │ BUZZJUICE       │                   │ BUZZJUICE       │
     │ STREAMS         │                   │ SOCIALS         │
     │                 │                   │                 │
     │ Unified adapter │                   │ Unified adapter │
     └────────┬────────┘                   └────────┬────────┘
              │                                     │
              ▼                                     ▼
       WoWonder UI                           QuickDate UI
```

BP Better Messages already provides private threads, group threads, participants, unread/read state, message retrieval, pagination, message creation, and the extension hooks needed for centralized policy enforcement. 

So the target becomes:

> **One message system with three interfaces.**

Not:

> Three message systems continuously synchronizing.

That distinction is the key to making this maintainable.

And the data ownership is unambiguous:

| System                       | Owns                                                                        |
| ---------------------------- | --------------------------------------------------------------------------- |
| BuddyBoss / Connections      | relationships, blocks, connection state                                     |
| Better Messages              | conversations, messages, participants, read/unread                          |
| BZJ Messaging                | authentication, cross-platform policy, chat requests, entitlements, gateway |
| Streams                      | UI + local platform session + optional realtime transport                   |
| Socials                      | UI + local platform session                                                 |
| Palmier/myCRED               | eventual temporary chat entitlement funding                                 |
| Streams/Socials old chat DBs | legacy history during transition                                            |

That separation is the part I would protect most strongly.

## The biggest architectural decision

I would **not implement `wp-load.php` yet, not replicate messages, not migrate historical chat, not synchronize native groups, and not build WebSockets first**.

The first working milestone should be extraordinarily simple:

```text
User A on Socials
        ↓
sends "Hello"
        ↓
BZJ Messaging Gateway
        ↓
BP Better Messages
        ↓
User B on WordPress
        ↓
sees "Hello"

User B replies on WordPress
        ↓
BP Better Messages
        ↓
BZJ Gateway
        ↓
User A on Socials
        ↓
sees reply
```

Then repeat:

```text
Streams → WordPress
WordPress → Streams
Streams → Socials
Socials → Streams
```

**Only after that works should we start adding the sophisticated Buzzjuice layer.**

That gives us a very clean evolution:

```text
PHASE 1
Unified text chat

        ↓

PHASE 2
Notifications + requests + blocks

        ↓

PHASE 3
H&S policy

        ↓

PHASE 4
Palmier temporary access

        ↓

PHASE 5
Groups

        ↓

PHASE 6
Push

        ↓

PHASE 7
Streams realtime

        ↓

PHASE 8
Advanced media/features

        ↓

PHASE 9
Selective legacy migration
```

This is substantially more robust than trying to make WoWonder, QuickDate and Better Messages behave as three equal messaging backends.
