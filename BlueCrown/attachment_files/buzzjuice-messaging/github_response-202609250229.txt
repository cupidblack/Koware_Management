## Recommendation

Use **BP Better Messages as the canonical network-wide messaging system**, while initially keeping WordPress isolated from the Streams and Socials runtimes.

The first implementation should be a **private, signed integration gateway** hosted by WordPress:

```text
WordPress / BP Better Messages
        ↑↓ private HTTPS bridge
Streams adapter ── QuickDate adapter
        ↑                    ↑
 WoWonder chat UI       QuickDate chat UI
```

Do **not** make Streams or Socials APIs the integration contract, and do not directly write into BP Better Messages tables from either application. Instead:

1. WordPress owns threads, messages, participants, read state, moderation, gating, and notifications.
2. Streams and Socials expose only small, private adapter endpoints for their own authenticated browser sessions.
3. Those adapters call the WordPress gateway.
4. The existing local chat systems become legacy or transitional views.
5. Real-time delivery is added after the request/response version is stable.

This is more feasible and safer than trying to synchronize three independent message databases.

# 1. Findings from the review

## 1.1 BP Better Messages is suitable as the canonical backend

The plugin already has the core primitives required for a unified network chat:

- Private threads.
- Group threads.
- Chat-room threads.
- Participants and participant management.
- Read/unread counts.
- Message deletion, editing, loading, and pagination.
- Attachments, files, stickers, GIFs, reactions, mentions, and optional encryption.
- REST endpoints for:
  - thread lists;
  - individual thread retrieval;
  - new conversations;
  - sending messages;
  - marking messages read;
  - loading older messages;
  - participants;
  - groups and chat rooms.

The plugin creates dedicated tables for threads, messages, recipients, metadata, users, moderation, and groups. The schema is not simply a WordPress post/comment model; for example, the core tables include:

- `threads`
- `messages`
- `recipients`
- `threadsmeta`
- `meta`
- `users`
- `moderation`
- `roles`

The table definitions and migration logic are in [`inc/api/db-migrate.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/api/db-migrate.php#L105-L120) and [`inc/api/db-migrate.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/api/db-migrate.php#L190-L306).

That makes BP Better Messages a much stronger canonical store than trying to make either WoWonder’s `messages` table or QuickDate’s `messages` table the network-wide source of truth.

## 1.2 The plugin already supports the required extension points

BP Better Messages exposes the most important backend extension points:

- `Better_Messages()->functions->new_message()`
- `get_pm_thread_id()`
- `get_unique_pm_thread_id()`
- `get_recipients()`
- `get_messages()`
- `messages_mark_thread_read()`
- `add_participant_to_thread()`
- `remove_participant_from_thread()`
- `better_messages_before_new_thread`
- `better_messages_before_message_send`
- `better_messages_can_send_message`
- `better_messages_message_sent`
- `better_messages_thread_updated`
- `better_messages_new_thread_created`

The plugin itself uses `new_message()` for normal, GIF, sticker, AI, bulk, and forwarded messages. See [`inc/functions.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/functions.php#L2996-L3070) and the REST send implementation in [`inc/rest-api.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/rest-api.php#L936-L1088).

That is important: external integrations can invoke the same internal function and filters used by the native WordPress user interface, instead of bypassing validation and notification behaviour.

## 1.3 Existing gating features are extensible

The plugin already supports restrictions through filters and actions:

- Preventing a new thread.
- Preventing a reply.
- Restricting messages to friends or followers.
- Restricting roles from starting threads or replying.
- Blocked-user restrictions.
- Rate limiting.
- Bad-word restrictions.
- Moderation and pending messages.
- MyCred/GamiPress message charges.

The points add-on already uses:

```php
better_messages_can_send_message
better_messages_message_sent
bp_better_messages_new_thread_created
better_messages_before_new_thread
```

See [`addons/points/points.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/addons/points/points.php#L6-L92).

The most appropriate implementation for the Health & Safety rules is therefore a **separate network policy service/class**, invoked by the same WordPress filters and also by the external gateway before any request reaches BP Better Messages.

The filter must remain the final enforcement point. Client-side controls and remote pre-checks are only user-experience features.

## 1.4 Real-time and polling are already supported

BP Better Messages supports:

- Its own WebSocket mechanism.
- Polling through `checkNew`.
- Incremental message retrieval using update timestamps.
- Thread update timestamps stored in `recipients.last_update`.

The plugin’s polling endpoint uses the user’s last update timestamp and returns changed threads/messages. See [`inc/rest-api.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/rest-api.php#L527-L649).

This makes polling the correct initial integration method. It avoids coupling the first release to either the Streams Node.js transport or the BP Better Messages WebSocket configuration.

## 1.5 Groups require separate treatment

BP Better Messages supports:

- Ordinary multi-user group threads.
- BuddyBoss group conversations.
- Dedicated chat rooms.

The plugin’s group/chat-room implementation handles participants, joining, leaving, auto-add, auto-remove, permissions, moderators, visibility, notification settings, and chat-room cleanup. See [`inc/chats.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/chats.php#L121-L205) and [`inc/chats.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/chats.php#L1419-L1433).

Do not attempt to map a QuickDate or WoWonder group directly into a BP Better Messages group in the first release. Define a clear initial scope:

- **Phase 1:** one-to-one conversations only.
- **Phase 2:** BP Better Messages group conversations.
- **Phase 3:** optional synchronization of native Streams/Socials groups.

Trying to unify group semantics immediately would create conflicts around ownership, membership, moderation, invitations, and deletion.

# 2. Recommended target architecture

## 2.1 Canonical identity mapping

The first requirement is a permanent cross-platform identity map.

The existing connection synchronizer maps WordPress users to external IDs through user metadata:

- `wo_user_id` for Streams.
- `qd_user_id` for Socials.

This pattern is visible in [`bzj-connections-sync.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/mu-plugins/bzj-connections-sync.php#L590-L610).

For chat, use a dedicated mapping table rather than relying only on user metadata:

```text
wp_bzj_chat_identity_map
------------------------
id
wp_user_id
streams_user_id
socials_user_id
external_username
status
created_at
updated_at
```

Recommended constraints:

- One WordPress user can map to at most one Streams user.
- One WordPress user can map to at most one Socials user.
- External IDs must be unique within each platform.
- Mapping must be created only after verified account ownership.
- Never trust a platform-supplied user ID without authenticating the current session.

The mapping must also record whether a platform account is:

- linked;
- pending verification;
- suspended;
- unlinked;
- conflicting.

## 2.2 Private gateway

Create a new WordPress mu-plugin or regular network plugin, for example:

```text
wp-content/mu-plugins/bzj-unified-chat.php
```

It should provide private REST routes such as:

```text
POST /wp-json/bzj/v1/chat/session
GET  /wp-json/bzj/v1/chat/threads
POST /wp-json/bzj/v1/chat/thread
GET  /wp-json/bzj/v1/chat/thread/{id}
POST /wp-json/bzj/v1/chat/thread/{id}/send
POST /wp-json/bzj/v1/chat/thread/{id}/read
GET  /wp-json/bzj/v1/chat/updates
POST /wp-json/bzj/v1/chat/request
POST /wp-json/bzj/v1/chat/request/{id}/accept
POST /wp-json/bzj/v1/chat/request/{id}/decline
```

These are not replacements for the native BP Better Messages REST endpoints. They are a controlled integration layer that:

- authenticates Streams/Socials;
- maps external identities to WordPress IDs;
- applies cross-network chat policy;
- calls BP Better Messages internally;
- converts the response into a platform-neutral format.

For example, the gateway should internally call:

```php
Better_Messages()->functions->new_message(...)
```

rather than directly inserting into `bpbm_messages`.

## 2.3 Signed authentication

The existing [`shared/bzj-connection-client.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/shared/bzj-connection-client.php) demonstrates a useful signed-request pattern:

- timestamp;
- HMAC signature;
- platform header;
- event UUID;
- idempotency.

Use the same general model, but do not reuse the relationship endpoint or credentials.

Each request should contain:

```text
X-BZJ-Platform: streams|socials
X-BZJ-Timestamp: Unix timestamp
X-BZJ-Key-Id: key identifier
X-BZJ-Signature: HMAC-SHA256
X-BZJ-Request-Id: UUID
```

Sign:

```text
timestamp + "." + HTTP method + "." + request path + "." + raw body
```

The gateway must verify:

- timestamp freshness;
- signature;
- platform;
- request ID replay status;
- mapped external identity;
- requested action;
- target user;
- rate limits.

The gateway must not accept a `wp_user_id` supplied by Streams or Socials as authoritative.

## 2.4 User authentication from Streams and Socials

Because WordPress is not currently loaded by either application, there are two viable approaches.

### Preferred first approach: short-lived signed chat session

When a logged-in user opens chat on Streams or Socials:

1. The platform adapter authenticates the local user using the existing platform session.
2. It sends a signed server-to-server request to WordPress.
3. WordPress verifies the external account mapping.
4. WordPress returns a short-lived chat session token, ideally 5–15 minutes.
5. Browser requests use that token against the gateway.
6. The adapter refreshes it when needed.

This avoids loading WordPress on every request and avoids exposing the platform’s permanent session or JWT to WordPress.

### Later approach: load WordPress

Loading `wp-load.php` from `streams/assets/init.php` or `social/bootstrap.php` could provide direct access to WordPress functions, but it has serious risks:

- memory and boot-time overhead;
- conflicting constants and globals;
- session name collisions;
- cookie/session interference;
- duplicated database bootstrapping;
- WordPress plugin side effects;
- potential output/header conflicts;
- difficult rollback.

Therefore, `wp-load.php` should be treated as a later optimization or shared-runtime experiment, not the initial integration design.

# 4. Message model

Use a platform-neutral response contract.

Example:

```json
{
  "thread_id": "wp:481",
  "type": "private",
  "participants": [
    {
      "user_id": "wp:91",
      "display_name": "User A",
      "avatar": "https://..."
    }
  ],
  "messages": [
    {
      "message_id": "wp:9021",
      "sender_id": "wp:91",
      "body": "Hello",
      "created_at": 1760000000,
      "is_read": false
    }
  ],
  "permissions": {
    "can_reply": true,
    "can_accept": false,
    "can_decline": false
  },
  "policy": {
    "status": "allowed",
    "reason": "",
    "credits_remaining": 0,
    "access_expires_at": null
  }
}
```

Use namespaced identifiers such as `wp:481` and `social:123`, or return both:

```json
{
  "wp_thread_id": 481,
  "external_thread_key": "bzj:private:91:104"
}
```

Do not expose raw WordPress thread IDs to the client unless there is a clear security reason to do so.

# 5. Implementing the connection/request rules

The Health & Safety requirements should be implemented as a central policy class, for example:

```text
BZJ_Unified_Chat_Policy
```

It should expose functions conceptually equivalent to:

```text
can_start_conversation(actor, recipient)
can_send_message(actor, thread)
can_accept_request(actor, request)
can_decline_request(actor, request)
get_access_state(actor, recipient)
```

## 5.1 Policy state

The policy needs to distinguish:

```text
orientation_level
health_safety_level
connection_state
chat_request_state
temporary_chat_access
blocked_state
```

For example:

```text
connection_state:
- none
- requested
- connected
- declined
- blocked

temporary_chat_access:
- none
- active
- expired
```

## 5.2 Proposed rules

For a private conversation:

1. If either user blocks the other, deny.
2. If the users are already connected, allow.
3. If the recipient has higher safety clearance and the sender does not:
   - deny ordinary chat;
   - offer paid temporary access if enabled.
4. If the sender has sufficient clearance:
   - allow a first-contact request.
5. The first message creates a pending request rather than an immediately active conversation.
6. The recipient may accept or decline.
7. Once accepted, the users become connected.
8. A connected relationship remains active until explicitly removed.
9. Temporary paid chat access expires independently of permanent connection state.
10. Every send operation rechecks the policy.

The policy should be attached to the BP Better Messages filters:

```php
add_action(
    'better_messages_before_new_thread',
    [$policy, 'validate_new_thread'],
    10,
    2
);

add_filter(
    'better_messages_can_send_message',
    [$policy, 'validate_reply'],
    10,
    3
);
```

The exact filter behaviour should be confirmed against the installed plugin version during implementation. The repository’s plugin uses these hooks in [`inc/hooks.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/hooks.php#L46-L74) and [`inc/hooks.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/hooks.php#L1986-L2104).

## 5.3 Do not rely on native BP friendship alone

The existing connectivity synchronizer maintains relationships across BuddyBoss, Streams, and Socials. It should remain the relationship control plane.

The chat policy should query that control plane’s canonical relationship state or a shared ledger, rather than independently inferring friendship from:

- QuickDate `conversations`;
- WoWonder followers;
- BuddyBoss friendships.

The current connection plugin already maintains a WordPress ledger with states such as `none`, `requested`, and `connected`. That ledger is a useful input to chat policy.

# 6. First-contact requests

A major design question is whether a BP Better Messages thread should be created before acceptance.

The recommended approach is:

## Option A — preferred

Create a BP Better Messages thread with a pending state or restricted recipient, then prevent replies until accepted.

Advantages:

- Message request history remains in one system.
- The recipient can see the request.
- Accept/decline can be represented as normal thread actions.
- Notifications can be generated by BP Better Messages.

However, verify that the installed plugin’s `is_pending` moderation state is appropriate for this purpose. It may be intended for moderation rather than connection requests.

## Option B — safer if pending semantics are unsuitable

Create a separate lightweight request table:

```text
wp_bzj_chat_requests
--------------------
id
actor_wp_id
recipient_wp_id
thread_id
status
reason
created_at
expires_at
responded_at
```

Workflow:

1. Sender requests conversation.
2. WordPress validates the policy.
3. WordPress creates the thread with no message or a system message.
4. Request row is created.
5. Recipient receives a BP Better Messages notification.
6. Recipient accepts or declines.
7. The gateway updates the request and permits or denies replies.

This avoids overloading BP Better Messages’ moderation semantics.

I recommend Option B initially because it clearly separates:

- moderation;
- relationship requests;
- temporary paid access;
- ordinary messages.

# 7. Notifications

## 7.1 WordPress notifications

BP Better Messages already creates unread state through its recipients table and native notification paths. The WordPress UI can therefore continue using native notifications.

The plugin’s unread and incremental update model is based on `recipients.unread_count`, `last_read`, and `last_update`. See [`inc/api/db-migrate.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/wp-content/plugins/bp-better-messages/inc/api/db-migrate.php#L220-L242).

## 7.2 Notifications on Streams and Socials

For the first release, use a polling endpoint:

```text
GET /wp-json/bzj/v1/chat/updates
```

The platform adapter sends:

```text
last_update=<timestamp>
```

WordPress returns:

```json
{
  "server_time": 1760000000,
  "unread_total": 3,
  "threads": [],
  "messages": []
}
```

Streams and Socials can then:

- update their existing notification badge;
- play an existing message sound;
- show a basic toast;
- open the unified chat view.

## 7.3 Push notifications

BP Better Messages already contains push-notification support and an OneSignal add-on. This should be integrated later by mapping external platform device subscriptions to the WordPress user.

Recommended model:

```text
wp_bzj_chat_devices
-------------------
wp_user_id
platform
external_user_id
device_id
push_provider
push_token
last_seen_at
```

When BP Better Messages sends a push notification:

1. WordPress resolves all registered devices for the recipient.
2. It sends the notification to WordPress, Streams, and Socials devices according to preferences.
3. The notification payload contains a signed deep-link token, not a raw permanent session.

Do not duplicate push logic inside Streams and Socials before the canonical event model is working.

# 9. Socials implementation

The QuickDate/Socials code has a tightly coupled local chat system:

- `send_message()`
- `upload_media()`
- `open_private_conversation()`
- `get_chat_conversation()`
- `get_prev_messages()`
- `get_conversation_list()`
- `accept_chat_request()`
- `decline_chat_request()`

These are in [`social/requests/ajax/chat.php`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/social/requests/ajax/chat.php), with the browser implementation in [`social/themes/love/assets/js/chat.js`](https://github.com/cupidblack/buzzjuice.net/blob/3dff25a16d40eb0ccaec06193773b922d537a5b3/social/themes/love/assets/js/chat.js).

Do not rewrite all of this initially. Add a separate unified mode:

```text
unified_chat_mode = legacy|network
```

When `network` is active:

- replace the local message list with the unified thread list;
- replace `send_message()` calls with gateway calls;
- replace local polling with `/bzj/v1/chat/updates`;
- preserve the current local chat as a rollback mode.

This is especially important because the current Socials implementation contains its own:

- message-request state;
- non-pro chat limits;
- paid chat credits;
- spam restrictions;
- block checks;
- media uploads;
- stickers and GIFs.

Those rules should not be accidentally applied twice. During rollout, decide explicitly whether each legacy restriction is:

1. disabled for unified chat;
2. translated into the central policy;
3. retained only for legacy conversations.

The unified gateway must be the final authority.

# 10. Migration strategy

Do not migrate all historical messages immediately.

## Phase 1: new conversations only

- Existing local conversations stay where they are.
- New conversations created through the pilot use BP Better Messages.
- User profiles open the unified conversation view.
- Legacy chat remains available for old conversations.

## Phase 2: read-only history bridge

For old conversations:

- show a “legacy conversation” marker;
- optionally display a read-only imported preview;
- do not duplicate all old messages into BP Better Messages yet.

## Phase 3: selective migration

Migrate only:

- active private conversations;
- conversations with recent activity;
- conversations involving users who have linked accounts.

Every imported message should include metadata:

```text
source_platform
source_message_id
source_created_at
migration_batch_id
```

Use an idempotency table:

```text
wp_bzj_chat_import_map
-----------------------
source_platform
source_message_id
wp_message_id
source_thread_key
wp_thread_id
created_at
```

Never perform an uncontrolled bulk import directly into BP Better Messages tables.

# 11. Group-chat strategy

## Stage 1

Only support BP Better Messages private threads in the unified client.

## Stage 2

Support WordPress/BP Better Messages groups:

- thread creation;
- adding participants;
- removing participants;
- leaving;
- group title;
- group avatar;
- basic group permissions.

Use the existing plugin methods and group APIs, not direct database writes. The plugin already exposes participant operations through its own group and chat implementations.

## Stage 3

Consider native platform groups.

A native Streams or Socials group should only be synchronized if all of the following are defined:

- canonical group owner;
- canonical membership;
- membership-change events;
- moderation authority;
- deletion semantics;
- message history policy;
- group ID mapping;
- failure recovery.

Without those rules, group synchronization will produce inconsistent membership and security problems.

# 12. Implementation procedure

## Step 1 — Freeze the current plugin version

Record:

- BP Better Messages version;
- WordPress version;
- BuddyBoss/BuddyPress version;
- PHP version;
- database engine/version;
- WebSocket or polling mode;
- enabled add-ons;
- notification provider;
- MyCred/GamiPress configuration.

Do not develop against an unrecorded production plugin build.

## Step 2 — Audit the actual installed hooks

The repository copy is useful, but hook signatures should be confirmed against the running production version.

Create a small diagnostic plugin that records:

- `better_messages_before_new_thread`;
- `better_messages_before_message_send`;
- `better_messages_can_send_message`;
- `better_messages_message_sent`;
- `better_messages_thread_updated`;
- `bp_better_messages_new_thread_created`.

Log only:

- user IDs;
- thread IDs;
- message IDs;
- policy result;
- request ID.

Never log message bodies, cookies, JWTs, or raw authorization headers.

## Step 3 — Build identity mapping

Create the identity-map table and an administrator mapping screen.

Require:

- verified external account;
- one-to-one mapping;
- duplicate detection;
- unlink protection;
- audit trail.

Use the existing mapping conventions from the connections synchronizer, but keep chat identity mapping separate.

## Step 4 — Build the WordPress policy layer

Implement:

```text
BZJ_Unified_Chat_Policy
BZJ_Unified_Chat_Requests
BZJ_Unified_Chat_Identity
BZJ_Unified_Chat_Audit
```

Start with:

- connected users can chat;
- approved first-contact requests can chat;
- blocked users cannot chat;
- all other users receive a clear denial.

Add Health & Safety level rules after the basic path works.

## Step 5 — Build the signed gateway

Add the private REST routes.

Implement:

- HMAC authentication;
- replay protection;
- request idempotency;
- external-to-WordPress identity resolution;
- rate limiting;
- structured errors;
- request tracing;
- no direct exposure of internal WordPress APIs.

The gateway should invoke BP Better Messages functions internally.

## Step 6 — Implement WordPress-to-BP Better Messages operations

Start with:

1. get/update session;
2. list threads;
3. create/get private thread;
4. send text;
5. get messages;
6. mark read;
7. accept request;
8. decline request;
9. unread count;
10. incremental updates.

Use `new_message()` for sending, `get_pm_thread_id()` for private thread resolution, and the plugin’s read/update functions.

## Step 7 — Build a standalone test client

Before touching Streams or Socials, create a simple authenticated test page or CLI client that exercises:

- two users;
- no connection;
- connection request;
- accepted connection;
- rejected request;
- blocked users;
- temporary chat access;
- expired access;
- unread messages;
- simultaneous sends;
- duplicate request IDs.

This isolates WordPress and policy problems.

## Step 8 — Add the Socials adapter

Add a feature-flagged unified mode to Socials.

The adapter should:

- obtain the local user from the existing Socials session;
- request a short-lived gateway session;
- render a minimal unified thread list;
- poll updates;
- send and read messages;
- display policy denial states;
- retain legacy mode as fallback.

Do not remove the current `send_message()` or local conversation code until the pilot is successful.

## Step 9 — Add the Streams adapter

Repeat the same procedure in Streams.

Do not integrate Node.js yet. Use polling first.

After polling is stable, add the Streams transport as an optional event relay. The Node.js layer should not become the message database; it should only deliver notifications that cause the client to fetch authoritative data from WordPress.

## Step 10 — Add push notifications

After unread polling works:

- register platform device tokens;
- associate them with mapped WordPress users;
- send BP Better Messages push events to selected platforms;
- add user notification preferences;
- test duplicate suppression.

## Step 11 — Add gating and credits

Implement the policy in this order:

1. block enforcement;
2. connected-user allowance;
3. first-contact request;
4. orientation/HS1700 eligibility;
5. temporary paid access;
6. access expiry;
7. credit/time meter;
8. connection permanence after acceptance.

Do not charge a user until a message or chat session is successfully authorized and recorded.

## Step 12 — Add group support

Only after private messaging has passed production testing.

## Step 13 — Gradual rollout

Use rollout levels:

```text
0%    disabled
1%    internal administrators
5%    staff/test accounts
10%   selected users
25%   monitored beta
50%   majority
100%  default
```

Monitor:

- gateway latency;
- failed authentication;
- policy denials;
- duplicate messages;
- unread mismatches;
- thread-creation failures;
- notification delivery;
- polling volume;
- WordPress CPU/database load;
- external adapter errors.

# 13. Important implementation risks

## Do not directly include `wp-load.php` initially

The limitation is real, but loading WordPress from both applications is not the safest first solution. Use signed HTTPS integration first.

## Do not use the existing product APIs as the contract

The existing Streams and Socials chat endpoints can be used for reference, but the unified system should use a new private gateway and adapters.

## Do not write directly to BP Better Messages tables

Direct writes would bypass:

- permission filters;
- notification hooks;
- unread counters;
- moderation;
- metadata;
- cache invalidation;
- WebSocket/polling update timestamps.

## Do not trust browser-supplied IDs

All actor identities must come from the authenticated platform session and the server-side identity map.

## Do not merge group chat prematurely

Private chat is a manageable first milestone. Group synchronization is a separate product.

## Review current security before reusing legacy code

The supplied Socials code has several areas that should not be copied into the new system without review, including:

- direct SQL in some paths;
- calls that update records based only on an ID;
- upload handling based primarily on filename extensions;
- inconsistent authentication checks across call endpoints;
- legacy chat-credit logic distributed between server and client.

The unified gateway should centralize these decisions and use strict authorization for every operation.

# 14. Final target state

The eventual network should look like this:

```text
                    ┌─────────────────────────┐
                    │ WordPress                │
                    │ BP Better Messages       │
                    │ Unified policy            │
                    │ Identity map              │
                    │ Notifications             │
                    └────────────┬────────────┘
                                 │
                    Private signed gateway
                    │                         │
          ┌─────────▼─────────┐     ┌────────▼────────┐
          │ Streams adapter    │     │ Socials adapter │
          │ unified-chat.js    │     │ unified-chat.js │
          └─────────┬─────────┘     └────────┬────────┘
                    │                         │
             Streams UI                 Socials UI
```

Later:

```text
Streams Node.js transport
        │
        └── notification/event relay only
```

The key principle is:

> **WordPress owns the message state. Streams and Socials own presentation and local-session authentication.**

That gives the network one consistent chat history, one permission model, one unread state, and one place to implement the Health & Safety and paid-access rules.
