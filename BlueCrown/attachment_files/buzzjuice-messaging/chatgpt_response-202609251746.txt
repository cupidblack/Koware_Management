# 2. One important correction to the earlier proposal

I would **not** make the browser on Streams/Socials directly call the WordPress gateway with the user's long-lived authentication credentials.

Instead:

```text
Browser
   ↓
Streams/Socials local endpoint
   ↓
signed server-to-server request
   ↓
WordPress Messaging Gateway
   ↓
BP Better Messages
```

This has several advantages:

* no CORS dependency;
* no WordPress authentication cookie exposed to Streams;
* no SSO JWT exposed to JavaScript;
* no external user ID supplied by the browser being trusted;
* existing Streams/Socials sessions remain authoritative for those applications;
* the gateway can determine the real user from the authenticated platform session;
* easier rollback;
* easier logging;
* easier rate limiting.

The GitHub recommendation of a short-lived session is still useful, but I would make the **short-lived messaging session a server-side adapter credential**, rather than making the browser the primary holder of it.

The 5–20 minute lifetime you proposed is appropriate.

# 10. Signing format

Use:

```text
timestamp
    .
HTTP_METHOD
    .
REQUEST_PATH
    .
RAW_BODY
```

Example:

```text
1758810000.POST./wp-json/bzj/v1/chat/thread/123/send.{"content":"Hello"}
```

Then:

```php
hash_hmac(
    'sha256',
    $canonical,
    $secret
);
```

Headers:

```text
X-BZJ-Platform
X-BZJ-Timestamp
X-BZJ-Key-Id
X-BZJ-Signature
X-BZJ-Request-Id
```

The server verifies:

1. platform;
2. key ID;
3. timestamp;
4. signature;
5. request ID;
6. replay status;
7. mapped external identity;
8. requested operation;
9. target user;
10. rate limit.

This follows the strongest portion of the GitHub proposal. ([GitHub][1])

I would **not call the new system merely "Better Messages integration."**

Call the abstraction:

## One thing I would change from the GitHub recommendation

The GitHub analysis recommends using the Better Messages functions, which is correct. But it also describes `create_new_conversation()` as an ordinary API operation. The current implementation actually creates the Better Messages thread and recipients directly inside that **plugin-owned function**. 

That is fine.

The rule should therefore be:

> **Never bypass Better Messages ourselves; using a Better Messages public function that internally performs its own database operation is acceptable.**

That distinction matters.

# 60. Final architecture decision

So I would officially establish this as **Buzz Messaging v1**:

```text
BUZZ MESSAGING v1
────────────────────────────────

Canonical backend:
    BP Better Messages 2.15.17

WordPress:
    bzj-messaging.php

Shared:
    shared/bzj-messaging/

External platforms:
    signed adapters

Authentication:
    platform session
        ↓
    HMAC server authentication
        ↓
    short-lived messaging session

Identity:
    dedicated Buzz Messaging identity map

Relationships:
    existing BZJ connection ledger

Private chat:
    supported

First-contact requests:
    dedicated BZJ request system

H&S policy:
    central policy engine

Credits:
    future addon

Rewards:
    future addon

Notifications:
    canonical BM event + platform adapters

Live updates:
    polling initially

Real-time:
    optional Node.js event relay later

Groups:
    deferred

Legacy chats:
    retained during migration

Historical migration:
    deferred

wp-load.php:
    deferred

Direct Better Messages DB writes:
    prohibited
```

This is materially stronger than simply "connecting three chat systems." It establishes **one messaging control plane** while keeping Streams and Socials decoupled from WordPress at runtime.

The existing Better Messages hooks are sufficiently rich to support this architecture, including message authorization, pre-send processing, successful-send events, participant changes, and thread updates. ([Better Messages][3])

### Next implementation step

The next concrete development artifact should therefore be **the actual Buzz Messaging v1 codebase**, beginning with:

```text
wp-content/mu-plugins/bzj-messaging.php
shared/bzj-messaging/core/*
shared/bzj-messaging/bzj-msg-streams-client.php
shared/bzj-messaging/bzj-msg-socials-client.php
```

plus the database schema, HMAC gateway, short-lived sessions, identity mapping, request system, logging switches, Better Messages hooks, and a standalone test endpoint.

**I would build that as Phase 1 before touching any existing Streams or Socials chat code.** This keeps the current production chat systems completely recoverable while we prove the canonical WordPress messaging layer first.
