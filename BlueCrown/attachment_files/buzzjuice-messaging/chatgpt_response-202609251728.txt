## Recommended architecture

I reviewed the two prior architecture documents, the current Buzzjuice connectivity control plane, the BP Better Messages source, and the current Better Messages hook/function documentation. The GitHub review's central recommendation is correct: **do not synchronize three independent chat databases**. Make BP Better Messages the canonical messaging engine and make Streams/Socials presentation/adaptation layers. 

The installed repository version I reviewed is **BP Better Messages 2.15.17**, and its source confirms the relevant programmatic functions and hooks, including `new_message()`, `get_pm_thread_id()`, `get_messages()`, `get_recipients()`, `messages_mark_thread_read()`, `better_messages_before_new_thread`, `better_messages_before_message_send`, `better_messages_can_send_message`, `better_messages_message_sent`, and `better_messages_thread_updated`. 

### The resulting architecture

```text
                    BUZZJUICE NETWORK
                           │
                           ▼
              ┌──────────────────────────┐
              │       WORDPRESS           │
              │                           │
              │   BP Better Messages     │
              │   Canonical messages      │
              │   Threads/participants    │
              │   Read/unread             │
              │                           │
              │   BZJ Messaging Core      │
              │   ├─ Gateway              │
              │   ├─ Authentication       │
              │   ├─ Policy               │
              │   ├─ Chat requests        │
              │   └─ Idempotency          │
              └────────────┬─────────────┘
                           │
                    Signed HTTPS
                           │
             ┌─────────────┴─────────────┐
             │                           │
      ┌──────▼──────┐             ┌──────▼──────┐
      │   STREAMS   │             │   SOCIALS   │
      │             │             │             │
      │ local PHP   │             │ local PHP   │
      │ adapter     │             │ adapter     │
      │      │      │             │      │      │
      │ Unified UI  │             │ Unified UI  │
      └─────────────┘             └─────────────┘
```

This also keeps the existing Connections Control Plane authoritative for relationships/blocks rather than letting messaging independently decide friendship state. Your existing ledger contains `connection_state`, `requested_by`, and directional block fields, so the messaging layer can consume that state without duplicating relationship logic. ([GitHub][1])

# Important improvements over the earlier proposal

### 1. No `wp-load.php`

I deliberately did **not** implement:

```php
require_once '/path/to/wp-load.php';
```

inside Streams or Socials.

The GitHub analysis correctly identified memory, bootstrap, global-variable, cookie/session, plugin-side-effect and rollback risks. The signed gateway is a cleaner first integration boundary. 

`wp-load.php` can still become a future optimization if we later prove that the shared runtime is safe.

---

### 2. Existing Streams/Socials APIs remain reference-only

The package does **not** use:

```text
streams/api/v2/endpoints/chat.php
streams/api/v2/endpoints/notifications.php

social/endpoint/v1/models/messages.php
social/endpoint/v1/models/notifications.php
```

as the messaging contract.

Instead:

```text
Streams/Socials
      ↓
BZJ Messaging Client
      ↓
/wp-json/bzj/v6/messaging
      ↓
BP Better Messages
```

That follows the strongest recommendation from the GitHub review. 

---

### 3. Dedicated messaging secrets

I did **not** reuse the existing connection-management secrets.

The package expects:

```text
BZJ_STREAMS_MESSAGING_SECRET
BZJ_SOCIALS_MESSAGING_SECRET
```

with different long random values.

This is important because:

```text
Connection control plane
        ≠
Messaging control plane
```

The existing `bzj-connection-client.php` provided a useful model for signed server-to-server communication, but the messaging credentials should remain independent. 

---

### 4. Short-lived messaging sessions

The gateway issues a **10-minute messaging session** with silent renewal.

The flow is:

```text
Streams local authenticated session
             ↓
Streams PHP adapter
             ↓
signed /messaging/session request
             ↓
WordPress verifies external ID
             ↓
10-minute messaging token
             ↓
Streams adapter stores token server-side
```

Same for Socials.

The browser does **not** receive the WordPress bearer token directly.

That is an improvement over allowing the browser to directly authenticate against the WordPress gateway.

---

### 5. Replay/idempotency protection

The package creates:

```text
wp_bzj_chat_idempotency
```

Every send operation receives a UUID.

For example:

```text
Socials
   │
   │ request_id = 8c...
   ▼
WordPress
   │
   ├── send message
   │
   └── store result
```

If Socials times out and retries the same UUID, the gateway can return the existing operation rather than intentionally creating a duplicate message.

This is particularly important for messaging because network timeouts commonly occur **after** the server has successfully saved the message.

# Data ownership

The implementation preserves this separation:

| System                       | Authority                                                            |
| ---------------------------- | -------------------------------------------------------------------- |
| BuddyBoss / Connections      | Connections, blocks, relationship state                              |
| BP Better Messages           | Threads, messages, participants, read/unread                         |
| BZJ Messaging                | Gateway, external authentication, policy, chat requests, idempotency |
| Streams                      | UI + local authentication                                            |
| Socials                      | UI + local authentication                                            |
| Streams Node.js              | Future transport only                                                |
| Old Streams/Socials chat DBs | Legacy during transition                                             |

That is the architectural boundary I would protect most strongly.

# First-contact chat

I made one additional correction that is important in practice.

Simply creating an empty Better Messages thread isn't enough because Better Messages' conversation list can exclude empty ordinary threads. Its own `get_threads()` implementation requires a message for normal threads. 

Therefore, when an unconnected user starts a first-contact conversation, the package:

1. creates/resolves the Better Messages thread;
2. creates a `bzj_chat_requests` record;
3. creates a request notice message;
4. prevents ordinary replies;
5. lets the recipient accept/decline;
6. allows conversation after acceptance.

The request itself is **not** treated as Better Messages moderation state. That keeps:

```text
chat request
≠
content moderation
≠
BuddyBoss connection
```

which is much cleaner for the future H&S/Palmier system.

# Current policy

For Phase 1:

```text
BLOCKED
   ↓
DENY

CONNECTED
   ↓
ALLOW

NOT CONNECTED
   ↓
FIRST-CONTACT REQUEST

REQUEST ACCEPTED
   ↓
ALLOW CHAT
```

The important part is that this is enforced server-side.

There are checks in:

```text
better_messages_before_new_thread
better_messages_before_message_send
better_messages_can_send_message
```

so a malicious client cannot simply remove a disabled Send button and bypass the policy. Better Messages itself uses these hooks for restrictions, and its source confirms their role in the message lifecycle.

# One deliberate deviation from the GitHub recommendation

GitHub suggested immediately creating:

```text
wp_bzj_chat_identity_map
```

I would **not make that a prerequisite for Phase 1**.

The current Buzzjuice system already has:

```text
wp_usermeta
    ├── wo_user_id
    └── qd_user_id
```

and the Connections Control Plane already relies on those mappings. ([GitHub][1])

The Phase-1 gateway therefore verifies:

```text
Streams external ID
        ↓
wo_user_id
        ↓
WordPress user

Socials external ID
        ↓
qd_user_id
        ↓
WordPress user
```

This avoids introducing a second identity authority before the basic system works.

**Phase 2**, once account-linking requirements become more sophisticated, should add:

```text
wp_bzj_chat_identity_map
```

with conflict detection, status, verification state and audit history.

That is a staged implementation of the GitHub recommendation rather than ignoring it.

# Step 14 — Add Streams realtime

Only after polling has proven reliable:

```text
Better Messages
       ↓
BZJ event
       ↓
Streams Node.js
       ↓
existing socket transport
       ↓
Streams browser
```

The Node.js layer should **never become the message database**.

It should only tell Streams:

```text
Something changed.
Fetch authoritative data.
```

Possible events:

```text
unified_chat.message
unified_chat.thread_updated
unified_chat.request_received
unified_chat.read_state_changed
```

That makes your requested configuration straightforward:

```text
BZJ_UNIFIED_CHAT_REALTIME_ENABLED=false
```

initially, then:

```text
false → polling
true  → Streams realtime
```

The existing Streams Node.js infrastructure therefore becomes an optional transport adapter rather than a dependency of the messaging architecture.

# Final target

The system can eventually evolve into:

```text
                         BUZZJUICE
                             │
                             ▼
                  ┌────────────────────┐
                  │     WORDPRESS      │
                  │                    │
                  │ Better Messages    │
                  │ BZJ Messaging      │
                  │ BZJ Connections    │
                  │ H&S Policy         │
                  │ Palmier            │
                  │ Notifications      │
                  └─────────┬──────────┘
                            │
                    Signed Messaging
                         Gateway
                       /          \
                      /            \
                     ▼              ▼
                STREAMS          SOCIALS
                   │                │
             Unified Chat      Unified Chat
                   │                │
             Polling / RT          Polling
                   │
             Node.js later
```

That gives Buzzjuice **one messaging system with multiple interfaces**, rather than three messaging systems that have to continuously synchronize.

The biggest architectural win is that a message sent on Socials becomes the **same message**, in the **same canonical conversation**, that appears on Streams and WordPress. There is no copy to reconcile and no "which database is correct?" problem. This is the direction supported by the combined architecture review and the actual Better Messages capabilities.
