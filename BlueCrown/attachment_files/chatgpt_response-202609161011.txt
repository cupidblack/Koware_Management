### Key architectural corrections

2. **Streams Friends must remain completely out of the model.** BuddyBoss connections map only to QuickDate friendship.

6. **Blocking must be destructive:** block → remove connection + both follows → project block. Unblock never reconstructs either relationship.

# 3. Blocking

Blocking is deliberately the strongest relationship state.

## Block

When:

```text
A blocks B
```

the canonical operation becomes:

```text
BLOCK A → B

        ├── BuddyBoss block
        ├── remove BB connection
        ├── remove BB A → B follow
        ├── remove BB B → A follow
        │
        ├── Streams block A → B
        ├── Streams remove A → B follow
        ├── Streams remove B → A follow
        │
        ├── Socials block A → B
        ├── Socials remove friend projection
        ├── Socials remove A → B follow
        └── Socials remove B → A follow
```

This also addresses the concern in your supplied advice about pre-existing BuddyBoss friendships.

The important distinction is:

> **Blocking destroys the relationship; unblocking does not restore it.**

That should be enforced everywhere.

# 4. QuickDate Friend vs Follow

This needs special treatment.

The architecture should regard the QuickDate `followers` record as:

```text
Required if:

BB connection projection exists
OR
BB follow projection exists
OR
a QuickDate friend request is pending
```

Therefore:

### Friend + follow

If:

```text
A and B are friends
A follows B
```

then QuickDate has one active row representing the required relationship.

If A subsequently unfollows B:

```text
BB follow removed
BB connection remains
        ↓
QuickDate row remains
```

That prevents an unfollow from accidentally destroying friendship.

Conversely:

```text
A and B are friends
A unfriends B
A still follows B
```

the QuickDate active row also remains.

This is a necessary correction to the simplistic:

```sql
DELETE FROM followers ...
```

approach.

# 5. External Platform Authentication

Every Streams/Socials request should contain:

```http
X-BZJ-Timestamp: 1778970000
X-BZJ-Signature: ...
Content-Type: application/json
```

Signature:

```text
HMAC-SHA256(
    timestamp + "." + raw_request_body,
    BUZZ_SSO_SECRET
)
```

The server rejects:

* missing signature
* invalid signature
* malformed JSON
* unknown platform
* unknown operation
* invalid user IDs
* same actor/target
* expired timestamp
* duplicate event IDs

The five-minute replay window is appropriate for these requests.

# 8. Event Loop Prevention

The system should use three layers.

### Layer 1 — Context

```text
BZJ internal operation
```

is stored while the plugin itself calls a BuddyBoss function.

### Layer 2 — Event UUID

Every operation receives:

```text
UUID
```

and the event is recorded once.

### Layer 3 — Pair lock

The pair:

```text
min(A,B):max(A,B)
```

is locked using MySQL:

```sql
GET_LOCK()
```

This prevents:

```text
A blocks B
+
A follows B
```

from racing against one another.

The second operation waits until the first has established the canonical state.

# 10. Recovery Behaviour

If:

```text
BuddyBoss = successful
Streams = successful
Socials = database unavailable
```

the request should **not** roll back BuddyBoss.

Instead:

```text
Canonical BB state
       ↓
event retained
       ↓
Socials projection queued
       ↓
retry
       ↓
projection eventually repaired
```

This is preferable to attempting a distributed database transaction across three independent applications.

A real cross-database transaction cannot provide the kind of atomicity you would want here without introducing substantially more infrastructure.

# 11. Reconciliation

The reconciliation engine should periodically ask:

```text
What does BuddyBoss say?
```

Then compare that with:

```text
Streams
Socials
```

For every discrepancy:

```text
BuddyBoss wins
```

and the external projection is repaired.

For example:

```text
BuddyBoss:
A follows B

Streams:
missing

Socials:
exists
```

Result:

```text
Streams → repair
Socials → leave
```

Another:

```text
BuddyBoss:
A does NOT follow B

Streams:
A follows B

Socials:
A follows B
```

Result:

```text
Streams → delete
Socials → delete
```

This makes the system self-healing.
