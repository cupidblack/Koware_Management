# 3. Canonical relationship state

I recommend storing:

```text
none
requested
connected
blocked
```

plus:

```text
requested_by
blocked_by
```

The canonical pair is always normalized:

```text
user_a < user_b
```

Therefore:

```text
101 ↔ 205
```

has exactly one canonical relationship record.

### State machine

```text

 ├── accept ────────────────► CONNECTED
```

# 18. Canonical state writer

The central function should be the only function allowed to change the canonical relationship record.

Conceptually:

```php
function bzj_connections_sync_set_state(
    $user_a,
    $user_b,
    $state,
    $requested_by = 0,
    $blocked_by = 0,
    $origin = 'wordpress',
    $event_type = ''
) {

    global $wpdb;

    $user_a = (int) $user_a;
    $user_b = (int) $user_b;

    if ($user_a === $user_b) {
        return false;
    }

    if ($user_a > $user_b) {
        $tmp    = $user_a;
        $user_a = $user_b;
        $user_b = $tmp;
    }

    /*
     * Pair lock.
     */
    if (
        function_exists('bzj_relationship_pair_lock')
    ) {
        $lock = bzj_relationship_pair_lock(
            $user_a,
            $user_b
        );

        if (! $lock) {
            return false;
        }
    }

    try {

        $table =
            $wpdb->prefix .
            'bzj_relationships';

        $existing = $wpdb->get_row(
            $wpdb->prepare(
                "
                SELECT *
                FROM {$table}
                WHERE user_a = %d
                  AND user_b = %d
                LIMIT 1
                ",
                $user_a,
                $user_b
            )
        );

        $old_state =
            $existing
                ? $existing->state
                : 'none';

        /*
         * No-op transitions should not generate
         * endless synchronization events.
         */
        if (
            $old_state === $state
        ) {
            return true;
        }

        $now = current_time('mysql');

        if ($existing) {

            $wpdb->update(
                $table,
                [
                    'state'        => $state,
                    'requested_by' => $requested_by ?: null,
                    'blocked_by'   => $blocked_by ?: null,
                    'updated_at'   => $now,
                ],
                [
                    'id' => $existing->id,
                ],
                [
                    '%s',
                    '%d',
                    '%d',
                    '%s',
                ],
                [
                    '%d',
                ]
            );

        } else {

            $wpdb->insert(
                $table,
                [
                    'user_a'       => $user_a,
                    'user_b'       => $user_b,
                    'state'        => $state,
                    'requested_by' => $requested_by ?: null,
                    'blocked_by'   => $blocked_by ?: null,
                    'created_at'   => $now,
                    'updated_at'   => $now,
                ],
                [
                    '%d',
                    '%d',
                    '%s',
                    '%d',
                    '%d',
                    '%s',
                    '%s',
                ]
            );
        }

        bzj_connections_sync_create_event(
            $event_type,
            $origin,
            $user_a,
            $user_b,
            $state,
            [
                'previous_state' => $old_state,
                'new_state'      => $state,
            ]
        );

        return true;

    } finally {

        if (
            function_exists('bzj_relationship_pair_unlock')
        ) {
            bzj_relationship_pair_unlock(
                $user_a,
                $user_b
            );
        }
    }
}
```

Conceptually:

```php
function bzj_project_relationship_to_streams(
    $wp_actor,
    $wp_target,
    $state,
    $requested_by = 0
) {

    $actor =
        bzj_get_cross_platform_ids($wp_actor);

    $target =
        bzj_get_cross_platform_ids($wp_target);

    if (
        empty($actor['wo']) ||
        empty($target['wo'])
    ) {
        return false;
    }

    $db = get_wowonder_db();

    if (! $db) {
        throw new RuntimeException(
            'WoWonder database unavailable.'
        );
    }

    $following_id = (int) $target['wo'];
    $follower_id  = (int) $actor['wo'];

    /*
     * Always remove stale relationship first
     * when state is none/blocked.
     */
    if (
        in_array(
            $state,
            ['none', 'blocked'],
            true
        )
    ) {

        $stmt = $db->prepare(
            "
            DELETE FROM T_FOLLOWERS
            WHERE following_id = ?
              AND follower_id = ?
            "
        );

        /*
         * Actual table constant cannot be used
         * outside Streams, so bridge should resolve
         * the configured physical table name.
         */

        return true;
    }

    return true;
}
```

I deliberately would **not** copy this exact SQL into production yet because the bridge operates outside the Streams PHP runtime and therefore cannot safely assume `T_FOLLOWERS` exists as a PHP constant.

The adapter should resolve the actual physical table name from the configured database/schema.

That is one of the places where the GitHub proposal was too speculative.

The GitHub response was useful as a conceptual second opinion, but **I would not deploy its code**. Its biggest weaknesses are guessed database schemas, missing accepted-friendship handling, incomplete reverse synchronization, and treating the external platforms too much like independent authorities.

The stronger Buzzjuice architecture is:

```text
                   ┌────────────────────┐
```
