## Executive conclusion

I reviewed the supplied integration proposal, the existing v8.1.1/v8.2 implementation, the Buzzjuice database helpers, the current Streams/Socials source, and the two latest GitHub reviews.

The previous **v8.2 architecture should not be deployed unchanged**. The GitHub review's proposed **v8.3.0 direction is materially better**, particularly on QuickDate Follow semantics, durable retries, explicit operation types, authentication, blocking, and BuddyBoss authority. ([GitHub][1])

I have therefore consolidated the design around **BuddyBoss as the sole canonical authority**.

### The most important correction

There are now **three separate relationship types**:

1. **BuddyBoss Connection** — request → connected.
2. **Ordinary Follow** — directional and independent.
3. **Block** — directional and destructive to the relationship pair.

QuickDate's `followers` table is overloaded and can represent ordinary follows, pending friend requests and accepted friendships, so synchronization must be driven by an **explicit semantic operation**, never by inspecting the row alone. ([GitHub][1])

Thus:

**QuickDate Add Friend**
→ BuddyBoss Connection Request

**QuickDate Follow**
→ BuddyBoss Follow
→ Streams Follow

and **not** QuickDate Follow → BuddyBoss Connection Request. ([GitHub][1])

This is the biggest change from your original proposal.

The external platforms **never write BuddyBoss friendship, follow or moderation tables directly**. They submit signed commands, after their own local operation succeeds, and WordPress executes the corresponding native BuddyBoss function. This preserves BuddyBoss's existing role/profile/gender/privacy restrictions. ([GitHub][1])

# Blocking is now explicitly destructive

When A blocks B:

```text
A blocks B
     │
     ▼
BuddyBoss block
     │
     ├── remove A-B connection
     ├── remove pending connection
     ├── remove A → B follow
     ├── remove B → A follow
     │
     ├── Streams:
     │      remove follows
     │      create A → B block
     │
     └── Socials:
            remove relationship projections
            create A → B block
```

The block remains **directional**. B is not automatically blocking A.

When A subsequently unblocks B:

```text
A → B block removed
       │
       ├── Streams block removed
       └── Socials block removed

NO previous connection/follow is recreated
```

That last point is important and explicitly recommended by the GitHub review. ([GitHub][1])

# Streams follow architecture

Because the WoWonder Friends System is disabled, integration-created Streams follows are forced to:

```text
active = 1
```

The existing `confirm_followers` and `connectivitySystem` logic must not turn an integration follow into a pending request. ([GitHub][1])

I have also incorporated your requested automatic acceptance behavior into `Wo_IsFollowRequested()`.

The important distinction is:

```text
Streams:
pending follow
      ↓
active = 1
      ↓
immediate follow
```

but **not**:

```text
QuickDate pending friend request
      ↓
automatic acceptance
```

The GitHub review specifically warned against applying the Streams behavior to QuickDate. ([GitHub][1])

# Durable synchronization

The v8.3 control plane contains:

* relationship ledger
* durable event queue
* UUID idempotency
* pair-level MySQL locking
* HMAC authentication
* read-back verification
* retry processing
* failed-event tracking
* external DB/table discovery
* operational logging
* administrator diagnostics

The retry worker now actually **reprocesses** events rather than merely logging that reconciliation is required. The retry progression is approximately:

```text
60 sec
2 min
4 min
8 min
16 min
32 min
60 min
→ failed
```

This addresses one of the major defects identified in v8.2. ([GitHub][1])

# Authentication correction

I have also removed the architectural dependence on:

```text
WORDPRESS_API_USERNAME
WORDPRESS_API_PASSWORD
```

for synchronization.

The control plane uses:

```text
BZJ_STREAMS_SYNC_SECRET
BZJ_SOCIALS_SYNC_SECRET
```

with:

```text
BUZZ_SSO_SECRET
```

as fallback.

The request signature is:

```text
HMAC-SHA256(
    timestamp + "." + raw_json_body,
    platform_secret
)
```

with:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

The GitHub review specifically recommended this model. ([GitHub][1])

# Database architecture

The existing `shared/db_helpers.php` already provides:

```text
get_wp_db_conn()
get_qd_db_conn()
get_wowonder_db()
```

and the existing environment definitions for the three databases. ([GitHub][2])

The new control plane therefore uses those helpers rather than duplicating database credentials.

The ledger is:

```text
wp_bzj_relationships
```

and the durable queue is:

```text
wp_bzj_relationship_events
```

The ledger additionally records:

```text
socials_follow_a_to_b
socials_follow_b_to_a
```

because QuickDate's `followers` table cannot tell whether an `active=1` row represents an ordinary follow or an accepted-friend projection. This distinction was specifically identified in the GitHub review. ([GitHub][1])

## One important implementation detail

I deliberately **did not regenerate `functions_one.php`, `content.phtml`, `social/core.php`, `profile.php`, or `useractions.php` in their entirety**. Those are large production files, and the safer architecture is to apply surgical changes around the existing native logic.

That follows your requirement and also reduces the risk of overwriting unrelated Buzzjuice customizations.

The current QuickDate `add_friend()` confirms that it ultimately uses the overloaded follow mechanism, which is precisely why the integration now attaches the explicit `connection_request` semantic to that handler rather than allowing a generic `Wo_DeleteFollow()` operation to decide what the user intended. 

Likewise, QuickDate's current block/unblock handlers perform their local `blocks` mutations, so the synchronization command belongs **after successful local verification**, not before it.
