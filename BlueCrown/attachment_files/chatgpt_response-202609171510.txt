# Updated Buzzjuice Network Connection & Moderation Integration Specification

### Version 8.3.0

# BUZZJUICE NETWORK

## Connection, Follow & Moderation Synchronization

### Architecture & Implementation Specification — v8.3.0

## 1. Authority Model

WordPress/BuddyBoss is the sole source of truth for:

* Connection requests
* Accepted connections
* Ordinary follows
* Blocks
* Unblocks
* Destructive consequences of blocking

Buzzjuice Streams and Buzzjuice Socials are synchronized projections and action interfaces.

External platforms must never directly modify:

* BuddyBoss friendship tables
* BuddyBoss follow tables
* BuddyBoss moderation tables

All external-originated actions must first be validated locally, then submitted through the signed WordPress connection-management endpoint.

---

## 2. Platform Relationship Model

### 2.1 BuddyBoss Connections

BuddyBoss connection state has three relevant states:

```text
none
requested
connected
```

A request is directional.

An accepted connection is reciprocal.

### 2.2 BuddyBoss Follows

BuddyBoss follows remain independent directional relationships:

```text
A → B
B → A
```

They must never automatically become BuddyBoss connections.

### 2.3 Blocks

Blocks are directional:

```text
A blocks B
```

does not mean:

```text
B blocks A
```

A block is nevertheless destructive to the relationship between the pair.

---

# 3. QuickDate Relationship Model

QuickDate's `followers` table is overloaded.

It represents:

1. Ordinary follows
2. Pending friend requests
3. Accepted friend projections

Therefore:

> A QuickDate `followers` row must never be interpreted solely from `active` or from the existence of reciprocal rows.

Two ordinary follows can produce the same database pattern as an accepted friendship.

The synchronization control plane must therefore maintain the distinction using the WordPress canonical ledger.

The latest GitHub review specifically identified this as a defect in the earlier implementation. ([GitHub][1])

---

# 4. BuddyBoss → QuickDate Connection Synchronization

## 4.1 Connection Request

When A sends a BuddyBoss connection request to B:

### BuddyBoss

Keep the normal pending connection.

### QuickDate

Create:

```text
following_id = B
follower_id  = A
active       = 0
```

### Streams

Do nothing.

No Streams follow is created.

---

## 4.2 Connection Request Withdrawal

When A withdraws the pending BuddyBoss request:

Delete only:

```text
QuickDate:
A → B
active = 0
```

Do not delete an ordinary QuickDate follow if one exists independently.

---

## 4.3 Connection Request Rejection

When B rejects A's BuddyBoss request:

Delete only the corresponding QuickDate pending request.

Streams remains unchanged.

The correct BuddyBoss hooks are:

```php
friends_friendship_requested
friends_friendship_accepted
friends_friendship_rejected
friends_friendship_withdrawn
```

`friends_friendship_post_delete` remains a defensive reconciliation hook.

The current BuddyBoss source confirms the request and acceptance hook signatures and the dedicated withdrawal/rejection lifecycle. ([GitHub][2])

# 5. Accepted BuddyBoss Connection

When BuddyBoss reports:

```text
is_friend
```

QuickDate must contain:

```text
A → B active = 1
B → A active = 1
```

Streams must not receive a friendship projection because the WoWonder Friends System is disabled.

The accepted QuickDate rows are therefore a representation of the canonical BuddyBoss connection.

---

# 6. BuddyBoss Connection Removal

When an accepted BuddyBoss connection is removed:

1. BuddyBoss remains authoritative.
2. QuickDate's accepted-friend projection is removed.
3. Independent ordinary follow relationships must be preserved.
4. Streams follows must not be deleted merely because the friendship disappeared.

This is important because:

```text
connection ≠ follow
```

The earlier implementation's tendency to delete every QuickDate row for the pair must therefore be removed.

# 7. BuddyBoss Ordinary Follow

This is an important correction to the previous implementation.

When:

```text
A follows B on BuddyBoss
```

the result is:

```text
BuddyBoss:
A → B follow

Streams:
A → B active follow

Socials:
NO synchronization
```

This follows the original Buzzjuice requirement that BuddyBoss follows should not automatically populate QuickDate Socials.

Therefore the earlier v8.2 design recommendation to project BuddyBoss follows into Socials is **not adopted**.

The BuddyBoss follow hooks are:

```php
bp_start_following
bp_stop_following
```

with:

```php
$follow->follower_id
$follow->leader_id
```

The direction is:

```text
follower_id → leader_id
```

The current BuddyBoss follow implementation confirms this lifecycle. ([GitHub][1])

# 10. Streams-Originated Follow

When A follows B on Streams:

```text
1. Streams creates A → B active follow.
2. Streams verifies the database row.
3. Streams submits signed command:
   origin   = streams
   operation = follow
4. WordPress maps:
   wo_user_id → WordPress ID
5. WordPress calls:
   bp_start_following()
6. BuddyBoss emits its native follow hook.
7. Streams is already correct.
8. Socials is not modified.
```

The local Streams action must succeed before the WordPress synchronization command is attempted.

If WordPress is temporarily unavailable:

```text
Streams action remains successful.
Synchronization event enters retry queue.
```

This prevents an external network failure from breaking the user's local action.

# 12. QuickDate Add Friend

QuickDate's Add Friend is **not an ordinary follow**.

Although QuickDate internally uses its `followers` table and ultimately invokes follow-style functionality, the synchronization layer must interpret the UI operation semantically.

When A chooses:

```text

```

the operation is:

```text

```

not:

```text
follow
```

Flow:

```text
QuickDate
   ↓

   ↓
verify
   ↓
signed WordPress command
   ↓
friends_add_friend(A,B)
   ↓
BuddyBoss restrictions
   ↓
BuddyBoss request hook
   ↓
canonical synchronization
```

This preserves BuddyBoss restrictions such as role/profile/gender/privacy restrictions rather than bypassing them. ([GitHub][1])

If BuddyBoss rejects the request:

```text
delete QuickDate pending row
log rejection
return failure
```

# 19. Critical QuickDate Code Rule

Do NOT use a generic:

```php
Wo_DeleteFollow()
```

operation to infer whether the user is:

* unfollowing,
* withdrawing a friend request,
* rejecting a friend request,
* or unfriending.

The same QuickDate table is used for all of these.

Instead:

```text
Add Friend       → connection_request
Approve Friend   → connection_accept
Reject Friend    → connection_reject
Cancel Friend    → connection_withdraw
Unfriend         → connection_remove
Follow           → follow
Unfollow         → unfollow
```

The QuickDate action handlers must explicitly tell the control plane what semantic operation occurred.

This eliminates the dangerous "reciprocal rows = friendship" inference identified in the review. ([GitHub][1])

# 20. Blocking

When A blocks B, the control plane must enforce:

```text

A → B block

BuddyBoss:

remove A → B follow

BuddyBoss:
remove B → A follow

Streams:
remove A → B follow
remove B → A follow
create A → B block

Socials:
remove A → B relationship
remove B → A relationship
create A → B block
```

The block itself remains directional.

The latest review specifically recommends this destructive cascade. ([GitHub][1])

# 29. Pair Locking

Every relationship operation for the same pair must use:

```text
bzj_pair_<lower_wp_id>_<higher_wp_id>
```

Therefore:

```text
A → B
B → A
```

use the same lock.

This prevents race conditions such as:

```text
follow
unfollow
block
friend accept
```

being processed simultaneously.

# 30. Retry Strategy

Failed operations must be executable by the recovery worker.

Recommended schedule:

```text
1 minute
2 minutes
4 minutes
8 minutes
16 minutes
32 minutes
1 hour
```

After the maximum retry count:

```text
status = failed
```

and the failure remains fully logged.

The recovery worker must actually retry the operation; merely logging pending events is insufficient. ([GitHub][1])

# 31. Authentication

The external endpoint:

```text
POST /wp-json/bzj/v6/connection-management
```

must use:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

Signature:

```text
HMAC-SHA256(
    timestamp + "." + raw_request_body,
    BUZZ_SSO_SECRET
)
```

Reject:

* missing timestamp
* invalid timestamp
* expired timestamp
* missing signature
* invalid signature
* invalid JSON
* invalid UUID
* unknown origin
* unknown operation
* invalid actor
* invalid target
* actor = target
* missing user mapping

The existing WordPress API username/password must NOT be used as the synchronization credential.

The HMAC channel is the appropriate machine-to-machine authentication mechanism. ([GitHub][1])

with one critical distinction:


This keeps the network semantically clean as Buzzjuice grows rather than allowing the three platforms' different relationship models to become progressively entangled.

## What I would change from v8.2.0

There are **five important changes** I would make before deploying anything:

1. **Do not deploy v8.2.0 as-is.** Its own GitHub review identifies truncated artifacts and synchronization defects. ([GitHub][1])
2. **Do not project BuddyBoss ordinary follows into Socials.** That conflicts with your explicit Buzzjuice requirement that BuddyBoss follows synchronize to Streams, not Socials.
3. **Do not infer QuickDate friendship from reciprocal `followers` rows.** That is unsafe because ordinary follows can create the same pattern. ([GitHub][1])
4. **Do not let generic `Wo_DeleteFollow()` determine the semantic action.** QuickDate must explicitly identify `unfollow` versus `unfriend` versus request cancellation/rejection.
5. **Fix event recovery before production.** A pending event must be resumable; a failed event must actually be retried rather than merely logged. ([GitHub][1])

### One further refinement I recommend

I would make **v8.3.0's ledger slightly more sophisticated than v8.1.1/v8.2.0** by adding the two QuickDate projection-ownership fields:

```text
socials_follow_a_to_b
socials_follow_b_to_a
```

That solves the hardest remaining ambiguity: QuickDate has one table for both ordinary follows and friendships. The ledger then tells the synchronizer *why* a row exists rather than forcing it to guess from the QuickDate database.

The existing v8.1.1 control plane already has the right overall foundation—canonical ledger, event queue, pair locks, HMAC endpoint, native BuddyBoss operations and external prepared SQL—but its recovery and QuickDate classification need the v8.3 refactor.  

**Next implementation sequence:** I would now build **v8.3.0 `bzj-connections-sync.php` as the complete new MU plugin first**, then apply the targeted `functions_one.php`, Streams, Socials and `wwqd_bridge.php` patches in that order. This avoids modifying the three live platforms until the canonical control plane and its diagnostics/recovery mechanisms are in place.
