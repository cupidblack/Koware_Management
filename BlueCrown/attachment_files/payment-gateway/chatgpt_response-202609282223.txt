# 2. Why the current bridge is vulnerable to dropped orders

The existing `wow-pgb_init.php` currently:

1. creates a `Wo_Payment_Transactions` row;
2. constructs a WooCommerce REST API URL;
3. performs cURL;
4. sends WooCommerce credentials;
5. waits for the remote response;
6. expects WooCommerce to return a payment URL;
7. then sends that URL back to the browser. 

The critical section is effectively:

```text
Streams PHP
     │
     │ cURL
     ▼
https://buzzjuice.net/wp-json/wc/v3/orders
     │
     ├── DNS
     ├── TLS
     ├── HTTP
     ├── authentication
     └── API processing
```

That is exactly the part we want to eliminate.

The new architecture instead makes the browser perform:

```text
Streams PHP
     │
     │ MySQL
     ▼
Wo_Payment_Gateway_Bridge
     │
     │ JSON response
     ▼
Browser
     │
     │ HTTPS
     ▼
WordPress
```

The earlier architecture analysis correctly identified that this makes the cPanel DNS failure irrelevant to the handoff.

# 3. The new durable bridge table

I agree strongly with the GitHub recommendation to **keep `Wo_Payment_Transactions`** and add a separate orchestration table.

The distinction should be:

### `Wo_Payment_Transactions`

The Streams financial/business transaction ledger.

### `Wo_Payment_Gateway_Bridge`

The cross-platform state machine.

That distinction is important. 

The new table is:

```text
Wo_Payment_Gateway_Bridge

id
token_hash
wow_order_id
wow_user_id
wp_user_id
transaction_kind
source_currency
source_amount
payload_json
status
woo_order_id
error_code
error_message
created_at
expires_at
claimed_at
fulfilled_at
```

with the state:

```text
ready
  ↓
claimed
  ↓
checkout
  ↓
fulfilled
```

or, when something fails:

```text
ready → failed
ready → expired
claimed → failed
```

The token itself is **never stored**.

Only:

```php
hash('sha256', $token)
```

is stored.

The browser receives:

```text
/pgb-checkout/?token=...&sig=...
```

where:

```php
$sig = hash_hmac(
    'sha256',
    $token,
    BUZZ_PGB_SECRET
);
```

This is the correct security model proposed in the earlier design.

# 4. WooCommerce checkout URL — the correct implementation

I specifically checked the WooCommerce source you supplied.

We should **not manually construct**:

```text
/checkout/order-pay/{id}/?pay_for_order=true&key=...
```

WooCommerce already has the correct method:

```php
$order->get_checkout_payment_url(false);
```

The installed WooCommerce source shows that this method generates:

```php
wc_get_endpoint_url(
    'order-pay',
    $this->get_id(),
    wc_get_checkout_url()
);
```

and adds:

```text
pay_for_order=true
key=<order key>
```

when `$on_checkout` is false. 

Therefore the new engine does:

```php
$checkout_url = $order->get_checkout_payment_url(false);

wp_safe_redirect($checkout_url, 303);
exit;
```

That is much safer than reproducing WooCommerce's internal URL construction.

The same principle applies to the receipt:

```php
$order->get_checkout_order_received_url();
```

# 21. Idempotency

The bridge has multiple protection layers.

### Bridge level

Unique:

```text
token_hash
wow_order_id
```

### WooCommerce level

Search:

```php

```

before creating another WooCommerce order.

### Fulfillment level

Order meta:

```text
_bzj_pgb_fulfilled
```

prevents duplicate fulfillment.

### Execution lock

A transient:

```text
bzj_pgb_lock_{order_id}
```

prevents concurrent completion handlers from executing the business logic simultaneously.

### WooCommerce recovery hooks

The engine listens to:

```php
woocommerce_payment_complete

woocommerce_order_status_completed
woocommerce_thankyou
```

This is preferable to relying exclusively on the Thank You page. The earlier analysis specifically identified this as important because a user can pay successfully and never return to the Thank You page.
