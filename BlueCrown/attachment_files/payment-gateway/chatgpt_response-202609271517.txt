# Executive conclusion

The proposed upgrade is **architecturally correct**, but I would not deploy the earlier v4.2 package exactly as supplied by the previous review. The GitHub review correctly identified the major structural direction, but there are several production-specific issues that need to be reconciled with the actual Buzzjuice implementation.

The most important change is this:

> **WooCommerce becomes the payment-state authority; the browser/thank-you page becomes presentation only.**

Your current bridge has a genuine durability problem because important fulfillment work is attached to `wp_footer` on the WooCommerce `order-received` page. If payment succeeds but the customer never loads that page, the fulfillment path can never execute. 

The current code also has several concrete defects:

* `wow-pgb_webhook.php` executes the same transaction UPDATE twice. 
* It contains a hard-coded WooCommerce webhook secret. 
* `wow-pgb_init.php` disables SSL certificate verification for cURL. 
* Streams currently creates `Wo_Payment_Transactions`, and for marketplace purchases creates `Wo_Purchases`/`Wo_UserOrders`, **before payment is actually confirmed**. 
* Streams currently possesses WooCommerce consumer credentials even though WordPress is the authoritative platform. 
* AffiliateWP processing is currently coupled to the old synchronization/redirect process rather than the WooCommerce paid lifecycle. 
* Jewel is coupled to the old webhook path. 

The upgraded architecture should therefore be:

```text
                BUZZJUICE STREAMS
                       │
                       │ signed payment intent
                       ▼
             WordPress PGB MU PLUGIN
                       │
              ┌────────┴─────────┐
              │                  │
        PGB transaction      WooCommerce
             ledger             order
              │                  │
              │                  ▼
              │             Payment Gateway
              │                  │
              │             PAYMENT SUCCESS
              │                  │
              └──────────────────┘
                       │
                       ▼
          WooCommerce paid lifecycle hooks
                       │
             ┌─────────┼──────────┐
             │         │          │
             ▼         ▼          ▼
          Streams   AffiliateWP  Jewel
        fulfillment   addon       addon
             │
             ▼
       Streams DB state
```

This is much more durable because WooCommerce's payment lifecycle is what drives fulfillment. WooCommerce itself recommends `$order->payment_complete()`/payment lifecycle mechanisms rather than relying on a browser return page. ([The WooCommerce Developer Blog][1])



The new flow is:

```text

   ↓

   ↓

   ↓

   ↓
```

So an abandoned checkout remains:


rather than appearing in Streams as a completed purchase.

This follows the previous review's recommendation and is one of the biggest durability improvements. ([GitHub][2])

# 15. WooCommerce Subscriptions

This requires special treatment.

The old system manually creates subscriptions through the WooCommerce REST API. ([GitHub][3])

I would **not carry that architecture forward**.

```text
       ↓
wcs_create_subscription()
       ↓
WC_Subscription
       ↓
active
```

The installed Subscriptions plugin remains responsible for the subscription lifecycle.

That is considerably cleaner than maintaining a second subscription engine.

## Root cause identified

The v5.0.0 MU plugin was **loading too early**.

WordPress loads files in `wp-content/mu-plugins/` before ordinary plugins. The original bootstrap immediately did:

```php
PGB_Bootstrap::instance();
```

and its constructor immediately checked:

```php
if (!class_exists('WooCommerce')) {
    ...
    return;
}
```

At that moment WooCommerce had not necessarily loaded yet.

So the sequence was effectively:

```text
MU plugin loads
    ↓
PGB_Bootstrap()
    ↓
WooCommerce class not loaded yet
    ↓
return
    ↓
PGB never initializes
```

That explains **all three symptoms**:

* no `wp_bzj_pgb_transactions`
* no admin page
* no PGB log files

There was also a secondary problem: the logger itself was configured with logging disabled by default, so even the bootstrap failure could be invisible.

# Corrected v5.0.1

I've corrected the architecture and generated a new package:

**[Download Buzzjuice Payment Gateway v5.0.1](sandbox:/mnt/data/buzzjuice-payment-gateway-v5.0.1.zip)**

I also PHP-linted all PHP files in the package; they pass syntax validation.

### The important changes

### 1. MU plugin waits for `plugins_loaded`

Instead of immediately executing the engine, it now does:

```php
add_action('plugins_loaded', static function () {
    try {
        PGB_Bootstrap::instance();
    } catch (Throwable $e) {
        error_log('[BZJ-PGB][bootstrap] Fatal bootstrap exception: ' . $e->getMessage());
    }
}, 20);
```

Therefore:

```text
MU plugins
    ↓
normal plugins load
    ↓
plugins_loaded
    ↓
PGB bootstrap
    ↓
WooCommerce available
```

This is the key fix.

---

### 2. Database installation no longer depends on WooCommerce

The schema is now installed before checking whether WooCommerce is available.

Therefore the following should be created even if WooCommerce is temporarily disabled:

```text
wp_bzj_pgb_transactions
```

---

### 3. Admin component no longer depends on WooCommerce

The Payment Gateway admin component is loaded independently.

The page registration therefore doesn't disappear merely because WooCommerce wasn't available during an early bootstrap.

---

### 4. First-install logging is enabled

A new installation defaults to:

```text
Logging: ON
Log level: DEBUG
```

Once you have verified the bridge, you can turn it off from the admin page.

The bootstrap logger also **touches its component log file**, so:

```text
shared/payment-gateway/log/class-pgb-bootstrap.log
```

should exist after PGB initializes.

---

### 5. Critical errors still reach PHP's error log

Even if PGB file logging is disabled, `error` and `critical` events still use PHP:

```php
error_log(...)
```

So disabling the PGB diagnostic files won't completely blind the system.
