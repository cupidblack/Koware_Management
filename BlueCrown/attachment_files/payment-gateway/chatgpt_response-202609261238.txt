## Executive conclusion

The two prior reviews are directionally correct, but I would make several important corrections before implementation.

The repository confirms that the current bridge has become a **distributed payment processor without a durable transaction coordinator**:

* Streams validates the browser request, creates the WoWonder payment transaction, constructs the WooCommerce order and currently carries WooCommerce credentials. 
* The Streams JavaScript sends client-supplied `amount`, `product_price`, `transaction_kind`, product IDs and related values directly into the payment initializer. 
* The current Streams webhook directly updates payment transactions and other business state. 
* The WordPress `wow-pgb_sync.php` has accumulated WooCommerce product creation, redirects, subscription processing, AffiliateWP processing, API communication and configuration. 
* The current webhook contains a **hard-coded WooCommerce webhook secret**, which should be removed and rotated. 
* The current Streams client disables SSL verification in its cURL requests, which must not remain in production. 
* The existing AffiliateWP implementation is substantial and should be preserved/refactored rather than replaced wholesale. It already has deterministic affiliate resolution, duplicate checking and accounting verification. 
* The existing Jewel implementation already contains useful idempotent wallet-credit logic and role/subscription synchronization. 

The most important architectural change is therefore:

> **Do not merely move `wow-pgb_init.php` and `wow-pgb_sync.php` into different folders. Replace the bridge's execution model with a persistent, idempotent PGB transaction coordinator.**

# 3. Transaction state machine

I would use two layers of state.

### Main state

```text

   ↓
order_created
   ↓
awaiting_payment
   ↓
payment_received
   ↓
processing
   ↓
fulfilled
   ↓

```

Independently:


For example:


That means an AffiliateWP failure does **not** cause the user's wallet/subscription to be processed a second time.

This component-level recovery recommendation from the earlier review is particularly important.

# 5. Streams should no longer know WooCommerce credentials

This is one of the biggest improvements.

Currently:

```text
Streams
   ↓
wow_api_url
wow_api_key
wow_api_secret
   ↓
WooCommerce REST API
```

The existing implementation explicitly reads those credentials from Streams configuration. 

That should become:

```text
Streams
   ↓
HMAC
   ↓
WordPress PGB
   ↓
WooCommerce PHP API
```

Because WooCommerce is installed in the same authoritative WordPress environment, there is no reason for the Streams application to authenticate to its own WordPress/WooCommerce installation with WooCommerce consumer credentials.

This removes an entire class of:

* credential exposure
* REST authentication failures
* API timeouts
* SSL problems
* duplicate order creation
* credential synchronization problems

# 6. Streams → WordPress authentication

The previous recommendation for HMAC should be retained. 

Headers:

```text
X-BZJ-PGB-Key
X-BZJ-PGB-Timestamp
X-BZJ-PGB-Nonce
X-BZJ-PGB-Signature
X-BZJ-PGB-Request-ID
```

Signature:

```text
timestamp
+
"\n"
+
nonce
+
"\n"
+
request_id
+
"\n"
+
raw_body
```

Then:

```php
hash_hmac(
    'sha256',
    $signing_string,
    $shared_secret
);
```

WordPress verifies:

1. HTTPS
2. timestamp tolerance
3. nonce
4. request ID
5. signature
6. request body
7. origin
8. transaction intent
9. authenticated user relationship

Nonce/request replay records should expire automatically.

# 7. Do not trust the browser's price

This is a major correction to the existing system.

The current JavaScript submits:

```text
product_price
amount
product_units
product_owner_id
transaction_kind
```

directly to the payment initializer. 

Those are useful as **intent information**, but not as authoritative financial values.

For example:

```text
Browser says:

product_price = 27
```

The server must independently establish:

```text
What product is this?
What is the authorised price?
What currency?
What variation?
What quantity?
What user?
What transaction type?
```

Only then should WooCommerce receive the final amount.

# 11. Idempotent order creation

This is essential for the "dropped orders" problem.

Suppose Streams sends:

```text
request_id = req_abc
idempotency_key = idem_xyz
```

WordPress creates:

```text
pgb transaction = pgb_123
Woo order = 456
```

but the HTTP response gets lost.

The browser retries:

```text
idempotency_key = idem_xyz
```

The PGB finds:

```text
idem_xyz → pgb_123 → Woo order 456
```

and returns:

```json
{
    "success": true,
    "transaction_id": "pgb_123",
    "woo_order_id": 456,
    "payment_url": "..."
}
```

It **does not create Woo order 457**.

This is one of the most important differences between the new system and the existing one.

# 19. AffiliateWP failure must not roll back payment

This is important.

```text

```

The transaction becomes:


```text

```


This is the correct durable model.

> **Every retry calls the same transaction processor.**

The PGB should periodically identify transactions such as:

```text

```

```text

Streams says pending
```


```text

       ↓

```

This is what turns the bridge from a collection of callbacks into a **recoverable payment system**.

# 34. Locking

The PGB transaction processor should acquire a transaction lock.

For example:

```text
transaction pgb_123
lock_until = now + 120 seconds
```

Only one worker processes it.

If a PHP request dies:

```text
lock expires
 ↓
Action Scheduler retries
```

This prevents:

```text
webhook
+
payment_complete
+
browser return
```

from simultaneously fulfilling the same transaction.

No pathway should implement its own copy of:

# 53. What happens when the user closes the browser?

```text

 ↓
```

```text

 ↓

```

# 55. What happens if `payment_complete` and webhook race?

Both execute:

```php
bzj_pgb_process_transaction($transaction_id);
```

The transaction lock allows one processor to proceed.

The second sees:

```text
transaction already processing/completed
```

and exits safely.

This is why the processor must be centralized.

---

# 56. What happens if AffiliateWP fails?

```text
Payment        = paid
Streams        = completed
AffiliateWP    = pending
Jewel          = completed
```

Action Scheduler retries:

```text
AffiliateWP
```

Only.

This is substantially safer than the current monolithic completion behaviour.

---

# 57. What happens if Streams fails?

```text
Payment        = paid
Streams        = pending
AffiliateWP    = pending
Jewel          = pending
```

The processor retries Streams first.

Once Streams succeeds:

```text
Streams        = completed
```

then the dependent addons can continue.

# 60. Final proposed architecture

The resulting Buzzjuice payment ecosystem becomes:

```text
                         BUZZJUICE NETWORK
                                │
                                ▼
                     ┌─────────────────────┐
                     │ Streams / WoWonder   │
                     │ Payment UI           │
                     └──────────┬──────────┘

                         PGB Client/HMAC

                                ▼

              │                                │
              │ bzj-payment-gateway.php       │
              └────────────────┬───────────────┘
                               │
             ┌─────────────────┼─────────────────┐
             │                 │                 │
             ▼                 ▼                 ▼
       PGB Transaction    WooCommerce       Action Scheduler
          State Store       Engine             Recovery
             │                 │                 │
             └─────────────────┼─────────────────┘
                               │
                               ▼
                     ┌──────────────────┐

   Streams Integration   AffiliateWP Addon   Jewel Integration
          │                   │                     │
          ▼                   ▼                     ▼
   WoWonder database    AffiliateWP DB        WP + Streams
```

## The architectural decisions I would lock in

**1. One MU-plugin file only.**

```text
wp-content/mu-plugins/bzj-payment-gateway.php
```

**2. Everything else belongs under:**

```text
shared/payment-gateway/
```

**3. WordPress/WooCommerce is the payment orchestration authority.**

**4. WooCommerce is the payment/order authority.**

**5. Streams remains the WoWonder business-data authority.**

**6. AffiliateWP remains the affiliate-accounting authority.**

**7. Jewel remains a modular integration.**

**8. The PGB transaction is the cross-system state authority.**

**9. `payment_complete`, webhook, retry and reconciliation all enter the same processor.**

**10. Idempotency, not browser behaviour, prevents duplicates.**

**11. Action Scheduler provides recovery.**

**12. Browser redirects are presentation only, never payment authority.**

**13. WooCommerce credentials leave Streams completely.**

**14. The existing working AffiliateWP and Jewel logic is migrated rather than rewritten unnecessarily.**

**15. `wow-pgb_init.php`, `wow-pgb_sync.php` and the old webhook become compatibility/deprecation layers during migration rather than remaining parallel payment processors.**

This incorporates the useful recommendations from both supplied reviews while correcting the MU-plugin directory conflict and, more importantly, correcting the deeper architectural issue: **the upgraded bridge should be a durable transaction/state machine with idempotent component processing, not simply a cleaner collection of PHP files.** 

### Implementation boundary

The next implementation should therefore be generated as a **complete file-by-file replacement package**, not as another conceptual patch to `wow-pgb_sync.php`. The first concrete package should contain the single MU bootstrap, the PGB core classes, database installer/migration, Streams HMAC client, WordPress REST endpoints, WooCommerce integration, processor/state machine, logging, Action Scheduler recovery, Blue Crown admin page, AffiliateWP addon, currency integration, Jewel integration, and the thin Streams compatibility adapter—followed by the specific edits to `requests.php`, payment settings and the payment JavaScript. This keeps the migration controlled while allowing the old bridge to remain available until the new transaction path has passed the full test matrix.
