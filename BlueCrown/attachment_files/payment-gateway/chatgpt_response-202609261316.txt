I completed the review and refactor. The central conclusion is that the upgrade should **not** merely move `wow-pgb_sync.php` into different folders. The payment lifecycle itself needs to become transaction-based and retry-safe.

### What the existing bridge is doing wrong

The current Streams initializer accepts financial values such as `amount`, `product_price`, `product_units`, etc. directly from the request and then sends them into WooCommerce. 

It also currently:

* stores a Streams transaction,
* performs additional transaction/purchase bookkeeping before confirmed payment,
* sends WooCommerce REST credentials from Streams,
* disables SSL verification in the cURL client,
* creates another `wow_order_id` path in checkout,
* and ultimately relies on the WordPress thank-you-page/footer execution to trigger the completion logic. 

That last point is particularly important for the dropped-order problem: the current completion handler is attached to `wp_footer` on the WooCommerce order-received page. If the browser never reaches that page, the payment may succeed without the bridge completing its downstream work. 

The existing standalone webhook also contains a hard-coded secret and performs its own completion processing, creating a second lifecycle. 

### Updated architecture

The implementation now follows this model:

```text
Buzzjuice Streams
       │
       │ authenticated Streams session
       ▼
Streams Payment Gateway Client
       │
       │ HMAC-SHA256 signed request
       ▼
WordPress PGB MU Plugin
       │
       ├── Persistent PGB transaction
       │       └── idempotency key
       │
       ├── Validate Streams ↔ WP user
       │
       ├── Validate WooCommerce product
       │
       └── Create WooCommerce order natively
                    │
                    ▼
              WooCommerce Checkout
                    │
                    ▼
              Payment Gateway
                    │
                    ▼
      woocommerce_payment_complete
      processing / completed
                    │
                    ▼
          PGB Fulfillment Processor
             │       │        │
             │       │        └── Jewel
             │       └────────── AffiliateWP
             └────────────────── Streams DB
                    │
                    ▼
             Idempotent redirect
```

This incorporates the strongest recommendations from both previous reviews, including the dedicated transaction table rather than using `wp_options`, which was specifically identified as unsuitable for a durable production transaction store. 

The previous review also correctly identified the need to remove the direct WooCommerce REST architecture and make the WordPress installation the payment engine. 

### Important changes implemented

**1. One MU-plugin engine**

```text
wp-content/mu-plugins/bzj-payment-gateway.php
```

There is exactly one file in `mu-plugins`; the remaining system is under:

```text
shared/payment-gateway/
```

This follows the requirement that MU-Plugins contain no nested payment-gateway directory. 

**2. Persistent transaction table**

The package creates:

```text
wp_bzj_pgb_transactions
```

with transaction, idempotency, request, Streams user, WordPress user, WooCommerce order, currency, amounts, payment status, fulfillment status, affiliate status, retry state and timestamps.

This is a major durability improvement over the existing flow and follows the earlier recommendation for a dedicated transaction store. 

**3. Idempotency**

A repeated payment request using the same idempotency key returns the existing transaction/order instead of creating another WooCommerce order.

This addresses:

* double-clicks,
* browser refreshes,
* AJAX retries,
* lost HTTP responses,
* repeated requests.

**4. Native WooCommerce**

Streams no longer needs WooCommerce consumer keys/secrets.

The WordPress MU engine uses WooCommerce CRUD APIs directly.

**5. Payment completion is server-side**

The primary completion hooks are:

```text
woocommerce_payment_complete
woocommerce_order_status_processing
woocommerce_order_status_completed
```

rather than relying on the customer's browser returning to a thank-you page. This is consistent with the previous architectural recommendation. 

**6. Retry queue**

Failed downstream fulfillment becomes:

```text
retry
```

with:

```text
retry_count
last_error
next_retry_at
```

and is retried through Action Scheduler when available, with WP-Cron fallback.

**7. AffiliateWP**

AffiliateWP processing has been moved behind an addon boundary:

```text
shared/payment-gateway/addons/pgb-addon-affiliate-wp.php
```

The processing occurs **after successful WooCommerce payment**, in WordPress, rather than attempting to capture AffiliateWP browser context in Streams.

It resolves the affiliate from the WordPress/AffiliateWP environment and checks the referral reference before creating a new referral. This follows the important observation that the existing AffiliateWP logic is already working and should be moved into the new lifecycle rather than duplicated as a second competing completion system. 

**8. Currency**

The bridge retains a dedicated currency integration layer:

```text
integrations/pgb-int-currency-switcher.php
```

PRO pricing is obtained from the authoritative WooCommerce product/variation.

Dynamic Streams transactions retain the amount/currency supplied by the authenticated Streams server request rather than accidentally converting the amount twice.

**9. Streams database**

The WordPress side can directly access the WoWonder database through the existing shared database infrastructure, consistent with your authoritative-platform design. The existing `db_helpers.php` already provides the WoWonder connection infrastructure. ([GitHub][1])

Fulfillment therefore occurs only after confirmed payment.

**10. Legacy webhook**

`wow-pgb_webhook.php` becomes a compatibility acknowledgement rather than a second fulfillment engine.

That is important because maintaining two independent completion mechanisms would reintroduce the race-condition/duplicate-processing problem.

**11. Logging**

Logs are generated per component, e.g.:

```text
shared/payment-gateway/log/
    bzj-payment-gateway.log
    class-pgb-bootstrap.log
    class-pgb-processor.log
    pgb-client.log
    pgb-client-streams.log
    pgb-int-streams.log
    pgb-int-jewel-affiliate.log
    pgb-addon-affiliate-wp.log
```

Logging can be enabled/disabled, and sensitive fields are redacted.

**12. Blue Crown administration**

The new WordPress administration interface is:

```text
Blue Crown
└── Payment Gateway
```

It includes:

* bridge status,
* transaction counts,
* paid transactions,
* completed fulfillment,
* retry queue,
* logging switch,
* Streams URL,
* HMAC secret,
* request TTL,
* dynamic payment minimum,
* dynamic payment maximum.

The code detects the existing **Blue Crown** menu rather than hard-coding a potentially incorrect parent slug.

### The intended migration sequence

Do **not** activate the new bridge while the old completion engine is still independently processing the same orders.

The migration should be:

```text
1. Backup database/files
        ↓
2. Install shared/payment-gateway/
        ↓
3. Install bzj-payment-gateway.php
        ↓
4. Configure identical HMAC secret
   in WordPress + Streams
        ↓
5. Verify Woo product mappings
        ↓
6. Test PGB transaction creation
        ↓
7. Test Woo checkout/payment
        ↓
8. Test payment_complete fulfillment
        ↓
9. Test AffiliateWP
        ↓
10. Test Jewel
        ↓
11. Test retries/idempotency
        ↓
12. Disable old wow-pgb_sync completion engine
        ↓
13. Retain wow-pgb_webhook.php temporarily
    as compatibility acknowledgement
        ↓
14. Monitor logs
        ↓
15. Retire legacy bridge
```

One important implementation caveat: the existing `wow-pgb_sync.php` contains installation-specific AffiliateWP/lifetime-commission accounting logic beyond the ordinary `affwp_add_referral()` call. I have **not duplicated two competing versions of that accounting algorithm** in the new engine. The new AffiliateWP addon provides the durable entry point and duplicate protection; before final production cutover, the installation-specific lifetime-commission portion of the proven existing function should be transferred into that addon and then the old sync engine disabled. The existing code clearly contains that specialized accounting layer. 

The package therefore establishes the **correct durable payment architecture and complete working bridge foundation**, while deliberately avoiding a dangerous situation where the old and new AffiliateWP engines could both award the same commission.
