# 1. What the cPanel DNS test actually proves

Your two tests are important:

```text
VS Code:
HTTP/1.1 200 OK
...
```

versus:

```text
cPanel:
curl: (6) Could not resolve host: buzzjuice.net
```

The second result does **not** mean that `buzzjuice.net` itself is inaccessible.

It means the particular server/environment running the cPanel terminal could not resolve the hostname through its DNS resolver.

That distinction matters:

```text
User's browser
      |
      | HTTPS
      v
buzzjuice.net
      |
      v
WordPress/WooCommerce
```

can work perfectly while:

```text
cPanel server
      |
      | curl https://buzzjuice.net
      X
DNS resolution failure
```

fails.

The current `wow-pgb_init.php` nevertheless depends on exactly that second type of server-to-server request. It constructs:

```php
$woocommerce_api_url = rtrim($GLOBALS['wo']['config']['wow_api_url'], '/') . '/wc/v3';
```

and eventually POSTs to:

```php
$woocommerce_api_url . '/orders'
```

using cURL. 

So your proposed architectural change is justified even without determining why cPanel's DNS resolver is failing.

# 3. The correct WooCommerce redirect mechanism

This was one of the most important findings from examining WooCommerce itself.

You do **not** need to manufacture the URL yourself.

WooCommerce already provides:

```php
$order->get_checkout_payment_url()
```

The current WooCommerce code defines this specifically as the URL allowing the customer to pay an unpaid/pending order. ([WooCommerce GitHub][1])

Internally WooCommerce generates an endpoint equivalent to:

```text
/checkout/order-pay/{ORDER_ID}/?pay_for_order=true&key={ORDER_KEY}
```

or the checkout variant with the key.

Therefore:

```php
$payment_url = $order->get_checkout_payment_url();
```

is the correct mechanism.

The REST API also exposes this same WooCommerce-generated payment URL as `payment_url`. ([WooCommerce GitHub][2])

### Consequently

These files you identified:

* `AbilitiesRestBridge.php`
* `class-wc-auth.php`
* `CheckoutSchema.php`

are **not the place where I would build the redirect mechanism**.

The correct underlying function is:

```php
WC_Order::get_checkout_payment_url()
```

The Store API/REST layer is unnecessary for this bridge.

# 5. Why this is much more durable

The current architecture contains a long chain:

```text
Streams
 ↓
cURL
 ↓
DNS
 ↓
HTTPS
 ↓
WordPress
 ↓
REST API
 ↓
WooCommerce REST authentication
 ↓
WooCommerce order creation
 ↓
API response
 ↓
Streams parses response
 ↓
redirect
```

Every one of those steps can fail.

The proposed architecture reduces it to:

```text
Streams
 ↓
local DB insert
 ↓
browser redirect
 ↓
WordPress
 ↓
WooCommerce PHP API
 ↓
order-pay
```

The important distinction is that WordPress is already executing inside the WooCommerce installation.

It therefore doesn't need:

```text
HTTP → DNS → HTTPS → REST → authentication
```

to access WooCommerce.

It can simply execute:

```php
wc_create_order();
wc_get_product();
$order->add_product();
$order->save();
$order->get_checkout_payment_url();
```

directly.

# 7. Why the token is important

I deliberately did **not** put the raw order data directly into the redirect URL.

Instead:

```text
random token
     ↓
HMAC-SHA256
     ↓
token_hash
     ↓
database
```

The browser receives only the temporary token.

The WordPress side validates:

1. token exists;
2. HMAC matches;
3. order is still `pending`;
4. token has not expired;
5. staging record has not already been claimed.

The token is also deliberately short-lived.

The default is:

```text
900 seconds
```

or 15 minutes.

This prevents someone from simply inventing:

```text
?wow_order_id=...
&amount=...
&user_id=...
```

and attempting to create arbitrary WooCommerce orders.

# 8. Concurrency protection

This is one of the most important durability improvements.

Suppose the customer double-clicks the button or the browser reloads:

```text
Request A ─────┐
               ├── same payment
Request B ─────┘
```

Both must **not** create:

```text
Woo Order #101
Woo Order #102
```

for one Streams transaction.

The WordPress manager therefore obtains the staging row using a database lock:

```sql
SELECT ...
FROM Wo_PGB_Orders
WHERE token_hash = ?
LIMIT 1
FOR UPDATE
```

Then it claims the staging record after successfully creating the WooCommerce order.

This is considerably stronger than simply checking:

```php
if (!$order_id) ...
```

# 10. The final redirect

After saving the WooCommerce order:

```php
$order->save();

$payment_url = $order->get_checkout_payment_url();
```

and then:

```php
wp_safe_redirect($payment_url);
exit;
```

This uses WooCommerce's own order key and order-pay endpoint rather than trying to construct a fake `order-received` URL. WooCommerce documents `get_checkout_order_received_url()` as the **thanks/order-received** URL, while `get_checkout_payment_url()` is specifically the unpaid-order payment URL. ([WooCommerce GitHub][1])

That distinction is important.

Your example:

```text
/checkout/order-received/146/?key=...
```

is the **post-payment/thank-you destination**, not the page where the customer should initially pay.

The bridge should initially send the customer to:

```text
/checkout/order-pay/146/?...
```

via:

```php
$order->get_checkout_payment_url()
```

# 11. Subscriptions

The existing architecture has been attempting to create/manage subscriptions through the WooCommerce REST API.

That should also be removed from the bridge's server-to-server path.

WooCommerce Subscriptions exposes:

```php
wcs_create_subscription()
```

and subscription objects can be associated with the parent order. The current Subscriptions implementation supports creating a subscription with an `order_id`, `customer_id`, billing period and billing interval. ([GitHub][3])

More importantly, Subscriptions provides lifecycle hooks including:

```text
woocommerce_subscription_payment_complete
woocommerce_subscription_renewal_payment_complete
woocommerce_subscription_payment_failed
woocommerce_checkout_subscription_created
subscriptions_created_for_order
woocommerce_subscription_status_updated
woocommerce_subscription_status_cancelled
woocommerce_subscription_status_expired
```

([WooCommerce][4])

The upgrade therefore follows this principle:

> **Do not manually recreate the entire Subscriptions engine.**

The bridge should establish the proper WooCommerce order/subscription relationship, then allow WooCommerce Subscriptions to manage its lifecycle.

The package includes initial PRO subscription handling using:

```php
wcs_create_subscription()
```

and links it to the parent WooCommerce order.

After payment, the PGB completion manager verifies/activates the relevant subscription.

and:


or:

```text

warning
```

Sensitive values are redacted.

# 42. One additional improvement I recommend

Although the generated v9 bridge solves the cPanel DNS problem, I would make the next production-hardening pass add a dedicated **PGB reconciliation process**.

For example:

```text
Wo_PGB_Orders
        |
        +-- pending > 15 min
        |
        +-- claimed but no Woo order
        |
        +-- claimed + Woo order unpaid
        |
        +-- Woo paid but Streams not finalized
```

This allows a scheduled process to find abnormal states.

That matters because "durable" payment architecture should not rely exclusively on the customer's browser returning successfully.

A customer can:

```text
pay successfully
↓
close browser
```

before your final redirect occurs.

WooCommerce has the authoritative payment event, so the PGB engine should be able to reconcile the Streams side independently.
