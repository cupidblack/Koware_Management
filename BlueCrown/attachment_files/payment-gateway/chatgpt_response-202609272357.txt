# Buzzjuice Payment Gateway Bridge — v7.0 Architecture

I reviewed the current Streams bridge, `wow-pgb_init.php`, `requests.php`, payment settings, the current WordPress sync engine, AffiliateWP implementation, webhook, `shared/db_helpers.php`, and the two prior design documents.

The central conclusion is:

> **Do not replace the current WooCommerce REST call with another HTTP API call. Replace the HTTP transport itself with a database-backed payment-intent handoff.**

That is better suited to the actual Buzzjuice hosting topology.

The current implementation creates WoWonder-side payment records before WooCommerce has confirmed payment, and then makes a direct cURL request to WooCommerce. The cURL code also explicitly disables SSL verification. 

The existing shared DB helper already provides a direct WordPress database connection through `get_wp_db_conn()`, while also providing the WoWonder connection through `get_wowonder_db()`. 

So we can eliminate the unreliable server-to-server HTTP dependency altogether.

# 2. Why I changed the previous REST proposal

The GitHub/previous proposal suggested:

```text
Streams
   ↓
HMAC
   ↓
/wp-json/bzj-pgb/v1/order
   ↓
WooCommerce
```

That is a sound architecture **when server-to-server HTTP is reliable**.

But your actual evidence shows:

```text
PC / VS Code
     ↓
buzzjuice.net
     ↓
200 OK


cPanel terminal
     ↓
buzzjuice.net
     ↓
DNS resolution failure
```

The existing `wow-pgb_init.php` depends on exactly that kind of server-side HTTP call. 

Therefore I would **not make the new system dependent on REST at all**.

Instead:

```text
Streams PHP
     │
     │ direct MySQL connection
     ▼
WordPress DB
     │
     │ browser redirect
     ▼
WordPress
```

This is a significant improvement because it removes:

* cPanel DNS dependency
* cURL dependency
* WooCommerce REST authentication
* WooCommerce API rate limits
* consumer key/secret storage in Streams
* same-host HTTP loopback
* SSL verification problems
* WooCommerce REST retry logic

And it uses infrastructure that Buzzjuice already has.

# 3. New transaction ledger

The previous recommendation for a durable ledger was:

```text
wp_bzj_pgb_transactions
```

I agree with this part completely. The state machine proposed previously was:

```text
initiated
    ↓
order_created
    ↓
paid
    ↓
fulfilling
    ↓
fulfilled
```

with failure states for order creation and fulfillment. ([GitHub][1])

The new implementation expands that slightly:

```text
initiated
    │
    ▼
order_created
    │
    ▼
WooCommerce payment
    │
    ▼
fulfilling
    │
    ├──────► fulfillment_failed
    │
    ▼
fulfilled
```

The important thing is that the ledger survives:

* browser closure
* checkout abandonment
* PHP timeout
* duplicate WooCommerce hooks
* duplicate browser requests
* failed affiliate processing
* failed Streams synchronization
* failed subscription processing

# 6. Signed browser handoff

The browser URL will look conceptually like:

```text
https://buzzjuice.net/?bzj_pgb=checkout
    &request_id=pgb_...
    &expires=...
    &sig=...
```

There is **no**:

```text
consumer_key
consumer_secret
WooCommerce API key
WooCommerce API secret
payment credentials
```

in that URL.

The signature is:

```text
HMAC-SHA256(
    request_id + "\n" + expires,
    BZJ_PGB_SECRET
)
```

The secret exists only in `.env`.

This follows the security principle in the previous architecture work: secrets should not be placed into Streams settings, HTML, JavaScript, WooCommerce metadata or logs. ([GitHub][1])

The old file currently:

```text
Streams
 ↓

 ↓
WooCommerce REST API
 ↓

```

```php

```

The replacement now:

```text
Streams
 ↓

 ↓

 ↓

 ↓
```

The browser then leaves Streams.

# 9. Very important change to payment records

The current implementation can create records such as marketplace purchases before payment has happened. The previous analysis correctly identified the resulting failure mode:

```text
User clicks Pay
      ↓
Streams creates purchase
      ↓
WooCommerce order created
      ↓
User abandons checkout
      ↓
Streams says purchase exists
```

That must disappear.

The new system treats:

```text
PGB ledger = payment intent
WooCommerce order = payment transaction
Streams fulfillment = post-payment consequence
```

That separation is fundamental.


# 26. One architectural improvement I would make after v7.0

Once v7 is stable, I would add a small **PGB recovery/admin interface** under:

```text
Buzzjuice
    └── Payment Gateways
```

The first version only shows:

```text
Request ID
WoWonder Order
WooCommerce Order
User
Type
Amount
Status
Attempts
Created
Updated
Error
```

Then eventually:

```text
[View Woo Order]
[Retry Fulfillment]
[View Logs]
[View Streams Record]
```

That would turn the current payment bridge from a collection of PHP callbacks into an actual **transaction orchestration system**.

The most important thing is that v7 should first establish the durable foundation:

```text
Payment Intent
      ↓
Ledger
      ↓
WooCommerce Order
      ↓
Payment Authority
      ↓
Idempotent Fulfillment
      ↓
Modular Integrations
```

That gives Buzzjuice a much better base for adding additional payment products, Jewel, subscriptions, marketplace purchases, donations and future payment providers without rebuilding the bridge each time.

**One caution before live deployment:** the package deliberately keeps the existing WooCommerce product IDs/configuration model, but because I cannot execute the new code against your production WordPress/WooCommerce database from here, the first live test should be performed against a controlled test order. In particular, verify the existing handler variation IDs and the exact WooCommerce Subscriptions product configuration before enabling recurring payments.
