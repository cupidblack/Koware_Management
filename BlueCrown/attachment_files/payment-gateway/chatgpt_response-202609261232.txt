## Executive assessment

The proposed direction is sound, but I would make the upgrade **more opinionated than the original proposal**.

The existing bridge is not failing because WooCommerce itself is inherently unreliable. The larger problem is that **payment initiation, transaction persistence, WooCommerce order creation, completion, affiliate processing, Streams fulfilment, webhook processing and browser redirection are currently coupled together across several execution paths**.

The repository confirms several concrete weaknesses:

* `wow-pgb_init.php` currently validates the request, creates the Streams transaction, determines transaction type, builds the WooCommerce payload, handles AffiliateWP context, performs API communication and participates in redirect behaviour. 
* Streams currently sends WooCommerce API credentials from its own payment settings, even though WooCommerce is installed inside the authoritative WordPress environment. 
* The existing webhook directly modifies `Wo_Payment_Transactions`, wallet balances and funding records. It therefore acts as a business-processing engine rather than merely a payment event signal. 
* The WordPress sync file contains browser/thank-you-page redirection and AffiliateWP processing alongside the payment bridge. 
* The existing AffiliateWP implementation is actually quite valuable: it has customer resolution, multiple affiliate-resolution sources, duplicate referral detection and accounting verification. That logic should be **extracted largely intact**, not rewritten unnecessarily. 
* The current Streams JavaScript constructs the payment request and sends values such as price, amount, product and transaction kind through AJAX. It already has some double-click protection, but the server-side PGB must remain authoritative. 
* The existing Jewel integration contains useful idempotent rebate processing and subscription/role synchronisation that should be migrated into the new completion architecture rather than duplicated. 

The previous ChatGPT review and GitHub review therefore converge on the right broad architecture: **WordPress PGB as orchestration authority, WooCommerce as payment/order authority, Streams as business-fulfilment authority, AffiliateWP as affiliate-accounting authority, and Jewel as a modular integration**. 

There is, however, one important refinement I would retain from the previous review: **the shared `payment-gateway` layer must not become another database monolith**. Shared code should provide transport/security/contracts/utilities; the WordPress MU plugin should own WordPress, WooCommerce and controlled Streams-database orchestration. 

Below is the resulting architecture I would use.

# Payment Gateway Bridge — Refactored Architecture & Implementation Proposal

## 1. Objective

Replace the current WoWonder/WooCommerce payment bridge with a durable, modular and recoverable Payment Gateway Bridge (PGB) that:

* prevents dropped orders;
* prevents duplicate WooCommerce orders;
* prevents duplicate Streams fulfilment;
* prevents duplicate wallet credits;
* prevents duplicate AffiliateWP referrals;
* prevents duplicate Jewel rewards;
* removes WooCommerce API credentials from Streams;
* makes WordPress the payment orchestration authority;
* keeps WooCommerce as the payment/order authority;
* keeps Streams as the WoWonder business-data authority;
* retains the existing successful AffiliateWP logic;
* retains the existing WooCommerce currency-switcher behaviour;
* provides independent recovery through WooCommerce webhooks;
* supports automatic retries;
* provides administrative transaction visibility;
* provides extensive but safe logging;
* allows addons/integrations to be added without modifying the processor;
* allows the bridge to evolve to other Buzzjuice services later.

The guiding principle is:

```text
Streams initiates
        ↓
WordPress PGB orchestrates
        ↓
WooCommerce processes payment
        ↓
WordPress PGB verifies payment
        ↓
Streams is fulfilled
        ↓
AffiliateWP / Jewel / other integrations execute
        ↓
PGB records final state
        ↓
Browser receives redirect instruction
```

# 2. Authority Model

The new system should explicitly define ownership.

| Component          | Authority                                    |
| ------------------ | -------------------------------------------- |
| Buzzjuice Streams  | WoWonder business records                    |
| WordPress PGB      | Payment orchestration and transaction state  |
| WooCommerce        | Woo order/payment state                      |
| AffiliateWP        | Affiliate accounting                         |
| Jewel Affiliate    | Jewel-specific entitlement/reward processing |
| Currency Switcher  | Currency conversion                          |
| Browser JavaScript | User experience only                         |

The browser must never be an authority.

It must never:

* determine the final price;
* determine commission;
* mark a transaction paid;
* activate PRO;
* credit wallet;
* create AffiliateWP referrals;
* award Jewel rewards.

# 5. Streams Client

The current:

```text
streams/assets/wow-pgb/wow-pgb_init.php
```

should ultimately become a thin adapter.

Its responsibility becomes approximately:

```text
1. Confirm logged-in user
2. Validate the requested Streams operation
3. Resolve server-side Streams data
4. Generate request ID
5. Generate idempotency key
6. Build PGB intent
7. Send signed request to WordPress
8. Receive checkout URL
9. Return JSON
```

It should no longer:

* create WooCommerce orders;
* contain WooCommerce API credentials;
* call WooCommerce REST API;
* perform payment completion;
* perform AffiliateWP processing;
* perform Jewel processing;
* perform final payment redirects.

# 8. Authentication

Streams → WordPress communication should use HMAC.

Headers:

```text
X-BZJ-PGB-Key
X-BZJ-PGB-Timestamp
X-BZJ-PGB-Nonce
X-BZJ-PGB-Signature
X-BZJ-PGB-Request-ID
```

Signature input:

```text
timestamp
+
"\n"
+
nonce
+
"\n"
+
request_id
+
"\n"
+
raw_body
```

Then:

```text
HMAC-SHA256(..., shared_secret)
```

WordPress verifies:

```text
HTTPS
timestamp window
nonce
signature
request ID
request body
origin
```

Replay protection must be enforced.

# 12. One PGB Transaction → One WooCommerce Order

This must be an enforced invariant.

```text
1 PGB transaction
        ↓
maximum 1 WooCommerce order
```

The unique idempotency key should be persisted before creating the order.

If Streams retries the same request:

```text
same idempotency_key
        ↓
existing PGB transaction found
        ↓
return existing transaction/order
```

Never create another WooCommerce order.

```text

       ↓

       ↓
```

```text
       ↓

       ↓

       ↓

       ↓
```

# 14. Transaction Locking

The following may occur simultaneously:

```text
WooCommerce payment_complete
WooCommerce webhook
scheduled retry
manual retry
browser status request
```

Only one worker should process the transaction.

Use an atomic lock such as:

```text
lock_token
lock_until
```

with an atomic database update.

Do not hold a MySQL transaction open while making remote operations against Streams.

The pattern should be:

```text
claim transaction
     ↓
process
     ↓
component-level idempotency
     ↓
update state
     ↓
release claim
```

Current:

```text

 ↓

 ↓

 ↓

 ↓
```

```text

 ↓
```

# 32. Automatic Recovery

Use WooCommerce/WordPress's existing Action Scheduler infrastructure.

Do not create an entirely separate custom queue unless future scale demonstrates a need for one.

Schedule:

```text
bzj_pgb_retry_transaction
```

Suggested retry sequence:

```text
1 minute
5 minutes
15 minutes
1 hour
6 hours
24 hours
```

After the retry limit:

```text
manual_review
```

A retry must invoke the same processor:

```php
bzj_pgb_process_transaction()
```

It must never have a second recovery implementation.


# 54. Final Architecture Principle

The upgraded bridge should not be thought of as:

```text
Streams → WooCommerce → Streams
```

It should be thought of as:

```text
                ┌───────────────┐
                │    STREAMS    │
                │ WoWonder      │
                └───────┬───────┘
                        │
                     Intent
                        │
                        ▼
              ┌──────────────────┐
              │   PGB CORE       │
              │ WordPress MU     │
              │                  │
              │ State            │
              │ Security         │
              │ Idempotency      │
              │ Recovery         │
              │ Orchestration    │
              └───────┬──────────┘
                      │
             ┌────────┼─────────┐
             │        │         │
             ▼        ▼         ▼
         WooCommerce Streams  Addons
         Payment      DB       │
         Authority   Authority │
                               │
                    ┌──────────┼──────────┐
                    ▼          ▼          ▼
                Affiliate    Jewel     Currency
                   WP
```

The fundamental upgrade is therefore **not merely moving `wow-pgb_sync.php` into an MU plugin**.

It is replacing the current request-dependent bridge with a **persistent transaction orchestration system**.

The payment itself becomes only one stage of a durable transaction.

That is what eliminates the current “dropped order” class of failures.

### Recommended implementation order

I would **not start by rewriting `wow-pgb_sync.php`**. The safest implementation sequence is:

1. **Create the PGB transaction table and core state/locking system.**
2. **Create the MU-plugin bootstrap, logger and HMAC API.**
3. **Build the Streams intent endpoint and make `wow-pgb_init.php` a thin client.**
4. **Move WooCommerce order creation into the MU plugin using native WooCommerce APIs.**
5. **Build the PRO/WALLET/FUND/MARKET handlers and make each idempotent.**
6. **Extract the existing AffiliateWP implementation almost intact.**
7. **Move the Jewel webhook logic into the PGB integration.**
8. **Make `payment_complete` the primary processor trigger.**
9. **Convert `wow-pgb_webhook.php` into recovery-only processing.**
10. **Implement Action Scheduler retries and the status endpoint.**
11. **Replace the current thank-you-page redirect logic with signed redirect/status handling.**
12. **Only then retire the old bridge code.**

One particularly important point is that the existing AffiliateWP code should **not** be treated as obsolete just because the architecture changes. Its five-source affiliate resolution, duplicate referral checks and accounting verification are some of the more mature pieces of the current implementation and are worth carrying forward. 

Likewise, the current Jewel implementation should be migrated rather than rewritten from scratch because it already contains useful mapping, subscription activation, role synchronisation and rebate-credit behaviour. 

**The next practical step should therefore be the actual Stage 1 implementation: the PGB MU-plugin foundation + database schema + logger + HMAC contract + transaction repository/state machine.** Once that foundation exists, the current `wow-pgb_init.php` and `wow-pgb_sync.php` can be migrated into it incrementally without creating another monolithic bridge.
