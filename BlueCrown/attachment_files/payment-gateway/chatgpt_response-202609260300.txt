# Executive assessment

The proposed direction is **correct**, but I would change one fundamental part of it:

> **The new Payment Gateway Bridge should not be primarily a “moved version” of `wow-pgb_init.php` + `wow-pgb_sync.php`. It should become a small payment-orchestration system with WooCommerce as the payment authority, a durable order state in Streams, and the WordPress MU plugin as the authoritative completion processor.**

The existing bridge contains several good pieces—especially the AffiliateWP resolution/verification work—but its lifecycle is fragmented. The biggest architectural weakness is that **payment completion, WoWonder fulfilment, AffiliateWP processing, and browser redirection are currently too closely coupled.**

WooCommerce itself exposes a `woocommerce_payment_complete` lifecycle hook when payment is completed, and its order system distinguishes payment completion from the eventual order status. ([WooCommerce][1]) That gives us a much better foundation than relying on the customer reaching the Thank-You page.

I recommend the following architecture.

# 2. The most important problem: the browser is currently part of the payment-processing architecture

The existing `wow-pgb_sync.php` contains a `wp_footer`/Thank-You-page mechanism that only runs when the customer reaches the WooCommerce order-received page. It checks the order and then calls `wowonder_order_redirect`. 

That is dangerous for a payment integration.

For example:

```text
Payment succeeds
      │
      ▼
WooCommerce order becomes paid
      │
      ▼
Customer closes browser
      │
      X
      │
      └── Thank-you code never runs
```

The payment was successful, but the bridge does not necessarily complete its downstream work.

Likewise:

```text
Payment succeeds
      │
      ▼
Webhook arrives
      │
      ▼
Webhook processing begins
      │
      ▼
some downstream operation fails
      │
      ▼
HTTP 500
```

WooCommerce will retry failed webhook deliveries, but webhooks are automatically disabled after repeated delivery failures by default, and WooCommerce documents five retries as the default threshold. ([The WooCommerce Developer Blog][2])

Therefore:

**Webhook = notification/input to our processing system.**

It should **not** be the entire processing system.

Instead of:

```text

    ↓
```

use:


Both routes eventually call:

That function is **idempotent**.

So if the same order arrives through:

* payment hook
* webhook
* manual retry
* scheduled recovery
* administrator retry

the result remains one successful fulfilment.


# 47. The new processing algorithm

Conceptually:

```php
process_order($woo_order_id)
{
    load order;

    if (!is_buzzjuice_pgb_order()) {
        return;
    }

    acquire transaction lock;

    if (already_completed()) {
        return SUCCESS;
    }

    verify_payment();

    if (!paid()) {
        update_state();
        return;
    }

    verify_amount();

    if (invalid_amount()) {
        mark_manual_review();
        return;
    }

    mark_processing();

    process_streams_fulfilment();

    if (retryable_failure) {
        release_for_retry();
        return;
    }

    process_affiliate();

    if (affiliate_failure) {
        queue_affiliate_retry();
    }

    mark_completed();

    create_redirect_instruction();

    release_lock();
}
```

Notice something important:

**AffiliateWP failure should not necessarily reverse a valid customer payment.**

The customer has already paid.

Affiliate processing can be retried independently.

# Bottom line

Your original proposal is directionally right, but I would upgrade it from:

> **“move the payment files into shared code and make the MU plugin handle completion”**

to:

> **“build a durable Buzzjuice Payment Gateway orchestration layer in which WooCommerce is the payment authority, WordPress PGB is the authoritative fulfilment processor, Streams is a client/adapter, webhooks are event sources rather than the sole processor, and every operation is idempotent and recoverable.”**

The most important changes are therefore:

1. **Remove browser/Thank-You dependency from payment processing.**
2. **Move WooCommerce credentials and order creation behind the WordPress PGB API.**
3. **Introduce a permanent PGB transaction ID.**
4. **Introduce idempotent WooCommerce order creation.**
5. **Use `woocommerce_payment_complete` as the primary payment event.**
6. **Keep the webhook as a secondary/recovery event source.**
7. **Create one central idempotent order processor.**
8. **Separate payment, fulfilment, AffiliateWP and redirect state.**
9. **Preserve the current working AffiliateWP engine rather than rewriting it.**
10. **Add retry/recovery so a transient API failure cannot turn a successful payment into a dropped order.**
11. **Stop trusting browser-supplied financial values.**
12. **Remove the SSL verification bypass.**
13. **Replace email-based identity resolution with explicit WP/Streams IDs, using email only as fallback.**
14. **Retire the duplicated PGB logic in `checkout.php`.**
15. **Keep legacy files temporarily as compatibility wrappers during migration.**

The existing code is actually a useful foundation: the AffiliateWP portion has already evolved toward retry-safe, duplicate-aware processing, and that same philosophy should now be applied to the **entire payment lifecycle**, not just affiliate commissions. 

### Recommended next implementation step

The safest next step is **not yet to modify `wow-pgb_init.php` or `wow-pgb_sync.php`**. First, I would build the **PGB v2 contract and file architecture**, including the exact request/response payloads, transaction states, metadata schema, WooCommerce hooks, idempotency rules, and migration map. Once that contract is fixed, we can implement the new MU plugin and `shared/payment-gateway/` files against it without accidentally carrying the current bridge's failure modes into the new system.
