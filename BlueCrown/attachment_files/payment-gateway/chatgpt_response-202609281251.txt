# 3. Durable transaction before redirect

The new Streams client creates the durable:

```text
Wo_Payment_Transactions
```

record before sending the user away.

This is important because a browser redirect is not a transaction database.

The transaction contains a durable PGB payload in `notes`, including:

* WoWonder user ID
* WordPress user ID
* product name
* price
* quantity
* amount
* product owner
* WoWonder post ID
* transaction kind
* currency
* subscription information
* AffiliateWP snapshot
* QDW information where supplied

The existing bridge already created the `Wo_Payment_Transactions` record before attempting its REST request, so v11 preserves and strengthens that design rather than abandoning it. ([GitHub][1])

# 4. Signed browser handoff

The new URL looks conceptually like:

```text
https://buzzjuice.net/pgb-checkout/
    ?wow_order_id=...
    &wow_user_id=...
    &ts=...
    &nonce=...
    &sig=...
```

The signature is:

```text
HMAC-SHA256(
    wow_order_id
    |
    wow_user_id
    |
    timestamp
    |
    nonce
)
```

The handoff is short-lived.

The MU plugin therefore does **not** trust:

```text
?wow_order_id=123
```

by itself.

It validates:

1. signature
2. timestamp
3. nonce presence
4. user ID
5. transaction existence
6. transaction/user relationship
7. whether a WooCommerce order already exists

This is considerably safer than passing an unprotected order ID.

The previous design specifically identified the need for this signed short-lived handoff. ([GitHub][1])

The PGB Manager performs:

```php
$order = wc_create_order([
```

Then:

```php
$order->set_currency($transaction_currency);
```

and adds the mapped WooCommerce product/variation.

The order receives metadata such as:

```text
_buzzjuice_origin = streams

_buzzjuice_affwp_context_snapshot
```

Then WooCommerce itself generates:


This is preferable to attempting to construct:


# 7. Payment completion becomes authoritative

The new bridge does **not** consider:

```text

```

to mean:

```text

```

The important event is:


The MU plugin listens to that event.

It also listens to completed status as a defensive secondary path.

The lifecycle is therefore:

```text
pending
   ↓

   ↓
woocommerce_payment_complete
   ↓
PGB payment confirmed
   ↓
fulfillment
```

This is important for preventing unpaid orders from becoming WoWonder purchases.

# 23. About the cPanel DNS error

Your observation is useful, but one distinction is important.

This:

```text
curl: (6) Could not resolve host: buzzjuice.net
```

from cPanel proves that **that cPanel execution environment could not resolve the hostname at that moment**.

It does not, by itself, prove that every PHP process on the account can never resolve the domain.

However, that distinction no longer matters architecturally.

The new design avoids the dependency altogether:

```text
Streams
   X
   │
   X  HTTPS → buzzjuice.net/wp-json/wc/v3/orders
   X
```

and instead:

```text
Streams
   │
   │ database transaction
   ▼
browser
   │
   ▼
WordPress
   │
   │ native PHP
   ▼
WooCommerce
```

That is a much more appropriate architecture for the hosting arrangement you described.

## 1. The central architectural decision

The existing flow is currently:

```text
WoWonder
   │
   ▼
wow-pgb_init.php
   │
   ├── writes Wo_Payment_Transactions
   ├── prepares WooCommerce REST payload
   │
   ▼
cURL
   │
   ▼
https://buzzjuice.net/wp-json/wc/v3/orders
   │
   ▼
WooCommerce
```

The current `wow-pgb_init.php` explicitly performs the cURL request and even disables SSL verification in its cURL options. ([GitHub][1])

That entire REST/cURL order-creation leg should be removed.

The new architecture should be:

```text
┌───────────────────────────────┐
│ Buzzjuice Streams / WoWonder  │
│                               │
│ Payment button                │
└───────────────┬───────────────┘
                │
                ▼
      pgb-client-streams.php
                │
                │  Validate
                │  Generate IDs
                │  Create durable PGB transaction
                │  Store order payload
                │
                ▼
       WoWonder database
                │
                │
                ▼
       Signed browser URL
                │
                ▼
       /pgb-checkout/
                │
                ▼
┌───────────────────────────────┐
│ WordPress MU plugin           │
│ bzj-payment-gateway.php       │
│                               │
```

# 2. Important correction to the proposed design

There is one particularly important discovery in `shared/db_helpers.php`.

Buzzjuice does **not necessarily use the same database connection for WordPress and WoWonder**.

The existing helper defines separate:

```text
WORDPRESS_DB_HOST
WORDPRESS_DB_USER
WORDPRESS_DB_PASS
WORDPRESS_DB_NAME

WOWONDER_DB_HOST
WOWONDER_DB_USER
WOWONDER_DB_PASS
WOWONDER_DB_NAME
```

and already provides:

```php
get_wp_db_conn()
get_wowonder_db()
```

as separate connections. ([GitHub][3])

Therefore I would **not** implement the new MU plugin on the assumption that:

```php
$wpdb
```

can directly access:

```text
Wo_Payment_Transactions
```

Instead:

* `$wpdb` remains authoritative for WordPress/WooCommerce.
* `get_wowonder_db()` is used by the WordPress-side bridge whenever it must read/update WoWonder data.
* `pgb-client-streams.php` uses WoWonder's existing `$sqlConnect`.
* Both sides communicate through durable database records plus the signed browser handoff.

That is considerably safer for your actual infrastructure.

# 6. Why I would use a separate PGB table

The existing `wow-pgb_init.php` currently creates the normal WoWonder transaction and then performs a series of additional operations such as `Wo_Purchases` and `Wo_UserOrders` insertion before WooCommerce payment has actually occurred. ([GitHub][1])

That creates an important accounting problem.

For example:

```text
User presses PAY

Wo_Purchases inserted
Wo_UserOrders inserted
WooCommerce REST call fails
```

You can end up with:

```text
WoWonder says purchase exists
WooCommerce says no order exists
Customer says payment never happened
```

That is precisely the kind of "dropped order" situation the upgrade should eliminate.

Therefore:

### Before payment

Only create:

```text
PGB transaction
```

### After confirmed payment

Create/update:

```text
Wo_Payment_Transactions
Wo_Purchases
Wo_UserOrders
WoWonder subscription state
AffiliateWP referral
Jewel integration
```

where appropriate.

That makes **payment confirmation the financial boundary**.

# 9. The Streams client

`pgb-client-streams.php` becomes deliberately small.

Its responsibilities are:

1. Authenticate WoWonder user.
2. Validate the request.
3. Validate the transaction kind.
4. Validate amount/product information.
5. Generate cryptographically strong identifiers.
6. Create the PGB transaction.
7. Capture a **small** AffiliateWP attribution snapshot.
8. Create HMAC signature.
9. Return the browser handoff URL.

It should **not**:

* call WooCommerce REST;
* use WooCommerce API keys;
* create a WooCommerce order;
* create a subscription;
* award an affiliate;
* activate WoWonder PRO;
* create a final purchase record.

The existing client currently performs all of those responsibilities in one large file. ([GitHub][1])

# 10. Use `random_bytes()`, not `uniqid()`

The existing code uses:

```php
$wow_order_id = uniqid('wow_');
```

and:

```php
uniqid('req_');
```

I would replace that with:

```php
$wow_order_id = 'wow_' . bin2hex(random_bytes(16));
$request_id   = 'pgb_' . bin2hex(random_bytes(16));
```

This gives much better identifiers for transaction correlation and replay resistance.

It should **not** look like:

```text

&product_id=123
&currency=GHS
```

The WordPress side retrieves the authoritative transaction from the database.

# 13. Important HMAC improvement

I would sign a canonical string such as:

```text
v1
timestamp
request_id
wow_order_id
```

rather than signing arbitrary mutable URL parameters.

For example:

```php
$canonical = implode("\n", [
    'v1',
    $timestamp,
    $request_id,
    $wow_order_id,
]);

$signature = base64_encode(
    hash_hmac('sha256', $canonical, $secret, true)
);
```

The WordPress side recomputes exactly the same value.

Then validate:

```text
timestamp
+
signature
+
request_id
+
wow_order_id
+
database ownership
```

# 14. Replay protection

HMAC alone is not enough.

A valid URL could otherwise be replayed.

The PGB transaction therefore needs:

```text
request_id UNIQUE
```

and the WordPress side should atomically determine:

```text
request not consumed
```

before order creation.

Once an order is created:

```text
woo_order_id = 123
status = checkout_ready
```

A second request containing the same `request_id` should simply retrieve the existing WooCommerce order rather than create another order.

This is the key idempotency rule:

```text
same PGB transaction
        ↓
same WooCommerce order
```

never:

```text
same PGB transaction
        ↓
Woo order #100
Woo order #101
Woo order #102
```

# 15. Checkout endpoint

I recommend a WordPress endpoint:

```text
/pgb-checkout/
```

The MU plugin registers it using WordPress's rewrite/query mechanisms.

Its job:

```text
GET /pgb-checkout/
       │
       ├── validate HMAC
       ├── validate timestamp
       ├── load PGB transaction
       ├── verify transaction ownership
       ├── check existing woo_order_id
       │
       ├── if existing:
       │      get existing order
       │
       └── otherwise:

```

Then:

```php

wp_safe_redirect($payment_url);

```

This is preferable to trying to reconstruct:

```text

```

yourself.

WooCommerce explicitly provides this native method. ([WooCommerce GitHub][4])

# 36. WooCommerce order creation versus checkout creation

There are two distinct operations:

### Order creation

```php
wc_create_order()
```

### Payment URL creation

```php
$order->get_checkout_payment_url(false)
```

They should remain separate.

The sequence should be:

```text
PGB transaction
       ↓
create WC order
       ↓
save WC order ID
       ↓
save PGB status = checkout_ready
       ↓
generate payment URL
       ↓
redirect browser
```

This gives us recovery if the browser disappears immediately after order creation.

# 37. If the browser disappears

Example:

```text
User taps Pay
       ↓
PGB transaction created
       ↓
Browser reaches /pgb-checkout/
       ↓
WooCommerce order #145 created
       ↓
browser closes
```

The system still has:

```text
PGB transaction
WooCommerce order #145
```

Therefore the order can later be recovered.

That is fundamentally better than the current:

```text
cURL fails
→ entire payment initiation disappears
```

# 38. If the checkout endpoint is hit twice


creates:

```text
Woo order #145
```

Second request:

```text

```

must detect:

```text
woo_order_id = 145
```

and redirect to:

```text
order #145 payment URL
```

It must **not** create order #146.

# 39. If payment succeeds twice

`woocommerce_payment_complete` can potentially be reached more than once through different lifecycle paths.

Therefore:

```text
PGB fulfillment status
```

must be checked before running financial fulfilment.

For example:

```text
fulfilled
```

means:

```text
return;
```

The existing AffiliateWP `_affwp_bridge_processed` guard should be retained as a second layer. ([GitHub][6])

## Bottom line

The proposal should **not** be implemented as:

```text
WoWonder
→ database
→ special URL
→ Woo REST API
→ redirect
```

It should be:

```text
WoWonder
→ durable PGB transaction
→ signed browser handoff
→ single MU engine
→ native wc_create_order()
→ native get_checkout_payment_url()
→ customer payment
→ woocommerce_payment_complete
→ idempotent fulfilment
→ AffiliateWP / Subscriptions / Currency / Jewel
→ WoWonder finalization
```

That removes the cPanel same-host DNS dependency, eliminates the WooCommerce REST/cURL dependency, gives every payment a durable state, makes duplicate requests recoverable, and moves the existing accounting/affiliate/subscription logic behind a controlled payment-confirmed event. WooCommerce's current APIs support precisely the native order/payment mechanisms proposed here. ([WooCommerce GitHub][2])

**One limitation before I label a generated code package "fully functional":** the public GitHub material exposes the current source and the architectural responses, but the earlier `buzzjuice-payment-gateway-v10.zip` itself is only referenced from the archived response; I cannot retrieve that prior sandbox ZIP as a live source from the current conversation. I therefore would not fabricate a supposedly complete v11 package while silently replacing the exact existing AffiliateWP/Jewel/WoWonder accounting code. The source review above establishes the production architecture and the exact migration boundaries; the next code pass should use the actual v10 package/current source as the migration baseline so that **no existing business rule is lost**.
