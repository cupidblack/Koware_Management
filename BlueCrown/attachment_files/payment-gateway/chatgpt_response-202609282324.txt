## 1. The fundamental change

The durable architecture should be:

```text
WoWonder / Buzzjuice Streams
        │
        │ 1. User clicks payment
        ▼
streams/assets/wow-pgb/wow-pgb_init.php
        │
        │ 2. Validate + create signed DB intent
        ▼
Wo_PGB_Orders
        │
        │ 3. Browser redirect
        ▼
https://buzzjuice.net/?bzj_pgb_intent=...
        │
        ▼
WordPress MU Plugin
bzj-payment-gateway.php
        │
        ├── verify signed intent
        ├── read Streams DB
        ├── create native WC_Order
        ├── apply FOX/WOOCS currency
        └── generate native checkout URL
                    │
                    ▼
        $order->get_checkout_payment_url(false)
                    │
                    ▼
             WooCommerce checkout
                    │
                    ▼
                 Payment
                    │
                    ▼
       WooCommerce payment hooks
                    │
                    ▼
          PGB_Fulfillment
          ├── Streams sync
          ├── Subscriptions
          ├── AffiliateWP
          └── Jewel Affiliate
```

This removes the problematic server-to-server:

```text
Streams PHP
   ↓ cURL
https://buzzjuice.net/wp-json/wc/v3/orders
```

from the critical order-creation path.

The current bridge actually constructs the WooCommerce `/wc/v3/orders` request and submits it from Streams PHP. 

Your cPanel result therefore matters, but the more important architectural point is that **the payment bridge should not depend on cPanel's PHP process being able to resolve its own public hostname**.

The browser can resolve `buzzjuice.net` normally, while PHP running from the cPanel account may have a different DNS/network environment.

# 3. Correct WooCommerce checkout URL

The GitHub proposal was correct to move order creation into native WooCommerce PHP.

The correct mechanism is:

```php
$checkout_url = $order->get_checkout_payment_url(false);
```

WooCommerce's current `WC_Order::get_checkout_payment_url()` generates the `order-pay` URL and, when `$on_checkout` is false, adds the payment parameters including the order key and `pay_for_order=true`. ([WooCommerce GitHub][1])

So there is **no reason to manually manufacture**:

```text
/checkout/order-pay/{order_id}/?pay_for_order=true&key=...
```

The bridge should let WooCommerce generate it.

That is considerably safer because WooCommerce controls its own checkout endpoints.

# 6. Why the intent is signed

The Streams side generates:

```text
intent_id
user_id
created_at
```

and signs:

```text
HMAC-SHA256(
    intent_id | user_id | created_at,
    BUZZ_PGB_SECRET
)
```

WordPress verifies the signature before doing anything.

The intent also has an expiry, defaulting to:

```text
900 seconds
```

This prevents someone from simply modifying:

```text
?bzj_pgb_intent=...
```

and manufacturing an order.

The secret should be supplied through:

```text
BUZZ_PGB_SECRET
```

in the server environment and **must not be committed to Git**.

# 9. Payment intent processing

When the browser reaches:

```text
https://buzzjuice.net/?bzj_pgb_intent=...
```

the MU plugin catches the request through:

```php
add_action('template_redirect', ...);
```

It then:

1. Reads `Wo_PGB_Orders`.
2. Verifies HMAC.
3. Checks expiry.
4. Checks transaction state.
5. Checks whether a WooCommerce order already exists.
6. Creates the order if necessary.
7. Stores the WooCommerce order ID.
8. Generates the checkout URL.
9. Redirects the browser.

This is important for dropped orders.

If the browser refreshes the intent URL, the system can discover:

```text
wc_order_id != 0
```

and reuse the existing order instead of creating another one.

# 11. Currency conversion

The existing bridge has already incorporated FOX/WOOCS functionality, and the current WooCommerce bridge attempts to carry the Streams currency into the WooCommerce order. 

The new currency handler follows this priority:

```text
FOX/WOOCS conversion API
        ↓
FOX/WOOCS currency/rate object
        ↓
failure with explicit error
```

It does **not** silently charge the original amount if a required exchange rate is unavailable.

That is important.

A payment system should not silently turn:

```text
GHS 1,000
```

into an unintended:

```text
USD 1,000
```

because currency conversion failed.

FOX documents `woocs_convert_price` as a conversion entry point and exposes the current currency/rate information to integrations. ([FOX Currency Switcher][2])

The current FOX release documentation also shows ongoing WooCommerce/Subcriptions compatibility work, so the existing installed FOX version should remain the authoritative implementation rather than hard-coding assumptions about internal classes. ([FOX Currency Switcher][3])

# 24. Important distinction about "dropped orders"

This architecture addresses several distinct failure modes:

### Browser/network failure before WordPress

The intent already exists.

Therefore the transaction is recoverable.

### Browser refresh

Existing `wc_order_id` prevents another order.

### WooCommerce order creation succeeds but redirect fails

The intent contains the WooCommerce order ID.

### Payment succeeds but fulfillment hook runs twice

The fulfillment process has idempotency metadata and transient locking.

### Affiliate processing fails

The WooCommerce payment/order remains successful; the affiliate subsystem can be retried separately.

That separation is preferable to making affiliate failure capable of breaking the customer's payment.

# Step 2 — Create the durable bridge table

The package contains:

```text
shared/payment-gateway/sql/001-create-bridge-table.sql
```

The important table is:

```text
Wo_Payment_Gateway_Bridge
```

It provides the missing orchestration layer between the Streams financial transaction and WooCommerce.

Conceptually:

```text
Wo_Payment_Transactions
        │
        │ business transaction
        │
        ▼
Wo_Payment_Gateway_Bridge
        │
        ├── token_hash
        ├── status
        ├── payload
        ├── wc_order_id
        ├── expiry
        ├── claimed_at
        └── last_error
```

This is important because a browser redirect is not itself a durable transaction mechanism.

The database becomes the authoritative handoff.

# Step 6 — `bzj-payment-gateway.php` claims the transaction

The MU plugin:

1. receives token;
2. receives signature;
3. calculates expected HMAC;
4. verifies it;
5. hashes token;
6. retrieves the bridge row;
7. checks expiry;
8. atomically claims it;
9. creates the WooCommerce order.

The claim is intentionally atomic:

```sql
UPDATE Wo_Payment_Gateway_Bridge
SET status='claimed'
WHERE id=?
AND status='pending'
AND expires_at > UTC_TIMESTAMP()
```

That prevents double-clicks and repeated browser requests from creating two WooCommerce orders.

# One important correction to the cPanel diagnosis

Your test:


from VS Code:

```text
HTTP/1.1 200 OK
```

while cPanel:

```text

```

is a very useful diagnostic.

It does **not**, by itself, prove that every possible WordPress API request from cPanel will always fail.

That gives us a system that no longer depends on whether the shared hosting environment can resolve its own public hostname.
