### Important correction to the GitHub proposal

I would **not** implement the proposed currency addon by changing a paid order's price based on whatever currency WooCommerce Currency Switcher happens to report at payment-complete time.

The amount and currency need to be authoritative at order creation. The new bridge therefore records the transaction currency and creates the WooCommerce order using that currency. This avoids a later currency-switcher state changing an already-created payment amount.

Likewise, WooCommerce Subscriptions should not continue using the old REST/cURL subscription creation mechanism. The Subscriptions API is intended to be extended through its hooks/classes/functions, and WooCommerce specifically notes that subscription status changes are normally driven by the WooCommerce order/payment lifecycle. ([WooCommerce][3])

# Step-by-step implementation

## 1. Do not delete the existing bridge immediately

First put the existing files into a deployment archive.

Do **not** simultaneously run:

```text
old wow-pgb_sync.php
+
new PGB MU plugin
```

because both systems can react to the same successful order and create duplicate subscriptions, referrals or fulfilment.

The package therefore turns the old sync file into a **deprecation shim**, rather than allowing its old payment hooks and redirects to remain active.

The existing sync file currently contains substantial redirect/payment logic, including product-specific redirects and AffiliateWP execution. 

---

## 2. Install the single MU plugin

Install:

```text
wp-content/mu-plugins/pgb-mu-plugin.php
```

It loads:

```text
shared/payment-gateway/config/
shared/payment-gateway/core/
shared/payment-gateway/addons/
shared/payment-gateway/integrations/
```

The MU plugin becomes the WordPress-side engine.

It is responsible for:

* loading the bridge;
* installing the transaction tables;
* validating the checkout handoff;
* creating WooCommerce orders;
* handling payment lifecycle events.

---

## 3. Create the transaction ledger

The package creates:

```text
wp_pgb_transactions
```

and:

```text
wp_pgb_fulfillment
```

The first table gives every payment an independent lifecycle:

```text
initiated
    ↓
checkout_ready
    ↓
paid
    ↓
fulfilled
```

with error/retry information alongside it.

This is important because a browser redirect is **not a reliable transaction ledger**.

If the user closes the browser after the Streams transaction is created but before WooCommerce loads, the transaction still exists.

If WooCommerce order creation fails, it remains identifiable.

If the payment succeeds but an addon fails, the payment itself remains recorded as successful and the failed addon can be retried independently.

That directly addresses the dropped-order problem identified in the supplied GitHub analysis. ([GitHub][4])

# 4. Replace `wow-pgb_init.php`

The old file currently does much more than initialize a payment. It validates input, writes `Wo_Payment_Transactions`, constructs the WooCommerce order payload, captures AffiliateWP context and then makes the problematic cURL request to WooCommerce. ([GitHub][2])

The new version only does the Streams-side work.

It:

1. verifies the logged-in WoWonder user;
2. validates payment parameters;
3. generates a unique `wow_order_id`;
4. generates a unique PGB request ID;
5. writes the transaction to the database;
6. stores the order payload;
7. captures the AffiliateWP snapshot;
8. signs the handoff;
9. returns the checkout URL.

There is **no `wp-load.php`** and no WordPress function dependency.

# 5. The browser handoff replaces same-host cURL

The generated URL is conceptually:

```text
https://buzzjuice.net/pgb-checkout/
    ?wow_order_id=...
    &request_id=...
    &ts=...
    &sig=...
```

The important difference is that the browser resolves:

```text
buzzjuice.net
```

rather than the cPanel PHP process trying to resolve its own public hostname.

Your observation:

```text
VS Code:
HTTP/1.1 200 OK

cPanel:
curl: (6) Could not resolve host
```

therefore becomes irrelevant to the new order-creation path.

There is no:

```text
Streams PHP
   ↓
curl
   ↓
https://buzzjuice.net/wp-json/
```

operation anymore.

# 6. Secure the handoff with HMAC

The URL isn't trusted merely because it contains a `wow_order_id`.

The Streams side creates:

```text
timestamp
request_id
wow_order_id
```

and signs the request with:

```text
HMAC-SHA256
```

using:

```text
BZJ_PGB_SECRET
```

The WordPress side verifies:

* signature;
* timestamp;
* request ID;
* transaction existence;
* request ID belonging to that transaction.

The secret must **not** be placed in:

* WoWonder settings;
* JavaScript;
* HTML;
* GitHub;
* WordPress options.

The GitHub recommendation to keep the secret in the server environment is appropriate. 

Generate one with:

```bash
openssl rand -base64 32
```

Then make the same secret available to both PHP execution environments.

# 7. Native WooCommerce order creation

This is the major architectural improvement.

The MU plugin retrieves the Streams transaction and calls:

```php
wc_create_order()
```

rather than:

```text
POST /wp-json/wc/v3/orders
```

WooCommerce's current developer reference explicitly provides `wc_create_order()` for programmatic order creation. ([WooCommerce GitHub][1])

The bridge then gets the payment URL from:

```php
$order->get_checkout_payment_url(false);
```

WooCommerce's current implementation constructs the `order-pay` checkout endpoint and adds the order key. ([WooCommerce GitHub][5])

So there is no reason to manufacture something such as:

```text
/checkout/checkout/order-pay/146/
```

or attempt to guess the URL.

WooCommerce itself generates it.

---

# 8. Do not use `payment_url` from the REST API anymore

The existing Streams implementation currently expects the WooCommerce API response to contain a payment URL. ([GitHub][2])

That entire dependency disappears.

The WordPress side directly obtains:

```php
$payment_url = $order->get_checkout_payment_url(false);
```

and redirects the browser.

This is both simpler and more resilient to WooCommerce REST/API changes.

# 9. Payment becomes the authoritative event

The critical distinction is:

```text
ORDER CREATED
```

does **not** mean:

```text
PAYMENT SUCCESSFUL
```

The new bridge therefore doesn't activate the user's WoWonder benefits merely because the order exists.

The authoritative event becomes:

```php
woocommerce_payment_complete
```

WooCommerce's payment API similarly instructs payment gateways to use `payment_complete()` when payment is actually complete rather than simply manipulating the order status. ([The WooCommerce Developer Blog][6])

The PGB lifecycle becomes:

```text
Woo order created
        ↓
pending payment
        ↓
customer pays
        ↓
woocommerce_payment_complete
        ↓
PGB payment confirmed
        ↓
addons/integrations
```
