## Executive summary

I reviewed the current Buzzjuice Streams payment bridge, the proposed architecture, the previous ChatGPT implementation, and the GitHub review. The proposed direction is **correct**, but the earlier v5 implementation should **not be installed unchanged**.

There are several important corrections I would make before production:

1. **WooCommerce must be the payment-state authority.**
2. **Streams should create only a payment intent/ledger reference—not completed purchase records.**
3. **A durable WordPress transaction ledger is required** to prevent dropped orders and duplicate fulfillment.
4. **The MU plugin must wait until `plugins_loaded`** before bootstrapping WooCommerce-dependent code. This was the direct reason the earlier v5 package produced no table, admin page, or logs. 
5. **AffiliateWP context should not be captured from Streams cookies.** Your observation is correct: AffiliateWP is WordPress-side, so affiliate resolution should occur after the WooCommerce order reaches WordPress. The existing `wow-pgb_sync.php` already has a substantially better deterministic AffiliateWP resolution mechanism that should be preserved/refactored. 
6. **The old hard-coded WooCommerce webhook secret must disappear.** The current `streams/wow-pgb_webhook.php` contains a hard-coded secret and is therefore unsuitable as the long-term architecture. 
7. **The old browser/thank-you-page fulfillment logic must disappear.** Payment completion must originate from WooCommerce hooks, not from a user's browser returning to the site.
8. **WooCommerce Subscriptions should be handled through its native APIs/hooks**, rather than treating a generic WooCommerce order as if it automatically creates a subscription. WooCommerce documents `wcs_create_subscription()` and subscription lifecycle hooks for this purpose. ([GitHub][1])
9. The previous v5 package also contained a **path problem**: for this Buzzjuice layout, `ABSPATH . 'shared/payment-gateway/'` is the correct root, not `dirname(ABSPATH)` in the MU plugin.
10. The existing Streams payment settings currently expose WooCommerce API credentials and webhook credentials. Those should be phased out from Streams. 

I have therefore prepared a **v5.1 refactored implementation package** based on those corrections.

**[Download the Buzzjuice Payment Gateway Bridge v5.1](sandbox:/mnt/data/buzzjuice-payment-gateway-v5.1.zip)**

All PHP files in the package have also been PHP syntax-checked successfully.

# 1. What is actually wrong with the current architecture?

The existing flow is effectively:

```text
Streams
   │
   ├── create Wo_Payment_Transactions
   ├── sometimes create Wo_Purchases
   ├── sometimes create Wo_UserOrders
   ├── sometimes create notifications
   │
   ▼
WooCommerce
   │
   ▼
payment
   │
   ▼
webhook
   │
   ▼
wow-pgb_sync.php
   │
   ├── subscriptions
   ├── AffiliateWP
   ├── redirects
   └── other fulfillment
```

The problem is that **payment initiation and fulfillment are mixed together**.

For example, the existing `wow-pgb_init.php` creates the `Wo_Payment_Transactions` record before payment has been confirmed. 

Worse, marketplace initiation can create `Wo_Purchases`, `Wo_UserOrders`, and notifications before the customer has actually paid. 

That means:

```text
customer clicks Pay
       ↓
Streams writes "purchase"
       ↓
customer abandons payment
       ↓
Streams can already look as though purchase occurred
```

That is exactly the kind of architecture that produces difficult-to-reconcile "dropped orders".

# 2. The new architecture

The new system should instead be:

```text
                 BUZZJUICE STREAMS
                       │
                       │ payment intent
                       ▼
              pgb-client-streams.php
                       │
                       │ HMAC
                       ▼
              WordPress REST endpoint
              /wp-json/bzj-pgb/v1/order
                       │
                       ▼
              PGB transaction ledger
              wp_bzj_pgb_transactions
                       │
                       ▼
               WooCommerce order
                       │
                       ▼
                 Customer pays
                       │
                       ▼
          WooCommerce payment lifecycle
                       │
             ┌─────────┴──────────┐
             ▼                    ▼
        payment_complete      order status
             │
             ▼
        PGB fulfillment
             │
       ┌─────┼───────────┐
       ▼     ▼           ▼
 Affiliate  Subscription  Streams
   WP        processing   fulfillment
       │
       ▼
    Jewel/etc.
```

This is the important distinction:

> **The PGB transaction is the bridge's durable state. The WooCommerce order is the payment authority. Streams becomes the fulfillment target.**

The previous design recommendation of a transaction ledger was therefore correct.

# 3. The transaction ledger

The new table is:

```text
wp_bzj_pgb_transactions
```

with the relationship:

```text
1 Buzzjuice payment
        =
1 PGB transaction
        =
1 WooCommerce order
```

The state machine becomes:

```text
initiated
    │
    ▼
order_created
    │
    ▼
paid
    │
    ▼
fulfilling
    │
    ├──── failure
    │        │
    │        ▼
    │   fulfillment_failed
    │
    ▼
fulfilled
```

This is substantially more durable than relying on:

```text
Woo webhook → PHP file → hope everything completed
```

The previous response correctly identified this as one of the most important architectural changes.

# 4. Important correction to the GitHub recommendation

The GitHub response suggested:

> capture AffiliateWP context before leaving Streams.

I would **not carry that recommendation into v5.1**.

Your note is correct.

AffiliateWP lives in WordPress. Therefore trying to preserve its browser context from WoWonder is unnecessarily fragile.

The existing `wow-pgb_sync.php` already has a useful server-side resolution strategy involving:

* AffiliateWP lifetime customers
* AffiliateWP customer relationships
* AffiliateWP customer metadata
* affiliate IDs
* deterministic duplicate referral checks

That logic is much more valuable than attempting to transfer browser cookies. 

The new architecture therefore becomes:

```text
Streams
   │
   │ wp_user_id + wow_user_id
   ▼
WooCommerce
   │
   ▼
AffiliateWP
   │
   ├── resolve customer
   ├── resolve affiliate
   ├── calculate commission
   ├── check existing referral
   └── create referral
```

That also means AffiliateWP can continue working even if the customer's browser changes, cookies expire, or the payment takes several hours.

# 5. AffiliateWP integration

The existing AffiliateWP code should **not simply be deleted**.

The good parts should be moved into:

```text
shared/payment-gateway/addons/
    pgb-addon-affiliate-wp.php
```

The new addon executes after payment confirmation:

```php
add_action(
    'pgb_payment_confirmed',
    'pgb_affwp_process',
    30,
    2
);
```

The addon then:

1. Loads the WooCommerce order.
2. Resolves the WordPress customer.
3. Resolves AffiliateWP customer.
4. Resolves affiliate.
5. Checks for an existing referral.
6. Calculates commission.
7. Creates the referral.
8. Stores the referral ID against the WooCommerce order.
9. Does **not** create a duplicate referral on retry.

That last point is critical.

Your existing code already contains a good duplicate check based on:

```text
reference = WooCommerce order ID
context   = woocommerce
affiliate_id
```

which should remain part of the refactored system.

# 6. WooCommerce Subscriptions

The existing implementation is doing something more complicated than necessary.

It currently builds subscription data and then calls the WooCommerce REST API from WordPress itself. 

There is no reason for WordPress to make an HTTP request back into its own WooCommerce REST API.

The new system can use the native Subscriptions API:

```php
wcs_create_subscription()
```

WooCommerce's current developer source documents this as the native subscription creation function. ([GitHub][1])

The v5.1 addon therefore works internally:

```text
Woo order paid
      ↓
identify subscription product
      ↓
wcs_create_subscription()
      ↓
add product
      ↓
copy address
      ↓
calculate totals
      ↓
set dates
      ↓
activate
```

This also aligns with the documented Subscriptions lifecycle. WooCommerce specifically documents:

```text
woocommerce_subscription_status_active
woocommerce_subscription_payment_complete
woocommerce_subscription_renewal_payment_complete
```

and related lifecycle hooks. ([WooCommerce][2])

    ↓

# 39. One thing I would deliberately do differently from the earlier v5 package

I would **not call v5.1 "production complete" immediately after uploading it**.

The architecture is now right, but the correct implementation strategy is:

```text
Install
   ↓
initialize
   ↓
ledger test
   ↓
REST test
   ↓
order creation test
   ↓
abandoned checkout test
   ↓
successful payment
   ↓
duplicate callback
   ↓
AffiliateWP
   ↓
Subscription
   ↓
Jewel
   ↓
Streams marketplace
   ↓
Wallet
   ↓
Fund
   ↓
production cutover
```

That staged approach is especially important because the existing bridge handles several different transaction classes, and the current code has accumulated business logic across multiple files.

The objective is not simply to produce a cleaner codebase. It is to make this invariant true:

> **Once WooCommerce says an order is paid, Buzzjuice can always determine what happened, what still needs to happen, retry it safely, and prove whether fulfillment completed.**

That is the architectural change that should eliminate the "dropped order" class of problems rather than merely moving the existing code into different folders.
