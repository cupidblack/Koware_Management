# Buzzjuice Payment Gateway Bridge — Updated Architecture & Implementation Proposal

I reviewed the current repository implementation, the supplied proposal, the previous ChatGPT design, and the GitHub review. The GitHub review is directionally strong, but I would make several architectural corrections before implementation.

The key conclusion is:

> **The upgrade should not simply move `wow-pgb_init.php` and `wow-pgb_sync.php` into new folders. The payment bridge should become a persistent, idempotent transaction coordinator owned by WordPress, with Streams acting as a thin payment client.**

That directly addresses the dropped-order problem rather than merely reorganizing the existing code.

---

# 1. What is actually wrong with the current bridge

The repository exposes several structural problems.

### 1.1 There are effectively multiple payment paths

The current system has payment logic in:

* `streams/assets/wow-pgb/wow-pgb_init.php`
* `streams/sources/checkout.php`
* `streams/wow-pgb_webhook.php`
* `wp-content/plugins/blue-crown-wp/wow-pgb_sync/wow-pgb_sync.php`
* payment-related JavaScript/modal code.

For example, `requests.php` directly includes `wow-pgb_init.php` when `payment_type=wow_payment`. 

Meanwhile, `checkout.php` contains another WooCommerce payment initialization path and even generates its own `wow_order_id`. 

That is exactly the type of fragmentation that makes a payment system difficult to recover when one HTTP request disappears.

---

## 1.2 The browser currently supplies financial information

The current initializer accepts:

* `amount`
* `product_price`
* `product_units`
* `product_owner_id`
* `transaction_kind`
* product information

directly from the request. 

Those values can be useful as **intent**, but they cannot be authoritative payment values.

The new architecture should therefore distinguish:

```text
Browser/Streams request
        ↓
"User wants product X"
        ↓
WordPress verifies product X
        ↓
WordPress determines price/currency
        ↓
WooCommerce order
```

not:

```text
Browser says amount = 27
        ↓
WooCommerce receives 27
```

# 2. The current WooCommerce REST architecture should be removed

The current Streams client obtains:

```text
wow_api_url
wow_api_key
wow_api_secret
```

and sends authenticated REST requests directly to WooCommerce. 

That is unnecessary because WooCommerce is installed inside the authoritative WordPress environment.

The new architecture should be:

```text
Buzzjuice Streams
       │
       │ signed PGB request
       ▼
WordPress PGB MU Plugin
       │
       │ native PHP
       ▼
WooCommerce
```

rather than:

```text
Streams
   │
   │ WooCommerce REST credentials
   ▼
WooCommerce
```

This eliminates a significant source of:

* credential failures
* REST authentication problems
* HTTP timeouts
* SSL problems
* duplicate order creation
* synchronization problems.

WooCommerce itself provides native order/payment APIs, including `payment_complete()`, which is preferable to independently manipulating payment state. ([The WooCommerce Developer Blog][1])

# 4. Do NOT use `wp_options` as the transaction database

The GitHub response suggested temporarily storing transactions as:

```php
update_option("pgb_txn_{$txn_id}", $txn_data, false);
```

I would **not implement that**.

It is acceptable for a prototype, but not for the durable bridge you are trying to build.

A dedicated table is much better:

```text
wp_bzj_pgb_transactions
```

with indexes on:

```text
transaction_id
idempotency_key
request_id
wow_order_id
woo_order_id
wp_user_id
streams_user_id
payment_status
fulfilment_status
created_at
updated_at
```

WordPress's `dbDelta()` is specifically intended for creating/updating plugin tables and allows the schema to evolve through versions. ([WordPress Developer Resources][2])

# 9. Idempotency solves the dropped-order problem

This is the central mechanism.

Suppose:

```text
Streams request

idempotency_key = abc123
```

WordPress creates:

```text
PGB transaction = pgb_1001
Woo order       = 5001
```

but the response gets lost.

Streams retries:

```text
idempotency_key = abc123
```

The PGB finds:

```text
abc123
   ↓
pgb_1001
   ↓
Woo order 5001
```

and returns the existing payment URL.

It **does not create Woo order 5002**.

This is much more important than merely adding retry loops.

# 10. Request authentication

The Streams client should use HMAC.

Headers:

```text
X-BZJ-PGB-Key
X-BZJ-PGB-Timestamp
X-BZJ-PGB-Nonce
X-BZJ-PGB-Signature
X-BZJ-PGB-Request-ID
```

Signature payload:

```text
timestamp
nonce
request_id
raw_body
```

joined deterministically.

WordPress verifies:

```text
HTTPS
timestamp tolerance
nonce
request ID
signature
request body
origin
authenticated user
transaction intent
```

The nonce/request ID should be persisted so a captured request cannot simply be replayed.

# 16. WooCommerce order creation

The PGB should use native WooCommerce PHP APIs.

Conceptually:

```php
$order = wc_create_order();

$order->set_customer_id($wp_user_id);

$item_id = $order->add_product(
    $product,
    $quantity,
    array(
        'subtotal' => $subtotal,
        'total'    => $total,
    )
);

$order->update_meta_data(
    'bzj_pgb_transaction_id',
    $transaction_id
);

$order->update_meta_data(
    'wow_order_id',
    $wow_order_id
);

$order->update_meta_data(
    'wow_user_id',
    $streams_user_id
);

$order->update_meta_data(
    '_buzzjuice_origin',
    'streams'
);

$order->calculate_totals();
$order->save();
```

Then:

```php
$order->get_checkout_payment_url(true);
```

becomes the payment destination.

WooCommerce's own APIs are designed around order/payment state, and its documentation specifically recommends `payment_complete()` for completing paid orders. ([The WooCommerce Developer Blog][1])

# 32. AffiliateWP failure must not reverse payment

This is critical.

The transaction needs independent component states:

```text
payment_status
streams_status
affiliate_status
jewel_status
```

For example:

```text
payment_status   = paid
streams_status   = completed
affiliate_status = pending
jewel_status     = completed
```

If AffiliateWP fails:

```text
payment remains paid
Streams remains completed
```

Only AffiliateWP is retried.

Therefore a retry cannot:

```text
credit wallet twice
activate PRO twice
create market purchase twice
```

This is one of the strongest recommendations in the previous architecture review.

# 52. Bottom line

The updated proposal should **not** be treated as a file-reorganization exercise.

The durable architecture is:

> **Streams creates an authenticated payment intent → WordPress creates and owns the PGB transaction → WordPress creates the WooCommerce order natively → WooCommerce payment signals enter one idempotent PGB processor → the processor independently fulfils Streams, AffiliateWP, Jewel and other addons → Action Scheduler repairs anything that fails → reconciliation catches anything that falls through.**

That architecture directly addresses the current dropped-order problem while preserving the parts of the existing implementation that are already working, particularly the AffiliateWP accounting logic and Jewel processing.

The current repository also gives us a clean migration boundary: `requests.php` already has a single `wow_payment` entry point, so that can become the thin Streams adapter rather than requiring broad changes throughout WoWonder. 

The next implementation step should therefore be **the actual production code package built against this architecture**, rather than another conceptual rewrite: one MU bootstrap plus the complete `shared/payment-gateway` tree, followed by the precise patches to `requests.php`, `wow-pgb_init.php`, the payment settings page, and the relevant Streams JavaScript/templates.
