## Executive conclusion

The proposed direction is correct, and the two GitHub reviews identify the major weaknesses of the current bridge. After reconciling them with the actual repository implementation, I would **not implement either proposal literally**.

The durable version should be **Buzzjuice Payment Gateway Bridge v2**, built around one principle:

> **The WordPress PGB transaction becomes the durable orchestration record; WooCommerce becomes the payment authority; Streams remains the WoWonder business/fulfilment system; every completion path feeds one idempotent processor.**

That directly addresses the current dropped-order problem.

The current implementation has several concrete architectural weaknesses:

* `wow-pgb_init.php` generates a new `uniqid('wow_')` and accepts financial values such as `amount` and `product_price` from the Streams request. ([GitHub][1])
* The current webhook is a large standalone Streams-side processor and contains a hard-coded WooCommerce webhook secret. ([GitHub][2])
* The WordPress bridge contains thank-you-page/`wp_footer` redirect logic, meaning browser activity is involved in the completion path. ([GitHub][3])
* SSL verification can currently be disabled in the WordPress-side cURL helper. ([GitHub][3])
* The existing `wow-pgb_sync.php` has grown to roughly 1,754 lines, while `wow-pgb_init.php` is roughly 2,956 lines. ([GitHub][3])
* The existing AffiliateWP implementation is comparatively mature and should be extracted rather than rewritten from scratch. Its five-source affiliate-resolution logic and commission calculation should be preserved. ([GitHub][3])

The previous ChatGPT/GitHub proposals correctly identified most of this. In particular, the recommendation for a dedicated `wp_bzj_pgb_transactions` table, explicit state, idempotency, one processor, modular handlers, and retryable addons is the right foundation. ([GitHub][4])

However, I would make **one important architectural correction** to those proposals:

> **Do not make the shared PGB client responsible for WP/Streams database access.**
>
> The shared client should be a transport/client layer. WordPress MU code should own WordPress/WooCommerce/Streams database operations.

That keeps the architecture clean and prevents the new shared layer from becoming another monolith.

# 2. The most important change: introduce a PGB transaction first

The current sequence is essentially:

```text
Streams request
     ↓
generate wow_order_id
     ↓
insert Streams records
     ↓
create WooCommerce order
     ↓
hope completion/webhook arrives
```

That creates the exact class of dropped-order scenarios you are experiencing.

For example:

```text
Streams
  │
  │ create Woo order
  ▼
WooCommerce
  │
  │ order successfully created
  ▼
network timeout
  X
Streams never receives response
```

The user retries.

```text
retry
 ↓
new wow_order_id
 ↓
new Woo order
```

You now potentially have:

```text
1 customer
2 Buzzjuice transactions
2 WooCommerce orders
```

The previous proposal correctly identified this duplicate-order risk. ([GitHub][4])

### New sequence

Instead:

```text
Streams
   │
   │ create payment intent
   ▼
WordPress PGB
   │
   ├── create PGB transaction
   │
   ├── assign pgb_transaction_id
   │
   ├── assign idempotency_key
   │
   ├── validate user
   │
   ├── validate product
   │
   ├── calculate/verify amount
   │
   └── save immutable transaction snapshot
   │
   ▼
Create WooCommerce order
   │
   ▼
return Woo checkout URL
```

If the response is lost:

```text
Streams retries
      │
      ▼
same idempotency key
      │
      ▼
PGB finds existing transaction
      │
      ├── Woo order exists → return it
      │
      └── Woo order absent → create it
```

Therefore:

```text
ONE PGB transaction
        ↓
MAXIMUM ONE WooCommerce order
```

This is the single biggest durability improvement.

# 13. Webhook becomes recovery, not authority

This is perhaps the most important conceptual correction.

The current system has:

```text
WooCommerce
     ↓
wow-pgb_webhook.php
     ↓
Streams
```

The new system should be:

```text
WooCommerce native payment lifecycle
                │
                ▼
         PGB Processor
                ▲
                │
          webhook/recovery
```

WooCommerce webhooks are background-delivered and have HMAC signatures; WooCommerce also disables a webhook after repeated delivery failures. ([The WooCommerce Developer Blog][7])

Therefore a webhook cannot be the **only** completion mechanism.

### New rule

All of these invoke:

```php

```

```text
woocommerce_payment_complete
woocommerce_order_status_processing
woocommerce_order_status_completed
WooCommerce webhook
scheduled recovery
manual administrator retry
customer status request
```

Exactly one processor.

That is the correct architecture. ([GitHub][4])

# 30. Authentication between Streams and WordPress

I recommend an HMAC request scheme.

Every request:

```text
X-BZJ-PGB-Key
X-BZJ-PGB-Timestamp
X-BZJ-PGB-Nonce
X-BZJ-PGB-Signature
X-BZJ-PGB-Request-ID
```

Signature:

```text
HMAC-SHA256(
    timestamp
    + "\n"
    + nonce
    + "\n"
    + request_id
    + "\n"
    + raw_body,
    shared_secret
)
```

WordPress validates:

```text
timestamp window
nonce
signature
request ID
body hash
```

This prevents:

* replay
* tampering
* forged payment initiation
* accidental duplicate requests

# 34. Automatic recovery

This is essential.

Use WooCommerce/WordPress's existing background scheduling infrastructure rather than inventing another queue. WooCommerce uses Action Scheduler for background tasks. ([The WooCommerce Developer Blog][9])

Schedule:

```text
bzj_pgb_retry_transaction
```

For example:

```text
attempt 1 → 1 minute
attempt 2 → 5 minutes
attempt 3 → 15 minutes
attempt 4 → 1 hour
attempt 5 → 6 hours
attempt 6 → 24 hours
```

Then:

```text
manual_review
```

if the retry budget is exhausted.

# 35. One processor, many triggers

This becomes the core resilience pattern:

```text
                 ┌─ payment_complete
                 │
                 ├─ order_status
                 │
                 ├─ webhook
                 │
                 ├─ scheduled retry
                 │
                 ├─ admin retry
                 │

                         │

                 │ PGB Processor  │
```

That is the major architectural simplification.

# 52. Idempotency rules

The following invariants should be explicitly enforced.

### Order

```text
1 PGB transaction
→ max 1 WooCommerce order
```

### Streams

```text
1 paid PGB transaction
→ max 1 fulfilment
```

### Wallet

```text
1 PGB transaction
→ max 1 wallet credit
```

### AffiliateWP

```text
1 Woo order
→ max 1 referral
```

### Jewel

```text
1 PGB transaction
→ max 1 Jewel entitlement/reward
```

### Redirect

```text
1 PGB transaction
→ one current redirect instruction
```

The previous architecture correctly identified these invariants. ([GitHub][4])

# 53. Database locking

The processor must protect against:

```text
Webhook
+
payment_complete
+
scheduled retry
```

arriving simultaneously.

For example:

```text
payment_complete
        │
        ├──── processor A
        │
        └──── processor B
```

Only one should obtain the transaction lock.

The other should receive:

```text
already_processing
```

or subsequently:

```text
already_completed
```

This is critical for preventing duplicate wallet credits and affiliate referrals.

---

# 54. Transactional database writes

Where the Streams database permits it, related writes should be grouped.

For example:

```text
START TRANSACTION

update Wo_Payment_Transactions
update Wo_UserOrders
insert/update purchase
wallet update

COMMIT
```

But do **not** attempt to create one giant cross-database transaction involving:

```text
WordPress DB
+
WooCommerce
+
Streams DB
+
AffiliateWP
```

That would create a fragile distributed transaction.

Instead use the PGB state machine and idempotent steps.

---

# 55. This is effectively a saga architecture

The system is best thought of as:

```text
PGB transaction
      ↓
WooCommerce payment
      ↓
Streams fulfilment
      ↓
AffiliateWP
      ↓
Jewel
      ↓
redirect
```

Each stage can succeed independently.

If stage 4 fails:

```text
stage 1 ✓
stage 2 ✓
stage 3 ✓
stage 4 ✗
```

the transaction remains:

```text
affiliate_pending
```

and resumes from stage 4.

That is far safer than attempting rollback of an already successful payment.

# 76. The strategic difference

The current bridge is essentially:

```text
payment
 ↓
try to synchronize everything
```

The new bridge becomes:

```text
intent
 ↓
durable transaction
 ↓
payment
 ↓
verified payment
 ↓
idempotent fulfilment
 ↓
independent addons
 ↓
recoverable completion
```

That is the architecture I would implement.

It incorporates the useful recommendations from both supplied GitHub reviews—particularly the dedicated PGB transaction table, state machine, one processor, modular handlers, AffiliateWP extraction, direct-but-controlled Streams DB fulfilment, compatibility wrappers, and retry model—while correcting the parts that would otherwise cause the new system to become another tightly coupled bridge. ([GitHub][4])

Most importantly, **the browser, thank-you page, and webhook are no longer allowed to be the thing that makes a payment "complete."** They become signals into a durable processor. WooCommerce's native payment lifecycle is the primary trigger, while webhook/retry/manual paths all converge on the same processor. ([GitHub][4])

### Recommended implementation order

1. **Build the PGB MU-plugin foundation and transaction table.**
2. **Build HMAC-authenticated PGB REST endpoints.**
3. **Build the idempotent transaction/order creation path.**
4. **Convert `wow-pgb_init.php` into the thin Streams adapter.**
5. **Build the central PGB processor/state machine.**
6. **Extract the existing AffiliateWP logic without changing its proven resolution/accounting behaviour.**
7. **Extract Currency Switcher and Jewel logic.**
8. **Move Streams fulfilment into the dedicated Streams integration.**
9. **Move redirects to signed/status-based presentation logic.**
10. **Convert `wow-pgb_webhook.php` into a compatibility/recovery shim.**
11. **Run old and new paths in controlled migration/reconciliation mode.**
12. **Retire `wow-pgb_sync.php`, legacy webhook business logic, and obsolete API/secret handling.**

This gives Buzzjuice a payment subsystem that can later support **Socials, courses, subscriptions, services, Jewel rewards, marketplace transactions and other WooCommerce-backed products without creating another payment-specific monolith**.
