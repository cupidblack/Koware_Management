The evidence points to a **transport/lifecycle problem rather than a checkout-generation problem**.

Your existing v14.1.1/v17.0.2 path is valuable because it already gets the customer from Streams to WooCommerce checkout. The part that should be replaced is the fragile **post-payment synchronization and REST-based subscription/commission handling**.

# 3. Why the current Thank You page is failing

The current system effectively does:

```text
payment
 ↓
WooCommerce order
 ↓
order-received
 ↓
wp_footer
 ↓
wowonder_redirect_after_purchase()
 ↓
subscription/API/AffiliateWP processing
 ↓
redirect
```

That creates several problems.

If the browser:

* closes,
* times out,
* does not render the footer,
* encounters another PHP error,
* receives a cached Thank You page,

the financial transaction has already succeeded but the business fulfillment never runs.

That explains the particularly important combination you are seeing:

> WooCommerce order exists
> Thank You page appears
> order details are missing
> subscription doesn't exist
> commission doesn't exist

The payment itself is not necessarily failing. **Fulfillment is failing after payment.**

The new bridge must therefore process fulfillment from:

```php
woocommerce_payment_complete
```

and use order/subscription status hooks as retry points.

WooCommerce's own source shows that `woocommerce_payment_complete` is emitted by `WC_Order::payment_complete()`, after the payment state has been recorded. ([GitHub][3])

# 6. Database design

I recommend retaining the durable queue concept from the previous v17 work, but use one authoritative WoWonder-side bridge table:

```text
Wo_Payment_Gateway_Bridge
```

It should contain at least:

```sql
CREATE TABLE IF NOT EXISTS Wo_Payment_Gateway_Bridge (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    request_id VARCHAR(80) NOT NULL,
    token_hash CHAR(64) NOT NULL,

    wow_user_id BIGINT UNSIGNED NOT NULL,
    wp_user_id BIGINT UNSIGNED NOT NULL,

    transaction_kind VARCHAR(50) NOT NULL,

    wow_post_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
    product_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
    variation_id BIGINT UNSIGNED NOT NULL DEFAULT 0,

    product_name VARCHAR(255) NOT NULL,
    quantity INT UNSIGNED NOT NULL DEFAULT 1,

    source_currency VARCHAR(20) NOT NULL,
    source_amount DECIMAL(20,8) NOT NULL DEFAULT 0,

    woo_currency VARCHAR(20) NOT NULL DEFAULT '',
    woo_amount DECIMAL(20,8) NOT NULL DEFAULT 0,

    woo_order_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
    woo_subscription_id BIGINT UNSIGNED NOT NULL DEFAULT 0,

    status VARCHAR(30) NOT NULL DEFAULT 'pending',

    payload_json LONGTEXT NULL,

    expires_at DATETIME NOT NULL,
    claimed_at DATETIME NULL,
    completed_at DATETIME NULL,

    last_error TEXT NULL,

    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,

    PRIMARY KEY (id),
    UNIQUE KEY request_id (request_id),
    UNIQUE KEY token_hash (token_hash),
    KEY wow_user_id (wow_user_id),
    KEY wp_user_id (wp_user_id),
    KEY woo_order_id (woo_order_id),
    KEY woo_subscription_id (woo_subscription_id),
    KEY status (status)
);
```

And a second table:

```text
Wo_Payment_Gateway_Events
```

for idempotency:

```sql
CREATE TABLE IF NOT EXISTS Wo_Payment_Gateway_Events (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    event_key VARCHAR(150) NOT NULL,
    request_id VARCHAR(80) NOT NULL DEFAULT '',
    woo_order_id BIGINT UNSIGNED NOT NULL DEFAULT 0,

    component VARCHAR(100) NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'processing',

    attempts INT UNSIGNED NOT NULL DEFAULT 0,

    error_message TEXT NULL,

    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    completed_at DATETIME NULL,

    PRIMARY KEY (id),
    UNIQUE KEY event_key (event_key),
    KEY request_id (request_id),
    KEY woo_order_id (woo_order_id),
    KEY component (component)
);
```

### Why two tables?

Because these are different concepts.

`Wo_Payment_Gateway_Bridge` answers:

> What payment request is this?

`Wo_Payment_Gateway_Events` answers:

> Has this particular operation already been performed?

For example:

```text
affiliate:woocommerce-order-1874
streams:woocommerce-order-1874
jewel:woocommerce-order-1874
subscription:woocommerce-order-1874
```

This prevents duplicate commissions and duplicate wallet credits when WooCommerce fires more than one lifecycle hook.

# 8. `pgb-client-streams.php`

The client should:

1. validate the user;
2. resolve `wp_user_id`;
3. validate the mapped product;
4. create a random token;
5. hash the token;
6. insert the durable bridge record;
7. verify the row;
8. generate the HMAC;
9. return a browser URL.

Conceptually:

```php
$token = bin2hex(random_bytes(32));

$token_hash = hash(
    'sha256',
    $token
);

$signature = hash_hmac(
    'sha256',
    $request_id . '|' . $token,
    $secret
);
```

The browser gets:

```text
token
sig
```

but the database only receives:

```text
token_hash
```

This is safer than putting the actual transaction identifier directly into the URL.

# 13. Currency conversion

The new currency handler is deliberately WordPress-side.

It determines:

```php
get_woocommerce_currency()
```

for the current WooCommerce request.

It then attempts to use the currently loaded Fox WOOCS object.

If the public conversion method isn't available, it falls back to the stored WOOCS currency/rate data.

The conceptual conversion is:

```text
source amount
      ÷
source WOOCS rate
      ×
target WOOCS rate
      =
WooCommerce amount
```

This means the amount actually placed into the WooCommerce order is the amount that WooCommerce is going to charge.

That is substantially safer than converting the value inside WoWonder before the order reaches WooCommerce.

# 39. Why this should be substantially more durable

The old architecture has this failure chain:

```text
WoWonder
 ↓
PHP
 ↓
DNS
 ↓
cURL
 ↓
HTTPS
 ↓
WordPress
 ↓
REST
 ↓
WooCommerce
```

The new architecture is:

```text
WoWonder
 ↓
local database
 ↓
browser HTTPS
 ↓
WordPress
 ↓
WooCommerce
```


still remembers the request.

prevents duplicate processing.

can be retried.

```text
jewel:<order>
```

can be retried.

That is the fundamental durability improvement.

## Review conclusion

I reviewed the current repository implementation, the previous v16 design, and the GitHub v17 response. The **core architectural direction is correct**, but I would **not deploy the GitHub v17 implementation as written**.

The most important correction is this:

> **Streams must remain completely independent of WordPress/PHP bootstrap.**

The GitHub proposal reintroduced `wp-load.php` into `streams/requests.php`, directly contradicting the established Buzzjuice Streams architecture. 

The durable architecture should instead be:

```text
Buzzjuice Streams
      │
      │ payment request
      ▼

      │
      │ MySQL only
      ▼
Wo_Payment_Gateway_Bridge
      │
      │ signed one-time browser handoff
      ▼

      │
      ▼
https://buzzjuice.net/pgb-checkout/
      │
      ▼
bzj-payment-gateway.php
      │
      ├── verify HMAC
      ├── claim handoff
      ├── resolve product
      ├── apply WOOCS conversion
      ├── create native WC order
      └── get_checkout_payment_url(false)
                    │
                    ▼
             WooCommerce Checkout
                    │
                    ▼
                 Payment
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      WCS        AffiliateWP   Jewel
        │           │           │
        └───────────┼───────────┘
                    ▼
             Streams fulfilment
```

That removes the problematic server-side request:

```text

   ↓

   ↓
```

# Step 2 — Create the durable bridge table

The package contains:

```text
shared/payment-gateway/sql/001-create-bridge-table.sql
```

The important table is:

```text
Wo_Payment_Gateway_Bridge
```

It provides the missing orchestration layer between the Streams financial transaction and WooCommerce.

Conceptually:

```text
Wo_Payment_Transactions
        │
        │ business transaction
        │
        ▼
Wo_Payment_Gateway_Bridge
        │

        ├── status
        ├── payload
        ├── wc_order_id
        ├── expiry
        ├── claimed_at
        └── last_error
```

This is important because a browser redirect is not itself a durable transaction mechanism.

The database becomes the authoritative handoff.

# Step 6 — `bzj-payment-gateway.php` claims the transaction

The MU plugin:

1. receives token;
2. receives signature;
3. calculates expected HMAC;
4. verifies it;
5. hashes token;
6. retrieves the bridge row;
7. checks expiry;
8. atomically claims it;
9. creates the WooCommerce order.

The claim is intentionally atomic:

```sql
UPDATE Wo_Payment_Gateway_Bridge
SET status='claimed'
WHERE id=?
AND status='pending'
AND expires_at > UTC_TIMESTAMP()
```

That prevents double-clicks and repeated browser requests from creating two WooCommerce orders.

from VS Code:


while cPanel:


is a very useful diagnostic.
