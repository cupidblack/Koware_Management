1. Executive Summary

This repository evidence supports a hybrid payment bridge in which the Streams application initiates a custom WooCommerce handoff, then WordPress/WooCommerce completes the transaction and a WordPress MU plugin triggers the post-payment AffiliateWP bridge. The clearest verified path is:

- Streams request routing accepts a custom payment request in streams/requests.php.
- The branch for f=payment with payment_type=wow_payment includes assets/wow-pgb/wow-pgb_init.php.
- A second verification in streams/sources/checkout.php shows that a wow_payment request validates required fields, writes a pending record to a local table named wo_payment_transactions, and redirects to a WooCommerce checkout URL using add-to-cart and query-string metadata.
- A WordPress MU plugin, wp-content/mu-plugins/buzzjuice-affwp-order-complete.php, loads the bridge and registers a handler on woocommerce_order_status_completed that calls bluecrown_affiliatewp_post_checkout_verification.

This is enough to say the current architecture is not a pure single-app integration. It is a cross-system handoff pattern: Streams creates a pending transaction and redirects the browser to WordPress/WooCommerce, while WordPress performs order completion and the post-payment bridge then handles AffiliateWP work.

The biggest gap is that the actual logic of wow-pgb_init.php and wow-pgb_sync.php is not directly evidenced in the repository snapshot inspected here. That prevents a reliable statement about API calls, cURL details, WooCommerce order creation APIs, subscriptions hooks, or the precise Streams-to-WooCommerce data contract beyond what is visible in the request/checkout flow.

Classification:
- VERIFIED: custom Streams payment branch exists and redirects to WooCommerce checkout.
- VERIFIED: MU plugin calls the completion bridge on WooCommerce order completion.
- INFERRED: the design is a brokered handoff across Streams and WordPress rather than a single database-driven system.
- UNKNOWN / REQUIRES VERIFICATION: exact inner logic of wow-pgb_init.php, wow-pgb_sync.php, and any WooCommerce Subscriptions/WOOCS plugin integration code.

5. Dropped-Order Failure Analysis

This section focuses on realistic loss points visible in the current architecture.

1) Streams request fails before redirect
- Failure location: Streams router or earlier processing before the checkout redirect.
- Evidence: custom payment request is handled in requests.php and checkout.php, but exact validation logic beyond the visible branch is not reviewed.
- Protection: basic required-field validation is present in checkout.php.
- Impact: no order is handed to WooCommerce.
- Recoverability: limited unless a durable transaction table or retry queue exists.
- Recommended mitigation: record a payment intent at creation time with status pending and retryable.

2) Streams validation fails
- Failure location: checkout.php validation loop.
- Evidence: required params are checked before insertion.
- Protection: explicit required-parameter validation exists.
- Impact: request rejected before creating pending record.
- Recoverability: user can retry with valid data.
- Recommended mitigation: consistent user-facing error codes and transaction log correlation.

3) Database insert fails
- Failure location: wo_payment_transactions insert.
- Evidence: insert is executed in checkout.php and returns error if execution fails.
- Protection: mysql execute call with error logging.
- Impact: no redirect occurs after failed insert.
- Recoverability: manual retry possible; no durable compensation shown.
- Recommended mitigation: transactional insert + idempotency key.

4) Redirect lost or browser closes after order creation
- Failure location: redirect to WooCommerce checkout and browser continuity.
- Evidence: redirect is issued with a URL that includes add-to-cart and metadata.
- Protection: none visible beyond redirect generation.
- Impact: customer does not reach checkout and the pending Streams record may remain without a corresponding WooCommerce order.
- Recoverability: weak without recovery queue or reconciliation logic.
- Recommended mitigation: store a durable handoff record and reconcile on return.

5) WooCommerce order created but response lost
- Failure location: the WooCommerce checkout path after add-to-cart.
- Evidence: the only visible handoff is the add-to-cart payload, not a direct server-side order create call.
- Protection: none visible in reviewed files.
- Impact: order may be created in WooCommerce without clean downstream completion.
- Recoverability: requires reconciliation by order metadata or unique payment intent key.
- Recommended mitigation: unique correlation ID in both Streams and WooCommerce metadata.

6) Payment gateway callback or order completion hook fires more than once
- Failure location: WooCommerce completion path and affiliate processing.
- Evidence: MU plugin registers a single completed hook, which is a good protective pattern, but no deduplication logic was reviewed in the bridge function itself.
- Protection: single-hook registration reduces duplicate processing risk.
- Impact: duplicate AffiliateWP or sync processing.
- Recoverability: depends on dedupe guards inside bridge functions.
- Recommended mitigation: idempotency key and processed marker at every downstream system boundary.

7) Payment succeeds but synchronization fails
- Failure location: downstream post-payment processing after order completion.
- Evidence: order completion triggers the bridge, but exact downstream logic is not reviewed.
- Protection: minimal evidence of a state machine or durable retry queue.
- Impact: customer sees payment success while Streams, subscriptions, or affiliate state remains incomplete.
- Recoverability: low without a reconciliation or scheduled repair process.
- Recommended mitigation: durable state tracking at every stage.

8) AffiliateWP or Jewel Affiliate processing fails
- Failure location: post-completion bridge and webhook flows.
- Evidence: AffiliateWP bridge is hooked to order completion; Jewel Affiliate appears to use a separate webhook file.
- Protection: no direct evidence of a retry or compensation layer in inspected files.
- Impact: referral credit or downstream account sync can be missed.
- Recoverability: weak unless webhook replay or scheduled reconciliation exists.
- Recommended mitigation: durable event log with replay ability.

6. Root-Cause Hypotheses

The most credible root-cause hypotheses, based on the reviewed code, are:

1) Cross-system state loss between Streams and WooCommerce
- Evidence: the visible handoff is a redirect with query parameters and a pending insert to wo_payment_transactions; there is no clearly shown durable transaction key linking Streams to WooCommerce order IDs.
- Classification: INFERRED / HYPOTHESIS
- Why plausible: browser redirect plus order creation URL is fragile if any step is interrupted.

2) Missing idempotency and correlation in the handoff
- Evidence: redirect includes query parameters but no explicit durable idempotency token or payment-intent registry is visible in the inspected files.
- Classification: HYPOTHESIS
- Why plausible: the visible flow can easily create duplicate or orphaned orders under refresh, double submit, or callback replay.

3) Payment completion may be the only reliable boundary currently guarded
- Evidence: MU plugin hooks on woocommerce_order_status_completed.
- Classification: VERIFIED for the hook
- Why plausible: this is a strong signal that the system relies on the order completion event as the authoritative post-payment trigger.

4) Streams-side custom payment flow is likely a compatibility bridge rather than a native WooCommerce payment implementation
- Evidence: add-to-cart checkout flow with a custom product ID and query parameters.
- Classification: INFERRED
- Why plausible: this is consistent with a cart-driven WooCommerce checkout path, not a direct API order create.

5) The exact failure profile around wow-pgb_init.php and wow-pgb_sync.php is unverified and could be the critical source of dropped orders
- Evidence: those files are named in the requested scope but not inspected in this repository snapshot.
- Classification: UNKNOWN / REQUIRES VERIFICATION

7. Architectural Options

Option A: Streams → WooCommerce REST/API → browser checkout
- Evidence: not directly confirmed in repository; no REST client code was inspected in the reviewed files.
- Assessment: possible but not evidenced in the available repo snapshot.
- Transaction durability: medium if handled with durable payment intent.
- Security: depends on signed requests and server-side validation.
- Compatibility: good with WooCommerce if native API is used.
- Conclusion: not proven by repo evidence.

Option B: Streams → durable payment intent → browser → WordPress → native WooCommerce PHP APIs → checkout
- Evidence: the repository shows a pending transaction insert plus redirect-based handoff, which aligns with a payment-intent pattern.
- Assessment: strongest architectural fit with existing evidence.
- Transaction durability: stronger than pure redirect-only flows.
- Network dependency: lower for server-side WordPress processing than external API calls.
- Security: good if server-side validation is enforced and browser data is not trusted.
- Compatibility: good for WordPress/WooCommerce native APIs.
- Conclusion: most aligned with current evidence, though not yet verified.

Option C: Streams → browser → WordPress endpoint → native WooCommerce processing
- Evidence: no direct WordPress endpoint implementation was inspected.
- Assessment: plausible but not evidenced.
- Transaction durability: good if the endpoint records intent and order state.
- Security: strong if endpoint is authenticated and signed.
- Conclusion: possible redesign path, but not the current repository pattern.

Option D: Current architecture with targeted reliability improvements
- Evidence: this is the repository’s actual displayed architecture.
- Assessment: the current pattern is observable and consistent with a hybrid redirect flow.
- Transaction durability: currently weak to moderate.
- Recovery: improved by adding state tracking and idempotency.
- Conclusion: best fit for the current evidence, but it needs reliability hardening before it can be considered robust.

8. Transaction State Model

The minimum durable state model should be designed around the actual handoff reality, not just order completion. A minimal model could include:

- created
  - Purpose: payment request accepted in Streams
  - Entry condition: user selects payment and request is received
  - Responsible: Streams
  - Valid transitions: validated, failed, recovery_required
  - Retry behavior: yes
  - Terminal: no

- validated
  - Purpose: required fields and business rules are accepted
  - Entry condition: request passes validation
  - Responsible: Streams
  - Valid transitions: handoff_pending, failed
  - Retry behavior: yes
  - Terminal: no

- handoff_pending
  - Purpose: transaction is ready to be sent to WooCommerce
  - Entry condition: Streams inserts pending record and creates redirect
  - Responsible: Streams
  - Valid transitions: woocommerce_order_pending, failed, recovery_required
  - Retry behavior: yes
  - Terminal: no

- woocommerce_order_pending
  - Purpose: order creation is expected but not yet confirmed
  - Entry condition: browser reaches WooCommerce checkout
  - Responsible: WordPress/WooCommerce
  - Valid transitions: woocommerce_order_created, failed, recovery_required
  - Retry behavior: yes
  - Terminal: no

- woocommerce_order_created
  - Purpose: order exists and is linked to the original transaction
  - Entry condition: WooCommerce order is created with metadata
  - Responsible: WordPress/WooCommerce
  - Valid transitions: checkout_ready, failed, recovery_required
  - Retry behavior: yes
  - Terminal: no

- checkout_ready
  - Purpose: customer is ready to pay
  - Entry condition: payment URL is valid and order is associated
  - Responsible: WooCommerce
  - Valid transitions: payment_pending, expired, cancelled
  - Retry behavior: yes
  - Terminal: no

- payment_pending / payment_processing / payment_completed
  - Purpose: gateway lifecycle tracking
  - Entry condition: gateway status progression
  - Responsible: WooCommerce/gateway
  - Valid transitions: post_payment_processing, failed, cancelled, expired
  - Retry behavior: yes
  - Terminal: no

- post_payment_processing
  - Purpose: downstream state sync after successful payment
  - Entry condition: WooCommerce completion hook fires
  - Responsible: WordPress bridge
  - Valid transitions: completed, failed, recovery_required
  - Retry behavior: yes
  - Terminal: no

- completed
  - Purpose: final success state
  - Entry condition: Streams, subscriptions, and affiliate processing succeeded
  - Responsible: multi-system
  - Valid transitions: none
  - Retry behavior: no
  - Terminal: yes

- failed / expired / cancelled / recovery_required
  - Purpose: failure and recovery paths
  - Entry condition: retry or manual triage needed
  - Responsible: relevant system
  - Valid transitions: retry or terminal resolution
  - Retry behavior: yes depending on state
  - Terminal: no for recovery_required; yes for terminal failed/expired/cancelled states

This is a recommended model, not a proven current model.

9. Idempotency Model

The inspected code reveals a strong need for idempotency, but not clear evidence of a complete idempotency model.

Current evidence:
- There is a pending insert into wo_payment_transactions with a generated wow_order_id in streams/sources/checkout.php.
- The redirect URL includes wow_order_id in query-string parameters.
- The MU plugin calls a handler on woocommerce_order_status_completed, which is a standard post-payment trigger.
- There is no visible dedupe key or processed marker for downstream steps in the inspected files.

Required idempotency boundaries:
- payment intent creation
  - Need: unique payment_intent_id and request hash
  - Current protection: minimal; required-field validation only
  - Recommendation: enforce unique external reference

- WordPress handoff
  - Need: stable key linking Streams request to WooCommerce cart/order
  - Current protection: none visible
  - Recommendation: correlate on a single transaction UUID

- WooCommerce order creation
  - Need: one order per payment intent
  - Current protection: not visible in repo evidence
  - Recommendation: guard on source intent ID and external order reference

- checkout requests
  - Need: refresh or repeated purchase should not generate duplicate orders
  - Current protection: not visible
  - Recommendation: prevent duplicate order creation by idempotency key

- payment callbacks
  - Need: prevent double handling of webhook or gateway callback data
  - Current protection: not visible in reviewed files
  - Recommendation: enforce callback receipt and processed marker

- order completion
  - Need: only one successful completion state transition
  - Current protection: MU plugin uses a single completed hook
  - Recommendation: maintain created/completed completion marker

- subscription processing
  - Need: avoid duplicate subscription activation
  - Current protection: not reviewed
  - Recommendation: rely on WooCommerce Subscriptions’ own idempotent activation, but verify

- AffiliateWP
  - Need: one commission per qualifying order
  - Current protection: single order completion hook is a positive sign
  - Recommendation: verify the bridge function itself before assuming safety

- Jewel Affiliate
  - Need: ensure one webhook event does not trigger duplicate referrals
  - Current protection: not visible
  - Recommendation: require replay-safe webhook processing

Conclusion:
- The repository currently shows a partial pattern of completion protection, but not a full transaction-wide idempotency model.

19. Security

The reviewed files show several security concerns that should be treated as architectural risks until proven otherwise.

Verified security issues present in the visible flow:
- browser-supplied values are used in the redirect parameters
- amount, product_name, product_price, product_units, product_owner_id, and wow_order_id are passed as query parameters
- the repo does not show a signed payload or server-side verification of those values before WooCommerce order creation

The following risks are valid concerns:
- amount manipulation
- product manipulation
- currency manipulation
- user-ID tampering
- order-ID manipulation
- return-URL manipulation
- replay of the same payment request
- transaction ownership mismatch
- untrusted browser metadata being accepted as authority

Important architectural principle:
- A browser must never be trusted as the authority for amount, currency, product price, subscription entitlement, or affiliate attribution.

The reviewed code does not provide enough evidence to conclude that the system currently enforces signed server-to-server validation at the handoff boundary. That is a major gap.
