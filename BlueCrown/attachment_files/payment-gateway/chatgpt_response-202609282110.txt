# Buzzjuice Payment Gateway Bridge v15 — Recommended Refactor

I reviewed the current Streams bridge, the current `wow-pgb_sync.php`, AffiliateWP handler, database helpers, Jewel webhook, the previous ChatGPT proposal, and the GitHub response.

The **core architectural direction is correct**, but I would make several important changes before deployment.

### The most important conclusion

The cPanel DNS result:

```text
curl: (6) Could not resolve host: buzzjuice.net
```

**does confirm a DNS-resolution problem from the cPanel server environment.** It explains why a server-side Streams → `https://buzzjuice.net/wp-json/...` cURL request is unreliable.

But it does **not** mean the browser cannot access `buzzjuice.net`.

That distinction is what makes the new architecture work:

```text
Streams server
     │
     │ database write only
     ▼
Wo_Payment_Gateway_Bridge
     │
     │ browser redirect
     ▼
https://buzzjuice.net/pgb-checkout/?token=...&sig=...
     │
     ▼
WordPress MU plugin
     │
     │ native PHP / WooCommerce CRUD
     ▼
WooCommerce Order
     │
     ▼
WooCommerce Checkout
     │
     ▼
Payment
     │
     ▼
WooCommerce hooks
     │
     ├── Subscriptions
     ├── AffiliateWP
     ├── Jewel
     └── Streams fulfillment
```

So **there is no server-side HTTP call from Streams to WordPress at all**, and there is no WooCommerce REST API order-creation call.

This is the major durability improvement over the current system. The current `wow-pgb_init.php` explicitly constructs `/wc/v3/orders` and sends it with cURL. ([GitHub][1])

# 1. What I would change from the GitHub proposal

The GitHub response got the major architecture right: browser handoff, one MU engine, WooCommerce-native order creation, and post-payment fulfillment. ([GitHub][2])

However, I would **not deploy that response verbatim**.

## Correction 1 — Do not create a new REST API

The previous proposal suggested:

```text
/wp-json/bzj-pgb/v1/checkout
```

The earlier ChatGPT analysis correctly rejected that because it simply moves the HTTP dependency rather than removing it. ([GitHub][3])

The new route should instead be:

```text
/pgb-checkout/
```

handled by:

```php
template_redirect
```

inside the MU plugin.

# 2. WooCommerce checkout URL

There is no reason to manually construct:

```text
/checkout/order-pay/{order_id}/?pay_for_order=true&key=...
```

WooCommerce already provides the correct API:

```php
$order->get_checkout_payment_url(false);
```

WooCommerce's current source implements that method specifically for unpaid orders and builds the `order-pay` endpoint and order key itself. ([WooCommerce GitHub][4])

So the new bridge should always do:

```php
$checkout_url = $order->get_checkout_payment_url(false);
wp_safe_redirect($checkout_url);
exit;
```

This is considerably safer than reproducing WooCommerce's URL-generation logic.

The same applies to the thank-you URL:

```php
$order->get_checkout_order_received_url();
```

rather than constructing `/checkout/order-received/` manually. ([WooCommerce GitHub][5])

# 3. Do not directly manipulate WooCommerce order tables

This is especially important because WooCommerce supports HPOS.

The new bridge uses:

```php
wc_create_order()
$order->add_product()
$order->set_currency()
$order->update_meta_data()
$order->calculate_totals()
$order->save()
```

rather than SQL against:

```text
wp_posts
wp_postmeta
wc_orders
wc_order_meta
```

WooCommerce explicitly recommends its order CRUD APIs because HPOS changes the underlying storage architecture. ([The WooCommerce Developer Blog][6])

That gives us a much better long-term architecture.

# 6. Durable payment handoff

This is one of the most important changes.

The Streams client generates:

```text
wow_order_id
token
token_hash
payload
expiry
```

and stores them in:

```text
Wo_Payment_Gateway_Bridge
```

The browser then receives:

```text
https://buzzjuice.net/pgb-checkout/?token=...&sig=...
```

The token is **not the order data**.

The URL contains only an opaque high-entropy token plus HMAC signature.

The database contains the actual transaction payload.

That gives us:

### No huge URL

We don't put:

```text
product_name
price
user data
affiliate data
```

into the URL.

### No WooCommerce credentials

The Streams installation no longer needs:

```text
WooCommerce API key
WooCommerce API secret
```

for order creation.

### No server-side self-request

The cPanel DNS problem becomes irrelevant to the handoff.

### Replay protection

The token is stored as a SHA-256 hash.

### Expiration

The handoff expires, by default, after:

```text
900 seconds
```

### Claim protection

The row changes:

```text
ready
   ↓
claimed
   ↓
checkout
   ↓
fulfilled
```

so two simultaneous requests cannot normally create two WooCommerce orders.

# 12. Currency architecture

There is one important conceptual correction to the original proposal.

Do **not** think of this as:

```text
create order
↓
change currency
↓
change price
```

The correct lifecycle is:

```text
Streams transaction currency
          ↓
PGB currency resolver
          ↓
WOOCS current checkout currency
          ↓
calculate target amount
          ↓
create WooCommerce order
          ↓
set order currency
          ↓
set line price
          ↓
checkout
```

WooCommerce's order itself has a currency field and WooCommerce supports explicit order currencies. ([The WooCommerce Developer Blog][7])

The new currency adapter therefore resolves the target currency **before the order is created**.

# 13. WOOCS

The new adapter looks for the active Fox WOOCS instance and its currency rates.

The important model is:

```text
Source currency
      ↓
WOOCS base
      ↓
Target currency
```

So if:

```text
GHS → USD
```

the conversion is effectively:

```text
GHS amount / GHS rate × USD rate
```

assuming the WOOCS rates are represented relative to the base currency.

The bridge records:

```text
_bzj_source_currency
_bzj_source_amount
_bzj_exchange_rate
_bzj_checkout_currency
```

inside the WooCommerce order.

That gives you an audit trail.

```text

```

```text

```

as recovery opportunities.

The key is that they all run through:


```text

      ↓

      ↓
```

No duplicate commission.

No duplicate Jewel rebate.

# 24. Important security property

The browser URL:

```text
/pgb-checkout/?token=...&sig=...
```

does **not** grant generic WooCommerce access.

It only permits the PGB engine to resolve a specific one-time database handoff.

The token is:

```text
random_bytes(32)
```

and only its SHA-256 hash is stored.

The signature is:

```php
hash_hmac(
    'sha256',
    $token,
    BZJ_PGB_SECRET
);
```

So an attacker cannot simply invent:

```text
?wow_user_id=1&amount=1
```

and create an arbitrary order.

## Bottom line

The **transport layer should definitely be replaced**. The cPanel DNS failure makes the current server-to-server self-cURL architecture unnecessarily fragile, while WooCommerce already provides native PHP order creation and the correct payment URL generation. ([WooCommerce GitHub][4])

The strongest architecture for Buzzjuice is therefore:

**Streams records the transaction → secure browser handoff → WordPress MU engine creates the WooCommerce order natively → WooCommerce handles checkout/payment → native WooCommerce hooks drive idempotent fulfillment → integrations update Streams.**

And importantly, I would **not rewrite the already-working AffiliateWP and Jewel business rules merely because the transport layer is being redesigned**. The existing AffiliateWP resolver and Jewel rebate implementation contain production-specific logic that the generic GitHub proposal does not fully reproduce. ([GitHub][8])

## Diagnosis

There are **two independent v15 defects**, and both are now identified.

### 1. The WordPress MU-plugin path is wrong

v15 used:

```php
$pgb_root = dirname(ABSPATH) . '/shared/payment-gateway';
```

With your installation:

```text
/home/enkaby/public_html/buzzjuice.net/
```

`ABSPATH` already points to the Buzzjuice WordPress root. Therefore `dirname(ABSPATH)` moves outside the project.

That directly explains:

```text
[BZJ-PGB] Required bridge files are missing or unreadable.
```

The corrected code is:

```php
$pgb_root = trailingslashit(ABSPATH) . 'shared/payment-gateway';
```

The same path error existed in the Jewel integration and has also been corrected.

---

### 2. The Streams client broke the existing WoWonder request contract

The current JavaScript sends:

```javascript
wow_post_id: wow_post_id
```

not:

```javascript
product_id: product_id
```

The existing JavaScript calculates `wow_post_id` from:

* `#product_id`
* `#fund_donate_id`
* `$wo['product']['id']`
* or the selected PRO package ID. 

The old `wow-pgb_init.php` then maps that value according to transaction type. In particular:

```text
PRO
1 → wow_pro_package_id
2 → wow_pro_package_id_2
3 → wow_pro_package_id_3
4 → wow_pro_package_id_4

WALLET → wow_wallet_topup_id

DONATE → wow_crowdfund_id

PRODUCT → wow_post_id
```

That mapping is present in the existing bridge. ([GitHub][1])

v15 accidentally removed this mapping and instead required:

```php
$product_id > 0
```

Since the JavaScript does not send `product_id`, v15 throws:

```text
Invalid payment request.
```

That explains the Streams:

```text
POST /streams/requests.php?f=payment 500
```

The AJAX routing itself is fine; `requests.php` correctly includes `wow-pgb_init.php` when `f=payment` and `payment_type=wow_payment`. ([GitHub][2])
