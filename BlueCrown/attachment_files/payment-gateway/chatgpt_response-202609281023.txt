# 1. What is actually wrong with the present architecture

Your diagnosis is directionally correct.

The existing flow is:

```text
WoWonder
   │
   ├── wow-pgb_init.php
   │       │
   │       ├── creates Wo_Payment_Transactions record
   │       ├── prepares WooCommerce order
   │       └── performs server-side WooCommerce REST/cURL
   │
   ▼
WooCommerce REST API
   │
   ▼
WooCommerce Order
   │
   ▼
Payment
   │
   ▼
wow-pgb_sync.php / webhook / MU plugin
   │
   ├── Streams transaction update
   ├── subscription handling
   ├── wallet/funding/pro activation
   └── AffiliateWP
```

The existing `wow-pgb_init.php` explicitly obtains WooCommerce API credentials and prepares the REST request. 

More importantly, the current initializer performs significant WoWonder-side operations **before the payment has actually succeeded**. For example, the current code creates the transaction and then, depending upon transaction type, can create owner-sale/purchase records before WooCommerce has confirmed payment. 

That is precisely the type of architecture that can produce:

* abandoned orders;
* duplicate orders;
* partially completed orders;
* payment successful but Streams not synchronized;
* Streams record created but WooCommerce order missing;
* WooCommerce order created but browser redirected incorrectly;
* duplicate affiliate commissions;
* subscription activation inconsistencies.

# 2. The new architecture I recommend

The durable architecture should instead be:

```text
                    BUZZJUICE STREAMS
                           │
                           │ authenticated request
                           ▼
              pgb-client-streams.php
                           │
                           │ INSERT ONLY
                           ▼
              Wo_Payment_Transactions
                           │
                           │ pending
                           │
                           │ HMAC signed browser redirect
                           ▼
                 WORDPRESS / WOO
                           │
                           ▼
                PGB MU-PLUGIN ENGINE
                           │
                    validates token
                           │
                    reads DB record
                           │
                    creates WC order
                           │
                           ▼
                 WooCommerce Checkout
                           │
                           ▼
                       PAYMENT
                           │
                           ▼
             WooCommerce authoritative state
                           │
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
       Subscriptions   AffiliateWP     Other addons
            │              │              │
            └──────────────┼──────────────┘
                           ▼
                PGB fulfillment engine
                           │
                           ▼
              Wo_Payment_Transactions
                           │
                           ▼
```

This eliminates the problematic server-side:

```text

        ↓

```

because that is a normal browser request. The cPanel server does not have to resolve `buzzjuice.net` and make the WooCommerce API request.

# 7. Why idempotency is essential

Suppose WooCommerce fires:

```php
woocommerce_payment_complete
```

and subsequently:

```php
woocommerce_order_status_processing
```

and:

```php
woocommerce_order_status_completed
```

The bridge must **not** do this:

```text
payment_complete
   → affiliate commission

completed
   → affiliate commission again
```

The new manager checks:

```php
pgb_fulfilled_at
```

before fulfillment.

Therefore:

```text
First execution
    ↓
fulfillment
    ↓
pgb_fulfilled_at = timestamp

Second execution
    ↓
already fulfilled
    ↓
STOP
```

This is one of the most important improvements for preventing dropped/duplicated transactions.

and the current sync code has substantial logic around the subscription products. 

That logic should be preserved where it is genuinely product configuration rather than payment-state logic.

I thoroughly traced the WooCommerce flow and the existing Buzzjuice implementation. There were **two important architectural corrections** to make.

### What the investigation established

WooCommerce's own checkout code distinguishes between:

* **Payment processing result → `redirect_url`**. The Store API exposes this as part of `payment_result`; it is populated by the payment-processing flow. ([GitHub][1])
* **An already-created order awaiting payment → `WC_Order::get_checkout_payment_url(true)`**. WooCommerce explicitly documents this method as the appropriate payment-page URL for an existing order. ([GitHub][2])

Therefore, the bridge **should not manufacture an `/order-received/` URL for an unpaid order**. The native WooCommerce URL is the order-pay/checkout URL containing the order key.

The old Buzzjuice implementation confirms that the important product IDs originate from the existing **WoWonder payment settings** — `wow_market_id`, `wow_pro_package_id` through `_4`, `wow_wallet_topup_id`, and `wow_crowdfund_id`. The old implementation then sent those IDs as WooCommerce `product_id`/`variation_id` values when creating the order. ([GitHub][3])

That exposed a significant problem in v8.1.2: I had moved the product mapping to separate WordPress options. That was not equivalent to the existing working implementation and could cause the `pgb_create_failed` response.

### What v8.1.3 changes

The new bridge now:

1. **Uses the existing WoWonder payment settings as the authoritative product source.**

   * Market purchases → `wow_market_id`
   * PRO 1–4 → corresponding `wow_pro_package_id*`
   * Wallet → `wow_wallet_topup_id`
   * Crowdfunding → `wow_crowdfund_id`

2. Stores the resolved WooCommerce product/variation ID in the signed transaction metadata before leaving Streams.

3. Creates the WooCommerce order natively with `wc_create_order()`.

4. Adds the configured WooCommerce product to the order.

5. Preserves the **actual Streams transaction amount** rather than silently replacing it with the product catalogue price. This matches the old implementation, which explicitly sent `price`, `subtotal`, and `total` in the WooCommerce order data. ([GitHub][4])

6. Uses:

```php
$order->get_checkout_payment_url(true)
```

for the browser redirect.

7. Uses `wp_safe_redirect()` only **after the order has successfully been created**.

8. Keeps the REST endpoint's JSON error response for genuine failures. Thus, if something genuinely prevents order creation, the endpoint can still return an HTTP 500 diagnostic rather than displaying a misleading WooCommerce page.

9. Includes the improved DB-helper initialization from the preceding issue, so the MU plugin resolves `db_helpers.php` from the same `shared/` tree as the bridge and avoids loading a second copy.

10. Keeps the Streams-side code completely independent of WordPress. There are no `wp_json_encode()`, `sanitize_text_field()`, WooCommerce classes, or other WordPress functions in the Streams payment client.
