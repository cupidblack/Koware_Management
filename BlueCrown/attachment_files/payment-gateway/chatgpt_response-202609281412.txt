## 1. The important architectural correction

The existing system currently does this:

```text
Streams
   │
   │ cURL / WooCommerce REST
   ▼
/wp-json/wc/v3/orders
   │
   ▼
WooCommerce Order
   │
   ▼
Payment
```

That is exactly the portion I recommend removing.

Your own test demonstrates that the cPanel execution environment cannot resolve `buzzjuice.net`, while the local PC can. The current `wow-pgb_init.php` also explicitly performs a cURL request to the WooCommerce `/wc/v3/orders` endpoint. 

The new architecture becomes:

```text
                  BUZZJUICE PAYMENT GATEWAY v13

┌───────────────────────┐
│ Streams / WoWonder    │

└───────────┬───────────┘
```

# 2. Why I changed the GitHub v12 proposal

The GitHub response correctly identified:

* WooCommerce should be the payment-state authority.
* REST/cURL should be removed from the Streams payment path.
* Orders should exist durably before redirects.
* HMAC should protect the browser handoff.
* processing should be idempotent.
* WooCommerce hooks should drive post-payment fulfillment.
* functionality should be split into addons. 

However, I found several things that should **not** be carried forward unchanged.

### A. No REST endpoint is needed

The GitHub version still creates:

```text
/wp-json/bzj-pgb/v1/checkout
```

That defeats part of the purpose of eliminating the API dependency.

The improved v13 instead uses:

```text
https://buzzjuice.net/pgb-checkout/
```

and the MU plugin catches that request with `template_redirect`.

There is therefore:

**no Streams → WordPress HTTP call**
**no WooCommerce REST API call**
**no WooCommerce API key/secret required for the bridge**

---

### B. `register_activation_hook()` should not be used

The GitHub proposal attempted to use:

```php
register_activation_hook(__FILE__, 'bzj_pgb_activate');
```

inside the MU plugin.

That is inappropriate for the requested architecture because this is an MU plugin, not a conventional activated plugin.

The v13 engine instead verifies the schema during WordPress execution using `dbDelta()`.

---

### C. No fallback security secret

The GitHub response included:

```php
fallback-secret-change-this
```

That should not exist in production.

v13 requires:

```text
BZJ_PGB_HANDOFF_SECRET
```

and refuses to process a handoff if the secret is absent.

---

### D. Streams should not create unpaid fulfillment records

The current `wow-pgb_init.php` already creates records such as `Wo_Purchases` and `Wo_UserOrders` during payment initiation. 

That is one contributor to the "dropped order" problem.

v13 separates:

**payment intent**

from

**paid fulfillment**.

So:

```text
Initiation
    ↓
PGB pending ledger
    ↓
WooCommerce order
    ↓
payment
    ↓
Wo_Purchases / Wo_UserOrders / membership / wallet
```

rather than:

```text
button
 ↓
purchase record
 ↓
maybe payment
```

# 6. Streams initiation

The old:

```text
streams/assets/wow-pgb/wow-pgb_init.php
```

is replaced by a very small delegator.

It now loads:

```text
/shared/payment-gateway/pgb-client-streams.php
```

The client:

1. authenticates the WoWonder session;
2. obtains the WoWonder user;
3. resolves the linked WordPress user;
4. validates amount/product/type/currency;
5. creates `wow_order_id`;
6. creates a cryptographically random nonce;
7. writes the complete order payload to the WordPress database;
8. verifies the inserted row;
9. generates an HMAC-SHA256 signature;
10. returns the browser redirect.

The handoff resembles:

```text
/pgb-checkout/
    ?pgb_order_id=wow_202609281400_xxxxx
    &ts=...
    &nonce=...
    &sig=...
```

No order details or price are trusted from that URL.

# 7. Why the signed handoff is important

The browser can technically modify:

```text
amount
product
user
order ID
```

if those values are placed directly into a URL.

Therefore v13 puts the authoritative payload in the database.

The URL contains only:

```text
order identifier
timestamp
nonce
signature
```

and the signature is:

```text
HMAC-SHA256(
    wow_order_id | timestamp | nonce,
    BZJ_PGB_HANDOFF_SECRET
)
```

WordPress independently recomputes the signature.

So changing:

```text
wow_order_id
```

or:

```text
timestamp
```

or:

```text
nonce
```

invalidates the handoff.

The GitHub proposal correctly identified signed handoffs as an important security improvement.

## 1. The most important architectural correction

Your proposed direction is correct, but I would make one important refinement:

> **Do not replace the failing server-to-server WooCommerce REST request with another server-to-server REST endpoint.**

The browser should perform the handoff to WordPress.

The durable flow should be:

```text
Buzzjuice Streams
      │
      │ User presses Pay
      ▼
pgb-client-streams.php
      │
      ├── validates authenticated Streams user
      ├── determines authoritative product/amount/currency
      ├── writes Wo_Payment_Transactions
      └── creates HMAC-signed handoff
      │
      ▼
Browser redirect
https://buzzjuice.net/pgb-checkout/?wow_order_id=...&sig=...
      │
      ▼
bzj-payment-gateway.php
      │
      ├── verifies HMAC
      ├── verifies nonce/expiry
      ├── retrieves the stored transaction
      └── creates WC_Order natively
      │
      ▼
WC_Order
      │
      ▼
$order->get_checkout_payment_url(false)
      │
      ▼
WooCommerce /checkout/order-pay/...
      │
      ▼
Customer pays
      │
      ▼
woocommerce_payment_complete
      │
      ├── WoWonder fulfillment
      ├── AffiliateWP
      ├── Subscriptions
      ├── Currency/integration logic
      └── Jewel integration
```

This follows the key recommendation in the previous analysis: WooCommerce itself should generate the payment URL instead of the Streams bridge trying to manufacture or obtain a `payment_url` through REST. 

### Why this is better

Your cPanel test:

```text
curl: (6) Could not resolve host: buzzjuice.net
```

is a strong indication that **the cPanel PHP process cannot reliably resolve the public hostname**.

The important distinction is that this doesn't prove WooCommerce itself is inaccessible. Your browser can clearly reach `https://buzzjuice.net`, as demonstrated by the 200 response. But it does mean the existing architecture is unnecessarily dependent on a network path that is failing.

The new design removes that dependency.

---

# 2. There is also a problem with the existing WooCommerce API assumption

The current `wow-pgb_init.php` constructs:

```text
.../wc/v3/orders
```

and expects the response to contain:

```php
$order['payment_url']
```

The WooCommerce source does **not** define `payment_url` as a `WC_Order` property.

Instead, the native order object has:

```php
$order->get_checkout_payment_url(false)
```

and WooCommerce constructs that URL using its checkout endpoint and order key. The current repository's `WC_Order` implementation explicitly does this at `get_checkout_payment_url()`. 

So the correct native mechanism is:

```php
$checkout_url = $order->get_checkout_payment_url(false);
```

not:

```php
$order['payment_url']
```

This is one of the most important corrections to the old bridge.

---

# 3. The Store API `redirect_url` should not be used for this

The proposal refers to the WooCommerce Store API's:

```json
"payment_result": {
    "redirect_url": "..."
}
```

That field is associated with **checkout/payment processing**, not simply creating an order and asking WooCommerce for an order-pay URL.

The current `CheckoutSchema.php` describes `payment_result.redirect_url` as a URL to redirect the customer **after checkout**, potentially to a payment processor. 

Therefore I would **not** build the new bridge around:

```text
POST /wc/store/v1/checkout
        ↓
redirect_url
```

or:

```text
POST /wc/v3/orders
        ↓
payment_url
```

The native PHP route is cleaner:

```php
$order = wc_create_order(...);

...

$checkout_url = $order->get_checkout_payment_url(false);
```

# 4. The GitHub v12 response contained several good ideas — but also things I would correct

The GitHub response's architectural principles are sound:

* database-first transaction
* signed handoff
* native `WC_Order`
* modular addons
* component logging
* WooCommerce payment lifecycle
* AffiliateWP retained
* removal of the old webhook
* no premature fulfillment

Those are all incorporated conceptually in v13. 

However, I would **not deploy the GitHub v12 implementation unchanged**.

### Problem 1 — it still uses a WordPress REST endpoint

The proposed v12 route was:

```text
/wp-json/bzj-pgb/v1/checkout
```

and registered a REST route. 

That isn't necessary.

The customer is already navigating to WordPress. A normal WordPress request can be intercepted by the MU plugin using `template_redirect`.

The v13 package therefore uses:

```text
/pgb-checkout/
```

instead.

---

### Problem 2 — the REST permission callback is inappropriate for the handoff

The GitHub implementation proposed:

```php
'permission_callback' => function() {
    return current_user_can('manage_woocommerce')
        || wp_verify_nonce($_GET['nonce'] ?? '', 'pgb_checkout_nonce');
}
```

That creates a conceptual problem.

The customer coming from Streams isn't a logged-in WordPress administrator and does not possess a WordPress nonce generated by the WordPress session.

The authentication mechanism should instead be the **server-generated HMAC handoff**.

The v13 signature covers:

```text
wow_order_id
wow_user_id
timestamp
nonce
```

and is verified by:

```php
hash_hmac('sha256', ...)
```

with `hash_equals()`.

---

### Problem 3 — MU-plugin activation hooks

The GitHub proposal uses:

```php
register_activation_hook(__FILE__, ...)
```

for the MU plugin.

That is not the right lifecycle mechanism for a must-use plugin.

MU plugins aren't activated/deactivated through the normal Plugins screen.

The v13 bootstrap therefore checks/creates the bridge table during WordPress initialization using a schema-version guard.

# 7. `pgb-client-streams.php`

This is now responsible for the Streams side only.

It:

1. verifies the Streams session;
2. resolves the WoWonder user;
3. resolves the mapped WordPress user ID;
4. validates the amount;
5. validates currency;
6. resolves the WooCommerce product;
7. creates the durable `wow_...` transaction ID;
8. stores the transaction in `Wo_Payment_Transactions`;
9. captures the AffiliateWP context where available;
10. creates a cryptographic nonce;
11. signs the handoff;
12. returns a browser redirect URL.

It does **not** call:

```text
wp-json/wc/v3/orders
```

anymore.

That is the key reliability improvement.

# 8. The new WordPress transaction table

The v13 MU engine creates:

```text
wp_bzj_pgb_orders
```

with:

```text
id
wow_order_id
wow_user_id
wp_user_id
woo_order_id
nonce
status
order_payload
error_message
created_at
updated_at
```

This table is deliberately separate from `Wo_Payment_Transactions`.

The distinction is important.

### WoWonder transaction

```text
Wo_Payment_Transactions
```

is the Streams-side payment ledger.

### PGB transaction

```text
wp_bzj_pgb_orders
```

is the bridge's orchestration ledger.

### WooCommerce order

```text
WC_Order
```

is the authoritative payment/order object.

This gives us:

```text
Streams transaction
        │
        │ wow_order_id
        ▼
PGB transaction
        │
        │ woo_order_id
        ▼
WooCommerce order
```

That makes dropped-browser-redirect and retry scenarios much easier to recover.

The previous response correctly emphasized that a browser redirect cannot itself be the transaction ledger.

# 9. Idempotency is particularly important

Suppose the user taps Pay and gets:

```text
wow_abc123
```

Then the browser:

```text
/pgb-checkout/?wow_order_id=wow_abc123...
```

is loaded twice.

The bridge should **not create two WooCommerce orders**.

Instead:

```text
wow_abc123
       │
       ▼
wp_bzj_pgb_orders
       │
       ├── woo_order_id = 0
       │       → create order
       │
       └── woo_order_id = 146
               → reuse order 146
```

That is why the bridge stores the WooCommerce order ID.

# 36. The biggest improvement to the failure model

The old flow was essentially:

```text
Streams
 ↓
insert transaction
 ↓
cURL WooCommerce
 ↓
if successful → redirect
```

A cURL/DNS failure could leave an ambiguous transaction.

The new flow is:

```text
Streams
 ↓
transaction = initiated
 ↓
signed handoff
 ↓
WordPress
 ↓
Woo order = created
 ↓
checkout_ready
 ↓
customer pays
 ↓
payment_complete
 ↓
paid
 ↓
fulfillment
```

So each stage is recoverable.

That is the durable state machine that the previous response recommended.

## Bottom line

The architecture I recommend is:

**Streams is the transaction initiator.**

**WooCommerce/WordPress is the payment authority.**

**The browser is the transport between them.**

**The HMAC-signed handoff authenticates the browser transition.**

**The PGB table provides durable bridge state.**

**`WC_Order` provides the actual WooCommerce order.**

**`$order->get_checkout_payment_url(false)` generates the payment URL.**

**`woocommerce_payment_complete` is the fulfillment trigger.**

**AffiliateWP remains based on your already-working logic rather than being rewritten blindly.**
