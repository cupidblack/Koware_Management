# Buzzjuice Streams Payment Gateway Bridge — Refactoring Assessment

I reviewed the current Streams bridge, `wow-pgb_init.php`, `requests.php`, payment-settings UI, the current `wow-pgb_sync.php`, AffiliateWP implementation, webhook, the v5.1 material, GitHub's v5.2 recommendations, and the resulting production logs.

The **overall direction of the proposal is correct**, but I would **not deploy the v5.1/v5.2 implementation as supplied**. There are several architectural and implementation problems that need to be corrected first.

The most important conclusion is:

> **The next version should be a transaction-oriented payment orchestration system, not another large replacement `wow-pgb_sync.php`.**

WooCommerce should be authoritative for payment state, while the PGB ledger provides durable bridge state and idempotency. Streams should initiate an intent and receive a payment URL; it should not decide that a purchase has been paid.

---

# 1. What the current system is doing wrong

The current `wow-pgb_init.php` is doing considerably more than payment initiation.

It:

* creates a `Wo_Payment_Transactions` row;
* creates `Wo_UserOrders`;
* creates notifications;
* determines product/sale information;
* constructs WooCommerce REST data;
* handles subscriptions;
* handles WooCommerce credentials;
* captures AffiliateWP context;
* communicates directly with WooCommerce;
* redirects the browser.

For example, the existing code writes `Wo_Payment_Transactions` before payment has happened. 

More seriously, for marketplace purchases it can create `Wo_UserOrders` and notifications before payment is confirmed. 

That creates this failure mode:

```text
User clicks Pay
      ↓
Streams creates purchase/order records
      ↓
WooCommerce order created
      ↓
User abandons checkout
      ↓
Streams already contains "purchase" information
```

That is exactly what we should eliminate.

# 5. The transaction ledger

The proposed table should be:

```text
wp_bzj_pgb_transactions
```

with the core relationship:

```text
Streams payment intent
        │
        ├── request_id
        ├── wow_order_id
        │
        ▼
PGB transaction
        │
        ▼
WooCommerce order_id
```

And the state machine should be:

```text
initiated
    ↓
order_created
    ↓
paid
    ↓
fulfilling
    ├──→ fulfillment_failed
    │
    ↓
fulfilled
```

This is what allows us to recover from:

* browser closure;
* network failure;
* webhook failure;
* PHP timeout;
* duplicate WooCommerce hooks;
* duplicate AJAX requests;
* duplicate callbacks;
* AffiliateWP retry;
* Streams database failure.

# 8. WooCommerce Subscriptions needs another correction

The existing implementation creates subscriptions through a WooCommerce REST request from WordPress back into the same WordPress installation. 

That should go.

The architecture should use native Subscriptions functionality wherever possible.

WooCommerce explicitly exposes subscription lifecycle hooks including:

```text
woocommerce_subscription_payment_complete
woocommerce_subscription_renewal_payment_complete
woocommerce_subscription_status_active
woocommerce_subscription_status_cancelled
woocommerce_subscription_status_expired
```

and related lifecycle actions. ([WooCommerce][1])

The Subscriptions documentation also specifically describes the native subscription objects and APIs. ([WooCommerce][2])

### Important distinction

A normal WooCommerce order containing a subscription product does **not automatically mean we can simply manufacture a subscription after payment**.

The preferred architecture is:

```text
WooCommerce subscription product
        ↓
WooCommerce checkout/order
        ↓
Subscriptions creates subscription
        ↓
payment confirmed
        ↓
subscription activated
```

rather than:

```text
PGB
 ↓
normal order
 ↓
PGB manually constructs subscription
```

If the existing Streams bridge absolutely requires programmatically creating subscriptions, we can use the native Subscriptions API, but that should be a dedicated addon and not a REST API round-trip.

# 16. HMAC authentication

The request should be:

```http
POST /wp-json/bzj-pgb/v1/order
```

with:

```text
X-BZJ-PGB-Timestamp
X-BZJ-PGB-Request-ID
X-BZJ-PGB-Signature
```

Signature:

```text
HMAC-SHA256(
    timestamp
    + "\n"
    + request_id
    + "\n"
    + raw_json_body,
    BZJ_PGB_SECRET
)
```

The secret should exist only in the server environment.

Not:

```text
Streams configuration
HTML
JavaScript
WooCommerce metadata
logs
browser cookies
```

# 17. Idempotency needs to be stronger than v5.2

The GitHub implementation uses:

```php
set_transient('pgb_req_' . $request_id, ...)
```

That is useful, but I would not make the transient the primary transaction mechanism.

Instead:

```text
request_id UNIQUE
wow_order_id UNIQUE
woo_order_id indexed
```

inside:

```text
wp_bzj_pgb_transactions
```

This means that even if:

```text
PHP restarts
Redis disappears
transient expires
```

the payment transaction remains protected.

A repeated request should ideally return the existing WooCommerce order rather than merely:

```text
409 duplicate
```

because a client retry should be recoverable.
