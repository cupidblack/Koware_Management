## Executive assessment

The proposed architecture is **the right direction**, and the GitHub review correctly identified the deeper problem: the existing bridge is not merely too large; payment state is spread across Streams, WooCommerce REST calls, the WooCommerce thank-you page, and the standalone webhook. That makes a successful payment dependent on several independent execution paths. 

I would therefore move Buzzjuice to this model:

```text
                 BUZZJUICE STREAMS
                       │
                       │ HMAC-authenticated request
                       ▼
        ┌──────────────────────────────┐
        │ WordPress MU Plugin          │
        │ Buzzjuice Payment Gateway    │
        │ Bridge / Engine              │
        └──────────────────────────────┘
             │          │          │
             │          │          └── Addons
             │          │                └─ AffiliateWP
             │          │
             │          └────────────── Integrations
             │                           └─ Jewel
             │
             ▼
        PGB Transaction Ledger
             │
             ▼
        WooCommerce Order
             │
             ▼
        Customer Payment
             │
             ▼
   WooCommerce server-side event
             │
             ▼
        PGB Fulfillment
          │     │     │
          ▼     ▼     ▼
       Streams AffWP Jewel
```

The browser is then only responsible for **starting payment and redirecting the customer**. It is no longer responsible for proving that payment succeeded.

# 1. What I found in the existing implementation

There are several concrete weaknesses in the current bridge.

### A. `wow-pgb_init.php` is doing too much

The current Streams initializer:

* creates the WoWonder payment transaction;
* performs product-specific database writes;
* creates marketplace purchase records;
* creates user-order records;
* creates notifications;
* calculates subscription information;
* contains WooCommerce API credentials;
* constructs the WooCommerce order;
* performs cURL;
* disables SSL verification;
* captures AffiliateWP browser/cookie context.

For example, the current code explicitly disables both certificate and hostname verification:

```php
CURLOPT_SSL_VERIFYHOST => 0,
CURLOPT_SSL_VERIFYPEER => 0,
```

That should disappear completely from the new architecture. 

More importantly, the current initializer performs marketplace writes before WooCommerce payment has actually succeeded. 

That is precisely the type of state inconsistency the new transaction ledger should eliminate.

---

### B. The thank-you page is currently part of the payment engine

The old `wow-pgb_sync.php` attaches fulfillment/redirect behaviour to:

```php
add_action('wp_footer', ...)
```

and then checks whether the customer has reached `order-received`. ([GitHub][1])

That creates the failure path:

```text
Payment succeeds
      ↓
WooCommerce marks order paid
      ↓
Customer closes browser
      ↓
WooCommerce thank-you page never loads
      ↓
old fulfillment never executes
```

The new architecture instead uses WooCommerce's server-side payment lifecycle. This was correctly identified in both the previous ChatGPT review and GitHub's review. 

---

### C. The old webhook has a real implementation defect

The existing `wow-pgb_webhook.php` contains:

```php
$stmt->execute();

if (!$stmt->execute()) {
```

so the same database statement is executed twice. 

It also contains a hard-coded WooCommerce webhook secret:

```php
$secret = '...';
```

which should not exist in source code. 

That endpoint should ultimately be retired.

# 2. Important corrections to GitHub's v4 implementation

I would **not deploy GitHub's generated v4 package unchanged**.

The architectural ideas are good, but there are several places where the implementation needs correction.

### Correction 1 — Idempotency must be database-enforced atomically

GitHub's implementation does:

```text
check duplicate
      ↓
no transaction found
      ↓
create Woo order
```

That is vulnerable to two concurrent requests both passing the duplicate check.

The ledger needs:

```text
UNIQUE(idempotency_key)
UNIQUE(request_id)
UNIQUE(pgb_transaction_id)
```

and the insertion must be treated as the atomic gate.

The idempotency key should represent the **logical purchase**, not simply the HTTP request.

I recommend:

```text
SHA256(
    wow_user_id
    |
    wow_order_id
    |
    transaction_type
    |
    wow_post_id
    |
    woo_product_id
    |
    woo_variation_id
    |
    amount
    |
    currency
)
```

The important point is that `wow_order_id` must be generated once by Streams and reused if the HTTP request is retried.

---

### Correction 2 — Do not clamp invalid amounts

GitHub's implementation effectively does:

```php
$amount = max($min_limit, min($amount, $max_limit));
```

That means:

```text
Requested GH¢0.50
       ↓
Minimum GH¢1
       ↓
Order becomes GH¢1
```

That is undesirable.

The correct behaviour is:

```text
amount < minimum → reject
amount > maximum → reject
```

The customer should never silently receive a financially different order.

---

### Correction 3 — AffiliateWP cannot rely on browser context

This is particularly important given your note.

GitHub's compact AffiliateWP addon still contains:

```php
affwp_get_affiliate_id()
```

as an affiliate-resolution mechanism. That is not sufficient for your architecture because the fulfillment request is now server-side.

Your existing AffiliateWP implementation is substantially more sophisticated. It already handles:

* AffiliateWP customer resolution;
* lifetime customers;
* customer metadata;
* affiliate resolution;
* product-specific rates;
* default rates;
* duplicate detection;
* referral creation;
* accounting verification;
* fallback accounting;
* processed markers. 

That working logic should therefore be **moved**, not replaced with a simplified AffiliateWP implementation.

The new location should be:

```text
shared/payment-gateway/addons/
└── pgb-addon-affiliate-wp.php
```

but its substantive logic should remain equivalent to the currently working implementation.

# 5. New status model

I recommend keeping the payment and fulfillment states separate.

### Payment

```text
pending
paid
failed
```

### Fulfillment

```text
pending
processing
retry
completed
failed
```

Therefore:

```text
PGB created
   │
   ▼
payment=pending
fulfillment=pending
   │
   │ customer pays
   ▼
payment=paid
fulfillment=processing
   │
   ├── Streams succeeds
   ├── AffiliateWP succeeds
   └── Jewel succeeds
             │
             ▼
       fulfillment=completed
```

If something downstream fails:

```text
payment=paid
fulfillment=retry
       │
       ▼
     retry
       │
       ├── success → completed
       │
       └── retry limit → failed
```

This is much more durable than making one WooCommerce order status represent everything.

# 8. Streams → WordPress authentication

The new request should be:

```http
POST /wp-json/bzj-pgb/v1/order

X-BZJ-PGB-Timestamp: 177...
X-BZJ-PGB-Request-ID: pgb_...
X-BZJ-PGB-Signature: ...
Content-Type: application/json
```

Signature:

```text
HMAC-SHA256(
    timestamp
    + "\n"
    + request_id
    + "\n"
    + raw_request_body,
    BZJ_PGB_SECRET
)
```

This improves on the current arrangement because Streams no longer needs WooCommerce consumer credentials.

The earlier architecture review correctly identified that those credentials can be retired from Streams.

# 10. WooCommerce subscriptions

This is one area where I would **not blindly transplant GitHub's implementation**.

The existing bridge manually creates subscriptions through the WooCommerce API. The previous review correctly identified this as something that needs to be reconciled with the actual installed WooCommerce Subscriptions lifecycle. 

The new bridge should **not** have two competing subscription engines:

```text
PGB
  └── manually creates subscription

WooCommerce Subscriptions
  └── creates subscription
```

That can result in duplicate subscriptions.

Instead:

```text
PGB
 ↓
WooCommerce order
 ↓
WooCommerce payment
 ↓
WooCommerce Subscriptions lifecycle
 ↓
subscription
```

The exact subscription creation mechanism needs to be validated against the installed version before the old manual subscription code is removed.

This is one of the two areas I would specifically regression-test before declaring the migration complete.

# 11. Jewel Affiliate

The same principle applies to Jewel.

The correct architecture is:

```text
WooCommerce paid
       ↓
PGB fulfillment
       ↓
pgb-int-jewel-affiliate.php
       ↓
Jewel business logic
```

not:

```text
WooCommerce
   ↓
Jewel webhook
   ↓
another payment engine
```

The previous review correctly identified that the existing Jewel implementation contains more business logic than the compact GitHub replacement. 

Therefore the existing:

```text
streams/jewel-affiliate-webhook.php
```

should be treated as the **migration specification**.

Its:

* rebate calculations;
* role changes;
* subscription mapping;
* existing-user behaviour;
* Streams database changes;
* idempotency;
* webhook-specific conditions

need to be migrated function-for-function into:

```text
shared/payment-gateway/integrations/
pgb-int-jewel-affiliate.php
```

before the old endpoint is retired.

```text

```

```text
one logical purchase
        =
one PGB transaction
        =
```

# 15. Final target

Once migration is complete, the old architecture:

```text
Streams
  ↓
Woo REST
  ↓
Woo
  ↓
thank-you page
  ↓
wow-pgb_sync
  ↓
webhook
  ↓
Jewel webhook
```

becomes:

```text
                     ┌───────────────┐
                     │    Streams    │
                     └───────┬───────┘
                             │
                       HMAC request
                             │
                             ▼
                  ┌────────────────────┐
                  │ PGB MU Plugin      │
                  │                    │
                  │ Transaction Ledger │
                  │ Idempotency        │
                  │ Woo Order          │
                  └─────────┬──────────┘
                            │
                            ▼
                       WooCommerce
                            │
                       payment event
                            │
                            ▼
                  ┌────────────────────┐
                  │ PGB Fulfillment    │
                  └─────────┬──────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
          Streams       AffiliateWP       Jewel
```

That gives Buzzjuice a much stronger long-term monetization architecture: **one authoritative payment event, one durable transaction record, one idempotent fulfillment engine, and multiple independent fulfillment consumers.** This is also the architectural pattern that can later support Buzzjuice courses, Socials, wallet services, affiliate products and other monetization systems without creating another payment bridge. 

**The next implementation step should be the exact migration of the existing `wow-pgb_sync.php` AffiliateWP block and the complete `jewel-affiliate-webhook.php` business logic into the new addon/integration files, followed by the WooCommerce Subscriptions lifecycle check.** That is the point where the v4.2 core package becomes a true production replacement rather than merely a structurally correct payment engine.
