I reviewed the current repository implementation, the supplied previous design response, and the relevant WooCommerce integration guidance. The previous response was directionally strong, but I would make several important changes before treating it as the final architecture.

### What the current code reveals

The current bridge has **multiple completion paths**: WooCommerce order status/thank-you processing, `wow-pgb_sync.php`, and `wow-pgb_webhook.php`. That creates race conditions and makes a successful payment dependent on which execution path happens to run first. The existing thank-you/`wp_footer` mechanism is particularly unsuitable as a payment-completion authority. 

There is also a genuine **duplicate-order risk**. `wow-pgb_init.php` generates a new `uniqid('wow_')` and directly POSTs a new WooCommerce order. If WooCommerce creates the order but the response is lost, a retry can create another order because there is no durable idempotency key at the WooCommerce creation boundary. 

The client currently accepts financial values such as `amount` and `product_price` from the Streams request. Those must become server-authoritative values. The new system should receive an intent and calculate/validate the actual payable amount against WooCommerce/Streams data. 

There are also implementation defects worth eliminating during the migration, including the literal `'null'` being used as a variation ID and SSL verification being disabled in the Streams cURL client. 

Most importantly, the current repository exposes a WooCommerce webhook secret directly in `wow-pgb_webhook.php`. That secret should be **rotated immediately**, independently of the refactor. 

WooCommerce itself provides a payment-completion lifecycle and recommends using `payment_complete()` for successful payments; its webhook system provides HMAC signatures but webhook delivery itself is background/retry-based and can become disabled after repeated failures. Therefore, the webhook should be an **event/recovery channel**, not the sole payment processor. ([The WooCommerce Developer Blog][1])

The existing AffiliateWP implementation is worth preserving. Its duplicate-referral checks, multi-source affiliate resolution, accounting verification and fallback logic are substantially more mature than the rest of the bridge. 

With those findings incorporated, this is the architecture I recommend as the **final updated proposal**.

# Buzzjuice Streams Payment Gateway Bridge v2

## Final Refactored Architecture & Implementation Proposal

### 1. Executive Decision

The existing Buzzjuice Streams Payment Gateway Bridge should be **refactored rather than merely moved**.

The new bridge should become a small, durable payment-orchestration system with:

* Buzzjuice WordPress as the authoritative integration platform.
* WooCommerce as the payment/order authority.
* A dedicated PGB transaction record for orchestration and recovery.
* Buzzjuice Streams as the originating application and WoWonder business ledger.
* One authoritative fulfilment processor.
* AffiliateWP as the affiliate authority.
* Jewel Affiliate as a PGB addon/integration.
* Webhooks as secondary event/recovery inputs.
* Browser redirects as presentation only.
* Idempotency at every payment boundary.
* Automatic and manual recovery.
* Structured, toggleable logging.
* Modular transaction handlers.
* Compatibility wrappers during migration.

The central rule is:

> **A payment must never depend on the customer's browser remaining open, the WooCommerce thank-you page loading, or a single webhook succeeding.**

The payment system must be able to complete correctly even if:

* the customer closes the browser;
* Streams times out;
* the WooCommerce API response is lost;
* the webhook is delayed;
* the webhook arrives twice;
* a downstream Streams operation temporarily fails;
* AffiliateWP temporarily fails;
* the customer retries the initiation request;
* WordPress receives the same completion event more than once.

# 5. Important Modification to the Previous Proposal

The previous proposal considered extending `Wo_Payment_Transactions` as the primary durable state.

For the new implementation, I recommend a stronger separation:

```text
WordPress PGB transaction
        ↓
orchestration state
        ↓
WooCommerce order
        ↓
Streams transaction
        ↓
Streams fulfilment
```

Create a dedicated WordPress table:

```text
wp_bzj_pgb_transactions
```

rather than making the WoWonder table responsible for the complete orchestration state.

This is preferable because the WordPress platform is authoritative and already hosts WooCommerce, AffiliateWP and the MU plugin.

The WoWonder table remains an important business ledger and compatibility record.

# 8. Idempotency

This is one of the most important upgrades.

The bridge must guarantee:

```text
ONE PGB transaction
        ↓
maximum ONE WooCommerce order
```

```text
ONE paid PGB transaction
        ↓
maximum ONE Streams fulfilment
```

```text
ONE WooCommerce order
        ↓
maximum ONE AffiliateWP referral
```

```text
ONE PGB transaction
        ↓
maximum ONE wallet credit
```

```text
ONE PGB transaction
        ↓
maximum ONE entitlement activation/update
```

The idempotency key should be generated before WooCommerce order creation.

The WordPress side must check:

```text
Does PGB transaction exist?
Does WooCommerce order already reference it?
Does the WooCommerce order already exist for wow_order_id?
```

before creating another order.

This specifically protects against:

```text
POST
 ↓
Woo creates order #500
 ↓
response lost
 ↓
client sees timeout
 ↓
retry
 ↓
WITHOUT idempotency → order #501
```

The new architecture instead returns:

```text
existing transaction
existing WooCommerce order #500
existing payment URL
```

# 17. PGB Processor

Conceptually:

```php
process_order($woo_order_id)
{
    load WooCommerce order;

    identify PGB transaction;

    acquire transaction lock;

    if already completed:
        return success;

    verify payment;

    verify amount;

    verify currency;

    verify customer;

    verify transaction integrity;

    mark payment_received/processing;

    process transaction handler;

    process addons;

    update Streams ledger;

    process AffiliateWP;

    process Jewel/Future addons;

    mark final state;

    create redirect instruction;

    release lock;
}
```

The important principle is that **payment verification happens before fulfilment**.

Before processing:

```text
acquire PGB transaction lock
```

The lock can use a WordPress/MySQL-safe mechanism.

The objective is:

```text
Webhook
       \
        → processor
       /
Payment hook
```

without both executions simultaneously crediting the customer.

The lock must have an expiry so a crashed PHP request does not permanently block a transaction.

# 32. Webhook

Retain a dedicated PGB webhook endpoint.

However:

```text
Webhook
   ↓
verify HMAC
   ↓
identify WooCommerce order
   ↓
identify PGB transaction
   ↓
queue/process PGB transaction
   ↓
return 2xx
```

The webhook should not perform a giant chain of fulfilment operations before returning.

This reduces the probability of WooCommerce disabling the webhook because of repeated long-running failures.

WooCommerce supports signed webhook requests and records webhook delivery information, making the webhook valuable as an additional event source and diagnostic mechanism. ([The WooCommerce Developer Blog][1])

# 56. Non-Negotiable Design Rules

The new bridge should enforce these rules:

### Rule 1

**No payment fulfilment from browser requests.**

### Rule 2

**No payment fulfilment from the WooCommerce thank-you page.**

### Rule 3

**No direct WooCommerce credentials in Streams.**

### Rule 4

**No trusting browser-supplied price or amount.**

### Rule 5

**No duplicate order creation for one PGB transaction.**

### Rule 6

**No duplicate wallet/pro/referral/Jewel fulfilment.**

### Rule 7

**Webhook is an event source, not the payment authority.**

### Rule 8

**AffiliateWP failure must not destroy successful customer fulfilment.**

### Rule 9

**Every recoverable operation must be retryable.**

### Rule 10

**Every retry must be idempotent.**

### Rule 11

**Every payment must have a permanent correlation chain.**

```text
pgb_transaction_id
      ↓
wow_order_id
      ↓
woo_order_id
```

### Rule 12

**Secrets never belong in browser code, Streams client code, logs, or Git.**

# 57. Final Recommended Architecture

The completed Buzzjuice Payment Gateway Bridge should therefore be:

```text
                    ┌───────────────────┐
                    │ Buzzjuice Streams │
                    └─────────┬─────────┘
                              │
                              ▼
                    PGB Streams Client
                              │
                              ▼
                       Signed PGB API
                              │
                              ▼
                 ┌────────────────────────┐
                 │ WordPress MU PGB       │
                 │                        │
                 │ Transaction Authority  │
                 │ Order Orchestrator     │
                 │ State Machine          │
                 │ Idempotency            │
                 │ Recovery               │
                 │ Locking                │
                 └───────────┬────────────┘
                             │
                ┌────────────┼────────────┐
                ▼            ▼            ▼
          PGB Database   WooCommerce    Addons
                             │            │
                             ▼            ├─ AffiliateWP
                          PAYMENT         ├─ Jewel
                             │            ├─ Currency
                 ┌───────────┴────────┐   └─ Future
                 ▼                    ▼
          payment_complete         webhook
                 │                    │
                 └──────────┬─────────┘
                            ▼
                     PGB Processor
                            │
                 ┌──────────┼──────────┐
                 ▼          ▼          ▼
              Streams   AffiliateWP   Addons
              fulfilment   reward
                 │          │
                 └────┬─────┘
                      ▼
                   COMPLETED
                      │
                      ▼
                Redirect/status
```

This is the architecture I would use for **Buzzjuice Streams Payment Gateway Bridge v2**.

It preserves the working parts of the current system, particularly the AffiliateWP implementation, while removing the structural causes of dropped orders: fragmented completion paths, lack of idempotency, browser-dependent processing, duplicated PGB logic, client-authoritative financial values, and direct WooCommerce access from Streams.

Most importantly, it gives Buzzjuice a reusable **payment platform**, rather than another WoWonder-specific payment script. That makes future integrations—Socials, WordPress services, Jewel Affiliate, courses, subscriptions, marketplace purchases and other Buzzjuice services—able to use the same payment orchestration layer.

### One immediate action before any refactor

Because the current public `wow-pgb_webhook.php` contains a real-looking webhook secret, **rotate that WooCommerce webhook secret now**, then configure the new secret through the secure configuration layer. Do not carry the existing secret into v2. 

The other architectural decision I would lock in before writing the implementation is **the dedicated `wp_bzj_pgb_transactions` table**. It gives the MU plugin a proper durable state machine without forcing the WoWonder schema to become the orchestration database, while `Wo_Payment_Transactions` remains the Streams business/financial ledger.

The next implementation step should therefore be **Phase 1 + Phase 2 together: define the exact PGB transaction schema/API contract and build the MU-plugin/core/client skeleton before touching the existing fulfilment logic**. This gives us a stable contract into which the existing PRO, wallet, market, donation, AffiliateWP and Jewel code can be migrated one component at a time.
