# 15. Directional blocks are important

The canonical record deliberately stores:

```text
block_a_to_b
block_b_to_a
```

rather than:

```text
blocked = yes
```

This means:

```text
A blocks B
```

is different from:

```text
B blocks A
```

That is the correct model.

For example:

```text
A → B = blocked
B → A = not blocked
```

Unblocking A→B does **not** automatically unblock B→A.

And more importantly:

```text
Block
 ↓
Remove connection
 ↓
Unblock
 ↓
Still NOT connected
```

The users must establish a new connection.

That prevents a potentially serious moderation loophole.

# 17. The canonical state machine

The resulting system has three relationship states:

```text
NONE
 │
 │ request
 ▼
REQUESTED
 │
 │ accept
 ▼
CONNECTED
```

And:

```text
REQUESTED ──remove──► NONE
CONNECTED ──remove──► NONE
CONNECTED ──block───► NONE + BLOCK
REQUESTED ──block───► NONE + BLOCK
BLOCK ──────unblock─► NONE
```

There is **no automatic**:

```text

```

# 18. Why the reconciliation layer is essential

Suppose:

```text
Socials
A follows B
```

The Socials database succeeds.

Then:

```text
Internet timeout
```

before the report reaches WordPress.

The local Socials action cannot be trusted as canonical.

The system therefore has two protection layers:

### Immediate

The reporter retries:

```text
0 sec
1 sec
3 sec
```

### WordPress durable reconciliation

Once WordPress knows the canonical state, the event queue repeatedly reconciles:

```text
pending
   ↓
retry
   ↓
retry
   ↓
...
   ↓
processed
```

with exponential backoff.

This is significantly more reliable than simply firing a REST request once.
