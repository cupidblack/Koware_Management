## Updated WoWonder Orphan-User Cleaner

I reviewed the supplied `db_helpers.php`, the current WoWonder `functions_one.php`, the supplied `Wo_DeleteUser()` implementation, and both the earlier ChatGPT/GitHub versions. The database helper confirms that `get_wowonder_db()` is the appropriate connection mechanism for the Streams database. ([GitHub][1])

The updated implementation incorporates the useful recommendations from both versions while correcting several issues I found in them.

### Key improvements

1. **Dry-run is the default** — nothing is deleted unless `--execute --yes` is supplied.
2. **`Wo_Users` is never modified.**
3. **Authoritative user-ID snapshot** — existing IDs are copied into an indexed temporary table before scanning.
4. **Confirmed-reference whitelist** — only tables/references demonstrably handled by `Wo_DeleteUser()` can be automatically cleaned. This follows the safer approach in the GitHub version. ([GitHub][2])
5. **Advisory schema discovery** — additional tables containing likely user-reference columns are reported but **never automatically deleted**.
6. **Fixed discovery bug** — the earlier version's `isset($knownTables[$table])` logic could suppress discovery because the table list had already been converted into a lookup array. The new version separates the table list from the confirmed lookup.
7. **Version/table aliases** — accommodates common WoWonder naming differences such as `Wo_Email`/`Wo_Emails`, `Wo_LiveSubscriptions`/`Wo_LiveSub`, etc.
8. **Handles VARCHAR-style user IDs** — uses numeric comparison so older/custom schemas don't require integer column types.
9. **Table-level transactions** — each deletion is committed independently; a failed table is rolled back.
10. **Fresh pre-delete snapshot** — the authoritative `Wo_Users` set is rebuilt immediately before deletion, preventing a user created between the dry run and execution from being incorrectly treated as orphaned.
11. **Post-cleanup verification** — the script rescans the confirmed references and reports anything remaining.
12. **JSON audit report** — preserves the findings, deleted-row counts and verification results.
13. **User-ID targeting** — allows investigating one known deleted user without scanning/deleting unrelated orphan data.
14. **Table targeting** — allows cautious staged cleanup, e.g. only `Wo_Followers`.
15. **No media/S3 deletion** — deliberately separated from database cleanup. This is safer than trying to imitate `Wo_DeleteUser()`'s filesystem cleanup generically.
16. **CLI-only** — prevents accidentally exposing a destructive database utility through the web.

The architecture is therefore:

**`Wo_Users` → authoritative ID set → confirmed reference audit → dry-run report → explicit execution → fresh ID set → deletion → verification**

That is safer than simply issuing a large collection of `DELETE ... NOT EXISTS` queries.

### Particularly useful investigation commands

For a specific deleted user:

```bash
php streams/tools/bzj-orphan-user-cleaner.php --user-id=123
```

For a specific table:

```bash
php streams/tools/bzj-orphan-user-cleaner.php --table=Wo_Followers
```

For broader schema investigation without deleting anything:

```bash
php streams/tools/bzj-orphan-user-cleaner.php --discover-only
```

The latter is important because the supplied `Wo_DeleteUser()` is not necessarily the complete schema definition for every installed WoWonder module.

### Only after reviewing the report

The actual cleanup is:

```bash
php streams/tools/bzj-orphan-user-cleaner.php --execute --yes
```

For additional caution, I would initially execute **one table at a time**, especially:

```bash
php streams/tools/bzj-orphan-user-cleaner.php \
    --table=Wo_Followers \
    --execute \
    --yes
```

Then review the result before progressing to messages, notifications, posts, etc.

## One important architectural point

I would **not** make this an automatic cron job that immediately deletes anything matching a column such as `user_id`.

The GitHub recommendation to distinguish **confirmed references** from **schema-discovered references** is important. The supplied `Wo_DeleteUser()` gives us strong evidence about what WoWonder itself regards as user-owned/dependent data, but a generic column named `user_id` does not necessarily establish the same semantics.

The current script therefore establishes three levels:

| Level                                       | Action                                            |
| ------------------------------------------- | ------------------------------------------------- |
| `Wo_Users`                                  | **Authoritative — never deleted by this utility** |
| Confirmed references from `Wo_DeleteUser()` | **Can be automatically cleaned**                  |
| Newly discovered possible references        | **Report only — human/schema review required**    |

That gives us a good foundation for the next stage: **after this cleanup has been safely run once, we should build a separate integrity-audit report that maps every WoWonder table/foreign-key-like relationship, including `Wo_Posts → comments/replies/reports`, `Wo_Funding → Wo_Funding_Raise`, group/page dependencies, and media references.** That would let Buzzjuice eventually have a repeatable database-integrity maintenance system rather than relying on manual cleanup after direct database deletions.
