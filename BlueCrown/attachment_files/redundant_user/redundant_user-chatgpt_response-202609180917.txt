### What is included

**1. Two-platform orphan scanning**

* WoWonder Streams → `Wo_Users`
* QuickDate Socials → `users`
* Scans the reference tables represented by the supplied deletion functions.
* Only positive numeric IDs that no longer exist in the authoritative user table are treated as confirmed orphan references.
* `NULL`, blank, zero, and non-numeric references are not automatically deleted.
* Authoritative `Wo_Users` / QuickDate `users` records are never deleted.

This follows the GitHub recommendation to treat the platform user tables as authoritative and clean only explicit reference tables. 

**2. Proper dry-run workflow**
The page provides:

1. Start Dry Run
2. Display WoWonder orphan results
3. Display QuickDate orphan results
4. Audit WordPress platform-ID mappings
5. Select mappings to repair
6. Clean confirmed orphan references
7. Display post-operation verification

The destructive operation performs a **new scan immediately before deletion**, rather than trusting the results displayed from an earlier dry run. This was one of the important GitHub recommendations. 

**3. Improved `wo_user_id` / `qd_user_id` alignment**

The mapping scan uses:

```text
WordPress user_login
WordPress user_email
        ↓
WoWonder username/email
QuickDate username/email
```

It then determines the actual platform ID.

A repair is offered only where the identity match is unambiguous. For example:

```text
Platform:       WoWonder
Platform ID:    184
WP Meta Value:  91
Status:         repairable_mismatch
```

The UI provides a checkbox for each repairable mismatch and:

> Select all repairable mismatches

The repair is rescanned immediately before writing, preventing stale checkbox data from changing an identity mapping that may have changed since the dry run. This follows the GitHub implementation's approach.

**5. Duplicate WordPress metadata is handled more safely**

I made an additional improvement over the GitHub version.

Instead of using:

```sql
MAX(CASE ...)
```

to select one `wo_user_id`/`qd_user_id`, the updated version reads all relevant `usermeta` rows.

Therefore, if a WordPress user has conflicting metadata such as:

```text

wo_user_id = 91
```

the cleaner reports:

```text

```

and **does not automatically repair it**.

That is safer than silently choosing one value.

**8. Media is deliberately not deleted**

This is an intentional safety improvement.

The supplied WoWonder and QuickDate deletion functions remove physical media/S3 objects. An orphan-cleaning utility should **not automatically remove those files merely because a database reference has disappeared**, because that can create irreversible collateral deletion.

Therefore this utility:

* deletes redundant database rows;
* does **not** delete local media;
* does **not** delete S3 objects;
* does **not** delete users.

This matches the GitHub safety recommendation.

**10. Transactions where supported**

For transactional/InnoDB tables, the cleaner starts a transaction for each table deletion and commits it only after the DELETE succeeds.

The dry run also identifies the table's storage engine.

### One important architectural decision

I have **not** made the cleaner automatically discover arbitrary tables and delete rows from them simply because they contain a column named `user_id`.

That would be dangerous.

The supplied `Wo_DeleteUser()` function contains platform-specific operations such as:

```text
Wo_DeletePage()
Wo_DeleteGroup()
Wo_DeletePost()
Wo_DeleteEvent()
Wo_DeleteForumThread()
Wo_DeleteThreadReply()
```

Those functions can themselves perform additional cascading cleanup that isn't represented merely by a `user_id` column. The updated cleaner therefore uses the explicit allow-list derived from the deletion functions rather than guessing at arbitrary relationships. The GitHub response likewise recommended keeping schema-discovered references advisory rather than automatically deleting them.
