### What this version does

**1. Safe WordPress-admin access**

* Bootstraps WordPress before doing anything.
* Requires a logged-in administrator.
* Uses the real WordPress table prefix.
* Requires both:

  * WordPress nonce
  * `BZJ_ORPHAN_CLEANER_KEY`
* Explicitly sends `no-cache/no-store` headers. This is an additional correction aimed at the previous **“Invalid security token. Please reload the page.”** problem.
* Does not use PHP sessions for the cleaner's security token.

The GitHub revision specifically identified avoiding session-based security tokens and using WordPress authentication/nonces as important corrections. 

**2. WoWonder orphan scan**

* Treats `Wo_Users.user_id` as authoritative.
* Checks the user-reference fields represented by `Wo_DeleteUser()`.
* Detects positive numeric IDs that no longer exist in `Wo_Users`.
* Shows:

  * table
  * reference column
  * orphan count
  * sample orphan IDs
  * storage engine/transaction status
* `Wo_Users` itself can never be deleted by this utility.

**3. QuickDate orphan scan**

* Treats `users.id` as authoritative.
* Checks the tables/columns represented by `delete_user()`.
* Shows the same orphan information.
* The QuickDate `users` table can never be deleted.

The allow-list approach follows the GitHub recommendation not to blindly delete every column named `user_id`, because such columns can have meanings unrelated to platform-user ownership. 

**4. Handles WoWonder table-name variations**
The cleaner now resolves known WoWonder naming variations such as:

* `Wo_AppSessions` / `Wo_AppsSessions`
* `Wo_EventsInterested` / `Wo_EventsInt`
* `Wo_PagesInvites` / `Wo_PagesInvaites`
* `Wo_LiveSub` / `Wo_LiveSubscriptions`
* `Wo_Email` / `Wo_Emails`
* monetization table variants

Unlike the earlier version, it can inspect **all existing aliases**, rather than arbitrarily selecting only one existing variant.

**5. Additional schema audit**
I added a separate **advisory schema audit**.

It searches for additional potentially user-referencing columns outside the deletion-function allow-list and reports possible orphan rows.

However, these are explicitly **not automatically deleted**. This preserves the GitHub recommendation that schema discovery should be advisory rather than destructive. 

**6. WordPress `wo_user_id` / `qd_user_id` alignment**
The cleaner compares each WordPress user's:

* `wp_users.ID`
* `user_login`
* `user_email`
* `wo_user_id`
* `qd_user_id`

against the authoritative platform records.

For each nonblank mapping it can identify:

* **Aligned**
* **Repairable mismatch**
* **Ambiguous identity**
* **Conflicting identity**
* **Stored ID missing from platform**
* **Stored ID has no identity match**

The matching logic uses the platform's actual username/email, rather than assuming the WordPress metadata value is correct. This follows the GitHub implementation. 

**7. Blank IDs are not treated as errors**

This is important for the Buzzjuice SSO architecture.

If:

```text
wo_user_id = blank
```

or:

```text
qd_user_id = blank
```

the cleaner treats that as an allowed state rather than attempting to manufacture an ID.

The GitHub revision explicitly recommended this behaviour because a blank can simply indicate that the user has not yet logged into the corresponding platform. 

**8. Individual repair checkboxes**

Every **repairable** mismatch gets its own checkbox.

There is also:

> **Select all repairable mismatches**

Only selected rows are submitted.

Ambiguous/conflicting rows cannot be selected.

The GitHub revision specifically added this functionality. 

**9. Repair always rescans first**

The submitted checkbox list is not trusted as proof that the mapping is still repairable.

Before changing WordPress metadata, the cleaner performs a fresh mapping scan and only repairs rows that are still unambiguously repairable.

This protects against the database changing between the displayed dry run and the repair operation. 

**10. Duplicate WordPress metadata rows are handled**

When repairing a mapping, the cleaner updates all existing rows for that:

```text
user_id + meta_key
```

combination rather than updating only one row.

If the metadata key doesn't exist, it inserts it.

The update is performed inside a transaction. 

**11. Orphan cleanup also rescans immediately before deletion**

The displayed dry-run result is never blindly used as the deletion instruction.

When the administrator presses:

> **Clean Confirmed Orphans**

the utility performs a fresh scan against the live databases and rebuilds the deletion conditions from the current schema.

This is one of the more important safety corrections in the GitHub revision. 

**12. Transaction support**

For InnoDB tables, each table's cleanup is performed transactionally.

If a deletion fails, the transaction is rolled back and the failure is reported.

Non-transactional tables are identified in the results so the administrator knows the deletion could not have the same rollback guarantee.

**13. Media is deliberately untouched**

The original deletion functions delete avatars, covers, post files, chat media, S3 objects, etc.

This cleaner **does not do that**.

That is intentional.

An orphan database reference does not by itself prove that a physical file is safe to remove. The GitHub recommendation was therefore to keep this utility focused on database orphan cleanup and leave media/S3 deletion out. 

**14. Existing `bzj_log()` is reused**

The file does **not** redeclare `bzj_log()`.

It checks whether the existing function is available and logs through it; otherwise it falls back to PHP's `error_log()`.

That is compatible with the existing registration kernel arrangement you specified.

**15. Results and verification**

After a cleanup or repair, the UI shows:

* operation results
* number of deleted rows
* metadata changes
* failures
* post-operation orphan scan
* post-operation schema audit
* post-operation platform-ID alignment

So the administrator can immediately see whether the operation actually resolved the detected problems.

### Important distinction

I intentionally did **not** make this equivalent to:

> “Find every database table containing `user_id` and delete anything whose ID isn't in `Wo_Users`.”

That would be substantially more dangerous.

Instead, the implementation has three layers:

```text
AUTHORITATIVE
    │
    ├── Wo_Users
    └── QuickDate users
          │
          ▼
CONFIRMED CLEANUP
    │
    └── Tables/fields derived from Wo_DeleteUser()
        and QuickDate delete_user()
          │
          ▼
ADVISORY SCHEMA AUDIT
    │
    └── Other possible user references
        (reported only, never automatically deleted)
```

That follows the strongest recommendation from the GitHub review: **use an explicit deletion allow-list for automatic cleanup and treat schema discovery as advisory.**
