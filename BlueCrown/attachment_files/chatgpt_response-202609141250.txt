## Executive assessment

I reviewed the current Buzzjuice source files, the previous ChatGPT proposal, and the 2026-09-14 GitHub revision. The GitHub revision contains several **important architectural improvements**, especially the separation of directional blocks from relationship state. However, I would **not deploy the GitHub 3.1.0 implementation as written**.

The main reasons are:

1. Its external REST endpoint can alter canonical state without sufficiently preserving the BuddyBoss request-policy path.
2. Its generic platform `/relationship` endpoints do not exist in the current Streams/Socials codebase.
3. It marks events processed even when an external platform write fails. 
4. Its unblock implementation in one part preserves the relationship, contradicting the stated principle that unblock should not restore a previous relationship. 
5. The proposed Streams wrappers use incorrect/incomplete function signatures and placeholders compared with the actual code.
6. QuickDate's `like()` is a **dating-like**, not the follower/connection mechanism, so using it as the connection synchronizer would be wrong. The actual follower system is `Wo_RegisterFollow()`, `Wo_DeleteFollow()` and `Wo_AcceptFollowRequest()` in `core.php`. 
7. The current Streams implementation explicitly uses `Wo_RegisterFollow()`, `Wo_DeleteFollow()` and the corresponding block functions, so synchronization should hook the **successful write operations**, not unrelated UI functions. 

I therefore recommend **Version 4.0.1** below.

# 1. Final architecture

The system should be:

```text
                         ┌───────────────────────────┐
                         │ WORDPRESS / BUDDYBOSS     │
                         │                           │
                         │   SOURCE OF TRUTH         │
                         │                           │
                         │ BuddyBoss connections     │
                         │ BuddyBoss blocks          │
                         │                           │
                         │ BZJ canonical state       │
                         │ BZJ durable event queue   │
                         └─────────────┬─────────────┘
                                       │
                    canonical fan-out │
                                       ▼
             ┌────────────────────────┴───────────────────────┐
             │                                                │
             ▼                                                ▼
    ┌─────────────────┐                              ┌─────────────────┐
    │ BUZZJUICE       │                              │ BUZZJUICE       │
    │ STREAMS         │                              │ SOCIALS         │
    │ WoWonder        │                              │ QuickDate       │
    │                 │                              │                 │
    │ followers       │                              │ followers       │
    │ blocks          │                              │ blocks          │
    └────────┬────────┘                              └────────┬────────┘
             │                                                │
             │ signed HMAC event                              │ signed HMAC event
             └──────────────────────┬─────────────────────────┘
                                    ▼
                         WordPress canonical endpoint
```

The critical distinction is:

### WordPress-originated action

```text
BuddyBoss action
       ↓
BuddyBoss hook
       ↓
canonical state
       ↓
durable event
       ↓
Streams + Socials
```

### Streams/Socials-originated action

```text
Native platform action
       ↓
successful local DB operation
       ↓
signed HMAC report to WordPress
       ↓
WordPress applies BuddyBoss policy
       ↓
canonical state
       ↓
Streams + Socials reconciliation
```

This preserves the principle that **external platforms may report an event, but they do not become the authority**.

# 2. Relationship model

The canonical relationship state is:

```text
NONE
REQUESTED
CONNECTED
```

Blocks are deliberately separate:

```text
block_a_to_b
block_b_to_a
```

Thus:

| Situation    | Relationship | A→B block | B→A block |
| ------------ | -----------: | --------: | --------: |
| Nothing      |         NONE |         0 |         0 |
| A requests B |    REQUESTED |         0 |         0 |
| Connected    |    CONNECTED |         0 |         0 |
| A blocks B   |         NONE |         1 |         0 |
| B blocks A   |         NONE |         0 |         1 |
| Both block   |         NONE |         1 |         1 |
| A unblocks B |         NONE |         0 |       0/1 |

This is the strongest part of the GitHub correction and should absolutely be retained. 

### Important

**Unblocking never automatically restores friendship.**

That avoids a dangerous situation where:

```text
A friends B
A blocks B
A unblocks B
```

silently recreates the friendship.

Instead:

```text
A blocks B
→ relationship = NONE

A unblocks B
→ relationship remains NONE

A must create a new connection
```

# 3. BuddyBoss restrictions remain authoritative

This is another area where I changed the previous design.

Suppose someone follows another user on Streams.

We should **not** simply force:

```php
friends_add_friend($a, $b, true);
```

because that can undermine BuddyBoss's connection-request restrictions.

Instead:

```php
friends_add_friend($a, $b, false);
```

The external follow therefore becomes a **BuddyBoss connection request**, subject to the existing WordPress/BuddyBoss rules.

The GitHub analysis correctly identified this principle, explicitly warning against `force=true`. 

So WordPress remains the policy engine.

# 5. Why I changed the GitHub REST architecture

The GitHub version proposed:

```text
Streams → WordPress REST
WordPress → /streams/api/relationship
WordPress → /socials/api/relationship
```

The problem is that those generic APIs aren't actually present in the supplied codebase.

The actual Streams implementation is based on functions such as:

```php
Wo_RegisterFollow()
Wo_DeleteFollow()
Wo_AcceptFollowRequest()
Wo_RegisterBlock()
Wo_RemoveBlock()
```

with direct database operations. 

Likewise, Socials' actual block implementation writes directly to its `blocks` table. 

Therefore the more realistic architecture is:

```text
WordPress
   ↓
existing wwqd_bridge.php
   ↓
direct database reconciliation
   ↓
actual WoWonder / QuickDate tables
```

while the reverse direction uses:

```text
Streams/Socials
   ↓
HMAC signed report
   ↓
WordPress
```

This avoids inventing APIs that do not exist.

# 7. Streams modifications

The actual Streams code confirms that:

```php
Wo_RegisterFollow()
```

is the write operation for following/connection creation. 

Likewise:

```php
Wo_DeleteFollow()
Wo_AcceptFollowRequest()
```

are the relevant relationship mutations. 

And:

```php
Wo_RegisterBlock()
Wo_RemoveBlock()
```

directly create/delete block records. 

### Therefore

Do **not** replace the functions.

After each successful operation, add the reporting call.

For example, after a successful follow:

```php
if ($query && function_exists('bzj_connections_sync_report_to_wordpress')) {
    bzj_connections_sync_report_to_wordpress(
        'streams',
        (int)$follower_id,
        (int)$following_id,
        ($active == 1 ? 'accept' : 'request')
    );
}
```

And after a successful block:

```php
if ($query && function_exists('bzj_connections_sync_report_to_wordpress')) {
    bzj_connections_sync_report_to_wordpress(
        'streams',
        (int)$logged_user_id,
```

# 9. Blocking behaviour

This is now deterministic.

### A blocks B on WordPress

```text
BuddyBoss block
       ↓
remove WP friendship/request
       ↓
canonical:
relationship = NONE
A→B = 1
       ↓
Streams:
delete A↔B followers
create A→B block
       ↓
Socials:
delete A↔B followers
create A→B block
```

### A blocks B on Streams

```text
Streams block succeeds
       ↓
signed report
       ↓
WordPress
       ↓
BuddyBoss block
       ↓
canonical state
       ↓
Streams + Socials reconciled
```

### B subsequently blocks A

Both flags can coexist:

```text
A→B = 1
B→A = 1
```

There is no ambiguity about who blocked whom.

# 10. Unblocking

Suppose:

```text
A→B = 1
B→A = 0
relationship = NONE
```

A unblocks B:

```text
A→B = 0
B→A = 0
relationship = NONE
```

The connection is **not restored**.

This is an intentional correction to the GitHub 3.1.0 implementation. The GitHub document correctly states that unblock should not restore the relationship, but its earlier implementation preserved the relationship state in the unblock handler. 

Version 4.0.1 consistently uses:

```text
unblock → relationship NONE
```

# 11. Retry reliability

Another significant improvement over the GitHub version is the event processing model.

The GitHub implementation could mark an event `processed` after attempting both external platforms, even if one of those operations failed. 

That is unacceptable for a synchronization system.

Version 4.0.1 instead uses:

```text
pending
   ↓
attempt
   ↓
both required platforms successful?
   ├── YES → processed
   │
   └── NO → retry
             ↓
          exponential backoff
             ↓
          failed after limit
```

The log therefore becomes useful for diagnosing actual delivery failures rather than merely recording that an attempt occurred.

# 13. One subtle but important design decision

The external platforms report **after their local operation succeeds**.

For example:

```text
Streams INSERT succeeds
        ↓
report to WordPress
```

rather than:

```text
report to WordPress
        ↓
Streams INSERT
```

This avoids the problem where WordPress immediately fans the relationship back into Streams while Streams is still inside the function that is creating the relationship.

The local operation is therefore allowed to complete naturally, then WordPress reconciles everything to the canonical state.

The reconciliation is idempotent because it rebuilds the relevant pair from canonical state.

# 16. One thing I would **not** implement yet

I would not introduce another synchronization database, Redis, message broker, or external microservice.

At the current Buzzjuice scale, that would be premature.

The combination of:

```text
WordPress canonical state
+
MySQL pair lock
+
durable event queue
+
existing wwqd_bridge
+
HMAC external reporting
+
file diagnostics
```

is sufficient and considerably easier to maintain.

The architecture can later evolve into a proper event bus without changing the canonical relationship model.

## Bottom line

The GitHub 3.1.0 proposal was **directionally good but not production-ready for the actual Buzzjuice codebase**.

The version I recommend is:

**Buzzjuice Connections Sync 4.0.1**

> **WordPress/BuddyBoss = authority**
