- clipping
- latency

## Test B — MIC 2

Move the condenser to MIC 2.

Record:

> "TEST TWO — MICROPHONE TWO."

## Test C — TWO INPUTS

Use:

```text
MIC 1 → "ONE ONE ONE"
MIC 2 → "TWO TWO TWO"
```

Determine whether REAPER receives:

```text
INPUT 1
INPUT 2
```

independently.

If yes:

> V8S becomes a potential multi-input device.

If no:

> Treat it as a mixed programme source.

---

# 15. V8S Decision Matrix

| Result | Decision |
|---|---|
| Single mono input | Local microphone/mixer |
| Stereo mixed output | Programme mixer |
| L/R separated inputs | Potential dual-source capture |
| Multiple discrete channels | Excellent; use for stems |
| Noisy/unreliable | Do not use as primary system |

The hardware determines the architecture.

Not the product name.

# 16. Sample Rate Policy

The studio target is:

> **48 kHz**

because the primary output is video.

However:

> **Do not force every device to 48 kHz if the device is demonstrably fixed at 44.1 kHz.**

The rule is:

```text
DEVICE NATIVE RATE
        ↓
STABLE RECORDING
        ↓
CONTROLLED RESAMPLING
        ↓
48 kHz MASTER
```

The previous 48 kHz recommendation therefore becomes a **target**, not an absolute hardware command.

---

# 17. Windows Audio Policy

For every production device:

1. Open the device's Windows sound properties.
2. Check its actual supported formats.
3. Prefer 48 kHz where supported.
4. Use 24-bit where available.
5. Disable unnecessary audio enhancements.
6. Prevent Windows system sounds from entering the recording path.
7. Avoid unnecessary exclusive-mode conflicts.
8. Do not change a working device simply to make every device look identical.

For REAPER, the audio device should be selected explicitly rather than relying on Windows default-device behaviour.

REAPER supports ASIO and WASAPI on Windows; ASIO should be preferred where a proper device driver exists, otherwise WASAPI is an appropriate fallback. citeturn2search2turn2search37

---

# 18. Windows Performance Policy

Do not blindly disable Windows security.

The Envy currently has:

- Secure Boot
- Credential Guard
- VBS

The Pavilion currently has:

- Secure Boot off
- VBS disabled
- App Control enforced

These are configuration facts, not reasons to dismantle security.

For production:

- connect AC power
- select the highest available Windows performance mode
- disable sleep during recording
- extend screen timeout
- enable Do Not Disturb
- close unnecessary applications
- pause nonessential synchronization
- postpone noncritical updates
- close browsers/tabs that are not required

Do **not** disable Defender, Credential Guard, App Control, Secure Boot or other security controls merely for performance unless a measured production problem requires it.

# 40. AI Participation Modes

The previous "unrestricted AI" idea is retained but refined.

The AI is allowed to reason, disagree, question and contribute naturally.

The **producer controls whether the AI is allowed onto the programme**.

Use four modes:

### MODE 0 — OFF

AI does not participate.

### MODE 1 — ASSIST

AI listens/receives selected information and prepares responses.

Producer decides whether to use them.

### MODE 2 — READ-OUT

AI responses are generated and converted into audio.

Producer triggers them.

### MODE 3 — LIVE

AI participates directly in the conversation.

Producer controls the AI's permission to speak.

# 118. The AI Three-Way Test

The definitive test is:

```text
HOST:
"AI, can you hear me?"

AI:
"Yes."

GUEST:
"Can you hear me?"

AI:
"Yes."

HOST:
"Can our guest hear you?"

GUEST:
"Yes."

AI:
"And I can hear both of you."
```

Then deliberately test:

```text
HOST SPEAKS
GUEST SPEAKS
AI SPEAKS
HOST SPEAKS
AI SPEAKS
GUEST SPEAKS
```

Check:

- no echo
- no feedback
- no duplicated audio
- no delayed response loop
- no AI hearing itself
- no guest hearing doubled AI
- no host hearing doubled guest

# 119. AI Feedback Protection

The architecture must prevent:

```text
AI SPEAKS
 ↓
PAVILION HEARS AI
 ↓
AI HEARS ITSELF
 ↓
AI RESPONDS
 ↓
AI HEARS RESPONSE
 ↓
LOOP
```

Therefore the AI input should be conceptually:

```text
HOST
+
GUEST
-
AI OUTPUT
```

The AI must not hear its own programme return.

This becomes a hard architectural requirement.

# 120. AI Live Mode Safety

Even in LIVE mode:

> The AI is not "unrestricted" in the technical sense.

It is:

> **Autonomous within a producer-controlled speech gate.**

That distinction is important.

The producer controls:

```text
CAN SPEAK?
```

The AI controls:

```text
WHAT SHOULD I SAY?
```

This produces natural participation without allowing the production system to become uncontrollable.

### The key architectural change I would emphasize

There is **one issue we should not gloss over** from the previous versions: the full live AI/guest/host conversation is not solved merely by sending Pavilion audio to the Envy.

We have proven:

**Pavilion → Envy**

but eventually need:

**Envy → Pavilion**

as well.

That creates the complete loop:

**Host ↔ Pavilion ↔ Guest/AI → Envy**

I would therefore make **the next commissioning stages deliberately sequential**: first V8S, then Dell camera, then dual recording, and **only then engineer and test the Envy→Pavilion return path for the live AI co-host**. That keeps the already-working studio intact while we add complexity one controlled layer at a time.
