# 1. Document Purpose

This document defines the **skeletal architecture** of the Classies Chronicles Studio.

It is the system-level blueprint for:

- studio hardware and workstation responsibilities
- production and recording architecture
- remote guest communications
- AI participation
- episode production
- AI-generated media
- archive and retrieval
- Buzzjuice integration
- consent and licensing
- publishing and monetization
- commissioning and future scaling

Detailed implementation specifications are intentionally kept in their own documents.

**Design principle:**

> Build the smallest reliable production system first, prove it, then add complexity only when a real production requirement justifies it.

---

# 2. System Identity

The Classies Chronicles Studio is a **small AI-assisted educational media operating system**.

It is designed to produce the immediate pilot:

> **Classies Chronicles — Pilot Season — Episode 1 — The Foundation Phase**

while establishing a reusable architecture for:

- future podcast episodes
- remote guests
- AI co-hosts
- presentations and slides
- short stories and music videos
- AI-generated comics and animation
- mobile reporting
- livestreams
- educational content
- community-generated stories
- social clips
- Buzzjuice Courses promotion
- subscriptions
- crowdfunding
- future commercial media production

The physical studio is the production layer.

The episode archive is the content source of truth.

The persistent AI Desk is the reasoning, retrieval, persona and AI-control layer.

---

# 3. Architectural Principles

## 3.1 Lean First

Do not commission complex infrastructure before the simple production chain works.

## 3.2 Separation of Concerns

Separate:

- physical production
- communications
- AI control
- episode content
- archive/index
- publishing
- business/conversion

## 3.3 One Persistent AI Desk

There is **one CC_AI_DESK for the entire Classies Chronicles franchise**.

Episodes are not given their own AI Desk.

Episode-specific material remains owned by the episode and is retrieved by the persistent Desk when permitted.

## 3.4 Archive Is Authoritative

The filesystem/archive is authoritative.

Indexes, caches and databases are derived and rebuildable.

## 3.5 Provider Neutrality

WhatsApp, Zoom, Google Meet, Riverside, Teams and future calling applications are replaceable endpoints.

The Studio communications architecture must not depend on one calling provider.

## 3.6 Human Editorial Authority

AI may assist, converse and eventually operate with substantial conversational freedom, but editorial, consent, licensing and emergency production controls remain under human authority.

# 8. Podcast Communications Architecture

The Pavilion is the **Guest Communications Desk** and now uses **Voicemeeter Potato as the Studio Communications Bus**.

The communications system is designed around three participants:

```text
HOST <-> GUEST
HOST <-> AI
GUEST <-> AI
```

while explicitly blocking:

```text
HOST -> HOST
GUEST -> GUEST
AI -> AI
```

The calling application is only an endpoint. The permanent routing architecture is the communications bus.

The current design uses Voicemeeter Potato buses for host monitoring, guest return and AI input/return, with mix-minus routing preventing digital feedback and headphones preventing acoustic feedback.

VB-Cable is **not a prerequisite** for the current implementation.

The detailed routing matrix, Voicemeeter Potato configuration, application I/O settings, mix-minus contracts, commissioning tests and future multi-call architecture are documented separately.

**Detailed specification:**

Podcast Communications Module.txt

https://github.com/cupidblack/Koware-Management/blob/main/Psymedia/Podcast%20Communications%20Module.txt

# 9. Communications Design Contract

The permanent communications contract is:

```text
A1 = HOST MONITOR
B1 = CALL / GUEST RETURN
B2 = AI INPUT
B3 = PRODUCTION / RECORDING RESERVE
```

Conceptually:

```text
HOST
  |
  +--> HOST MONITOR
  +--> GUEST
  +--> AI

GUEST
  |
  +--> HOST
  +--> AI
  -X-> GUEST

AI
  |
  +--> HOST
  +--> GUEST
  -X-> AI
```

The calling platform must receive the appropriate local programme/host bus and must never receive the guest's own returned audio.

The AI input must contain host + guest but not the AI's own generated return.

# 10. Audio Feedback Protection

Two feedback classes must be controlled.

## Digital feedback

Prevented through correct mix-minus routing.

## Acoustic feedback

Prevented primarily through headphones.

During live communications:

- USB monitor speakers remain muted
- Bose SoundDock remains out of the live monitoring chain
- host/producer uses headphones
- AI return never routes into the AI input
- guest return never routes back to the guest

# 14. Gain Philosophy

Prioritize:

1. microphone placement
2. microphone distance
3. clean source gain
4. room control
5. routing
6. conservative processing

A clean quiet recording can be recovered.

Clipping, distortion and severe noise cannot reliably be recovered.

# 22. AI Operating Modes

AI is not simply on/off.

## LISTEN

AI receives permitted conversation but does not speak.

## ASSIST

AI prepares research, suggestions and responses for producer review.

## CO-HOST

AI may speak through the controlled production path.

## AUTONOMOUS

AI may initiate relevant questions, respond spontaneously, challenge assumptions and participate without sentence-by-sentence approval.

Autonomous means:

> conversational initiative inside the production environment.

It does not bypass safety, consent, licensing or producer emergency controls.

# 26. Retrieval Architecture

Initial implementation:

> SQLite + FTS5

Index meaningful units rather than treating an entire transcript as one record.

Example stable IDs:

```text
S01E01:TRANSCRIPT:0042
S01E01:HEADLINE:H003
S01E01:RESEARCH:R007
```

Every useful retrieval result should provide:

- episode
- source file
- section/location
- permission state
- source reference

Semantic embeddings are deferred until FTS5 demonstrably fails on real production queries.

# 27. AI Persona Governance

Persona evolution follows:

```text
EPISODE
   ↓
TRANSCRIPT
   ↓
OBSERVATIONS
   ↓
POST-EPISODE ANALYSIS
   ↓
PERSONA PROPOSAL
   ↓
PRODUCER REVIEW
   ├── REJECT
   └── APPROVE
          ↓
   NEW PERSONA VERSION
          ↓
      CHANGELOG
```

Never silently mutate the persona.

Changes must be:

- versioned
- reversible
- source-attributed
- reviewable
- small enough to understand

Relationship files must describe legitimate production interaction characteristics and must not become hidden personal dossiers.

```text

TEST C — HOST ↔ GUEST ↔ AI
TEST D — HOST ↔ GUEST ↔ AI + OBS
TEST E — HOST ↔ GUEST ↔ AI + OBS + REAPER
TEST F — FULL SIMULATED EPISODE
```

Only Test F qualifies the communications system for a real guest production.

# 36. Consent and Revocation

Consent must be explicit and granular enough to distinguish:

- AI analysis
- AI retrieval
- internal production
- commercial production
- public distribution
- archival retention

When consent is withdrawn:

```text
SOURCE
  ↓
RESTRICTED / WITHDRAWN
  ↓
RETRIEVAL FILTER
  ↓
INDEX INVALIDATION / REBUILD
```

A stale index must never override current consent.

# 52. Error Handling

The Studio must fail safely.

Examples:

```text
MISSING EPISODE CONTEXT
→ Do not index

INVALID CONSENT
→ Do not retrieve for restricted operation

STALE INDEX
→ Warn / rebuild

MISSING SOURCE
→ Return unavailable; do not invent

AMBIGUOUS RETRIEVAL
→ Ask / qualify uncertainty

AI PROVIDER FAILURE
→ Remain safe; AI MUTE / LISTEN state remains available

NETWORK FAILURE
→ Preserve local archive and recording capability where possible
```

# 53. Security and Privacy

Never store API keys in Git.

Use:

- environment variables
- Windows credential storage
- secret manager when justified

Never place secrets in:

- config files committed to Git
- prompt files
- episode context
- Git history

Participant data must be minimized.

Episode participant records are not a CRM.

The AI Desk should use controlled platform APIs rather than arbitrary database access.
