# BZJ-PGB-0200 — Architectural Engineering Analysis

I have reviewed the three production-workflow guides and the current GitHub implementation evidence you supplied. The workflow guides strongly support your proposed **architecture-first → challenge → specification → implementation → independent validation → production** model. In particular, they establish GitHub as the engineering source of truth, require evidence before code, formal task packets, independent agent roles, explicit stop conditions, and a Challenge-Before-Build gate. 

There are also several important issues in the current Payment Gateway Bridge that mean **we should not yet give an implementation agent permission to redesign it**.

The most significant are:

* the current Streams bridge still creates WooCommerce orders through the REST API;
* the browser/client currently supplies financial values that ultimately enter the order payload;
* the current cURL implementation explicitly disables TLS verification;
* the Streams webhook contains a hard-coded webhook secret;
* the existing webhook and WordPress fulfilment paths overlap;
* AffiliateWP context is currently captured in Streams even though the authoritative processing already occurs on WordPress;
* subscription, wallet, Jewel Affiliate and Streams fulfilment responsibilities are distributed across several places;
* the browser redirect cannot be treated as a durable fulfilment mechanism;
* the current system does not yet appear to have a formal payment-intent state machine/reconciliation layer;
* and the proposed automatic filesystem-driven database recreation requires an architectural decision because the workflow guide explicitly warns against automatic schema rebuilding based solely on filesystem state. 

The following is therefore the **agent-facing Architectural Engineering Analysis**, rather than the final ADR. It is deliberately written so Claude, Jules and Copilot can independently investigate the repository and return evidence without prematurely implementing the proposed architecture.

# 1. Purpose

The Buzzjuice Streams (WoWonder) Payment Gateway Bridge currently experiences dropped orders and requires architectural modernization.

The objective of this analysis is **not to implement the replacement bridge**.

The objective is to independently investigate the existing implementation, identify the actual causes of dropped or inconsistent transactions, evaluate the proposed replacement architecture, identify risks and contradictions, and produce evidence that can be synthesized into the formal:

1. Architectural Decision Record;
2. Implementation Specification;
3. Task Packet(s);
4. Migration Plan;
5. Testing and Validation Plan.

No agent should modify production code during this phase.

# 10. Current System — Evidence Inventory

The current implementation must be treated as the baseline.

## 10.1 Streams Payment Initiation

Current entry path includes:

```text

    ↓
Wo_GetWooCommerceLink()
    ↓

    ↓

    ↓
wow-pgb_init.php
```

The current JavaScript collects product, amount, currency, units, owner and transaction information in the browser before submitting it to the payment endpoint. 

This is a significant architectural concern.

The new architecture must determine which values are:

```text

server-derived
database-derived
WooCommerce-derived
configuration-derived
```

Financial values must ultimately be server authoritative.

# 11. Current WoWonder Request Router

`streams/requests.php` currently routes:

```text
f=payment
payment_type=wow_payment
```

to:

```text
assets/wow-pgb/wow-pgb_init.php
```

The current endpoint also permits the request through the WoWonder request allow-list and login checks. 

The architectural analysis must determine whether this router should remain the public initiation boundary or whether a thinner Payment Gateway Client should replace the current mechanism.

# 12. Current Payment Initialization

`wow-pgb_init.php` currently:

1. authenticates the WoWonder user;
2. validates submitted values;
3. generates a WoWonder order identifier;
4. writes transaction data;
5. resolves the WordPress user ID;
6. builds WooCommerce order data;
7. captures AffiliateWP browser context;
8. sends a WooCommerce REST API request;
9. creates the WooCommerce order;
10. receives the WooCommerce payment URL;
11. redirects the user toward payment.

The current WooCommerce order creation occurs through:

```text
POST /wc/v3/orders
```

and the returned payment URL is used for browser redirection. 

This is the principal area requiring architectural investigation.

# 18. Current Webhook Idempotency Concern

The webhook currently updates payment transaction state and performs fulfilment based on payment status.

The architecture must determine whether repeated WooCommerce webhook delivery can cause:

```text
duplicate wallet credit
duplicate funding contribution
duplicate subscription activation
duplicate role update
duplicate Jewel rebate
duplicate downstream effects
```

WooCommerce webhook delivery must be assumed capable of repetition.

The new design must therefore be idempotent independently of webhook delivery count.

# 22. Important Architectural Correction

The proposed architecture currently implies:

```text
Streams
 ↓
database row
 ↓
browser redirect
 ↓
MU plugin
 ↓
WooCommerce
```

This must be challenged.

A browser redirect is not a durable server-side transaction mechanism.

Consider:

```text
Streams database insert succeeds
↓
browser redirect fails
```

or:

```text
Streams database insert succeeds
↓
user closes browser
```

or:

```text
browser request times out
↓
WooCommerce order was never created
```

The payment intent could then remain orphaned.

Therefore the architecture must distinguish:

```text
Payment Intent Creation
```

from:

```text
Browser Handoff
```

and:

```text
WooCommerce Order Creation
```

and:

```text
Payment
```

and:

```text
Fulfilment
```

and:

```text
Reconciliation
```

The agent challenge must explicitly investigate this.
