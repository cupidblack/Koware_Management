## 2. Root cause of "dropped orders" — VERIFIED

Three independent, browser- or network-dependent steps sit between "customer paid" and "Streams fulfils":

**(a) WordPress → Streams webhook is the only fulfilment trigger for Streams state.**
`streams/wow-pgb_webhook.php:121` acts **only** on `status === "completed"`. It updates `Wo_Payment_Transactions.payment_status` (`:129`), credits the wallet (`:176`), records funding (`:193`), and sets `Wo_Users.is_pro/pro_type/pro_time` (`:227`). There is no other path in the repo that performs these writes for a PGB order.

**(b) The observed cPanel DNS failure kills exactly that path.**
`curl: (6) Could not resolve host: buzzjuice.net` from the server means WooCommerce cannot deliver the webhook to the Streams URL. Result: the order is **paid in WooCommerce**, the `Wo_Payment_Transactions` row stays at its initial state forever, wallet is never credited, pro is never activated, and the customer is charged. **There is no reconciliation job to detect or repair this** (see §9).

**(c) WooCommerce-side fulfilment is browser-triggered, not server-triggered.**

```
wp-content/mu-plugins/buzzjuice-affwp-order-complete.php:34   add_action('woocommerce_order_status_completed', …, 999)
wp-content/plugins/blue-crown-wp/wow-pgb_sync/wow-pgb_sync.php:509-529
    add_action('wp_footer', …)   → if (is_wc_endpoint_url('order-received'))
                                      && status in ['processing','completed']
                                      → do_action('wowonder_order_redirect')
:532  add_action('wowonder_order_redirect', 'wowonder_redirect_after_purchase')
```

`wowonder_redirect_after_purchase()` (`:195`) creates the **WooCommerce subscription** (`:435-442` → `create_woocommerce_subscription()` at `:1684` → `POST /subscriptions`), calls the AffiliateWP bridge (`:246, :455, :473, :495`), and `wp_redirect(); exit()` (`:254, :460, :466, :482, :488, :502`).

**So: browser closed, refresh timed out, mobile network dropped → no subscription, no referral, no redirect.** The customer is charged and receives nothing. And `retry_with_backoff($cb, 10, 2, 300)` at `:318-356` can `sleep()` for up to ~300 s **inside a page render**, which is a second-order cause of abandoned checkouts.

This directly confirms Claude's §22 challenge: *browser navigation is not the source of truth*. **VERIFIED, and it is worse than the proposal assumed** — it is not just the handoff that is browser-bound, the entire post-payment fulfilment chain is.

## 5. Assessment of the three options Claude left open

**Option A (Streams → REST → browser checkout): keep REST as the transport, but fix it.** The DNS observation is *not* evidence against REST — it is evidence that **whatever host is configured in `wow_api_url` must resolve from cPanel**, which is a deployment/config defect, not an architectural impossibility. Verify: `curl -s -o /dev/null -w '%{http_code}' "$wow_api_url/wp-json/wc/v3/system_status" -u key:secret` from cPanel. If that succeeds, Option A survives.

**Option B (durable intent → signed WP handoff → native WooCommerce PHP APIs): viable for the *order*, but INCOMPLETE for subscriptions.** §Gap 3 proves `wc_create_order()` + `add_product()` will **not** create a subscription — WCS 8.6.0 reads `WC()->cart->recurring_carts` exclusively. Any Option B design must either (a) deliberately synthesise a `WC_Cart` + recurring cart and fire `woocommerce_checkout_order_processed` (heavy, high blast radius), or (b) accept that the initial order is created natively and the subscription is created by **WCS itself** once payment completes — which requires the order to actually pass through WooCommerce checkout rather than being created pre-paid.

**This is the single largest unresolved design question in the whole project, and no prior report surfaced it.** It must be settled before the ADR.

**Option C (hybrid): the only architecture that survives §Gap 3 and §Gap 4 simultaneously** — WordPress-native order creation for pricing/currency correctness, with the browser handoff carrying only an intent reference, and WCS owning the subscription lifecycle.

**Option D (Store API): REJECT.** Verified cart-bound; cannot create an arbitrary order (§Gap 2).

## 7. Position for BZJ-PGB-0230 (ADR)

The evidence now supports a firm architectural conclusion that prior reports only gestured at:

> **The Buzzjuice Payment Gateway Bridge has two independent fulfilment paths, and *both* are unreliable. The Streams side is triggered by a replayable, hard-coded-secret webhook over a network path observed to fail DNS. The WordPress side is triggered by `wp_footer` on the order-received page — i.e. by the browser.** No reconciliation job exists for either. No durable transaction identifier, no unique constraint, no idempotency key, and no lock exists anywhere in the payment path.

**Recommended architectural direction** (for ADR debate, not implementation):

1. **Browser never triggers fulfilment.** Move subscription provisioning and AffiliateWP off `wp_footer` onto server-side order-status events, and stop creating subscriptions via `POST /subscriptions` with `status=active` — let WCS 8.6.0 own it.
2. **A durable payment-intent row is mandatory**, created before any WooCommerce call, with a real UUID primary key, a unique idempotency key, and a `state` column — replacing `uniqid('wow_')` + unkeyed `Wo_Payment_Transactions`.
3. **Server-side price and currency authority.** Amount must be re-derived from the WooCommerce catalogue inside WordPress; the browser submits only a *product/plan reference*.
4. **Idempotent, locked, transactional financial effects** — modelled on the two correct patterns already in the codebase: `jewel_apply_rebate_credit()` (`jewel-affiliate-webhook.php:279-340`) and `bzj-connections-sync.php` (GET_LOCK `:134`, unique `event_uuid` `:110`, backoff queue `:93-112, :906-934`).
5. **A reconciliation cron + WP-CLI command**, following `bzj-connections-sync.php` and `bzj-affiliate-access-gate.php:488-502` exactly, covering reconciliation cases A–F from 0200 §32.
6. **Keep AffiliateWP logic as-is** (`AGENTS.md` protected functionality). Wrap it; do not rewrite. But the double-invocation surface must be collapsed to a single entry point before any of it is touched.

**Stop condition for this stage: met.** All 10 evidence gaps are closed from repository source, with 4 items (V-01…V-04, V-06, V-07) requiring production-environment access before the ADR can be finalised. No production code was written and no repository file was modified.
