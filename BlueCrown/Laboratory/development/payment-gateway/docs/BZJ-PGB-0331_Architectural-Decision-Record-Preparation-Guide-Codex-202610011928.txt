Yes. We should now treat **BZJ-PGB-0325 as the formal gate record** and execute BZJ-PGB-0330 as a controlled architecture-development stage—not as the beginning of coding.

The closure record explicitly establishes the sequence: **0325 Challenge Closure → 0330 Architecture Decision + Strategy → 0340 Implementation Specification → 0400 Database/Migration Specification → 0500 Task Packets → 0600 Development**, with no production-code modification before the development stage. ([GitHub][1])

We have this.

# Step 3 — Establish the architectural thesis

Before we get lost in implementation details, BZJ-PGB-0330 needs one sentence that everything else can be tested against.

The challenge closure provides the appropriate baseline:

> **Buzzjuice Payment Gateway Bridge SHALL use a durable Payment Intent orchestration layer stored in `koware_iapd_db`, with WordPress/WooCommerce as the authoritative payment execution environment, a signed browser handoff between Streams and WordPress, server-authoritative commercial data, independently idempotent fulfilment effects, and asynchronous recovery/reconciliation.** ([GitHub][1])

This becomes our **Architecture Thesis AT-001**.

Every proposed component should answer:

> Does this strengthen or violate AT-001?

That prevents implementation convenience from gradually recreating the old architecture.

---

# Step 4 — Turn the thesis into formal decisions

This is where BZJ-PGB-0330 becomes an actual ADR.

For each decision we need five things:

### 1. Decision

What are we choosing?

### 2. Rationale

Why does the architecture require it?

### 3. Constraints

What must implementation obey?

### 4. Consequences

What becomes easier/harder because of the decision?

### 5. Acceptance criteria

How will we later prove that implementation conforms?

For example:

### ADR-D003 — Native WooCommerce Execution

**Decision**

> The Buzzjuice Payment Gateway Bridge SHALL create and manage WooCommerce orders within the WordPress execution environment using native WooCommerce APIs and SHALL NOT require a Streams-to-WordPress HTTP API call on the critical payment-initiation path.

This is much stronger than:

> "Native WooCommerce is better."

The closure guidance specifically gives this distinction as the correct way to turn an architectural observation into a testable decision. ([GitHub][1])

### Consequences

**Positive**

* removes the critical self-HTTP dependency;
* uses the actual installed WooCommerce runtime;
* allows native WooCommerce validation;
* gives direct access to WooCommerce order APIs.

**Negative**

* more logic moves into WordPress;
* the MU/shared bridge must understand WooCommerce;
* Streams can no longer be treated as the payment-order authority.

### Acceptance criteria

Later testing must demonstrate:

```text
Streams request
      ↓
Payment Intent
      ↓
signed handoff
      ↓
WordPress
      ↓
native WC order creation
```

with **no Streams → WordPress REST/cURL dependency for critical order creation**.

# Step 5 — Define system ownership

This is one of the most important parts of the ADR.

The architecture must explicitly answer:

> **Who owns what?**

The challenge closure already proposes this ownership boundary. ([GitHub][1])

### Streams / WoWonder

Owns:

* Streams user context;
* payment UI/request;
* Streams entitlement representation;
* existing Streams financial records.

Does **not** own:

* final WooCommerce price;
* WooCommerce order creation;
* payment confirmation;
* global fulfilment state.

### IAPD

Owns:

* Payment Intent;
* payment events;
* payment attempts;
* payment effects;
* recovery state;
* reconciliation state.

Database:

```text
koware_iapd_db
```

### WordPress / WooCommerce

Owns:

* product;
* authoritative commercial data;
* WooCommerce order;
* payment execution;
* subscription lifecycle.

### AffiliateWP

Owns:

* AffiliateWP referral/commission domain.

But BZJ-PGB owns the **controlled integration effect**.

### Jewel

Owns:

* Jewel-specific rebate/business logic.

But it is an optional integration, not core payment authority.

This ownership model is essential because the old architecture had multiple components effectively behaving as though they owned the same transaction.

# Step 6 — Define the transaction model

Now we formalize the state architecture.

I would use three layers.

## Layer A — Payment Intent

```text
CREATED
   ↓
VALIDATED
   ↓
HANDOFF_READY
   ↓
WC_ORDER_CREATED
   ↓
PAYMENT_PENDING
   ↓
PAYMENT_CONFIRMED
   ↓
FULFILMENT_PENDING
   ↓
COMPLETED
```

With recovery/error states:

```text
FAILED
EXPIRED
CANCELLED
RECOVERY_REQUIRED
```

## Layer B — Payment events

Examples:

```text
intent.created
handoff.accepted
wc_order.created
payment.pending
payment.completed
payment.failed
subscription.created
subscription.payment_completed
```

Events are evidence/history.

They should not be treated as mutable current state.

## Layer C — Effects

Examples:

```text
STREAMS_ENTITLEMENT
SUBSCRIPTION
AFFILIATEWP
JEWEL_REBATE
```

Each gets its own lifecycle:

```text
PENDING
   ↓
PROCESSING
   ↓
COMPLETED

        ↘ FAILED
             ↓
           RETRY
             ↓
        PROCESSING
```

That is what makes recovery possible without replaying the payment.

---

# Step 7 — Define commercial-data authority

This deserves its own ADR decision.

The browser/Streams request may identify:

```text
product
transaction type
user
requested operation
```

But it cannot dictate:

```text
final price
currency
discount
tax
subscription price
```

Those are resolved by WordPress/WooCommerce.

The Payment Intent should capture a **commercial snapshot** once validated.

Conceptually:

```text
Requested product
       ↓
WordPress resolves product
       ↓
price/currency/tax/subscription rules
       ↓
validated commercial snapshot
       ↓
Payment Intent
```

This prevents a later product-price change from silently changing the meaning of an already-created payment transaction.

It also gives us an important future reconciliation property:

> We can determine exactly what the system believed the customer was purchasing when the Payment Intent was created.

---

# Step 8 — Define idempotency formally

This is another area where BZJ-PGB-0330 should be precise.

We need different idempotency identities.

Conceptually:

```text
intent_uuid
      │
      ├── Woo order identity
      │
      ├── payment event identity
      │
      ├── subscription effect identity
      │
      ├── Streams effect identity
      │
      ├── AffiliateWP effect identity
      │
      └── Jewel effect identity
```

The key principle is:

> **One logical effect may be attempted many times, but it may be committed only once.**

This is especially important for wallet/entitlement operations.

We should not rely on:

```text
if not processed:
    process()
```

alone.

The implementation specification later needs atomic database constraints/operations wherever possible.

---

# Step 9 — Define recovery architecture

Recovery is not an emergency afterthought.

It is part of the architecture.

```text
Payment confirmed
       │
       ▼
Effects generated
       │
       ├──────► Streams
       ├──────► AffiliateWP
       └──────► Jewel
                    │
                    ▼
              failure?
                    │
                    ▼
               retry queue
                    │
                    ▼
               reconciliation
```

The recovery worker must be able to ask:

> Which effects are missing?

rather than:

> Should I run the whole payment again?

This is a major architectural distinction.
