## CHALLENGE 1: Challenge the Native WooCommerce Approach

**Challenge Block:** "Can native WooCommerce PHP APIs be the primary order-creation mechanism without exposing browser-supplied values as authoritative?"

### Architectural Resolution

**ACCEPTED with mandatory modifications:**

1. **Verified:** Native `wc_create_order()` API exists (WooCommerce 11.1.0, `includes/wc-core-functions.php:89`)

2. **Critical Issue Found (Kilo F-05):** WooCommerce automatically overwrites posted `line_item.total` and `line_item.subtotal` with the product's database price. This means:
   - Browser-supplied `amount` is **silently discarded**
   - The authoritative price comes from the WooCommerce product catalogue
   
   **This is a feature, not a bug**, and proves native APIs enforce server authority.

3. **Architectural Decision:**
   - ✅ Use `wc_create_order()` as the primary order-creation path
   - ✅ Browser submits **product reference + plan/units only**, NOT amount
   - ✅ WordPress derives the final price from `wc_get_product()` on the product ID
   - ❌ REJECT: allow browser to supply or influence `$_POST['amount']` or `$_POST['product_price']`

4. **Consequence for Design:**
   - The WooCommerce PGB bridge products (`wow-pgb_fund`, `wow-pgb_market`, `wow-pgb_pro_*`) must have correct `_regular_price` set in the product database (currently 0 or unset — **BLOCKS ADR** until V-01 production DB dump confirms actual prices)
   - Streams UI displays the *expected* amount as UI feedback only, not as financial authority
   - Server recalculates the total inside WordPress before creating the order

**Challenge Status: RESOLVED** ✅ (pending V-01 verification)

## CHALLENGE 2: Challenge the Payment Intent State Model

**Challenge Block:** "Is a separate durable payment-intent table justified, or should the model rely on WooCommerce order state alone?"

### Architectural Resolution

**ACCEPTED with stronger justification than proposed:**

The current system has:
- Streams: `wo_payment_transactions` table (unindexed, no PK, no unique constraints)
- WooCommerce: `wp_posts` (post_type='shop_order') + postmeta
- No linkage between them until webhook delivery succeeds

**Kilo Finding F-08:** Current `wow_order_id = uniqid('wow_')` is:
- Generated before any persistence ❌
- Not a UUID ❌
- The only join key between Streams and WordPress ❌
- Vulnerable to race conditions under concurrent submissions ❌

**Architectural Decision:**

A **dedicated IAPD table is mandatory** with:

```sql
CREATE TABLE bzj_payment_intents (
  id                    BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  intent_uuid           BINARY(16) UNIQUE NOT NULL,  -- true UUID
  idempotency_key       VARCHAR(255) UNIQUE NOT NULL,
  state                 ENUM('created','validated','handoff_pending','wc_order_created','checkout_ready','payment_pending','payment_completed','fulfillment_complete','failed','expired') NOT NULL,
  streams_user_id       BIGINT UNSIGNED NOT NULL,
  wp_user_id            BIGINT UNSIGNED,
  streams_reference     VARCHAR(255) UNIQUE,
  wc_order_id           BIGINT UNSIGNED,
  subscription_id       BIGINT UNSIGNED,
  product_id            BIGINT UNSIGNED NOT NULL,
  amount_cents          BIGINT UNSIGNED NOT NULL,
  source_currency       VARCHAR(3) NOT NULL,
  wc_currency           VARCHAR(3) NOT NULL,
  exchange_rate         DECIMAL(20,8),
  payment_status        ENUM('pending','processing','completed','failed','refunded'),
  retry_count           INT UNSIGNED DEFAULT 0,
  correlation_id        VARCHAR(255),
  created_at            TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at            TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  expires_at            TIMESTAMP,
  failure_reason        TEXT,
  recovery_data         JSON,
  KEY (state, created_at),
  KEY (streams_user_id),
  KEY (wp_user_id),
  KEY (wc_order_id),
  KEY (intent_uuid),
  UNIQUE KEY (idempotency_key)

```

**Why it's mandatory:**
- WooCommerce order creation is not transactional across Streams/WordPress (Kilo F-09: orphaned transactions occur)
- Webhook delivery can fail (DNS resolution failure observed in cPanel environment)
- Subscription creation is browser-triggered and can fail mid-flight (Kilo F-11)
- Payment may complete while Streams never receives the webhook
- Reconciliation requires a source-of-truth independent of WooCommerce order status
- Idempotent handoff requires a stable key that exists before the handoff occurs

**Challenge Status: RESOLVED** ✅

## CHALLENGE 4: Challenge Currency/Price Authority

**Challenge Block:** "Which system owns the authoritative amount and currency: browser, Streams, WOOCS, or WooCommerce?"

### Architectural Resolution

**Three-tier authority model (strictly enforced):**

**Tier 1 — UI Display (Streams, browser-influenced):**
- Streams UI shows a *provisional* amount in the customer's selected currency
- Calculated by: `base_price × units × WOOCS_conversion_rate`
- Used for UX only; not financial authority

**Tier 2 — Request Boundary (Streams → WordPress handoff):**
- Browser submits: product ID, plan/units, source currency (reference only)
- Browser **does NOT submit** amount or price
- Idempotency key submitted so duplicate requests return same result

**Tier 3 — Authoritative Calculation (WordPress, inside `bzj-payment-gateway.php` MU plugin):**
```php
// Inside bzj-payment-gateway.php:handle_payment_intent()
$product = wc_get_product($request['product_id']);
$base_price = $product->get_regular_price();  // ← from WooCommerce catalogue
$quantity = intval($request['units']);
$base_amount = $base_price * $quantity;

// WOOCS currency conversion
$woocs_rate = WOOCS::convert_from_to_currency(
    get_option('woocommerce_currency'),  // WC base
    $request['selected_currency'],        // customer selection
    1.0
);
$wc_amount = $base_amount * $woocs_rate;
$wc_currency = get_option('woocommerce_currency');
```

**Critical Constraint (Kilo F-04 + Gap-4):**
- WOOCS is disabled on `/wp-json/*` endpoints (verified)
- Therefore: `POST /wc/v3/orders` REST API **cannot use WOOCS conversion** ❌
- **Solution:** Do NOT use REST API for order creation
- Use `wc_create_order()` native PHP API inside WordPress MU plugin (applies WOOCS filters)

**Challenge Status: RESOLVED** ✅ (pending WOOCS runtime verification V-06)

## CHALLENGE 5: Challenge Subscription Lifecycle

**Challenge Block:** "Can subscriptions be created before payment, or must they be created after? What is the correct WCS activation hook?"

### Architectural Resolution

**Subscriptions MUST be created after order completion; browser-triggered creation is prohibited:**

**Evidence (Kilo Gap-3, definitive):**

- ❌ `wcs_create_subscription()` **does not create line items or totals** (`:222-259`)

- ❌ Hooked **only** on `woocommerce_checkout_order_processed` (not `woocommerce_payment_complete`)

- ✅ **Subscriptions are activated after payment** via `woocommerce_order_status_completed` → `WC_Subscriptions_Order::maybe_record_subscription_payment()`

**Current Bridge Defect (Kilo F-11):**
- Creates subscription via `POST /subscriptions` with `'status'=>'active'`
- Triggered from `wp_footer` (browser-dependent)
- `retry_with_backoff()` is implemented but **never used** in the real code path

**Architectural Decision:**

**Reject the current Streams-created subscription model entirely:**

1. ✅ Order creation (native PHP API, synchronous)
2. ✅ Order status transitions to `'completed'` (WordPress/payment gateway)
3. ✅ `woocommerce_order_status_completed` hook fires (guaranteed, server-side)
4. ✅ Check if order contains subscription product: `wcs_order_contains_subscription($order_id)`
5. ✅ If yes, Subscriptions plugin auto-creates the subscription (built-in WCS behavior)
6. ✅ Do NOT manually create subscriptions; let WCS handle it

**For renewal payments:**
- WCS handles all renewals via Action Scheduler (internal)
- No custom code required
- Recurring Referrals add-on (v1.9.2) hooks `woocommerce_subscription_renewal_payment_complete`

**Consequence:** This resolves Kilo's §Gap 3 discovery — the architecture no longer needs separate subscription creation code.

## CHALLENGE 8: Challenge Reconciliation/Retry Design

**Challenge Block:** "Can a simple webhook/hook-based model handle all failure cases, or is a durable queue required?"

### Architectural Resolution

**Hybrid model required: Hooks for happy path, durable queue for recovery:**

**Observed Failures (Kilo F-02, F-09, F-10, F-11):**
- Wallet credit is not idempotent (repeated webhook → double credit)
- Financial writes are not atomic
- Subscription creation fails mid-flight with no recovery
- Browser-triggered `wp_footer` fulfilment is abandoned on browser close

**Architectural Decision:**

**Use the `bzj-connections-sync.php` pattern exactly (already production-proven):**

```php
// Create a durable queue table
CREATE TABLE wp_bzj_payment_events (
  id               BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  event_uuid       VARCHAR(36) UNIQUE NOT NULL,    -- idempotency key
  payment_intent_id BIGINT UNSIGNED NOT NULL,
  event_type       ENUM('order_created','payment_completed','subscription_created','referral_created','jewel_credited','streams_synced'),
  status           ENUM('pending','processing','completed','failed','terminal_failed') DEFAULT 'pending',
  attempts         INT UNSIGNED DEFAULT 0,
  max_attempts     INT UNSIGNED DEFAULT 12,
  next_attempt_at  TIMESTAMP,
  last_error       TEXT,
  processed_at     TIMESTAMP,
  created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  KEY (status, next_attempt_at),
  KEY (payment_intent_id)
) ENGINE=InnoDB;
```

**Flow (synchronous on happy path, async on retry):**

1. **Happy path (synchronous):**
   - `woocommerce_order_status_completed` hook fires
   - Insert a row into `wp_bzj_payment_events` with `status='pending'`
   - Call handler immediately (inline)
   - On success, mark `status='completed'`
   - On error, increment `attempts` and set `next_attempt_at = now() + backoff(attempts)`

2. **Scheduled recovery (hourly cron, following `bzj-connections-sync.php:931-934`):**
   ```php
   wp_schedule_event(time(), 'hourly', 'bzj_payment_events_recover');
   ```
   - Query: `SELECT * FROM wp_bzj_payment_events WHERE status='pending' AND next_attempt_at <= NOW() LIMIT 100`
   - For each row, acquire MySQL `GET_LOCK('bzj_payment_' . $intent_id, 15)` (reentrancy guard)
   - Retry the handler
   - Update `status` and `next_attempt_at`
   - Release lock
   - Log outcome

3. **Terminal failure:**
   - After 12 attempts (MAX_ATTEMPTS), mark `status='terminal_failed'`
   - Require manual intervention or admin-initiated retry

**Reconciliation (also following precedent):**

```php
wp_schedule_event(time(), 'hourly', 'bzj_payment_events_reconcile');
```
- Query last 7 days of completed payment intents
- For each, verify:
  - WooCommerce order exists and is paid
  - Subscription exists (if expected)
  - Referral exists (if expected)
  - Streams state is synchronized
  - Wallet is credited
- If a step is missing, insert a recovery event

**Idempotency Enforcement:**
- Every handler is idempotent (can be called multiple times safely)
- Guarded by `event_uuid` (unique constraint)
- Each financial operation checked for "already applied" before executing

**Challenge Status: RESOLVED** ✅

## CHALLENGE 9: Challenge Migration and Rollback

### Architectural Resolution

**Staged, reversible deployment model:**

1. Deploy new MU plugin `bzj-payment-gateway.php` in **disabled mode** (feature flag)
2. No traffic routed yet
3. Schema created but no data written

**Phase 1 — Shadow mode (0% production traffic):**

**Phase 3 — Ramp (10% → 50% → 100%):**
- Gradual increase of traffic to new bridge

1. **If Phase 1 Shadow shows unrecoverable defects:**
   - Disable feature flag
   - New bridge stops executing
   - Existing bridge continues
   - Manual cleanup of partial payment intents (small batch expected)
   - No customer impact; payment continues on old path

2. **If Phase 2/3 shows data divergence:**
   - Route new traffic back to existing bridge
   - Let new bridge drain (existing in-flight payments complete)
   - Manual reconciliation of divergent payment intents

3. **If production fails at 100%:**
   - Feature flag `BZJ_PGB_ROLLBACK = true`

- New bridge creates new payment intents for new requests only
- Old bridge continues handling old intents until manually archived
- Dual-running period: 6 months minimum (until old intents are naturally aged out)

**Rollback Complexity:**
- ✅ Low: New code runs in a feature flag
- ✅ Reversible: Disable flag → existing bridge active
- ⚠️ Medium: Existing in-flight payments may have state in both systems
- ⚠️ Requires reconciliation logic to detect and repair divergence

### Architectural Resolution

**Architectural Decision:**

Streams → WordPress handoff is signed and durable:

**Step 1 — Streams creates a payment intent in its database:**
```php
// streams/assets/wow-pgb/wow-pgb_client.php
$intent = [
    'id' => uniqid('intent_'),
    'user_id' => $user_id,
    'product_id' => $product_id,
```

**Step 2 — Streams signs a token and redirects:**
```php
$secret = getenv('BUZZ_SSO_SECRET'); // or fallback
$payload = [
    'intent_id' => $intent['id'],
    'user_id' => $user_id,
    'iss' => 'streams',
    'aud' => 'wordpress',
    'exp' => time() + 600,  // 10 minute expiry
    'nbf' => time(),        // not-before

$token = JWS::sign($payload, $secret, 'HS256');
header("Location: https://buzzjuice.net/wp-json/bzj-pgb/v1/payment-intent?token=$token");
```

**Step 3 — WordPress validates and stores:**
```php
// bzj-payment-gateway.php (MU plugin)
$token = $_GET['token'];
$payload = JWS::verify($token, $secret, 'HS256');

// Verify claims
if ($payload['exp'] < time()) return 403; // Expired
if ($payload['iss'] !== 'streams') return 403; // Wrong issuer
if ($payload['aud'] !== 'wordpress') return 403; // Wrong audience

// Dedupe on jti (JWT ID)
if (get_option('bzj_pgb_replay_' . $payload['jti'])) {
    return 409; // Already processed (replay attempt)
}

// Mark as seen
set_transient('bzj_pgb_replay_' . $payload['jti'], 1, 600);

// Fetch Streams intent (verify it exists)
$streams_intent = fetch_from_streams_db(...);
if (!$streams_intent) return 404;

// Create WordPress payment intent
create_payment_intent($streams_intent);
```

**Replay Prevention:**
- ✅ `jti` (JWT ID) is unique per request (use client-side nonce)
- ✅ Checked against a transient (expires after token expiry)
- ✅ Even if token is replayed, second call finds existing intent and returns 409

**CSRF Prevention:**
- ✅ Token signed with server secret (attacker cannot forge)
- ✅ `nbf` and `exp` claims enforce time window (token is valid for 10 minutes only)
- ✅ No form-based POST required (GET with token query param is safe for idempotent operations)

**Upgrade if needed (post-Phase-1):**
- Use asymmetric signing (RS256) if Streams and WordPress operate independently
- Add rate limiting on handoff endpoint
- Log all handoff attempts for audit

## CHALLENGE 11: Challenge Concurrent Payment / Idempotency Scenarios

**Challenge Block:** "Can the system handle: duplicate requests, double-submit, concurrent payments by same user, race conditions?"

### Architectural Resolution

**Idempotency enforced at three levels:**

**Level 1 — Request Deduplication (Streams side):**
```php
$idempotency_key = hash('sha256', $user_id . '|' . $product_id . '|' . $units . '|' . $selected_currency);
$stmt = $db->prepare("SELECT id FROM wo_payment_intents_streams WHERE idempotency_key = ?");
$stmt->execute([$idempotency_key]);
if ($stmt->fetch()) {
    return ['redirect_url' => ..., 'message' => 'Payment already initiated'];
}
// Proceed to create intent
```

**Level 2 — Database Uniqueness Constraint:**
```sql
UNIQUE KEY (idempotency_key)
```
- Streams side: prevents duplicate intent creation
- WordPress side: prevents duplicate payment intent creation
- Even if two concurrent requests arrive, one succeeds, one fails with constraint violation (idempotent response)

**Level 3 — Processed Marker (WordPress side):**
```php
if (get_post_meta($order_id, '_bzj_pgb_processed', true)) {
    return; // Already handled this order, skip
}
update_post_meta($order_id, '_bzj_pgb_processed', 1);
```

**Scenario Tests:**

| Scenario | Handling | Outcome |
|---|---|---|
| **Duplicate form submission (double-click)** | Same `idempotency_key` triggers DB constraint → client sees "already pending" | ✅ User sees previous intent |
| **Browser back/forward refresh** | `idempotency_key` allows second call to see existing intent | ✅ No duplicate intent |
| **Webhook delivered twice** | `_bzj_pgb_processed` marker prevents re-execution | ✅ Idempotent |
| **Concurrent payments by same user** | Different products/units → different `idempotency_key` → allowed | ✅ Concurrent user allowed |
| **Race condition in wallet credit** | MySQL `GET_LOCK('bzj_payment_' . $intent_id)` (reentrancy guard) | ✅ Serialized credit |
| **Same order completed twice** | `_bzj_pgb_processed` checked before AffiliateWP call; `_affwp_bridge_processed` checked in bridge | ✅ Single affiliate credit |

**Challenge Status: RESOLVED** ✅

## CHALLENGE 12: Challenge Production Failure Scenarios

**Challenge Block:** "What happens in: DNS failure, payment gateway timeout, browser close, failed WooCommerce order, incomplete fulfilment?"

### Architectural Resolution

**Each failure mode has a mapped recovery path:**

| Failure Mode | Root Cause | Detection | Recovery |
|---|---|---|---|
| **DNS failure (cPanel observed)** | Streams webhook URL unresolvable from WordPress | WooCommerce webhook fails to deliver | Reconciliation cron detects WC order paid but Streams not synced; re-trigger webhook locally or via fallback endpoint |
| **Payment gateway timeout** | `send_woocommerce_request()` has no `CURLOPT_TIMEOUT` (Kilo F-01) | cURL hangs; PHP timeout | Add 30-second timeout; on timeout, insert recovery event; assume payment is pending and poll gateway status from cron |
| **Browser closes during checkout** | `wp_footer` subscription creation abandoned (Kilo F-11) | Order exists, subscription missing | Reconciliation cron checks: if order has subscription product but no subscription, create it manually via `wcs_create_subscription()` |
| **WooCommerce order creation fails** | API error / authentication / network (Kilo F-09) | REST call returns error; state is `'handoff_pending'` | Retry cron follows backoff; on max retries, insert `'terminal_failed'` event; admin manually reviews payment intent |
| **Subscription activation fails** | WCS compatibility issue / product misconfiguration | Order completed but subscription status is not 'active' | Reconciliation cron detects and auto-activates via `$subscription->update_status('active')` + `wcs_update_dates_after_early_renewal()` |
| **AffiliateWP commission missing** | Double-credit vector live (Kilo F-05 item 2) | Referral count mismatch | Audit log: check if referral exists; if yes, idempotency block worked; if no, reconciliation re-inserts |
| **Wallet double-credited** | Webhook delivered twice + no lock (Kilo F-02) | `Wo_Users.wallet` overstated | Reconciliation: compare actual wallet against sum of confirmed payments; correct via debit transaction |
| **Incomplete fulfillment** | Any step in post-payment chain failed | `payment_events` table has `'failed'` status | Reconciliation identifies failed event; re-runs handler; includes retry logic; escalates to admin after max retries |
| **Streams database unavailable** | Network partition / database down | Webhook call to Streams URL times out / 503 | Reconciliation cron polls Streams state; on failure, marks as `'pending'` with later retry; eventual consistency (within 24 hours) |
| **Jewel mapping misconfigured** | `bz_rebate_mapping_json` is invalid JSON | Jewel webhook throws error | Logging catches exception; event marked `'failed'`; admin corrects mapping; manually re-trigger webhook |

**Reconciliation Cron Workflow:**

```
Every hour:
  Query wp_bzj_payment_intents WHERE state IN ('fulfillment_complete') created > 24h ago
  For each intent:
    1. Verify WooCommerce order status is 'completed'
    2. Verify subscription exists (if expected)
    3. Verify referral created (if expected)
    4. Verify Streams synchronization (webhook delivered or fallback succeeded)
    5. Check wallet balance
    6. If any step missing, create recovery event
    7. Capture outcome in audit log
  
  Query wp_bzj_payment_events WHERE status IN ('failed', 'terminal_failed')
  For each:
    1. Check retry count and backoff
    2. If backoff expired, retry handler
    3. If max_attempts exceeded, escalate to admin dashboard
```

**Admin Dashboard (Phase 1 basic version):**
```
Buzzjuice → Payment Gateway
├── Summary
│   ├── Last 7 days payments: X
│   ├── Success rate: Y%
│   ├── Failed: Z (pending retry)
│   └── Terminal failures: N (require manual action)
├── Payment Intents (search, filter, view)
│   ├── State
│   ├── Streams user
│   ├── Amount / Currency
│   ├── WooCommerce order (link)
│   ├── Status
│   └── Actions: [View logs] [Retry] [Manual sync]
└── Recovery Events (audit trail)
```

**Challenge Status: RESOLVED** ✅
