# BZJ-PGB-0200 — Architectural Engineering Analysis

I have reviewed the three production-workflow guides and the current GitHub implementation evidence you supplied. The workflow guides strongly support your proposed **architecture-first → challenge → specification → implementation → independent validation → production** model. In particular, they establish GitHub as the engineering source of truth, require evidence before code, formal task packets, independent agent roles, explicit stop conditions, and a Challenge-Before-Build gate. 

There are also several important issues in the current Payment Gateway Bridge that mean **we should not yet give an implementation agent permission to redesign it**.

The most significant are:

* the current Streams bridge still creates WooCommerce orders through the REST API;
* the browser/client currently supplies financial values that ultimately enter the order payload;
* the current cURL implementation explicitly disables TLS verification;
* the Streams webhook contains a hard-coded webhook secret;
* the existing webhook and WordPress fulfilment paths overlap;
* AffiliateWP context is currently captured in Streams even though the authoritative processing already occurs on WordPress;
* subscription, wallet, Jewel Affiliate and Streams fulfilment responsibilities are distributed across several places;
* the browser redirect cannot be treated as a durable fulfilment mechanism;
* the current system does not yet appear to have a formal payment-intent state machine/reconciliation layer;
* and the proposed automatic filesystem-driven database recreation requires an architectural decision because the workflow guide explicitly warns against automatic schema rebuilding based solely on filesystem state. 

The following is therefore the **agent-facing Architectural Engineering Analysis**, rather than the final ADR. It is deliberately written so Claude, Jules and Copilot can independently investigate the repository and return evidence without prematurely implementing the proposed architecture.

# 22. Important Architectural Correction

The proposed architecture currently implies:

```text

 ↓

 ↓
browser redirect
 ↓
MU plugin
 ↓
WooCommerce
```

```text

↓
```

```text

↓

```

```text

```

from:

```text

```

and:

```text

```

and:

```text
Payment
```

and:

```text
Fulfilment
```

and:

```text
Reconciliation
```

The agent challenge must explicitly investigate this.

# BZJ-PGB-0300 — Cross-Agent Synthesis

I have reviewed the **six reports**: the first and second reports from Claude, GitHub/Copilot, and Jules. I have also incorporated your clarification that **`koware_iapd_db` is the authoritative database for all new Payment Intent tables**.

The reports are sufficiently convergent that we can now move from broad discovery into a **formal architecture-definition phase**. However, I would **not yet write the final ADR**. There are several points where the agents agree strongly, but there are also a few claims that need to be resolved before the ADR becomes authoritative.

The most important result is this:

> **The dropped-order problem is not fundamentally a WooCommerce API problem. It is a transaction-state, idempotency, recovery and fulfilment-coordination problem.**

The DNS/API issue is an important contributing failure mode, but replacing cURL alone would not make the payment system durable.

---

## 1. What all three agents substantially agree on

### 1.1 The current bridge has no durable Payment Intent layer

This is the strongest cross-agent conclusion.

The existing flow creates a `Wo_Payment_Transactions` row, then attempts WooCommerce order creation. If that call fails, the Streams transaction can remain without a WooCommerce order. The current implementation also generates a fresh `uniqid('wow_')` for each request, making repeated submissions capable of producing separate transactions/orders. Claude documents this explicitly, including the orphaned-row scenario. ([GitHub][1])

Jules reaches essentially the same conclusion and proposes a formal Payment Intent state machine and unique intent UUID. ([GitHub][2])

GitHub/Copilot likewise identifies the lack of durable transaction state as a primary architectural gap. ([GitHub][3])

### Architectural conclusion

The new system needs:

```text
Payment Intent
        ↓
WooCommerce Order
        ↓
Payment
        ↓
Fulfilment
        ↓
Reconciliation
```

rather than treating the existing Streams payment transaction row as the entire transaction lifecycle.

---

# 2. The new Payment Intent database is now settled

Your clarification resolves an important open architectural question:

> **All new Payment Intent tables belong in `koware_iapd_db`.**

That should become an explicit architectural constraint for the next phase.

So the architecture should now be:

```text
                    BZJ PAYMENT ENGINE
                           │
                           ▼
                    koware_iapd_db
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼                   ▼
          Payment Intents       Payment Events
                 │                   │
                 └─────────┬─────────┘
                           │
                           ▼
                      WooCommerce
```

Existing platform databases remain where they currently belong.

For example:

```text
Streams DB
    └── existing Wo_* tables

WordPress DB
    └── WooCommerce
    └── Subscriptions
    └── AffiliateWP

koware_iapd_db
    └── NEW BZJ-PGB payment-intent tables
    └── NEW BZJ-PGB event/recovery tables
```

This is a significant improvement over having the new payment state depend upon the Streams database.

---

# 3. The browser must no longer be part of transaction integrity

This is another strong point of convergence.

The current architecture has several points where the browser participates in the transaction lifecycle.

The agents identify failure modes such as:

```text
Streams request
      ↓
transaction inserted
      ↓
WooCommerce order creation
      ↓
redirect
      ↓
browser closes
```

leaving an incomplete transaction.

Claude's failure analysis specifically identifies failed HTTP calls, lost responses, browser closure, duplicate submissions, invalid checkout URLs and post-payment synchronization failures as separate failure classes. ([GitHub][1])

### Therefore:

The browser should only perform:

```text
USER EXPERIENCE
```

not:

```text
TRANSACTION CONTROL
```

The browser may navigate to WooCommerce, but the server-side Payment Intent must already exist and remain recoverable if the browser disappears.

---

# 4. Native WooCommerce execution is now the leading architecture

This is where the reports become particularly useful.

Jules evaluates multiple approaches and rejects both:

* direct browser cart manipulation; and
* simply keeping the existing cURL architecture with minor fixes.

Jules instead proposes WordPress-native WooCommerce order creation after a signed handoff. ([GitHub][2])

The proposed model is:

```text
Streams
   │
   │ create Payment Intent
   ▼
koware_iapd_db
   │
   │ signed handoff
   ▼
WordPress
   │
   │ native WooCommerce PHP APIs
   ▼
WC_Order
   │
   ▼
checkout/payment
```

This is substantially cleaner than:

```text
Streams
   │
   │ cURL
   ▼
buzzjuice.net
   │
   ▼
WooCommerce REST API
```

because it removes the cPanel → same-domain DNS dependency from the critical order-creation path.

However, this is **not yet an ADR-approved decision**.

We still need one targeted technical verification of the installed WooCommerce version and its native order/payment URL behaviour before formally committing to it.

---

# 5. The cPanel DNS problem is a symptom, not the architecture

This distinction is important.

The observed:

```text
curl: (6) Could not resolve host: buzzjuice.net
```

is real evidence from the cPanel environment, and Jules records it. ([GitHub][2])

But we should not write the ADR as:

> "The WooCommerce REST API cannot be used because cPanel cannot resolve buzzjuice.net."

That is too strong.

The correct architectural statement is:

> **The current synchronous self-referential HTTP dependency is operationally fragile in the current hosting environment and should not be a required component of the critical payment-intent/order-creation path.**

That remains true even if DNS is subsequently repaired.

The native WordPress architecture is therefore preferable because it removes an unnecessary network boundary.

---

# 6. The current financial-security problem is more serious than initially understood

Claude identifies that the Streams initiation endpoint accepts:

```text
amount
product_name
product_price
product_units
product_owner_id
transaction_kind
wow_currency_code
```

from `$_POST` and forwards those values into the WooCommerce order. ([GitHub][1])

That means the architecture currently has a potentially dangerous trust boundary:

```text
Browser
   ↓
financial parameters
   ↓
Streams
   ↓
WooCommerce
```

The new architecture should instead use:

```text
Browser
   ↓
product/transaction request
   ↓
Streams server
   ↓
authoritative product/configuration lookup
   ↓
authoritative amount
   ↓
authoritative currency
   ↓
Payment Intent
```

This is a **CRITICAL architectural requirement**.

The browser can request:

> "I want product X."

It should not be authoritative for:

> "Product X costs GHS 37.50."

---

# 7. Idempotency becomes a first-class subsystem

This is probably the most important technical addition to the original proposal.

Jules proposes:

```text
intent_uuid
UNIQUE(intent_uuid)
```

and:

```text
idempotency_key
UNIQUE(idempotency_key)
```

along with WooCommerce order metadata:

```text
_wow_intent_uuid
```

so the WordPress handoff can find an existing order instead of creating another one. ([GitHub][2])

That is the correct direction.

The system needs idempotency at **multiple levels**, not just one.

### Level 1 — Intent creation

```text
same request
      ↓
same idempotency key
      ↓
same Payment Intent
```

### Level 2 — WooCommerce order creation

```text
Payment Intent
      ↓
existing WC order?
      ├── yes → reuse
      └── no  → create
```

### Level 3 — Payment completion

```text
WC order completed
      ↓
already fulfilled?
      ├── yes → no-op
      └── no  → fulfil
```

### Level 4 — Financial effects

Each financial effect must independently be idempotent:

```text
Wallet
AffiliateWP
Jewel rebate
Funding
Subscription
Streams entitlement
```

This is critical because a single global:

```text
_affwp_bridge_processed
```

flag cannot protect unrelated effects.

GitHub/Copilot explicitly identifies this limitation. ([GitHub][3])

---

# 8. The wallet problem is a CRITICAL finding

The existing webhook performs:

```text
wallet = wallet + amount
```

without first establishing that the transaction has not already been credited.

Jules identifies this directly. ([GitHub][2])

Therefore:

```text
Webhook #1
    wallet + 50

Webhook #2
    wallet + 50
```

can produce:

```text
+100
```

from a single payment.

This is more than a reliability bug.

It is a **financial-integrity vulnerability**.

The new architecture therefore needs an effect-level idempotency record or equivalent atomic mechanism.

---

# 9. AffiliateWP should remain WordPress-side

The reports reinforce the direction already identified in BZJ-PGB-0200.

The Streams-side AffiliateWP cookie snapshot should not become the authoritative AffiliateWP mechanism.

Instead:

```text
WooCommerce
     ↓
AffiliateWP
     ↓
referral/commission
```

should remain a WordPress responsibility.

The existing working AffiliateWP implementation should therefore be **extracted/reorganized rather than casually rewritten**.

The new bridge should provide the appropriate authoritative WooCommerce metadata needed by AffiliateWP, while AffiliateWP remains responsible for its own referral processing.

---

# 10. Jewel Affiliate needs separation from core payment processing

Claude identifies an important existing problem: the Jewel Affiliate webhook appears to be intended to run from the completed payment path, but its wiring is uncertain. Claude also identifies duplicated Pro activation logic and direct serialized capability writes. ([GitHub][1])

This suggests the new architecture should separate:

```text
CORE PAYMENT
```

from:

```text
JEWEL AFFILIATE INTEGRATION
```

Conceptually:

```text
Payment completed
        │
        ▼
Core fulfilment
        │
        ├── Subscription
        ├── Streams entitlement
        ├── AffiliateWP
        └── Jewel Affiliate
```

but each integration gets its own idempotent processing state.

That makes Jewel an integration rather than a dependency embedded inside the payment engine.

---

# 11. The Payment State Machine is now clearly required

Jules' proposed state model is one of the strongest pieces of the reports:

```text
CREATED
   ↓
VALIDATED
   ↓
HANDOFF_PENDING
   ↓
WC_ORDER_CREATED
   ↓
PAYMENT_PROCESSING
   ↓
PAYMENT_COMPLETED
   ↓
POST_PAYMENT_SYNC
   ↓
COMPLETED
```

with:

```text
FAILED
EXPIRED
RECOVERY_REQUIRED
CANCELLED
```

as additional states. ([GitHub][2])

I recommend retaining the concept but **not copying the exact state names into the ADR yet**.

We should first normalize the state machine against:

* WooCommerce order states;
* WooCommerce Subscriptions;
* payment gateway callbacks;
* Streams transaction states;
* reconciliation;
* retry states.

The Payment Intent state machine should represent **Buzzjuice's transaction orchestration**, not duplicate WooCommerce's order state machine.

---

# 12. Recovery becomes a formal subsystem

This is where the new architecture becomes substantially more durable.

We should be able to query:

```text
Payment Intent:
PI-123

Status:
PAYMENT_COMPLETED

WooCommerce:
Order 456

Fulfilment:
INCOMPLETE

AffiliateWP:
COMPLETE

Jewel:
FAILED

Streams:
NOT_SYNCED
```

and then recover only the missing effects.

Rather than:

```text
"run the whole payment again"
```

we want:

```text
retry Jewel
retry Streams entitlement
```

without:

```text
retry payment
retry wallet
retry AffiliateWP
```

This is the difference between **transaction retry** and **effect retry**.

---

# 13. The new IAPD tables should probably be more than one table

The exact schema should be decided in the ADR/specification phase, but the reports suggest that a single:

```text
bzj_payment_intents
```

table may not be sufficient.

A more scalable conceptual model is:

```text
koware_iapd_db

bzj_payment_intents
        │
        ├── bzj_payment_events
        │
        ├── bzj_payment_effects
        │
        └── bzj_payment_attempts
```

Potential responsibilities:

### `bzj_payment_intents`

The durable business transaction.

### `bzj_payment_events`

Immutable lifecycle/event history.

### `bzj_payment_effects`

Tracks individual downstream effects:

```text
subscription
wallet
affiliatewp
jewel
streams_entitlement
funding
```

### `bzj_payment_attempts`

Tracks retries and operational attempts.

This is **not yet an approved schema**. It is the architecture question I recommend we take into BZJ-PGB-0310.

# 14. Database migration strategy is now easier to resolve

Because the authoritative database is explicitly:

```text
koware_iapd_db
```

we can avoid the dangerous design of:

```text

        ↓
automatically mutate schema
```

Instead, use:

```text
Git
 ↓
versioned migration

IAPD schema version
 ↓
explicit deployment
```

The runtime can still perform an integrity check:

```text
Does required schema exist?
```

but should not blindly reconstruct arbitrary tables merely because an addon directory appeared.

That should be a firm architectural distinction.

## BZJ-PGB-0310 — Architecture Verification Synthesis

### 1. The most important finding: the problem is larger than the REST call

The agents now provide strong evidence that the dropped-order problem has **three separate failure boundaries**:

**Initiation**

`Streams → cURL → WooCommerce REST API`

This is vulnerable to the demonstrated cPanel DNS/loopback failure.

**Payment**

`WooCommerce → payment gateway`

This can successfully charge the customer even when downstream Buzzjuice fulfilment fails.

**Post-payment fulfilment**

`WooCommerce → browser Thank-You page / Streams webhook → subscriptions / AffiliateWP / Streams`

The verification shows that significant post-payment processing is still dependent on browser navigation. If the customer closes the browser, loses connectivity, or the page times out, some fulfilment operations do not happen. Kilo specifically verified the `wp_footer` path and its potentially very long retry/sleep behaviour. ([GitHub][1])

So the architectural objective should now be:

> **A successful payment must become a durable server-side transaction whose fulfilment can complete independently of the customer's browser, with each financial/entitlement effect independently idempotent and recoverable.**

That is stronger than simply replacing cURL.

---

# 2. A major new finding: the current amount/currency model is unsafe

This is probably the most important new discovery from the verification.

The current Streams frontend calculates the amount and sends `amount` and `product_price` to `wow-pgb_init.php`. Kilo traced that data all the way into the WooCommerce REST request. ([GitHub][1])

But WooCommerce 11.1.0 then recalculates product line totals from the actual WooCommerce product price when a real product ID is supplied.

At the same time, Kilo found that the installed FOX/WOOCS integration disables itself for the `/wp-json/wc/v3/*` route. Consequently, the existing REST-created order is not receiving the same currency conversion that the storefront displays. ([GitHub][1])

This means we should **not** carry forward the existing model of:

> Streams calculates amount → payment bridge trusts amount → WooCommerce receives amount.

Instead:

> **Payment Intent identifies what is being purchased → WordPress/WooCommerce resolves the authoritative product, price, currency and applicable conversion → Woo order is created from authoritative server-side values.**

This is a fundamental architecture requirement.

It also means we should **not approve the final currency architecture yet** until the actual live prices of the `wow-pgb_*` products/variations are verified. Kilo found that the repository's product-creation routine sets prices to zero and that its activation hook appears not to execute from the file where it is registered. Therefore the production product prices cannot safely be inferred from source code. ([GitHub][1])

### Required evidence before ADR

We need a production/staging database dump of:

* every `wow-pgb_*` product
* every relevant variation
* `_price`
* `_regular_price`
* product type
* variation/product relationship
* WooCommerce currency
* relevant WOOCS configuration/rates
* existing subscription product configuration

**This should be a hard gate before the final currency/order model is approved.**

# 3. Native WooCommerce execution is now strongly supported

The verification confirms:

* WooCommerce **11.1.0**
* `wc_create_order()`
* native `WC_Order` APIs
* `WC_Order::get_checkout_payment_url()`
* native WooCommerce order creation
* WooCommerce Subscriptions
* Action Scheduler

are all available in the installed environment. ([GitHub][1])

More importantly, WooCommerce REST has **no built-in idempotency protection for repeated order creation**. Retrying a REST order creation request can therefore create another order. ([GitHub][1])

That gives us a very strong architectural distinction:

### Current

```text
Streams
   │
   │ HTTP/cURL
   ▼
Woo REST API
   │
   ▼
Woo Order
```

### Proposed

```text
Streams
   │
   │ signed intent
   ▼
WordPress
   │
   │ native PHP
   ▼
WooCommerce
   │
   ▼
Woo Order
```

The second architecture removes the critical same-server HTTP dependency and gives us direct access to the installed WooCommerce APIs.

This is now sufficiently evidence-backed to become the **leading architecture candidate**.

It is not yet an approved ADR decision.

---

# 4. Payment Intent database is now locked

Your clarification is important and should be incorporated into the architecture baseline:

> **All new Payment Gateway Bridge database tables will be created in `koware_iapd_db`.**

The verification confirms that the repository already contains `get_iapd_db_conn()` and that `IAPD_DB_NAME` is supplied through the environment as `koware_iapd_db`. No existing IAPD schema was found in the repository. ([GitHub][2])

Therefore our architecture baseline should now state:

```text
Payment Intent / orchestration database
        ↓
koware_iapd_db
```

Not:

```text
wp_bzj_payment_intents
```

and not:

```text
koware_buzzjuice
```

unless a future architecture decision specifically determines that an existing WP table must be modified.

### Important distinction

Existing system tables remain where they are.

For example:

```text
koware_iapd_db
    └── BZJ-PGB orchestration tables

koware_buzzjuice
    └── existing WP/Woo/WordPress data

koware_buzzjuice_streams
    └── existing WoWonder transaction/user data
```

The bridge can modify existing tables in those databases when required, but **new BZJ-PGB state belongs in IAPD**.

The verification also found no existing IAPD migration framework, so the architecture will need to establish one rather than relying on filesystem-driven table creation. ([GitHub][1])

# 5. The Payment Intent should become the orchestration authority

I would now formalize the conceptual architecture as:

```text
                 ┌─────────────────────┐
                 │  Buzzjuice Streams   │
                 │     WoWonder        │
                 └──────────┬──────────┘
                            │
                       Create Intent
                            │
                            ▼
                 ┌─────────────────────┐
                 │   koware_iapd_db    │
                 │                     │
                 │ Payment Intent      │
                 │ Events              │
                 │ Attempts            │
                 │ Effects / Recovery  │
                 └──────────┬──────────┘
                            │
                     Signed handoff
                            │
                            ▼
                 ┌─────────────────────┐
                 │ WordPress / MU      │
                 │ bzj-payment-gateway│
                 └──────────┬──────────┘
                            │
                     Native Woo APIs
                            │
                            ▼
                 ┌─────────────────────┐
                 │    WooCommerce      │
                 │                     │
                 │ Order               │
                 │ Payment             │
                 │ Subscription        │
                 └──────────┬──────────┘
                            │
                    server-side events
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
        Streams         AffiliateWP     Jewel
        entitlement     commission      rebate
             │              │              │
             └──────────────┴──────────────┘
                            │
                            ▼
                      Reconciliation
```

The browser participates in the **handoff and payment UI**, but does not own transaction state.

# 6. Subscription architecture needs another correction

There is an important disagreement/evolution across the reports.

Earlier architecture material proposed various subscription hooks, but Kilo verified that some previously suggested hook names **do not exist** in the installed WooCommerce Subscriptions version. It specifically identified the real hooks such as:

* `woocommerce_subscription_payment_failed`
* `woocommerce_subscription_renewal_payment_complete`

and warned against planning around nonexistent hook names. ([GitHub][1])

Therefore:

**We should not yet write the subscription lifecycle into the ADR from memory or from the earlier reports.**

Instead, the final architecture verification must establish:

1. parent subscription creation
2. initial payment
3. subscription activation
4. renewal order creation
5. renewal payment completion
6. renewal failure
7. cancellation
8. expiration
9. suspension
10. Streams entitlement extension

This is particularly important because Streams currently receives entitlement updates through its own payment logic.

---

# 7. AffiliateWP is more complicated than previously thought

This is another important correction.

AffiliateWP 2.32.2 has a **native WooCommerce integration**, including:

* pending referral creation
* processing/completed referral handling

while the existing Buzzjuice bridge also invokes its own AffiliateWP processing. Kilo found overlapping triggers, potentially producing up to three invocations for a single order. ([GitHub][1])

So we should **not simply say "AffiliateWP is working, preserve it unchanged."**

The correct architectural statement is:

> **AffiliateWP is protected working functionality, but its current trigger topology must be rationalized during the redesign without changing its proven commission behaviour.**

That is different.

We preserve:

* commission calculations
* Lifetime Commissions
* Recurring Referrals
* Multi-Tier behaviour
* existing attribution semantics

but we need to determine **one authoritative BZJ-PGB orchestration point** and prevent competing triggers from producing duplicate effects.

The verification also found a concrete issue in the custom bridge: its referral creation path does not provide the same effective customer handling as assumed, and its duplicate detection has race/coverage weaknesses. ([GitHub][1])

That should therefore become part of the Architecture Challenge rather than being carried into implementation unchanged.

---

# 8. Jewel Affiliate is now definitively an addon

This is probably the clearest correction to the earlier architecture.

Kilo found that:

> `jewel_affiliate_process()` exists, but is not called.

The file's own documentation claims it is called from the completed webhook, but the webhook contains no such call. ([GitHub][1])

Therefore the previous assumption that Jewel Affiliate was currently functioning as part of the payment completion chain is **not supported by the repository evidence**.

This changes the architecture classification:

```text
Core payment processing
        │
        ├── Woo order
        ├── payment
        ├── subscription
        ├── Streams entitlement
        └── reconciliation

Optional/business addon
        │
        └── Jewel Affiliate
              ├── rebate
              ├── role mapping
              └── Jewel-specific entitlement
```

The Jewel code should therefore be moved conceptually into:

```text
shared/payment-gateway/addons/
```

rather than being part of the core payment engine.

And importantly:

**we should not preserve nonexistent behaviour merely because the old architecture document said it existed.**

---

# 9. Reconciliation is now a first-class subsystem

The verification found an existing Buzzjuice pattern that is extremely useful.

The Connections Sync project already has:

* durable DB-backed queue
* status
* attempts
* `next_attempt_at`
* `last_error`
* `processed_at`
* unique event UUID
* backoff
* maximum attempts
* terminal failure state
* reconciliation
* MySQL locking

Kilo explicitly identified this as the strongest existing recovery pattern in the repository. ([GitHub][1])

That gives us an excellent internal precedent.

I would therefore make the payment architecture:

```text
Payment processing
       +
Durable event/effect queue
       +
Retry
       +
Reconciliation
       +
Idempotency
```

rather than trying to make one giant WooCommerce completion callback perform everything synchronously.

# 10. The state machine should be refined

The earlier proposed state machine is directionally correct, but after verification I would separate **intent state** from **effect state**.

### Payment Intent

```text
CREATED
   ↓
VALIDATED
   ↓
HANDOFF_READY
   ↓
WC_ORDER_CREATED
   ↓
PAYMENT_PENDING
   ↓
PAYMENT_CONFIRMED
   ↓
FULFILMENT_PENDING
   ↓
COMPLETED
```

With terminal/error states:

```text
EXPIRED
CANCELLED
FAILED
RECOVERY_REQUIRED
```

But then individual effects have their own lifecycle:

```text
Streams entitlement
    PENDING → PROCESSING → COMPLETED
                       ↘ FAILED → RETRY

AffiliateWP
    PENDING → PROCESSING → COMPLETED
                       ↘ FAILED → RETRY

Jewel rebate
    PENDING → PROCESSING → COMPLETED
                       ↘ FAILED → RETRY
```

This prevents a failed AffiliateWP operation from causing us to re-run the entire payment transaction.

That distinction is fundamental for financial reliability.

# 11. Security architecture is also confirmed

Three security issues should now be treated as mandatory remediation:

### TLS verification

The existing Streams cURL code disables:

```text
CURLOPT_SSL_VERIFYHOST = 0
CURLOPT_SSL_VERIFYPEER = 0
```

That must disappear from the new payment path. ([GitHub][3])

### Webhook secret

The WooCommerce → Streams webhook secret is hardcoded.

Even more seriously, Kilo found that the admin-configured `wow_webhook_secret` is apparently not actually used by the verifier. ([GitHub][1])

Therefore:

> **The current webhook secret must be treated as compromised and replaced during migration.**

### Signed handoff

The existing Buzzjuice SSO architecture already provides a reusable HS256/JWT-style signing and verification pattern, including claim/replay discipline and environment-based secret resolution. ([GitHub][1])

That is a strong precedent for the BZJ-PGB signed handoff.

# 12. The logging architecture should be centralized

Your requirement for extensive toggleable logging remains appropriate.

But the verification suggests we should avoid creating dozens of unrelated log formats.

A central:

```text
BZJ-PGB logger
```

should expose stages such as:

```text
INTENT
HANDOFF
ORDER
PAYMENT
SUBSCRIPTION
STREAMS
AFFILIATE
JEWEL
RECOVERY
RECONCILIATION
SECURITY
MIGRATION
```

with a common correlation identifier:

```text
intent_uuid
```

and where applicable:

```text
wc_order_id
streams_user_id
wp_user_id
effect_id
event_id
```

The repository already has a structured/toggleable logging precedent that can be reused conceptually. ([GitHub][1])

Sensitive values must never enter these logs.

# 14. One thing I would NOT do yet

I would **not move directly to BZJ-PGB-0330 ADR approval yet**.

The Architecture Verification has closed most of the original evidence gaps, but there are still a few **architecture-blocking facts** that need to be resolved first.

### Mandatory remaining evidence

**A. Live WooCommerce product/variation pricing**

We need the actual `_price` / `_regular_price` values.

**B. Live currency configuration**

We need:

* WooCommerce base currency
* relevant WOOCS currencies
* current exchange-rate configuration
* which prices are stored in base currency
* what the customer is expected to pay in Streams

**C. WooCommerce Subscriptions**

Verify the actual installed subscription product structure and lifecycle used by the current Buzzjuice subscriptions.

**D. Existing `Wo_Payment_Transactions` production schema**

Kilo found that the repository SQL/schema and the columns used by the bridge appear to have drifted. That must be resolved before deciding exactly which existing columns should be retained, altered, or deprecated. ([GitHub][1])

**E. Production IAPD state**

The repository shows no schema, but the actual `koware_iapd_db` database needs to be inspected before the migration architecture is frozen.

**F. Production scheduling**

The repository does not establish whether WP-Cron is reliable in the actual production environment. The existing Streams OS-cron precedent may be preferable for payment recovery. ([GitHub][1])

---

## My architectural conclusion

The independent verification has now moved us from:

> **"We think a native WooCommerce handoff will fix the dropped orders."**

to something much stronger:

> **The current payment bridge has verified architectural failure modes at initiation, payment-to-fulfilment, browser-dependent post-payment processing, currency determination, duplicate financial effects, and recovery. A durable Payment Intent architecture with native WordPress/WooCommerce execution, server-authoritative pricing, effect-level idempotency, asynchronous recovery and reconciliation is therefore justified by the evidence.**

The proposed architecture is **not yet the final approved architecture**, because the live product/currency/subscription/database evidence still needs to be locked down.

### Recommended next stage

I recommend we make **BZJ-PGB-0320 — Architecture Challenge** the next formal stage.

Its purpose should be to attack the proposed architecture rather than merely refine it:

1. **Challenge the Native WooCommerce approach**
2. **Challenge the Payment Intent state model**
3. **Challenge the `koware_iapd_db` schema concept**
4. **Challenge currency/price authority**
5. **Challenge subscription lifecycle**
6. **Challenge AffiliateWP trigger ownership**
7. **Challenge Jewel addon isolation**
8. **Challenge reconciliation/retry design**
9. **Challenge migration and rollback**
10. **Challenge security and replay protection**
11. **Challenge concurrent-payment/idempotency scenarios**
12. **Challenge production failure scenarios**

Only if that challenge produces no unresolved architecture blocker should we proceed to **BZJ-PGB-0330 — ADR / Architecture Decision & Approval**.

This also preserves the original project rule: **no production implementation until the architecture has survived independent verification and challenge.**
