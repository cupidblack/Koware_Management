## EXECUTIVE SUMMARY

This report documents the forensic discovery of the existing Buzzjuice Market Payment Gateway Bridge implementation. The investigation examines the three primary payment processing files (`wow-pgb_init.php`, `wow-pgb_sync.php`, `wow-pgb_webhook.php`), supporting infrastructure, database schemas, and integration boundaries.

**Primary Finding:** The current architecture exhibits critical architectural gaps that directly support the reported dropped-order problem. The system lacks durable server-side transaction state, relies on browser-driven handoffs, and contains multiple race-condition vectors where payment intent can be lost.

## 2. ASSUMPTIONS

### 2.1 WooCommerce Order Creation Mechanism

**ASSUMPTION:** Based on the code structure and the presence of webhook processing, the order creation occurs via one of:

1. **REST API call** from `wow-pgb_init.php` (likely, but not visible in provided code excerpt)
2. **Browser redirect** to WooCommerce checkout with pre-populated order data
3. **cURL-based creation** as hinted by the historical analysis documents

**EVIDENCE:** The webhook handler expects a `$data['id']` (WooCommerce order ID), which suggests WooCommerce successfully creates an order before the webhook is fired.

**STATUS:** Requires inspection of the full `wow-pgb_init.php` file beyond line 158 to verify.

### 2.2 TLS Verification Status

**ASSUMPTION:** The cURL calls to WooCommerce REST API may have disabled TLS verification (as mentioned in the architectural document section 13).

**EVIDENCE:** The document references: "The current cURL implementation contains: CURLOPT_SSL_VERIFYHOST => 0, CURLOPT_SSL_VERIFYPEER => 0"

**STATUS:** Not found in the current code provided; may be in a section of `wow-pgb_init.php` not shown in search results.

### 2.3 Payment Intent Lifecycle

**ASSUMPTION:** Currently, payment intent existence is conflated with Streams transaction record in `Wo_Payment_Transactions`.

**EVIDENCE:** The schema lacks sufficient fields for full state tracking; webhook operations reference fields not in the Node.js model.

**STATUS:** This architecture is fragile and susceptible to loss if the Streams database transaction is interrupted.

### 2.4 Idempotency Mechanisms

**ASSUMPTION:** The only idempotency guard currently implemented is `_affwp_bridge_processed` in WordPress metadata.

**EVIDENCE:** `wow-pgb_sync.php` checks this guard before processing AffiliateWP logic.

**STATUS:** This guard only protects AffiliateWP; it does NOT protect against duplicate:
- WooCommerce order creation
- Subscription activation
- Wallet credit
- Funding contributions

## 3. INFERENCES

### 3.1 Dropped Order Root Cause — Browser Redirect Dependency

**INFERENCE:** The architecture relies on browser navigation to complete the payment flow:

```
Streams initiates
  ↓
Wo_Payment_Transactions INSERT
  ↓
Generate WooCommerce order (REST API or redirect)
  ↓
User redirected to WooCommerce checkout
  ↓
User completes payment
  ↓
WooCommerce fires webhook
  ↓
Streams webhook processes
```

If **any** of these steps fail or the browser closes:
- Payment intent record exists in Streams (`Wo_Payment_Transactions`)
- But WooCommerce order may not exist
- Or WooCommerce order exists but webhook never fires
- Or webhook fires but processing fails

**EVIDENCE:** No durable transaction state exists outside of Streams' `Wo_Payment_Transactions`, which contains no payment status tracking, no WooCommerce order reference initially, and no recovery/retry metadata.

### 3.2 Race Condition — Duplicate Orders

**INFERENCE:** The current system has no protection against duplicate WooCommerce order creation:

If a user submits the payment form twice (browser double-click, network retry):
1. Two `Wo_Payment_Transactions` records created (different `order_id` values)
2. Two WooCommerce orders initiated
3. Two webhooks may fire
4. Two wallet credits / subscription activations occur

**EVIDENCE:** The `uniqid('wow_')` order ID generation creates unique Streams IDs, but there is no check in `wow-pgb_init.php` for duplicate intent before creating a new transaction record.

### 3.3 Webhook Reliability — Single Delivery Assumption

**INFERENCE:** The webhook processing assumes **single delivery**:

```php
if (in_array($order_status, ["completed"])) {
    // Process wallet, funding, subscription directly
}
```

WooCommerce webhooks may be **retried** on failure, yet the code contains minimal idempotency:

- Wallet update: `UPDATE Wo_Users SET wallet = wallet + $amount` — **NOT idempotent** if webhook retried
- Funding insert: `INSERT INTO Wo_Funding_Raise` — **NOT idempotent** (no duplicate key)
- Pro update: `UPDATE Wo_Users SET pro_time=?` — **NOT idempotent** if timestamp changes
- Subscription activation: called via MU plugin hook, relies on `_affwp_bridge_processed` guard

**EVIDENCE:** If a webhook is delivered twice:

```
First delivery:
  wallet = 100 + 50 = 150
  
Second delivery (retry):
  wallet = 150 + 50 = 200  ❌ DUPLICATE CREDIT
```

### 3.4 Email-based User Resolution — Fragile

**INFERENCE:** WooCommerce webhook resolves WoWonder user via email lookup:

```php
$user_id = getUserIdByEmail($customer_email, $db)
```

If:
- Customer email is misspelled in WooCommerce
- Or customer email differs between Streams and WooCommerce
- Or user has multiple accounts with different emails

The webhook cannot resolve the correct user and silently fails with `User ID not found for email: $customer_email`.

**EVIDENCE:** Line 272 in webhook: `error_log("User ID not found for email: $customer_email")` — but no alert/remediation mechanism.

### 3.5 Metadata Dependency — Complex Handoff

**INFERENCE:** The webhook extraction logic is fragile:

```php
$order_id = null;
if (!empty($data['meta_data'])) {
    foreach ($data['meta_data'] as $meta) {
        if ($meta['key'] === 'wow_order_id') {
            $order_id = $meta['value'];
            break;
        }
    }
}
```

Multiple issues:
1. If metadata is missing, `$order_id` remains null
2. The webhook continues processing with null values
3. Silent failures in subsequent conditional checks

**EVIDENCE:** The code does not validate that required metadata exists before processing.

### 3.6 State Loss During Browser Close

**INFERENCE:** If the browser closes during checkout:

```
Streams: Wo_Payment_Transactions INSERT ✓
Browser: Redirect to WooCommerce ✓
WooCommerce: Order created ✓
Browser: User closes/navigates away
WooCommerce: Payment never submitted
Webhook: Never fires
Streams: Order remains in perpetual "pending" state
```

No reconciliation mechanism exists to:
- Detect incomplete orders
- Retry payment
- Notify customer
- Clean up abandoned intents

**EVIDENCE:** The webhook only processes "completed" status; no handling for "pending" recovery.

### 3.7 Subscription Activation Ordering

**INFERENCE:** WooCommerce Subscription activation depends on precise sequencing:

```
1. Order status → completed
2. MU plugin hook fires (buzzjuice-affwp-order-complete.php)
3. Calls bluecrown_affiliatewp_post_checkout_verification()
4. Inside: activate WCS subscription via variation metadata
```

If:
- The MU plugin doesn't load
- Or the hook fires before metadata is set
- Or variation_id metadata is missing

The subscription is never activated, but payment succeeds.

**EVIDENCE:** `wow-pgb_sync.php` performs WoWonder user pro-type verification via API call with retry logic, suggesting timing sensitivity.

### 3.8 Currency Conversion — Unexplored

**INFERENCE:** The current code accepts browser-supplied currency:

```php
$wow_currency_code = htmlspecialchars($_POST['wow_currency_code'], ENT_QUOTES, 'UTF-8')
```

No validation that this currency:
- Matches Streams source currency
- Matches WooCommerce base currency
- Is actually exchanged properly
- Or if WOOCS conversion is applied

**EVIDENCE:** The architectural document (section 20) flags this as a critical concern: "For example: ZAR 500 must never become GHS 500 merely because the WooCommerce store base currency is GHS."

Current code does not prevent this scenario.

### 3.9 Logging — No Correlation

**INFERENCE:** Logging exists but is not correlated across the payment lifecycle:

- Streams logs: `error_log("🟡 WooCommerce Payment Init: Incoming POST...")`
- Webhook logs: `error_log("WooCommerce Webhook Data Received. Processing Order....")`
- Sync logs: `error_log("✅ (wow-pgb_sync.php) User's WordPress role matches WoWonder post ID.")`

No common `correlation_id` or `request_id` ties these together. Debugging a dropped order requires:
1. Find Streams transaction ID
2. Search webhook logs for that ID
3. Search sync logs for order-related entries
4. Cross-reference across three separate log streams

**EVIDENCE:** No `correlation_id` or `idempotency_key` in the transaction schema.

## 14. ARCHITECTURAL OPTIONS

### OPTION A: Minimal Durable State Layer (Recommended Initial Step)

**Description:**

Extend `Wo_Payment_Transactions` with payment-intent fields; add idempotency mechanism within Streams database.

```sql
ALTER TABLE Wo_Payment_Transactions ADD COLUMN (
  idempotency_key VARCHAR(255) UNIQUE,
  correlation_id VARCHAR(255),
  woo_order_id BIGINT,
  payment_status ENUM('pending', 'processing', 'completed', 'failed', 'cancelled'),
  fulfillment_status ENUM('pending', 'processing', 'completed', 'failed'),
  intent_created_at TIMESTAMP,
  intent_expires_at TIMESTAMP,
  last_error VARCHAR(500)
);
```

**Pros:**
- Minimal schema changes
- Leverages existing Streams database
- Lower migration risk
- Can be implemented incrementally

**Cons:**
- Streams database used for payment state (architectural coupling)
- Doesn't solve multi-database recovery scenario
- Limited to Streams availability

**Recommendation:** Suitable as Phase 1; prepare migration path to IAPD in Phase 2.

---

### OPTION B: Separate IAPD Payment Intent Table (Proposed)

**Description:**

Implement durable payment-intent storage in separate `koware_iapd_db` via `get_iapd_db_conn()`.

```sql
-- In IAPD database
CREATE TABLE bzj_payment_intents (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  intent_uuid VARCHAR(36) UNIQUE,
  idempotency_key VARCHAR(255) UNIQUE,
  correlation_id VARCHAR(255),
  
  streams_user_id INT,
  wp_user_id INT,
  woo_user_id INT,
  
  transaction_kind VARCHAR(50),
  product_id VARCHAR(100),
  
  source_currency CHAR(3),
  source_amount DECIMAL(19,2),
  base_currency CHAR(3),
  base_amount DECIMAL(19,2),
  checkout_currency CHAR(3),
  checkout_amount DECIMAL(19,2),
  exchange_rate DECIMAL(19,6),
  
  wc_order_id BIGINT,
  wc_order_key VARCHAR(100),
  wc_payment_url TEXT,
  
  intent_status VARCHAR(50),
  payment_status VARCHAR(50),
  fulfillment_status VARCHAR(50),
  redirect_status VARCHAR(50),
  
  subscription_status VARCHAR(50),
  affiliate_status VARCHAR(50),
  jewel_affiliate_status VARCHAR(50),
  streams_fulfillment_status VARCHAR(50),
  
  attempt_count INT DEFAULT 0,
  last_attempt_at TIMESTAMP,
  next_retry_at TIMESTAMP,
  last_error_code VARCHAR(50),
  last_error_message VARCHAR(500),
  
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  validated_at TIMESTAMP,
  handoff_at TIMESTAMP,
  payment_completed_at TIMESTAMP,
  fulfillment_completed_at TIMESTAMP,
  completed_at TIMESTAMP,
  expires_at TIMESTAMP,
  updated_at TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  
  UNIQUE KEY idx_intent_uuid (intent_uuid),
  UNIQUE KEY idx_idempotency (idempotency_key),
  KEY idx_correlation (correlation_id),
  KEY idx_streams_user (streams_user_id),
  KEY idx_woo_order (wc_order_id),
  KEY idx_status (intent_status, payment_status),
  KEY idx_expires (expires_at)
);
```

**Pros:**
- Durable, separate from application databases
- Supports recovery and reconciliation
- Full state machine support
- Independent of Streams availability
- Audit trail via timestamps

**Cons:**
- Requires new database connection
- Migration more complex
- Operational overhead (schema management, backups)

**Recommendation:** Better long-term architecture; requires explicit approval.

---

### OPTION C: Hybrid — IAPD Intent + Wo_Payment_Transactions Sync

**Description:**

Implement IAPD payment-intent table (Option B) but maintain Streams `Wo_Payment_Transactions` as compatibility record.

```text
bzj_payment_intents (IAPD)      ←→ Wo_Payment_Transactions (Streams)
    [durable state]                  [compatibility record]
    [recovery logic]                 [existing integration]
    [full audit trail]               [backward compatible]
```

**Pros:**
- Full durable state in IAPD
- Backward compatibility via sync
- Existing code continues to work
- Can migrate incrementally

**Cons:**
- Dual-write complexity
- Potential sync lag
- Data consistency risk

**Recommendation:** Best approach if new payment-intent system must coexist with legacy for extended period.

## 15. RECOMMENDED ARCHITECTURAL DIRECTION

Based on the evidence above, the following architectural decisions are recommended for BZJ-PGB-0200 → BZJ-PGB-0230 ADR:

### 15.1 Payment Intent Model — REQUIRED

**Recommendation:** Implement a durable payment-intent record (IAPD `bzj_payment_intents` table or extended `Wo_Payment_Transactions`).

**Rationale:**
- Current system lacks server-side transaction state durability
- Browser handoff creates orphaned orders
- No recovery path for incomplete transactions
- This is the root cause of dropped orders

**Evidence:**
- F-001 (Browser Navigation Loss)
- D-001, D-002, D-003, D-004 (State schema insufficient)
- Webhook processing lacks context if metadata missing

---

### 15.2 Idempotency Key — REQUIRED

**Recommendation:** Add globally unique `idempotency_key` to payment intent. Implement duplicate detection on:
- Payment initiation
- Webhook reception
- Each fulfillment operation

**Rationale:**
- Current system has no duplicate protection at initiation level
- Webhook retry creates duplicate credits
- F-002 (Duplicate Processing)

**Evidence:**
- D-002 (No Idempotency Key)
- AFF-001 (Guard only for AffiliateWP)

---

### 15.3 Server-Authoritative Amounts — REQUIRED

**Recommendation:** Payment server must:
1. Accept only product/plan identifier from browser
2. Look up authoritative amount/currency from Streams
3. Validate browser-supplied amount (if any) against authoritative
4. Reject if discrepancy

**Rationale:**
- S-002 (Browser-Supplied Financial Values)
- C-001 (No Currency Authority)
- Prevents financial manipulation

**Evidence:**
- Browser can currently modify amount payload
- No server-side validation against Streams product definition

---

### 15.4 Webhook Signature Secret — ENVIRONMENT-BASED

**Recommendation:** Store webhook secret in `.env` file; load via `getenv()`.

**Rationale:**
- S-001 (Hard-coded Webhook Secret)
- Follows existing pattern in `shared/db_helpers.php`
- Prevents secret exposure in source code

**Evidence:**
- Current code contains hard-coded secret
- Other integrations use environment variables

---

### 15.5 SQL Injection Prevention — IMMEDIATE

**Recommendation:** Replace all direct string interpolation in SQL with prepared statements.

**Rationale:**
- S-004 (SQL Injection — Direct Query)
- S-003 (Email-based User Resolution — SQL injection)
- Unacceptable security risk

**Evidence:**
- `$sqlConnect->query("... WHERE order_id = '$order_id'")` pattern throughout
- getUserIdByEmail uses direct query

---

### 15.6 Webhook Payload Validation — REQUIRED

**Recommendation:** Implement comprehensive validation of webhook payload:
1. Verify required fields present
2. Validate data types
3. Explicit error logging and alerting if validation fails
4. Do not proceed with null/missing values

**Rationale:**
- F-005 (Missing WooCommerce Order ID Reference)
- F-006 (Webhook Metadata Extraction Fragility)
- Current code silently continues with null values

**Evidence:**
- D-003 (Missing Correlation ID)
- Email lookup fails silently

---

### 15.7 Currency Model — SINGLE AUTHORITY

**Recommendation:** Establish single authoritative currency source:

```text
Streams product currency (authoritative) →
  ↓
WooCommerce base currency mapping →
  ↓
WOOCS checkout currency (if active) →
  ↓
Payment gateway currency
```

Document and test the complete conversion chain.

**Rationale:**
- C-001 (No Currency Authority Established)
- C-002 (WOOCS Integration Unclear)
- Prevents silent currency mismatches

**Evidence:**
- Document section 20 flags this as critical
- No current handling of currency authority

23. Migration Strategy

A staged migration is the safest approach given the evidence:

1) Stage 1: map and codify current state
- preserve existing Streams redirect pattern
- record correlation IDs and state transition data
- ensure no functionality is lost

2) Stage 2: add durable transaction ledger
- implement a single payment transaction record that is authoritative for handoff and reconciliation
- keep the current code path functional while introducing the new record

3) Stage 3: add idempotency guards
- dedupe payment intent creation
- dedupe WooCommerce order creation
- dedupe completion callbacks
- dedupe affiliate processing

4) Stage 4: introduce a more direct WordPress transaction boundary
- prefer native WordPress/WooCommerce server-side APIs
- retain the browser redirect only as the user-facing handoff, not as the only durable state

5) Stage 5: staged coexistence
- keep current architecture working
- introduce feature flags for alternative route selection
- monitor completion rate and reconciliation

This should be no more than a controlled migration, not a disruptive replacement.
