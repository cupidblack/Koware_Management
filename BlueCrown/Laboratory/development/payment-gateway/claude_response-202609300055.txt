## 1. Executive Summary

1. **[V] The real lifecycle differs from the working hypothesis in six material ways.** (a) Streams talks to WooCommerce over an **HTTP REST self-call** (`POST {wow_api_url}/wc/v3/orders`), not a native API. (b) Price and amount are **taken from the browser** and written into the WooCommerce order. (c) The `PRODUCT` (marketplace) branch **never reaches WooCommerce** and records the purchase as "placed". (d) Post-payment work is split across **three uncoordinated executors**: an MU-plugin hook, a browser-triggered thank-you-page hook, and a WooCommerce webhook into Streams. (e) `wow-pgb_sync.php` creates the WooCommerce Subscription **after** payment, via another HTTP REST call. (f) Streams entitlement (wallet, Pro, crowdfund) is written by the **webhook**, not by `wow-pgb_sync.php`.
2. **[V] No durable, shared transaction state exists.** Streams inserts a `Wo_Payment_Transactions` row before handoff, then nothing tracks it: no expiry, no reconciler, no state machine, no retry queue. A failed handoff leaves an orphan row.
3. **[V]** The handoff has **no cURL timeouts and TLS verification disabled**. **[O]** shell `curl` from the server cannot resolve `buzzjuice.net`. **[I]** If PHP shares that resolver failure, order creation and webhook delivery both fail; whether PHP does is **UNKNOWN**.
4. **[V]** The thank-you hook runs **subscription creation, role verification with sleep-based retries (worst case ≈23 minutes), affiliate processing and `wp_redirect()` inside `wp_footer`**. Redirects there are unreliable once output has started. **[H]** This is a leading cause of customers being stranded after paying.
5. **[V]** Side effects are **largely not idempotent**: wallet credit and crowdfund insert in the webhook, subscription creation by `POST /subscriptions`, and Streams init on refresh. **[I]** The AffiliateWP bridge's own `$order->save()` can itself trigger another `order.updated` webhook.
6. **[V] Security defects exist that are independent of the dropped orders:** browser-controlled amount/plan pricing, a webhook HMAC secret hard-coded in source (value deliberately not reproduced here), TLS verification disabled, session hash and customer email written to logs.
7. **[V] AffiliateWP handling is comparatively well-guarded** (origin flag, processed flag, duplicate-referral check, five-source affiliate resolution). Preserve its data contract (Section 15).
8. **[V] Jewel Affiliate code appears unwired.** `jewel_affiliate_process()` is defined but no caller was found; its header says the webhook calls it and the webhook does not.
9. **Direction [R][A]:** verify the UNKNOWNs first (Section 25), then harden the current flow (Option D subset), then introduce a durable payment intent (Option B) behind a feature flag. No option is adopted here.

### 4.2 Initiation (brief 7.1) [V]
Originating JS is `Wo_GetWooCommerceLink`. Kind is derived from **URL substrings** (`wallet`, `checkout`, `fund`, `go-pro`). `amount = product_units × product_price`, where price comes from the DOM or from the server-rendered `pro_packages` JSON. User identity is the Streams session (`$wo['user']`); the POSTed `user_id` is ignored by init. Currency is `wow_currency_code` (for non-PRODUCT it defaults to `$wo['config']['currency']`). `hash_id` is sent but init does not check it; whether `requests.php` checks it globally is UNKNOWN.

### 4.3 Init behaviour (brief 7.2) [V]
- **Validation:** `empty()` check on seven fields; `intval/floatval` casts; PRO `wow_post_id` restricted to 1–4 via config map; **no** recomputation or comparison of `amount`/`product_price` against server-side pricing.
- **Writes:** one `Wo_Payment_Transactions` row up front. The `PRODUCT` branch additionally writes a `SALE` row for the owner (same `order_id`), `Wo_Purchases`, `Wo_UserOrders` (`placed`) and `Wo_Notifications`, then **redirects to `/purchased` without any WooCommerce call**.
- **cURL:** `CURLOPT_SSL_VERIFYPEER/HOST = 0`; **no `CURLOPT_TIMEOUT`/`CONNECTTIMEOUT`**; no retry. Comment says "for local testing".
- **Identity:** `Wo_Users.wp_user_id` lookup. If missing it only logs and **continues, creating a guest order** (`customer_id` 0). Later stages (sync, AffiliateWP) need a customer.
- **Unused work:** `build_address_block()` builds billing/shipping but they are **not included in the order payload**. **[I]** Orders likely carry no billing email; downstream code depends on it (Sections 5, 6).
- **Response:** on failure `$response` is never initialised and carries no `status` key; HTTP code stays 200.
- **Logging:** logs the entire POST (including `hash_id`) and the AffiliateWP snapshot (including customer email).

### 4.4 Handoff, order, checkout (briefs 7.3–7.5)
- **Mechanism [V]:** synchronous server-side HTTP REST (Basic auth key/secret from Streams config `wow_api_key/wow_api_secret`, base `wow_api_url`). No queue, no browser-mediated handoff.
- **Order [V]:** created by `WC_REST_Orders` (E11). Product = configured WC ID (`wow_pro_package_id[_2-4]` variation, `wow_wallet_topup_id`, `wow_crowdfund_id`; fallback literal `694`). Price = explicit `total` from the browser-derived amount, `subtotal` = unit price. Currency = client-supplied code. `set_paid:false`; no `payment_method`; status defaults to `pending` (E15). `payment_url` is `get_checkout_payment_url()` (E11).
- **Customer/guest [I]:** customer is the mapped WP user; order-pay behaviour for a user not logged into WordPress is UNKNOWN (no WordPress session guarantee from Streams login is verified here).
- **Refresh/repeat [V]:** each click generates a new `uniqid` and a new WC order; nothing deduplicates.

### 4.5 Completion and post-payment (briefs 7.6–7.7)
- **Status path [I]:** products are created virtual + downloadable, so WooCommerce normally auto-completes after payment; hence `completed` hooks fire. Confirm on real orders.
- **A. MU hook [V]:** only AffiliateWP.
- **B. Thank-you hook [V]:** per SKU. PRO: auth to Streams API (`$_ENV` creds, up to 5 retries), find WP user by billing email, read order meta `userid`, **wait until the user's WP role equals the plan role** (10 retries), derive variation, compute `next_payment_date`, create subscription via REST (5 retries), call AffiliateWP, redirect. Wallet/Fund/Market: AffiliateWP + redirect only.
- **C. Webhook [V]:** on status `completed`: updates transaction (`payment_status, payment_method, woo_order_id, amount`); credits wallet when product = wallet top-up handler and no `qdw_order_id`; inserts `Wo_Funding_Raise` for crowdfund; sets `is_pro/pro_type/pro_time` when variation ∈ Pro IDs and `wow_post_id` ∈ 1–4. Other statuses update `payment_status` only. User is resolved **by billing email**, not by the order's `userid` meta.
- **Roles [I]:** role names are created by `blue-crown-wp/includes/user-roles.php`. What assigns them after payment is not in the read files. The Addify plugin hooks `woocommerce_order_status_completed`, so it is a candidate; its rules are UNKNOWN.

## 7. Architectural Options

### 7.1 Evaluation

Scale: ● strong · ◐ partial · ○ weak. Options are evaluated against the reconstructed system, not assumed preferences.

| Criterion | A: Streams → WC REST → browser | B: durable intent → browser → WP → native WC PHP | C: Streams → browser → WP endpoint | D: current + targeted hardening |
|---|---|---|---|---|
| Transaction durability | ○ (row not linked to order lifecycle) | ● | ◐ (needs signed intent to be safe) | ◐ |
| Network dependency | Streams→WP HTTP required | none server-to-server for order creation | none server-to-server | Streams→WP HTTP still required |
| DNS dependency | **high** | **low** | low | high unless resolver fixed |
| Security | ○ (trusts browser amount) | ● (server-priced intent) | ○ unless signed, then equals B | ◐ (can fix pricing) |
| Idempotency | ○ | ● | ◐ | ◐ |
| WooCommerce compatibility | ● REST is supported | ● native CRUD | ● | ● |
| Subscriptions compatibility | ◐ manual post-hoc creation | ● can use WCS native APIs with parent guard | ● | ◐ |
| Currency handling | ◐ client currency | ● WP decides | ● | ◐ |
| AffiliateWP compatibility | ● (working) | ● if meta contract kept | ● | ● |
| Recovery | ○ | ● reconciler over states | ◐ | ◐ |
| Observability | ○ | ● correlation ID | ◐ | ◐ |
| Migration complexity | none | high | medium | low |
| Rollback complexity | none | medium (feature flag) | medium | low |

Reading: A is the current design. C is only safe if the browser carries an opaque **server-issued, signed** token, which is B without the stored record. D lowers risk fastest but keeps the DNS-sensitive self-call. Another candidate warranted by the evidence is **E = D plus a WordPress-side reconciler** that scans pending Streams-origin orders and re-drives fulfillment; it needs a persisted record to be reliable, which converges on B. **No option is selected in this section.**

### 7.2 Communication paths (brief 11) — what each design really needs

| Path | Description | Used today [V] | Needed by A | B | C | D |
|---|---|---|---|---|---|---|
| **A** Streams server → HTTP → WordPress | `wow_api_url/wc/v3/orders` | **Yes** | Yes | No | No | Yes |
| **B** WordPress PHP → local WC PHP | Native CRUD (`wc_create_order`, WC/WCS classes) | No. The sync plugin instead **loops back over HTTP** to `woocommerce_api_url` for subscriptions, and to Streams API for auth | No | Yes | Yes | No |
| **C** Browser → WordPress | order-pay URL, thank-you page | Yes | Yes | Yes | Yes | Yes |
| **D** WordPress → Streams DB | direct mysqli via `get_wowonder_db()` | Present in shared helpers; used by Jewel/WWQD, **not** by the sync plugin | No | Optional | Optional | No |
| **E** WooCommerce webhook → Streams | HTTP from WP host to Streams URL | **Yes** (E6) | Yes | Replaceable by D | Replaceable by D | Yes |

Key conclusions: **[V]** the browser is unaffected by the server's DNS problem, which explains why local `curl` works. **[I]** Paths A, E and the sync plugin's two loopbacks all resolve `buzzjuice.net` from the server, so all fail if PHP resolution fails. **[V]** WordPress→Streams DB and Streams→WordPress DB access already exist (`db_helpers.php`), so server-to-server HTTP is **not architecturally mandatory**. Native WooCommerce PHP APIs are therefore an option, not a requirement. **The DNS condition is [O] for shell `curl` only; PHP-FPM/lsphp resolution is UNKNOWN** and must be tested before drawing conclusions.

## 8. Transaction State Model

Design goal: the minimum durable model that makes every transition recoverable. Owner of truth: WordPress side [R][A]. States are **not adopted automatically**.

| Proposed state | Decision | Purpose / entry | Responsible | Valid next | Retry | Terminal? | Recovery |
|---|---|---|---|---|---|---|---|
| `created` | **Keep** | Intent persisted with server-priced snapshot | Streams (or WP) | `order_created`, `failed`, `expired`, `cancelled` | order creation retried with same idempotency key | No | reconciler re-drives |
| `validated` | Merge into `created` | Validation is a pre-condition, not a persisted state | Streams | — | — | — | — |
| `handoff_pending` | Merge into `created` with attempt counter | Distinguish by `attempts`/`next_retry_at` | reconciler | — | backoff | — | — |
| `woocommerce_order_pending` | Reject (transient) | In-flight lock only; a state would strand on crash | — | — | — | — | — |
| `woocommerce_order_created` / `checkout_ready` | **Keep as `order_created`** | WC order ID, key and payment URL persisted | WordPress | `paid`, `expired`, `cancelled`, `failed` | URL regenerated on demand | No | resend link |
| `payment_pending` / `payment_processing` | Reject (mirror WC status) | WC order status is already authoritative | WooCommerce | — | — | — | — |
| `payment_completed` | **Keep as `paid`** | Order reached paid/completed status (verified server-side) | WordPress hook | `fulfilling` | none | No | — |
| `post_payment_processing` | **Keep as `fulfilling`** | Subscription/entitlement/affiliate/Jewel steps in progress, per-step flags | WordPress worker | `completed`, `recovery_required` | step-level retry | No | resume by step |
| `completed` | **Keep** | All steps confirmed incl. Streams sync | WordPress | — | — | **Yes** | — |
| `failed` | **Keep** | Unrecoverable pre-payment failure (validation/order creation exhausted) | any | — | — | **Yes** | manual only |
| `expired` | **Keep** | No payment within TTL; WC order cancelled | scheduler | — | — | **Yes** | new intent |
| `cancelled` | **Keep** | User/gateway cancel | WP/WC | — | — | **Yes** | new intent |
| `recovery_required` | **Keep** | Paid but a step failed beyond retry limit; needs operator | reconciler | `fulfilling` after fix | manual trigger | No | manual queue |

Per-step completion flags inside `fulfilling` (subscription created, Streams entitlement written, affiliate processed, Jewel processed) are recommended because the failure analysis shows steps fail independently.

## 9. Idempotency Model

Existing guards were inspected first; new guards are only proposed where a gap is proven.

| Operation | Existing guard [V] | Gap | Proposed key [R] |
|---|---|---|---|
| Payment intent creation | none (`uniqid` per request) | refresh/re-click creates duplicates | client-generated or server-issued intent UUID; reuse open intent for same user + kind + item |
| WordPress handoff | none | retry after lost response duplicates orders | idempotency key = intent UUID stored as order meta; look up before create |
| WooCommerce order creation | none (`wow_order_id` meta not checked) | as above | lookup by meta `_bzj_intent_uuid` |
| Checkout requests | order key only | none needed if URL regenerated from same order | one order per intent |
| Payment callbacks | gateway-specific: UNKNOWN | UNKNOWN | rely on WC `is_paid()`; verify per gateway |
| Order completion hooks | thank-you: `did_action` (same request only); MU: none | repeat visits/refresh re-run steps | per-step flags on the intent |
| Subscription processing | **none**; WCS REST `POST /subscriptions` has no parent guard (E13) | duplicate on retry | check `wcs_order_contains_subscription` style relation first, or use WCS's order-based route which refuses if the order already has subscriptions (E13) |
| AffiliateWP | `_buzzjuice_origin`, `_affwp_bridge_processed`, duplicate lookup by `reference+context+affiliate` | flag check-then-set not atomic; two callers (MU + thank-you); unique index on referrals UNKNOWN | keep; add an atomic claim on the intent, do not rewrite bridge |
| Jewel | select `notes LIKE '%Rebate%'` + DB transaction | TOCTOU; no unique key | unique `(woo_order_id, kind)` on a ledger |
| Streams webhook effects | signature only | wallet `+=`, funding insert are repeatable; Pro `pro_time` reset each time | ledger row per `(woo_order_id, effect)` applied once |

## 10. Database Design

**Is a dedicated table required? [I] Yes, for Option B/E; not for Option D.** `Wo_Payment_Transactions` cannot serve as the authority: the `PRODUCT` branch inserts two rows with the same `order_id`, so `order_id` cannot be unique [I]; it has no state, attempts, expiry or step flags; `payment_status`, `payment_method`, `woo_order_id` are custom columns added to a WoWonder core table (upgrade risk) [V]; webhook overwrites `amount` with the WC total, losing the original [V].

Proposed fields (each justified by a lifecycle need); **table not created, location [A]**:

| Field | Justification |
|---|---|
| `id` (PK, bigint) | internal key |
| `uuid` (UNIQUE) | idempotency, correlation, safe external reference |
| `idempotency_key` (UNIQUE, nullable) | client retry safety |
| `streams_user_id`, `wp_user_id` | ownership; guest-order defect (#H8) |
| `kind` (`PRO/WALLET/DONATE/…`), `plan_id`/`wow_post_id`, `item_ref` | what is being bought |
| `streams_ref` (legacy `order_id`) | link to existing rows during coexistence |
| `amount_minor`, `source_currency` | server-computed original amount (integer minor units) |
| `wc_currency`, `wc_total_minor`, `fx_rate`, `fx_source` | conversion audit (Section 14) |
| `woo_order_id` (UNIQUE, nullable), `woo_order_key` | order link; payment URL derivable |
| `subscription_ids` (JSON) | Subscriptions link |
| `state`, `payment_status` | state model (Section 8) |
| `step_flags` (JSON: subscription, entitlement, affiliate, jewel) | independent step recovery |
| `attempts`, `next_retry_at`, `last_error_code` | reconciler |
| `correlation_id` | logging |
| `created_at`, `updated_at`, `paid_at`, `expires_at` | lifecycle |
| `failure_data` (JSON, redacted) | recovery |

Keys/indexes: PK `id`; UNIQUE `uuid`, `idempotency_key`, `woo_order_id`; INDEX `(state, next_retry_at)` for the reconciler, `(streams_user_id, state)`, `(wp_user_id)`, `(expires_at)`. Optional append-only `events` table `(intent_id, from_state, to_state, at, correlation_id, detail)` for audit. Versioning: schema-version option checked on load with an additive-only migration routine (MU plugin), never destructive. Rollback: table remains inert if the feature flag is off.

## 13. WooCommerce Subscriptions

Verified in installed WCS (E13):
- `POST /wc/v3/subscriptions` accepts `parent_id`, dates (incl. `next_payment_date`), `status`, `line_items`; **no guard against a second subscription for the same parent**.
- `POST /wc/v3/orders/{id}/subscriptions` (added 7.9.0) refuses if the order already has subscriptions, requires a customer, **only handles subscription-type products**, sets status `active` if the order is paid else `pending`, copies order meta, and runs in an SQL transaction.
- The bridge uses the first route, after payment, with `status:active`.

Findings:
1. **[V]** Products are created as plain `WC_Product_Variable`/`WC_Product_Variation` with subscription meta written manually (and the code that sets PRO prices/meta sits inside the simple-product loop referencing an undefined `$variation`, so it never runs). Whether the parent was later converted to a subscription-type product in admin is **UNKNOWN**, and it decides whether WCS's native machinery applies.
2. **[V]** Subscription line items pass `product_id` only (the parent, from `get_product_id()`), **no `variation_id`**.
3. **[V]** `next_payment_date` is computed with server-local `date()` although WCS dates are GMT.
4. **[V]** No `payment_method` is set; **[H]** renewals are therefore manual-renewal orders. Renewal, failed-payment and cancellation behaviour cannot be confirmed without gateway inspection (UNKNOWN).
5. **[V per repo search, index caveat]** no `woocommerce_subscription_status_*` listeners exist in MU plugins or `shared/`; **[I]** cancellation/expiry does not revert Streams `is_pro` or the WP role except through WoWonder's own expiry logic (UNKNOWN).
6. **Creating a subscription before payment [I]:** WCS's own REST helper assigns `pending` when the parent is unpaid and `active` when paid, so association before payment is compatible with WCS's model if activation follows payment. Forcing `active` after payment (current) bypasses that lifecycle. **Which to adopt is [A]** and needs a test on the installed version.
7. Duplicate activation protection: none in the bridge (Section 9).

## 15. AffiliateWP (protected)

**Verified pipeline [V] (E4/E5):** MU hook at `completed` (prio 999) and the thank-you path both call `bluecrown_affiliatewp_post_checkout_verification`. Stages: load order (guards: `_buzzjuice_origin == 'streams'`, not `_affwp_bridge_processed`) → resolve AffiliateWP customer by `user_id`, else by snapshot email, else create via `affwp_add_customer` → resolve affiliate through five deterministic sources (Lifetime customers table, snapshot visit, customer meta `affiliate_id`, `referring_affiliate_id`, snapshot affiliate) → ensure Lifetime customer record → compute commission from product/variation overrides or global rate on item totals → duplicate referral check → create referral through public `affwp_add_referral` → verify accounting, with a conditional fallback increase only if unpaid earnings did not change → set processed flag only on success (zero-commission also marks processed).

**Preserve (data contract):** order meta `_buzzjuice_origin=streams`, `_buzzjuice_affwp_context_snapshot` (v2 JSON incl. cookies, referer, `wp_user_id`, `customer_email`), `userid`, `wow_order_id`, `wow_post_id`; order `customer_id`; line item totals and variation IDs; `reference`=WC order ID; function names and hook/priority; the "not processed on failure" retry-safety.

**Observations, not change requests:**
1. Commission is computed on item `total`, which is currently **browser-controlled** (Section 19).
2. Attribution relies partly on cookies captured in the Streams request; server-side sources are tried first, which is the right order.
3. Two callers plus a non-atomic flag can race (idempotent in outcome because of the duplicate check, subject to referrals-table uniqueness, UNKNOWN).
4. Manual calculation (`calculation_source: manual_bridge`) bypasses AffiliateWP's native integration and Recurring Referrals logic; renewal-order interaction is **UNKNOWN**. AffiliateWP's own WooCommerce integration also hooks completion (E-search), so overlap should be checked on a real order.
5. `BC_AFFWP_DEBUG` is `false` by default; the equals-sign banners are unconditional log lines.

**Recommendation [R]:** change nothing in AffiliateWP logic; only ensure any new architecture supplies the same meta contract and invokes the same function.

## 19. Security

| Risk | Evidence | Severity | Mitigation [R] |
|---|---|---|---|
| **Amount/plan price manipulation** | init trusts `amount`, `product_price`, `product_units`; PRO not compared to package price; activation keyed only on variation + `wow_post_id` | **Critical** | server-side price resolution; ignore client amounts |
| Currency/product manipulation | client `wow_currency_code`, `wow_post_id`, `product_owner_id` | High | derive from server data |
| Hard-coded webhook secret in source | `wow-pgb_webhook.php` (value withheld here) | **High** | rotate; load from environment; treat as compromised since it is in Git history |
| TLS verification disabled | init cURL; sync `$_ENV[...] ?? 0` default | High | enable; pin CA; explicit timeouts |
| Log leakage | init logs full POST incl. `hash_id`; snapshot with email | High | redact; toggle |
| CSRF / session check on `f=payment` | `hash_id` sent, not validated in init; global check UNKNOWN | Medium-High | verify router; validate |
| Replay / duplicate webhook | HMAC only; no timestamp/ID guard; effects repeatable | High | delivery-ID ledger |
| Unauthorised order-ID lookup / return-URL tampering | order-pay is key-bound; Streams URLs fixed in code | Low-Medium | keep key-bound; do not accept return URLs from client |

| User binding by billing email | webhook and sync | Medium | bind by intent/`userid` meta |

| Predictable SSO fallback secret | `bzj_get_sso_secret` derives from `ABSPATH` if env missing | Medium (out of scope; noted) | separate issue |

## 23. Migration Strategy

1. **Stage 0 – Evidence:** close the UNKNOWNs (Section 25). No change.
2. **Stage 1 – Instrument:** correlation logging and redaction; read-only reports of pending/orphan rows.
3. **Stage 2 – Harden (Option D subset):** timeouts, TLS on, server-side pricing, idempotent webhook effects, remove blocking sleeps, move redirect off `wp_footer`. Independent flags per change.
4. **Stage 3 – Intent (Option B) in shadow mode:** write intents alongside the old flow; reconcile against existing behaviour; no user-visible change.
5. **Stage 4 – Cut over by kind** (WALLET first, then DONATE, then PRO) via a Streams config flag; old and new orders distinguished by `_bzj_intent_uuid`.
6. **Stage 5 – Retire** legacy paths only after zero traffic and mapping is complete.

Coexistence: webhook accepts both; in-flight pending orders finish on the old path; existing subscriptions untouched; AffiliateWP contract unchanged; currency behaviour changed only under a separate approval; rollback is flag-off with intents left inert; monitoring on pending age, orphan counts, webhook failures and step-flag stalls.
