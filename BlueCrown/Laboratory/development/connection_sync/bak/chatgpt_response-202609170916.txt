# 1. EXECUTIVE ARCHITECTURE

The previous design used a central WordPress relationship ledger.

That design should be changed.

The integration must **not create a second authoritative relationship model** such as:

`wp_bzj_relationships`

because that table can eventually disagree with BuddyBoss and inadvertently become a second source of truth.

Instead:

```text
                         BUZZJUICE
                   WORDPRESS + BUDDYBOSS
                         SOURCE OF TRUTH
                              |
             +----------------+----------------+
             |                |                |
             v                v                v
        CONNECTIONS         FOLLOWS          BLOCKS
             |                |                |
             +----------------+----------------+
                              |
                     BZJ SYNC CONTROL PLANE
                              |
                +-------------+-------------+
                |                           |
                v                           v
       BUZZJUICE STREAMS            BUZZJUICE SOCIALS
          WoWonder                    QuickDate
        PROJECTION                    PROJECTION
```

BuddyBoss owns:

* connection requests
* accepted connections
* rejected/withdrawn connections
* connection removal
* ordinary follows
* ordinary unfollows
* blocks
* unblocks
* connection eligibility
* connection privacy
* role/profile restrictions
* BuddyBoss-specific permission rules

Streams and Socials may originate actions, but the requested action must ultimately be accepted or rejected by BuddyBoss.

# 2. IMPORTANT SEMANTIC DISTINCTIONS

The integration must maintain three separate concepts.

## 2.1 Connection

A connection is the BuddyBoss "friend" relationship.

It maps to:

```text
BuddyBoss connection
        ↓
QuickDate friend projection
```

It does NOT automatically mean:

```text
WoWonder follow
```

because the WoWonder Friends System is disabled.

---

# 2.2 Ordinary Follow

An ordinary follow is independent of friendship.

It maps:

```text
BuddyBoss follow
      ↕
Streams follow
      ↕
Socials ordinary follow
```

An ordinary follow must never automatically become:

```text
BuddyBoss connection
```

or:

```text
QuickDate friendship
```

The QuickDate implementation internally using its `followers` table for both concepts does not change this semantic distinction.

---

# 2.3 Block

A block is the dominant relationship state.

When:

```text
A blocks B
```

the integration must:

1. retain the BuddyBoss block;
2. remove BuddyBoss connection A ↔ B;
3. remove BuddyBoss follow A → B;
4. remove BuddyBoss follow B → A;
5. remove Streams follow A → B;
6. remove Streams follow B → A;
7. create Streams block A → B;
8. remove Socials ordinary follow A → B;
9. remove Socials ordinary follow B → A;
10. remove Socials friend projection;
11. create Socials block A → B.

This follows the corrected GitHub design that blocking is dominant over every other relationship. ([GitHub][1])

---

# 3. UNBLOCK SEMANTICS

Unblocking is deliberately non-restorative.

When:

```text
A unblocks B
```

only:

```text
A → B block
```

is removed.

The system must NOT automatically restore:

* previous connection;
* previous follow;
* previous friend request;
* previous QuickDate friendship.

A subsequent relationship must be established as a new user action.

This prevents stale relationships from silently reappearing after moderation. ([GitHub][1])

# 5. QUICKDATE FRIEND-PROJECTION PROBLEM

This is the most important schema correction.

QuickDate currently uses:

```text
followers
```

for:

* ordinary follows;
* pending friend requests;
* accepted friendships.

That creates a collision.

For example:

```text
A follows B
```

may already create:

```text
followers:
A → B active=1
```

Then:

```text

```

cannot safely reuse that same row to represent:

```text
A → B pending friend request
```

without destroying the existing ordinary follow state.

The GitHub review correctly identifies this as unsafe. ([GitHub][1])

# 11. NON-RECURSIVE Wo_IsFollowRequested()

The requested automatic follow acceptance must NOT call:

```php
Wo_AcceptFollowRequest()
```

from inside:

```php
Wo_IsFollowRequested()
```

because the current `Wo_AcceptFollowRequest()` calls `Wo_IsFollowRequested()`, creating recursion.

The correct implementation is:

```php
function Wo_AutoAcceptFollowRequest($following_id, $follower_id)
{
    global $sqlConnect;

    $following_id = (int) $following_id;
    $follower_id  = (int) $follower_id;

    if (
        $following_id < 1 ||
        $follower_id < 1 ||
        $following_id === $follower_id
    ) {
        return false;
    }

    $query = mysqli_query(
        $sqlConnect,
        "UPDATE " . T_FOLLOWERS . "
         SET `active` = '1'
         WHERE `following_id` = {$following_id}
           AND `follower_id` = {$follower_id}
           AND `active` = '0'
         LIMIT 1"
    );

    if (!$query) {
        error_log(
            '[BZJ Streams] Automatic follow acceptance failed: ' .
            mysqli_error($sqlConnect)
        );

        return false;
    }

    return mysqli_affected_rows($sqlConnect) > 0;
}
```

Then `Wo_IsFollowRequested()` should:

1. validate IDs;
2. find the pending row;
3. return false if no row exists;
4. call `Wo_AutoAcceptFollowRequest()`;
5. return true.

It must not call `Wo_AcceptFollowRequest()`.

This is specifically required to eliminate the recursive failure identified in the GitHub review. ([GitHub][1])

`Wo_AcceptFollowRequest()` should additionally be made idempotent so that an already-active row is treated as successfully accepted.

# 26. ENDPOINT AUTHENTICATION

All non-WordPress-originated requests must use:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

The signature is:

```text
HMAC-SHA256(
    timestamp + "." + raw_json_body,
    BUZZ_SSO_SECRET
)
```

The raw JSON body must be signed exactly as transmitted.

Reject:

* missing secret;
* missing timestamp;
* missing signature;
* expired timestamp;
* invalid signature;
* invalid UUID;
* invalid origin;
* unsupported operation;
* missing mapping;
* actor mismatch;
* self-action;
* replayed event.

This authentication design is retained from the GitHub correction. ([GitHub][1])

```text

```


# 69. FINAL IMPLEMENTATION DECISION

The production architecture should therefore be:

```text
                         BUDDYBOSS
                    CANONICAL CONTROL PLANE
                              |
        +---------------------+----------------------+
        |                     |                      |
   CONNECTIONS             FOLLOWS                BLOCKS
        |                     |                      |
        +---------------------+----------------------+
                              |
                       BZJ SYNC ENGINE
                              |
             +----------------+----------------+
             |                                 |
        WOWONDER STREAMS                 QUICKDATE SOCIALS
             |                                 |
        followers / blocks           followers / blocks
                                      +
                               friend projections
```

with:

```text
/wp-content/mu-plugins/bzj-connections-sync.php
```

as the central synchronization controller;

```text
/shared/db_helpers.php
```

as the DB connection layer;

```text
/shared/wwqd_bridge.php
```

as the identity/profile bridge;

```text
streams-bzj-sync.php
```

as the Streams → BuddyBoss transport;

```text
socials-bzj-sync.php
```

as the Socials → BuddyBoss transport;

```text
wp_bzj_relationship_events
```

as the recovery queue;

```text
bzj_friend_projections
```

as the QuickDate friendship projection;

and:

```text
/data/logs/bzj-connections-sync.log
```

as the operational log.

This preserves BuddyBoss as the source of truth while allowing users to initiate equivalent actions from Streams and Socials without ever allowing those platforms to directly overwrite BuddyBoss relationship tables.

### What changed from v8.1.2

The most important corrections are:

1. **Removed the relationship ledger as a source of state.** The old v8.1.2 plugin explicitly created `wp_bzj_relationships`; that should no longer be used as an authority. 
2. **Added a dedicated QuickDate friend-projection model** because QuickDate's `followers` table cannot safely distinguish an ordinary follow from a friend request. ([GitHub][1])
3. **Streams remains follow-only.** No synchronized WoWonder friendship state is created. ([GitHub][1])
4. **External platforms request BuddyBoss actions rather than writing BuddyBoss directly.** ([GitHub][1])
5. **BuddyBoss-originated events project directly**, rather than unnecessarily calling the REST endpoint back into the same WordPress installation. ([GitHub][1])
6. **`Wo_IsFollowRequested()` is explicitly non-recursive.** The automatic acceptance occurs through a direct `UPDATE`, not `Wo_AcceptFollowRequest()`. ([GitHub][1])
7. **The HMAC endpoint fails closed** if `BUZZ_SSO_SECRET` is unavailable; the fallback secret in the existing DB helper must not be accepted for synchronization. ([GitHub][1])
8. **Pair locking and idempotency remain**, but are now recovery/concurrency mechanisms rather than relationship authority. ([GitHub][1])
9. **The QuickDate ordinary-follow/friend collision is explicitly resolved.**
10. **Your special QuickDate ordinary-unfollow → unfriend rule is retained** as a Buzzjuice-specific business rule, rather than allowing generic QuickDate semantics to override it.

The current `db_helpers.php` is suitable as the database foundation: it already exposes WordPress, QuickDate and WoWonder connections and the relevant identity mappings. ([GitHub][2]) The existing `wwqd_bridge.php` is large enough that, consistent with your instruction, it should receive only targeted identity/helper additions rather than being regenerated. ([GitHub][5])

**One important implementation point:** I would **not yet deploy the existing `bzj-connections-sync-v8.1.2.php`**. The GitHub review's statement that it should not be deployed unchanged is justified, particularly because its current code still contains the relationship ledger and its QuickDate projection logic derives friendship/follow state from that ledger. ([GitHub][1])

The next implementation stage should therefore be **v8.2.0 code generation**, consisting of the complete new `bzj-connections-sync.php`, the complete `streams-bzj-sync.php`, the complete `socials-bzj-sync.php`, the exact `functions_one.php` targeted patches, and the QuickDate `bzj_friend_projections` migration—followed by PHP syntax checks before anything is installed.
