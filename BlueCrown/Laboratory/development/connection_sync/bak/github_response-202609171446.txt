<<START GITHUB>>

The previous v8.2.0 package should **not be deployed as-is**. The retrieved MU-plugin and adapter files are truncated, and the design contains several synchronization problems that could create loops, incorrectly classify QuickDate follows as friendships, or permanently leave failed events pending.

The corrected design below keeps **BuddyBoss as the only relationship authority** while allowing WoWonder Streams and QuickDate Socials to remain standalone applications without `wp-load.php`.

---

# Buzzjuice Network Relationship Synchronization

## 1. Final authority model

BuddyBoss is authoritative for:

1. Connection requests.
2. Accepted connections.
3. Ordinary follows.
4. Blocks and unblocks.
5. Destructive consequences of blocking.

WoWonder Streams and QuickDate Socials are projections and action adapters.

External platforms must never:

- Write BuddyBoss friendship tables directly.
- Write BuddyBoss follow tables directly.
- Write BuddyBoss moderation tables directly.
- Treat an external database row as proof that BuddyBoss accepted a relationship.

The correct flow is:

```text
BuddyBoss action
    ↓
BuddyBoss native hook
    ↓
Synchronization control plane
    ↓
Direct projection into Streams and/or Socials


Streams/Socials action
    ↓
Local external operation succeeds
    ↓
Signed WordPress connection-management command
    ↓
BuddyBoss native function
    ↓
BuddyBoss hook
    ↓
External projections are reconciled
```

The endpoint is:

```text
POST /wp-json/bzj/v6/connection-management
```

The endpoint name should remain `connection-management`, not `relationship`.

# 2. Important corrections to the original proposal

## 2.1 BuddyBoss connections and platform friendships are different concepts

A BuddyBoss connection is a canonical connection.

A QuickDate friendship request is only a representation of a BuddyBoss connection request.

Therefore:

| State | BuddyBoss | QuickDate Socials | WoWonder Streams |
|---|---|---|---|
| Pending connection | Pending friendship | One `followers` row with `active = 0` | No row |
| Accepted connection | Accepted friendship | Reciprocal `active = 1` rows | No friendship row |
| Rejected/withdrawn | No connection | Pending row removed | No change |
| Removed connection | No connection | Connection projection removed | Independent follows remain |
| Ordinary follow | One directional BuddyBoss follow | One directional `active = 1` row | One directional `active = 1` row |

The same QuickDate `followers` table is used for both ordinary follows and friends. Consequently, **the row itself cannot reliably tell the synchronizer whether it represents an ordinary follow or an accepted friendship**.

The canonical distinction must be maintained in BuddyBoss and in the WordPress synchronization ledger.

---

## 2.2 QuickDate friend state cannot be inferred solely from reciprocal rows

The previous implementation used logic equivalent to:

```php
if (both directions are active) {
    treat as friend;
}
```

That is unsafe. Two independent ordinary follows can produce the same reciprocal rows.

The correct rule is:

```text
QuickDate accepted-friend projection exists only when BuddyBoss
currently reports the pair as connected.
```

When BuddyBoss reports that users are connected:

- Ensure the friend projection exists.
- Preserve any independent ordinary-follow projections represented by canonical BuddyBoss follows.

When BuddyBoss reports that users are not connected:

- Remove only the rows that are no longer required by the canonical ordinary-follow state.
- Do not assume that every reciprocal active row is a friendship row.

Because QuickDate has no native relationship-type column in the supplied schema, the synchronization ledger must track projection ownership.

---

## 2.3 Blocking is destructive

Blocking must perform the following operations:

1. Create the canonical BuddyBoss block.
2. Remove the BuddyBoss connection, including pending requests.
3. Remove both BuddyBoss ordinary-follow directions.
4. Remove the corresponding Streams follows.
5. Create the directional Streams block.
6. Remove the corresponding Socials relationship rows.
7. Create the directional Socials block.

Unblocking must:

1. Remove the canonical BuddyBoss block.
2. Remove the corresponding Streams block.
3. Remove the corresponding Socials block.
4. Never restore a previous connection or follow.

A block is directional:

```text
A blocks B ≠ B blocks A
```

---

## 2.4 Do not rely on nonexistent or incorrect moderation hooks

The following are the relevant hooks confirmed in the supplied BuddyBoss source:

```php
bp_moderation_after_save
bb_moderation_after_delete
```

The AJAX action names:

```php
bp_moderation_block_member
bp_moderation_unblock_user
```

are request handlers, not reliable post-operation synchronization hooks.

The hook callback must verify that the moderation object represents a user block:

```php
$item_type === BP_Moderation_Members::$moderation_type
```

and that it is not a report-only moderation record.

---

## 2.5 BuddyBoss already removes some relationships during blocking

The supplied BuddyBoss REST moderation code already removes:

- Existing friendship/pending friendship.
- The blocker’s follow toward the blocked user.

The synchronizer must still reconcile **both follow directions** after the block. It must not assume that the BuddyBoss block operation alone has removed every relationship direction.

---

## 2.6 The previous recovery implementation is incomplete

The previous event design has a serious defect:

```php
if ($this->event_exists($uuid)) {
    return already_processed;
}
```

If an event is inserted as `pending`, a retry with the same UUID is treated as already processed. Additionally, the recovery process only logs pending events rather than executing them.

The corrected behavior is:

```text
new event UUID:
    insert pending event

same UUID with status=processed:
    return already_processed

same UUID with status=pending:
    resume processing

same UUID with status=failed:
    resume only if retry policy permits
```

A failed projection must be retried by a real worker, not merely reported in a log.

# 3. Canonical relationship behavior

## 3.1 BuddyBoss connection request

When A sends a BuddyBoss connection request to B:

```text
BuddyBoss:
    native connection request remains pending

QuickDate:
    create A -> B followers row with active = 0

Streams:
    no follow row is created
```

The relevant BuddyBoss hook is:

```php
friends_friendship_requested
```

The callback must use the hook arguments:

```php
($friendship_id, $initiator_user_id, $friend_user_id)
```

The current source confirms this signature.

---

## 3.2 Withdrawal or rejection

Use:

```php
friends_friendship_withdrawn
friends_friendship_rejected
```

Also retain:

```php
friends_friendship_post_delete
```

as a defensive reconciliation hook.

When the request is withdrawn or rejected:

```text
QuickDate:
    delete only the pending A -> B row with active = 0

Streams:
    no change
```

Do not use `friends_friendship_deleted` alone to determine whether the relationship was a pending request or an accepted connection. That hook is fired before the friendship object is deleted and can represent more than one state.

---

## 3.3 Connection acceptance

When the BuddyBoss connection is accepted:

```text
QuickDate:
    ensure A -> B active row
    ensure B -> A active row

Streams:
    no friendship projection
```

The relevant hook is:

```php
friends_friendship_accepted
```

The connection is authoritative only after BuddyBoss reports the accepted state.

---

## 3.4 Connection removal

When either user removes an accepted BuddyBoss connection:

```text
BuddyBoss:
    connection is removed

QuickDate:
    remove the accepted-connection projection

Streams:
    independent ordinary follows remain
```

The synchronizer must calculate the desired QuickDate state from:

```text
BuddyBoss connection state
BuddyBoss follow A -> B state
BuddyBoss follow B -> A state
```

It must not blindly delete every QuickDate row for the pair.

---

# 4. Ordinary follow behavior

WoWonder Friends System remains disabled.

All Streams follows must therefore be immediate:

```text
active = 1
```

The following configuration values must not create pending Streams follow rows for this integration:

```php
confirm_followers
connectivitySystem
```

The safest implementation is to modify the integration path so that it explicitly inserts an active follow row, rather than changing global WoWonder behavior for every installation.

If the global Streams follow system must be immediate, then `Wo_RegisterFollow()` must retain:

```php
$active = 1;
```

and must not later overwrite it with:

```php
$active = 0;
```

for Buzzjuice ordinary follows.

The BuddyBoss follow hooks confirmed in the source are:

```php
bp_start_following
bp_stop_following
```

The compatibility aliases may also be registered:

```php
bp_follow_start_following
bp_follow_stop_following
```

The callback receives a follow object with:

```php
$follow->leader_id
$follow->follower_id
```

The correct direction is:

```text
follower_id → leader_id
```

Example:

```php
$actor_id  = (int) $follow->follower_id;
$target_id = (int) $follow->leader_id;
```

# 5. Streams-originated actions

When A follows B in Streams:

1. Streams inserts A → B with `active = 1`.
2. Streams verifies the row exists.
3. Streams sends a signed command:

```json
{
  "origin": "streams",
  "operation": "follow",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

4. WordPress maps the Streams IDs through:

```text
wp_usermeta.meta_key = wo_user_id
```

5. WordPress calls BuddyBoss:

```php
bp_start_following(
    array(
        'leader_id'   => $target_wp_id,
        'follower_id' => $actor_wp_id,
    )
);
```

6. BuddyBoss emits its follow hook.
7. The control plane projects the canonical follow to QuickDate.

Streams unfollow follows the same sequence using:

```php
bp_stop_following()
```

The local Streams operation must succeed before the command is sent. If the WordPress command fails, the Streams action should remain successful locally, but the event must be placed in the WordPress retry queue.

---

# 6. Socials-originated actions

## 6.1 QuickDate Add Friend

QuickDate `add_friend()` must not be treated as an ordinary follow.

The required behavior is:

1. Validate the QuickDate action.
2. Do not call the ordinary follow synchronization adapter.
3. Create the local pending QuickDate row with:

```text
following_id = target
follower_id  = actor
active       = 0
```

4. Verify the row.
5. Send:

```json
{
  "origin": "socials",
  "operation": "connection_request",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

6. WordPress calls BuddyBoss’s native:

```php
friends_add_friend( $actor_wp_id, $target_wp_id )
```

This preserves BuddyBoss connection restrictions, including role, profile, gender, privacy, and other configured restrictions.

If BuddyBoss rejects the request, QuickDate must either:

- delete the local pending row immediately, or
- retain it only as a failed local projection and allow reconciliation to remove it.

The recommended behavior is to delete it immediately and log the rejection.

---

## 6.2 QuickDate friend approval

After QuickDate changes the pending row to active:

1. Verify the local update.
2. Send:

```json
{
  "origin": "socials",
  "operation": "connection_accept",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

The WordPress endpoint must:

1. Map both QuickDate IDs through `qd_user_id`.
2. Locate the BuddyBoss pending friendship.
3. Call:

```php
friends_accept_friendship( $friendship_id )
```

4. Verify:

```php
friends_check_friendship_status( $actor_wp_id, $target_wp_id )
```

is:

```text
is_friend
```

The endpoint must not directly update BuddyBoss friendship tables.

---

## 6.3 QuickDate rejection or withdrawal

When a QuickDate pending friend request is rejected:

1. Delete the QuickDate pending row.
2. Verify deletion.
3. Send:

```json
{
  "origin": "socials",
  "operation": "connection_reject",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

When the requester cancels the request, use:

```text
connection_withdraw
```

The endpoint must call the appropriate native BuddyBoss function:

```php
friends_reject_friendship()
friends_withdraw_friendship()
```

The command must be idempotent if the BuddyBoss request has already disappeared.

---

## 6.4 QuickDate unfriend

An accepted QuickDate friendship removal must produce:

```json
{
  "origin": "socials",
  "operation": "connection_remove",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

The endpoint must call:

```php
friends_remove_friend( $actor_wp_id, $target_wp_id )
```

It must not call `bp_stop_following()` as a substitute for removing a connection.

Independent ordinary follows must survive unless the canonical BuddyBoss follow state says they should be removed.

---

## 6.5 QuickDate ordinary follow

QuickDate ordinary follow is distinct from QuickDate Add Friend.

It must send:

```json
{
  "origin": "socials",
  "operation": "follow",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

The WordPress endpoint calls:

```php
bp_start_following(
    array(
        'leader_id'   => $target_wp_id,
        'follower_id' => $actor_wp_id,
    )
);
```

No Socials ordinary follow may create a BuddyBoss connection request.

# 7. Blocking behavior

## 7.1 BuddyBoss-originated block

Register:

```php
add_action(
    'bp_moderation_after_save',
    array( $this, 'handle_buddyboss_moderation_save' ),
    20,
    1
);
```

The handler must verify:

```php
$item_type === BP_Moderation_Members::$moderation_type
```

and:

```php
(int) $moderation->user_report === 0
```

Then:

```text
A → B block:
    remove BuddyBoss connection
    remove BuddyBoss A → B follow
    remove BuddyBoss B → A follow
    delete Streams A → B follow
    insert Streams A → B block
    delete Socials A → B relationship rows
    insert Socials A → B block
```

The BuddyBoss native functions should be used for BuddyBoss state:

```php
friends_remove_friend()
bp_stop_following()
```

The external databases should be updated using prepared `mysqli` statements.

---

## 7.2 Streams-originated block

After the local Streams block insert succeeds and is verified, send:

```json
{
  "origin": "streams",
  "operation": "block",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

WordPress calls the native BuddyBoss moderation function or moderation API already available in the installation.

It must not directly insert a BuddyBoss moderation row.

The BuddyBoss moderation hook then performs the canonical outward reconciliation.

---

## 7.3 Socials-originated block

After QuickDate inserts:

```text
blocks.user_id = actor
blocks.block_userid = target
```

and verifies the row, send:

```json
{
  "origin": "socials",
  "operation": "block",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

WordPress then creates the canonical BuddyBoss block and performs the complete destructive cascade.

---

## 7.4 Unblock

Unblock is non-restorative.

After the local external block is deleted and verified, send:

```json
{
  "origin": "streams",
  "operation": "unblock",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

or:

```json
{
  "origin": "socials",
  "operation": "unblock",
  "actor_id": 123,
  "target_id": 456,
  "event_id": "uuid"
}
```

The endpoint removes the BuddyBoss block through native BuddyBoss moderation functions. The BuddyBoss moderation deletion hook removes the corresponding external blocks.

No previous connection or follow should be restored.

# 8. Signed endpoint requirements

The endpoint must use HMAC authentication.

Required headers:

```text
X-BZJ-Timestamp
X-BZJ-Signature
```

The signature is:

```text
HMAC-SHA256(
    timestamp + "." + raw_request_body,
    BUZZ_SSO_SECRET
)
```

The endpoint must reject:

- Missing timestamp.
- Non-numeric timestamp.
- Timestamp outside the allowed window.
- Missing secret.
- Invalid HMAC.
- Invalid JSON.
- Invalid UUID.
- Unknown origin.
- Unknown operation.
- Missing actor or target.
- Actor equal to target.
- Missing WordPress mapping.
- Unsupported relationship state.

The WordPress username and password from `.env` must not be used as the synchronization credential. The signed HMAC channel is the correct credential.

The endpoint may use:

```php
'permission_callback' => '__return_true'
```

only because Streams and Socials are standalone applications. The callback itself remains protected by HMAC validation.

# 9. Idempotency and event processing

The synchronization event table should contain at least:

```text
event_uuid
origin
operation
actor_wp_id
target_wp_id
status
attempts
next_attempt_at
last_error
processed_at
created_at
updated_at
```

Allowed states:

```text
pending
processing
processed
failed
```

Processing rules:

```text
new UUID:
    insert pending

existing processed UUID:
    return already_processed

existing pending UUID:
    process again

existing failed UUID:
    retry if attempts remain

existing processing UUID:
    reject as busy or recover after timeout
```

The pair lock must be based on the sorted WordPress IDs:

```text
bzj_pair_<lower_id>_<higher_id>
```

Every operation on the same pair must acquire the same lock.

The retry worker must actually execute pending commands. It must not only log them.

Recommended retry schedule:

```text
1 minute
2 minutes
4 minutes
8 minutes
16 minutes
32 minutes
1 hour
```

After the maximum number of attempts, mark the event as:

```text
failed
```

and leave a detailed entry in:

```text
/data/logs/bzj-connections-sync.log
```

# 12. Safer external database helpers

All external writes must use prepared statements.

A projection helper should follow this pattern:

```php
function bzj_streams_delete_follow(mysqli $db, $following_id, $follower_id) {
    $following_id = (int) $following_id;
    $follower_id  = (int) $follower_id;

    if ($following_id < 1 || $follower_id < 1) {
        return false;
    }

    $stmt = $db->prepare(
        'DELETE FROM `Wo_Followers`
         WHERE `following_id` = ?
           AND `follower_id` = ?'
    );

    if (!$stmt) {
        bzj_streams_sync_log(
            'Unable to prepare Streams follow deletion',
            array(
                'table' => 'Wo_Followers',
                'error' => $db->error,
            )
        );

        return false;
    }

    $stmt->bind_param('ii', $following_id, $follower_id);
    $ok = $stmt->execute();
    $error = $stmt->error;
    $stmt->close();

    if (!$ok) {
        bzj_streams_sync_log(
            'Streams follow deletion failed',
            array(
                'table' => 'Wo_Followers',
                'following_id' => $following_id,
                'follower_id' => $follower_id,
                'error' => $error,
            )
        );

        return false;
    }

    $verify = $db->prepare(
        'SELECT 1
         FROM `Wo_Followers`
         WHERE `following_id` = ?
           AND `follower_id` = ?
         LIMIT 1'
    );

    if (!$verify) {
        return false;
    }

    $verify->bind_param('ii', $following_id, $follower_id);
    $verify->execute();
    $result = $verify->get_result();
    $exists = $result && $result->num_rows > 0;
    $verify->close();

    if ($exists) {
        bzj_streams_sync_log(
            'Streams follow deletion verification failed',
            array(
                'table' => 'Wo_Followers',
                'following_id' => $following_id,
                'follower_id' => $follower_id,
            )
        );

        return false;
    }

    return true;
}
```

The same pattern must be used for:

- Follow insert.
- Follow update.
- Block insert.
- Block deletion.
- QuickDate relationship deletion.
- QuickDate block insertion.
- QuickDate block deletion.

A zero-row delete is not necessarily fatal because the desired state may already exist, but it must be logged.

# 13. Streams `Wo_IsFollowRequested()` correction

The proposed modification has a behavioral problem: making a lookup function mutate the database is unsafe.

This function is called from multiple UI and relationship paths. Turning:

```php
Wo_IsFollowRequested()
```

into a function that automatically accepts rows can:

- Accept a request during a display check.
- Trigger unexpected notifications.
- Create inconsistent activity records.
- Bypass the intended distinction between ordinary follow and friend request.

Because the Buzzjuice Streams Friends System is disabled, the preferred approach is:

1. Make all ordinary Streams follows insert with `active = 1`.
2. Remove or disable the UI/API path that creates pending follow requests.
3. Keep `Wo_IsFollowRequested()` read-only.
4. Use an administrative migration to convert any existing pending ordinary follow rows to active rows.

Recommended migration logic:

```sql
UPDATE Wo_Followers
SET active = 1
WHERE active = 0;
```

This must only be executed after confirming that the table contains no relationship type that requires pending requests. A backup is required first.

If the function must be changed, use a read-only compatibility implementation and do not perform an `UPDATE` from inside it.

Modify only these functions in `streams/assets/includes/functions_one.php`:

```text

Wo_DeleteFollow()
Wo_RegisterBlock()
Wo_RemoveBlock()
```

- Adapter receives external IDs.
- Block adapter is called only after local block insert succeeds.

Modify only:

```text
social/requests/ajax/profile.php
social/requests/ajax/useractions.php
social/core.php
```

- Accepted friendship removal sends `connection_remove`.

2. Target user.

# 15. `wwqd_bridge.php` changes

Do not move relationship orchestration into `shared/wwqd_bridge.php`.

That file should remain responsible for:

- User identity mapping.
- Profile synchronization.
- Existing compatibility helpers.
- Database connection wrappers.

The relationship control plane belongs exclusively in:

```text
/wp-content/mu-plugins/bzj-connections-sync.php
```

One important correction is required in the existing bridge: the conditional wrappers shown in the supplied file are recursively self-referential:

```php
if (!function_exists('get_wp_db_conn')) {
    function get_wp_db_conn() {
        if (function_exists('get_wp_db_conn')) {
            return \get_wp_db_conn();
        }
    }
}
```

Because the function is being defined inside the conditional, this fallback pattern can recurse when invoked. Since `shared/db_helpers.php` already defines these functions, the wrappers should be removed or renamed rather than redefining the same global functions.

Use the existing functions from `db_helpers.php` directly:

```php
get_wp_db_conn()
get_qd_db_conn()
get_wowonder_db()
bzj_get_sso_secret()
```

```php
    public function handle_connection_management(WP_REST_Request $request) {
        $raw = $request->get_body();

        $result = $this->authenticate_request($request, $raw);
        if (is_wp_error($result)) {
            return $result;
        }

        $payload = json_decode($raw, true);
        if (!is_array($payload)) {
            return new WP_Error('bzj_invalid_payload', 'Invalid JSON payload.', array('status' => 400));
        }

        $origin = isset($payload['origin']) ? sanitize_key($payload['origin']) : '';
        $operation = isset($payload['operation']) ? sanitize_key($payload['operation']) : '';
        $actor_id = isset($payload['actor_id']) ? absint($payload['actor_id']) : 0;
        $target_id = isset($payload['target_id']) ? absint($payload['target_id']) : 0;
        $event_uuid = isset($payload['event_id']) ? sanitize_text_field($payload['event_id']) : '';

        if (empty($origin) || empty($operation) || $actor_id < 1 || $target_id < 1 || $actor_id === $target_id) {
            return new WP_Error('bzj_invalid_operation', 'Missing or invalid operation metadata.', array('status' => 400));
        }

        if (!preg_match('/^[0-9a-fA-F-]{36}$/', $event_uuid)) {
            return new WP_Error('bzj_invalid_event', 'Invalid event UUID.', array('status' => 400));
        }

        $this->record_event($event_uuid, $origin, $operation, $actor_id, $target_id);

        $done = $this->route_operation_from_remote($origin, $operation, $actor_id, $target_id);

        if (is_wp_error($done)) {
            return $done;
        }

        return rest_ensure_response(array(
            'success' => true,
            'event_id' => $event_uuid,
            'origin' => $origin,
            'operation' => $operation,
            'actor_id' => $actor_id,
            'target_id' => $target_id,
        ));
    }

    private function authenticate_request(WP_REST_Request $request, $raw) {
        $signature = $request->get_header('X-BZJ-Signature');
        $timestamp = $request->get_header('X-BZJ-Timestamp');

        if (empty($signature) || empty($timestamp)) {
            return new WP_Error('bzj_missing_signature', 'Missing HMAC headers.', array('status' => 401));
        }

        if (!is_numeric($timestamp)) {
            return new WP_Error('bzj_bad_timestamp', 'Invalid timestamp.', array('status' => 401));
        }

        $now = time();
        if (abs($now - (int) $timestamp) > 300) {
            return new WP_Error('bzj_stale_timestamp', 'Request expired.', array('status' => 401));
        }

        $secret = function_exists('bzj_get_sso_secret') ? bzj_get_sso_secret() : (defined('BUZZ_SSO_SECRET') ? BUZZ_SSO_SECRET : '');
        if (empty($secret)) {
            return new WP_Error('bzj_missing_secret', 'SSO secret not configured.', array('status' => 401));
        }

        $expected = hash_hmac('sha256', $timestamp . '.' . $raw, $secret);
        if (!hash_equals($expected, $signature)) {
            return new WP_Error('bzj_invalid_signature', 'Invalid HMAC signature.', array('status' => 401));
        }

        return true;
    }

    private function record_event($event_uuid, $origin, $operation, $actor_id, $target_id) {
        global $wpdb;

        $exists = $wpdb->get_var($wpdb->prepare(

            $event_uuid
        ));

        if ($exists) {
            return $exists;
        }

        $ts = time();
        $wpdb->insert(
            $this->events_table,
            array(
                'event_uuid' => $event_uuid,
                'origin' => $origin,
                'operation' => $operation,
                'actor_wp_id' => $actor_id,

                'attempts' => 0,

                'updated_at' => $ts,

    private function route_operation_from_remote($origin, $operation, $actor_id, $target_id) {
        $actor_id = absint($actor_id);
        $target_id = absint($target_id);

                case 'follow':
                    return $this->canonical_follow_upsert($actor_id, $target_id, 'active');

                case 'block':

                case 'unblock':

                default:
                    return new WP_Error('bzj_unsupported_streams_op', 'Unsupported Streams operation.', array('status' => 400));
            }
        }

        if ($origin === 'socials') {
            switch ($operation) {
                case 'connection_request':
                    return $this->canonical_connection_request($actor_id, $target_id);
                case 'connection_accept':

                case 'connection_reject':
                    return $this->canonical_connection_reject($actor_id, $target_id);
                case 'connection_withdraw':

                case 'connection_remove':
                    return $this->canonical_connection_remove($actor_id, $target_id);
                case 'follow':
                    return $this->canonical_follow_upsert($actor_id, $target_id, 'active');
                case 'unfollow':

        return new WP_Error('bzj_unknown_origin', 'Unknown origin.', array('status' => 400));
    }

    private function canonical_follow_upsert($actor_id, $target_id, $state) {
        if (!function_exists('bp_start_following') || !function_exists('bp_stop_following')) {
            return new WP_Error('bzj_missing_buddypress_follow', 'BuddyBoss follow APIs not available.', array('status' => 500));
        }

        $state = strtolower($state);

        if ($state === 'active') {
            $exists = function_exists('bp_is_following') ? bp_is_following(array(
                'leader_id' => $target_id,
                'follower_id' => $actor_id,
            )) : false;

            if (!$exists) {
                $ok = bp_start_following(array(
                    'leader_id' => $target_id,
                    'follower_id' => $actor_id,
                ));
                if (!$ok) {
                    return new WP_Error('bzj_follow_start_failed', 'Unable to start BuddyBoss follow.', array('status' => 500));
                }
            }
        } elseif ($state === 'deleted') {
            $exists = function_exists('bp_is_following') ? bp_is_following(array(
                'leader_id' => $target_id,
                'follower_id' => $actor_id,
            )) : false;

            if ($exists) {
                $ok = bp_stop_following(array(
                    'leader_id' => $target_id,
                    'follower_id' => $actor_id,
                ));
                if (!$ok) {
                    return new WP_Error('bzj_follow_stop_failed', 'Unable to stop BuddyBoss follow.', array('status' => 500));
                }
            }
        }

        return true;
    }

    private function canonical_block_upsert($actor_id, $target_id, $state) {
        if (!function_exists('bp_moderation_add') || !function_exists('bp_moderation_delete')) {
            return new WP_Error('bzj_missing_moderation_api', 'BuddyBoss moderation APIs not available.', array('status' => 500));
        }

        if (!class_exists('BP_Moderation_Members')) {
            return new WP_Error('bzj_missing_moderation_class', 'BuddyBoss moderation class not available.', array('status' => 500));
        }

        $state = strtolower($state);

        if ($state === 'blocked') {
            $existing = bp_moderation_report_exist($target_id, BP_Moderation_Members::$moderation_type);
            if (!$existing) {
                $moderation = bp_moderation_add(array(
                    'content_id' => $target_id,
                    'content_type' => BP_Moderation_Members::$moderation_type,
                    'note' => 'Member block',
                ));

                if (empty($moderation) || empty($moderation->id)) {
                    return new WP_Error('bzj_block_not_created', 'Unable to create BuddyBoss member block.', array('status' => 500));
                }
            }
        } elseif ($state === 'unblocked') {
            $moderation = new BP_Moderation($target_id, BP_Moderation_Members::$moderation_type);
            if ($moderation && !empty($moderation->id)) {
                $deleted = bp_moderation_delete(array(
                    'content_id' => $target_id,
                    'content_type' => BP_Moderation_Members::$moderation_type,
                ));

                if (empty($deleted) || empty($deleted->report_id)) {
                    return new WP_Error('bzj_block_not_removed', 'Unable to remove BuddyBoss member block.', array('status' => 500));
                }
            }
        }

        return true;
    }

        $secret = function_exists('bzj_get_sso_secret') ? bzj_get_sso_secret() : (defined('BUZZ_SSO_SECRET') ? BUZZ_SSO_SECRET : '');
        if (empty($secret)) {
            return false;
        }

        $json = wp_json_encode($payload);
        $timestamp = (string) time();
        $signature = hash_hmac('sha256', $timestamp . '.' . $json, $secret);

        $request_url = home_url('/wp-json/bzj/v6/connection-management');

        $args = array(
            'timeout' => 15,
            'headers' => array(
                'Content-Type' => 'application/json',
                'X-BZJ-Timestamp' => $timestamp,
                'X-BZJ-Signature' => $signature,
            ),
            'body' => $json,
            'method' => 'POST',
        );

        $response = wp_remote_post($request_url, $args);

        if (is_wp_error($response)) {
            // Never fail the canonical side because the external side has not yet processed.
            return false;
        }

        $code = wp_remote_retrieve_response_code($response);
        if ($code >= 400) {
            return false;
        }

        return true;
    }
```

```php
                return 0;
            }

            $stmt = $db->prepare("SELECT user_id FROM users WHERE wp_user_id = ? LIMIT 1");
            if (!$stmt) {
                return 0;
            }

            $stmt->bind_param('i', $wp_user_id);
            $stmt->execute();
            $stmt->bind_result($mapped);
            $stmt->fetch();
            $stmt->close();

            return (int) $mapped;
        }

        return 0;
    }
}

if (!function_exists('bzj_get_pair_key')) {
    function bzj_get_pair_key($actor_id, $target_id) {
        $a = (int) $actor_id;
        $b = (int) $target_id;

        if ($a === $b) {
            return sprintf('pair_%d_%d', $a, $b);
        }

        if ($a < $b) {
            return sprintf('pair_%d_%d', $a, $b);
        }

        return sprintf('pair_%d_%d', $b, $a);
    }
}
```
