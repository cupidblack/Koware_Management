I reviewed the current Buzzjuice source, the supplied BuddyBoss implementation, the existing `wwqd_bridge.php`, the 5.0 MU plugin, and both GitHub responses. The architecture is sound, but I would **not deploy 5.0.0 as-is**.

Several important corrections are required before deployment.

## 1. Critical corrections

### A. Connections and follows must be separate canonical states

The previous implementation treats the relationship as essentially:

`none → requested → connected`

That is insufficient because Buzzjuice now has **two independent relationship dimensions**:

1. **Connection**

   * none
   * requested
   * connected

2. **Follow**

   * A follows B
   * B follows A
   * both
   * neither

A user can therefore be:

> A connected to B, while A follows B and B does not follow A.

The canonical ledger needs independent `follow_a_to_b` and `follow_b_to_a` fields.

### B. QuickDate "Like" should not be the synchronization primitive

This is the most important correction to the original proposal.

QuickDate's `like()` operates on its `likes` table and is part of the dating/matching mechanism. The actual QuickDate friend/follower mechanism uses the `followers` table and `Wo_RegisterFollow()`. 

Therefore:

**BuddyBoss follow**
→ Streams follow
→ QuickDate follower

not:

**BuddyBoss follow**
→ QuickDate dating like.

Likewise:

**QuickDate dating like**
→ should **not** automatically create a BuddyBoss follow.

Otherwise a dating swipe becomes a network relationship, which couples two completely different product concepts.

### C. QuickDate Add Friend is implemented through `followers`

The current `add_friend()` calls `Wo_RegisterFollow()`. 

Therefore the synchronization layer should interpret:

`Socials Add Friend → BuddyBoss connection request`

while the local QuickDate representation remains its existing follower/request row.

### D. The BuddyBoss rejected/withdrawn hook signatures in 5.0 are wrong

The installed BuddyBoss source shows:

* `friends_friendship_rejected` receives **2 arguments**: friendship ID and friendship object.
* `friends_friendship_withdrawn` also receives **2 arguments**: friendship ID and friendship object.
* `friends_friendship_deleted` receives **3 arguments**.
* `friends_friendship_requested` and `friends_friendship_accepted` receive the friendship ID, initiator, friend, and friendship object. 

So the 5.0 registration:

```php
add_action('friends_friendship_rejected', '...', 20, 3);
```

and routing it into a function expecting three user IDs is incorrect.

The updated implementation must extract:

```php
$friendship->initiator_user_id
$friendship->friend_user_id
```

for rejected/withdrawn events.

### E. BuddyBoss's native connection API must remain authoritative

`friends_add_friend()` creates the connection request and fires the appropriate lifecycle hook. 

Therefore external requests should **never directly insert into `wp_bp_friends`**.

They must call:

```php
friends_add_friend($actor, $target, false);
```

This preserves the existing Buzzjuice restrictions on connection requests.

Likewise, acceptance must use the actual friendship ID:

```php
friends_accept_friendship($friendship_id);
```

The BuddyBoss source confirms this API requires the friendship ID. 

### F. Blocking should proactively remove existing connections

The supplied recommendation is correct conceptually.

When:

> A blocks B

the canonical state becomes:

```text
A → B blocked
connection = none
A → B follow = false
B → A follow = false
```

and the existing BuddyBoss connection should be removed immediately.

The block itself remains **directional**. Thus:

```text
A → B blocked
```

does not automatically mean:

```text
B → A blocked
```

The external platforms, however, should prevent the blocked pair from maintaining any follower/connection relationship.

### G. Unblocking must never restore the old relationship

This remains a hard rule:

```text
block
   ↓
remove connection/follows
   ↓
unblock
   ↓
still no connection/follow
```

The user must deliberately reconnect/follow again.

### H. The external platform should report after successful local writes

This recommendation from the GitHub analysis is correct. The current Streams implementation actually performs direct database operations such as the `Wo_RegisterFollow()` insert and `Wo_DeleteFollow()` delete. 

Therefore:

```text
External local operation
        ↓
successful
        ↓
signed report to WordPress
        ↓
BuddyBoss canonical operation
        ↓
canonical reconciliation
```

rather than trying to intercept the operation before it happens.

# 10. External connection requests

The most important implementation rule is:

```php
friends_add_friend(
    $actor_wp_id,
    $target_wp_id,
    false
);
```

**Never:**

```php
INSERT INTO wp_bp_friends ...
```

The native BuddyBoss function performs the normal BuddyBoss processing and emits the lifecycle event. 

This preserves your existing BuddyBoss request restrictions.

For example:

```php
case BZJ_OP_CONNECTION_REQUEST:

    if (!function_exists('friends_add_friend')) {
        return false;
    }

    $status = friends_check_friendship_status(
        $actor_wp_id,
        $target_wp_id
    );

    if (
        $status === 'is_friend' ||
        $status === 'pending' ||
        $status === 'awaiting_response'
    ) {
        bzj_csync_enqueue_reconcile(
            $actor_wp_id,
            $target_wp_id,
            'connection_request_already_exists'
        );

        return true;
    }

    bzj_csync_context_set($event_uuid, $origin);

    try {
        $result = friends_add_friend(
            $actor_wp_id,
            $target_wp_id,
            false
        );
    } finally {
        bzj_csync_context_clear();
    }

    return (bool)$result;
```

# 17. External reconciliation algorithm

The queue processor should never replay the original event blindly.

Instead:

```text
event arrives
      ↓
read current canonical state
      ↓
lock pair
      ↓
rebuild Streams
      ↓
rebuild Socials
      ↓
success → processed
failure → retry
```

This is one of the strongest recommendations in the GitHub analysis. The previous 4.1 architecture explicitly moved toward state-based reconciliation and exponential retry. 

For example, if these happen almost simultaneously:

```text
A follows B
A unfollows B
A follows B
```

the queue should not blindly replay:

```text
follow
unfollow
follow
```

Instead it reads:

```text
canonical follow_a_to_b = 1
```

and simply makes both external platforms converge to:

```text
A follows B
```

# 18. Retry model

Use:

```text
attempt 1 → 60 seconds
attempt 2 → 120 seconds
attempt 3 → 240 seconds
attempt 4 → 480 seconds
...
maximum → 1 hour between attempts
```

with a maximum retry count such as:

```php
define('BZJ_CSYNC_MAX_RETRIES', 8);
```

and:

```php
$delay = min(
    3600,
    60 * pow(2, max(0, $attempt - 1))
);
```

This is materially better than marking an event processed merely because the first reconciliation attempt occurred.
