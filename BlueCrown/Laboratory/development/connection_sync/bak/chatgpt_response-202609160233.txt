## The key design rules

1. **BuddyBoss is the source of truth.**
2. **Connection, follow and block are separate canonical dimensions.**
3. **Streams has no synchronized Friend relationship because its Friend system is disabled.**
4. **QuickDate Add Friend is represented using its existing follower/request mechanism.**
5. **QuickDate Likes remain completely outside this system.**
6. **Blocks dominate connections and follows.**
7. **Unblocking never automatically restores previous relationships.**
8. **External platforms request/report state changes; they do not become authorities.**
9. **BuddyBoss's existing connection restrictions remain authoritative.**
10. **Direct external DB access is encapsulated in `wwqd_bridge.php`.**
11. **Every external event is authenticated, UUID-addressable and idempotent.**
12. **Pair-level locking prevents relationship races.**
13. **Canonical state, not queued events, determines the desired final state.**
14. **Failed propagation is retried rather than rolling back BuddyBoss.**
15. **Reconciliation repairs drift without changing the canonical state.**
16. **Operational state uses database tables; diagnostic logging uses `/data/logs`.**
17. **Existing long files are patched incrementally rather than regenerated.**

This is materially stronger than the original four-step implementation plan because it gives Buzzjuice a proper **relationship control plane**, rather than a collection of database synchronizers. It also incorporates the useful GitHub recommendations—durable queue, canonical ledger, pair locking, HMAC/event IDs, reconciliation, block precedence and event context—while correcting the places where the earlier proposal did not match the actual current Buzzjuice source.

Then we can apply the incremental `wwqd_bridge.php`, Streams and Socials patches against this stable core.
