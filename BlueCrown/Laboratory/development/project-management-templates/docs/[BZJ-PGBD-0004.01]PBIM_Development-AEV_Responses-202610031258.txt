### OPEN QUESTIONS FOR THE ARCHITECTURAL CHALLENGE GATE

The AEC should specifically address:

1. **Complexity vs. Ceremony Trade-off**
   - Does the three-layer model (Governance → Assurance → Execution) reduce overhead or create it?
   - Would a simpler two-layer model (Governance → Execution with inline verification) work for small projects?
   - Is the four-artifact protocol (AEA → AEV → AEC → AECC) the right decomposition or should it be streamlined?

2. **Identifier System Viability**
   - Does the provisional 49-process structure, once a registry is in place, actually provide useful process navigation?
   - Or does it create a false sense of structure that obscures the simpler lifecycle states?
   - Can the system operate effectively with just Project ID, Task ID, Artifact ID, and Lifecycle State without a 49-process overlay?

3. **Scalability Proof**
   - Can the Mandatory Core actually be applied to a one-person, one-agent small project without becoming trivial or burdensome?
   - Does risk-based conditional control selection actually occur in practice, or does every project end up with maximum ceremony?

4. **Authority Collapse Risk**
   - On a small project where one person performs multiple roles, can the logical separation of authority actually be enforced?
   - Is there a hidden handoff procedure or tool required to prevent informal authority shortcuts?

5. **Challenge Gate Timing**
   - Is a single AEC gate before implementation sufficient, or should recurring challenge gates be added during implementation and before release?
   - If a major requirement changes mid-project, does the architecture require re-challenge, or is that a change-management issue?

6. **Governance Repository Contamination**
   - How is the Governance Repository kept distinct from source code without requiring two separate physical repositories?
   - What prevents a developer from accidentally committing governance documents to the production repository?
