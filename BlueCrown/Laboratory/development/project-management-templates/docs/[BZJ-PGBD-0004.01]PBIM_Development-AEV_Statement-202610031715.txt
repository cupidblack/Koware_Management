### Revised Controlled Baseline Candidate — R1.3

**System:** Project Base Integration Initialization Manager (PBIIM)
**Previous AEV:** R1.2
**AEC Challenged Version:** R1.2
**Current Revision:** R1.3
**Lifecycle:** AEV — RE-VERIFICATION REQUIRED
**Implementation Authorization:** NOT GRANTED
**Production Authorization:** NOT GRANTED
**AECC Authorization:** NOT GRANTED

---

# 1. Revision Purpose

R1.3 is produced in response to the PBIIM R1.2 Architectural Engineering Challenge Duel.

The AEC duel demonstrated that R1.2 remained vulnerable to:

* risk-scaling regression;
* missing operational-readiness control;
* ambiguous requirement-change handling;
* incomplete operating-template readiness;
* uninstantiated human authority;
* authority/technical-permission mismatch;
* registry integrity and recovery failure;
* insufficient challenge-independence enforcement;
* Task Packet bypass;
* weak stop/reset/emergency enforcement;
* evidence manipulation;
* repository-admin override;
* automation compromise;
* human-authority unavailability.

These findings are documented in the collaborating-agent challenge results. Kilo classified the architecture **AEC FAIL — RETURN TO AEV**, while GitHub/Copilot independently classified several of the same mechanisms as blockers. Jules classified the architecture **AEC PASS WITH AMENDMENTS**, but identified four material amendments required before closure.

R1.3 resolves these findings at the architectural level.

It does not claim that the required implementation mechanisms already exist.

---

# 2. Controlled Disposition

R1.2 is:

**SUPERSEDED AS A BASELINE CANDIDATE**

R1.3 becomes the current:

**CONTROLLED AEV BASELINE CANDIDATE**

The architecture remains:

**NOT APPROVED FOR IMPLEMENTATION**

and:

**NOT APPROVED FOR PRODUCTION**

---

# 3. Core Architectural Model

The following remains retained:

**Governance → Assurance → Execution**

and:

**AEA → AEV → AEC → AECC**

The fundamental distinction remains:

> Governance determines authority.
> Assurance determines whether the authorized design and evidence satisfy the governing conditions.
> Execution performs authorized work.

---

# 4. Architectural Maturity Boundary

R1.3 retains the distinction:

**DESIGNED → ENFORCEABLE → ENFORCED**

and:

**E0 → E1 → E2 → E3 → E4**

but introduces an additional rule:

> No architectural control may be treated as operationally effective solely because an enforcement mechanism is described.

The architecture therefore distinguishes:

### AEV Verification

The architecture specifies an enforceable control.

### Implementation Verification

The implementation demonstrates that the control actually operates.

This prevents architectural verification from falsely claiming implementation evidence.

---

# 5. Risk-Scaled Governance Profiles

This is a mandatory R1.3 correction.

R1.2's removal of explicit governance profiles is reversed.

PBIIM shall provide:

### LIGHT

For genuinely low-risk, bounded work.

### STANDARD

For normal project work.

### HIGH-ASSURANCE

For high-impact, security-sensitive, financial, irreversible or production-critical work.

The profiles scale both:

* governance ceremony;
* evidence depth.

They are not merely evidence-depth profiles.

---

# 6. LIGHT PROFILE

The Light Profile may reduce:

* document volume;
* review depth;
* Task Packet granularity;
* challenge breadth;
* approval frequency.

It may not eliminate:

* authority assignment;
* protected security controls;
* appropriate traceability;
* secret handling;
* stop conditions;
* material-change escalation;
* required human authorization.

A one-day low-risk task must not automatically receive the same full architectural ceremony as a high-risk payment-system migration.

This directly resolves the R1.2 risk-scaling regression identified by Kilo and Jules.

---

# 7. STANDARD PROFILE

The Standard Profile is the default.

It includes:

* normal Task Packet governance;
* appropriate AEA;
* AEV;
* proportional AEC;
* evidence controls;
* implementation verification;
* operational-readiness review;
* release authorization.

---

# 8. HIGH-ASSURANCE PROFILE

The High-Assurance Profile applies where one or more conditions exist:

* financial impact;
* security-critical operation;
* sensitive data;
* irreversible migration;
* production infrastructure;
* material customer impact;
* regulatory/legal requirement;
* high blast radius;
* safety-critical operation.

High-Assurance work requires stronger independent review and evidence.

---

# 9. Risk Classification

Every project must establish its governance profile before chartering.

If classification is disputed:

**the higher applicable profile applies until the dispute is resolved.**

A project cannot select the lower profile merely because it reduces governance overhead.

---

# 10. Human Authority Register

R1.3 makes H0 an instantiated authority rather than merely an abstract role.

Before project chartering, the Human Authority Register must identify:

```yaml
project_id:
h0_principal:
h0_delegate:
h1_reviewer:
authority_scope:
appointment_date:
appointment_authority:
expiry_or_review:
```

A project cannot enter `CHARTERED` without a valid H0 assignment.

---

# 11. H0 Unavailability

If H0 becomes unavailable:

1. the registered delegate may act only within delegated authority;
2. the delegate cannot exceed H0's recorded scope;
3. constitutional changes remain blocked;
4. high-risk production authorization requires the applicable higher authority;
5. the event is recorded.

No participant becomes H0 merely because they possess technical credentials.

---

# 12. H0 Substitution

Changing H0 is a governance event.

It requires:

* recorded appointment;
* authority verification;
* register update;
* applicable review;
* audit trail.

A technical administrator cannot silently become H0.

---

# 13. Authority/Permission Dual Control

R1.3 establishes two separate models:

### Governance Authority

Who is authorized to decide.

### Technical Capability

Who can physically execute the decision.

Neither substitutes for the other.

A person may have technical capability without governance authority.

A person may have governance authority without technical execution capability.

---

# 14. Authority-Permission Matrix

Every material project shall maintain:

**Authority → Account → Capability → Repository Permission → Deployment Permission**

The mapping must identify:

* human account;
* agent identity;
* automation identity;
* repository role;
* branch rights;
* merge rights;
* deployment rights;
* credential scope.

---

# 15. Permission Drift

Where actual permissions exceed declared authority:

`AUTHORITY-PERMISSION-DRIFT`

is created.

Affected operations are blocked until the discrepancy is resolved.

Where declared authority exceeds technical capability:

`AUTHORITY-CAPABILITY-GAP`

is recorded.

This does not grant technical access automatically.

---

# 16. Registry Integrity

The identifier registry remains canonical but is no longer treated as an ordinary mutable file.

It is governed as a **controlled state store**.

Required characteristics:

* protected canonical branch;
* restricted write authority;
* serialized updates;
* schema validation;
* uniqueness validation;
* append-only audit history;
* integrity verification;
* recovery procedure;
* backup;
* restore verification;
* conflict detection.

---

# 17. Registry Write Serialization

Identifier creation shall follow:

**REQUEST → RESERVE → VALIDATE → COMMIT → CONFIRM**

Only one authoritative registry transaction may establish a particular identifier.

Concurrent requests must be serialized.

A stale branch cannot create authoritative identity.

---

# 18. Registry Integrity Anchor

Each authoritative registry revision shall contain or reference:

* revision ID;
* parent revision;
* content hash;
* authorizing authority;
* timestamp;
* validation result.

Restoration requires verification that the restored registry revision is authoritative.

---

# 19. Registry Recovery

If the canonical registry is corrupted or unavailable:

`REGISTRY-BLOCKED`

is entered.

Recovery requires:

1. identify last trusted revision;
2. validate its integrity;
3. identify changes after that revision;
4. reconcile pending reservations;
5. establish a new canonical revision;
6. independently verify the result.

No local backup becomes authoritative merely because it is newer.

---

# 20. Registry Administrative Override

Repository administration cannot silently redefine the registry.

Any operation that:

* force-pushes;
* restores;
* deletes;
* replaces;
* rewrites;
* or changes registry history

must generate a governance event.

For high-assurance projects, registry recovery requires independent review.

---

# 21. Challenge Independence

R1.3 strengthens the AEC independence model.

Independence is no longer established by metadata alone.

It requires:

1. distinct principal;
2. distinct role;
3. no conflicting ownership;
4. independent evidence path where practical;
5. challenge appointment authority;
6. recorded conflict-of-interest status.

---

# 22. Challenge Independence Classes

### I1 — Organizational Independence

Different accountable principal.

### I2 — Evidence Independence

Challenge is not based solely on the design owner's supplied evidence.

### I3 — Technical Independence

Challenger does not possess uncontrolled authority over the challenged implementation.

### I4 — Governance Independence

Challenger cannot be overruled by the design owner.

For High-Assurance projects, I1–I4 are mandatory.

---

# 23. Small-Team Independence

If a project is too small to provide meaningful independent challenge:

The architecture does not pretend that role reassignment creates independence.

The project must instead use:

* external reviewer;
* separate governance authority;
* independent agent/principal;
* or another approved challenge authority.

If none exists:

`CHALLENGE-BLOCKED`

---

# 24. Epistemic vs Organizational Independence

R1.3 explicitly records two different concepts:

### Epistemic Independence

The challenger independently reasons about the evidence.

### Organizational Independence

The challenger has genuinely separate authority/accountability from the design owner.

Epistemic independence alone cannot satisfy High-Assurance AEC.

This addresses the disclosure in the Kilo duel response that its challenge was epistemically independent but not organizationally independent.

---

# 25. Evidence Integrity

E0–E4 remains.

R1.3 adds an evidence-chain requirement.

Material evidence must be traceable to an integrity anchor.

Examples include:

* immutable commit;
* signed artifact;
* trusted timestamp;
* append-only log;
* external audit store.

The exact mechanism may vary.

The principle does not.

---

# 26. Evidence Verification

A verifier must be able to determine:

1. where evidence originated;
2. whether it changed;
3. who generated it;
4. when it was generated;
5. which system produced it;
6. whether the evidence was sanitized;
7. whether the raw evidence remains available to authorized reviewers.

A sanitized report cannot by itself establish E3/E4.

---

# 27. Evidence-of-Evidence

Where evidence itself is material to approval, the verification record must preserve the provenance of the evidence.

This prevents:

**report → report verification → report verification verification**

from becoming an infinite loop.

The trusted boundary is established through an integrity anchor and accountable verifier.

---

# 28. Task Packet Scope

R1.3 expands Task Packet enforcement to include derived effects.

Scope validation must consider:

* direct files;
* generated files;
* dependencies;
* migrations;
* configuration;
* build artifacts;
* schema changes;
* deployment effects;
* infrastructure effects.

A change cannot escape Task Packet control merely because a tool generated it.

---

# 29. Task Packet Dependency Expansion

If implementation discovers necessary work outside scope:

**STOP → REPORT → NEW/SUPERSEDING PACKET**

The worker may not silently expand authority.

Emergency work follows the emergency protocol.

---

# 30. Task Packet Immutability

Once dispatched:

**DRAFT → APPROVED → DISPATCHED**

the packet cannot be silently edited.

Scope expansion requires:

* new packet;
* superseding packet;
* or authorized emergency packet.

Historical packets remain immutable.

---

# 31. Stop Enforcement

A stop state now has both:

### Governance State

The project is prohibited from progressing.

### Execution Control

Technical mechanisms prevent applicable progression.

For material/high-risk work, both are required.

---

# 32. Stop Classes

### S1 — Advisory Stop

Work may continue only where explicitly permitted.

### S2 — Mandatory Stop

Affected work cannot continue.

### S3 — System Stop

All dependent work stops.

### S4 — Emergency Safety Stop

Execution is halted immediately.

---

# 33. Resume Control

Resume requires:

* stop ID;
* cause;
* resolution;
* evidence;
* reviewer;
* authority;
* timestamp.

A worker cannot resume its own stopped task without the required authorization.

---

# 34. Reset Operationalization

Architectural Reset becomes an executable governance transition:

`ACTIVE → RESET-TRIGGERED → FROZEN → REASSESSMENT → REBASELINING`

Affected approvals are invalidated.

---

# 35. Reset During Migration

If reset occurs during an irreversible migration:

PBIIM must not pretend that application rollback equals system rollback.

The recovery decision must account for:

* data state;
* schema state;
* external side effects;
* downstream dependencies;
* operational state.

If complete rollback is impossible, recovery must be handled as a new controlled architectural state.

---

# 36. Emergency Governance

Emergency authority is bounded.

Emergency action may bypass **ordinary sequencing**, but may not bypass:

* accountability;
* evidence;
* security;
* post-event review;
* architectural reconciliation.

---

# 37. Emergency Delegate

The Human Authority Register may designate an emergency delegate.

The delegate's authority must contain:

* permitted actions;
* maximum risk;
* expiry;
* notification requirements;
* post-event obligations.

The delegate does not become constitutional H0.

---

# 38. Operational-Readiness Gate

R1.3 inserts a distinct gate:

**IMPLEMENTATION-VERIFIED → OPERATIONALLY-READY → RELEASE-AUTHORIZED**

A project cannot be released merely because implementation passes verification.

---

# 39. Operational-Readiness Criteria

The gate must evaluate, as applicable:

1. monitoring;
2. alerting;
3. observability;
4. rollback;
5. backup;
6. data recovery;
7. migration recovery;
8. incident ownership;
9. operational documentation;
10. dependency readiness;
11. security readiness;
12. capacity/performance;
13. support/on-call readiness.

Not every criterion must apply to every project, but applicability must be determined.

---

# 40. Release Boundary

The release authority must verify:

**Implementation Verified**

AND

**Operationally Ready**

AND

**Required approval present**

before:

**Release Authorized**

This closes the production-readiness gap identified by both Kilo and Jules.

---

# 41. Requirement-Change Materiality

R1.3 defines four levels.

### Level 0 — Non-material

No architecture, security, dependency or acceptance change.

→ Task-level handling.

### Level 1 — Material

Changes requirement scope or acceptance but not architecture.

→ AEV impact review.

### Level 2 — Architecture-changing

Changes architectural structure, authority, dependency, security or lifecycle.

→ AEV + AEC.

### Level 3 — Load-bearing failure

Invalidates an approved assumption.

→ Architectural Reset.

---

# 42. Requirement-Change Decision Matrix

| Change                                      | Action                          |
| ------------------------------------------- | ------------------------------- |
| Wording/formatting                          | Task/document update            |
| Local implementation detail                 | Task Packet                     |
| Acceptance criteria change                  | AEV impact review               |
| Dependency architecture change              | AEV                             |
| Security boundary change                    | AEV + AEC                       |
| Authority model change                      | PBIIM constitutional review     |
| Load-bearing assumption failure             | Reset                           |
| Release/operational risk materially changes | Operational-readiness re-review |

---

### Template Skeleton

### Production Template

Must have passed:

* AEV;

The known empty sections:

`0004.02 – 0004.09`

* be populated;

# 46. Contradictory Workflow Sources

Where multiple workflow documents exist, one must be declared canonical.

The architecture prohibits:

* simultaneous canonical guides;
* silent precedence;
* branch-local governance becoming globally authoritative.

A conflict produces:

`WORKFLOW-SOURCE-CONFLICT`

and blocks affected governance decisions.

Changes to:

* authority;

* identifier semantics;
* risk profiles;
* challenge independence;
* security controls;
* reset;
* stop/resume;

---

# 48. Risk Profile Cannot Be Weakened by Local Instruction

A lower-level instruction cannot change:

`HIGH → STANDARD`

or:

`STANDARD → LIGHT`

without the applicable governance authority.

Risk classification is therefore part of controlled project state.

---

# 49. Governance Escalation

Where risk classification is uncertain:

**select the higher applicable profile**

until an authorized review establishes the lower classification.

This prevents governance minimization through ambiguity.

---

# 50. Automation Trust Boundary

Automation is treated as a controlled principal.

Every material automation identity must have:

* defined authority;
* defined permissions;
* defined inputs;
* defined outputs;
* audit trail;
* revocation mechanism.

Automation cannot approve its own authority.

---

# 51. Compromised Automation

If governance automation becomes untrusted:

`AUTOMATION-TRUST-BLOCKED`

is entered.

The system must:

1. stop dependent governance actions;
2. preserve evidence;
3. revoke/disable affected automation;
4. establish trusted validation;
5. review affected decisions;
6. restore service under independent verification.

---

# 52. Repository Administrator Boundary

Repository administration is treated as technical capability.

Repository administrators cannot silently override governance.

High-assurance governance controls must therefore protect against:

* branch deletion;
* force-push;
* CI modification;
* CODEOWNERS modification;
* registry replacement;
* governance-file alteration.

Administrative changes to these controls become auditable governance events.

---

# 53. Human Unavailability

Where H0/H1 are unavailable:

* registered delegates may act within defined scope;
* emergency authority may act within predefined limits;
* constitutional decisions remain blocked;
* irreversible high-risk actions require the appropriate escalation.

Unavailability does not create an implicit authority transfer.

---

# 54. PBIIM Scalability

The architecture now explicitly scales:

**Ceremony + Evidence + Review Depth**

according to:

* risk;
* scope;
* blast radius;
* reversibility;
* security;
* operational impact.

This resolves the prior distinction between evidence scaling and ceremony scaling.

---

# 55. Small Project

A low-risk project may use:

* Light Profile;
* reduced AEA;
* simplified Task Packet;
* reduced challenge scope;
* proportionate evidence.

It still requires:

* H0;
* protected controls;
* material-change escalation;
* required operational-readiness checks.

---

# 56. Large Project

Large projects use:

* delegated authority;
* workstream governance;
* parallel Task Packets;
* distributed verification;
* controlled registry operations;
* bounded escalation.

H0 is not required to personally review every low-level task.

---

# 57. Authority Delegation

Delegation records:

* delegator;
* delegate;
* scope;
* limit;
* expiry;
* escalation;
* revocation.

Delegation cannot silently create constitutional authority.

---

# 58. Agent Role Combination

Agents may combine operational roles where the applicable risk profile permits it.

However:

**role combination cannot collapse mandatory independence.**

A single agent cannot simultaneously satisfy two roles that are required to be independent.

---

# 59. AEC Independence for High-Assurance Work

* independent principal;
* independent evidence path;
* no design ownership;
* no implementation ownership;

`AEC-BLOCKED`
