## 4. CRITICAL DEVELOPER-FACING GAPS FOR AEC CHALLENGE

### Challenge Target 1: PR/Code Review Integration

**What is missing:**
- Does production code go to `buzzjuice.net` before or after AECC closes?
- What GitHub PR template should developers use?
- When is code review scheduled relative to AEC?
- Who is the code reviewer (the lead agent? a human? another developer)?

**Why this matters:**
Developers cannot begin implementation if they do not know when code review occurs.

**AEC Attack Surface:**
- Assume: "Code review occurs after AEV approval"
- Attack: "If AEC finds a critical security flaw, the code is already merged"
- Falsification: "Design the review gate to prevent code merge before AECC"

### Challenge Target 2: Evidence Submission Workflow

**What is missing:**
- Evidence types (E1–E5) are defined, but where does a developer put their evidence?
- Is evidence a GitHub Issue? A PR comment? A markdown file? A directory?
- How does evidence become "verified"?
- Who reviews evidence?

**Why this matters:**
Developers need to know the format and location for evidence before they can close a task.

**AEC Attack Surface:**
- Assume: "Evidence lives in `docs` folder and is human-reviewed"
- Attack: "If the human reviewer is unavailable, does the task hang indefinitely?"
- Falsification: "Define a maximum evidence review SLA or escalation rule"

### Challenge Target 3: AGENTS.md Inheritance

**What is missing:**
- Line 682 requires IVP-004 `AGENTS.md Precedence`
- But the inheritance rule is not defined in the AEV
- Example: Does a developer at `buzzjuice.net/wp-content/mu-plugins/streams/AGENTS.md` inherit from `buzzjuice.net/AGENTS.md`?
- Or does `buzzjuice.net/wp-content/AGENTS.md` override both?

**Why this matters:**
Developers at different directory levels will see conflicting instructions if precedence is ambiguous.

**AEC Attack Surface:**
- Assume: "Root AGENTS.md is authoritative, subdirectory can override"
- Attack: "Multiple developers with different override rules create conflicting local instructions"
- Falsification: "Define a strict precedence algorithm and make it machine-readable"

### Challenge Target 4: Stop Condition Escalation

**What is missing:**
- Line 580: Task Packets have a `stop_condition` field
- Example stop conditions: "If repository unavailable" or "If agent disagreement"
- But the document does not define:
  - Who detects the stop condition?
  - Who escalates?
  - What is the SLA?
  - Is escalation synchronous or asynchronous?

**Why this matters:**
A developer might encounter a stop condition (e.g., repository locked) and not know whether to pause, resume, or escalate.

**AEC Attack Surface:**
- Assume: "Stop condition is detected by the assigned agent and escalated to human authority"
- Attack: "Agent never detects the condition; developer waits indefinitely"
- Falsification: "Require the developer to actively report stop conditions within an SLA"

### Challenge Target 5: Identifier Collision in GitHub Branches

**What is missing:**
- Line 636 example: `docs/aea/[artifact]`
- What if two different tasks generate the same artifact? Do they share a branch or create branch-name collisions?
- Identifier Registry is machine-readable but is there a GitHub branch validation check?

**Why this matters:**
Developers might accidentally push to the wrong branch if identifiers are ambiguous in branch names.

**AEC Attack Surface:**
- Assume: "Identifiers are unique and branch names reflect them"
- Attack: "Two different AEA artifacts both want to create `docs/aea/0000.01`"
- Falsification: "Require unique artifact IDs and automated branch-name validation"
