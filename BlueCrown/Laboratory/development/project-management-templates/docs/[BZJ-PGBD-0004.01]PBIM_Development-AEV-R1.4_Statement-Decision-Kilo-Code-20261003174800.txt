# TWO MINOR OBSERVATIONS (non-blocking; for the fresh AEC to probe)

These are **not** conditions (R1.4 §46: "Conditions that identify unresolved architectural
defects shall prevent advancement"). Neither is an *unresolved architectural defect* —
both are *correct by inference* and are appropriate *attack vectors* for the fresh AEC
(R1.4 §48). I list them here so the fresh duel probes them explicitly.

## OBS-1 — CA instantiation for the template vs a concrete project
R1.4 §4.2 frames CA registration as a *project* event ("At project registration, the
project shall identify: constitutional_authority..."). For a *concrete project*, CA is the
"project-owning organization" (§4.1) — clear. For the *reusable template/architecture
itself* (PBIM as a Koware/IAPD-PMO asset), the CA is the *owning organization* (implicit,
not explicitly registered). This is a minor clarity point, not a defect: the *boundary*
is established (§4.1 "outside the PBIM decision structure"); the *registration* of CA for
a concrete project is a project event. **Fresh-AEC attack:** "Is CA for the PBIM
*architecture itself* (vs a concrete project) explicitly identified and recorded, or is
it implicit?" Severity: minor. Correct by inference; appropriate for the fresh AEC.

## OBS-2 — CA unavailability is not explicitly stated
R1.4 §7 explicitly states the H0-unavailability rule ("an authorized delegate may act only
within documented scope; constitutional authority remains unchanged; emergency delegation
shall expire according to its defined boundary"). The *analogous* CA-unavailability rule
("if CA is unavailable, constitutional changes remain blocked") is **correct by inference**
— CA is the *terminal* constitutional authority (§4.3), so without CA, constitutional
changes *cannot* proceed. But it is not *explicitly stated* as it is for H0. This is a
minor explicitness point, not a defect. **Fresh-AEC attack:** "What happens when CA is
unavailable? Are constitutional changes blocked, or is there a CA delegate?" Severity:
minor. Correct by inference; appropriate for the fresh AEC. (Note: §4.2's `CA` schema has
no `ca_delegate` field, which *would* be a genuine gap if CA-delegation were intended —
but R1.4 does *not* intend CA-delegation, so the absence is *correct*, not a gap. The
fresh AEC should confirm this is intentional: CA is *not* delegable, unlike H0.)

Neither observation blocks an unconditional AEV APPROVE. Both are *expected* items for the
fresh AEC to attack, consistent with R1.4 §48 ("A fresh AEC shall attack PBIM R1.4
itself").
