# AEV DECISION

## AEV APPROVE WITH CONDITIONS — FOR A FRESH AEC DUEL

R1.3 is a strong, honest, architecturally-sound response to the AEC R1.2 duel. It resolves
all four of my blocking findings (BF-1..BF-4) **at the architectural level** and, critically,
it does **not** falsely claim that the required implementation mechanisms already exist —
which was the fatal defect of R1.0 and the defect my AEC identified as "documentation is not
enforcement." R1.3 explicitly separates architectural verification from implementation
verification (§4, §61, §68) and lists twelve mechanisms that "remain future implementation-
verification obligations" (§68). That separation is the single most important advance in the
whole R-series, and it is correct.

I therefore approve R1.3 **with five architectural conditions** (C-1..C-5) that close
residual *design* gaps so the fresh AEC duel (required by R1.3 §73) attacks a defined
architecture rather than a set of "may vary" placeholders. These are *architectural*
conditions, not *implementation* demands — consistent with R1.3's own principle that AEV
specifies enforceable controls without claiming they operate.

I do **not** give a clean "AEV APPROVE" because four residual *architectural* items remain
open (the external constitutional boundary, the minimum integrity-anchor property, the
authority-permission-matrix verification mechanism, and durable-ref pinning). I do **not**
give "AEV RETURN" or "AEV BLOCK" because R1.3 is internally coherent, does not introduce
new authority conflicts, resolves my blockers at the architectural level, and is the right
architecture to build.

Implementation: **NOT AUTHORIZED.** Production: **NOT AUTHORIZED.** AECC: **NOT AUTHORIZED**
(until the fresh AEC duel passes and R1.3 §74's eight conditions are met).

# CONDITIONAL APPROVAL — FIVE ARCHITECTURAL CONDITIONS

These are *architectural* conditions to close residual *design* gaps before the fresh AEC
duel. They are NOT implementation demands — consistent with R1.3 §4 (AEV specifies
enforceable controls without claiming they operate). I carry them so the fresh AEC duel
attacks a *defined* architecture, not a set of "may vary" placeholders.

## C-1 (MODERATE) — Pin the external constitutional boundary
§10's `appointment_authority` and §47's constitutional path ("AEA → AEV → AEC → AECC →
H0 authorization") do not explicitly establish an *external* (above-PBIIM) constitutional
authority. H0 is *within* PBIIM, so a constitutional change to PBIIM *itself* (e.g.,
amending "PBIIM cannot change its own constitution") still loops back to H0 — the
self-reference my Attack Y/Z identified. R1.3 *substantially* addresses this (§37's
"delegate does not become constitutional H0," §11's "constitutional changes remain
blocked" when H0 unavailable), but it does not *pin* the external boundary.
**Condition:** explicitly designate an *external* constitutional authority (the
organization, or a named external entity above PBIIM) that (a) appoints H0, and (b) is the
terminal authority for PBIIM constitutional changes — so §47's constitutional path
terminates at the external authority, not at H0. This makes the "who approves a change to
the entity that approves changes?" question (Attack Z) have a non-circular answer.
*Severity: moderate* — the mechanism is present (register + appointment_authority); the
*boundary* is not pinned. The fresh AEC should be able to confirm the external authority
is named and its scope is bounded.

## C-2 (MINOR) — Pin the minimum integrity-anchor property
§18 and §25 say the integrity anchor "may vary." That is a reasonable design choice
(principle over mechanism), but at the AEV level it leaves the *specific* tamper-evident
property undefined, which the fresh AEC cannot attack (Attack W/AG need a defined property
to test).
**Condition:** pin the *minimum* property the anchor must satisfy, e.g.: "the integrity
anchor must be (a) append-only, (b) out-of-band from the principal that produces the
evidence, and (c) verifiable by an independent verifier without trust in the producing
principal." The *specific store* (immutable commit / signed artifact / external audit
store) may still vary, but the *property* it must satisfy must be fixed. This lets the
fresh AEC test "is this anchor out-of-band and append-only?" rather than "did they pick a
good store?"
*Severity: minor* — the principle is fixed; the minimum property just needs pinning.

## C-3 (MINOR) — Pin the authority-permission-matrix verification mechanism
§14 says "every material project shall maintain" an Authority → Account → Capability →
Repository Permission → Deployment Permission matrix, and §15 defines AUTHORITY-
PERMISSION-DRIFT / AUTHORITY-CAPABILITY-GAP states. Good. But *where the matrix lives,
who verifies it, and how drift is detected* are not specified — so the fresh AEC
(Attack C/X) cannot attack a concrete verification mechanism.
**Condition:** specify (a) *where* the matrix lives (a governed artifact, e.g., a section
of the Human Authority Register or a dedicated authority-permission file), and (b) *what*
verifies it (tie it explicitly to the §15 drift states: "a periodic comparison of the
matrix against the actual repository permission system produces AUTHORITY-PERMISSION-DRIFT
on mismatch"). This makes the dual-control model *testable* rather than *asserted*.
*Severity: minor* — the model is sound; the verification hook just needs pinning.

## C-4 (MINOR) — Forbid authoritative links to ephemeral/deletable refs
[FACT E-5] the template's authoritative links are still pinned to ephemeral session
branches (`kilo/mute-summit-kd9`, `jules-1604558848482024...`) — 2 occurrences. R1.3 §60
addresses *baseline drift* but does not explicitly forbid pinning authoritative
registry/evidence/baseline links to *deletable, rewritable* session refs. My Attack AB
(session/artifact link failure) requires *durable* refs so governance history survives a
deleted branch or expired session.
**Condition:** add an explicit rule that authoritative links (registry revisions,
evidence anchors, baseline references, authority-register entries) must be to
*persistent* refs (immutable tags or commit SHAs), **not** to deletable session branches.
A session branch is a valid *working* ref but not a valid *authoritative* ref. This closes
the residual of my Attack AB and is consistent with §18's revision-ID/content-hash anchor
(which already implies durability, but the ref-pinning rule should be explicit).
*Severity: minor* — §18's hash-chain anchor already implies this; the explicit rule makes
it testable.

## C-5 (NOTE, not a condition) — Live defects correctly deferred to implementation
The live AGENTS.md still drifts [FACT E-2] and the template stubs are still empty [FACT
E-4]. R1.3 §61/§45/§68/§74 *correctly* treat these as implementation-verification /
template-completeness items, not as falsely-claimed fixes. I do **not** make these AEV
conditions (that would violate R1.3's correct §4 separation). I note them here so the
fresh AEC and the AECC gate (§74 condition 6: "the PBIIM operating template is complete";
§74 condition 7: "the human authority model is instantiated") explicitly track them to
closure. They are *expected* to be open at this stage; they must be *closed* before AECC
and before production.
