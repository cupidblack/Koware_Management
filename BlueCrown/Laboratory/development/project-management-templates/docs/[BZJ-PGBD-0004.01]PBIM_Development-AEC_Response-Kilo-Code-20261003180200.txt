# 1. EXECUTIVE VERDICT

## AEC PASS WITH AMENDMENTS

PBIM R1.4 **survives the adversarial attack at the architectural level.** No load-bearing
assumption (LA-01..LA-15) is **invalidated**. The architecture does **not** permit a
material governance bypass that *cannot* be contained by an existing control. The R1.4
amendments (CA external constitutional authority, 5-property integrity anchor, Authority–
Permission Matrix with location + verifier, durable artifact-reference rule, state models,
traceability, constitutional-protection list) **close the R1.2/R1.3 attack paths** at the
architectural level and **do not relocate** the vulnerabilities — they *raise the floor*.

However, the duel surfaced **five MATERIAL residual gaps** that require **architectural
amendment** (not implementation) before AECC can close:

- **F-1 (MATERIAL):** CA is a *root-of-trust with no architectural defense above it*. If CA
  is compromised, the entire constitutional chain collapses; R1.4 has no defense and
  *correctly* does *not* invent one (per duel §AB's instruction), but it must *acknowledge*
  this as a trust boundary and require *CA-level (organizational)* mitigation.
- **F-2 (MATERIAL):** The 5-property integrity anchor defines the *minimum property* but
  not the *detection of its violation*. An anchor that satisfies all 5 properties
  *architecturally* but is stored in a compromised repository defeats property 2 (out-of-
  band); the architecture specifies the property but not the *mechanism to detect that the
  property is being violated*. This is the "documentation is not enforcement" pattern, now
  at the *property* level.
- **F-3 (MATERIAL):** Challenge independence (I1–I4) is *required* but not *detectable*.
  R1.4 says independence "must be genuine" but does not define a *mechanism to detect
  false independence* (shared credentials, shared ownership, shared evidence generation,
  shared compromised context). The requirement is real; the *detection* is absent.
- **F-4 (MATERIAL):** The Authority–Permission Matrix (§9) is version-controlled, but
  *which revision is authoritative* under concurrent modification or conflicting versions
  is not fully specified. The registry has REQUEST→RESERVE→VALIDATE→COMMIT→CONFIRM
  serialization; the matrix has no equivalent, so two concurrent matrix changes can
  produce a stale-authoritative state.
- **F-5 (MATERIAL):** Requirement materiality (§24) handles *individual* change
  classification but not *cumulative* materiality: a *sequence* of Level-0 changes that
  *collectively* constitute a Level-2 architectural change is not required to trigger
  Level-2 review. "A change shall not be classified merely by convenience" addresses a
  single change, not a *convergent series*.

None of these is a *load-bearing-assumption invalidation*; each is a *material weakness*
recoverable through a *defined architectural amendment*. R1.4 §47 allows "AEC PASS WITH
AMENDMENTS" for exactly this: "No fundamental invalidation, but material amendments are
required before closure." Therefore the verdict is **AEC PASS WITH AMENDMENTS** (F-1..F-5).

**Implementation: NOT AUTHORIZED. Production: NOT AUTHORIZED. AECC: NOT YET AUTHORIZED**
(only after F-1..F-5 are amended and the fresh-duel findings are dispositioned).

# 4. FINDINGS (per duel §46 format)

## F-1 — CA Root-of-Trust with No Architectural Defense Above It [MATERIAL]
**Attack:** Domain AB (CA Compromise). The Constitutional Authority is compromised.
**Preconditions:** CA is compromised (the organization that appoints/verifies CA is
compromised, or CA is a single point of trust with no above-CA check).
**Exploit path:** A compromised CA can (a) redefine PBIM's constitution (§4.3:
constitutional changes → CA; a compromised CA approves any constitutional change), (b)
remove H0/AEV/AEC (§42's unilateral-removal prohibition applies to "project participant,
agent, task packet, repository administrator or automation process" — CA is *not* in the
list), (c) weaken protected controls (§42: a compromised CA can redefine them via the
constitutional change process), (d) approve its own self-amendment (§4.4 binds PBIM, not CA
— CA is the external authority).
**Expected control:** None above CA — R1.4 §4 makes CA the external root; there is no
authority above CA.
**Actual result:** The architecture fails to defend against a compromised CA. The
constitutional chain collapses: a compromised CA can rewrite the constitution, remove the
gates, weaken the invariants. R1.4 has no architectural defense and correctly does not
invent one (duel §AB: "Do not invent an additional authority merely to make the
architecture appear complete").
**Evidence:** [FACT] R1.4 §4.1 ("The authority... shall exist **outside the PBIM decision
structure**"), §4.3, §4.4, §42 (prohibition list does not include CA). [INFER] A
compromised CA is not a "project participant" — it is the external authority; §42 does not
apply to CA.
**Severity:** MATERIAL (architectural limitation, not a defect — but R1.4 must acknowledge
it).
**Architectural impact:** authority (the root of trust is compromisable); governance
integrity (the constitutional chain collapses on CA compromise).
**Resolution requirement:** R1.4 must explicitly acknowledge: (a) CA is the root-of-trust
of PBIM; (b) a compromised CA collapses the constitutional chain (no architectural defense
above CA, by design); (c) the mitigation is CA-level (organizational), not PBIM-level
(independent CA appointment, CA verification, CA rotation, CA quorum — above PBIM). Without
this acknowledgment, R1.4 implies CA is invulnerable, which is false.

## F-2 — Integrity Anchor: Properties Defined but Violation Undetectable [MATERIAL]
**Attack:** Domain G. Construct an anchor that satisfies the 5 properties' wording while
providing little practical integrity.
**Preconditions:** The anchor is stored in the same compromised repository as the state it
anchors (defeating property 2, out-of-band); or the anchor's verifier is compromised
(defeating property 3, independent verifiability).
**Exploit path:** An attacker with write access to the repository (a compromised repo-admin,
Domain U) can tamper with the governed state and the anchor simultaneously (same repo). The
anchor still satisfies the 5 properties' wording (append-only [1], "out-of-band" in the
sense of a separate file [2, weakened], verifiable [3], durable [4], revision-associated
[5]) — but is not genuinely out-of-band. R1.4 has no mechanism to detect that property 2
is violated. Property 3's "independent verifiability" requires the verifier to be
independent, but the verifier-of-the-verifier recursion is not pinned (it loops to CA, F-1).
**Expected control:** §11 (5 properties; "The architectural minimum is fixed even where
implementation technology is not").
**Actual result:** The properties are well-chosen, but detection of violation is absent.
Property 2 is load-bearing: if the anchor is in the compromised repo, it is useless. R1.4
specifies the property but not the mechanism to detect its violation.
**Evidence:** [FACT] R1.4 §11 (5 properties; "architectural minimum is fixed"). [INFER] §11
does not specify a detection mechanism for property 2/3 violation. [FACT] A compromised
repo-admin has write access to the repository (where the anchor is stored, per §11's
"append-only log / external audit store" examples — if the store is in the repo, the admin
can access it).
**Severity:** MATERIAL.
**Architectural impact:** evidence (the integrity anchor is the foundation of E3/E4; if
undetectable-when-compromised, E3/E4 is unsound); assurance (the assurance chain §35
relies on the anchor being genuine).
**Resolution requirement:** R1.4 must specify: (a) the anchor must be verifiable by a
principal that does NOT have write access to the governed-state repository (out-of-band
enforced, not just stated); (b) the anchor's storage location must be independently
attestable (a separate principal confirms the location is not in the compromised repo);
(c) the verifier-of-the-verifier recursion must be broken at CA (CA verifies the
verifier's independence, as the root of trust). This loops to F-1.

## F-3 — Challenge Independence: Required but Not Detectable [MATERIAL]
**Attack:** Domain I/J. A challenger that appears independent while sharing ownership/
credentials/evidence generation/repo admin/decision authority/the same compromised context.
**Preconditions:** The challenger shares organizational control with the design owner (same
agent context, same repository, same lineage — exactly my disclosed situation, §2).
**Exploit path:** The challenger passes the I1–I4 requirement on paper (distinct principal,
distinct role, no conflicting ownership, independent evidence path, challenge appointment
authority, recorded COI — R1.4 §21/§22) but is actually compromised. R1.4 has no mechanism
to detect this false independence: it requires independence but does not verify that it is
genuine. "The challenge record must preserve the limitation" (duel §4) is a recording
requirement, not a detection mechanism.
**Expected control:** §14 (I1–I4; "An agent thinking independently is not automatically an
organizationally independent challenger"; CHALLENGE-BLOCKED), §37.
**Actual result:** The requirement is real, but detection of false independence is absent.
My own disclosed limitation (§2) is a live instance: I appear to be challenging R1.4 but
share the context/repo/lineage with the design — exactly the "false independence" R1.4 §14
warns about. R1.4 has no mechanism that would have detected my false independence except
my voluntary disclosure.
**Evidence:** [FACT] R1.4 §14, §37. [INFER] §14/§37 do not specify a detection mechanism
for false independence. [FACT] My own disclosure (§2) demonstrates the gap: I share the
context/repo/lineage and R1.4 has no mechanism that would have detected that except my
voluntary disclosure.
**Severity:** MATERIAL.
**Architectural impact:** assurance (the AEC gate is the assurance mechanism; if
independence is undetectable-when-false, the AEC gate is unsound); governance integrity
(the challenge record preserves the limitation but does not detect that it is material).
**Resolution requirement:** R1.4 must specify: (a) the challenger's organizational
independence must be attested by a principal OTHER than the challenger; (b) the evidence
path must be verifiably independent (the challenger's evidence is not derived from the
design owner's evidence — checkable by comparing provenance, §12); (c) the challenger's
repository access must be verifiably not broader than read-only on the target (I3,
enforced by the Authority-Permission Matrix §9, not just stated). Loops to F-4 and F-1.

## F-4 — Authority–Permission Matrix: No Authoritative Revision Under Concurrency [MATERIAL]
**Attack:** Domain E/AC. Two concurrent matrix changes (H1 grants a permission while the
verifier is checking); or two conflicting matrix versions.
**Preconditions:** The matrix is version-controlled (§9.1) but has no serialization
mechanism (unlike the registry, §10, which has REQUEST→RESERVE→VALIDATE→COMMIT→CONFIRM).
**Exploit path:** Two concurrent matrix changes can produce a stale-authoritative state:
the verifier checks the pre-grant matrix, approves agent X based on the old permissions,
but agent X now has the new (broader) permissions → permission grant before verification
(Domain E.8). Or two conflicting matrix versions (H1 grants X, H1' revokes X,
simultaneously) → which revision is authoritative? R1.4 §9.1 says the matrix is
"version-controlled and associated with the applicable project identifier and revision,"
but does not specify which revision is authoritative under concurrency. The registry does
(§10: "only one authoritative registry transaction may establish a particular identifier;
concurrent requests must be serialized"); the matrix has no equivalent.
**Expected control:** §9.1, §9.3, §9.4.
**Actual result:** The location and verifier are pinned (resolving my C-3), but which
revision is authoritative under concurrency is NOT specified. The registry has
serialization (§10); the matrix does not.
**Evidence:** [FACT] R1.4 §9.1 (no serialization specified). [FACT] R1.4 §10 (registry:
"Concurrent requests must be serialized" — the matrix has no such rule). [INFER] Two
concurrent matrix changes → no serialization → stale-authoritative or last-writer-wins →
permission grant before verification is possible.
**Severity:** MATERIAL.
**Architectural impact:** authority (the matrix is the authority mapping; a stale-
authoritative matrix means wrong permissions are enforced); security (a compromised or
stale matrix can grant broader permissions than authorized).
**Resolution requirement:** R1.4 must extend the registry's serialization pattern to the
matrix: (a) matrix changes must be serialized; (b) a matrix revision is authoritative only
when it passes the verifier (§9.3) — the verifier's approval is part of the COMMIT; (c)
concurrent matrix changes must queue; (d) the verifier-of-the-verifier recursion must be
broken at CA. Loops to F-1 and F-3.

## F-5 — Requirement Materiality: Cumulative/Convergent Changes Not Addressed [MATERIAL]
**Attack:** Domain P/O. A sequence of Level-0 changes that collectively constitute a
Level-2 architectural change; or a high-risk change split into multiple apparently minor
tasks.
**Preconditions:** The actor classifies each change individually (each is "Level 0" or
"LIGHT") but the series collectively changes the architecture (Level 2) or accumulates to
high risk.
**Exploit path:** An actor makes change 1 (Level 0: "add a log line"), change 2 (Level 0:
"refactor a function"), change 3 (Level 0: "add a config option"), change 4 (Level 0:
"update a dependency"). Each individually is "Level 0" and passes task-level handling
(§24). But collectively the series changes the architecture. R1.4 §24 says "A change shall
not be classified merely by convenience" and "Where materiality is uncertain, escalation to
the higher level is required" — but this addresses a single change, not a series. There is
no rule that a convergent series of Level-0 changes that collectively constitute a Level-2
change triggers Level-2 review.
**Expected control:** §24.
**Actual result:** Individual classification is sound, but cumulative materiality is the
gap. An actor could incrementally erode the architecture through many "Level 0" changes
that each individually pass but collectively change the architecture.
**Evidence:** [FACT] R1.4 §24 ("A change shall not be classified merely by convenience" —
singular "change"). [INFER] §24 does not address a series of changes (cumulative
materiality).
**Severity:** MATERIAL.
**Architectural impact:** assurance (the requirement-materiality gate is the assurance
mechanism for requirement changes; if cumulative changes bypass it, the architecture can be
eroded incrementally); governance integrity (the baseline is eroded by many small "approved"
changes that collectively change it).
**Resolution requirement:** R1.4 must add a cumulative-materiality rule: (a) a window of
changes (all changes since the last baseline review) must be assessed collectively for
materiality, not just individually; (b) if the collective effect of a window constitutes a
higher level than the individual levels, the window triggers that higher level's review;
(c) splitting a high-risk change into multiple low-risk tasks must be detectable (tasks
linked to a requirement; if multiple tasks serve the same high-risk requirement, the tasks
are assessed at the requirement's risk level). Loops to Domain O (cumulative risk).

## F-6 — Operational-Readiness: Per-Criterion Minimum Evidence Not Defined [MINOR]
**Attack:** Domain R. What evidence is sufficient to establish each operational-readiness
criterion?
**Preconditions:** R1.4 §25 lists 15 criteria but does not define the minimum evidence for
each.
**Exploit path:** An implementer claims "rollback is ready" and provides a rollback
runbook (documentation, E1) instead of a tested rollback (E3/E4). §12 + §13 say
documentation alone is not E3/E4, but §25 does not say "rollback evidence must be a tested
rollback."
**Expected control:** §25, §12/§13.
**Actual result:** The principle (evidence must be E3/E4) is clear; the per-criterion
minimum is not. This is a MINOR clarity gap; the specific minimum per criterion is an
implementation-verification detail.
**Severity:** MINOR.
**Resolution requirement:** R1.4 should add a table of per-criterion minimum evidence
