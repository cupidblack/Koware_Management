R1.2 is the architectural amendment to AEV R1.1 following the collaborating-agent re-verification.

The R1.1 review confirmed substantial architectural improvement but identified unresolved control-definition gaps.

GitHub/Copilot identified eight remaining blockers:

4. `AGENTS.md` conflict enforcement;

R1.2 does not falsely claim that implementation machinery already exists.

---

# 2. Verification Principle

The architecture now distinguishes three states:

### DESIGNED

The architecture defines the control.

### ENFORCEABLE

The architecture defines a concrete mechanism by which unauthorized action can be prevented or detected.

### ENFORCED

Implementation evidence demonstrates that the mechanism exists, is active, and operates as specified.

Therefore:

**Architectural specification does not equal implementation evidence.**

An AEV document may verify that an enforcement mechanism is architecturally complete without claiming that the mechanism has already been implemented.

Implementation verification remains a separate gate.

---

# 3. Governance → Assurance → Execution

The fundamental architecture remains:

**Governance → Assurance → Execution**

### Governance

Defines:

* authority;
* policy;
* state;
* identity;
* approval;
* escalation;
* exceptions.

### Assurance

Defines and independently evaluates:

* analysis;
* verification;
* challenge;
* evidence;
* traceability;
* control effectiveness.

### Execution

Performs:

* implementation;
* testing;
* deployment;
* operations.

Execution cannot create its own authority.

---

# 4. Assurance Lifecycle

The controlled lifecycle remains:

**AEA → AEV → AEC → AECC**

with the following interpretation:

### AEA

Determines what architecture is being proposed and identifies assumptions.

### AEV

Determines whether the proposed architecture is internally coherent, sufficiently specified and verifiable.

### AEC

Attempts to invalidate it.

### AECC

Determines whether the challenge findings have been resolved, contained or formally accepted.

No stage may silently perform the authority of another stage.

# 5. Canonical Registry Governance

## 5.1 Canonical Location

The canonical project identifier registry shall reside in the **Governance Repository**.

For the current concrete project:

```text
Koware_Management/
└── BlueCrown/
    └── Laboratory/
        └── development/
            └── payment-gateway/
                └── governance/
                    └── registry/
                        └── BZJ-PGBD-Identifier-Registry.yaml
```

The exact production path may be adjusted by the project charter, but once approved it becomes canonical.

A project-specific registry location must never be inferred from a local agent workspace.

---

# 6. Registry Authority

The registry has:

### Read Authority

All participating agents may read the registry.

### Write Authority

Only the designated **Registry Authority** may approve registry changes.

### Validation Authority

Automated validation verifies schema, uniqueness, sequence and referential integrity.

### Governance Authority

H0 authorizes changes that alter identifier semantics or registry governance.

Registry authority does not equal project authority.

---

# 7. Registry Branch Control

The canonical registry shall be maintained on the protected governance branch.

Normal changes follow:

**proposal → validation → review → approval → merge**

Direct modification of the protected canonical registry is prohibited except through a formally declared emergency procedure.

A local copy is never authoritative.

---

# 8. Registry Schema

Every registry entry shall distinguish at minimum:

```yaml
project_id:
process_id:
work_id:
task_id:
artifact_id:
revision_id:
lifecycle_state:
sequence_index:
status:
created_at:
created_by:
```

The schema must reject:

* duplicate identifiers;
* duplicate sequence indexes where uniqueness is required;
* invalid identifier grammar;
* missing mandatory fields;
* illegal lifecycle states;
* invalid state transitions.

---

# 9. Registry Conflict Resolution

If two branches propose conflicting registry changes:

1. neither branch becomes authoritative;
2. the conflict is recorded;
3. affected identifier creation is blocked;
4. Registry Authority reviews the conflict;
5. H0 resolves governance-level semantic conflicts;
6. the corrected registry is revalidated;
7. only the canonical branch may establish the resulting identifier.

A stale local registry can never win through recency.

---

# 10. Registry Failure State

If the canonical registry:

* cannot be read;
* fails validation;
* contains contradictory state;
* becomes unavailable;
* or loses integrity;

the affected identifier-dependent operation enters:

`REGISTRY-BLOCKED`

No substitute local registry may silently assume authority.

# 11. Challenge Independence Model

R1.2 replaces the previous generic requirement for "an independent challenger" with a concrete selection model.

## 11.1 Primary Model — Independent Challenge Agent

AEC shall normally be performed by an agent/person that did not:

* author the challenged architecture;
* own the architecture;
* perform the relevant implementation;
* or approve the challenged design.

## 11.2 Secondary Model — Rotating Challenge Agent

Where multiple qualified agents exist, the challenger shall rotate between projects or major architectural cycles.

The design owner may not select itself as challenger.

## 11.3 Tertiary Model — Human Challenge Authority

Where no independent agent exists, the project enters:

`CHALLENGE-BLOCKED`

and escalates to H0/H1 for appointment of an independent challenger.

The absence of an independent challenger cannot be converted into AEC PASS.

# 15. AGENTS.md Precedence — Corrected

The R1.1 hierarchy contained a conflict between:

* the approved-baseline precedence rule;
* and the statement that existing `AGENTS.md` security/payment rules remain in force.

R1.2 resolves this explicitly.

## 15.1 Constitutional Security Rule

Security, credential, secret-handling and safety controls that are designated **Protected Controls** cannot be weakened by a lower-level document.

The precedence model is therefore:

**Human Governance Authority**
↓
**Protected Security/Safety Controls**
↓
**Approved Architectural Baseline**
↓
**Project Charter**
↓
**Repository AGENTS.md**
↓
**Subsystem AGENTS.md**
↓
**Task Instructions**
↓
**Runtime Defaults**

A lower level may strengthen a protected control.

It may not weaken it.

* a protected security control;

1. identify the conflict;

# 18. Architectural Reset Authority

Architectural Reset is a formal governance action.

## 18.1 Reset Initiators

A reset may be initiated by:

* H0;
* H1 where a verified load-bearing failure exists;
* AEC where an architectural invalidation is established;
* automated controls where a mandatory safety condition has been violated, limited to stopping the affected execution.

Automation may halt.

Automation cannot unilaterally redesign the architecture.

---

# 19. Reset Evidence Threshold

A reset must identify:

* failed assumption;
* evidence;
* affected architecture;
* affected tasks;
* affected implementation;
* affected verification;
* operational consequence.

For a load-bearing assumption, evidence must demonstrate that the approved architecture can no longer satisfy the condition on which approval depended.

---

# 20. Reset Effects

Upon reset:

1. affected execution stops;
2. affected approval states are invalidated;
3. affected Task Packets are suspended;
4. evidence is preserved;
5. affected artifacts are marked;
6. the project returns to AEA or AEV as appropriate;
7. a replacement architecture is produced;
8. verification restarts;
9. implementation resumes only after reauthorization.

Previous approval cannot automatically survive architectural invalidation.

---

# 21. Reset Appeal

A reset may be challenged only by escalation to a higher governance authority.

The design owner cannot reverse an independent reset finding unilaterally.

The appeal must produce a recorded governance decision.

---

# 23. Task Scope Enforcement

Implementation changes shall be compared against the Task Packet.

At minimum the enforcement mechanism must detect:

* unauthorized files;
* unauthorized paths;
* unauthorized operations;
* unauthorized branch;
* missing prerequisite state;
* expired packet;
* superseded packet.

A violation creates:

`TASK-SCOPE-VIOLATION`

The affected work cannot be marked VERIFIED.

---

# 24. Task Packet Override

A Task Packet cannot be expanded informally.

Additional work requires:

**new packet** or **controlled superseding packet**.

Emergency expansion requires:

* emergency authority;
* explicit scope;
* evidence;
* post-event review.

Editing a dispatched packet to conceal an unauthorized change is prohibited.

---

# 25. Stop/Resume Control Model

The project state machine shall distinguish:

`RUNNING`

from:

`STOPPED`

and:

`BLOCKED`.

## STOPPED

Execution is intentionally halted by authorized control.

## BLOCKED

A required condition prevents advancement.

Neither state permits ordinary execution.

---

# 26. Stop Trigger

A stop may be triggered by:

* unresolved blocker;
* security violation;
* authority conflict;
* registry failure;
* Task Packet violation;
* architecture invalidation;
* evidence-integrity failure;
* governance drift;
* failed mandatory dependency.

---

# 27. Stop Enforcement

When a mandatory stop is active:

* affected Task Packets become non-executable;
* new affected Task Packets cannot be dispatched;
* implementation verification cannot complete;
* release authorization cannot proceed.

Automation may enforce the mechanical portion of the stop.

---

# 28. Resume Authority

Only the authority designated for the stop class may resume work.

Resume requires:

```yaml

resolution:
evidence:
reviewer:
resume_authority:
timestamp:
```

A stopped task cannot resume merely because the implementing agent believes the problem is fixed.

# 33. Enforcement Evidence Model

For each architectural control, implementation verification shall classify evidence as:

### E0 — Specification

Control exists only in architecture.

### E1 — Configuration

Required configuration exists.

### E2 — Automated Enforcement

A mechanism automatically prevents or detects violation.

### E3 — Operational Evidence

The mechanism has successfully operated under test or real conditions.

### E4 — Independent Verification

An independent verifier confirms the mechanism operates as required.

This provides a direct bridge between AEV and future implementation verification.
