The correct approach is to make `millennium-timezone.php` the central source for date and timezone calculations, expose reusable PHP functions for the other Palmier scripts, use the existing IAPD and Palmier database connections for shared state, and retain calculation history in log files rather than database tables.

I have reviewed the previous ChatGPT response and the GitHub response you supplied. GitHub's recommendations are useful, but some implementation details need correcting before deployment. In particular, including a PHP file is not the same as executing its HTTP endpoint, and a same-domain HTTP request should not be retained when an equivalent local PHP function can return the same data.

### Cache behaviour

1. Read the last successful result and its timestamp.
2. If it is less than 12,345 seconds old, return the cached result.
3. If it is older, refresh the required calculation and probe data.
4. Record the new result and timestamp only after a successful refresh.
5. If refreshing fails, retain the last valid result and report that it is stale rather than replacing it with an error or fabricated value.
6. Write historical records to protected log files, using file locking to prevent concurrent requests from corrupting them.

The threshold is a cache-refresh policy, not a guarantee that a cached timestamp is the exact current second. The `current` field must be clearly distinguished from the time at which the cached result was generated.

## 2. Critical Corrections to the GitHub Recommendations

The GitHub response contains useful architectural recommendations, but I would not deploy its proposed code without correcting the following issues.

### 2.1 The database table prefix must be handled consistently

The required naming convention is:

`koware_iapd.millennium_timezone_...`

The proposed helper in the GitHub response uses the database name and constructs a table name dynamically. That is a reasonable approach, provided the database identifier comes from trusted configuration and the table suffix is validated. 

I recommend centralizing this in `db_helpers.php`, rather than duplicating database-name and table-name logic across the Millennium Timezone files.

The existing `get_iapd_db_conn()` and `get_palmier_db_conn()` functions should remain the authoritative connection mechanisms.

Before adding new helpers, verify that both functions are already present in the complete deployed version of `db_helpers.php`. The publicly retrieved portion confirms the Palmier environment configuration, but does not establish the complete implementation of both requested connection functions. 

### 2.2 The proposed probe integration contains a filesystem-path error

The GitHub proposal attempts to locate the probe using:

```php
$file = dirname(__DIR__) . '/shared/millennium-timezone/millennium-probe.php';
```

When the calling file resides in `shared/millennium-timezone/`, this constructs an incorrect path because `dirname(__DIR__)` already resolves to the parent `shared` directory.

The proposed code also attempts to pass a query string to a filesystem path:

```php
file_get_contents($file . '?probe=now');
```

A local filesystem path does not execute PHP or interpret `?probe=now` as a request parameter.

**The correct solution is to expose a reusable function from the probe engine and invoke it directly.**

For example, the intended integration should look conceptually like this:

```php
require_once __DIR__ . '/millennium-probe.php';

$probe = millennium_probe_now();
```

This is an integration pattern, not a complete replacement for the probe engine. The function must be implemented so that including the file does not inadvertently render its HTML interface or terminate the calling script.

### 2.3 The historical date must not be confused with the current date

This is the most important calculation issue.

The proposed GitHub helper returns:

```php
$iso = $json['current'];

return new DateTime($iso, new DateTimeZone('UTC'));
```

However, `current` represents the actual current timestamp in the proposed data model.

It is not necessarily the historical date that the gold calculator needs.

The existing gold calculator obtains a historical date and uses that date to select a gold-price anchor from its CSV data. Returning the current timestamp instead could select the wrong historical gold price. 

The new JSON contract should distinguish at least these values:

| Field              | Meaning                                                                     |
| ------------------ | --------------------------------------------------------------------------- |
| `current`          | Actual current timestamp in UTC                                             |
| `historical_iso`   | Exact historical date and time calculated by the Millennium Timezone engine |
| `reference_year`   | Year associated with the historical reference date                          |
| `local`            | Calculated historical local time                                            |
| `probe`            | Date and time represented by the Millennium Probe                           |
| `probe_value_days` | Numerical probe displacement, in days                                       |

The gold calculator must use `historical_iso` when resolving its historical gold-price anchor.

The value must be derived from the existing historical calculation—not from the current timestamp or an approximation based solely on `reference_year`.

### 2.4 Do not create database tables on every request

The GitHub response proposes a function that creates the snapshot table when invoked.

Although `CREATE TABLE IF NOT EXISTS` can be useful during initial setup, schema management should not run on every public page request.

Instead:

1. Create the required tables once through a controlled migration.
2. Use the existing database helpers to access them.
3. Read cached state where appropriate.
4. Update state only when necessary.
5. Keep historical calculation logs in files.

This separates deployment responsibilities from runtime responsibilities.

### 2.5 File logging needs a defined retention policy

The existing oscillator uses a 12,345-second interval, while the probe also defines a 12,345-second cache lifetime. 

The new timezone engine can use the same interval to decide when a refresh is due.

However, simply appending to a log forever would eventually create a storage problem.

The implementation should therefore distinguish:

* **Current cached state:** the latest valid calculation.
* **Historical log:** previous calculations retained for auditing.
* **Error log:** failed refreshes and calculation errors.

The current state can be read efficiently without scanning a large historical log. Historical records can be rotated by month or another defined retention policy.

## 3. Database Design

I recommend using the IAPD database for shared Millennium Timezone state and the Palmier database only for Palmier-specific state that genuinely needs persistence.

The database should not become a repository for every calculation performed.

### IAPD database

The following table names follow your required prefix convention.

| Table                             | Purpose                                    |
| --------------------------------- | ------------------------------------------ |
| `millennium_timezone_state`       | Current valid timezone calculation         |
| `millennium_timezone_probe_state` | Latest valid probe calculation             |
| `millennium_timezone_metadata`    | Optional engine version and cache metadata |

Their fully qualified names would be:

```text
koware_iapd.millennium_timezone_state
koware_iapd.millennium_timezone_probe_state
koware_iapd.millennium_timezone_metadata
```

Historical calculations should remain in the log files.

### Important distinction

A database cache and a log file solve different problems.

The database cache makes it possible for multiple PHP files to retrieve the same calculated state without repeating the computation.

The log file preserves the historical record.

For this project, I would use both only where justified: a small database-backed state cache for cross-component retrieval and append-only file logs for historical calculations.

If database persistence proves unnecessary for a particular value, a file-backed cache is also reasonable. The objective is to avoid duplicated work, not to introduce tables merely because they are available.

## 4. The 12,345-Second Refresh Mechanism

The intended behaviour is:

1. Read the most recent valid cached timezone result.
2. Determine its age.
3. If it is younger than 12,345 seconds, reuse it.
4. If it is older, calculate a fresh result.
5. Record the successful refresh in the log.
6. Update the shared cached state.
7. Return the same result to every consumer.

The refresh threshold is approximately **3 hours, 25 minutes, and 45 seconds**.

There is an important implementation detail: the log must not be the sole source of truth for determining whether a calculation succeeded.

If a refresh fails, the system should preserve the last valid result rather than replace it with incomplete or invalid data.

The system should also use a lock or another concurrency-control mechanism to prevent multiple simultaneous requests from performing the same expensive refresh.

This is particularly important when several visitors, automated agents, or scheduled tasks request the timezone simultaneously.

### AI-readable output

The public page should support both:

* An HTML view for people.
* A JSON view for applications and AI agents.

The response should explicitly identify the fields and their meanings, with timestamps expressed in UTC using ISO 8601 formatting.

The HTML page should visibly display:

* Day
* Date
* Month
* Jubilee
* Reference Year
* Local
* Current
* Probe

The JSON response should additionally include the exact historical timestamp, probe displacement, calculation timestamp, and cache status.

That provides a stable contract for future agents and applications without requiring them to interpret the page's visual layout.

**New timezone endpoint**

The new endpoint is designed to serve structured data at:

`https://buzzjuice.net/shared/millennium-timezone/millennium-timezone.php?endpoint=full`

It exposes the requested fields:

* `day`
* `date`
* `month`
* `jubilee`
* `reference_year`
* `local`
* `current`
* `probe`

The `probe` field remains `null` until the existing probe engine is integrated. The endpoint does not fabricate a probe value or make an unnecessary HTTP request to its own domain.

**Database integration**

The package includes a database adapter designed to reuse `get_iapd_db_conn()` and the requested `millennium_timezone_` table prefix.

The database writes are optional; the public endpoint does not automatically create a new database record on every request.

**Historical logging**

The design retains file-based logging for calculation histories rather than introducing a database logging table.

### 3. What remains before production deployment?

The following work is still required:

1. Integrate the existing Millennium Probe calculations and oscillator dependency into the new directory.
2. Update `gold_calc.php` and `gold_calc_helpers.php` to retrieve the historical reference date through local PHP functions rather than HTTP requests.
3. Review `palmier_calc.php` and eliminate unnecessary same-domain requests without disrupting external currency-data providers.
4. Verify that the CSV-processing scripts continue to operate correctly.
5. Review `db_helpers.php` for compatibility with the database adapter and existing consumers.
6. Run regression tests comparing the old and new calculations before retiring the old endpoints.

The existing `palmier_logger.php` should retain its application-activity logging responsibilities unless you explicitly decide to change them. Calculation-history logging and user-activity tracking are separate concerns.
