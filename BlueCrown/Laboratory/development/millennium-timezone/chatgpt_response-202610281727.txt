## 3.2 Establish a stable JSON contract

The new endpoint should support:

```text
https://buzzjuice.net/shared/millennium-timezone/millennium-timezone.php?output=json
```

The response should be machine-readable and predictable.

Recommended contract:

```json
{
  "success": true,
  "timezone": "UTC",
  "day": "Sunday",
  "date": "28th",
  "month": "October",
  "jubilee": "REFERENCE_VALUE",
  "reference_year": 2026,
  "local": "00:00:00",
  "current": "2026-10-28T00:00:00Z",
  "historical": "HISTORICAL_ISO_TIMESTAMP",
  "probe": "PROBE_ISO_TIMESTAMP",
  "generated_at": "2026-10-28T00:00:00Z"
}
```

**This is the proposed response structure, not a representation of a verified live calculation.** The example timestamps and placeholder-like values above are illustrative; the implementation must generate actual values and must never return those illustrative strings as calculation results.

The contract should be implemented with these rules:

1. `day` contains the exact day name.
2. `date` contains the formatted day of the month.
3. `month` contains the full month name.
4. `jubilee` contains the value calculated by the existing Jubilee formula.
5. `reference_year` contains the actual calculated reference year.
6. `local` contains the correctly defined local time value.
7. `current` contains the actual current UTC timestamp.
8. `historical` contains the historical timestamp calculated by the existing engine.
9. `probe` contains the current Millennium Probe result.
10. `generated_at` records when the snapshot was generated.

The JSON response should use a consistent schema and appropriate HTTP status codes.

### Backward compatibility

The current engine already supports endpoint parameters such as:

```text
?endpoint=historical
?endpoint=current
?endpoint=probe
```

These should remain supported during the migration.

For example, the historical endpoint should continue to return:

```json
{
  "iso": "ACTUAL_HISTORICAL_TIMESTAMP"
}
```

The actual timestamp must be calculated at runtime.

Keeping the old response shapes temporarily reduces the risk of breaking dependent scripts while they are migrated to the new internal architecture. 

## 3.3 Database integration

The timezone engine should:

1. Calculate its snapshot.
2. Serialize the snapshot as JSON.
3. Save the latest snapshot in the designated `koware_iapd` table.
4. Write the historical calculation record to the appropriate log file.
5. Return the snapshot to the caller.

When another script needs the current snapshot, it should read the database rather than request the same-domain PHP endpoint.

The implementation must also define what happens when the database is unavailable. A database failure must not silently produce a plausible but incorrect timestamp.

# Phase 1 — Prepare the database architecture

## Step 1. Establish the database naming convention

You specified these two database table prefixes:

* `koware_iapd.millennium timezone_`
* `koware_iapd.palmier_`

There is one naming detail worth resolving before creating tables.

I recommend interpreting the first prefix as:

```text
millennium_timezone_
```

The space in `millennium timezone_` is undesirable in MySQL table names. Although MySQL can support identifiers containing spaces when appropriately quoted, using underscores will make your PHP code, SQL queries and future integrations considerably easier to maintain.

The resulting table names would be:

```text
koware_iapd.millennium_timezone_cache
koware_iapd.millennium_timezone_logs

koware_iapd.palmier_cache
koware_iapd.palmier_logs
```

These are proposed names, not existing tables that I have verified in your database.

## Step 2. Decide what belongs in each table

I recommend using two complementary storage mechanisms:

1. **Cache tables:** Store the latest calculated values that other PHP files need to retrieve.
2. **Log tables:** Preserve historical calculation records for auditing, troubleshooting and later analysis.

This avoids treating a historical record as though it were necessarily the latest value.

### A. Millennium Timezone cache

`millennium_timezone_cache` should store the latest shared Millennium Timezone data.

For example:

| cache_key           | Purpose                                   |
| ------------------- | ----------------------------------------- |
| `current_time`      | Current UTC timestamp                     |
| `historical_time`   | Calculated historical timestamp           |
| `timezone_snapshot` | Complete current and historical time data |
| `probe_snapshot`    | Latest Millennium Probe result            |

Each record should contain a JSON payload and a timestamp indicating when the data was generated.

### B. Millennium Timezone logs

`millennium_timezone_logs` should preserve historical snapshots where those records are useful.

For example:

* Historical-time calculations.
* Probe calculations.
* Calculation timestamps.
* Phase and year information.
* Calculation inputs needed to reproduce a result.

Do not automatically record every second indefinitely. The existing browser interface updates frequently, but a database log should use a deliberate retention policy.

### C. Palmier cache

`palmier_cache` should hold the latest reusable currency calculations.

Suggested keys include:

| cache_key          | Purpose                                    |
| ------------------ | ------------------------------------------ |
| `gold_prices`      | Latest historical gold-price calculation   |
| `oscillator`       | Latest oscillator values                   |
| `palmier_currency` | Latest Palmier valuation and currency data |

The `palmier_currency` payload should preserve the existing structure returned by `palmier_calc.php`, including the base currency, live currencies, gold-price averages and Palmier values.

### D. Palmier logs

`palmier_logs` should preserve historical calculation records.

Suggested record types include:

* `gold_prices`
* `oscillator`
* `palmier_currency`

Each record should identify its calculation period or slot. This is important because your current gold calculator and Palmier calculator use different caching intervals.

**Architectural principle:** The cache holds the latest reusable result; the log holds the historical record. They should not be treated as interchangeable.

### 4.2 Add a generic cache-write function

Below the connection function, add:

```php
function bzj_cache_set(
    string $table,
    string $key,
    array $payload,
    int $ttl = 0
): bool {

    $allowedTables = [
        'millennium_timezone_cache',
        'palmier_cache'
    ];

    if (!in_array($table, $allowedTables, true)) {
        throw new InvalidArgumentException(
            'Invalid cache table'
        );
    }

    $db = bzj_millennium_db();

    if (!$db) {
        return false;
    }

    $json = json_encode(
        $payload,
        JSON_UNESCAPED_UNICODE
        | JSON_UNESCAPED_SLASHES
        | JSON_THROW_ON_ERROR
    );

    $now = gmdate('Y-m-d H:i:s');

    $expires = $ttl > 0
        ? gmdate('Y-m-d H:i:s', time() + $ttl)
        : null;

    $sql = "
        INSERT INTO {$table}
            (
                cache_key,
                payload_json,
                generated_at,
                expires_at
            )
        VALUES (?, ?, ?, ?)

        ON DUPLICATE KEY UPDATE
            payload_json = VALUES(payload_json),
            generated_at = VALUES(generated_at),
            expires_at = VALUES(expires_at)
    ";

    $stmt = $db->prepare($sql);

    $stmt->bind_param(
        'ssss',
        $key,
        $json,
        $now,
        $expires
    );

    $stmt->execute();
    $stmt->close();

    return true;
}
```

The allowlist is important because SQL table identifiers cannot be protected by parameter binding in the same way as ordinary data values.

Only explicitly approved table names should be accepted.

### 4.3 Add a generic cache-read function

Next, add:

```php
function bzj_cache_get(
    string $table,
    string $key
): ?array {

    $allowedTables = [
        'millennium_timezone_cache',
        'palmier_cache'
    ];

    if (!in_array($table, $allowedTables, true)) {
        throw new InvalidArgumentException(
            'Invalid cache table'
        );
    }

    $db = bzj_millennium_db();

    if (!$db) {
        return null;
    }

    $sql = "
        SELECT payload_json
        FROM {$table}
        WHERE cache_key = ?
          AND (
              expires_at IS NULL
              OR expires_at >= UTC_TIMESTAMP()
          )
        LIMIT 1
    ";

    $stmt = $db->prepare($sql);
    $stmt->bind_param('s', $key);
    $stmt->execute();

    $result = $stmt->get_result();
    $row = $result->fetch_assoc();

    $stmt->close();

    if (!$row) {
        return null;
    }

    $data = json_decode(
        $row['payload_json'],
        true
    );

    return is_array($data) ? $data : null;
}
```

These two functions establish the basic pattern:

```php
// Save shared data.
bzj_cache_set(
    'millennium_timezone_cache',
    'historical_time',
    $payload,
    60
);

// Retrieve shared data.
$payload = bzj_cache_get(
    'millennium_timezone_cache',
    'historical_time'
);
```

The example uses a 60-second expiry for illustration. The appropriate expiry depends on the type of data being stored.

For example, the historical date changes continuously under your calculation, whereas a historical gold-price result may be deliberately calculated on a six-hour schedule.

**Do not apply one universal TTL to every cache entry.**

### 4.4 Add a shared logging function

You will also need a common way to write historical records.

Add the following:

```php
function bzj_db_log(
    string $table,
    string $type,
    string $periodKey,
    array $payload
): bool {

    $allowedTables = [
        'millennium_timezone_logs',
        'palmier_logs'
    ];

    if (!in_array($table, $allowedTables, true)) {
        throw new InvalidArgumentException(
            'Invalid log table'
        );
    }

    $db = bzj_millennium_db();

    if (!$db) {
        return false;
    }

    $json = json_encode(
        $payload,
        JSON_UNESCAPED_UNICODE
        | JSON_UNESCAPED_SLASHES
        | JSON_THROW_ON_ERROR
    );

    $now = gmdate('Y-m-d H:i:s');

    $sql = "
        INSERT INTO {$table}
            (
                record_type,
                period_key,
                recorded_at,
                payload_json
            )
        VALUES (?, ?, ?, ?)

        ON DUPLICATE KEY UPDATE
            recorded_at = VALUES(recorded_at),
            payload_json = VALUES(payload_json)
    ";

    $stmt = $db->prepare($sql);

    $stmt->bind_param(
        'ssss',
        $type,
        $periodKey,
        $now,
        $json
    );

    $stmt->execute();
    $stmt->close();

    return true;
}
```

This logging function uses the unique `record_type` and `period_key` pair to prevent the same logical period from accumulating duplicate records.

One consequence is worth understanding: repeated writes for the same period update that record rather than preserving every intermediate calculation. That is useful for periodic snapshots, but it is not a substitute for a separate audit log when every change must be retained.

        'timezone_snapshot'
    );

    if (
        !$data
        || empty($data['historical_iso'])
    ) {
        throw new RuntimeException(
            'Historical timezone data unavailable'
        );
    }

    return new DateTime(
        $data['historical_iso'],
        new DateTimeZone('UTC')
    );
}
```

    . '/../../millennium-timezone/millennium-timezone-db.php';
```

The path above is relative to `shared/palmier/gold_calc/`, so it points to the proposed shared helper.

# Phase 9 — Handle cache freshness and dependency order

## Step 16. Avoid stale or circular dependencies

There is a subtle problem with replacing HTTP requests with database reads.

A database does not automatically guarantee that the value being read is current.

For example, if the oscillator's latest value is missing or stale, the Millennium Probe must not silently assume that it is zero.

Similarly, if the gold calculator's latest record is absent, the Palmier calculator should not treat an empty historical average as a valid result.

I recommend the following dependency order for a cache refresh:

1. Calculate and store the Millennium Timezone snapshot.
2. Calculate and store the oscillator snapshot.
3. Calculate and store the Millennium Probe result using the latest valid oscillator data.
4. Calculate and store the historical gold-price result.
5. Calculate and store the latest Palmier Currency result.

The two independent branches—the oscillator and historical gold-price calculation—can be run separately. The critical rule is that a consumer must not read a result before its producer has generated a valid record.

### Recommended initial freshness policies

These are starting recommendations, not requirements already present in your system.

| Data                                 | Suggested initial policy                           |
| ------------------------------------ | -------------------------------------------------- |
| Current and historical time snapshot | Refresh on demand, with a short cache lifetime     |
| Millennium Probe                     | Preserve the existing freshness interval initially |
| Oscillator                           | Preserve the existing 12,345-second interval       |
| Historical gold prices               | Preserve the existing six-hour slots               |
| Palmier Currency                     | Preserve the existing slot and weekend rules       |

The correct values should be confirmed against your intended business logic before deployment.

### Missing-data policy

Use three distinct outcomes:

* **Valid result:** Return the stored value.
* **Stale result:** Recalculate or refresh according to the existing schedule.
* **Unavailable result:** Return a controlled error and log the failure.

Do not replace missing values with zero unless zero is explicitly the correct mathematical result.

This is especially important for the oscillator and probe.

## 24. Avoid mixing Palmier application logs with database integration logs

Your existing `palmier_logger.php` writes activity records to `Wo_UserActivityLog`.

These serve different purposes:

| Table                      | Purpose                                     |
| -------------------------- | ------------------------------------------- |
| `Wo_UserActivityLog`       | User activity records                       |
| `millennium_timezone_logs` | Millennium Timezone and Probe history       |
| `palmier_logs`             | Currency and oscillator calculation history |

Keeping these concerns separate will make it easier to diagnose errors, reconstruct currency calculations and analyse user activity without conflating them.
