# Millennium Timezone — Refactoring and Implementation

The right approach is to make `millennium-timezone.php` the central source of Millennium/Palmier date calculations, move the Probe engine alongside it, and eliminate unnecessary HTTP requests between PHP files running on Buzzjuice itself.

I have reviewed the supplied original PHP resources and both the previous ChatGPT and GitHub responses. The important architectural decision is to separate shared data, historical calculation records, and live calculations. GitHub's recommendations provide a useful starting point, but the implementation needs several corrections before it should be deployed.&#x20;

## 2. Corrections that must be incorporated

The source files expose several issues beyond simple path changes.

| Area            | Finding                                                                                                               | Required correction                                                                               |
| --------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Timezone engine | The existing `palmier_time()` calculation contains the historical-date algorithm.                                     | Preserve its calculation and test its outputs before changing anything.                           |
| HTTP calls      | Gold and Palmier calculators request other Buzzjuice PHP endpoints over HTTPS.                                        | Replace equivalent same-server calls with local functions where possible.                         |
| Probe           | The old timezone page requests the old Probe URL, and the Probe requests the oscillator over HTTP.                    | Update the path and introduce callable functions for internal use.                                |
| Caching         | The oscillator and Probe have file-based caching, but the cache paths and freshness checks are not fully coordinated. | Apply the 12,345-second freshness rule consistently, with locking to avoid duplicate refreshes.   |

| Logs            | `palmier_logger.php` writes user activity to the Palmier database.                                                    | Separate business activity data from calculation-history logs; retain logs in files as requested. |

The current `gold_calc_helpers.php` calls the old endpoint using `file_get_contents()`. The Palmier calculator also makes same-domain requests for gold and oscillator data. Those are concrete places to eliminate redundant HTTP calls.&#x20;

### Important distinction: current time versus historical date

The new engine must not treat these as the same value.

- Current: the actual UTC timestamp at the time of calculation.
- Local: the date/time representation defined by the existing Palmier algorithm.
- Historical / Reference Year: the date and year calculated by that algorithm.
- Jubilee: the existing Jubilee calculation, using its established input year.
- Probe: the output of the Probe calculation at the selected instant.

The external time service should not be allowed to redefine the Palmier historical calendar. If the server's UTC clock is the trusted clock source, a remote request is not required for every calculation. If you retain an external time API as a fallback or synchronization source, its response must be validated and cached separately.

This is also why I would not blindly adopt the GitHub example's proposed `worldtimeapi.org` integration as a replacement for the existing algorithm. It is a different responsibility from calculating the Palmier historical date.

Add the following block immediately after those connection functions. It centralizes the table prefix and validates suffixes before constructing SQL identifiers.

```

/**
 * Millennium Timezone database configuration.
 *
 * Tables are stored in the koware_iapd database and use
 * the millennium_timezone_ prefix.
 */
if (!defined('MILLENNIUM_TIMEZONE_DB_NAME')) {
    define('MILLENNIUM_TIMEZONE_DB_NAME', 'koware_iapd');
}

if (!defined('MILLENNIUM_TIMEZONE_TABLE_PREFIX')) {
    define(
        'MILLENNIUM_TIMEZONE_TABLE_PREFIX',
        'millennium_timezone_'
    );
}

/**
 * Return a fully qualified, quoted Millennium Timezone table name.
 *
 * Example:
 * millennium_timezone_table('snapshot')
 * returns `koware_iapd`.`millennium_timezone_snapshot`
 *
 * Only use fixed, application-controlled suffixes.
 */
if (!function_exists('millennium_timezone_table')) {
    function millennium_timezone_table(string $suffix): string
    {
        if (!preg_match('/^[a-z][a-z0-9_]*$/', $suffix)) {
            throw new InvalidArgumentException(
                'Invalid Millennium Timezone table suffix.'
            );
        }

        return '`' . MILLENNIUM_TIMEZONE_DB_NAME . '`.`'
            . MILLENNIUM_TIMEZONE_TABLE_PREFIX
            . $suffix . '`';
    }
}

```

Why this is necessary: the requested prefix is a database-and-table naming convention, not a standalone table. For example, the complete table name for a current snapshot is `koware_iapd.millennium_timezone_snapshot`.

### Database access permissions

Before deploying, verify that the MySQL user configured for `get_iapd_db_conn()` has the required permissions on the new tables. If it cannot write to `koware_iapd`, the code should log the database failure and continue serving valid cached data when possible.

Do not duplicate database credentials in any of the new files.

## 4. Step two — Create the Millennium Timezone tables

Use `koware_iapd` for shared, structured timezone state and cache data. Do not create a database table for every calculation or log entry.

Run the following SQL in phpMyAdmin against the `koware_iapd` database. It creates a current-state snapshot table and a small cache-metadata table.

```

CREATE TABLE IF NOT EXISTS `millennium_timezone_snapshot` (
    `id` TINYINT UNSIGNED NOT NULL,
    `timestamp` BIGINT UNSIGNED NOT NULL,
    `iso` VARCHAR(40) NOT NULL,
    `day` VARCHAR(20) NOT NULL,
    `date` VARCHAR(20) NOT NULL,
    `month` VARCHAR(20) NOT NULL,
    `year` SMALLINT UNSIGNED NOT NULL,
    `time` VARCHAR(20) NOT NULL,
    `historical_iso` VARCHAR(40) DEFAULT NULL,
    `historical_year` SMALLINT DEFAULT NULL,
    `jubilee` VARCHAR(32) DEFAULT NULL,
    `probe_value` VARCHAR(80) DEFAULT NULL,
    `updated_at` TIMESTAMP NOT NULL
        DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS `millennium_timezone_cache` (
    `cache_key` VARCHAR(100) NOT NULL,
    `fetched_at` BIGINT UNSIGNED NOT NULL,
    `payload_json` LONGTEXT NOT NULL,
    `updated_at` TIMESTAMP NOT NULL
        DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`cache_key`)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

```

These are proposed new tables, not existing tables confirmed on your server. The `snapshot` table holds the latest structured result; the `cache` table holds cached payloads for data that is expensive to retrieve.

Historical calculation records remain in append-only log files. Use the database only for state that must be queried by multiple PHP files.

```
    define('MTZ_CACHE_TTL', 12345);

```

The path is important: `dirname(__DIR__)` resolves to `shared/`, so the include resolves to `shared/db_helpers.php`.

Retain the existing `$historicalHourMap`, weekday/month arrays, `ordinal()`, `jubilee()` and `palmier_time()` functions. Do not replace them with a new date formula just to accommodate the new filename.

### 5.2 Make the historical calculation reusable

The existing `palmier_time()` returns the current time, the calculated historical date and an error value. It should become the internal calculation function used by both the HTML page and JSON responses.

Add a result-building function that derives the display fields from those values. For example, the following function illustrates the required output structure and can be used once the existing engine has been retained in the file.

```

if (!function_exists('mtz_build_calendar_result')) {
    function mtz_build_calendar_result(): array
    {
        global $daysShort, $daysFull, $months;

        [$now, $historical, $error] = palmier_time();

        if (!$now instanceof DateTime ||
            !$historical instanceof DateTime) {
            throw new RuntimeException(
                'Palmier date calculation did not return valid dates.'
            );
        }

        $currentUtc = clone $now;
        $currentUtc->setTimezone(new DateTimeZone('UTC'));

        $historicalUtc = clone $historical;
        $historicalUtc->setTimezone(new DateTimeZone('UTC'));

        $weekdayIndex = (int) $currentUtc->format('w');
        $historicalWeekdayIndex = (int) $historicalUtc->format('w');

        return [
            'status' => $error ? 'warning' : 'ok',
            'timezone' => 'UTC',
            'generated_at' => gmdate('Y-m-d\TH:i:s\Z'),
            'day' =>
                $daysShort[$historicalWeekdayIndex] .
                $daysFull[$weekdayIndex],
            'date' => ordinal(
                (int) $historicalUtc->format('d')
            ),
            'month' =>
                $months[(int) $historicalUtc->format('n') - 1],
            'jubilee' => jubilee(
                (int) $currentUtc->format('Y')
            ),
            'reference_year' =>
                (int) $historicalUtc->format('Y'),
            'local' => $historicalUtc->format(
                'Y-m-d\TH:i:s\Z'
            ),
            'current' => $currentUtc->format(
                'Y-m-d\TH:i:s\Z'
            ),
            'historical_iso' => $historicalUtc->format(
                'Y-m-d\TH:i:s\Z'
            ),
            'error' => $error ?: null
        ];
    }
}

```

This function establishes the machine-readable contract. It is not a complete replacement for the existing engine: the original `palmier_time()` must remain available, and the Probe value still needs to be added by the Probe integration described below.

The `local` field above deliberately retains the UTC representation of the historical value produced by the existing algorithm. If “Local” is intended to mean a different timezone or a specific historical display value, that semantic must be established before changing it.

### 5.3 Add JSON endpoint handling

The new page should support these query parameters:

| Query                  | Purpose                                        |
| ---------------------- | ---------------------------------------------- |
| `?endpoint=historical` | Return the historical date and reference year. |
| `?endpoint=current`    | Return the current UTC date/time.              |
| `?endpoint=probe`      | Return the current Probe result.               |
| `?endpoint=timezone`   | Return the complete structured payload.        |
| No query parameter     | Render the human-readable HTML page.           |

The JSON handler must execute before HTML output and must not run when the file is included by another PHP script.

Use a single dispatcher, with `json_encode()` and the `Content-Type: application/json` header. Return an appropriate HTTP status code when a requested calculation fails. Do not return PHP warnings or HTML fragments inside a JSON response.

### 5.4 Implement the 12,345-second cache correctly

Use the log file to determine the age of the last successful refresh. When it is fresh, serve the cached result. When it is stale, refresh only once, then update both the file log and the database snapshot.

The required refresh condition is:

```
$shouldRefresh = (
    !$lastSuccessfulRefresh ||
    (time() - $lastSuccessfulRefresh) >= 12345
);
```

That is the freshness rule, not a complete concurrency-safe cache implementation. In production, use `flock()` around the refresh operation so simultaneous AI-agent requests do not all fetch the same endpoint.

The fallback order should be:

1. Return the fresh cached result.
2. If stale, acquire the lock and check the cache again.
3. Refresh the necessary external data only if still stale.
4. Persist the successful payload to the log and database.
5. If the refresh fails, return the last valid cached payload and report its age.
6. If no valid cached payload exists, return an explicit error rather than fabricating a successful remote result.

Important: a 12,345-second refresh interval is approximately 3 hours, 25 minutes and 45 seconds. It does not mean that the current UTC clock should be stale for that duration. A locally generated current timestamp can be calculated without a network request; the cache applies to the expensive shared data being refreshed.

The existing implementation also supports `?probe=now`; retain that external behavior, but make the internal calculation reusable without executing the dashboard.

### 6.3 Return a stable Probe payload

The timezone endpoint should expose the Probe value as a field of its complete JSON payload, not require the consumer to call a second URL to discover it.

A recommended response structure is:

```
{
  "status": "ok",
  "timezone": "UTC",
  "generated_at": "2026-10-28T21:00:00Z",
  "day": "WedWednesday",
  "date": "28th",
  "month": "October",
  "jubilee": "calculated-value",
  "reference_year": 2026,
  "local": "calculated-historical-timestamp",
  "current": "2026-10-28T21:00:00Z",
  "probe": {
    "value": "calculated-probe-value",
    "timestamp": 1793221200
  }
}
```

Illustrative schema only. The Jubilee, historical timestamp and Probe value must be computed by the existing algorithms; the example values are not a validated calculation output.

For AI agents, also include a cache timestamp, cache age and a `stale` indicator. This allows the agent to read the page directly and decide whether the data is sufficiently recent without repeatedly polling the endpoint.

```
function getPalmierHistoricalDate(): DateTime
```

The gold calculator's six-hour cache is a separate policy from the timezone engine's 12,345-second refresh. Do not merge them into one TTL.

## 2. Critical Corrections to the GitHub Recommendations

The GitHub response contains useful architectural recommendations, but I would not deploy its proposed code without correcting the following issues.

### 2.1 The database table prefix must be handled consistently

The required naming convention is:

`koware_iapd.millennium_timezone_...`

The proposed helper in the GitHub response uses the database name and constructs a table name dynamically. That is a reasonable approach, provided the database identifier comes from trusted configuration and the table suffix is validated. 

I recommend centralizing this in `db_helpers.php`, rather than duplicating database-name and table-name logic across the Millennium Timezone files.

The existing `get_iapd_db_conn()` and `get_palmier_db_conn()` functions should remain the authoritative connection mechanisms.

Before adding new helpers, verify that both functions are already present in the complete deployed version of `db_helpers.php`. The publicly retrieved portion confirms the Palmier environment configuration, but does not establish the complete implementation of both requested connection functions. 

### 2.2 The proposed probe integration contains a filesystem-path error

The GitHub proposal attempts to locate the probe using:

```php
$file = dirname(__DIR__) . '/shared/millennium-timezone/millennium-probe.php';
```

When the calling file resides in `shared/millennium-timezone/`, this constructs an incorrect path because `dirname(__DIR__)` already resolves to the parent `shared` directory.

The proposed code also attempts to pass a query string to a filesystem path:

```php
file_get_contents($file . '?probe=now');
```

A local filesystem path does not execute PHP or interpret `?probe=now` as a request parameter.

**The correct solution is to expose a reusable function from the probe engine and invoke it directly.**

For example, the intended integration should look conceptually like this:

```php
require_once __DIR__ . '/millennium-probe.php';

$probe = millennium_probe_now();
```

This is an integration pattern, not a complete replacement for the probe engine. The function must be implemented so that including the file does not inadvertently render its HTML interface or terminate the calling script.

### 2.3 The historical date must not be confused with the current date

This is the most important calculation issue.

The proposed GitHub helper returns:

```php
$iso = $json['current'];

return new DateTime($iso, new DateTimeZone('UTC'));
```

However, `current` represents the actual current timestamp in the proposed data model.

It is not necessarily the historical date that the gold calculator needs.

The existing gold calculator obtains a historical date and uses that date to select a gold-price anchor from its CSV data. Returning the current timestamp instead could select the wrong historical gold price. 

The new JSON contract should distinguish at least these values:

| Field              | Meaning                                                                     |
| ------------------ | --------------------------------------------------------------------------- |
| `current`          | Actual current timestamp in UTC                                             |
| `historical_iso`   | Exact historical date and time calculated by the Millennium Timezone engine |
| `reference_year`   | Year associated with the historical reference date                          |
| `local`            | Calculated historical local time                                            |
| `probe`            | Date and time represented by the Millennium Probe                           |
| `probe_value_days` | Numerical probe displacement, in days                                       |

The gold calculator must use `historical_iso` when resolving its historical gold-price anchor.

The value must be derived from the existing historical calculation—not from the current timestamp or an approximation based solely on `reference_year`.

### 2.4 Do not create database tables on every request

The GitHub response proposes a function that creates the snapshot table when invoked.

Although `CREATE TABLE IF NOT EXISTS` can be useful during initial setup, schema management should not run on every public page request.

Instead:

1. Create the required tables once through a controlled migration.
2. Use the existing database helpers to access them.
3. Read cached state where appropriate.
4. Update state only when necessary.
5. Keep historical calculation logs in files.

This separates deployment responsibilities from runtime responsibilities.

### 2.5 File logging needs a defined retention policy

The existing oscillator uses a 12,345-second interval, while the probe also defines a 12,345-second cache lifetime. 

The new timezone engine can use the same interval to decide when a refresh is due.

However, simply appending to a log forever would eventually create a storage problem.

The implementation should therefore distinguish:

* **Current cached state:** the latest valid calculation.
* **Historical log:** previous calculations retained for auditing.
* **Error log:** failed refreshes and calculation errors.

The current state can be read efficiently without scanning a large historical log. Historical records can be rotated by month or another defined retention policy.

## 4. The 12,345-Second Refresh Mechanism

The intended behaviour is:

1. Read the most recent valid cached timezone result.
2. Determine its age.
3. If it is younger than 12,345 seconds, reuse it.
4. If it is older, calculate a fresh result.
5. Record the successful refresh in the log.
6. Update the shared cached state.
7. Return the same result to every consumer.

The refresh threshold is approximately **3 hours, 25 minutes, and 45 seconds**.

There is an important implementation detail: the log must not be the sole source of truth for determining whether a calculation succeeded.

If a refresh fails, the system should preserve the last valid result rather than replace it with incomplete or invalid data.

The system should also use a lock or another concurrency-control mechanism to prevent multiple simultaneous requests from performing the same expensive refresh.

This is particularly important when several visitors, automated agents, or scheduled tasks request the timezone simultaneously.

### AI-readable output

The public page should support both:

* An HTML view for people.
* A JSON view for applications and AI agents.

The response should explicitly identify the fields and their meanings, with timestamps expressed in UTC using ISO 8601 formatting.

The HTML page should visibly display:

* Day
* Date
* Month
* Jubilee
* Reference Year
* Local
* Current
* Probe

The JSON response should additionally include the exact historical timestamp, probe displacement, calculation timestamp, and cache status.

That provides a stable contract for future agents and applications without requiring them to interpret the page's visual layout.
