> **Contract directive.** This document defines the meaning, lifecycle, privacy, accepted-state projection and portability of episode continuity records. It does not create a physical database schema, approve a migration, grant write permission, or promote draft events into canon. Existing physical field names may remain where a verified lossless compatibility map exists.

## 1. Purpose and responsibility

The ledger is the durable memory of the serial, not another creative master prompt. It preserves accepted story state, proposed changes, source evidence, rights, character knowledge, mission position, open storylines, challenges, derivatives, editorial decisions and a self-contained handover. It is episode-owned and revision-aware. A daily run may produce a proposed update; only the authorized editorial process can accept it.

The governing master controls story policy and exact B1–B8 meaning. The daily protocol controls retrieval and run sequence. This ledger controls record semantics and continuity custody. The alignment review controls compatibility/adoption evidence. No companion silently changes another's authority.

## 2. Security and data separation

Use sensitivity classes `PUBLIC`, `INTERNAL` and `RESTRICTED` at record and embedded-field level. Access to read a source does not grant permission to quote, portray, adapt, publish, export or transfer it. Diary entries, personal identifiers, private correspondence, HR material, answer keys, credentials, secret tokens and security evidence must not enter a public export or ordinary B6.

`challenge_answer_key` is a restricted logical family, not a command to instantiate it. An ordinary daily A/B run never stores or prints its body. B7/B8 may contain only opaque custody status and a safe reference when one exists. If custody is absent, record exactly: `RESTRICTED OUTPUT NOT CREATED; HUMAN SECURE CUSTODY REQUIRED`. Never leak answers through alt text, metadata, filenames, comic panels, prompts, captions or error messages.

Retention, revocation, lawful erasure and privacy restrictions override simplistic append-forever rules. Authorized custodians may apply audit-preserving redaction/tombstones and invalidate dependent exports under actual policy. Do not preserve forbidden content merely because it once appeared in a continuity record.

## 5. Episode, calendar and identity semantics

The episode can contain up to ten separately commissioned weekday Chronicles. A two-week episode ordinarily spans Monday through the second Friday, but the approved calendar controls. Do not assume a phase starts on Monday or that a partial block is a valid episode. Keep production date, invocation timestamp, timezone, phase boundary convention and source capture times separate.

Maintain chapter-wide role-check day 1–40 separately from episode slot 1–10 and calendar date. A role chart check index is not the day of month. Do not infer chapter or episode identity from `T05`, `CH05`, a Probe phase number or a filename. Preserve `S00_T05`, `S00_T05_E01` and any other existing IDs until a human-approved bidirectional crosswalk exists.

## 6. Three clocks and location state

Store P/H/F independently:

- P: production/present story date/time and approved timezone.
- H: historical/reference endpoint and associated historical context.
- F: field/Probe destination, timestamp, phase and mission state.

For each store actual source, original offset-aware value, acquisition time, parse/status, conversion, freshness, missing fields and confidence. A historical reference is not proof of current physical presence; a future Probe date is not a source of future journalism or observed weather. Keep HQ/control, lab, Enka's physical present, Enka's historical reference, Probe destination and every active field participant distinct. A character cannot change place without an accepted causal transport/return event.

## 7. Event lifecycle and accepted-state projection

### 7.1 Event contract

Each `continuity_event_log` event contains: immutable ID; source A day/revision and scene/beat; fictional effective time and place; actor/mission/project/storyline; accepted pre-state; exact proposed delta and hypothetical post-state; prerequisites; character knowledge; applicable canon/rights; lifecycle `PROPOSED`, `ACCEPTED`, `REJECTED` or `SUPERSEDED`; real approval evidence/time; and correction links (`supersedes`, `correction_of`, `reverses`).

Never edit an accepted past event in place. Record an authorized correction/compensating event and retain the original history subject to lawful retention. An accepted in-world event is franchise truth within its scope, not proof a real employee performed the action.

### 7.2 Projection algorithm

1. Select the authorized episode and last accepted event head; read actual base revision.
2. Load effective canon and accepted parent carry-forward references.
3. Read events in accepted revision/sequence order; retain fictional effective time as a separate field.
4. Exclude proposed, rejected, revoked and unapproved events from accepted projection.
5. Validate predecessors and causal prerequisites; log broken causality instead of guessing.
6. Apply accepted deltas to scoped character, mission, storyline and episode state.
7. Recompute downstream projections affected by an approved correction/supersession.
8. Record exact contributing event refs and actual accepted revision.
9. Before any authorized write, compare current head to base revision; stale base requires reconciliation.
10. Apply lawful redaction/tombstone and downstream export invalidation when authorized.

A stranded person remains stranded until an accepted contact/return/transport event changes that state. A character cannot know an event from an unaccepted draft. An episode boundary does not automatically retrieve a mission team, heal an injury, resolve a relationship or complete a project.

### 7.3 Editorial acceptance and canon promotion

Acceptance of story prose, acceptance of event deltas, canon promotion, real-person portrayal consent, repository write and publication are separate decisions. Record the exact scope of each. A model suggestion is always a proposal until a human decision with real evidence is recorded.

## 8. Rights, challenge and derivative dependency

Permission is action-, audience-, asset- and time-specific. Track access, quotation, portrayal, adaptation, public distribution, transfer, attribution and revocation separately. A diary can be accessible but not publishable. A portrait or voice permission can be withdrawn; affected derivatives then become restricted/stale and must be re-evaluated.

The public challenge is the last meaningful content of A. Record its exact approved wording or safe reference, A revision, accessibility/fairness, source and reveal obligation. Never place the answer or revealing rationale in B1–B8. `challenge_answer_key` requires separate secure authorization and actual access-controlled custody. Do not create C in ordinary daily production.

Every derivative records exact source A revision, challenge revision, canon and rights references. If any dependency changes, mark affected assets `STALE_SOURCE` until rechecked or regenerated. A prompt, storyboard, render, assembled file and published file are different states. A proposed Service Card is not a real product or reward transaction. Future integrations such as QR/Buzz Codes, Palmier/myCred, badges, points and automated awards require separate privacy, security, economic, moderation and eligibility approval.

## 10. Mandatory fifteen-part B6

1. Identity/revisions: season/chapter/episode/day, legacy crosswalk, A revision, editorial state, owner and effective master/protocol/ledger editions.
2. Calendar: requested local date, approved timezone, weekday, episode slot #1–#10, chapter role day #1–#40 where verified, authority and fit.
3. Temporal/spatial snapshot: P/H/F values, source ages and distinct HQ, Enka-present, Enka-historical, lab, Probe and deployed-person positions.
4. Accepted recap: last accepted story, distinct from today's draft, consequences and source revisions.
5. Character projection: location/time, knowledge, relationships, obligations, permitted injury data, era capability, rights and proposed/accepted distinction.
6. Mission projection: roster, temporal coordinates, charge/comms, last contact, equipment, risk and outstanding retrieval.
7. Organization/project: chart revision, chapter workday, featured roles, actual/fictional/proposal classification.
8. Study/practical learning: reading anchor, selected work, verse provider/date/translation and real H&S course/lesson.
9. Research provenance: verified history/current reporting versus `FICTION_PROBE_SCENARIO`, event/publication/retrieval dates, geography/weather and omissions.
10. Storyline/event changes: open/advanced/resolved/deferred threads, accepted event refs, proposed changes and hypothetical post-state.
11. Challenge: nonrevealing public question ref, source A revision, reveal obligation and opaque custody state only.
12. Derivatives/cards: actual commissioned assets, source bindings, rights and current/stale/not-commissioned state.
13. Exceptions/decisions: missing evidence, conflicts, severity, decision owner and resolution requirement.
14. Next eligible working day: accepted opening position, opportunities, character/mission constraints and refresh tasks.
15. Operational truth: actual A/B locations, write/readback/commit evidence, editorial/lock/release state and recipient permissions.

A new provider must reconstruct state from authorized editions, accepted records, corrections and permission-filtered B6. Never rely on hidden conversation memory or import private diaries/keys. Day #10 reports readiness only; it does not trigger compilation.

## 11. Concurrency, migration and rollback

Use optimistic concurrency with actual `base_revision`, current head and expected parent. Two writers on one base cannot silently overwrite each other. On mismatch, stop the write, retain both drafts and request reconciliation. Never force-push or overwrite accepted records to make a validation pass.

A document edition and deployed `schema_version` are independent. Before physical migration, require an approved mapping, backup, dry-run, data-integrity comparison, access-control review, migration receipt, readback and rollback procedure. Preserve legacy IDs and aliases. No destructive rename or migration is authorized by this candidate.

## 12. Validation and lifecycle

For each family, validate required semantic fields, sensitivity, rights, lineage, source refs, status reasons and dependent assets. For each daily handover, include all Q01–Q16 results or honest `NOT_RUN`/`NOT_APPLICABLE` status. The ledger itself does not certify that a live episode passed. Editorial, persistence, release and derivative axes remain independent.
