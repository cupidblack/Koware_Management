## 1. Goals, authority and nonnegotiable invariants

One ordinary episode supports **ten distinct Monday–Friday production dates** across two complete weeks, even when public Part numbering uses an approved historical compression exception. The ledger preserves authority and chapter/episode/day identity; original accepted story revisions; immutable as-of sources, three clocks and independent participant positions; role and real-work boundaries; rights and consent; open threads and Edubeam devices; canon-compatible in-universe decisions; challenge obligations without an answer; artwork/media dependencies; Q gates; editorial action; and next-operator portability.

**Invariants:** (i) only **accepted, effective** events enter the authoritative fictional state, (ii) old accepted revisions are not destructively overwritten by new drafts, (iii) a story-world occurrence is not an actual completed Koware project, (iv) current human rights/revocation outrank mere accessibility and historical caching, (v) public A is physically separate from internal B and separately restricted C, (vi) a general handover never carries a challenge key or private raw diary, (vii) downstream art/media is stale when source/canon/rights/question changes until revalidated, (viii) every claimed external write or public release requires successful independent proof, (ix) aliases are preserved until reversible owner-authorized migration, and (x) an absent value never becomes a fabricated record.

The persistent `CC_AI_DESK` contains reusable prompts, registry and approved shared canon, **not** the automatic authoritative home for all changing episode events, credentials or personal diaries. Higher-level chapter/season/series rollups cite accepted episode sources and require explicit separate review; writing a story cannot self-promote canon.

## 3. Security model and separated outputs

Use `PUBLIC`, `INTERNAL`, `RESTRICTED` **per artifact and sensitive field**; further policies may restrict internal transfer. `PUBLIC` is an actual authorized release classification, not merely an attractive draft. Rights must be independently scoped for **read**, **internal summarize**, **quote**, **fictional portrayal**, **adapt**, **third-party model upload**, **external transfer**, **publish**, **retain**, **correct** and **revoke**. A publicly readable character file, logo or diary is not consent from the human represented or copyright clearance.

| Class | Authorized examples | Not authorized by default |
|---|---|---|
| `PUBLIC` | Approved public A and exact approved challenge wording; legally cleared sourced attribution | A draft marked public merely because it was generated |
| `INTERNAL` | B1–B8, evidence summaries, draft deltas, role checks, accepted-event references, safe consent-status metadata | Raw private diaries or a challenge answer/marking rationale |
| `RESTRICTED` | Challenge solution key and rubric, raw personal diaries and proof of sensitive consent, credentials | Public GitHub, unrestricted ZIP, ordinary model handover, public alt text |

`challenge_answer_key` is a **restricted logical record family only**. Create, inspect or export it only in a separately commissioned operation with actual authenticated secure storage, permission and an access log. A `challenge_public_register` may record an **opaque custody-status or nonrevealing reference**; an unverified vault pointer must not be presented as an existing secure key. B8 states `RESTRICTED OUTPUT NOT CREATED; HUMAN SECURE CUSTODY REQUIRED` in ordinary daily runs absent proof. Privacy rights including revocation, lawful erasure and redaction can require **tombstone-and-audit preservation**, not indefinite retention of forbidden sensitive content. Never preserve an illegal disclosure solely because the event log is append-oriented.

The physical separation test is strict: **A ends at the literal public challenge**; B is a separate internal document, channel or permission-filtered transfer. A restricted C, when exceptionally authorized, lives in a different verified custody. If the environment cannot safely isolate B from public readers, produce only a safe high-level status and mark `RESTRICTED_NOT_EMITTED`; do not put B in a public story footer or concatenate all three into one archive.

## 7. Accepted-state event lifecycle and deterministic projection

A story-draft's *suggested in-universe action* is `PROPOSED`; even a beautifully written manuscript cannot mark it `ACCEPTED`. Event state machine is `PROPOSED → ACCEPTED | REJECTED`; an accepted event can later be superseded/corrected by a separate authorized compensating event with `SUPERSEDED` linkage. Never silently edit the old accepted record. For any accepted event require: source `daily_chronicle_record` accepted revision/scene; actor/authority; causal preconditions; exact in-world time and physical place; affected persons, mission, equipment, storyline and risks; state delta; actual editor acceptance and effective date; source rights. Future timeline time and editorial acceptance time are separate.

**Projection algorithm:**

1. Determine the **actual approved** episode and effective canon boundary, plus the last accepted `base_revision` in the authorized storage. Confirm its identity/legacy crosswalk.
2. Read all **effective accepted** continuity events in stable recorded acceptance/revision order. Use in-world fictional timestamps to verify causality but **not** to reorder acceptance history arbitrarily; flashbacks and editorial correction are different operations.
3. Exclude `PROPOSED`, `REJECTED`, ineffective/revoked and superseded content according to genuine supersession semantics; do not confuse a record **present in an append-only log** with one effective in the projection.
4. Validate prerequisites, scope and rights for each applied delta. Apply changes to correctly scoped characters, mission team positions, knowledge, storyline/open clue, artefacts and episode state; resolve accepted corrective/reversal events in authenticated decision order.
5. Recompute dependent projections whenever an approved correction changes an earlier premise. If the successor's prerequisite becomes impossible, log `CONFLICTING` or block rather than invent a reconciliation.
6. Produce an immutable **accepted projection read view**, base revision and exact diff-to-proposed-draft. Only approved edits can change the authoritative projection. Preserve unresolved source, place/clock and permission exceptions and report source freshness.

A hypothetical **post-state if accepted** is explicitly marked conditional in B5 and B6, and never becomes the next day’s real starting position without an intervening acceptance event. Human editorial acceptance and the physical commit/write mechanism are independent axes. Actual project/task completion needs external organizational evidence beyond its fictional analogue.

### 7.1 Conflict-safe physical write protocol (separate authorized job only)

1. Confirm `ARCHIVE_WRITE` or relevant mutation was expressly commissioned; verify true owner-approved destination, content classes, permissions and actual access credentials through supported tools.
2. Acquire source `head_revision`, accepted baseline, ACL, dependent assets and versioned diff; validate actual revocation and sensitive fields again.
3. Compare `head_revision` with the recorded `base_revision` (**optimistic concurrency**). A mismatch becomes `CONFLICT_REQUIRES_RECONCILIATION`; no blind overwrite/retry.
4. Apply only the authorized atomic/transactional change supported by the actual implementation. Where transactions are absent, stage and validate a reversible change plan before writing.
5. Read back persisted content/metadata and verify revision, digest if calculated, classification and absence of restricted leakage before `COMMITTED_VERIFIED`. On partial failure mark `WRITE_FAILED` and preserve incident details safely.
6. Preserve independent evidence for editorial `ACCEPTED`, release `PUBLISHED_VERIFIED` and any `CANON_PROMOTION`; none is implied by a successful file save.

An A/B file generated locally is an **unsaved repository draft**; a file's logical planned path is not proof it has been created in GitHub or a private Studio database. Concurrent editors need actual merge/rebase authorization. Privacy containment and lawful deletion/tombstones may override normal retention under the system's approved legal controls.
