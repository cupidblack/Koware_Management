## 1. Contract goals and scope

A two-week ordinary episode has up to ten individually commissioned weekday chronicles. The episode ledger must preserve: approved calendar and identity; actual story revisions; source observations and claims; consent/licensing restrictions; what accepted events changed the fictional world; proposed changes in unreleased drafts; individual character knowledge and location; Edubeam mission deployment; storyline openings and closure; organizational roles and verified real work; public challenges **without answers**; derivative provenance; owner/editor decisions; actual quality checks; and a self-contained next-day handover. Preserve original story history and reasons for corrections without confusing a proposed event with an approved fictional fact.

The persistent `CC_AI_DESK` houses reusable prompt/schema/catalog definitions, routing and approved shared canon. It does **not** automatically own every episode's research, sensitive diary, restricted key or changing mission state. Approved episode archives are responsible for their own continuity, source and production records. Parent-level rollups cite contributing accepted episodes. Canon changes require a distinct authorized promotion, not an automatic consequence of writing a story.

**Core invariants:** one authoritative accepted projection per episode revision; no accepted state from draft events; full correction/supersession links; no challenge key in public/internal records; no raw private diary exported by default; no unverified archive write; no derivative labeled current when upstream revision mismatches; no phantom family rows to satisfy a count; no unapproved expansion from a daily commission to an episode/media commission.

## 2. Security, partitioning and custody

Use field- and artifact-level classifications: `PUBLIC`, `INTERNAL`, `RESTRICTED`; actual Studio policy can require narrower controls. `PUBLIC` describes genuinely approved output, not a proposed draft merely suitable for publication. Retrieval/access, internal use, character portrayal, adaptation, public release, cross-platform transfer, retention and revocation are **separate** rights. A public GitHub file or model-created character canon does not prove permission to publish someone's diary, face, voice or identity.

| Data class | Examples | Default destination |
|---|---|---|
| `PUBLIC` | Human-approved A, exact public question wording, approved public learning attribution | Approved public release location, after separate release authorization |
| `INTERNAL` | B1–B8, draft text, event history, project charts, source assessments, *nonrevealing* consent statuses | Approved private episode/editor workspace and permission-filtered receiving collaborator |
| `RESTRICTED` | Challenge answer/rationale; private diaries, identity documents, credentials and sensitive consents where restricted | Actual purpose-specific access-controlled custody; **never** generic chat, ordinary B, public repository or shared ZIP |

`challenge_answer_key` is a **restricted logical family**, not an instruction to instantiate it. An ordinary daily A/B run never stores or prints its body. Create/retrieve C only for an independent explicit operation with verified authority and secure custody. B7/B8 preserve only nonrevealing custody states and genuinely safe opaque references. Do not put answer-bearing clues in captions, metadata, images, prompts, page alt text, filenames or error messages. If custody is absent, B8 records `RESTRICTED OUTPUT NOT CREATED; HUMAN SECURE CUSTODY REQUIRED`; the A draft can remain permissible while competitive release awaits a separate editor decision.

Data retention, revocation, lawful erasure, emergency containment and privacy restrictions outrank a simplistic “append forever” rule. Authorized custodians apply audit-preserving corrections, redaction or tombstones under actual law/policy. Never preserve forbidden content merely because it once appeared in an event record.

## 3. Common logical record envelope

The following **logical semantic fields** are required when a family is instantiated; implementations can use different physical names with a documented lossless mapping.

| Field | Meaning / validation |
|---|---|
| `record_id`, `family`, `schema_id`, `schema_version` | Persistent unique identity; canonical family; `CC-ECLPM`; **actual deployed** schema version; no invented persisted ID. |
| `episode_id`, `day_id`, `legacy_id_refs` | Actual canonical and legacy identities when verified; day legitimately absent for episode-wide items; preserve `S00_T05` / `S00_T05_E01` until authorized crosswalk. |
| `record_revision`, `parent_revision`, `base_revision` | Actual immutable change lineage / optimistic-concurrency input; no imaginary commit or hash. |
| `artifact_uri`, `storage_proof`, `captured_at`, `updated_at`, `actor` | Real source/commit readback proof, offset-aware times and actual author/tool. A generated local draft is `DRAFTED_NOT_COMMITTED` for repository persistence. |
| `classification`, `sensitive_field_policy`, `audience`, `permitted_uses` | Record plus sensitive embedded-field access; deny unsupported use; never include credentials or keys in exports. |
| `source_refs`, `source_revisions`, `snapshot_ref`, `evidence_status` | Actually read source and source revision, acquisition date/digest when measured, factual/fictional classification and missing reasons. |
| `editorial_status`, `approval_evidence`, `effective_at` | Real `UNREVIEWED`/`ACCEPTED`/`LOCKED` and actual human decision/time; generation is not acceptance. |
| `body`, `field_statuses`, `conflict_refs` | Family-specific content, type-compatible null plus explanation, unresolved issue refs; no dummy completed observations. |
| `integrity_digest`, `supersedes`, `superseded_by`, `dependent_asset_refs` | Measured content digest when calculated; change history, correction links and actual dependent assets. |

**Missing-value semantics:** typed JSON `null` requires an accompanying status/reason such as `not_retrieved`, `not_verified`, `source_down`, `restricted`, `not_authorized`, `conflicting`, `editorial_decision_required` or `not_applicable`. In Markdown, state the same reason explicitly. Distinguish `NO_CHANGE` (verified unchanged), `NOT_APPLICABLE` (explained by scope), `NOT_RUN` (check not performed), `UNAVAILABLE` (attempted but unavailable) and `UNKNOWN` (not established). Null does not mean false, and a missing mission status does not prove “no mission.”

Physical references do not themselves prove persisted objects. Read the actual repository head before approved write, compare base revisions and reconcile mismatches. Do not overwrite accepted episodes, canon or previously recorded identifiers without explicit authority.

## 5. Calendar, three-clock and source-snapshot contracts

For a daily `episode_context_snapshot`, store the requested production local date and separate actual acquisition/operation timestamp; approved timezone name; authority reference; phase start/end and inclusive/exclusive convention; first-Monday anchor; *whole* Monday–second-Friday episode fit; nonnegative `elapsed_days` and `block_day`; authorized episode number 1–4, chronicle number 1–10 and chapter working day 1–40; target weekday; accepted ID/legacy crosswalk; duplicates and exception state. A weekend, phase gap or unsupported partial episode gets **no** invented ordinary number. Resolve from the approved calendar, not telemetry alone.

For each clock P/H/F store source URL/record, original offset-aware ISO timestamp if actually supplied, parse status, converted dates/times, actual captured-at timestamp, freshness, source field missing reasons and the **independently determined location**. Clock P on a retrospective request is the *requested story date*, while today's retrieval is separately audited; Clock H is an historical-reference value, not proof of current physical presence; Clock F is a Probe time, not access to future newspapers. Track separately HQ/control, actual/unknown current Enka, historical-reference Enka, Edubeam lab, Probe destination and each active team member. Travel/retrieval and story knowledge follow accepted continuity.

The `source_snapshot_register` records real raw `iso`, `probe_iso`, `now_iso`, `phase_start_iso`, `phase_end_iso`, `phase_index`, oscillation and amplitude **only where actually returned** from the historical or Probe endpoints. Store any HTTP errors, parse failures and partial responses. Fresh Probe telemetry can support present observations but does not authorize a chapter calendar or describe conditions on an old story date. User-supplied fallback values retain their original acquisition time and limitations; do not rebrand a cached result as newly fetched.

## 6. Append-only events, accepted-state projection and canon promotion

### 6.1 Event semantics

A `continuity_event_log` event records: immutable ID; source A day/revision and cited scene/beat; event effective fictional time and *place*; actor, mission, project and storyline identities; accepted **pre-state**; exact **proposed delta** and hypothetical post-state; causal prerequisites; what each character can know; applicable locked canon/rights; event lifecycle `PROPOSED`, `ACCEPTED`, `REJECTED` or `SUPERSEDED` under actual decision rules; real acceptance evidence and effective time; corrections linked through `supersedes`/`correction_of`/`reverses`. Editing an accepted past event in place is forbidden; use a separately recorded, approved correction/compensating event. The original remains historically traceable subject to lawful retention.

An accepted in-world event is franchise truth **only within its scope**, not proof that a human performed the action in reality. `role_project_log` needs independently verified organizational work evidence before stating a real project was completed.

### 6.2 Accepted-state projection algorithm

1. Select the authorized episode and its last *accepted* event head; check parent episode carry-forward references and current effective canon. Preserve actual `base_revision`.
2. Read events in unambiguous accepted revision/sequence order, retaining the event's fictional effective time as a distinct attribute. Sorting flashback timestamps must not reverse a later editorial correction.
3. Exclude proposed, rejected, revoked or unapproved events from the **accepted** projection. Validate every accepted predecessor; unresolved broken causality becomes a logged conflict, not guessed world state.
4. Apply each effective accepted delta to correctly scoped character, mission, storyline and episode projections. Use approved supersession/reversal semantics without erasing audit history. If an old event is corrected, recompute dependent subsequent state and escalate any invalid downstream prerequisite.
5. Record the projection's actual accepted revision and exact contributing event refs. A proposed new chapter is *hypothetical state only* until an authorized editor accepts it. Before a write, compare the accepted head revision again.
6. Upon revoked usage rights or lawful erasure, execute custodial redaction/tombstone and public-export invalidation under actual policy. Do not disclose restricted history merely to preserve the append-only abstraction.

**Causal invariants:** a stranded person stays stranded until an accepted return/contact/transport event changes that state. A character cannot know a revelation known only in an unaccepted draft. An episode/chapter boundary does not manufacture a team retrieval, healed injury, resolved romance, project completion or challenge release.

### 6.3 Acceptance and canon are different actions

Accepting A's prose revision, accepting proposed continuity deltas, promoting cross-episode canon, approving a real person's portrayal, granting a repository write and authorizing public release are **distinct** decisions with separately recorded scopes/effective times. If the owner accepts only story text, do not infer acceptance of rights, reward transactions, mission technology powers or an altered character canon. A character-specific approved era file outranks a generic unratified Edubeam suggestion. Failed or impossible approval evidence remains pending.

## 7. Public challenge, rights, Service Cards and derivative dependency graph

The current **one** public question is literally the final content of A and its exact approved/public wording is held in `challenge_public_register`, with source A revision, accessibility/fairness, source reference, audience release state and next-episode reveal obligation (or chapter-final human exception). Never put an answer, correct letter, solution rationale, grade rubric revealing the answer or hint in B1–B8, ordinary story metadata, comics or media prompts. `challenge_answer_key` is instantiated only by a separate secure operation with actually verified custodial permissions. Without that store, do **not** generate C. Absence of vault does not by itself prevent a *draft* A, but a competitive publication can remain blocked by owner policy.

The `production_manifest` binds any expressly commissioned comic/image/collage/audio/video/podcast to the exact source A revision and optionally exact public challenge version, comic page/panel or media scene/shot/clip, visual canon version, rights, approved input/output audience and the creator/provider's actual verified settings. Track whether a thing is a *plan*, *prompt*, *rendered asset*, *assembled file*, *validated export* or *published artifact*. A detailed storyboard is not a rendered comic. A text-to-video prompt is not an actual playable export. Include actual checksum, duration, media dimensions or commit ref **only if measured**.

**Dependency chain:** approved calendar/canon/rights/source snapshots → accepted story A revision → challenge version → comic plan/pages/panels → media script/provider prompts → real clips/audio → edit/assembly/captions → human publication. On an upstream story, public challenge, canonical appearance or usage-rights change, identify dependent assets by exact version and mark them `STALE_SOURCE` / `STALE_REVALIDATION_REQUIRED` as the actual implementation permits. Record which assets, cause and responsible reviewer. Do not infer automatic deletion, regenerations, external video credits or verified files. Consent revocation may invalidate media even when story text is unchanged.

`service_card_register` is optional: only a separately commissioned evidence-backed, permission-reviewed, accessible card may be recorded as a product; a suggested card is a proposal. “43 Clues,” QR/Buzz Codes, badges, Palmiers, myCred, rewards, treasure hunts, answer-award automation and tracking are **future integrations subject to separate authorization** and associated privacy/security/eligibility rules. A fictional points award does not create a real transaction.

| **B8 — Validation, exceptions and approval register.** | `validation_report`, `exception_conflict_register`, `editorial_decision_log`, `handover_record` |

**The 15 mandatory B6 informational elements are:**

1. **Identity and revisions:** verified/provisional season/chapter/episode/day IDs, legacy path crosswalk, A revision, editorial state, actual owner reference and effective master/protocol/ledger *document* editions.
2. **Calendar:** requested local production date, approved timezone, weekday, episode #1–#10/day and chapter role day #1–#40 where verified, approved calendar and fit/exception result.
3. **Temporal/spatial snapshot:** P/H/F values and evidence ages/uncertainty; distinct HQ, Enka-present, Enka-historical, lab, Probe destination and deployed-person positions with safe unknowns.
4. **What happened:** accurate recap of the last **accepted** story separated from today's **draft**, with causal consequences and story revision references.
5. **Character projection:** relevant character location/time, knowledge, relationship, obligations, injury if permitted, era capability and source refs; accepted vs proposed changes and rights.
6. **Mission projection:** active/unknown mission roster, temporal coordinates, device charge/comms, last accepted contact, equipment/risk and outstanding retrieval; no invented reset.
7. **Organizational chart/project:** actual aliased role-chart version, chapter working-day check, featured roles and `ACTUAL_VERIFIED` vs `FICTIONAL_STORY` vs `PROPOSAL_ONLY` distinction.
8. **Study and practical learning:** reading week anchor/day assignment status, actual work selected, attributed verse provider/date, genuine H&S course/lesson and qualified source refs.
9. **Research provenance:** verifiable history/current reporting versus `FICTION_PROBE_SCENARIO`, source/event/publication/retrieval-date distinction, geography/weather evidence and omitted research.
10. **Storyline/event changes:** `OPEN`, `ADVANCED`, `RESOLVED`, `DEFERRED` threads; accepted event references, today's proposed changes, hypothetical post-state and pending canon proposals.
11. **Challenge:** nonrevealing public question reference or authorized public wording, source A revision, prior challenge obligation, default next-episode release gate and **opaque** restricted custody status only.
12. **Derivatives/cards:** actual commissioned comic/video/audio/Service Cards, source bindings, visual/rights status, `CURRENT`/`STALE_SOURCE`/`NOT_COMMISSIONED` as applicable; never claim nonexistent rendered assets.
13. **Open exceptions/decisions:** missing evidence, canon/rights/calendar/security conflicts, severity, genuine decision owner and what would resolve each item.
14. **Next eligible working day:** safe accepted opening position, plausible story opportunities, must-preserve character/mission knowledge and refreshed-source tasks; do not assume today's draft was accepted.
15. **Operational truth:** actual A/B artifact/storage references, write/readback/commit evidence if any, editorial/lock/release status, outstanding approvals and recipient permissions.

A new provider must load the actually authorized editions, latest **approved** manifest/events and any later corrections, then the rights-filtered B6 and source records. Do not depend on another model's conversation memory or silently import private diaries/keys. At Chronicle #10 additionally provide ten separately accepted/pending day slots and their real revisions; this is **compilation readiness** only, not automatic compilation or title approval.

## 9. Editorial decisions, exceptions, validation and production statuses

`editorial_decision_log` distinguishes **proposal**, **approval**, **rejection**, **deferral**, **revision request**, **canon promotion**, **storage migration**, **publication** and **challenge release**. Each decision has actual scope, human authorizer/evidence when genuine, effective time, impacted IDs/revisions and follow-up owner. A model suggestion remains a proposal. A user may authorize a narrowly stated draft operation but that does not constitute separate licensing, third-party consent or persistent rights clearance.

`exception_conflict_register` tracks `ADVISORY`, `MATERIAL` and `BLOCKING` issues, cited conflicting source versions/observations, affected day/artifact, missing evidence, responsible owner, safe workaround and `OPEN`/`RESOLVED` disposition. Typical issues: phase gap/short fourth episode, historical Probe misuse, incomplete Bible reading anchor, false verse-provider attribution, wrong role-day, era/canon conflict, unauthorized private diary, insecure challenge custody, duplicate A, two simultaneous ledger editors, stale media, unclear release rights. Do not hide material contradictions behind a generic “pass.”

`validation_report` contains each exact master gate: `Q01_SCOPE`, `Q02_CALENDAR`, `Q03_THREE_CLOCKS`, `Q04_IDENTIFIERS`, `Q05_CANON`, `Q06_ROLE_PROJECT`, `Q07_STUDY`, `Q08_VERSE_HS`, `Q09_RESEARCH`, `Q10_RIGHTS`, `Q11_STORY`, `Q12_CHALLENGE`, `Q13_RECORDS`, `Q14_DERIVATIVES`, `Q15_INTEGRITY`, `Q16_BOUNDARIES`. Each has actual check/run timestamp, checker, source evidence, result (`PASS`, `FAIL`, `NOT_RUN`, `NOT_APPLICABLE`), explanation and remediation. Legacy `BLOCKED` and `NOT_CHECKED` remain observable distinctions and cannot be treated as a pass. Comic C01–C22 and media M01–M30 are specialist checks **only when actually commissioned and performed**, not automatic daily green marks.

Track master §4's independent **process**, **editorial**, **persistence**, **release** and **derivative** status axes for record and handover. Do not compress them into “complete.” A locally generated file can be `DRAFTED_NOT_COMMITTED` while editorial remains `UNREVIEWED`, release `NOT_ELIGIBLE` and derivative `NOT_COMMISSIONED`.

## 10. Safe writes, concurrency, schema migration and rollback

**A daily generation instruction is not an archive write grant.** For an explicitly approved archive change:

1. Verify the actual owner-approved storage implementation, write privilege, ACL and classification; preserve existing IDs and actual paths.
2. Read latest authorized head and `base_revision`; assemble the exact A/B drafts, source/rights evidence and proposed append/supersession deltas. Recheck revoked permissions.
3. Compare the repository/store's current head to `base_revision`. If it changed, set `CONFLICT_REQUIRES_RECONCILIATION`, inspect intervening work and require approved merge/rebase; never force-overwrite accepted text.
4. Perform the supported atomic/transactional or approved change-controlled write. Preserve historical revision and documented rollback; keep restricted and private records out of public destinations.
5. Verify **actual readback** of destination, content/hash, revision and audience permissions. Mark `COMMITTED_VERIFIED` only upon proof. Unperformed or failed writes are `DRAFTED_NOT_COMMITTED` or `WRITE_FAILED`, as truthful. Publication, approval and canon promotion still require **distinct** evidence.
6. For migration, inventory all approved old records, old B3/B7 headings and `calendar_probe_record`; prepare reversible field-by-field source→destination mapping with checks for null reasons, offsets, old pointers, consent and restricted data. Test dual-read, conflict resolution and rollback before approved cutover. A doc version upgrade alone never upgrades deployed `schema_version`.

**Historical mapping:** old B3 role/project data belongs in new B3 alongside character/rights; old B7 permission/editorial data belongs as appropriate in new B2/B3/B7/B8, without dropping legal evidence. Old Probe records preserve their actual captures and field-level missing states through a compatibility alias. Legitimate deletion and revoked-rights procedures follow approved custodial policy with downstream public/derivative review.

## 11. Episode compilation, cross-episode continuity and derivative handoff

`EPISODE_COMPILATION` is separately commissioned **after ten distinct dates** have accepted chronicles, source/identity refs and real approvals. Check for missing/unreviewed days, corrections, open storylines and challenge obligations. Do not generate absent days under a compilation command. Chapter/season rollups derive only from accepted lower-level source records; provisional titles do not become canonical by reaching Day #10. Missions, deployed characters, unresolved relational consequences and reveal obligations persist across weekends and chapter transitions until accepted actions change them.

For an explicitly requested comic/media derivative, provide only the permitted exact A revision (accepted or an expressly commissioned draft), approved canon/visual/rights source state, public challenge wording without an answer, story-to-panel/shot provenance, source and stale flags. Specialist requirements remain in CC-UPMP §§28–35 and actually adopted comic/media companions. The ledger manages trace and lifecycle; it does not itself commission, generate, edit or certify a playable file.

## 12. Required negative and migration regression scenarios

Execute with **clearly identified nonproduction fixtures** or real authorized cases: exactly 19 families and old alias; preserved old Probe payload; B3/B7 migration without rights loss; doc edition different from deployed schema; null plus reason; all Q checks with real outcomes; P/H/F and physical positions independent; weekend/day/phase exception correctly blocked; proposed event excluded from accepted state; rejected event ignored; superseding event preserves old audit; retrospective editorial correction recomputes downstream causality; two concurrent writers reject stale base; character deployed into next episode; unapproved `S00_T05` relabel rejected; real source permission revoked after a comic render; challenge solution absent from all A/B/B6/alt text; no answer-vault claim without verified ACL; Day #10 with one unaccepted day cannot compile; no invented repository commit; receiving provider reconstructs correct state without old conversation; lawful deletion overrides naive event immutability. Record actual inputs, observed outcomes and reviewer in validation; this list is **not evidence** those production tests have already passed.

For each expressly authorized daily chronicle, preserve a truthful episode-owned source/continuity **proposal**, physically distinct internal B1–B8, full fifteen-part safe B6 and exact daily QA. Derive *accepted* world state only from authorized accepted event history; retain correction/rights scope; preserve original IDs and record-family meanings; keep challenge secrets and private content out of normal transfers; track derivative dependencies; report actual—not imagined—approval, storage, rendering and publication. No filesystem migration or release occurs by reading this document.
