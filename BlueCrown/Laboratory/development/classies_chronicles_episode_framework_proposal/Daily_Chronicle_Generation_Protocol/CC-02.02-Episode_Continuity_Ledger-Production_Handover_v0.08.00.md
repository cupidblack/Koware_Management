# 1. PURPOSE AND SCOPE OF DURABLE CONTINUITY

A standard two-week Classies Chronicles episode comprises up to ten individually authored, source-backed Monday–Friday chronicles. To preserve narrative integrity over multi-year story arcs, continuity cannot rely on volatile conversational context, hidden model memories, or loose text summaries.

Continuity is governed by an **event-sourced architecture**:
1. **Immutable History:** Fictional events occurring within the narrative are recorded as immutable causal log entries (`continuity_event_log`). Events are never deleted or modified in place.
2. **Traceable Corrections:** Erroneous historical assertions are corrected by appending superseding correction events that explicitly reference and invalidate earlier event IDs.
3. **Accepted State Projections:** Current canonical story truth is dynamically projected exclusively from **authorized, accepted, non-superseded events**. Draft events produced during daily runs remain isolated proposals until ratified by an authenticated human editor.
4. **Episode Ownership:** Each episode archive owns its local chronicle texts, research registers, event logs, and handover states. Shared franchise canon is updated only through explicit human promotion.
5. **Cross-Provider Portability:** The state contract guarantees that an episode drafted by one AI platform (e.g., Gemini) can be resumed seamlessly by another (e.g., Claude, GPT, Copilot, or a human writer) without loss of continuity or context drift.

```text

│                      EVENT SOURCING ARCHITECTURE                       │
│                                                                        │
│   [ Event E01 ] ──► [ Event E02 ] ──► [ Event E03 ] ──► [ Event E04 ]  │

```

# 2. GOVERNANCE, OWNERSHIP AND ACCESS PARTITION

The continuity framework enforces strict boundaries between different data custodians and access classifications:

## 2.1 Custodian Responsibilities

| Custodian / Subsystem | Authorized Scope & Responsibilities | Forbidden Assumptions & Inferences |
|---|---|---|
| **Ratified Franchise Canon** | Durable franchise-wide world laws, character backstories, core technologies, and visual bibles. | A daily fictional draft never alters or expands locked franchise canon without human approval. |
| **Persistent `CC_AI_DESK`** | Reusable master prompts, operational runbooks, record schemas, validation harnesses, and crosswalk indexes. | The AI Desk does not own episode stories, operational logs, or personal private diaries. |
| **Approved Episode Archive** | Episode manifests, chronicle revisions, research registers, source snapshots, event logs, and handovers. | A proposed logical schema does not authorize arbitrary filesystem restructuring or file renaming. |
| **Koware Business Owners** | Real-world organizational chart, departmental roles, actual project documentation, and business accomplishments. | Fictional narrative success never proves that real-world business milestones were achieved. |
| **Restricted Custody Vault** | Challenge solution keys, sensitive grading rubrics, and access-restricted editorial credentials. | Ordinary chat threads, Markdown headings, public repos, or files labeled "restricted" **are not secure**. |
| **Authorized Human Editor** | Acceptance, locking, title finalization, canon promotions, depiction permissions, and publication sign-off. | An AI system can **never** approve, lock, promote, or publish content on behalf of a human editor. |

## 2.2 Access Classification Partitions
Every record family, section, and individual field is assigned one of three security classifications:
* **`PUBLIC`:** Eligible for public distribution following human editorial approval (e.g., Output A, public challenge questions).
* **`INTERNAL`:** Restricted to production collaborators, editorial staff, and approved automation (e.g., Output B1–B8, research registers, mission states, continuity event logs).
* **`RESTRICTED`:** Strictly isolated to authenticated, access-controlled channels (e.g., `challenge_answer_key`, private personal diary excerpts, sensitive security credentials).

# 3. RECORD ENCODING, IDENTITY, VERSIONS AND EVIDENCE CLASSES

## 3.1 Common Logical Envelope Schema
Every instantiated record within the continuity framework must implement the thirteen core envelope attributes:

```yaml
record_id: "CC-E01-C01-EVT-001"            # Unique identifier within governed scope
record_type: "continuity_event_log"        # One of the 19 canonical families
schema_id: "CC-ECLPM"                      # Canonical logical schema ID
schema_version: "v0.08.00"                 # Schema version (distinct from prompt version)
episode_id: "CC-CH01-E01"                  # Verified parent episode identifier
chronicle_id: "CC-CH01-E01-C01"            # Verified parent chronicle identifier (or null with reason)
record_version: 1                          # Integer sequence version of this record
record_status: "DRAFT"                     # DRAFT | AWAITING_REVIEW | ACCEPTED | LOCKED | SUPERSEDED
storage_status: "DRAFTED_NOT_COMMITTED"    # UNSAVED | DRAFTED_NOT_COMMITTED | COMMITTED_VERIFIED
created_at: "2026-11-09T14:30:00Z"         # ISO-8601 instant with timezone offset
classification: "INTERNAL"                 # PUBLIC | INTERNAL | RESTRICTED
evidence_class: "NEW_FICTIONAL_DRAFT"      # One of the 8 canonical evidence classes
source_refs: ["CC-SRC-20261109-001"]       # Explicit references to underlying evidence
```

*Rule on Missing Values:* Unknown values must be represented as explicit typed `null` accompanied by a documented status reason (e.g., `UNVERIFIED`, `INACCESSIBLE`, `NOT_APPLICABLE`, `AWAITING_EDITORIAL_DECISION`). The operator must never invent plausible filler to populate empty fields.

## 3.2 Canonical Evidence Classes
Every claim, event, and record must be classified into exactly one of eight evidence classes:

| Evidence Class | Operational Semantics & Usage Criteria |
|---|---|
| `APPROVED_CANON` | Ratified franchise lore, character bibles, core technology mechanics, and locked historical continuity. |
| `PRIOR_DOCUMENTED_EVENT` | Fictional event accepted and locked in a previous approved chronicle within the same or earlier episodes. |
| `VERIFIED_REAL_WORLD_FACT` | Real-world factual data verified through primary documentary research, news reports, or academic sources. |
| `HISTORICAL_INTERPRETATION` | Scholarly commentary, historical analysis, or philosophical critique regarding real-world events. |
| `NEW_FICTIONAL_DRAFT` | Imaginative narrative scenes, dialogue, and character actions introduced in the current draft chronicle. |
| `PROPOSED_CANON_CHANGE` | Narrative innovations that introduce new capabilities, lore, or world rules, pending human canon review. |
| `FICTION_PROBE_SCENARIO` | Speculative, future, or alternate-timeline telemetry and narrative events derived from Edubeam probe scenes. |
| `UNVERIFIED_EXCLUDED` | Claims, lore, or sources that failed verification or lacked depiction permissions, excluded from the story. |

## 3.3 Dates, Retrievals and Correction Semantics
1. **Four Independent Time Dimensions:**  
   * **Event Date:** The date when an event occurred within the narrative or real world.
   * **Publication Date:** The date when a source document was publicly issued.
   * **Retrieval Instant:** The exact timestamp (with offset) when the operator accessed the source.
   * **Production Date:** The civil calendar date of the requested production day.
2. **Append-Only Corrections:** When an accepted event or record is found to be erroneous, the operator must append a new event specifying `supersedes_event_id: "..."` and detail the correction rationale.
3. **Concurrency & Revisions:** Before committing updates, verify that the `base_revision` matches the current repository head. If a concurrent write has occurred, re-read and reconcile deltas rather than blindly overwriting.

# 5. EPISODE, CALENDAR AND DAILY STORY CONTRACTS

## 5.1 Episode Manifest and Context Snapshot
* `episode_manifest` maintains approved parent chapter identity (`CC-CH01` through `CC-CH05`), episode ordinal (`1` through `4`), calendar start (Monday week 1) and end (Friday week 2), approved production timezone, and title approval state (`PROVISIONAL` until Chronicle #10 is accepted).
* `episode_context_snapshot` records the state of narrative play as of the current draft. It freezes the active plot premises, known historical facts, and approved world constraints.

## 5.2 Three Clocks and Location Derivation
The ledger records source evidence for the three independent clocks:
* **Clock P (Production):** Requested production date, civil calendar day, and approved timezone (Africa/Accra).
* **Clock H (Historical):** Target historical date, geographic location, and archival documentary source.
* **Clock F (Probe Destination):** Probe timestamp, era, destination coordinates, and telemetry payload.
* **Locations:** Entity positions must be tracked independently: Enka (Clock P), Enka (Clock H), Koware HQ, Laboratory, Probe Target, and deployed team members.

## 5.3 Daily Chronicle Record
Records metadata for exactly one daily story:
* Identifier: `CC-CH01-E01-C01` through `CC-CH05-E04-C10`.
* Production Date and Weekday (Monday–Friday).
* Episode Chronicle Number ($1 \dots 10$) and Chapter Working Day ($1 \dots 40$).
* Word Count, Estimated Reading Time, and Story Revision Hash.
* Editorial Status (`UNREVIEWED`, `CHANGES_REQUESTED`, `ACCEPTED`, `LOCKED`).
* Persistence Status (`DRAFTED_NOT_COMMITTED`, `COMMITTED_VERIFIED`).

# 6. EVENT SOURCING, CHARACTER, MISSION AND ROLE CONTROLS

## 6.1 `continuity_event_log` — Append-Only Narrative Events
Every material narrative change must generate an event entry:
```yaml
event_id: "CC-E01-C01-EVT-004"
parent_chronicle: "CC-CH01-E01-C01"
story_clock: "Clock P"
story_time: "2026-11-09T14:15:00"
location: "Koware HQ, Lab Wing B"
characters_present: ["Enka", "Kofi", "Dr. Mensah"]
event_summary: "Calibration test on Probe Array Gamma reveals frequency drift."
causal_antecedents: ["CC-E01-C01-EVT-002"]
consequences: ["Probe deployment delayed by two hours; team placed on standby."]
supersedes_event_id: null
evidence_class: "NEW_FICTIONAL_DRAFT"
status: "PROPOSED"
```

## 6.2 `character_state_record`
Tracks character evolution across episodes:
* Physical Location and Local Time.
* Personal Knowledge Gates: Explicitly records what the character has seen, heard, or deduced. Differentiates eyewitness knowledge from hearsay.
* Emotional & Relational Deltas: Changes in trust, tension, or alignment.
* Era Capability Limits: Enforces canonical power constraints (e.g., early-era Enka capabilities).
* Personal Privacy Protection: Private personal diary details must never be recorded in public or unredacted character state fields without explicit consent.

## 6.3 `mission_state_record`
Governs active Edubeam missions:
* Mission ID, Codename, and Target Coordinates (Era / Location).
* Operational Stage: `PLANNED`, `PREPARING`, `CALIBRATING`, `DEPLOYING`, `DEPLOYED`, `INVESTIGATING`, `OUT_OF_COMMUNICATION`, `RETRIEVING`, `RETURNING`, `DEBRIEFING`, `ON_HOLD`, `CLOSED`.
* Deployed Field Roster vs. HQ Support Personnel.
* Equipment, Energy Limits, and Communication Status.
* Open Retrieval Commitments: A deployed team remains deployed until a source-backed, earned retrieval event occurs. **No automatic mission resets.**

## 6.4 `role_project_log`
Tracks workplace authenticity:
* Chapter Working Day ($1 \dots 40$).
* Scheduled Role Checks against the Koware organizational chart.
* Featured Roles: Spotlight 1–2 roles (maximum 4; 5 requires an authorized exception).
* Strict Activity Categorization: `DOCUMENTED_ACTUAL`, `FICTIONAL_SCENE`, `PROPOSAL_FOR_REAL_REVIEW`.

## 6.5 `storyline_register`
Tracks individual narrative arcs:
* Storyline ID, Title, and Thematic Purpose.
* Origin Chronicle and Origin Event ID.
* Status: `OPEN`, `ADVANCED`, `RESOLVED`, `DEFERRED`, `DISPUTED`.
* Causal Dependencies and Open Payoff Commitments.

# 7. CLAIM-LEVEL RESEARCH AND PERMISSIONS

## 7.1 `research_register`
Captures granular research claims across the six passes:
* Claim ID, Stage Pass (1–6), and Temporal Stream (H, P, F).
* Exact Source Citation: Title, Author, Publisher, URI/Path, Edition/Revision.
* Temporal Distinction: Event Date, Article Publication Date, and Retrieval Instant.
* Evidence Class: `VERIFIED_REAL_WORLD_FACT`, `HISTORICAL_INTERPRETATION`, or `FICTION_PROBE_SCENARIO`.
* Narrative Integration: Story beat or dialogue passage influenced.

## 7.2 `source_permission_register`
Enforces the four-level permission model:
* Target Entity / Source Reference.
* Proposed Scope: Research, Internal Analysis, Fictional Inspiration, Public Portrayal, Direct Quotation, Visual Adaptation.
* Rights & Consent States: `GRANTED`, `LIMITED`, `WITHDRAWN`, `NOT_REQUIRED`, `UNKNOWN`.
* Verification Evidence: License identifier, written consent document, or public domain verification.
* Revocation Protocol: If consent is withdrawn, flag affected story segments and derivative assets immediately for revalidation or withdrawal.

# 8. CHALLENGE, DERIVATIVE AND SERVICE CARD CONTRACTS

## 8.1 `challenge_public_register`
Stores public-facing challenge data:
* Challenge ID and Parent Chronicle ID.
* Exact Public Question Wording and Educational Objectives.
* Fairness & Answerability Criteria (anchored in narrative or public research).
* Solution Release Schedule: Default release is scheduled with the **next episode's public release**, never the next daily chronicle. Chapter-final exceptions require human approval.
* Custody Pointer: Opaque reference to the restricted vault location; **no answer text or hints**.

## 8.2 `challenge_answer_key` — RESTRICTED ONLY
Stores the solution in an authenticated, access-controlled vault:
* Exact Answer, Derivation, and Explanatory Rationale.
* Acceptable Alternative Phrasings and Common Misconceptions.
* Source Citations Supporting the Solution.
* Author / Reviewer Identity and Human Approval Reference.
* **Strict Isolation Rule:** Must never appear in Output A, Output B, B6 handovers, or ordinary chat.

## 8.3 `production_manifest` and Derivative Invalidation
Tracks derivative adaptations (comics, audio, video, collages):
* Asset ID, Adaptation Type, and Commission Reference.
* Source Chronicle ID and Exact **Source Story Revision Hash**.
* Applied Specialist Prompt Version (`CC-03.xx` Comic / `CC-04.xx` Media).
* Dependency Staleness Invariant:  
  $$\text{Upstream Story Revision Changed} \implies \text{Derivative Status} = \text{STALE\_SOURCE / STALE\_REVALIDATION\_REQUIRED}$$  
  A derivative asset cannot be approved or released if its source text has been revised.

## 8.4 `service_card_register`
Tracks optional, practical 3–5 step actionable guides:
* Topic, Educational / H&S Source Backing, Approved Version, and Release Channel.
* Gamification concepts (QR codes, Buzz Codes, 43 Clues, myCred rewards) remain unratified proposals until independently approved.

# 9. EDITORIAL DECISIONS, CONFLICTS AND VALIDATION

## 9.1 `editorial_decision_log`
Logs every human editorial action:
* Decision ID, Timestamp, and Responsible Human Approver.
* Scope: Story Acceptance, Canon Promotion, Title Finalization, Rights Approval, Answer Release, or Publication Clearance.
* Disposition: `PROPOSAL`, `APPROVED`, `REJECTED`, `CHANGES_REQUESTED`.

## 9.2 `exception_conflict_register`
Logs unresolved issues:
* Exception ID, Date, and Severity Level (`CRITICAL`, `MAJOR`, `MINOR`).
* Category: Calendar Mismatch, Canon Conflict, Missing Source, Rights Ambiguity, or Concurrency Collision.

## 9.3 `validation_report`
Preserves immutable QA verification records:
* Report ID, Chronicle ID, Evaluator (Human / Automated Agent), and Timestamp.
* Detailed Evaluations for Quality Gates `Q01` through `Q16` (Daily), `C01` through `C22` (Comic), or `M01` through `M30` (Media).
* Overall Disposition: `PASS`, `PASS_WITH_EXCEPTIONS`, or `FAIL_BLOCKED`.

# 11. PORTABLE B6 HANDOVER CONTRACT

The `B6. Portable production handover` is the critical operational contract that enables seamless, stateless handover across disparate AI models, automated agents, and human writers. B6 must contain **all information necessary to resume production without conversational memory**.

Every instantiated B6 handover must include the **fifteen mandatory sections**:

1. **Chronicle Identifiers & Hierarchy:** Verified Season, Chapter, Episode, and Chronicle IDs; physical archive path; story revision hash; and current editorial status.
2. **Calendar & Production Coordinates:** Requested local date, weekday, episode chronicle number ($1 \dots 10$), chapter working day ($1 \dots 40$), approved timezone, and calendar validation status.
3. **Three Clocks & Physical Locations:** Sourced Clocks P, H, and F (with offsets and timestamps); distinct physical locations for Enka (P), Enka (H), Koware HQ, Lab, Probe Target, and deployed roster.
4. **Narrative Summary of Realized Events:** Objective summary of what actually transpired in the chronicle and immediate causal consequences (not predictions or outlines).
5. **Character Positions & Knowledge Boundaries:** Current coordinates, emotional states, relationship deltas, and precise knowledge limits for all featured cast.
6. **Active Edubeam Mission State:** Operational stage, field roster, HQ team, equipment energy, communication link status, and open retrieval commitments.
7. **Koware Workplace & Role Check Log:** Chart revision, chapter working day ($1 \dots 40$) role check result, featured roles, and categorized business activities.
8. **Research & Source Backing:** Core citations for reading plan, dated verse, Buzzjuice H&S lesson, and documentary news sources.
9. **Fact vs. Fiction Demarcation:** Explicit delineation of verified real-world facts, historical interpretations, and labeled fictional probe scenarios.
10. **Storyline Dynamics & Event Deltas:** Status of all open, advanced, resolved, and deferred storylines; new event IDs added to the append-only ledger.
11. **Public Audience Challenge:** Exact public question wording, learning objective, and non-revealing custody status pointer (zero answers).
12. **Derivative Adaptation Status:** Upstream text revision hash, status of commissioned comics/videos, and dependency staleness flags.
13. **Active Exceptions & Open Decisions:** Unresolved sources, canon questions, or rights ambiguities, severity levels, and assigned human owners.
14. **Next Production Day Starting Baseline:** Sourced starting constraints, eligible production date, next chronicle number, and continuity boundaries for the subsequent run.
15. **Storage, Commit and Approval Verification:** Explicit persistence status (`DRAFTED_NOT_COMMITTED` or `COMMITTED_VERIFIED` with commit hash/URI) and human approval status.

*Chronicle #10 Special Handover Rule:* When compiling Chronicle #10, B6 must state `EPISODE_COMPILATION_READY`, list the acceptance status of all ten daily installments, and halt. Do not automatically compile, finalize titles, or retrieve deployed field teams.

# 12. RECONCILIATION, CONCURRENCY AND PERSISTENCE

1. **Optimistic Concurrency Control:** Every read operation pins the `base_revision` hash. When preparing a write, verify that the storage target has not been updated by another process. If a collision occurs, execute a three-way merge or escalate to an editor.
2. **Delta Generation:** Write only newly created events, claim entries, and record revisions; never overwrite past historical entries.
3. **Write Verification:** A write is recognized as `COMMITTED_VERIFIED` only upon successful API return containing a commit SHA, transaction ID, or filesystem readback verification. Otherwise, status remains `DRAFTED_NOT_COMMITTED`.
4. **Data Retention and Privacy Compliance:** Legitimate legal, privacy, and consent revocation erasures supersede append-only story conventions. Erasures must be executed by authorized custodians with full audit logging.

---

# 13. EPISODE COMPLETION AND CONTROLLED ROLL-UP

1. **Prerequisites for Compilation:** An episode compilation (`EPISODE_COMPILATION`) may be initiated **only** after ten distinct, correctly dated chronicles are individually marked `ACCEPTED` by a human editor.
2. **Provisional Titling:** Daily and episode titles remain provisional until the full episode is compiled and approved by an authorized human editor.
3. **No Automatic Infill:** If an episode contains missing chronicle slots (e.g., only 8 of 10 days written), the system must halt and report missing days. Never generate uncommissioned chronicles to fill gaps.
4. **Higher-Level Roll-Ups:** Chapter roll-ups (4 episodes / 40 days) and season roll-ups (5 chapters / 200 days) must derive strictly from accepted lower-level episode ledgers.

# 14. BACKWARD COMPATIBILITY, MIGRATIONS AND RETENTION

1. **Preservation of Legacy Assets:** Maintain complete backward compatibility with v0.02.00, v0.03.01, and v0.04.00 records. Never destroy or rename legacy files (`S00_T05`, `E01`, `TP`, `CH`).
2. **Bidirectional Identifier Crosswalk:** Maintain an authoritative crosswalk mapping legacy folder structures to v0.08.00 canonical IDs.
3. **Legacy Section Mapping:** Old B3 (Role/Project) maps to new B3 (Character/Role/Project); old B7 (Rights/Editorial) maps across B2, B3, B7, and B8.
