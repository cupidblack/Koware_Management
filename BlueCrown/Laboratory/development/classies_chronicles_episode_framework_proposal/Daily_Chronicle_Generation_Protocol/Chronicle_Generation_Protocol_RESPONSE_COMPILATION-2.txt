## 1. Purpose, boundaries and execution states

The Unified Production Master Prompt defines the creative, authority, canon, calendar, research and output contracts. This protocol defines the order of work, preflight checks, stopping conditions and handover procedure for a daily chronicle. The Episode Continuity Ledger defines durable record meaning and ownership.

A standard daily run is:

**One authorized date → one source-grounded evidence set → one Output A draft → a separate internal Output B → truthful validation and handover.**

Output C is not part of an ordinary response. It may be created only under the master’s explicit authorization and verified restricted-custody requirements.

### 1.1 Request classification

Use the mode names defined by the master. In particular:

- `REVIEW_ONLY` means documentation work only; do not generate a chronicle.
- `DAILY_CHRONICLE` means exactly one eligible daily chronicle.
- `DAILY_REVISION` means a new draft revision of an identified chronicle, not silent replacement of an accepted version.
- `EPISODE_COMPILATION` and `CHAPTER_OR_SEASON_ROLLUP` are separately commissioned operations.
- Comic and audiovisual modes are separately commissioned derivatives governed by their specialist prompts.
- `ARCHIVE_WRITE` requires actual authorization, write capability, an approved destination and revision-conflict handling.

When the request does not clearly authorize a daily chronicle, do not infer that it does.

### 1.2 Process states

Use the master’s process statuses and keep them separate from editorial, persistence, release and derivative statuses:

| Process state | Meaning |
|---|---|
| `REQUEST_CLASSIFIED` | Mode, scope and requested production date have been identified. |
| `PREFLIGHT` | Applicable sources, authority, permissions and prior continuity are being checked. |
| `GO` | Essential requirements are verified. |
| `GO_WITH_OMISSIONS` | Essential requirements are met; nonessential missing material will be omitted and disclosed. |
| `BLOCKED` | An essential date, authority, permission, canon or evidence dependency remains unresolved. |
| `EVIDENCE_LOCKED_FOR_DRAFT` | The evidence and chronology used for this draft are identified and pinned. |
| `DRAFTED` | Candidate Output A and, where authorized, separate Output B have been prepared. |
| `AWAITING_EDITORIAL_REVIEW` | Draft is awaiting an actual authorized human decision. |

Do not treat `DRAFTED`, `COMMITTED`, `ACCEPTED`, `LOCKED`, `RELEASE_ELIGIBLE`, `PUBLICATION_AUTHORIZED` and `PUBLISHED_VERIFIED` as interchangeable or as automatic steps in a single workflow.

---

## 2. Phase 0 — establish scope and authority

Before retrieving or writing:

1. Confirm that the user requests `DAILY_CHRONICLE`, not review, revision, compilation or a derivative.
2. Identify the requested production date. If the user says “today,” resolve it using the approved production timezone, not the system’s assumed timezone or Probe clock.
3. Identify the authorized output surface and recipient. Do not send internal or restricted information into an unapproved public destination.
4. Record the governing document versions and their actual approval status. Treat v0.08.00 as a proposed working baseline unless an authorized adoption record is available.
5. Confirm that the request does not presume access to private diaries, accounts, calendars, organization records, source material or restricted answer storage that has not actually been granted.
6. Determine whether the request is for a definitive draft or an explicitly authorized provisional draft. A provisional designation does not waive privacy, rights, safety or locked-canon requirements.

**Stop** if the operation, essential authority or recipient boundaries cannot be established.

---

## 3. Phase 1 — source inventory and preflight

Actually retrieve material used in the story. A URL, search snippet, filename, directory listing or prior model statement does not prove that the linked content was read.

Record, as applicable, the actual URI or path, source owner, version or revision, retrieval result, retrieval time, source status, intended use and limitations.

### 3.1 Preflight source groups

| Source group | Purpose | Missing-source handling |
|---|---|---|
| Approved effective-dated calendar, production timezone, episode manifest and ID crosswalk | Establish eligible production date, episode position, full episode span and existing identifiers. | Block a definitive assignment if the correct slot cannot be established. |
| Current approved governance and applicable character, world and Edubeam canon | Respect authority, identity, era and capability constraints. | Block a central unresolved conflict; omit or qualify noncentral unsupported elements. |
| Latest accepted chronicle, current episode state, event history and portable B6 | Preserve story events, character knowledge, locations and open missions. | Record the gap; block only if it prevents a coherent, safe and continuity-consistent story. |
| Current organizational chart, aliases and role-check schedule | Identify relevant people and chapter working-day checks. | Omit unsupported names or role claims; do not invent chart content. |
| Koware project and activity sources | Distinguish documented real activity from fictional scenes and proposals. | Do not imply that undocumented business work occurred. |
| Character canon and publication permissions | Establish character identity, abilities, appearance and eligible use. | Exclude material without required permission; block central uses that cannot safely be replaced. |
| Diary material, if relevant | Inform story context where access and intended use are authorized. | Access does not grant publication permission; omit when use is not authorized. |
| Eternal Dreamfall plan and approved date-to-reading mapping | Select the actual weekly item. | Do not invent a current week, daily assignment or missing text. |
| Date-specific Verse of the Day | Attribute the verse and provider accurately. | Use an allowed, accurately attributed alternative only when appropriate; otherwise disclose omission. |
| Actual Buzzjuice Health & Safety course or lesson | Support a real course-related claim. | Do not invent a course, lesson or instruction. |
| Historical, current and destination reporting | Support factual claims across the three time streams. | Omit nonessential unsupported claims; classify speculative future content as fiction. |
| Relevant public challenge record | Check public wording and any applicable editorial status. | Do not inspect restricted answers. Report a material wording conflict. |
| Derivative records | Identify possible stale comics or media if the run concerns them. | Mark not applicable when no derivative is commissioned. |

Follow necessary links within acquired material when accessible and authorized. If a GitHub `blob` link is unavailable, try the matching raw URL using the actual repository, branch and path. Do not invent paths or filenames.

### 3.2 Go/no-go decision

- **`GO`:** date and episode position are established; applicable canon and essential permissions are reconciled; required central evidence is available.
- **`GO_WITH_OMISSIONS`:** only optional or noncentral sources are missing. Omit unsupported elements and log the omissions.
- **`BLOCKED`:** essential calendar assignment, authority, permission, source or locked-canon reconciliation is unresolved.

A blocked report states the requested date and verified timezone if available, exact unresolved dependency, what was actually checked, the material risk and the specific evidence or human decision needed.

For each actual retrieval, record the source URL, actual retrieval time and timezone offset when available, request outcome, fields actually returned, missing or malformed fields, and the original response or an authorized immutable evidence reference.

A live Probe result is not an approved historical calendar. Do not use a present-day payload as if it were retrieved on a historical production date. Do not infer missing fields.

Record relevant locations separately: Enka’s current location, Enka’s historical-reference location, Koware headquarters, the laboratory where relevant, the Probe destination and every active team member’s location.

## 5. Phase 3 — resolve the production date and identifiers

Use the approved calendar and manifest first. Only apply the master’s first-Monday and fourteen-calendar-day calculation when the approved calendar explicitly authorizes it and its dates, timezone and episode structure are verified.

Validate:

1. The requested local date and timezone.
2. The approved phase boundary and its stated end-date convention.
3. The first Monday anchor, where authorized.
4. The fourteen-day block and weekday position.
5. The chronicle number, if the date is an eligible working day.
6. The chapter working day, independently of episode chronicle number.
7. The episode’s Monday start and second-Friday end.
8. The complete episode span against the approved phase.
9. The approved episode slot and actual archive ID/path crosswalk.
10. Duplicate-day or conflicting assignments.

The normal mapping is:

- Block positions 0–4 → Chronicle #1–#5.
- Block positions 5–6 → weekend; no normal chronicle.
- Block positions 7–11 → Chronicle #6–#10.
- Block positions 12–13 → weekend; no normal chronicle.
- `chapter_working_day = 10 × (episode_ordinal − 1) + chronicle_ordinal`.

Do not equate Probe `phase_index` with chapter, term or archive IDs. Do not rename or migrate identifiers. A weekend, unallocated gap, incomplete episode, phase-boundary conflict or absent crosswalk is an exception, not an invitation to guess.

## 6. Phase 4 — reconcile continuity and roles

Before imagining new events, read the latest applicable accepted story and current approved corrections. Distinguish accepted history from drafts and proposals.

Prepare an internal state-of-play covering:

1. Episode premise, accepted events and open, deferred or resolved threads.
2. Active characters, identities, locations, relationships, knowledge and applicable capability limits.
3. Mission identity, team roster, individual locations, mission stage, destination, equipment, communication, risks and retrieval obligations.
4. Current role-chart source and chapter working-day check; do not substitute episode day 1–10 for chapter working day 1–40.
5. Documented Koware work versus `FICTIONAL_SCENE` and `PROPOSAL_FOR_REAL_REVIEW`.
6. Relevant character-canon references, use permissions and unresolved decisions.

Normally feature one or two relevant organizational roles. Four is the ordinary maximum; a fifth requires an authorized exception. Use documented aliases and names.

Do not automatically return a deployed team, reset a mission, grant knowledge or change a relationship. Keep proposed story corrections separate from accepted continuity.

## 7. Phase 5 — complete the six research passes

Perform the master’s six stages as cumulative internal passes, not as six public retellings:

1. **Eternal Dreamfall Bible Study:** verify the actual plan item and approved date-to-week mapping; identify the source category accurately.
2. **Eternal Dreamfall Chronicle:** verify the date-specific verse and actual provider, or accurately attribute an allowed alternative.
3. **Refreshed Eternal Dreamfall:** inspect the actual relevant Health & Safety source and cite the real lesson or topic.
4. **Headlined Eternal Dreamfall:** research historical, current and Probe streams separately; distinguish facts from interpretation and fictional projection.
5. **Classies Eternal Dreamfall:** reconcile approved archives, continuity, character state and authorized diary material.
6. **Classies Chronicles:** create one original story integrating relevant evidence, characters, organization and consequences.

Treat headline counts as research ambitions, not output quotas. Do not invent headlines, Bible-plan mappings, verse attributions, lessons, telemetry or weather.

Log selected claims and their sources in B2. Note source dates, locations, factual or fictional classification, permissions and material omissions.

## 8. Phase 6 — compose Output A

Prepare a private outline with the established date and identifiers, setting and story clock, viewpoint, central need or choice, source-backed constraints, continuity state, causal progression and terminal challenge.

Write one original, coherent and emotionally credible chronicle. Ordinary reading time is approximately three to five minutes unless the commission warrants otherwise. Let daily routines, faith, education, safety, research, community and work enter naturally; do not turn them into a compulsory checklist.

The audience challenge is the last public-facing element of Output A. Do not append citations, a ledger, technical notes, an answer or explanation after it.

## 1. Purpose and scope

The ledger preserves what a chronicle actually states, the evidence used to create it, the proposed or accepted continuity changes and the production state needed for the next authorized operation.

The record system supports event-sourced continuity:

- Retain source-backed events and corrections as history.
- Separate proposed events from accepted events.
- Derive current accepted state only from authorized, non-superseded events.
- Keep episode records distinct from reusable prompts and schemas.
- Carry forward only state whose status and authority are clear.

A regular two-week episode has up to ten separately commissioned weekday chronicles. A chronicle does not, by itself, complete or publish an episode. Chapter, season and franchise roll-ups require their own authorized review.

## 2. Ownership and access classification

- Actual season, chapter, episode and chronicle IDs, with existing legacy identifiers preserved.
- Actual source URI/path, source revision and base revision, when known.
- Record status and storage status as independent values.
- Real creation or update time only when the action occurred.
- Author or responsible human editor only when actually identified.
- Source references, access classification and permission evidence.
- Change reason and the record or event superseded, if applicable.
- Approval reference only when a real authorized decision exists.
- Exception references for unresolved source, rights, calendar or canon issues.

Unknown structured values may be represented as typed `null` only when accompanied by an explicit missing status and reason. Narrative records use statuses such as `UNVERIFIED`, `INACCESSIBLE`, `NOT_APPLICABLE`, `NOT_AUTHORIZED` or `AWAITING_EDITORIAL_DECISION`, with a reason. ### 3.2 Dates, retrievals and corrections

- Preserve actual source retrievals and relevant payloads or authorized immutable references.
- Treat source snapshots and event history as append-only subject to applicable retention, privacy and legal requirements.
- Correct a record by adding a traceable superseding revision or event, not by silently changing accepted history.
- Before an authorized write, compare the proposed base revision with the current stored revision. Re-read and reconcile conflicts rather than overwriting them.

# 5. PHASE 3 — RESOLVE CALENDAR DAY, EPISODE AND IDENTIFIERS

The operator must resolve and validate calendar position using the approved effective-dated manifest first. Only when the manifest authorizes derivation, execute the deterministic calendar algorithm:

## 5.1 Calendar Resolution Algorithm
Given an approved phase start instant and phase end instant in the approved production timezone:

$$\text{anchor} = \text{first Monday on or after } \text{local\_phase\_start}$$
$$\text{elapsed\_days} = \text{target\_local\_date} - \text{anchor} \quad (\text{measured in whole civil calendar days})$$
$$\text{episode\_ordinal} = \lfloor \text{elapsed\_days} / 14 \rfloor + 1$$
$$\text{block\_day} = \text{elapsed\_days} \pmod{14}$$

### Block Day Mapping:
* $\text{block\_day} \in [0, 4] \implies \text{chronicle\_number} = \text{block\_day} + 1 \quad (\text{Week 1: Monday–Friday, Chronicles \#1–\#5})$
* $\text{block\_day} \in [5, 6] \implies \text{Weekend; no regular chronicle scheduled}$
* $\text{block\_day} \in [7, 11] \implies \text{chronicle\_number} = \text{block\_day} - 1 \quad (\text{Week 2: Monday–Friday, Chronicles \#6–\#10})$
* $\text{block\_day} \in [12, 13] \implies \text{Weekend; no regular chronicle scheduled}$

### Chapter Working Day Formula:
$$\text{chapter\_working\_day} = 10 \times (\text{episode\_ordinal} - 1) + \text{chronicle\_number}$$
* Episode 1: Chronicles \#1–\#10 $\implies$ Chapter Working Days 1–10.
* Episode 2: Chronicles \#1–\#10 $\implies$ Chapter Working Days 11–20.
* Episode 3: Chronicles \#1–\#10 $\implies$ Chapter Working Days 21–30.
* Episode 4: Chronicles \#1–\#10 $\implies$ Chapter Working Days 31–40.

$$\text{episode\_start} = \text{anchor} + 14 \times (\text{episode\_ordinal} - 1)$$
$$\text{episode\_end} = \text{episode\_start} + 11 \text{ calendar days (second Friday)}$$

## 5.2 Calendar Validation Invariants
The operator must verify:
1. Target date falls strictly within the approved phase boundaries.
2. $\text{elapsed\_days} \ge 0$.
3. $\text{episode\_ordinal} \in \{1, 2, 3, 4\}$ (each chapter consists of exactly four complete episodes).
4. The full 12-day episode span (Monday week 1 through Friday week 2, including the intervening weekend) fits completely within the phase boundary.
5. $\text{chronicle\_number} \in \{1, \dots, 10\}$ and $\text{chapter\_working\_day} \in \{1, \dots, 40\}$.
6. Calendar dates govern calculations; daylight saving transitions or midnight offsets must never alter day indices.

## 5.3 Identifier Integrity and Legacy Crosswalk
The operator must preserve existing physical archive paths and legacy identifiers:
* Maintain bidirectional crosswalk between new logical identifiers (`CC-CH01-E01-C01`) and legacy filesystem structures (`S00_T05`, `E01`, `TP`, `CH`).
* Never perform bulk renaming of legacy files or directories.
* Probe telemetry `phase_index` does not automatically equal Chapter or Archive ID.
* Chronicle \#10 indicates episode drafting completion; it **does not** authorize automatic compilation, final titling, or team retrieval.

# 1. PURPOSE AND SCOPE OF DURABLE CONTINUITY

A standard two-week Classies Chronicles episode comprises up to ten individually authored, source-backed Monday–Friday chronicles. To preserve narrative integrity over multi-year story arcs, continuity cannot rely on volatile conversational context, hidden model memories, or loose text summaries.

Continuity is governed by an **event-sourced architecture**:
1. **Immutable History:** Fictional events occurring within the narrative are recorded as immutable causal log entries (`continuity_event_log`). Events are never deleted or modified in place.
2. **Traceable Corrections:** Erroneous historical assertions are corrected by appending superseding correction events that explicitly reference and invalidate earlier event IDs.
3. **Accepted State Projections:** Current canonical story truth is dynamically projected exclusively from **authorized, accepted, non-superseded events**. Draft events produced during daily runs remain isolated proposals until ratified by an authenticated human editor.
4. **Episode Ownership:** Each episode archive owns its local chronicle texts, research registers, event logs, and handover states. Shared franchise canon is updated only through explicit human promotion.
5. **Cross-Provider Portability:** The state contract guarantees that an episode drafted by one AI platform (e.g., Gemini) can be resumed seamlessly by another (e.g., Claude, GPT, Copilot, or a human writer) without loss of continuity or context drift.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                      EVENT SOURCING ARCHITECTURE                       │
│                                                                        │
│   [ Event E01 ] ──► [ Event E02 ] ──► [ Event E03 ] ──► [ Event E04 ]  │
│   (Immutable)       (Immutable)       (Superseded)      (Correction)   │
│                                            │                  │        │
│                                            └──────────────────┘        │
│                                                                        │
│   DYNAMIC PROJECTION:                                                  │
│   Accepted State = Project( Approved Events - Superseded Events )      │
└────────────────────────────────────────────────────────────────────────┘
```

# 11. PORTABLE B6 HANDOVER CONTRACT

The `B6. Portable production handover` is the critical operational contract that enables seamless, stateless handover across disparate AI models, automated agents, and human writers. B6 must contain **all information necessary to resume production without conversational memory**.

Every instantiated B6 handover must include the **fifteen mandatory sections**:

1. **Chronicle Identifiers & Hierarchy:** Verified Season, Chapter, Episode, and Chronicle IDs; physical archive path; story revision hash; and current editorial status.
2. **Calendar & Production Coordinates:** Requested local date, weekday, episode chronicle number ($1 \dots 10$), chapter working day ($1 \dots 40$), approved timezone, and calendar validation status.
3. **Three Clocks & Physical Locations:** Sourced Clocks P, H, and F (with offsets and timestamps); distinct physical locations for Enka (P), Enka (H), Koware HQ, Lab, Probe Target, and deployed roster.

13. **Active Exceptions & Open Decisions:** Unresolved sources, canon questions, or rights ambiguities, severity levels, and assigned human owners.
14. **Next Production Day Starting Baseline:** Sourced starting constraints, eligible production date, next chronicle number, and continuity boundaries for the subsequent run.

*Chronicle #10 Special Handover Rule:* When compiling Chronicle #10, B6 must state `EPISODE_COMPILATION_READY`, list the acceptance status of all ten daily installments, and halt. Do not automatically compile, finalize titles, or retrieve deployed field teams.

# 12. RECONCILIATION, CONCURRENCY AND PERSISTENCE

1. **Optimistic Concurrency Control:** Every read operation pins the `base_revision` hash. When preparing a write, verify that the storage target has not been updated by another process. If a collision occurs, execute a three-way merge or escalate to an editor.
2. **Delta Generation:** Write only newly created events, claim entries, and record revisions; never overwrite past historical entries.
3. **Write Verification:** A write is recognized as `COMMITTED_VERIFIED` only upon successful API return containing a commit SHA, transaction ID, or filesystem readback verification. Otherwise, status remains `DRAFTED_NOT_COMMITTED`.
4. **Data Retention and Privacy Compliance:** Legitimate legal, privacy, and consent revocation erasures supersede append-only story conventions. Erasures must be executed by authorized custodians with full audit logging.

# 13. EPISODE COMPLETION AND CONTROLLED ROLL-UP

1. **Prerequisites for Compilation:** An episode compilation (`EPISODE_COMPILATION`) may be initiated **only** after ten distinct, correctly dated chronicles are individually marked `ACCEPTED` by a human editor.
2. **Provisional Titling:** Daily and episode titles remain provisional until the full episode is compiled and approved by an authorized human editor.
3. **No Automatic Infill:** If an episode contains missing chronicle slots (e.g., only 8 of 10 days written), the system must halt and report missing days. Never generate uncommissioned chronicles to fill gaps.
4. **Higher-Level Roll-Ups:** Chapter roll-ups (4 episodes / 40 days) and season roll-ups (5 chapters / 200 days) must derive strictly from accepted lower-level episode ledgers.

## 1.2 The Failure Modes of Monolithic Consolidation
Attempting to merge CC-02.01, CC-02.02, and CC-02.03 into CC-01.01 would introduce severe architectural and operational defects:

## 1. Purpose, boundaries and run-state model

The CC-UPMP is the policy and creative contract; **this file prescribes the sequence, checks, intermediate artifacts and stopping decisions**. The CC-ECLPM defines the durable record semantics and security of the resulting episode data. Do not restate a modified version of the master's creative or calendar rules here; use the governing sections identified in CC-UPMP Parts I–IX.

### 1.1 Classify the requested operation

| Mode | Execution rule |
|---|---|
| `REVIEW_ONLY` | Inspect or revise documentation. **Do not** produce a chronicle or alter canon. |
| `DAILY_GENERATION` | Run the complete protocol for one eligible production working day. |
| `DAILY_REVISION` | Reconcile a specified existing daily revision against accepted evidence and issue a new draft revision and changed-state report. Do **not** mutate the accepted historical revision in place; append a new revision event. |
| `SPECIAL_WEEKEND` | Require a separate explicit editorial commission; never consume a standard episode-day slot by default. |
| `COMPILATION` | Separate approved ten-day episode assembly; **not** a daily run. |
| `DERIVATIVE` | Separate comic, audio, video, collage or Service Card order; use the approved current derivative companion specifications. |
| `OTHER` | Respond within the expressly requested scope; do not infer story-production authorization. |

A weekday request is not automatically date-eligible. A date must be assigned by an approved effective-dated calendar or a computation **explicitly authorized by that calendar**. A weekend, phase gap, invalid partial episode, missing prerequisite or conflicting locked state is an exception to report, not an invented chapter.

### 1.2 Run states and transitions

| State | Entry / exit condition | Next action |
|---|---|---|
| `REQUEST_CLASSIFIED` | Scope, requested date and operating mode understood | Check governance, authorized inputs and permissions |
| `PREFLIGHT` | Source inventory and previous state read or accurately marked inaccessible | Determine material blockers |
| `BLOCKED` | Essential authority, date, canon, permission or mandatory evidence unresolved | Issue precise blocker report; no definitive Output A |
| `GO_WITH_OMISSIONS` | Essential requirements met; optional inputs unavailable | Log omissions and continue |
| `GO` | Essential requirements verified | Pin temporal evidence and resolve chronology |
| `EVIDENCE_LOCKED_FOR_DRAFT` | Exact run snapshots, date mapping and sources identified | Reconcile continuity, conduct research |
| `DRAFTED` | One candidate A and separately classified B assembled | Validate, correct, mark editorial status |
| `AWAITING_EDITORIAL_REVIEW` | QA results and actual storage status communicated | No self-approval or publication |
| `APPROVED` / `LOCKED` | Only an evidenced authorized human decision | Downstream use only within explicit permissions |
| `COMMITTED` | Only an authorized, verified repository/record operation | Record URI/revision/action evidence; not equivalent to approval |

`DRAFTED`, `COMMITTED`, `APPROVED`, `LOCKED` and `PUBLISHED` are **independent dimensions**, not automatic steps in a single ascending ladder. A draft can be stored without approval; approval does not prove storage; neither proves publication.

### 1.3 Output partition

**Output A — public-eligible literary draft.** A self-contained, original daily chronicle. Its **final public element** is the audience challenge; there is no appended technical note, solution or B-packet section. The file may still require human acceptance before publication.

**Output B — internal production and episode handover.** Eight ordered sections, **B1 through B8**, with source-backed metadata, deltas and a portable B6. Never append this packet to the publishable A file. In an editorial session, show it only where the recipient is authorized; otherwise use genuinely separate files or withhold sensitive details.

**Output C — restricted challenge solution.** Create only with explicit authorization and verified access-controlled storage. An ordinary chat, public repository, Markdown heading or file named "restricted" is **not** proof of restricted custody. If custody is unavailable, do not generate or retain a solution in ordinary outputs; register `RESTRICTED OUTPUT NOT CREATED; HUMAN SECURE CUSTODY REQUIRED` in B8 and a nonrevealing key status in B7. **This is not by itself a block on drafting A**; an actual release/competition policy may separately require secure-key review before publication.

### 3.2 Go/no-go decision

- **`GO`:** date/episode position and core canon are valid; required central source material and publication eligibility for the proposed public portrayal are established.
- **`GO_WITH_OMISSIONS`:** only nonessential weather, some news topics, a secondary project record, a minor character image, a particular verse fallback or a luxury asset is missing; omit or attribute a valid alternative; disclose in B2/B8.
- **`BLOCKED — SOURCE OR APPROVAL REQUIRED`:** the authoritative calendar/date/episode number is unresolved; central locked canon contradicts itself; an essential real person's use/consent is invalid; or an explicitly required central reading, verse or H&S source cannot be obtained after reasonable, lawful retrieval attempts.

A block report states the requested date, exact unverified dependency, locations actually checked, relevant competing claims, risk of fabrication, and concrete editorial evidence/decision required. It must **not** fill the gap with plausible fiction while presenting the result as a completed chronicle. An authorized **provisional nonpublishable fiction exercise** may be separately produced when safe, visibly labeled outside public A.

## 4. Phase 2 — pin independent temporal evidence

Follow CC-UPMP §9–10. Keep separate actual/supported HQ, Enka-current, Enka-historical, mission destination and individual deployed-team locations. An unknown location is `UNVERIFIED`; it is not automatically New Legon, Las Vegas or wherever a previous story happened.

**Interfaces to attempt where within scope:**

For each actual request, register the endpoint, retrieval instant with timezone, request outcome and parse result, returned fields, omitted fields, raw payload or immutable authorized reference, source offset, normalized timestamps, freshness and evidence classification (`LIVE`, `SUPPLIED`, `CACHED`, `ARCHIVED`, `INACCESSIBLE`). An old user-supplied payload remains **supplied historical evidence** even if its contents resemble a live response. Do not substitute the current `phase_index` for an effective-dated historical chapter assignment. ## 5. Phase 3 — resolve calendar day, episode and IDs

**First:** use the exact date-to-episode entry from an approved effective-dated manifest and its official identifiers. **Only when its terms expressly authorize the four-episode/eight-week derivation**, and phase start/end instants and timezone are verified, perform the following calculation from CC-UPMP §6:

```text
local_phase_start = calendar_date(phase_start_instant in approved_production_timezone)
local_phase_end   = calendar_date(phase_end_instant in approved_production_timezone)
anchor            = first Monday on or after local_phase_start
elapsed_days      = target_local_date − anchor, measured in whole calendar dates
episode_ordinal   = floor(elapsed_days / 14) + 1
block_day         = elapsed_days mod 14
block_day 0–4     → chronicle_ordinal = block_day + 1
block_day 7–11    → chronicle_ordinal = block_day − 1
block_day 5,6,12,13 → WEEKEND_NOT_SCHEDULED; no regular chronicle
chapter_working_day = 10 × (episode_ordinal − 1) + chronicle_ordinal
episode_start     = anchor + 14 × (episode_ordinal − 1) calendar days
episode_end       = episode_start + 11 calendar days  (second Friday)
```

**Validation:** target must fall in the approved effective phase; `elapsed_days` must be in [0, 55]; the **whole episode window** must lie inside the approved chapter window; episode ordinal must be 1–4 for an unextended chapter; `block_day` 5, 6, 12, 13 are weekends. If any check fails, follow the approved shortened/special episode policy or raise `CALENDAR_EXCEPTION`.

**Boundary examples (test cases, not production claims):**

| `elapsed_days` | Episode | Chronicle | Chapter working day |
|---:|---:|---:|---:|
| 0 | 1 | #1 | 1 |
| 4 | 1 | #5 | 5 |
| 7 | 1 | #6 | 6 |
| 11 | 1 | #10 | 10 |
| 14 | 2 | #1 | 11 |
| 28 | 3 | #1 | 21 |
| 42 | 4 | #1 | 31 |
| 53 | 4 | #10 | 40 |

Weekends at `elapsed_days` 5, 6, 12, 13 and their subsequent 14-day multiples have no ordinary chronicle number.

**Phase output:** B1 calendar record; validated episode/chronicle IDs; `CALENDAR_EXCEPTION` details if applicable; immutable legacy-to-new ID crosswalk reference.

## 6. Phase 4 — continuity, canon and role preflight

Before constructing any story:

1. Read the actual previous accepted public chronicle and last B6 handover. If missing, record the exact gap; do not retroactively fabricate missing installments.
2. Reconstruct the accepted mission state, deployed member positions and unresolved story threads from approved events in the CC-ECLPM `continuity_event_log`. An episode boundary does not automatically return a deployed team.
3. Verify the central and featured characters against their individual canon files (`CC_AI_DESK/04_CANON/CHARACTERS/...`). Flag any unresolvable canon conflict as `BLOCKED` for the affected character. Log canon-review triggers for recurring characters lacking approved canon spanning three or more episodes.
4. Resolve the `chapter_working_day` against the authorized organization role-check chart (`Organizational_Chart_Structure-Aliased_Checks.txt`). Map values 1–40; do not conflate 1–10 episode-day numbering with 1–40 chapter working days.
5. Classify each project reference as `DOCUMENTED_ACTUAL`, `FICTIONAL_SCENE` or `PROPOSAL_FOR_REAL_REVIEW`.
6. Check public-challenge release obligations from the previous episode's `challenge_public_register`; a prior challenge due for publication must be noted in B7 and actioned per the editorial policy, not automatically appended to this day's Output A.

## 8. Phase 6 — compose Output A

Apply CC-UPMP §16 prose standards:

1. Open with a scene, not a production briefing or metadata header. A provisional/approved title is permitted; mark it `PROVISIONAL` in B if not yet editorially accepted.
2. Write approximately 3–5 minutes of natural reading (≈600–1,000 words) unless the commission specifies otherwise; length should be story-driven, not quota-driven.
3. Maintain consistent time and place transitions; do not stage Enka or a deployed member simultaneously in two locations.
4. Let research inform the plot through character choices, environment, dialogue and consequence. Do not paste raw news excerpts or stage-labels into public prose.
5. Draw on the morning/routine palette selectively and flexibly (see CC-UPMP §12); do not open every chronicle with four alarms if the character is deployed, traveling or mid-episode.
6. Follow the ten-chronicle dramatic arc from CC-UPMP §15 as narrative guidance, not a mandatory formula.
7. End Output A with **exactly one fair public question** (CC-UPMP §20): multiple-choice A–E when the format fits; solvable from the public story and/or a genuinely public resource; no answer, rationale or revealing hint included.
8. **Stop Output A immediately after the challenge text.** No endnotes, credits, editorial comments, B-section headers or link footers follow.

**Phase output:** complete draft Output A ending on the public challenge.

## 1. Purpose and scope of durable continuity

A two-week episode comprises up to ten separately commissioned Monday–Friday chronicles. For each day, preserve the authorized **narrative that actually exists**, the evidence that informed it, the source/rights status, the actual approval and save state, the fictional changes occurring in its world, the active Edubeam and character state, the public challenge obligation, derivative dependencies and a safe starting context for the next production day. Distinguish all of these from unapproved creative suggestions and actual Koware business facts.

The logical record system is not merely a prompt appendix. It supports **event-sourced continuity**: authenticated or clearly marked draft events are retained as history; state projections identify which accepted events determine the current story truth; superseding corrections preserve auditability. The episode archive is authoritative for that episode, and only approved promotions alter franchise-wide canon. Neither event authorship nor a model's file attachment proves editorial acceptance.

**Episode boundary:** day → episode → chapter/phase → season → permitted franchise roll-up. Carry forward only the appropriately approved state, with references back to the source episode. Do not reset deployed characters, unclosed plot threads, public-challenge release obligations or permissions simply because a calendar boundary passed.

## 2. Governance, ownership and access partition

| Custodian | Authorized content | Unsafe inference |
|---|---|---|
| Approved franchise/world/character/visual/technology canon | Durable locked characterization, powers, relationships and world laws | Any daily fiction can revise locked canon |
| Persistent `CC_AI_DESK` | Reusable prompts, schemas, catalogs, metadata indexes, automation and operational controls | The Desk owns all episode stories, missions and raw personal diaries |
| Approved `CC_EPISODE_ARCHIVES` / current episode archive | Manifest, story revisions, source snapshots, research, rights metadata, events, evolving state, handovers, approved assets | A proposed logical family authorizes a new folder, filename or migration |
| Approved Koware record owners | Real organization roles, projects, tasks, genuine completion and evidence | Fictional task success proves work was done |
| Actually access-controlled editorial vault | Challenge solutions and sensitive review details when authorization exists | A Markdown heading, ordinary chat or public repository is secure storage |
| Authorized human editor/owner | Acceptance, locks, titles, canon promotions, permissions, release and publication decisions | A model can declare approval on the editor's behalf |

**Access classifications** are `PUBLIC`, `INTERNAL` and `RESTRICTED`. Apply classification to **the record and any higher-sensitivity field**. A publicly shareable challenge question is not a permission to share its answer or a participant's private diary. Access grants and permission evidence must be checked at use time; never infer consent from a public source URL or a reachable repository. Sensitive metadata should not be included in an otherwise portable packet simply to fill a field.

**Audience destinations:** A is a separable public-eligible draft; B1–B8 is internal to authorized editorial collaborators; C exists only inside an actually controlled restricted environment. If these cannot be separated in the current medium, withhold or redact nonpublic material. Publication eligibility is distinct from authorization to inspect a source.

## 3. Record encoding, identity, versions and evidence classes

### 3.1 Semantics of each record envelope

The following are the **common logical fields**. The approved storage solution may implement them as Markdown front matter, JSON, YAML, table entries or database columns, provided semantics and access controls remain intact.

| Field | Value and validation rule |
|---|---|
| `record_id` | Actually registered unique identifier in governed scope; a proposed ID must be marked provisional and is not evidence of an existing item |

| `canonical_id` / `legacy_id` / `original_path` | Existing approved identities and physical URI/path; absent ones are not fabricated |
| `record_version` / `base_revision` | Actual revision/sequence; when only preparing a draft, state not yet persisted and preserve source revision read |
| `record_status` | `DRAFT`, `AWAITING_REVIEW`, `APPROVED`, `LOCKED`, `REJECTED`, `SUPERSEDED`, or an approved mapped status, **only if evidenced** |

**No data placeholders:** unverified fields use real **typed** `null` (for structured representations) plus a precise status/reason; narrative packets use `UNVERIFIED`, `INACCESSIBLE`, `NOT_APPLICABLE` or `AWAITING_EDITORIAL_DECISION` with cause. These are truthful runtime states, **not** synthetic sample dates or employees. A logical contract is allowed to name fields; it must not pretend their values exist.

### 3.2 Evidence types, revisions and time

Use the approved source-specific evidence vocabulary: `APPROVED_CANON`, `PRIOR_DOCUMENTED_EVENT`, `VERIFIED_REAL_WORLD_FACT`, `HISTORICAL_INTERPRETATION`, `NEW_FICTIONAL_DRAFT`, `PROPOSED_CANON_CHANGE`, `FICTION_PROBE_SCENARIO`, `UNVERIFIED_EXCLUDED`. Where imported records use `FACT`, `DRAFT` or `APPROVED`, preserve the original and record an explicit semantic mapping rather than silently relabeling.

- **Local dates** are `YYYY-MM-DD` with an independently recorded approved production timezone (prefer approved IANA zone when available). **Instants** include their actual timezone offset. Do not compare a local requested date with the UTC date of a Probe reading as if they were the same measure.
- **Source retrieval** records actual UTC and source-local offsets where known. Store event date, publication date and retrieval date **independently**.
- **Snapshot/evidence records and continuity events** are append-only under the approved retention policy. Corrections append a new event with `supersedes_record_ref` and a reason; projections may be recalculated and revisioned.
- **Only approved, non-superseded causal events** can be promoted to accepted continuity. Draft events remain reviewable alternatives. Canon promotion is a separate human-approved action, not a field default.
- **No silent rebase:** compare `base_revision` with the latest approved ledger revision before any authorized write; on conflict, reread and reconcile or escalate. Existing filenames and `S00_T05`, `TP` and `CH` paths remain unchanged absent an approved migration.

## 5. Episode, calendar and daily story contracts

### 5.1 `episode_manifest` and `episode_context_snapshot`

Maintain actual IDs for season, chapter/phase, episode and legacy archive; owner and approval evidence; authoritative effective-dated calendar reference; approved production timezone; full episode Monday-to-second-Friday start/end; approved phase bounds; mapping between numeric phase index and `CH`/`T`/`TP` **only if authorized**; role-check chapter index rules; 1–10 day-slot eligibility; prompt/protocol/schema versions and their individual approval states; provisional title and title status; relevant canon constraints; current story premise and approved vs unapproved goals; prior episode/season handovers; actual archive reference, update time and `base_revision`. An actual phase response may expose only some fields: absent values remain absent with status.

A context snapshot captures when its assertions became effective, prior approved events, known character/mission positions, open stories and applicable rights; tag each assertion `APPROVED`, `LOCKED`, `DRAFT`, `UNVERIFIED` or `EDITORIAL_PROPOSAL` as appropriate. Do not convert an AI reconstruction of a missing gist into a verified historical approved manifest.

### 5.2 Clock/date derivation — B1 source evidence

Record three independent axes, using the CC-UPMP §9 designations:

1. **Clock P (production present)** — requested local calendar date, timezone, actual execution/retrieval instant and applicable current news context.
2. **Clock H (historical reference)** — actual `historical.iso` or approved dated archival snapshot, Enka's sourced historical-reference location, and whether the reference is a memory/flashback rather than current physical location.
3. **Clock F (Edubeam probe/destination)** — actual `probe_iso` and location, in-universe mission status, future vs documented-historical classification.

Also distinguish current HQ/control base, Enka-current and each team member's physical/temporal whereabouts. These are separate attributes even when geographically equal.

Derivation per CC-UPMP §6 and CC-DCGP §5 uses an approved effective-dated calendar before any formula. Preserve phase-local start/end, first Monday anchor, target local day, whole-date elapsed count, 14-day block index, episode ordinal 1–4 if authorized, weekend exception, chronicle 1–10, chapter working day 1–40, complete episode dates and boundary fit. The canonical ID crosswalk must be independently verified. The five nominal eight-week chapters account for only forty weeks; gaps have no inferred episode. A live Probe reading today **does not** prove an earlier requested day was in that phase.

### 5.3 `source_snapshot_register`

Every material retrieval stores: actual source URL/path, source revision/commit or observed checksum if obtained, retrieval time, response status/content type, raw returned payload or approved immutable pointer, received fields and missing fields, parse validity, timezone interpretation, origin (`LIVE`, `SUPPLIED`, `CACHED`, `ARCHIVED`), license/retention/access classification and downstream claim IDs. Use one clearly pinned run snapshot for chronology; later recalibration gets a separate snapshot and event. A URL without retained revision is not equivalent to immutable evidence, and retaining a raw payload containing personal data requires separate authorization.

### 5.4 `daily_chronicle_record`

Record the actually resolved `chronicle_id`/`episode_id`, production date and weekday, episode day 1–10 and chapter working day 1–40, calendar source and proof, working title plus provisional/approved status, precise story text or approved asset revision, author/creation time, master/protocol/schema versions, six-stage evidence references, three-clock references and supported locations (using P/H/F designations), character/mission/role state links, public challenge ID, rights/quality checks, actual draft/approval/lock/publication statuses and write evidence. Never describe a locally AI-generated text as a repository-stored day record before verifying the action.

## 6. Event sourcing, character, mission, storyline and role controls

### 6.1 `continuity_event_log` — append-only causal history

Every proposed or accepted event contains: real or explicitly provisional `event_id`; parent day/episode; exact fictional-story time/clock and location where established; event summary and scene/story revision; affected characters, mission, organization or object; preceding cause and consequential change; classification (`NEW_FICTIONAL_DRAFT`, `PRIOR_DOCUMENTED_EVENT`, etc.); source references; approval status and real editor reference if approved; predecessor/superseded event if corrected; privacy/licensing constraints; state projection impact. **Never delete earlier history solely to make the new draft look continuous.** An accepted story revision that changes an event must trigger dependent state and media review.

Projection rules: construct the **accepted** current state from approved non-superseded events in their story-time/causal order; keep unapproved deltas separately; detect contradictory simultaneous locations, duplicated day records, impossible character knowledge, impossible equipment state and unclosed retrieval. A time-travel narrative can intentionally use nonlinear scene order while the ledger still records the correct in-universe temporal positions and evidence.

### 6.2 `character_state_record`

Link each individual to the actual approved character canon file and its version, approved alias and relation to role chart where applicable, physical location/time, personal knowledge (seen/inferred/told), current motivations, relationship change, health/injury only when established in fiction and appropriate for access, obligations, usable powers at that particular era, recent actions and affected event IDs. State deltas belong to the episode record; reusable character canon only changes via explicit human promotion. Individual canon paths under `CC_AI_DESK/04_CANON/CHARACTERS/` must be actually found, not inferred from a directory listing.

For real-person-inspired figures, differentiate internal access from public portrayal rights; never turn a private family/diary statement into a compulsory public story detail. Record actual exclusions without reproducing the sensitive content in a widely shared B packet.

### 6.3 `mission_state_record`

The mission state is a revision derived from events, not a story convenience reset. Fields include actual or verified proposed mission identifier and stage (`PLANNED`, `PREPARING`, `CALIBRATING`, `DEPLOYING`, `DEPLOYED`, `INVESTIGATING`, `OUT_OF_COMMUNICATION`, `RETRIEVING`, `RETURNING`, `DEBRIEFING`, `ON_HOLD`, `CLOSED` where canon permits), roster and each member's temporal/spatial location, destination/probe reference, HQ/lab communications, equipment/energy and approved Edubeam limits, material transfers only when canon permits, findings, risks, injuries, open rescue/retrieval commitments and prior event links. An inaccessible mission ID is `UNVERIFIED`; a sourced absence can be `NO VERIFIED ACTIVE MISSION`. No automatic Thursday retrieval, Friday departure or episode reset, and no unexplained early-era Enka power upgrade.

### 6.4 `storyline_register`

For each plot thread store: origin day/event, thematic or narrative purpose, involved cast, known evidence, last accepted advance, status (`OPEN`, `ADVANCED`, `RESOLVED`, `DEFERRED`, `DISPUTED`), causal dependencies, explicit promised payoff if any, deadline only when a real accepted story constraint, and next-day continuity guidance **without prescribing a future plot**. A resolved thread needs an event demonstrating resolution; an unresolved mission is not resolved by a chapter title change.

### 6.5 `role_project_log`

Record chart URI/revision and approved schedule semantics, `chapter_working_day` 1–40 rather than 1–10, scheduled role checks and actual aliases, featured roles (normally one or two, at most four under the working master unless a verified approved exception applies), source for real tasks, scene portrayal and source/consent limits. Each action is `DOCUMENTED_ACTUAL`, `FICTIONAL_SCENE` or `PROPOSAL_FOR_REAL_REVIEW`. A character discussing a real project does not certify any corresponding actual milestone, staff activity or new management obligation.

## 7. Claim-level research, permissions and the six-stage link

### 7.1 `research_register`

Each **claim or selected educational insight**, not merely each website, records: stable actual/provisional claim ID; statement/topic; pass 1–6 and historical/current/probe stream (using P/H/F clock designations); title, author/publisher, source URI and edition/revision; exact relevant section or short allowable quotation reference; geographic/temporal scope; **event date, publication date and retrieval instant separately**; primary/secondary/fictional type; evidence classification; method/corroboration; confidence and uncertainty; use rights; story passage/beat influenced; selection/rejection reason.

A newspaper's publication date is not automatically the event's date. Fictional future projections have **real research inspiration references** but cannot claim a future newspaper exists.

For the required research modes:
- **Eternal Dreamfall weekly reading:** actual 250-entry plan item plus an independently approved date/week anchor; distinguish weekly assignment from authorized daily selection; accurately classify canonical, apocryphal, pseudepigraphal, lost or fragmentary works and available editions.
- **Verse:** verified YouVersion reference/date/translation **or** named independent alternative, never false YouVersion attribution.
- **H&S:** genuine Buzzjuice course/module/lesson path, title, exact section and actual supported practice; no invented course.
- **Historical (Clock H):** Clock H location/time supported by documentary reporting; distinguish fact from interpretation.
- **Current (Clock P):** Clock P requested day and verified relevant local/global reporting; distinguish event from publication time.
- **Probe (Clock F):** Clock F documented history if actually past; otherwise explicitly `FICTION_PROBE_SCENARIO`, not authenticated future reporting.
- **Weather/environment:** observed/archived source for factual weather; otherwise fiction, not a measurement.
- **Koware/archive/diaries:** approved records and specific permission for intended use, including real/fictive differentiation.

Legacy large headline targets and three-global/five-local synthesis belong in **internal candidate pools**, not a quota to fabricate news or force into A. Record actual omissions and rejections; preserve only appropriate evidence excerpts under license.

### 7.2 `source_permission_register`

Each relevant source/participant/asset use stores: `source_or_participant_ref`, owner or author, proposed scope (research, internal paraphrase, fictional inspiration, public portrayal, direct quotation, visual adaptation), `retrieval_eligible` (`YES`/`NO`/`UNKNOWN`), `publication_eligible` independently, `consent_state` (`GRANTED`, `LIMITED`, `WITHDRAWN`, `NOT_REQUIRED`, `UNKNOWN`), `license_state` (`APPROVED`, `RESTRICTED`, `EXPIRED`, `UNKNOWN`), actual evidence and restriction references, checking/revocation dates, reviewer, recipient policy and next review if required. **Default exclude affected use on `UNKNOWN`, `NO`, withdrawn or unclear rights**; a public URL is not a rights grant and an accessible employee chart is not consent to depict real staff.

Permissions are rechecked before actual publication and derivative distribution. A consent revocation produces an access/rights event and a revalidation/withdrawal review for affected assets; do not expose the revoked private content merely by describing the issue.

## 8. Challenge, Service Card and derivative contract

### 8.1 `challenge_public_register`

Record only: actual challenge ID (or explicitly provisional generated identifier), parent day/story revision, **exact public question/options**, intended learning purpose, fairness/nonrevealing evaluation criteria, status, separately approved public hint if harmless, default **subsequent-episode** solution-release reference, chapter-final exception decision status, and an **opaque** restricted-key custody state or opaque authorized pointer. Do not store solution, near-solution, private grading rule or answer-revealing hint in this register, B sections or an ordinary provider handover.

### 8.2 `challenge_answer_key` — RESTRICTED only

Only if a **verified, authorized, access-controlled custody channel** exists: solution, explanation, acceptable alternatives, source basis, revealing hints if any, responsible editor, access permissions/logging, production/review/approval status and actual approved release trigger belong **there and nowhere else**. Do not create C in an unprotected chat or public repository. Otherwise record the nonrevealing state `RESTRICTED OUTPUT NOT CREATED; HUMAN SECURE CUSTODY REQUIRED` in B8. **Lack of secure storage alone does not prevent drafting A**; competitive release may be governed by a separately ratified requirement to have approved custody first.

An answer's default public release belongs with the **next episode's authorized release**, not the next chronicle day. Chapter-final exceptions require an actual human decision; an older answer, if separately released, must not be appended after the current A's own final challenge.

### 8.3 `production_manifest` and `service_card_register`

Track text and any separately commissioned comic, collage, video, audio, graphic or card asset with: actual asset ID, episode/day parent, type, exact **source story revision**, media/prompt version and required visual canon, approved creator/commission, permissions/licensing, creation and editor review states, intended public destination, actual storage/publication reference if verified, version/checksum when available, and **dependency-staleness** status (`CURRENT`, `STALE_REVALIDATION_REQUIRED`, `NOT_APPLICABLE`).

A change to a source story, character appearance, challenge wording or accepted canon triggers revalidation of affected derivatives rather than quietly treating an earlier image as canon-compliant.

Service Cards remain **optional** practical 3–5-step evidence-backed guides, separately approved and integration-tested. A generated story does not award a prize, credit, point or digital badge. Service Cards, 43 Clues, QR/Buzz Codes, myCred and membership points are future separately approved integrations requiring actual rules, accessibility, fraud handling, age/privacy compliance, anti-spam process and an auditable award ledger.

## 9. Quality, write operations and failure handling

### 9.1 Validation report

Each `validation_report` covers: episode/day scope; applied gate set (Q01–Q16 for daily, C01–C22 for comic, M01–M30 for media); individual gate verdicts (`PASS`, `FAIL`, `NOT_CHECKED`, `NOT_APPLICABLE`) with evidence; failed-gate remediation actions; source failures and fallbacks; rights/consent gaps; overall verdict; reviewer identity and timestamp. `NOT_CHECKED` is not `PASS`. A dry-run may pass documentary consistency while failing operational permissions.

### 9.2 Authorized write operations

When writes are authorized and tools actually support them: read current head/revision → validate roles/permission and expected `base_revision` → prepare output to distinct paths with audience restrictions → atomic/transactional commit where possible → verify by readback/hash/identifier → mark `COMMITTED_VERIFIED` only on actual success. If the branch/revision changed, stop with `CONFLICT_REQUIRES_RECONCILIATION`; never force-push or overwrite an approved story on a stale base. A downloadable local file is an **unsaved repository draft**, not a commit. Write errors go in B8; do not backdate commits.

### 9.3 Exception and conflict register

Each `exception_conflict_register` entry holds: exception type and severity (`INFORMATIONAL`, `MATERIAL`, `BLOCKING`), affected records, competing claim sources, safe default behavior, resolution owner, required evidence/decision, current resolution state and any cross-register links. Material and blocking exceptions must be communicated to the responsible human editor before finalization.
