## 2.3 Stage 2 — Calendar and episode resolution

Prefer an approved, effective-dated episode calendar.

If no directly applicable calendar entry exists, apply the approved calculation rules from CC-UMP v0.04.00 only when the source data supports them.

Record:

- Phase/chapter start.
- Phase/chapter end.
- Production timezone.
- Anchor Monday.
- Requested local date.
- Elapsed calendar days.
- Episode number.
- Episode start and end.
- Day within the two-week block.
- Chronicle number.
- Chapter working-day index.
- Approved logical and legacy identifiers.

Calculation:

```
anchor = first Monday on or after phase_start

elapsed_days = target_local_date - anchor

episode_number = floor(elapsed_days / 14) + 1

day_in_block = elapsed_days mod 14

if day_in_block is 0–4:
    episode_day = day_in_block + 1

if day_in_block is 7–11:
    episode_day = day_in_block - 1

if day_in_block is 5, 6, 12 or 13:
    weekend — no normal chronicle

chapter_working_day =
    10 × (episode_number - 1) + episode_day
```

Validation:

- Episode number must be within approved episode slots.
- Chapter working day must be within the approved 1–40 structure.
- The complete Monday-to-second-Friday episode must fit the authorized phase.
- Phase gaps and incomplete periods must not be assigned invented episode numbers.

A current Probe response must not be used as retroactive proof of a historical production date's phase.

# 1. PURPOSE AND SCOPE

## 1.1 Objective

Maintain a reliable, auditable and portable source of episode-specific truth throughout the ten independently produced working-day chronicles of an episode.

The ledger must preserve:

- What each chronicle actually contains.
- What happened in the story.
- Which facts are established and which are draft fiction.
- Which characters participated and how their states changed.
- Where deployed characters are located.
- How Edubeam missions progressed.
- Which external sources informed the narrative.
- Which permissions and publication restrictions apply.
- Which editorial decisions were made.
- Which storylines remain unresolved.
- What the next AI provider or editor needs to continue.

## 1.2 Governing division of responsibility

| Component                 | Responsibility                                                            |
| ------------------------- | ------------------------------------------------------------------------- |
| CC-UMP v0.04.00           | Governing narrative, canon, authority, outputs and production constraints |
| CC-DCGP v0.04.00          | Daily research and generation execution                                   |
| CC-ECLPM v0.04.00         | Logical records, schemas, event history, continuity and handover          |
| Approved Studio Blueprint | Actual repository paths, storage ownership and implementation             |
| Human editor              | Approval, locking, canon promotion, publication and controlled release    |

This document does not independently authorize story generation.

## 1.3 Continuity hierarchy

Daily chronicle → Episode → Chapter → Season → Franchise.

Only approved records may be promoted into higher-level established continuity.

Episode-owned records remain the source of truth for their episode.

Approved franchise canon remains authoritative for reusable global rules.

# 2. OWNERSHIP, STORAGE AND SECURITY

## 2.1 Data ownership

### Franchise canon

Owns approved reusable:

- Character identities and profiles.
- Visual canon.
- Relationships.
- Technology capabilities and restrictions.
- World rules.
- Locations and timelines.

A daily ledger cannot rewrite permanent canon.

### Persistent CC_AI_DESK

Owns reusable:

- Master prompts.
- Execution protocols.
- Record schemas.
- Retrieval indexes.
- Source catalogs.
- Operational instructions.
- Approved reusable tools.

It is not the default custodian of daily episode narratives or raw episode media.

### Episode archive

Owns episode-specific:

- Manifest and context.
- Daily chronicles.
- Temporal snapshots.
- Research registers.
- Permissions.
- Mission records.
- Character-state changes.
- Event history.
- Challenges.
- Production records.
- Editorial decisions.
- Daily handovers.
- Approved derivatives.

### Restricted editorial storage

Owns:

- Challenge answer keys.
- Sensitive source material.
- Protected diary content.
- Other information requiring restricted access.

A `RESTRICTED` label does not itself create access control.

### Human editor/owner

Controls:

- Approval and rejection.
- Story locking.
- Episode title finalization.
- Canon promotion.
- Permissions.
- Challenge-answer release.
- Publication.
- Archive migration.
- Retention decisions.

## 2.2 Physical storage

The approved Studio Blueprint determines the actual storage paths.

Potential logical areas must be verified against the current architecture.

Do not assume that the presence of `CC_EPISODE_ARCHIVES`, `01_EPISODE_CONTEXT` or any proposed directory name authorizes creation of a new physical location.

Preserve existing legacy structures, including `S00_T05`, `E01`, `TP` and `CH` identifiers, where they actually exist.

Do not store sensitive diary material or challenge answers in public GitHub repositories.

# 3. RECORD FORMAT AND COMMON ENVELOPE

## 3.1 Supported representation

Markdown is suitable for readable narrative records and handovers.

JSON or YAML may be used for structured data when authorized by the approved architecture.

The same field semantics must be preserved across representations.

Do not claim that a schema has been machine-validated unless an actual validator was executed.

## 3.2 Common record envelope

Every stored logical record should include the following fields or their approved schema equivalents:

| Field                   | Purpose                                        |
| ----------------------- | ---------------------------------------------- |
| `record_id`             | Stable unique identifier                       |
| `record_type`           | Approved logical record family                 |
| `schema_id`             | Record schema identity                         |
| `schema_version`        | Actual schema version                          |
| `record_version`        | Revision of this particular record             |
| `episode_id`            | Parent episode identifier where applicable     |
| `chronicle_id`          | Parent daily chronicle where applicable        |
| `status`                | Actual workflow status                         |
| `classification`        | Evidence/narrative classification              |
| `access_classification` | PUBLIC, INTERNAL or RESTRICTED                 |
| `created_at`            | Actual creation timestamp                      |
| `updated_at`            | Actual revision timestamp                      |
| `created_by`            | Actual creator or producing system             |
| `responsible_editor`    | Known responsible editor, otherwise unresolved |
| `source_refs`           | Supporting source references                   |
| `approval_refs`         | Actual human approval references               |
| `supersedes_record_ref` | Previous record when corrected                 |
| `change_reason`         | Reason for the revision                        |
| `access_policy_ref`     | Applicable access policy                       |

Do not invent existing record identifiers or approval references.

## 3.3 Timestamp conventions

Use ISO 8601/RFC 3339 date-time values with the original timezone offset whenever available.

Preserve the distinction between:

- Production local dates.
- Historical reference timestamps.
- Probe/destination timestamps.
- Actual retrieval timestamps.
- Narrative event timestamps.
- Editorial approval timestamps.

Normalize to UTC where useful, but do not discard the original offset.

## 3.4 Unknown values

Use explicit status values:

- `UNVERIFIED`
- `INACCESSIBLE`
- `AWAITING_EDITORIAL_DECISION`
- `NOT_APPLICABLE`
- `WITHDRAWN`
- `DRAFTED — NOT COMMITTED`

In structured records, use actual typed null values where appropriate, accompanied by a status and explanation.

Never use fictional sample values as evidence of an existing record.

## 3.5 Evidence classification

Use the governing classifications from CC-UMP:

- `APPROVED_CANON`
- `PRIOR_DOCUMENTED_EVENT`
- `VERIFIED_REAL_WORLD_FACT`
- `HISTORICAL_INTERPRETATION`
- `NEW_FICTIONAL_DRAFT`
- `PROPOSED_CANON_CHANGE`
- `FICTION_PROBE_SCENARIO`
- `UNVERIFIED_EXCLUDED`

## 3.6 Access classification

Use:

- `PUBLIC`
- `INTERNAL`
- `RESTRICTED`

Apply classifications at both record and sensitive-subfield level.

A public challenge does not make its answer public.

# 4. CALENDAR, IDENTIFIERS AND TEMPORAL RECORDS

## 4.1 Episode manifest

The episode manifest identifies:

- Season.
- Chapter/phase.
- Episode.
- Ten chronicle slots.
- Approved calendar authority.
- Phase boundaries.
- Production timezone.
- Episode start/end dates.
- Approved and legacy identifiers.
- Governing document versions.
- Episode owner/editor.
- Title and approval status.
- Actual archive references.

Use the approved identifiers and preserve legacy mappings.

## 4.2 Calendar calculations

Use an approved dated calendar record wherever available.

If the approved calendar requires calculation, preserve:

- Phase start/end.
- First Monday on or after phase start.
- Target local production date.
- Elapsed days.
- Episode number.
- Chronicle number.
- Chapter working-day index.
- Episode start/end.
- Phase-boundary validation.

The five eight-week chapter model covers forty weeks rather than a complete year.

Unallocated dates, inter-phase gaps and incomplete episode periods must remain explicit exceptions until an approved calendar resolves them.

A current Probe snapshot cannot establish a historical date's earlier phase assignment.

## 4.3 Three-clock record

Every daily temporal record must independently capture:

**Clock A — Production**

Requested production date, actual execution time and approved timezone.

**Clock B — Historical reference**

Historical endpoint timestamp and Enka's verified historical location.

**Clock C — Probe/destination**

Actual Probe timestamp and mission location.

Separately record:

- Current Koware headquarters/control-base location.
- Individual Edubeam team-member locations.

## 4.4 Probe snapshot

Capture:

- Endpoint URL.
- Retrieval timestamp.
- Raw response or immutable snapshot reference.
- Response format.
- Returned fields.
- Missing expected fields.
- Source timezone.
- Normalized values.
- Freshness.
- Validation status.
- Live/supplied/cached classification.

Only fields actually returned may be stored as source values.

One pinned snapshot governs the production run.

A later recalibration creates a new evidence record and event.

- `APPROVED`

- Conflicting claim A.
- Conflicting claim B.
- Source and version for each.
- Applicability.
- Impact.
- Severity.
- Current disposition.
- Required human action.
- Resolution evidence.

Severity:

- `ADVISORY`
- `MATERIAL`
- `BLOCKING`

- Requirement.
- Check performed.
- Result: `PASS`, `FAIL`, `BLOCKED` or `NOT_APPLICABLE`.
- Evidence.
- Responsible checker.
- Actual timestamp.
- Remediation.

A check not performed is not a pass.

# 1. EXECUTIVE FINDING

3. Retrieve, when accessible and authorized, the current episode context, previous chronicle, latest handover, continuity and mission records, character canon, role/check-day source, and relevant project or diary sources.

## 4. Temporal acquisition and calendar resolution

### 4.1 Keep the clocks separate

Record available evidence for:

- **Clock A — Production:** requested production date, actual run time, approved production timezone, and relevant current locations.
- **Clock B — Historical reference:** historical timestamp and Enka’s supported historical location.
- **Clock C — Probe/destination:** observed Probe timestamp, mission destination, and documented deployment state.

### 4.2 Inspect and pin available temporal evidence

Potential interfaces:

- `https://buzzjuice.net/shared/millennium-timezone/millennium-probe.php?probe=now`
- `https://buzzjuice.net/shared/millennium-timezone/millennium-timezone.php?endpoint=historical`
- `https://buzzjuice.net/shared/millennium-timezone/millennium-timezone.php?endpoint=probe`

Inspect the actual responses. Record source URL, retrieval time and offset, source status (live, supplied, or cached), payload or approved immutable reference, the fields actually returned, and missing or invalid fields. Do not invent expected values.

Pin one validated run snapshot. A current/live response does not by itself establish the calendar assignment for a requested historical date.

### 4.3 Resolve the episode day

Use an applicable, valid, effective-dated approved calendar manifest first. Only if the approved schedule and verified phase boundaries support the standard model, apply the CC-UMP calculation:

1. Convert boundaries and the requested production timestamp to the approved timezone.
2. Confirm the requested local date falls within the authoritative phase.
3. Set the anchor to the first Monday on or after phase start.
4. Calculate whole local calendar days from the anchor; require a nonnegative result.
5. Calculate episode number as `floor(elapsed_days / 14) + 1`; validate it is an approved full episode slot.
6. Treat block-day values 5, 6, 12, and 13 as weekends. Do not generate a regular daily chronicle for them.
7. Map block days 0–4 to chronicle days 1–5 and block days 7–11 to chronicle days 6–10.
8. Calculate `chapter_working_day = 10 × (episode_number − 1) + chronicle_day`; validate it is 1–40.
9. Confirm the full Monday-to-second-Friday episode fits the approved phase.
10. Record the source, inputs, timezone, computation, validation, exceptions, and actual identifier crosswalk.

The five nominal eight-week phases cover only forty weeks. Do not infer the schedule for phase gaps, short phases, incomplete episodes, Foundation Phase mappings, or older dates. A weekend request receives a weekend-status and continuity response unless a special weekend chronicle is authorized.

|---|---|---|
| Approved franchise canon | Reusable approved character, visual, technology, relationship, world, and timeline constraints | A draft daily event does not rewrite canon |
| Persistent `CC_AI_DESK` | Reusable prompts, schemas, retrieval rules, indexes, catalogs, and tools | Not the episode archive by default |
| Approved episode archive | Episode manifests, stories, source snapshots, research, temporary story states, event deltas, handovers, permissions, and production records | Use only verified approved paths |
| Koware records | Actual business facts, operational decisions, and project status | Fictional proposals are not actual work |
| Restricted editorial channel | Challenge answer keys and other protected data, with appropriate access controls | A label such as “restricted” does not secure an ordinary file or chat |
| Authorized human editor/owner | Review, approval, locks, canon promotion, permissions, release, publication, and migration | AI-generated labels do not constitute approval |

Do not assume access to private repositories, diaries, calendars, accounts, or secure answer stores. Verify the actual approved Studio Blueprint, archive layout, retention rules, and access policy before use. Do not expose personal secrets or confidential operations in handovers.

## 3. Record conventions

Use the approved schema and storage format. Markdown can support readable handovers; structured JSON/YAML may be used only where the approved architecture permits it.

For actual records:

- Preserve timestamps with source timezone/offset where available. Distinguish local production dates from historical and Probe instants.
- Use explicit unknown/status values rather than fabricated data: `UNVERIFIED`, `INACCESSIBLE`, `NOT APPLICABLE`, `AWAITING EDITORIAL DECISION`, or `NO CHANGE`.
- Preserve actual approved IDs and legacy paths. Proposed ID patterns are not permission to create or rename records.
- Record source URLs, repository revisions, retrieval times, or approved immutable snapshot references when available.
- Distinguish evidence classes: `APPROVED_CANON`, `PRIOR_DOCUMENTED_EVENT`, `VERIFIED_REAL_WORLD_FACT`, `HISTORICAL_INTERPRETATION`, `NEW_FICTIONAL_DRAFT`, `PROPOSED_CANON_CHANGE`, and `UNVERIFIED`.
- Distinguish access classes such as `PUBLIC`, `INTERNAL`, and `RESTRICTED` only when actual access controls support them.
- Make event history and immutable evidence snapshots append-only where the approved schema requires it. Record corrections as superseding entries with a reason; do not silently erase history.
- Record actual creation, modification, approval, and commit status. A draft in chat is not a committed record.

Where the approved schema supports a common record envelope, include actual `record_id`, `record_type`, `schema_id`/version, parent IDs, record version/status, real timestamps and actors, source references, access classification, change reason, and superseded-record reference as applicable.

## 4. Calendar, identifiers, and temporal evidence

Use an approved effective-dated calendar record and approved ID mapping first. If the standard calendar calculation is applicable, retain the inputs and results required by CC-UMP Part II:

- Approved phase dates and production timezone.
- First Monday on or after phase start.
- Requested local date and elapsed local calendar days.
- Episode number, episode day, chapter working day, and episode start/end.
- Validation that the full Monday-to-second-Friday episode fits the phase.
- Source, calculation, exception, and approved legacy/canonical ID crosswalk.

The five nominal eight-week phases do not cover the full year. Do not infer dates for gaps, incomplete phases, legacy Foundation mappings, or historical dates without valid authority.

Each daily temporal record distinguishes:

1. Production date/time and timezone.
2. Historical-reference timestamp and supported Enka location.
3. Probe/destination timestamp, location, and mission state.
4. Current headquarters/control-base location and each relevant character/team location.

Retain the actual endpoint source, retrieval time, returned fields, payload or approved immutable reference, and missing-field status. Do not treat a live Probe payload as an effective-dated historical calendar record.

## 5. Episode-owned logical record families

The approved physical file layout may differ. These logical capabilities should be represented in the approved archive or its authorized equivalent:

| Record family | Purpose |
|---|---|
| `episode_manifest` | Approved episode/season/chapter IDs, calendar, owner, source versions, title/status, and archive references |
| `episode_context_snapshot` | Dated episode premise, approved and draft threads, relevant canon, and starting states |
| `calendar_probe_record` | Daily date calculation, three clocks, locations, endpoint evidence, and status |
| `source_snapshot_register` | Source revision/fetch details and immutable evidence pointers |
| `daily_chronicle_record` | Story revision, date/day slot, research and continuity references, and editorial status |
| `research_register` | Claim-level sources, educational material, selected/rejected research, and classifications |
| `source_permission_register` | Access eligibility, publication eligibility, consent, licensing, restrictions, and revocation checks |
| `role_project_log` | Organization-chart/check-day source, featured roles, verified project facts, and fiction/real distinction |
| `mission_state_record` | Mission stage, roster, locations, equipment/energy, communications, objectives, and risks |
| `character_state_record` | Episode-specific state deltas linked to approved character canon |
| `storyline_register` | Open, advanced, resolved, or deferred narrative threads |
| `continuity_event_log` | Append-only material events, causes, consequences, provenance, and status |
| `challenge_public_register` | Public wording, challenge ID, intended learning, release status, and opaque secure-record reference |
| `challenge_answer_key` | Answer and evidence, stored only in an authorized restricted system |
| `production_manifest` | Story and derivative versions, approvals, dependencies, and stale/review states |
| `service_card_register` | Optional sourced and approved card candidates or deliverables |
| `editorial_decision_log` | Human decisions, proposals, approvals, rejections, deferrals, and canon promotions |
| `exception_conflict_register` | Missing evidence, conflicts, impacts, resolution, and blockers |
| `validation_report` | Actual daily/episode checks, results, evidence, and reviewer |
| `handover_record` | Portable, source-linked state for the next authorized run |

A non-applicable record family should be marked truthfully, such as `NOT APPLICABLE` or `NO CHANGE`, with a reason where useful. Do not create fictitious IDs or completed records just to fill a schema.

## 6. Manifest and daily chronicle record

The episode manifest should, where known, identify actual approved season/chapter/episode IDs and legacy mappings, calendar authority, timezone, episode dates, source versions, title and title status, archive references, owner, and actual editorial status.

The daily chronicle record should reference the actual chronicle and episode IDs, production date and weekday, episode day, chapter working day, calendar evidence, prompt/protocol/schema versions actually used, source and temporal snapshot references, exact story revision or genuine asset reference, status, prior chronicle/handover, research, permissions, challenge, mission, continuity events, and derivatives.

Permitted story statuses may include `DRAFT`, `AWAITING_REVIEW`, `APPROVED`, `LOCKED`, `REJECTED`, or `WITHDRAWN`, according to the approved schema. An AI cannot transition a record to an approval or lock state.

The public export contains only the public chronicle and its final audience challenge. Internal metadata, Output B, and restricted Output C are not part of that public asset.

## 7. Continuity events and current state

Create a continuity event for a material new story occurrence, relationship or mission change, consequential research reference, editorial correction, or storyline transition. Record, where applicable:

- Stable event ID and chronicle/episode references.
- Narrative timestamp and time axis: `PRODUCTION`, `HISTORICAL`, `PROBE`, or `IN_UNIVERSE_UNRESOLVED`.
- Character, location, mission, and storyline references.
- Summary, cause, consequence, and follow-up.
- Evidence/source references and evidence classification.
- Draft/approval status.
- Superseded event ID and correction reason, if applicable.

Maintain derived current character and mission states from documented events and approved canon. Track known locations, knowledge, capability limits, relationships, obligations, mission objective/stage, communications, equipment, energy, risks, and return obligations only as supported by records. Never make an unknown state appear verified.

Role/project records should preserve the chart version, chapter working day/check day, scheduled and featured roles, and the difference between verified Koware activity, fictional depiction, and proposed follow-up.

## 8. Research and permission provenance

Associate important factual or educational claims with their actual sources and dates. Include, when applicable:

- Eternal Dreamfall entry, work classification, approved date/week mapping, and passage status.
- Actual YouVersion verse or accurately attributed alternative.
- Verified Buzzjuice course/module/lesson and relevant section.
- Historical evidence tied to Clock B.
- Current reporting tied to Clock A, distinguishing event date from publication date.
- Probe research tied to Clock C; label future/alternate material fictional.
- Weather/environment evidence, if reported as observation.
- Approved canon, archive, role, project, or diary sources and the permitted purpose for use.

Track retrieval permission separately from publication eligibility. A public repository or accessible file does not establish consent, license, or permission to depict a person. Unknown, withdrawn, or insufficient permission blocks the affected use. Record actual evidence and review status; do not invent consent.

## 9. Challenge record and release control

The public challenge record may contain its ID, exact wording, public options, non-answer-revealing fairness criteria, intended learning, release status, and an opaque reference/status for the restricted key.

The answer key contains the solution, explanation, acceptable alternatives, evidence, hints, review state, release schedule, access policy, and authorizing editor. Store it **only** in an actually authorized restricted channel. If no such mechanism is verified, record `RESTRICTED ANSWER RECORD — SECURE STORAGE REQUIRED`; do not generate or disclose the answer in ordinary Output B or handover.

Default answer release is with the next episode. A final-chapter exception requires a recorded human decision.

## 10. Output B crosswalk to episode records

The CC-UMP v0.04.00 defines these exact Output B headings. Use them in the same order:

| Master heading | Record families most directly supported |
|---|---|
| **B1. Run and temporal manifest** | Episode manifest, calendar/Probe record, daily chronicle metadata, source snapshot |
| **B2. Research/source register** | Research register, source snapshots, permission references |
| **B3. Character, Koware role and project register** | Character state, role/project log, permission and decision references |
| **B4. Mission and technology state** | Mission state, mission-related character/event deltas |
| **B5. Append-only continuity and story ledger** | Continuity event log, storyline register, derived current state |
| **B6. Portable production handover** | Handover record, references to current approved/draft states |
| **B7. Derivative/media and challenge status** | Production manifest, Service Card register, public challenge register, opaque restricted-key reference only |
| **B8. Validation, exceptions and approval register** | Validation report, exception/conflict register, editorial decision log, actual write status |

Permissions and editorial status remain required information even though they are not standalone headings in the master: include them under the relevant B2/B3/B7/B8 sections. Do not put challenge answers in B7 or B8.

## 11. Daily reconciliation and handover workflow

For each authorized run:

1. Read the actual episode manifest/context, previous chronicle, latest handover, current continuity and mission states, source permissions, decisions, and derivative manifest.
2. Record source versions and the actual requested date. Pin temporal evidence without overwriting prior snapshots.
3. Draft one Output A and the master-aligned Output B1–B8. Use Output C only through authorized secure storage.
4. Identify deltas: new events, changed derived states, research sources, permissions, mission/role changes, challenge status, derivative dependencies, and exceptions.
5. Validate IDs, timestamps, story chronology, evidence classifications, permissions, challenge separation, status transitions, and the complete B output.
6. If an authorized write is available and requested, verify the approved path, authorization, latest revision, and concurrent changes before writing. Otherwise report `DRAFTED — NOT COMMITTED`.
7. Record only human decisions that actually occurred. Provide a portable handover that distinguishes approved, draft, unresolved, blocked, and unpublished material.

If another contributor changes a record during drafting, re-read and reconcile the latest revision. Do not silently overwrite concurrent changes.

The handover should include actual IDs and version/status; calendar and three-clock evidence; concise account of what happened; character, mission, and storyline states; role/project context; key research and permission warnings; challenge ID and opaque secure-key status; derivatives and stale flags; open questions and next evidence; safe continuity constraints; and actual storage status. On day 10, report compilation readiness and open work, not presumed episode completion.

## 12. Episode compilation and roll-up

Episode compilation is a separate, human-led task after ten distinct chronicles have been separately generated. It should verify:

1. Ten distinct day slots and valid calendar evidence.
2. Approved or locked chronicle revisions and chronological continuity.
3. Event history, character/mission states, source provenance, permissions, and unresolved exceptions.
4. Ten public challenges and restricted answer custody/release decisions.
5. Derivative dependencies, rights, and stale status.
6. Editorial review, episode title decision, publication authorization, and actual archive writes.
7. Approved chapter/season/franchise roll-ups with provenance and backwards references.

Ten records alone do not prove an episode is complete, approved, published, or archived. Do not move episode-owned data into the persistent AI Desk by default.

## 13. Migration and acceptance

Preserve v0.03.01 records and existing archive paths until an authorized migration plan is approved. A migration should retain original provenance, map fields and IDs non-destructively, identify any exposed challenge answers for security remediation, and verify permissions, links, revisions, and concurrent changes.

A controlled pilot should demonstrate that:

- Ten daily chronicles are produced separately and correspond to valid day slots.
- Temporal snapshots distinguish production, historical, and Probe data.
- Claims are sourced and classified, and fictional future events are not presented as news.
- Draft events do not rewrite approved canon.
- Permissions, answer-key separation, and public challenge placement are maintained.
- A receiving editor can continue from the portable handover without hidden chat history.
- Actual writes, approvals, and publications are evidenced; unperformed actions remain proposals.
- The approved archive and AI Desk boundaries are respected.

# 1. Updated Daily Chronicle Generation Protocol

```markdown
# CLASSIES CHRONICLES — DAILY CHRONICLE GENERATION PROTOCOL

## Daily execution procedure for the Unified Master Prompt

| Control | Value |
|---|---|
| Document ID | CC-DCGP |
| Version | 0.04.00 |
| Status | PROPOSED — requires authorized human editorial approval |
| Governing master | CC-UMP v0.04.00 — `Classies_Chronicles_Unified_Master_Prompt_v0.04.00.md` |
| Record specification | CC-ECLPM v0.04.00 |
| Replaces upon approval | CC-DCGP v0.03.01 |
| Operational unit | Exactly one authorized production working day |
| Prepared | 2026-11-05 |

> **Authority boundary.** This protocol implements CC-UMP v0.04.00. It does not override the master, approved Studio Blueprint, approved franchise canon, approved calendar records, permissions, publication rules, or human editorial decisions. If CC-UMP v0.04.00 has not been adopted, identify it as the requested working baseline, not ratified authority.

---

## 1. Purpose

This protocol defines the ordered execution path for generating **one** daily Classies Chronicle and its separate internal production records.

It answers:

- What must be checked before generation begins.
- What order the daily workflow follows.
- When the run may proceed, proceed with disclosed omissions, or stop.
- How the daily output maps to episode-owned records.
- What must be handed to the next authorized editor or provider.

The master remains authoritative for **what** the chronicle must contain and what rules govern it. This protocol governs **how** a daily run is executed.

---

## 2. Activation and request classification

Activate this protocol only for an explicitly authorized daily generation request.

Classify the request first:

| Mode | Treatment |
|---|---|
| `REVIEW_ONLY` | Do not generate a chronicle |
| `DAILY_GENERATION` | Execute this protocol for one eligible weekday |
| `SPECIAL_WEEKEND` | Execute only if separately authorized and scoped |
| `COMPILATION` | Use the episode compilation workflow, not this daily protocol |
| `DERIVATIVE` | Use the applicable comic, video, audio, or media workflow |
| `OTHER` | Resolve scope before proceeding |

A request to inspect, revise, discuss, or approve this protocol does **not** activate chronicle generation.

A daily run produces:

1. **Output A — Public Daily Chronicle draft.**
2. **Output B — Internal Production and Handover Appendix, B1–B8.**
3. **Output C — Restricted Challenge Answer Record**, only through a demonstrably authorized restricted channel.

Never combine A, B, and C into a public-facing artifact. Never place an answer, answer-revealing hint, source key, or restricted metadata in Output A or Output B.

---

## 3. Preconditions

Before drafting, establish the following from actual sources or record an explicit unresolved status:

1. Authorized production date and approved timezone.
2. Approved or explicitly provisional season, chapter, episode, and chronicle identifiers.
3. Effective-dated calendar authority or a clearly identified calendar exception.
4. Current episode manifest, context snapshot, and latest approved or clearly labeled draft chronicle.
5. Latest continuity, mission, character, storyline, permission, and handover records.
6. Applicable character canon, capability limits, visual references, and diary-use permissions.
7. Required temporal evidence for production, historical-reference, and Probe/destination clocks.
8. Required source access for Eternal Dreamfall, Verse of the Day, Health & Safety, historical/current/probe research, and Koware records.
9. Challenge-release status and secure-answer-storage status.
10. Any active editorial decisions, conflicts, revocations, or derivative-staleness flags.

Do not infer a missing permission, calendar assignment, archive record, endpoint field, or approval from convenience.

---

## 4. Daily execution sequence

Execute the following sequence for one authorized day.

### Step 1 — Confirm run scope

- Confirm that the request is `DAILY_GENERATION` or an authorized special.
- Confirm exactly one requested production date.
- Confirm the approved production timezone.
- Confirm that no additional chronicle, episode compilation, media asset, publication, reward, or archive write has been authorized.

### Step 2 — Load governing context

Load, inspect, and record:

- CC-UMP v0.04.00.
- CC-ECLPM v0.04.00.
- Current approved governance and Studio Blueprint references.
- Current episode manifest and context.
- Latest prior chronicle and handover.
- Applicable canon and permissions.

Record document versions, approval status, retrieval status, and any version conflicts.

### Step 3 — Establish temporal evidence

Use CC-UMP §7–§8.

- Acquire or inspect the Millennium Probe and, where required, historical/probe supplemental interfaces.
- Pin one immutable run snapshot.
- Record the exact retrieval time, timezone/offset, returned fields, missing fields, raw payload or approved immutable pointer, and validation status.
- Keep Clock A production, Clock B historical reference, and Clock C Probe/destination separate.
- Record production, historical, destination, headquarters, and individual team-member locations separately.

Do not reuse an old Probe response as a live read. Do not use a current Probe snapshot to retroactively establish the phase of an earlier requested date.

### Step 4 — Resolve calendar and identifiers

Use an approved calendar manifest where available. Otherwise apply CC-UMP §8 only when its stated conditions are satisfied.

Record:

- `phase_start_date_local`
- `phase_end_date_local`
- `production_timezone`
- `anchor`
- `elapsed_days`
- `episode_number`
- `block_day`
- `chronicle_number`
- `chapter_working_day`
- `episode_start_date`
- `episode_end_date`
- Legacy identifier mapping
- Any exception, gap, partial episode, or unresolved mapping

A weekend receives a weekend status or separately authorized special treatment. It does not receive a normal chronicle number.

### Step 5 — Load continuity and mission state

Inspect the current episode-owned continuity state.

Record:

- Open, advanced, resolved, and deferred storylines.
- Character knowledge, relationships, locations, obligations, and capability restrictions.
- Active or absent Edubeam mission.
- Mission stage, roster, communications, equipment, energy, risks, and unresolved retrieval obligations.
- Koware role-check day, scheduled roles, aliases, and relevant project context.

Do not reset a mission at day boundaries. Do not fabricate a mission, team return, staff member, project completion, or organizational action.

### Step 6 — Perform six-stage synthesis

Perform the six cumulative editorial stages defined in CC-UMP §16:

1. Eternal Dreamfall Bible Study.
2. Eternal Dreamfall Chronicle.
3. Refreshed Eternal Dreamfall.
4. Headlined Eternal Dreamfall.
5. Classies Eternal Dreamfall.
6. Classies Chronicles.

These are internal research and editorial layers. Produce one integrated public story, not six separate drafts or six published sections.

For each stage, record only the evidence, selection, uncertainty, classification, and use permission required by CC-ECLPM v0.04.00.

### Step 7 — Plan and draft the story

Prepare a compact private plan containing:

- One major causal movement.
- Principal characters and setting.
- Character goals, stakes, conflict, choice, and consequence.
- Relevant continuity constraints.
- One or two meaningful relationship or character changes.
- Educational, organizational, historical, or mission motifs where relevant.
- A credible ending and next-day continuity needs.

Write Output A as one original, standalone, engaging narrative. Integrate only verified or properly fictionalized material that serves the scene.

The public chronicle must end with exactly one audience challenge. Nothing public may follow it.

### Step 8 — Prepare internal records

Prepare Output B1–B8 in the exact order and with the field semantics defined by CC-ECLPM v0.04.00.

Use only actual values or explicit statuses:

- `UNVERIFIED`
- `INACCESSIBLE`
- `NOT_APPLICABLE`
- `AWAITING_EDITORIAL_DECISION`
- `DRAFTED — NOT COMMITTED`

Never populate a record with invented IDs, dates, source results, mission data, permissions, or approvals.

### Step 9 — Handle the challenge answer

Design one fair challenge answerable from public material or explicitly permitted references.

- Place the public challenge as the final element of Output A.
- In Output B, include only the challenge ID, public wording/reference, planned release episode, and opaque restricted-record status.
- Create Output C only if an authorized access-controlled storage channel actually exists.
- If no secure channel exists, record `RESTRICTED ANSWER RECORD — SECURE STORAGE REQUIRED` in Output B8 and do not generate or expose the solution.

Default release is with the subsequent episode, subject to an explicit human exception.

### Step 10 — Run quality gates

Apply the quality gates in CC-UMP §23 and the daily gate table in §6 below.

If a nonessential source is unavailable, omit it transparently and record the omission. If an essential dependency is unavailable, issue a `BLOCKED — SOURCE OR APPROVAL REQUIRED` report rather than producing a misleading complete chronicle.

### Step 11 — Prepare handover

Prepare a portable Output B6 handover that allows the next authorized editor or provider to continue without relying on another model’s hidden memory.

The handover must distinguish:

- What happened in the story.
- What remains unresolved.
- What is approved, draft, proposed, or unverified.
- What was actually written or committed.
- What remains pending human review.

## 5. Output separation

### Output A — Public chronicle

Output A contains only:

- Resolved or qualified daily identification.
- Provisional daily title, where appropriate.
- One standalone literary narrative.
- Continuity-consistent character, mission, location, and relationship material.
- Earned final beat.
- Audience challenge as the final public element.

Output A must not contain:

- Six-stage labels.
- Research tables.
- Source lists.
- Probe diagnostics.
- Internal statuses.
- Continuity logs.
- Challenge answers.
- Answer-revealing hints.
- Editorial notes.

### Output B — Internal production appendix

Output B contains B1–B8 only, using the CC-ECLPM v0.04.00 record mapping.

### Output C — Restricted answer

Output C exists only in an authorized restricted environment. It is never part of ordinary chat output, public files, normal repositories, or portable handovers.

## 6. Daily quality gates

| Gate | Pass condition | Failure response |
|---|---|---|
| Scope | Exactly one authorized daily chronicle and requested deliverables | Cancel unintended work |
| Calendar | Date, timezone, phase, episode position, and chapter working day validated or explicitly unresolved | Block definitive Output A if essential |
| Three-clock integrity | Production, historical, and destination clocks and locations remain separate | Correct metadata or report missing evidence |
| Canon and continuity | Approved character, technology, mission, and prior-event constraints respected | Block or escalate contradiction |
| Research | Essential claims sourced; optional omissions disclosed | Omit optional item; block essential failure |
| Rights and privacy | Retrieval and publication eligibility distinguished; revocations checked | Exclude affected material; block if indispensable |
| Narrative | One causal movement, original prose, earned ending, continuity respected | Revise before release |
| Challenge | Fair, public-answerable, final public item, no answer leakage | Revise or withhold |
| Records | B1–B8 present with genuine values or explicit statuses | Mark incomplete or blocked |
| Commit status | Actual repository writes distinguished from drafted output | Record `DRAFTED — NOT COMMITTED` |
| Approval | No unapproved publication, canon promotion, archive write, or approval claim | Leave pending for human action |

---

## 7. Stop conditions

Stop definitive public generation and report a blocker when:

- The requested production date or episode assignment cannot be established.
- Phase boundaries, timezone, or calendar evidence conflict.
- Essential locked canon cannot be reconciled.
- Required participant consent or publication permission is absent, revoked, or unknown.
- A mandatory factual, educational, or source-backed input cannot be acquired after reasonable authorized attempts.
- Secure challenge-answer storage is required but unavailable.
- The requested output would disclose restricted information or create an unauthorized derivative.

Do not replace a blocker with invented material.

---

## 8. Handover and next-run procedure

After drafting:

1. Prepare the daily record delta.
2. Mark all uncommitted work as `DRAFTED — NOT COMMITTED`.
3. Provide the portable B6 handover.
4. Identify actual versus pending archive writes.
5. Identify unresolved editorial decisions.
6. Identify source-version and derivative-staleness risks.
7. On the next authorized run, read the latest handover, current episode-owned ledger, latest approved chronicle, and any later approved corrections.

Do not treat a prior model’s hidden conversation memory as authoritative continuity.

---

## 9. Portable execution directive

When explicitly commissioned to generate a Classies Chronicle:

1. Load CC-UMP v0.04.00, CC-ECLPM v0.04.00, current governance, episode context, and applicable permissions.
2. Confirm one authorized production day and timezone.
3. Acquire and pin genuine temporal evidence.
4. Resolve calendar position and identifiers.
5. Reconcile continuity and mission state.
6. Perform the six-stage synthesis.
7. Draft one public chronicle ending exactly with its audience challenge.
8. Prepare separate B1–B8 internal records and a portable handover.
9. Create a challenge answer only through an authorized restricted channel.
10. Apply quality gates, disclose omissions, stop on essential blockers, and never claim unperformed writes, approvals, publication, or other real-world actions.

## 15. Daily reconciliation workflow

When a daily generation is authorized:

1. Read the current approved episode manifest, context, prior chronicle, latest ledger, mission/character/storyline state, permissions, and decisions.
2. Pin or inspect verified temporal evidence.
3. Derive calendar position without overwriting a prior day’s snapshot.
4. Draft Output A and Output B1–B8.
5. Identify record deltas.
6. Validate IDs, timestamps, chronology, permissions, classifications, challenge separation, and state transitions.
7. If authorized repository write access exists, confirm approved paths, check concurrency, append immutable events/snapshots, and update materialized state pointers only with evidence of success.
8. If no write occurs, record `DRAFTED — NOT COMMITTED`.
9. Obtain human review for approval, lock, publication, canon promotion, or restricted release.
10. Issue a portable B6 handover reflecting actual accepted, draft, unresolved, unpublished, and blocked states.

If another collaborator changes the ledger during drafting, re-read the latest revision, compare changes, record the conflict, and reconcile through the authorized editor. Do not silently overwrite.

4. Concise actual story recap with causal outcomes.
5. Character state changes, locations, knowledge, relationships, and capability restrictions.

7. Organizational chart version, chapter working day, role spotlight, and real-versus-fictional project context.

10. Open, advanced, resolved, and deferred storylines.
11. Challenge ID, public wording reference, planned release, and opaque secure-key status only.
12. Service Card and derivative status.
13. Outstanding conflicts, blockers, missing evidence, and owners.
14. Safe next-day starting context without a mandated plot.
15. Actual record storage status: `DRAFTED — NOT COMMITTED`, `COMMITTED` with evidence, or `INACCESSIBLE`.

## 17. Episode completion

1. Verify ten distinct weekday slots in chronological order.
2. Reconcile immutable event history, character state, mission state, and research provenance.
3. Recheck rights, consent, source versions, and outstanding exceptions.
4. Verify ten public challenges and restricted answer custody.
5. Reconcile derivative assets against approved source versions.
6. Compile the episode.
7. Obtain human editorial approval.
8. Archive the approved master.
