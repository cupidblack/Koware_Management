## 6. The most consequential compatibility changes

### 6.1 Exact v0.04.00 B1–B8 headings

1. **B1. Run and temporal manifest.**
2. **B2. Research/source register.**
3. **B3. Character, Koware role and project register.**
4. **B4. Mission and technology state.**
5. **B5. Append-only continuity and story ledger.**
6. **B6. Portable production handover.**
7. **B7. Derivative/media and challenge status.**
8. **B8. Validation, exceptions and approval register.**

The current master does **not** allocate B7 as a dedicated rights/production/editorial heading. Those essential fields are cross-cutting: rights evidence in B2/B3/B7, actual editor/permission decisions in B7/B8, and source-specific ownership in CC-ECLPM. Creating an additional ninth B section would itself introduce drift. The exact eight-heading mapping appears identically in both new companions.

### 6.2 Canonical families and the legacy calendar record

The master's §20 list contains **19** named families. The old ECLPM's `calendar_probe_record` is useful, but not one of those nineteen. This review recommends a **non-destructive compatibility alias/view** retaining the old record's captured three-clock/calendar evidence while logically mapping it to master-owned B1/manifest/snapshot/day-record semantics. This choice resolves the count discrepancy without losing a real stored legacy record or inventing an additional required family. Whether to implement a physical table, view or merged Markdown section belongs to the **approved Studio Blueprint and migration owner**.

### 6.3 Restricted key: drafting vs releasing

CC-UMP explicitly says to **withhold restricted C and report absence of custody** when no actually secured store exists. It does not universally require blocking an otherwise source-safe **draft A**. The updated companions therefore distinguish:

- **Draft production:** a fair question may end A; no solution is generated/persisted in ordinary A/B; B7/B8 records custody needed.
- **Restricted solution work:** occurs only with verified role authorization and secure storage; no public/internal key exposure.
- **Publication or competition:** may require separate human approval that verifies key custody, grading, fairness or reward terms. That decision can block **release**, but is not an invented blanket block on mere writing.

This correction follows the higher-priority explicit master contract while preserving platform reviewers' legitimate concern about accidental key exposure.

### 6.4 Evidence and approved storage

An actual live Probe response is a run snapshot, not an approved calendar, especially for retrospective requests. A file that appears in GitHub is not necessarily approved, permission-cleared, immutable or adopted. An agent-generated handover is not a repository commit. The documents therefore require actual timestamped source reads, approved manifest mappings, rights checks, commit receipts and explicit human approval evidence where relevant. In the absence of such evidence, the truthful outcome is **drafted and not committed**, not a fictional completed workflow.
