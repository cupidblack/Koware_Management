# 1. Executive finding

**Retain the Master Comic Generation Prompt as a dedicated, explicitly commissioned derivative-production document.** The Unified Master Prompt specifies the creative/editorial authority, conditions for ordering a comic, public/internal/restricted data separation, continuity and high-level media expectations. It does **not** specify enough comic-oriented narrative allocation, camera/panel design, visual canons, typography, image-generation verification, collage geometries, production manifest semantics or per-page quality assurance to replace a specialized comic prompt. The Daily Chronicle Generation Protocol produces **one textual chronicle** per eligible day; the Episode Continuity Ledger describes **episode-owned state and records**; the comic prompt converts an authorized Output A revision into **traceable visual derivatives**. The review document logs recommendations and adoption decisions, not story text or a competing record schema.

The v0.03.01 comic prompt already supports most of the right mechanics: separate review/plan/storyboard/generate/assemble modes; original, cinematic visual retelling; binding commissioned page counts; complete 9:16 portrait pages; five-stage dramatic progression; five-level A–E panel scale; character, mission and prop continuity; no visible scene/panel numbering; an unanswered exact public challenge as the final element; manifest/QA/stale dependency tracking; and truthful distinction between draft and publication. **Preserve those capabilities.** The v0.04.00 upgrade is a precise authority, source, security, feasibility and cross-document refactor, not a replacement of visual storytelling with administration.

The supplied multi-platform compilation contains several overlapping candidate versions and critiques, some already asserting completion or adoption. Such assertions are not independent evidence that a file was ratified, a QA test ran, a repository changed, a renderer produced images, or a storage hook exists. This review incorporates feasible advice while explicitly rejecting unsupported implementation claims. The source compilation also includes a statement that the v0.04 ledger has **18** record families; the actual CC-UMP §20 and CC-ECLPM §4 inventory contains **19**. The resulting prompt follows the actual inventory.

**Recommendation:** approve the updated comic prompt and this review together only after verifying the governing approved Studio/canon/rights baseline and performing an evidence-based short-form pilot. Documents are complete, portable **draft specifications**, not automatically production-released tools.

Approved franchise governance, Studio Blueprint and locked applicable canon control their scopes. ## 5.4 `PERPLEXITY-1` material

## 5.5 Rules for choosing between conflicting recommendations

A higher-numbered **unapproved** draft does not automatically displace an approved canon or release rule. Exact owner-commissioned page count outranks a default category, but not actual renderer limitations or missing consent. A public question belongs to its approved revision; a mismatched register is a **conflict**, not a license to choose one automatically. Separate image output requirements and composite rendering are complementary **only if** pixel geometry and actual deliverable inventory match the commission. Where suggestions assert actual integrations without evidence, retain the desired *requirement* as a conditional design and reject the unsupported assertion of deployment.

# 8. Mobile geometry and media feasibility decision

Let each page have integer width **W** and height **H** satisfying **H/W = 16/9**, with required QA at mobile viewing scale.

| Delivery/rendering form | Pixel geometry before padding/gutters | Interpretation |
|---|---|---|
| One independent page | W × H | Must be complete, readable, 9:16 |
| N independent pages | N distinct files/assets, each W × H | Preferred for per-page quality; exact asset count documented |
| One-column vertical scroll of N pages | W × N·H | Total aspect 9:(16N), **not** 9:16 when N>1 |
| 2×2 four-page sheet | 2W × 2H | Outer ratio happens to be 9:16; cell legibility still must be checked |
| 2×4 eight-page sheet | 2W × 4H | Outer aspect 9:32; may exceed renderer pixel support |
| 1×8 eight-page scroll | W × 8H | Outer aspect 9:128; high risk of unreadable letters if downsized |

Example when the tool genuinely supports 1080×1920 cells: a four-cell 2×2 sheet requires **2160×3840 px**; an eight-cell 2×4 sheet requires **2160×7680 px**. These are *computed design requirements*, not assertions that a given image generator can produce or export them. Never equate an eight-cell low-resolution image with eight validated standalone comic pages. After slicing, inspect the actual dimensions, text and crop for each result; record the count of genuinely created slice files. The **explicit commission** controls whether separate page images, a single composite or both are required.

The five visual intensity classes A–E and varied composition survive the upgrade. Requiring 3–5 panels on *every* page was not adopted because it conflicts with full-page splash layouts and scene pacing. Branding, optional page counts and caption colors remain conditional on actual approved design specifications.

# 9. Challenge and release decision logic

The challenge is a **public narrative artifact** but the answer is **restricted**. The `challenge_public_register` is an authoritative public-challenge state record when approved/available; the actual chosen Output A revision is the exact narrative text the comic must adapt. Their relationship is **reconciliation**, not silent replacement. If both versions disagree in wording, options, punctuation affecting meaning or publication status, register a conflict and do not claim final-page approval until a human decides what public revision is valid.

If the register cannot be accessed, the exact Output A wording may be used for a **clearly provisional draft-only** page only when the relevant approved policy permits; record the unavailable source and the verification deficit. If no complete public question exists in the authorized source, don't invent one, derive one from restricted C or call an incomplete final image complete. A challenge is terminal in **all forms**: no post-challenge copyright line, logo, series identification, URL or page counter in the image. The source's earned narrative closure must appear before the question.

To prevent accidental solutions, inspect obvious answer-revealing visual clues using public text and source meaning. Do not retrieve C. If the distinction requires secret knowledge, have a **qualified, separately authorized** reviewer conduct any restricted check through the approved secure process and return only a nonrevealing pass/fail decision to production. Avoid false claims that an image generator can guarantee semantic secrecy without access to a review mechanism.

The comic workflow does not release answers, issue keys, adjudicate prizes or override CC-UMP's default next-episode challenge answer timing. Those remain separate governance and restricted-store decisions.

# 10. Approval, roll-out and rollback

## 10.1 Adoption prerequisites

1. An authorized owner confirms **which approved franchise/Studio and canon versions actually govern** the pilot; treat the v0.04.00 technical set as a working candidate until formally ratified.
2. Owner/editor approves the updated `CC-MCGP v0.04.00` and companion `CC-MCGP-REVIEW v0.04.00`, without retroactively overwriting the v0.03.01 historical review.
3. Select an **actually accessible, fully identified Output A revision** and determine whether it is a draft-test source or an approved publication-eligible story. Do not guess a chronicle's approval merely from its title or prior chat mention.
4. Verify permitted visual canon, brand license, actual personal-portrayal consent, applicable Edubeam capability constraints and public challenge source.
5. Identify the authorized reviewers, target mobile output specs and true allowed archive/storage operations.
6. Conduct a small 3-page or standard 5-page pilot, then a 4-page count-override and 16-page stress test as production capacity and permissions allow; measure actual result—not hypothetical compliance.
7. Record all tested pages/files, source/rights/canon/checks and editorial decisions in authorized ECLPM-compatible records.
8. Only after QA and an actual separate human release decision may publication proceed through the authorized publishing process.

## 10.2 Failure/rollback

A failure in canonical source reconciliation, visual consent, answer-leak safeguards, essential narrative fidelity or actual renderer capacity is a **release blocker**, not a reason to reduce requirements silently. Preserve prior accepted assets; flag new draft and affected dependencies; use source-versioned corrections rather than destructive overwrite. If v0.04.00 adoption must be reversed, re-enable the last **actually approved** version, preserve both draft and accepted revision history, and inspect derivative dependencies made under the reverted baseline. A rollback is itself an authorized recorded action, not a claim created by this document.
