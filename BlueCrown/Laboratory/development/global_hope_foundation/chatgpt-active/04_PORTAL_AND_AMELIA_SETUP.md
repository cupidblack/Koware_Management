# Deployment runbook: Buzzjuice, Koware.org, Google Forms and Amelia
**Release:** 1.00 | **No live form or booking URLs have been invented.**

## A. Account, law and permissions — deployment gate

1. Confirm Hopeful Way Foundation is the intended data controller; document the responsible administrator and the Foundation's Ghana Data Protection Commission registration/compliance status. Review Act 843, data minimisation, lawful consent, Google cloud arrangements, access, 90-day proposed inactive-lead schedule and withdrawal mechanism. Obtain sign-off before accepting submissions.
2. Use a Foundation-managed Google account with MFA. Do not create client responses in a private team member's personal Gmail account or a public GitHub repository.
3. Designate **one primary privacy/intake owner** and **one named backup**. Limit Google Sheet access to these people and the Chapter Chairperson only as genuinely needed. Do not enable link access, publishing, anonymous sharing or forwarding of submission notifications with identifying content.
4. Create a restricted private folder for the final signed presentation authority, current dated bylaws, house costs, risk/incident procedures, acceptance votes and actual financial documents. Keep these outside public GitHub.

## B. Run the Apps Script to create the intake Form and Sheets

1. Go to https://script.google.com/ and create a new project titled `Hopeful Way Oxford House Intake v1` while signed into the approved Google account.
2. Delete the default sample code; paste the complete source from `02_GOOGLE_FORM_BUILDER.gs`, save, and run `createHopefulWayIntake`. Read the account permission prompts and authorise only if consistent with the approved Foundation policy.
3. Open **Executions** and identify the **Form edit URL**, **Form public respondent URL**, **restricted Sheet URL**. Copy those only to the private implementation record. They are generated by Google; they are not present in this deliverable because the account has not been used here.
4. Confirm the Form remains **not accepting responses** until the public wording and privacy terms are approved.
5. Verify each field and set Form permissions: no forced login, no respondent list, no public response charts, no automatic collection of personal Google email, no access for the public to the underlying Sheet. If Google requires an explicit **Publish** step, perform it after final approval.
6. Run a test (test persons must be synthetic and obviously fake), confirm the Pipeline tab receives a unique case reference, verify the generic notification to `support@buzzjuice.net`, and test access from a private browser. Check the configured notification recipient is monitored; the actual mail account must be able to receive messages from Apps Script.
7. Delete synthetic submissions from Form and Sheet, ensure case-reference rows/notification copies are cleared, and confirm row data do not appear in the public form. Open responses only after approval.

**Data route:** The form saves complete consent/interest responses in **Google Forms and linked response Sheet**; a **separate internal Pipeline tab** stores a pseudonymous reference and stage, not medical details. The support email receives only a generic “new submission” notice and case reference.

## C. Branded immediate-load link

The public requested paths are:
- Primary: https://buzzjuice.net/hopefulway-oxfordhouse
- Secondary: https://koware.org/hopefulway-oxfordhouse

**Recommended pilot:** Make the primary path a temporary (HTTP **302**) redirect to the *Google Forms respondent URL generated in step B*. The visitor then sees the form without another button click. The secondary path redirects to the primary path. Use a durable **301** only after the campaign and hosting arrangement are confirmed. Keep the consent notice inside the form because a redirect cannot display a separate information page first.

**Buzzjuice routing check:** First identify whether the actual URL is handled by WoWonder/Streams, an Apache `.htaccess`, NGINX config, reverse proxy or WordPress. Add the rule in that system, not by guessing. Avoid modifying a general rewrite rule that controls WooCommerce or Streams. The destination must be the **public responder link**, not the Form's editing link. A user with no Google account must be able to submit.

**Koware.org WordPress check:** If the site is WordPress, use an existing well-maintained redirect function/plugin, or website routing configuration, for the exact relative path `/hopefulway-oxfordhouse`, and set the destination to the primary Buzzjuice path. Prevent redirect loops. Test from phone and logged-out desktop.

**Alternative branded embedded page:** If a landing page is more desirable, use the Google Form `Send → Embed` iframe code once the live form exists, place it at the very top of a mobile-optimised page on Buzzjuice, and include brief context and privacy/safety links. Avoid introducing a separate “Apply” click that conflicts with the requirement that the form immediately load. The embed must show the full consent and conditions, with a mobile-friendly height and scroll behavior. Test third-party browser privacy settings and accessibility. If mobile embed is unreliable, revert to a verified direct 302 redirect.

## D. Amelia setup — separate institutional presentation service

1. Sign in to the actual Koware.org WordPress admin. Navigate to **Amelia → Employees**. Assign the Chapter Chairperson (and an authorised backup, if supported) to the presentation service. Ensure availability reflects travel/work and is synchronised to an appropriate calendar if possible.
2. In **Amelia → Catalog → Services** create **Hopeful Way Oxford House — Institutional Presentation**, duration **30 minutes**, price **GHS 0** if institutional presentations are approved as complimentary; otherwise retain the actual Foundation-approved price. Mark confirmation as controlled/approved, not assumed where staff travel matters.
3. Create separate **On-site** and **Virtual** services if attendance type cannot be captured accurately in one service; for on-site sessions, set a **30-minute buffer** and at least **48 hours' lead time** as a pilot preference. Set capacity of one institution per booking and prevent collisions across employees/calendars.
4. In Amelia **Custom Fields** configure: Institution Name, Contact Person, Official Phone/Email, Institution Town, Format, Estimated Attendees, Accessibility Needs, and Nonclinical Comments. Do **not** request names or medical history of clients.
5. Configure **Notifications** to the assigned presenter and `support@buzzjuice.net` as appropriate. Emails should carry **institution logistics only**; appointment reminders should be enabled for staff, subject to the site settings. Use `Africa/Accra` timezone.
6. Create a dedicated booking page on Koware.org and insert the proper shortcode/booking block copied from Amelia's actual configured service. Official documentation: https://wpamelia.com/documentation/amelia-shortcodes/ and https://wpamelia.com/documentation/service-quick-start/.
7. Make a test booking from an unrelated browser; verify the booking displays, emails arrive, cancellations/reschedules work and duplicate/colliding times are not exposed. Delete the test booking. Only then include the *actual page URL* in outreach.
8. Until this booking page is verified, request appointments simply by replying to the Chairperson's WhatsApp message or calling the Foundation's verified official reception contact. Never publicise a guessed Amelia booking address.

## E. Four tests that must pass before the first broadcast

| Test | Pass criteria |
|---|---|
| Applicant privacy | Incognito/mobile access to Form works; private Sheet cannot be seen; no health detail sent in email |
| Contact permission | Adult personally confirms/refuses contact; a supervisor's submission alone does not progress the adult |
| Booking calendar | Two simultaneous requests cannot book same presenter/time; timezone and travel buffer correct |
| Website links | Both canonical paths load form directly; no 404, looping redirect, long login requirement or accidental admin/edit URL |

## F. System monitoring and incident response

Every business day, the intake coordinator checks submission notifications, restricted Pipeline and withdrawn enquiries; every Friday, the Chairperson checks backlog and response time. Maintain a simple incident log for accidental personal-data sharing, spam/harassment complaints, mistaken contacts, broken links or other safeguarding events. Refer legal or clinical issues to qualified Ghana professionals. Maintain a private signed approval register showing exactly when public copy, house facts and privacy notice were authorised.
