# Deployment guide and acceptance tests
Version 1.0.0 | This is a release candidate, not a deployed service. All steps are performed by authorized administrators in the named accounts. Do not upload applicant data or authorization originals to a public repository.

## Step 1 — Approve the service and privacy terms

Follow the release gate in 01_MASTER_PLAYBOOK.md. In a restricted operations file, record decision, owner, date and evidence for each item, including actual current house availability, fees, threshold, lease, approved rules, current charter wording, local regulatory review, signatory and contact, Foundation-controlled Google account and mailbox, processor arrangements, privacy/retention policy and future contact. If the house is not accepting, change the form's wording/choices to information or future interest only before opening; if the privacy arrangements are not approved, leave it unpublished. Confirm whether a general Foundation mailbox or the technical support address is authorized to handle applicant requests. The script uses info@hopefulwayfoundation.org for applicant rights enquiries and support@buzzjuice.net for internal alerts only. Test both routing and response ownership.

## Step 2 — Create the form and registers (Google Apps Script)

1. Sign in at https://script.google.com/ using the Foundation-managed Google account. Enable MFA and confirm its Google Workspace administrator permits Forms, Sheets and Apps Script. Do not use a personal account.
2. New project; name it `HWF Oxford House Intake v1.0.0`. Set Project Settings time zone to Africa/Accra. Replace the contents of Code.gs with the entire `03_Intake.gs` file. Save.
3. Select `createHopefulWayIntake` in the function dropdown and Run. Google will request authorization for Forms, Sheets, triggers and email. The authorized owner must review permissions and approve; do not blindly bypass administrator restrictions. The function creates an unpublished form, applicant spreadsheet, separate institution spreadsheet, and form-submit plus hourly reconciliation triggers. It does not send outreach or collect data by itself.
4. View execution log for four generated URLs (form edit, responder, applicant register, institution register). Store in private operations records. Use `showHopefulWayLinks` to retrieve again, not the creation function. If creation fails, inspect execution, Drive and Script Properties (`BUILD_STARTED`, `FORM_ID`, `SHEET_ID`, `INSTITUTION_ID`, `BUILD_COMPLETE`); don't clear them or rerun until an authorized operator has reconciled incomplete assets and removed duplicates/triggers. The guard prevents accidental second builds; there is no automated rollback.
5. In the form edit UI, review each question and verify consent language. Insert the exact approved house facts (costs, rules, vacancy and terms or a safe means of obtaining them before commitment), charter wording only if verified, current contact and privacy notice including retention periods, controller and processors. Remove the internal sentence “Ghana privacy approval is required before publication” only after approval. Do not rename question titles or rearrange the routing without updating the script's `HW.questions` and re-testing; responses map to exact titles. Change choices as houses actually open/close; preserve old data interpretation. Ensure all applicants have an accessible alternative channel. Settings: no file uploads, no collecting Google account emails, no limit-to-one response requiring sign-in, no response summary, no edit link. Publish initially for synthetic testing only; choose appropriate responder access (public anyone-with-link only after approval) and confirm acceptance of responses. On newer Forms, publishing may reset accepting responses; check both in UI. Never share form edit URL.
6. In Google Drive, check form and spreadsheet access is restricted to approved staff; the form's responder permission is distinct from editor permission. The institutional spreadsheet must be shared separately with outreach staff; applicant sheet, dashboard and deletion audit restricted. Do not share form editor access with referrers. This script writes to the restricted Sheet by trigger; do not additionally create a native response destination (would create an unmanaged duplicate). On the Applicants tab the first 16 columns are workflow metadata; subsequent fields are submitted responses. Never rename headers, delete data rows manually, sort partial column ranges, or edit response ID/reference. Use filter views rather than shared sorting while triggers run. Enter admin dates as actual dates; status dropdown; owner, next action and review date mandatory operationally even though not all are machine-enforced.
7. Confirm both triggers in Apps Script → Triggers. Ensure authorized owner remains active and quotas sufficient. Review Executions daily during pilot; failed alerts are retried by hourly reconciliation. A transient failure may cause duplicate alerts; reference identifies the same record. Only generic alert and reference are sent to support@buzzjuice.net. Do not log names/phone or send whole form responses. If email fails permanently, use the restricted sheet queue and investigate mailbox/quotas; never resend via personal accounts. Do not run `handleHopefulWaySubmission` manually (requires an event); use `reconcileHopefulWayIntake` for recovery.
8. Test both self and assisted routes with invented test data marked synthetic (not real client details), submit via responder link in incognito and on phone. Check exact fields, first-person consent gate, skips, source, sponsor status, preferred location, reference, sheet, date, dashboard and email. Trigger reconciliation twice; ensure no duplicate row/alert. Test withdrawal and deletion. Close/unpublish until the entire release gate passes.

### Operating the intake register

New interest → verify applicant's personal permission directly → record Consent verified on and separate Sponsor verification as applicable → assign owner → next action date. If sponsor pending, record information-only and don't advance to a financial commitment until agreed. For self-funded adults, mark not applicable. Use the provided stages and date columns; status is current snapshot, not cumulative counts. On each contact update Last contact and Retention review on (according to approved policy, proposed 90 days after last meaningful contact for closed cases; 180 days opt-in future). Add no sensitive clinical notes; retain minimum operational notes in approved secure case record if necessary. Deduplicate manually with applicant confirmation, using deletion process for duplicate once authorized. Every morning review due actions and alerts; once weekly review dashboard and actual occupancy in separate management report. For multiple operators, use one intake coordinator responsible for register edits during pilot; avoid simultaneous sorting/deletion during trigger activity.

### Approved deletion and correction

For approved deletion: verify identity/authority, stop communications, review retention/legal exceptions, note reason category. In Apps Script Project Settings → Script Properties create `DELETE_REFERENCE` with actual application reference copied from the restricted register and `DELETE_REASON` with one of `Withdrawal`, `Retention expiry`, `Synthetic test`, `Correction replacement`. Run `deleteApprovedHopefulWayRecord`. It deletes the corresponding Google Forms response and tracker row, appends a minimal restricted audit entry and clears those properties. Inspect both stores, remove any separately exported copies according to policy, and verify a reconciliation does not re-create the record. This is not guaranteed erasure from provider backups/version history; address retention in cloud contract/policy. If failure occurs midway, check both stores and reconcile under authorized review; do not delete arbitrary rows. Corrections to submitted facts should be handled through approved private procedures; no public edit links. Audit reference is pseudonymous, not anonymous; restrict and apply its own retention policy.

## Step 3 — Publish both direct URLs (WordPress)

1. Confirm actual WordPress installation at each root, admin rights, backups, and any existing page/redirect at the target slug. `04_hopefulway-form-redirect.php` is a small plugin; package contains single-file plugin ZIP `hopefulway-form-redirect.zip`. In each WP admin choose Plugins → Add New → Upload Plugin, upload ZIP, install and activate (or place PHP in `wp-content/mu-plugins/` after review; use only one method). No other WordPress modifications required. If either site isn't WordPress, ask its host admin to configure an exact path temporary 302 to the same actual Google responder URL; no redirect to a sheet or edit URL. Do not assume a path's server architecture from its name.
2. Settings → HopefulWay Oxford House. Paste the actual published responder URL from Step 2 (a clean `/viewform` or `forms.gle` URL; remove tracking query strings). Keep disabled until approved. Plugin defaults to 503 at target path when disabled, not a fictitious form. When approved enable and Save Changes on both domains. Uses 302 and no-cache headers; no open redirect based on visitor input. It leaves all other URLs untouched. If either is cached by CDN/page cache, exclude `/hopefulway-oxfordhouse` and trailing slash from caching, purge after changes, and ensure redirect executes before any host-level rewrite.
3. Test https://buzzjuice.net/hopefulway-oxfordhouse and https://koware.org/hopefulway-oxfordhouse plus trailing slash, on a phone and logged-out browser. Both must lead to the actual same responder, not a login, edit link or 404. Test malformed URL and disabled switch on staging, verify unrelated pages unaffected, and check query parameters aren't forwarded. To rollback, disable the toggle (503 with informational message), or deactivate/remove plugin and restore prior route. Close form separately to stop submissions from already-distributed Google URLs. No new campaign links before end-to-end verification.
4. Optional: create a separate resource page with the factsheet, FAQ, official video and booking CTA, but keep the primary application URL direct. Generate QR only from the verified public URL using an approved local/organizational QR generator; test on phone. No applicant data in QR, tracking query or analytics. Put QR and human-readable URL on printed materials.

## Step 4 — Configure Amelia on Koware.org

Amelia interface and features depend on installed version/licence. Review official docs: https://wpamelia.com/documentation/service-quick-start/ ; https://wpamelia.com/documentation/amelia-shortcodes/ ; https://wpamelia.com/documentation/google-calendar-settings/ ; https://wpamelia.com/documentation/custom-fields/ .

1. In WordPress Amelia → Services create category `HopefulWay Oxford House`. Add service `Institutional Oxford House Presentation` (30 minutes, one institution per slot, no overbooking, default Pending, free if approved). If travel management needs separate services, create `On-site Institutional Presentation` and `Virtual Institutional Presentation`, both linked to same coordinator so no double bookings. Confirm buffers 30–60 minutes based on real travel; set actual working hours, days off and holiday blackouts. Set WP timezone Africa/Accra, verify Amelia and employee calendar display UTC+0. Do not create invented employee credentials or promise slots.
2. Assign actual Chairperson/coordinator employee and appropriate service. Connect approved Google Calendar through Amelia integration if supported; set busy events to block availability, pending appointments to sync, create event details with institution/service only. Check external travel and team commitments manually before confirming. If Google integration unavailable, manually maintain blocked time and review each request, not fake automated availability. Never include applicant names or personal recovery status.
3. Configure booking fields (institution, contact/role, business phone/email, venue/format, approximate audience, preferred topics and logistics). Mark required only for essential scheduling. No applicant records or health questions. Set notification templates to acknowledge pending request, confirmation, 24h reminder, cancellation/reschedule. Verify Chairperson and approved internal mailbox recipients using installed version's notification options; if additional email recipients not supported, use a monitored authorized shared inbox or approved internal forwarding of institutional-only notices. Use tested SMTP, no assumed mail delivery. Use Google Meet only if supported/approved; otherwise send meeting details privately after confirming.
4. Create WordPress page titled `HopefulWay Oxford House Presentation`, slug `hopefulway-oxfordhouse-presentation`. Insert Amelia booking block or shortcode generated by the installed plugin, filtered to the actual category/services; never guess service IDs. Preview and verify only presentation services show. Include wording: “Requests are pending until confirmed by the Chairperson. Please do not supply client names or medical details.” Publish only after testing. Link: https://koware.org/hopefulway-oxfordhouse-presentation/ (proposed until tested). If not ready, retain reply/call booking in WhatsApp kit; applicant form is separate and can launch without Amelia if the reply path works.
5. Test pending booking → coordinator calendar block → approve → reminders → cancel → reschedule; try two browsers requesting same slot and external calendar busy block. Verify time zone, buffer, correct recipient, no public client info, no clashing on-site/virtual service. Test on a mobile device. If any issue, keep page unpublished and coordinate manually. Do not advertise unverified booking links.
