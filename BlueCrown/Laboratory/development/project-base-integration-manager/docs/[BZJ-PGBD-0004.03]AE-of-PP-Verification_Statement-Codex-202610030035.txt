# 2. VERIFICATION PURPOSE

This document establishes the **controlled Architectural Engineering Verification baseline candidate** for the proposed Project Base Integration Initialization.

Its purpose is to determine which architectural propositions survive independent analysis and to establish a coherent architecture that can subsequently undergo:

```text
Architectural Engineering Challenge
        ↓
Architectural Engineering Challenge Closure
        ↓
Final Project Base Integration Initialization
```

This document is therefore neither:

* the final Project Base Integration Initialization;
* the final Project Template;
* a Project Charter;
* nor an implementation specification.

It is the controlled architectural baseline candidate from which those later artifacts may be produced.

# 5. PM PROCESS GOVERNANCE

The 49 PM processes remain the **canonical governance spine**.

They must not be renumbered merely to accommodate software-engineering activities.

For example:

```text
0004.1 Develop Project Charter
```

remains the canonical PM process identifier.

A custom engineering section must not masquerade as `0004.1`.

Likewise:

```text
9004.7 Close Project or Phase
```

remains the canonical closing process.

The project engineering workflow may attach custom artifacts and activities to these processes, but must not silently redefine the PM process identifiers.

This separation is supported by all three analyses. Copilot specifically identifies confusion between PM process IDs, artifact IDs, task IDs, lifecycle stages and baseline versions as a major architectural risk.

# 8. SUBSECTION GRAMMAR

Only one custom subsection grammar shall be authoritative.

The candidate standard is:

```text
SSSS.SS
```

where:

* `SSSS` = lifecycle/process position;
* `SS` = zero-padded custom subsection.

Therefore:

```text
0000.01
0000.02
0005.00
0005.01
```

are structurally valid.

The following shall not be used for new artifacts:

```text
0005.0
0005.01.01
```

unless a future architectural decision explicitly creates and documents a different grammar.

The existing corpus contains multiple competing forms, including `0005.00`, `0005.0`, `0005.01` and the undefined three-part `0005.01.01`. Kilo identified this as a direct automation risk.

---

# 9. SORTING AND MACHINE INTERPRETATION

The identifier architecture must not depend on prose exceptions.

The special ordering relationship surrounding:

```text
4004.4
4004.36
```

must be represented in a machine-readable registry rather than relying upon explanatory prose.

Kilo found that ordinary string sorting and the documented numeric ordering disagree at multiple positions because `4004.4` is intentionally treated as the continuous PM anchor after custom `4004.xx` activities.

### Required Control

A future identifier registry shall contain at minimum:

```text
identifier
identifier_class
pm_process
knowledge_area
lifecycle_band
sequence
display_order
status
```

Automation must sort according to this registry rather than infer lifecycle order from filenames.

# 14. AEA / AEV / AEC / AECC PROTOCOL

The four-artifact protocol is retained.

## AEA

Determines:

* requirements;
* assumptions;
* architecture;
* alternatives;
* risks;
* dependencies;
* evidence.

## AEV

Determines:

* what survives analysis;
* what is rejected;
* what is modified;
* what remains unresolved;
* what becomes baseline candidate.

## AEC

Attempts to invalidate the architecture.

It must not merely edit or improve the AEV.

## AECC

Records the disposition of every challenge.

Allowed dispositions:

```text
FIXED
ACCEPTED AS KNOWN LIMITATION
REJECTED WITH REASON
ESCALATED TO HUMAN
```

Jules explicitly defined these four closure outcomes.

---

# 15. AEC ADVERSARIAL FLOOR

An AEC shall be considered invalid if it contains no substantive architectural objection, failure condition, or falsification attempt.

At minimum, each AEC should contain:

```text
Challenge ID
Target
Assumption Under Attack
Failure Condition
Attack Method
Expected Result
Observed Result
Severity
Disposition
```

Kilo identified the absence of such a mechanical floor as a weakness because an empty "challenge" could otherwise pass the workflow.

# 28. HUMAN AUTHORITY

Human authority is mandatory for:

1. final PBI baseline approval;
2. acceptance of unresolved critical architecture risks;
3. production access;
4. secret/credential authorization;
5. critical architectural changes;
6. scope-affecting changes;
7. security exceptions;
8. final template release;
9. project charter authorization where required.

Human authority must not be represented by an indefinitely available single person.

A project authority register must include:

```text
Primary Authority
Deputy / Alternate
Delegation Conditions
Emergency Authority
Escalation Path
```

Kilo identified the single-human dependency as a critical operational weakness.

---

# 29. CONVERGENCE MODEL

Review cycles shall be bounded.

Proposed default:

```text
PASS
PASS WITH CONDITIONS
REVISION REQUIRED
BLOCKED
ESCALATE
```

Maximum ordinary revision cycles:

```text
3
```

After three unresolved cycles:

```text
Mandatory Human Escalation
```

A critical finding cannot be overridden merely because the cycle limit has been reached.

Jules independently proposed a three-cycle limit with mandatory escalation for unresolved critical findings.

---

# 30. ARCHITECTURE RESET CONDITION

A review-cycle counter must not force continuation of a fundamentally invalid architecture.

If an AEC invalidates a load-bearing architectural assumption:

```text
Current Level
      ↓
ARCHITECTURE RESET
      ↓
Return to AEA
      ↓
Reconstruct AEV
      ↓
AEC
      ↓
AECC
```

The cycle counter resets because the architecture itself has changed.

Kilo identified this as necessary to prevent iterative refinement of a fundamentally invalid premise.

# 31. TRANSITION CHALLENGE

A dedicated transition challenge shall occur after the pre-charter template architecture has been challenged and before the project proceeds into the normal PM lifecycle.

Purpose:

```text

the project about to use it?
```

This is distinct from:

* challenging the template architecture itself;
* testing implementation code;
* monitoring project execution.

Kilo identified the absence of this transition challenge as a material gap.

# 32. IMPLEMENTATION LIFECYCLE

Implementation activities shall not be artificially placed in pre-charter sections.

The controlled lifecycle remains:

```text
Pre-Charter
    ↓
Charter
    ↓
Planning
    ↓
Execution
    ↓
Monitoring & Controlling
    ↓
Closing
```

Implementation controls such as:

* code checks;
* automated testing;
* PR review;
* reliability review;
* security review;
* deployment;
* reconciliation;

belong in the execution or monitoring/control ranges appropriate to their function.

Kilo verified the existing re-sequencing of these activities and confirmed that the approach correctly moves implementation controls out of the early lifecycle.

# 33. SMALL-PROJECT PROFILE

The generic framework must support a reduced governance profile.

A one-developer project should not be forced through the entire governance burden of a large multi-subsystem project.

A future project initialization must select a recorded profile such as:

```text
LIGHT
STANDARD
FULL
```

The profile must not remove critical safety controls.

It may reduce:

* number of participating agents;
* documentation depth;
* review redundancy;
* automation;
* reporting frequency.

It must not remove required human gates for critical activities.

Kilo identified the absence of a lightweight profile as a direct threat to the requirement that the framework remain quick to implement.

# 36. SECURITY OF EVIDENCE

Evidence is itself a security surface.

Therefore:

* no secrets in prompts;
* no credentials in committed evidence;
* no raw environment dumps;
* no raw production configuration;
* no sensitive database output unless explicitly authorized;
* evidence branches should use secret scanning;
* private-by-default handling should be considered for sensitive evidence.

Kilo specifically identified agent-generated evidence as a potential credential-exposure path.
