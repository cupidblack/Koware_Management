# Recommended Buzzjuice AI Development Workflow

I reviewed the two previous workflow documents you provided, including the newer **Developer Workflow Implementation Guide** and the **production workflow trial**. The underlying direction is strong, but I would make one fundamental change:

> **Stop treating the AI systems as a sequence of assistants that exchange prompts and responses. Treat them as specialized engineering agents operating around one GitHub-controlled source of truth.**

That distinction will substantially reduce context loss, duplicated reasoning, prompt drift, and the risk of one AI unconsciously accepting another AI's incorrect assumption.

Your existing workflow already contains much of the foundation for this. The production trial specifically identified GitHub as the engineering control centre, Codex as a primary engineering system, Claude as an independent reviewer, Jules as an implementation/CI reviewer, and GitHub Actions as deterministic validation. ([GitHub][1])

The next version should formalize that into an actual **Buzzjuice AI Engineering Pipeline**.

---

# 1. The Main Problem With the Current Workflow

Your current process is essentially:

```text
You
 ↓
ChatGPT
 ↓
You
 ↓
GitHub/Copilot
 ↓
You
 ↓
ChatGPT
 ↓
You
 ↓
GitHub
 ↓
repeat
```

This works, but it has a structural weakness.

### The human becomes the message router.

You are continually doing:

* prompt interpretation
* context transfer
* response comparison
* prompt rewriting
* implementation coordination
* bug interpretation
* reviewer coordination
* state tracking

That creates several risks.

### 1.1 Context degradation

Suppose ChatGPT understands:

```text
Requirement A
Constraint B
Architecture C
Existing behaviour D
```

You send its response to Copilot.

Copilot may interpret it as:

```text
Requirement A
Constraint B
Architecture C
```

but miss D.

Then you send Copilot's response back to ChatGPT.

ChatGPT now sees:

```text
Original context
+
Copilot interpretation
```

and can accidentally begin reasoning about Copilot's assumptions as though they were facts.

After several cycles, the conversation becomes a mixture of:

* requirements
* proposed architecture
* assumptions
* implementation
* corrections
* obsolete decisions
* agent-generated assumptions.

This is **prompt drift**.

# 2. The New Core Principle

I recommend changing the workflow to:

```text
                 ┌─────────────────────┐
                 │       YOU           │
                 │ Product Owner /     │
                 │ Final Authority     │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │     CHATGPT         │
                 │ Architecture /      │
                 │ Planning / Strategy │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │      GITHUB         │
                 │ SOURCE OF TRUTH     │
                 │ Issues / Specs / PR │
                 └──────────┬──────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
          CODEX          COPILOT         JULES
        Engineering     Repository      Independent
        / execution     integration     validation
             │              │              │
             └──────────────┼──────────────┘
                            ▼
                       CLAUDE CODE
                    Adversarial Review
                            │
                            ▼
                    GitHub Actions
                    Deterministic CI
                            │
                            ▼
                    Human Review
                            │
                            ▼
                         MERGE
                            │
                            ▼
                      STAGING TEST
                            │
                            ▼
                       PRODUCTION
```

The critical difference is:

**The agents communicate primarily through the repository, issue, specification, branch, commits and PR—not through you copying one AI's answer into another AI.**

# 3. Give Each AI a Specific Job

This is probably the most important improvement.

Don't ask four AI systems to independently "help develop the feature."

Give them different responsibilities.

## Role A — ChatGPT / Codex

### Architecture + Primary Engineering

This should become the primary engineering reasoning system.

Use it for:

* requirements analysis
* architecture
* decomposition
* implementation plans
* difficult debugging
* repository-level implementation
* test design
* refactoring
* cross-system reasoning
* reviewing implementation decisions

Current Codex supports repository-level development, tests, refactoring, migrations and code review, and supports project-specific `AGENTS.md` instructions. ([OpenAI][2])

For Buzzjuice this is particularly valuable because the platform isn't a conventional single application.

You have:

```text
WordPress
BuddyBoss
WoWonder
QuickDate
WooCommerce
WooCommerce Subscriptions
AffiliateWP
MU plugins
SSO
cross-database synchronization
payment infrastructure
shared helpers
```

So the primary engineering agent needs to understand the **whole system**, not just a PHP file.

# 6. Phase 1 — Discovery

You start with the problem.

For example:

> Buzzjuice Streams payment gateway intermittently loses orders.

Don't immediately ask an AI to write code.

First create:

```text
BZJ-PGB-001
Payment Gateway Bridge Reliability Upgrade
```

Then establish:

### Problem

What is happening?

### Current behaviour

How does the existing system work?

### Desired behaviour

What should happen?

### Constraints

What must not change?

### Dependencies

What other systems are involved?

### Unknowns

What do we not yet know?

### Evidence

What code/database/logs establish the current behaviour?

The prompt should not say:

The output becomes something like:

```text
BZJ-PGB-001
Architecture Decision

BZJ-PGB-002
Implementation Specification
```

This is very close to what your existing Payment Gateway workflow already started doing.

Your previous work correctly introduced:

* evidence lock
* architecture decision
* implementation specification
* staged implementation
* scope locks
* completion gates. ([GitHub][3])

I would make that standard across **all Buzzjuice development**, not just payment work.

# 8. Phase 3 — Evidence Lock

This is particularly important for Buzzjuice.

Before implementation:

```text
AI must inspect:
    ↓
actual repository
    ↓
actual files
    ↓
actual hooks
    ↓
actual database
    ↓
actual integrations
    ↓
actual logs
```

The agent must distinguish:

```text
FACT
ASSUMPTION
INFERENCE
UNKNOWN
```

This one change will prevent a huge amount of AI-generated coding error.

For example:

```text
FACT:
wow-pgb_sync.php calls function X.

ASSUMPTION:
function X is always triggered after payment.

UNKNOWN:
whether webhook Y can arrive before X.

REQUIRED INVESTIGATION:
inspect webhook Y.
```

That is much safer than letting an AI fill the gap with a plausible explanation.

# 10. Phase 5 — Implementation

Now assign **one primary implementation agent**.

I recommend:

### Codex OR GitHub Copilot

—not both simultaneously modifying the same branch.

For example:

```text
Codex
   ↓
feature branch
   ↓
commit
   ↓
Pull Request
```

or:

```text
Copilot
   ↓
feature branch
   ↓
commit
   ↓
Pull Request
```

The choice can depend on the task.

### Codex

Best suited to:

* complex reasoning
* architecture-heavy implementation
* cross-file changes
* complicated debugging
* larger refactors
* test creation

### Copilot

Best suited to:

* repository-native work
* GitHub PR workflow
* incremental changes
* IDE assistance
* fixing review comments
* repository-aware implementation

GitHub's current agent workflow can create PRs and then have Copilot review and iterate on the work. ([GitHub Docs][4])

# 11. Do Not Have Two Agents Edit the Same Branch

This is one change I would make very strongly.

Avoid:

```text
Codex → branch
Copilot → same branch
Jules → same branch
Claude → same branch
```

Instead:

```text
              TASK
                │
                ▼
        implementation branch
                │
          ┌─────┴─────┐
          ▼           ▼
       Codex       Copilot
       option A    option B
```

For competing implementations, let them produce separate branches.

Then compare.

For normal work:

```text
Primary agent
     ↓
single implementation
     ↓
reviewers
```

# 12. Jules Should Become the Independent Verification Agent

Your previous workflow was already moving toward this.

The trial explicitly defined Jules as an independent reviewer checking implementation correctness, CI/reliability and edge cases. ([GitHub][1])

That is a good role.

Jules can work asynchronously against GitHub repositories, execute tasks, run tests and open PRs; Google also provides a Jules CLI and API for integrating asynchronous coding work into development workflows. ([Google Developers Blog][5])

Therefore:

### Jules should NOT receive:

> "Here is Codex's answer. Is it correct?"

Instead:

> "Here is the approved specification. Independently inspect the implementation and determine whether it satisfies the specification."

That distinction matters enormously.

The reviewer should be blind to the implementer's reasoning where practical.

# 13. Claude Code Should Be the Adversarial Reviewer

This is another part of your existing workflow that I would preserve.

Your trial correctly separated:

```text
Jules
=
implementation correctness

Claude
=
adversarial design/security review
```

([GitHub][1])

That's excellent.

Claude should attack the implementation.

For example:

### Payment system

Ask Claude:

```text
Can this lose an order?

Can this create two orders?

Can this process one payment twice?

Can a replay succeed?

Can the browser manipulate the amount?

Can a timeout produce an inconsistent state?

Can two requests race?

Can the webhook arrive first?

Can the webhook arrive twice?

Can subscription activation happen twice?

Can AffiliateWP commission happen twice?
```

### Relationship sync

Ask:

```text
Can the two systems enter a loop?

Can a duplicate event produce duplicate friendship?

Can concurrent requests produce inconsistent state?

Can an origin marker be bypassed?

Can blocked users become connected?

Can an event be replayed?
```

This is much more valuable than having Claude simply say:

> "The code looks good."

AI opinions should never be the final quality gate.

The hierarchy should be:

```text

        │         │         │
        └─────────┼─────────┘
                  │

                  │
```

The actual code must pass deterministic tests.

Keep this.

# 23. Separate Facts From AI Opinions

I recommend a formal notation:

```text

ASSUMPTION
DECISION
PROPOSAL

RISK

```

For example:

```text

wow-pgb_sync.php currently handles subscription activation.
```

# 26. Add a "Challenge Before Build" Gate

For complicated work:

```text
Architecture proposal
        ↓
Challenge
        ↓
Architecture revision
        ↓
Implementation
```

For example:

### ChatGPT proposes:

> Use a payment-intent table.

### Claude challenges:

> What happens if the database insert succeeds but the redirect fails?

### Jules challenges:

> What happens if two browser requests create the same intent?

### ChatGPT revises:

> Add unique idempotency key and durable transaction state.

Then implementation begins.

This is considerably cheaper than discovering those issues after production code exists.

| **GitHub Copilot**  | Repository-native implementation + PR workflow + review     |          No direct protected branch |
| **Google Jules**    | Independent implementation validation / tests / reliability |            No during initial review |
| **Claude Code**     | Adversarial architecture/security/legacy-code review        |            No during initial review |

| **You**             | Architecture approval, scope, risk, merge, deployment       |                                 Yes |
| **Production**      | Runtime environment                                         |         Never directly edited by AI |

That gives each system a reason to exist.

you do:

```text
18. Monitor.
```

# 41. The Most Important Change to Your Existing Workflow

If I had to reduce the entire redesign to one sentence:

> **Move the communication bus from the human/AI conversation to GitHub.**

ChatGPT remains extremely important—but primarily as your **architect, strategist, technical co-founder and high-level reasoning partner**.

GitHub becomes the **system of record**.

Codex/Copilot become **builders**.

Jules becomes an **independent verifier**.

Claude becomes the **adversarial challenger**.

GitHub Actions becomes the **objective judge**.

You remain the **decision-maker and release authority**.

That gives you a genuine multi-agent engineering system rather than four AI assistants being manually chained together.
