# 4. VERIFICATION METHOD

Verification is divided into five evidence classes.

| Evidence Class                     | Meaning                                                                             |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| `E1 — Direct Artifact Evidence`    | A specific source document, file, section, record or repository state was inspected |
| `E2 — Structural Verification`     | Machine-checkable structure, numbering, graph or schema was validated               |
| `E3 — Agent Finding`               | An independent collaborating-agent observation                                      |
| `E4 — Architectural Decision`      | A controlled decision adopted after reconciliation                                  |
| `E5 — Implementation Verification` | A control has been demonstrated in the actual repository/toolchain                  |

Agent agreement is **not itself evidence**.

Agreement is treated as a confidence signal only.

A claim cannot be marked `VERIFIED` solely because two or more agents agree.

## FVR-003 — Identifier grammar and machine interpretation

**Source:** GitHub Copilot and Kilo
**Severity:** HIGH

The verification response identified ambiguity between:

* `0005.0`
* `0005.00`
* `0005.01`
* `4004.4`
* `4004.36`
* `0005.01.01`

and noted that a future registry was not sufficiently defined.

### Resolution

Two identifier domains are now formally separated.

### A. Canonical PM identifiers

Canonical inherited PM identifiers remain authoritative and are not renumbered.

Example:

`0004.1`

Their meaning is determined by the canonical PM registry.

They must **not** be interpreted by generic decimal parsing.

### B. Custom workflow identifiers

New custom workflow section identifiers use:

`SSSS.SS`

where:

* `SSSS` = four-digit workflow sequence;
* `SS` = two-digit subsection.

Example:

`0000.01`

Canonical PBI identifiers are therefore:

```text
0000.01
0000.02
0000.03
0000.04
0000.05
0000.06
0000.07
0000.08
0000.09
```

### Invalid for new custom workflow use

```text
0005.0
0005.01.01
```

### Legacy identifiers

Existing legacy identifiers are not silently renumbered.

They remain in the historical record and must be cross-referenced through the migration/crosswalk registry.

### `4004.4` and `4004.36`

These are interpreted according to the canonical PM registry, not the custom `SSSS.SS` grammar.

Ordering is determined by an explicit `sequence_index`, not string sorting.

**Disposition:** FIXED
**Verification state:** CONTROL-SPECIFIED / IMPLEMENTATION-UNVERIFIED

# 11. FVR-007 — Task Packet immutability

**Source:** GitHub Copilot
**Severity:** HIGH

The previous Task Packet concept was sound but lacked precise creation, amendment, status and supersession rules.

### Resolution

A Task Packet is an immutable work authorization after dispatch.

### Lifecycle

```text
DRAFT
  ↓
READY_FOR_REVIEW
  ↓
APPROVED
  ↓
DISPATCHED
  ↓
IN_PROGRESS
  ↓
SUBMITTED
  ↓
VERIFIED
  ↓
CLOSED
```

Alternative terminal states:

```text
REJECTED
SUPERSEDED
CANCELLED
ESCALATED
```

### Amendment rule

Before dispatch:

* Task Packet may be amended;
* revision number increments.

After dispatch:

* original packet becomes immutable;
* material change requires a new superseding packet.

### Required fields

```text
artifact_id

scope

stop_condition
supersedes
superseded_by
status
revision
```

### Uniqueness

`task_id` must be globally unique across the project and collision-resistant across projects.

# 13. FVR-009 — Operational friction and failure handling

**Source:** GitHub Copilot
**Severity:** MEDIUM/HIGH

The previous design did not explicitly define responses to project identity drift, stale references, branch conflicts, approval delays, prompt drift and unresolved disagreements.

### Resolution — Operational Failure Protocol

| Failure                             | Required response                                                  |
| ----------------------------------- | ------------------------------------------------------------------ |
| Project ID change                   | Freeze affected packets; create change record                      |
| Stale artifact                      | Mark stale; require superseding artifact                           |
| Missing evidence                    | `EVIDENCE-PENDING`; no verification claim                          |
| Branch conflict                     | Pause merge; preserve source branches; resolve through task owner  |
| AGENTS conflict                     | Apply deterministic precedence                                     |
| Prompt drift                        | Compare against approved prompt hash/version                       |
| Human approval delay                | Escalate through authority register; do not infer approval         |
| Agent unavailable                   | Reassign through Task Packet; preserve original assignment history |
| Unresolved disagreement             | Record disagreement; escalate according to severity                |
| Broken reference                    | Mark evidence invalid until corrected                              |
| Duplicate ID                        | Reject artifact; repair through registry                           |
| Secret exposure                     | Stop processing; security incident procedure                       |
| Production contamination            | Freeze branch and perform repository audit                         |
| Invalidated architecture assumption | Trigger Architecture Reset                                         |

# 14. ARCHITECTURE RESET CONDITION

A special reset condition is added.

An **Architecture Reset** is mandatory when a load-bearing assumption becomes demonstrably false.

Examples:

* source-of-truth repository is incorrect;
* required repository cannot support the proposed workflow;
* security boundary is invalid;
* identifier model cannot represent the required lifecycle;
* human authority model is unavailable;
* critical dependency invalidates the DAG;
* production architecture contradicts the governing project boundary.

Architecture Reset is not treated as ordinary iterative refinement.

It creates a new baseline lineage:

```text
Current Baseline
      ↓
Invalidated Assumption
      ↓
Architecture Reset Record
      ↓
New AEA
      ↓
New AEV
      ↓
New AEC
      ↓
New AECC
      ↓
Human Gate
      ↓
New Baseline
```

# 15. AEA / AEV / AEC / AECC PROTOCOL

The four-artifact protocol is retained.

## AEA — Architectural Engineering Analysis

Independent analysis of the assigned artifact.

AEA does not approve.

## AEV — Architectural Engineering Verification

Controlled synthesis of:

* requirements;
* AEA findings;
* evidence;
* decisions;
* dispositions.

AEV is not merely a summary.

## AEC — Architectural Engineering Challenge

Adversarial attempt to falsify the AEV architecture.

AEC must attack assumptions rather than merely proofread the AEV.

## AECC — Architectural Engineering Challenge Closure

Every challenge receives one of:

```text
FIXED
ACCEPTED AS KNOWN LIMITATION
REJECTED WITH REASON
ESCALATED TO HUMAN
```

The closure record must reference the original challenge.

# 16. INDEPENDENCE MODEL

Agent independence has two separate dimensions:

### Analysis lens

The perspective from which an agent examines an artifact.

Examples:

* architecture;
* implementation;
* security;
* operations;
* quality.

### Review independence

Whether the reviewer had authorship responsibility for the artifact being challenged.

These must not be conflated.

An agent can have a different analysis lens while still lacking review independence.

### Minimum challenge rule

The principal AEC challenger must not be the sole author of the artifact being challenged.

Where the available agent pool prevents true independence, the limitation must be recorded and the challenge must be supplemented by:

* another agent;
* an external reviewer;
* or the Human Authority.

The current verification cycle must therefore record actual reviewer independence rather than assuming it.

# 26. EMERGENCY CHANGE CONTROL

Emergency changes may bypass ordinary sequencing only where delay creates a greater operational or security risk.

An emergency change must still create:

1. emergency change record;
2. responsible authority;
3. affected artifact;
4. reason;
5. immediate risk assessment;
6. implementation record;
7. post-hoc AEA/verification;
8. post-hoc challenge where materially architectural;
9. Decision Ledger entry.

Emergency processing is therefore an exception to sequencing, not an exemption from governance.

Required controls include:

* no-raw-secret evidence rule;
* redaction;
* least-privilege repository access;

A suspected secret exposure is an automatic security escalation.
